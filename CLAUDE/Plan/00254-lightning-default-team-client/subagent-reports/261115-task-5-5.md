## Which reader was used

I wrote no YAML parser. The checker imports the existing Python readers:

- `helpers.agent_bus.declare.parse`/`entry_of` for the `agent_bus_element_teams` entries, and
  `parse` for the `agent_bus_teams` states. This is the line reader ccy-teams uses.
- `helpers.agent_bus.element.parse_profiles` validates each entry with its client already
  resolved, the same as the play's check step. `element.check_user` is the user guard for
  `~/.config/pingbus/`, including its consent-record exception.
- `agent_bus_matrix_client` is a top-level scalar that no reader exposes. It is read line by
  line in declare's subset: one value, a tag refused, set twice means COULD NOT ESTABLISH.
- `helpers.pingbus.config.MATRIX_CLIENTS.client("Lightning")` gives the app id and data folder.

The resolution is the play's: the team's `client:`, else `agent_bus_matrix_client`, else
`element`, and a team declared absent in `agent_bus_teams` is dropped. An https team is one
whose entry has a `ca_file` (url = its base_url), or whose
`/var/lib/teamchat-status/teams/<team>/approved.json` names an https url. This is
`tasks/https-team-ca.yml`'s rule. A vaulted value or an unreadable approval means COULD NOT
ESTABLISH.

## What each check does

For each lightning team:

1. Under `~/.var/app/org.lightning_matrix.Lightning/`, `teams/`, `teams/<team>/` and its
   `data`, `config` and `cache` folders are each checked by lstat. Each must be a real directory
   owned by this user with mode 0700.
2. `teams/<team>/config/MatrixClient/matrix-client.conf` must be a regular file with mode 0600.
   Its `[homeserver] url` is read with configparser and must equal the base_url. Lightning's
   canonical rewrite is **also accepted**, but only when it has the same scheme, host, port and
   path after normalising (lower-case host, default port dropped, trailing slash dropped). The
   PASS line says which of the two matched. A url pointing at a different host (for example a
   delegated one) is a FAIL. That rule is my reading of "canonical", and the first host run with
   a signed-in instance should confirm it.
3. `~/.local/share/applications/agent-bus-<team>-lightning.desktop` must have mode 0644 and
   exactly one `Exec=` line, equal to `lightning.go` `execLine`. The test
   `test_exec_line_is_the_one_the_go_command_writes` pins the expected line.
4. No `agent-bus-<team>-element.desktop` may exist.
5. For an https team: `teamchat-ca/<team>.pem` must be a regular file, mode 0644, holding a PEM
   certificate. `~/.local/libexec/tls-trust-check/tls-trust-check` (where
   `tasks/lightning-team-ca.yml` installs it) must exist and be executable. The bash then runs
   `flatpak run --command=env --filesystem=<check dir>:ro org.lightning_matrix.Lightning SSL_CERT_FILE=/etc/ssl/certs/ca-certificates.crt SSL_CERT_DIR=<CA dir> <check> --url <url>`,
   the play's form. It sets `XDG_RUNTIME_DIR` only if it is unset.

For each element team: no `agent-bus-<team>-lightning.desktop` may exist.

NOT ESTABLISHABLE, printed for the owner: each team's window opens on its own login page with
the homeserver filled in, signing in works, and two teams open as two windows.

Exit codes:

- 0: every check passed.
- 1: a FAIL (naming the team, the file and the cause), or a refusal: root, a user holding
  pingbus bundles, or an entry the play would refuse.
- 2: COULD NOT ESTABLISH: the host vars or an approval could not be read, or **no team opens in
  Lightning**. Until a team is set to lightning, the host run will exit 2.
- 64: usage error.

## Decision: a plan-script entry, not a plan-folder entry

I added a script entry after the play rather than converting the play entry to the plan-folder
form. Two reasons:

- The folder form would also run `triage.bash`, the Task 3.1 probe that opens Lightning windows.
- This plan has no `deploy.bash`, and the play is shared and run by ccy-teams, so it stays a
  `playbooks/` entry.

The header allows a script named `*acceptance*.bash` to exit 2.
