How the rawpy-dependent paths are exercised without rawpy or an ARW fixture:
a `fake_rawpy` fixture installs a `types.ModuleType("rawpy")` into
`sys.modules` via `monkeypatch.setitem`. Its `imread` returns a context
manager exposing `raw_image_visible`, `raw_colors_visible`, `white_level`,
`black_level_per_channel` and `raw_pattern` built from numpy RGGB mosaics, and
raises a `LibRawError` for any filename not registered, which is how a corrupt
ARW is simulated. Black levels are the non-identical tuple (512, 514, 512, 514)
so H1 stays honoured. The real-ARW run remains the Phase 2 host task and every
docstring on those tests says so.

Other choices worth knowing when resuming:

- JPG paths write real 16x16 JPEGs with Pillow (quality 100, no subsampling) and skip via `pytest.importorskip` if Pillow is absent.
- CLI tests call `main()` in-process with `capsys` and assert directory listings before and after. The `run_main` helper prepends `--jobs 1` because the default is `nproc`: under Python 3.11's fork start method the pool happened to inherit the fake module and the conftest-loaded `clip_scan`, but under 3.14's forkserver default a worker would see neither. The pool is tested on its own terms instead.
- The two `--jobs 2` tests run the deployable script as a subprocess under `sys.executable` over four Pillow JPGs, so workers import the script exactly as production does; the stderr header `2 workers` proves the pool branch ran.
- `--jobs 1` and the single-group case monkeypatch `ProcessPoolExecutor` to raise if constructed.
- The `--json` test checks every field and type of the DECISIONS.md schema and pins the only additions to `analysis_source` plus the two JPG cutoffs in `config`, which PLAN.md already documents.
- Collision behaviour as implemented and now locked by test: the pre-existing target and the source ARW stay untouched, the sibling JPG without a collision is still renamed, the run reports `collisions: 1` and exits 0.
