## Why a --check re-run is not the idempotency oracle

The brief allowed either a `--check` re-run in acceptance.bash or a stated reason for
putting it in deploy.bash. Reading the module source rather than assuming, it is **both**:

- `get_url` in check mode issues a **HEAD** (`get_url.py:633`), then at lines 679-683
  compares `sha1(tmpsrc)` — the *empty* HEAD body — against `sha1(dest)`. Unless the server
  answers 304 it reports `changed` for a byte-identical file.
- `Remove The Stale Google Signing Key` is a `command:`, which check mode skips, so a dry
  run cannot tell "the loop was empty" from "it did not run". The play states this itself at
  `play-browsers.yml:148`.

Those are exactly the two tasks Task 4.2 is about. Resolution:

- deploy.bash leg 2 is the real second run.
- acceptance.bash check 7 still performs the `--check` run — it IS sound for `rpm_key`, the
  `copy`, `yum_repository` and `dnf` tasks, and it captures the real stdout of the decision
  task, which carries `check_mode: false` and therefore executes for real.
- Checks 3 and 5 judge the two unsound tasks by the same predicates the real tasks use.

All three scripts state this reasoning in their own text.

## Not establishable by script, and other flags

- **Task 4.3b (close issue #45)** is a `gh` action, not a check. The gate's ACCEPTED message
  says so explicitly rather than pretending to cover it.
- **dnf query-format tags could not be confirmed.** This container has no `dnf` and no
  `rpm`, so `%{repoid} %{location}` is unverified against dnf5. Check 6 degrades to
  `cannot` (exit 2) printing dnf's raw answer if the format is not what it expects, and
  distinguishes that from the real finding (dnf genuinely not offering the package from
  `google-chrome`, which is a FAIL). It will not produce a wrong verdict, but the first host
  run may need one iteration there.
- **Check 6 downloads the whole Chrome package.** `dnf download` was avoided deliberately:
  it comes from `dnf5-plugins`, which nothing in this repo declares, and adding it would
  mean editing a playbook outside the plan folder. The fetch uses `urllib`, and the file is
  deleted once `rpm --checksig` has run.
- **Check 7 needs sudo** — the play uses `become` even under `--check`. In gather mode an
  unprimed sudo is a warning and check 7 then reports that it could not establish its fact.
- The scripts are **untracked and uncommitted**. Other agents are modifying this checkout
  concurrently (`_planlib.inc.bash` was bumped to 1.3.0 mid-session by another agent, not by
  this one), so sequencing the commit was left to the coordinator. Nothing outside the plan
  folder was edited.
