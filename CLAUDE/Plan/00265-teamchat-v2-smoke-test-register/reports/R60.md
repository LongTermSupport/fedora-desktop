## The bound on the wait

The add waits `Waits.Apply` (10 s), the wait every add already had. It is not lengthened. If the
team has not answered by then, the add prints "not joined" and the reason, then puts the seat
back. Running the same command again retries the join. teamsync marks a team down only once a
failure streak is 15 s old, and a connection to a homeserver that drops packets fails only at the
member transport's dial limit. So in the live case the add ends on "the session's link has had no
answer from team X's homeserver yet". The "cannot reach" wording, with its cause, appears once
the team is marked down: in `session list`, in `teamchat status`, and in an add made after that.
Marking a team that never answered as down at once was considered and not done. It would change
SY8's down timing, which the wiring tests' wait is derived from
(`TestAJitterPutsTheDownMarkAfterTheFifthWait`), and it would not help the add, because the add's
10 s ends first.

## Defence Before Fix

**The class:** a remote join reported done on local proof only (a lock held, a generation
applied, a handle read).

**Can a go/analysis rule express it? Confirmed that it cannot, in general.** An analyzer sees the
syntax and types of code. Whether a value is proof that a remote party answered is a fact about
what the value means, and no syntax marks it. A rule like "a function that reads `state.Report`
and returns a joined/applied bool must read `last_sync_ok_ms` and `down`" would be keyed to one
type and one function's naming. It would catch this one instance and nothing else of the class
(v1's add, a board's state, a future verb), so it would be a unit test dressed as a rule.

**What was added instead: two reflection tests that close the data path.**

- `engine` `TestEveryHealthFieldReachesTheReportOrSaysWhyNot` reflects over every field of
  `team.Health`. Each field must either reach the keeper's report (a pair of healths whose sent
  states differ) or be named with why not. A new Health field fails until it is placed.
- `keeper` `TestEveryKeyOfTheLinksStateReachesTheReport` checks that every JSON key of
  `wire.State` reaches report.json under the same key and value.

So a reach fact that status shows cannot silently stop short of what the host reads. The
judgement itself is held by the `Applied` test.

## Compatibility

report.json is decoded strictly on both sides, and the two are updated at different times: the
play rebuilds the host's `ccy-teams` at once. A running session keeps writing with the keeper
of the image it started on until it is relaunched. So the new reader takes a report with no
`down`, as a keeper built before R60 writes it, as `down: null` (`state.withDownNull`,
coordinator's review). Without this, every v2 session running on the old image would have its
report refused by the updated host, and `session add`, `remove` and `list` would fail for it
until it restarted.

The reverse is not covered: an old host reading a new keeper's report refuses the unknown
`down`. The play updates the host before any image built from this commit exists, so that order
does not arise. The container version is bumped so the image is rebuilt with the new keeper.
