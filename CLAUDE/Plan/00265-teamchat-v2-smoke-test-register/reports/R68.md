# R68: a coordinator's `reply` to an older questions-room post is refused "no item in main"

Fixed on `v2-smoke`, batch 20 (`f59504a18`).

## What was seen

Reported by a coordinator seat (team A), unchecked by us: after a relaunch (the seat resumed its
recorded conversation), `teamchat reply '<id>'` on two older owner posts in the questions room
ended exit 23, "team <t> has no item <id> in main". The seat had to ask the owner afresh with
`ask-human`. Earlier the same day it saw the same refusal on a questions-room id and fell back to
`teamchat thread Q<n> --note`. The documented procedure (the `teamchat:coordinator` skill, the
teamchat skill) answers a person with `reply`, so the documented path broke exactly when a
coordinator returns to unanswered posts.

## Cause (read in code, confirmed by a failing test)

`reply` (`member/engine/reply.go`) takes the item's room from the seat's store (`repliedTo`:
the ledger, then pending). Only for an id the store holds does it see `room: questions` and go to
`replyQuestions`. For any other id it called `fetched`, which re-fetched the id **from main
only** (`st.tm.Refetch(ctx, proto.PurposeMain, id)`). A questions-room event is not in main, the
homeserver answers 404, and `fetchErr` turns that into `msgNoSuchItem`: exactly the reported text.

Of the two shapes the coordinator suggested:

- **(a) the id is in questions and reply looks only in main: yes, this is the defect.** It holds
  for every questions-room id the store does not hold, relaunch or not.
- **(b) reply sees only what this launch delivered: no.** The store (ledger and pending) is the
  persisted `store.json`, not per launch; a relaunch keeps it, and `returnEarlierRun` moves an
  earlier run's unproven deliveries back to pending, which `storedItem` still finds. A post the
  store does hold is answered correctly, before and after this fix
  (`TestReplyToATopLevelAttachedPostLinksBack` and its siblings).

So the posts the coordinator answered were not in its store. Why they were not is **unchecked**
(no access to the seat's `store.json`). R64's evidence points the same way: after the 18:48Z
relaunch the link re-judged 45 already-shown owner posts in questions, which happens only to ids
neither pending nor in the ledger (`storewrite.go`'s seen lookup). Candidates, none confirmed:
the ledger keeps the last 1024 delivered items of all rooms (`capLedger`), and a coordinator
receives every main item too; an id taken from `teamchat questions` or `history --room questions` (which list posts the seat was never delivered, a predecessor's or ones made before
its join, OW4) is never in the store. The fix does not depend on which: whatever is missing from
the store is now found on the homeserver.

## Spec

The code departed from the spec. SPEC-n3f QR1 (Plan 00209): "An id the ledger does not know is
looked up on the homeserver in main (n3d's lookup) and, only for the coordinator with the
questions room ready, in questions; a member that is not the coordinator never asks questions
(its 403 would read as 22), so for it an id main does not have is 23 `not-found`." The questions
half of that lookup was never built; `verify` has the same fallback (R10) and `reply` did not.
QR1's test list names only the worker's half ("a worker's `reply` to an id only in questions: 23,
no request to questions"), which is why the coordinator's half went untested.

## Fix

- `fetched`: when main answers 404 and this member is the coordinator of a team whose roster
  names a questions room (`sendTeam.coordinatesQuestions`), the id is fetched from questions
  (`fetchedQuestions`). Found, the reply goes to `replyQuestions` with the fetched post, so it is
  not fetched a third time (`replied.post`, `questionsPost`); its class, edit and index checks are
  unchanged. Not found there either: 23, "team <t> has no item <id> in main or questions". Any
  other questions-room failure is `fetchErr`'s (20 for no answer).
- A worker never fetches from questions: an id main does not have stays 23 naming main.
- "Questions room ready" is read as "the verified roster names it"; a room the coordinator has
  not joined answers 404/403, which reads as not found, as before.

## Tests (`member/engine/questionsverbs_test.go`)

The engine's fake team answered `Refetch` from every room alike, so no test could see which
room was read. It now records each fetch's room (`refetchedFrom`) and can hold an id in one room
alone (`heldIn`), answering the homeserver's 404 from the others.

- `TestR68ACoordinatorsReplyFindsAQuestionsPostItsLedgerLacks`: a coordinator with an empty
  ledger replies to an owner post attached to Q1, held in questions alone. **Red** on the old
  code: `reply = team ops has no item $…502 in main`. **Green**: the answer is in Q1's thread,
  replying to the post, with its link-back; fetched from main then questions, once each.
- `TestR68AnIDInNeitherRoomNamesBoth`: **red** (`…in main`, and a questions-room outage read as
  23); **green**: 23 naming both rooms, and 20 when questions does not answer.
- `TestR68AWorkersReplyNeverAsksQuestions`: green before and after (QR1's worker half): 23, one
  fetch, from main.

## Defence Before Fix

**The class:** an event id whose room is not known, looked up in one fixed room, so an id in a
room the lookup does not name reads as "not there". Sweep of every place teamchat fetches an
event by id (`Refetch`, `GetEvent`, `Verify`) in `src-go/internal/teamchat`:

| Site                                                                      | Verdict                                                                                     |
| ------------------------------------------------------------------------- | ------------------------------------------------------------------------------------------- |
| `engine/reply.go` `fetched` (main only)                                   | **Instance, fixed** (this report).                                                          |
| `teamsync/verbs.go` `verify` (`teamchat verify`)                          | Defended: main, then questions when the roster names it (R10).                              |
| `engine/recv.go` refetch of a restored item                               | Not an instance: the room is the stored item's own (`c.room`).                              |
| `engine/questionsverbs.go` `replyQuestions` (questions)                   | Not an instance: reached only once the room is known to be questions.                       |
| `teamsync/questions_compose.go` (questions verbs' named posts)            | Not an instance: the verb's id is a questions post by definition; refused naming that room. |
| `teamsync/verbs.go` `questionOf`, `session.go` `resolveInput` (relations) | Not instances: a relation is read in the event's own room.                                  |

One instance, now fixed.

**Can a go/analysis rule express it?** No rule is built. The fixed and the correct sites have the
same shape: a `Refetch` or `GetEvent` with a room constant (`replyQuestions` passes
`PurposeQuestions` exactly as `fetched` passed `PurposeMain`). What makes one wrong is whether
the room is known at that point, which is data flow from the store, not syntax. A rule flagging
`Refetch(ctx, proto.PurposeMain, …)` would match only the line just fixed. The guard is the
tests above and the fake that now keeps rooms; the second instance of "a test fake that keeps
fewer rooms than the code uses" is recorded in [GoProjectRules.md](../../../GoProjectRules.md)
under that class (no rule, held by fakes that keep the room). `link`'s fake `Refetch` still
takes no room; no link test asks which room was read.
