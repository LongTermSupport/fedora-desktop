# U7: R14, presence proves nothing

Branch `v2-smoke-u7-presence`, based on `v2-smoke`.

## Cause

`teamchat status` never asked anyone about presence. The member record was built in
`src-go/internal/teamchat/member/engine/status.go` (`memberRecords`) as:

```go
// Presence is not tracked here: only this member is known to be present.
... Present: id == v.userID
```

So `present` was `true` for the seat itself and `false` for every other member, always,
whatever they were doing. No code path could set it true for another member. Evidence:

- `git grep 'Present'` over `src-go/internal/teamchat`: `records.Member.Present` is assigned in
  that one place only.
- The design asks for more. Plan 00209 `DESIGN-v2-A-protocol.md` 6.6 says `status` shows
  Matrix presence, labelled display and not liveness. `DESIGN-v2-B-member.md` 2.6 step 09 says
  the link's long-poll sync is the only `/sync` a member makes, so it is what marks the member
  `online`. The link sets `offline` at a clean end, and the server's timers mark a dead member
  `unavailable` and then `offline` (C 3.2.4: 120 s and 60 s, rendered by
  `host/render.go`).
- The client could write presence but not read it. `matrix` had `SetPresence` (M50) and no
  read. The sync response parser drops the top-level `presence` section, although the member
  filter (`proto/filter.go`) asks for it.
- The homeserver is not at fault. Host check HC-A1 (Plan 00209 `DONE-n0-n1.md`, the
  `tuwunel`-tagged `presenceCycle`) recorded Tuwunel 1.9.4 serving presence with federation
  off: a default sync marks the member online, a PUT of offline sets it, and the timers move
  a stopped member to unavailable and then offline. That test reads presence by
  `GET /presence/{u}/status`. The team config already sets both timers and does not turn
  presence off. **No IaC or play change is needed.**

## Class (Defence Before Fix)

The class is "an output-contract field filled from a placeholder instead of its source": here,
a self-comparison standing in for a reading the code never made. No analyzer can tell a
placeholder from a real derivation. A detector for this one shape (a record bool assigned only
from `x == self`) would catch this instance and nothing else, so this is fixed conventionally.

I swept `member/` by hand for the same shape. I searched for placeholder comments ("not
tracked", "until then", "always", "stub") and read every `records.*` field assignment in the
engine. `TeamCounts.SeenTwice` has a stale comment ("until then it is 0"), but `proof.go` now
sets it, so it is not an instance. No other instance was found.

## Fix

- **`matrix.Client.Presence(ctx, user) (presence, found, err)`** (new SPEC-matrix **M54**):
  - It sends `GET /presence/{u}/status`, a direct read that touches no presence.
  - An answer that is not `online`, `offline` or `unavailable` is malformed.
  - A 404 `M_NOT_FOUND` gives `found=false`. Any other 404 is `ErrNotFound`.
- **`fakehs`** answers the GET from the presence it already keeps (M51), with a 404 `M_NOT_FOUND`
  when none was set.
- **The `team.Notices` interface** gains `Presence`, implemented in `teamsync` on the team's
  client.
- **`status`** (engine):
  - For each verified team, it reads the presence of every agent in the roster, this seat
    included. It does this off the state goroutine, under one 5 s bound per team.
  - Humans are not asked.
  - A read that fails is logged and shows as `unknown`.
- **`records.Member`** gains `presence`, which is `online`, `unavailable`, `offline` or
  `unknown`. `present` is now exactly `presence == online`. The field names the source honestly:
  it is Matrix presence, which only the link's live sync keeps `online`.
- **Docs:**
  - SPEC-matrix M44 no longer says the client has no presence read, and M54 is added.
  - DESIGN-B's example member record shows `presence`.

What the field means: `online` means the member's link synced within the idle timer, so the
link is connected and long-polling. After a crash, it lags by at most 120 s (then
`unavailable`, then `offline` 60 s later). A clean end shows `offline` at once.

## Live proof needed

There is nothing to deploy on the host apart from the new `teamchat` binary that the next kit
or image build carries. No play changes. Once seats of one team run a build that contains this
branch:

1. On seat A, while seat B is running and answering, run `teamchat status --team <team>`.
   - **Accept:** B's `member` record shows `"presence":"online","present":true`, and A's own
     record shows the same.
2. End seat B cleanly. Within a few seconds, on A, run `teamchat status --team <team>`.
   - **Accept:** B shows `"presence":"offline","present":false`.
3. Kill seat B's link with no clean end (for example `kill -9` the `teamchat run` process).
   On A, run `status` at about 30 s, about 150 s and about 200 s.
   - **Accept:** B shows `online` at about 30 s, `unavailable` by about 150 s, and `offline`
     by about 200 s.
4. Optionally, run the HC-A1 regression against the pinned Tuwunel:
   `FAKEHS_TUWUNEL_BIN=<tuwunel> go test -race -tags tuwunel -run Tuwunel ./internal/teamchat/matrix/`.
   - **Accept:** it passes. It now exercises `Client.Presence`.

## NOT proven

- Nothing has been run against a live team or against real Tuwunel in this unit.
- The GET of an account whose presence was never set is modelled as the Matrix specification's
  404 `M_NOT_FOUND`. HC-A1 did not record this case. If Tuwunel answers differently, `status`
  shows `unknown` with a logged error, never a false `present`.
- Tuwunel may also refuse to show presence to an account that shares no room with the member.
  Members share main, so this should not arise.
