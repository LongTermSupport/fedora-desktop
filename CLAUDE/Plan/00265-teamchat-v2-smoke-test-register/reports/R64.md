# R64: a link restart re-judges the questions room and rate-drops the owner's posts

Batch 13, on v2-smoke. ccy 3.124.61, container 2.84.83 (`member/teamsync` is an image source).

- Fix: `544ebda3d` (code, tests, versions, changelog).
- This report and the register row: the commit after it.

## The cause

Every event a room's read hands to `judgeRoom` is judged against the answer's one receive flood
window (`Flood: &j.flood`, `teamsync/session.go:869` before the fix), whose times are the
judging time (`NowMs: j.now`), not the sending time. The questions room is read again from its
start on a build (`builder.go:96-103`, by design), and `qtake` skips an event the floor covers
only when its verdict is Deliver (`questions.go:579`). So the replayed human posts filled one
sender's window within one minute; past `recv_per_sender_minute` (60) each was judged Drop
`rate`, taken, counted in `dropped_by` and logged. A NEW post past the floor in the same
burst was dropped the same way, and the questions floor was raised past it
(`questions.go:588-592`), so it was never fetched again.

## The fix

An event that is history this link reads again is judged against a window of its own, which is
thrown away, so it never counts toward the flood window a new post is admitted by. Its verdict
is otherwise unchanged, so the fold (`idx.Feed`, `Attach`) and the floor skip work as before.

- `teamsync/session.go:875-881` (`judgeRoom`): for an event `rj.replayed` names, the judge's
  `Flood` is a fresh `proto.Window`.
- `teamsync/session.go:804-814` (`roomJudge`): the new field `replayed func(ts, id) bool`, nil
  for none.
- Questions room: `replayed` is the room's floor, `Covers` (`questions.go:533`, `qjudge`;
  `builder.go:316`, `buildPage`).
- Main room: `resume` builds `replayed` from the marker floor and the restored test
  (`session.go:260-262`), carried on `answer.replayed` (`session.go:537`) into `judgeAll`
  (`session.go:581, 776-779`).

Humans are not exempted from the limit: a live burst past 60 a minute is still dropped `rate`
(`TestQS6APostDroppedRateIsStillAttached` still passes, unchanged).

## Main room

The same order exists in main, in one case only. With a stored position of the roster's epoch,
main resumes from its token and reads nothing again (`session.go:186-187`). Without one,
`resume` reads main backwards and `cut` drops what the marker covers (`session.go:356`), but
KEEPS every event after the seat's release time, even one the marker covers
(`bd.hasReleased && ts > bd.released`), and `judgeAll` takes every kept event with no floor
check (`session.go:788-797`). A seat taken after a release (`seat/take.go:332-338` sets
`ReleasedMS`) therefore replays main's history between the release and the marker, judged
against the live flood window. Fixed the same way: `replayed` is the marker floor's `Covers` or
the restored test.

## Defence Before Fix

The class is "a flood limit applied to replayed history". A go/analysis rule cannot express it:
whether an event is history is a fact of the data at run time (the floor, the marker, the
release time), not of the code's shape. Every judge call already goes through one `Judge` with
a `Flood` field, and nothing syntactic distinguishes a call over replayed events from one over
live ones. The tests above are the guard: each read path that replays (the build, main's
resume) has a test with more replayed posts than the limit and a new post after them.

## Human exemption (follow-up)

Batch 16, on v2-smoke. ccy 3.124.63, container 2.84.84 (`proto` and `member/*` are image
sources). Code commit: `d9a4fcc80`; this section and the register rows are the commit after it.

**The decision.** The team coordinator's, 25 Nov 21:21Z, on the owner's standing rule; the owner
has been told how to reverse it. A declared team human is exempt from the per-sender receive
flood limit in main and in the questions room: a human post is never dropped `rate`. A drop is
final (the position and the questions floor move past it), and a human's words must never be
lost. A 11.1 and 7.6 rules 05 and 10 (Plan 00209 `DESIGN-v2-A-protocol.md`) and SPEC-n3f QS6
now say so, with the reason and the reversibility.

**The code.**

- `proto/verdict.go` (`Judge.human`): the `rate` case is gone. The post is still judged against
  the window (`admit`; past the limit it is not entered, as any refusal), and the result is the
  new `Verdict.OverLimit`; the post is delivered HUMAN either way. The agent path
  (`Judge.agent`) and the admin's exemption are unchanged.
- `member/team/team.go`: `Counts.HumanOverLimit`, in `IsZero` and `Add`.
- `member/teamsync/session.go` (`take`, new `judged.overLimit`): a delivered item whose verdict
  is over the limit is counted and logged.
- `member/records/records.go`: `TeamCounts.HumanOverLimit`, the status key
  `counts.human_over_limit`; `member/engine/status.go` fills it.
- The teamchat skill text (`member/kit/skill.txt` and the plugin's `SKILL.md`) names the key.

**The guard against a runaway client, and why this one.** A counter in status plus one log
line per post over the limit: `human post <id> over the flood limit (60 a minute), delivered`.
A bounded summary would hide which posts were over; one line per post is exactly the volume the
old `dropped <id>: rate` line logged for the same events, so the log grows no faster than
before, and each line names a post that can be fetched. The counter is what `teamchat status`
shows without reading the log, beside `dropped_by`.

**The new status key and older readers.** `records` is encode-only: no Go code decodes a `team`
status record (the strict decoders in the tree, `status/status.go`, `state/strict.go`,
`seat/records.go` and others, read other records). No host-side reader parses
`teamchat status` output: `ccy-teams` reads a seat's `report.json`, not status records, and the
v1 pingbus helpers have their own format. An older reader cannot refuse the key, so no reader
needed to accept its absence. The encoder test (`records_test.go`) pins the key.

**Defence Before Fix.** The class is "a rate limit that can drop a message that must never be
lost". A go/analysis rule cannot express it: which messages must never be lost is a protocol
fact (a human's post, the admin's item), and a limiter call (`Window.Admit`) is the same call
whether the event behind it is an agent's or a human's; telling them apart needs the sender's
class, a run-time value of the roster. A rule keyed on "a `drop(…, ReasonRate)` in a function
that handles humans" would be a name match on today's layout, not the class. The tests are the
guard: the verdict's routing corpus pins a flooded human as delivered in main, the proto test
holds both rooms, and the two teamsync burst tests hold the end to end count, delivery and log.
