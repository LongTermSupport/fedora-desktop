# U6: human messages, register entries R10 and R12

Branch `v2-smoke-u6-human-msgs`, based on `v2-smoke`. Both faults have one root shape: the fake
homeserver (`matrix/fakehs`) answered two requests otherwise than Tuwunel does, so the code it
tested was shaped by an answer the real server never gives. The causes were read from Tuwunel's
source at the pinned tag v1.9.4 (`files/usr/local/share/teamchat/tuwunel.pin`). A sparse clone
was made under `untracked/`, which is not committed.

## R10: a reply to an edited human message is refused

**Cause.** Every reply is shaped the same way, and the error shows on a reply in questions.
`teamchat reply '<edit id>'` on a human post in questions goes through
`engine/questionsverbs.go` `replyQuestions` to `proto.Composer.threadRelation`. A post that is
not attached to a question (or one whose edit carries no thread root: `DecodeHuman` gives an
edit no `ThreadRoot`) is answered with `InThread(<answered>, <answered>, true)`, a new thread
rooted at the id given. For an edit, that root is the `m.replace` event. Tuwunel 1.9.4
`src/api/client/send.rs` `check_nested_thread` (MSC3440) refuses a thread whose root's content
names a `rel_type`: `400 M_UNKNOWN "Cannot start threads from an event with a relation."`. The
engine's `sendFailed` turns any non-transient `matrix.Error` into `msgServerRefused` ("the
homeserver refused the send; tell a human", `CodeInternal`). A reply to the original id works
because the original has no relation. A reply in main is `m.in_reply_to` only, which Tuwunel
does not check, so the refused reply was in questions.

**Evidence.** The new test `TestReplyToAnEditAnswersTheOriginal` was red before the fix and
showed the thread rooted at the edit's id (`EventID:...506`, the edit). The new fakehs test
`TestAThreadRootedAtAnEventWithARelationIsRefused` was red: the fake answered 200.

**Fix.**

- `fakehs.send` refuses a thread rooted at an event whose content names a `rel_type`, with
  Tuwunel's status, errcode and text (`nestedThread`).
- `replyQuestions`: when the post fetched is a human's edit (`Human.Revises`), the reply fetches
  and answers the original. The thread, the in-reply-to and any link-back are the original's,
  as for a reply to the original's id. A 7.5 accepts an edit only of the same sender's post in
  the same room, so the original is always the human's own post.

**Not changed.**

- The reply in main to an edit's id still sets `m.in_reply_to` to the edit. Tuwunel accepts it.
  Resolving it needs a fetch per reply, because the ledger does not keep `revises`, and U2 is
  editing `repliedTo`.
- `msgServerRefused` still says "tell a human" for a 4xx the agent could fix. U1 owns that
  message (send.go) and has agreed it is outside their rule `project_refusal_reason_text`. It
  is an unowned class, logged below.

## R12: a worker cannot verify a human's message from the questions room

**Cause.** The spec is sound: A 4.1 has the admin invite every non-parked member to questions,
and A 10.6 has a worker's link read questions by event ID. The code joined only on the wrong
answer. `teamsync/verbs.go` `getQuestionsEvent` joins the room (by the invite every worker
holds) only when the read is refused `ErrForbidden`. Tuwunel 1.9.4
`src/api/client/room/event.rs` answers an event the user cannot see (`user_can_see_event`
false: not joined, with `shared` history) `404 M_NOT_FOUND "Event not found."`, never 403. So a
worker never joined, `verify` took the 404 as "not there" (exit 23, "not in the team's main
room, nor in a questions room this member reads"), and `relayed` (`teamsync/relay.go`) dropped
every relay `provenance`. The second effect is worse than the register says: no relayed human
answer could reach a worker at all, which explains "the human is asked again". `status`
showing questions `not-coordinator` is the label for a worker, not the cause.

**Evidence.** The fake answered a non-member 403 (`joinedRoom`), which is why the tests passed.
With the fake corrected (`TestAnEventAUserCannotSeeIsNotFound`, red first: 403), the whole
teamchat suite turned red in exactly four `teamsync` tests:

- `TestAWorkersVerifyOfAQuestionsPost`: exit 23, which is R12 itself.
- `TestAWorkerGetsTheRelayedPostAsHuman`: no item.
- `TestARelayedAnswerOutlivesASessionRestart`: the relay was dropped.
- `TestAWorkersRefetchOfARelayedPost`: 404.

**Fix.**

- `fakehs.getEvent` answers an event the user cannot see 404 `Event not found.`
- `getQuestionsEvent` joins on a 403 or a 404 when this member does not coordinate, then reads
  again.
- `TestAWorkersVerifyOfAQuestionsPost` also checks the skill's `--room questions` form.

The skill text (section 3) is correct once this works, so it is unchanged.

## Defence Before Fix

- **Class:** teamchat code shaped by a fake homeserver answer Tuwunel does not give. Its
  hazard is that the tests pass and the live system fails.
- **Detector:** an analyzer cannot judge it, because what a server answers is not a syntax
  shape. It is entered under "Defect classes that cannot be a rule" in
  `CLAUDE/GoProjectRules.md`. What holds it is the fake, corrected to Tuwunel's source and
  proven red, then green, by the two fakehs tests.
- **Sweep:** the whole `./internal/teamchat/...` suite ran under the corrected fake before the
  member fixes. Only the four tests above failed. Every other `GetEvent` caller already treats
  403 and 404 alike.
- **Fix:** the two member fixes above.
- **Other fake departures:** other 403s from the fake's `joinedRoom` (state, messages,
  receipts) were not checked against Tuwunel's source. They are not proven either way.

## Faults met while working (dogfooding)

- The edit hook's golangci-lint denied edits with "parallel golangci-lint is running" while
  other units ran lint. That is a false lint failure. It is logged in fedora-desktop#426, and U1 saw it too.
- Unowned class: a non-transient homeserver refusal is reported as `msgServerRefused`, "tell a
  human", exit `CodeInternal`, with the server's errcode and text only in `link.log`. A 4xx
  that the agent's input caused should name the cause and use a fix-class exit. This needs its
  own detector and a decision on the exit, so it is a register candidate for the coordinator.
- The questions index (`QuestionIndex.Attach`) lists a human's edit of an unattached post as a
  second unattached post. A reply clears only the one it names (`plainReply`), so after a reply
  to the original, `teamchat questions` still lists the edit as unanswered. Replying to it again
  now resolves to the original and posts a second reply. This is not fixed (it touches the
  index's state) and is a register candidate.
