**Where the name is formed:** never by the launcher. The handle is fixed at step 3 by the
`--prefix` and `--seat` the person typed; step 4 names the pool directory after it; the launcher
only matches the seat part (`ChooseSeat`). The `project.number+machine.type` the owner expects is
exactly the handle grammar `<repo>.<seat>+<site>.<type>`.

### 1.2 What v1 needed for the same

One command: `ccy --teams N@T` (or a team alone and a choice). `agent-bus seat take` created any
seat that did not exist with one `sudo agent-bus add-member` inside the launch, and the handle's
site came from `HOOKS_DAEMON_HOSTNAME` / `CCY_HOST_HOSTNAME`, else `local`
(`files/var/local/claude-yolo/lib/agent-bus-seats.bash` header, `lib/common.bash` ccy.env.local
text, the `--teams` help in `claude-yolo`). v2 dropped the in-launch create on purpose: the launch
never calls sudo (the store is the owner's, the root verb is password sudo, and the pool must be
filled under the allocation lock before the take). That is the regression the owner feels.

### 1.3 What the design already decided but was never built

DESIGN-v2-C-host.md 3.6.3, 3.7.3 and 3.7.4 already say that **ccy-teams** chooses the seat number
in process (lowest free in the checkout and on the roster, retrying up to three times on an
`enrolled` refusal), calls `member add --seat S` through sudo, and places the answer into a claimed
pool directory under the allocation lock. Only the LXC caller (`lxc apply`) and the manual pipe
exist; no ccy-teams verb does it. SPEC-cross-network X25 decided the site: declared
`teamchat_site`, default `local`, never a hostname.

## 2. The design: a couple of commands

The smallest design that gives the owner what v1 gave, keeping v2's boundaries:

1. `ccy-teams seats add <team> [--host] [--human-text]` in the checkout, on the machine that runs
   the team's homeserver: derives the handle, asks sudo once, issues, places, prints `N@team`.
   **Built in this unit** (section 4).
2. `ccy --teams N@team` launches it, unchanged.

Then, in order, the slices that need an owner answer (section 3):

3. The chooser offers "a new seat" when the checkout has none (or always, as v1's "lowest free or a
   new one"), and runs step 1 itself before the launch. U3 owns the chooser (R3); this is a small
   follow-on once U3 lands, and it is where "the launcher derives the name" fully happens.
4. A member machine that does not run the homeserver: the verb needs a route to the bus host's
   `member add`. Today that is the documented ssh pipe; built into the verb it is `ssh <bus> sudo -S`
   with the owner's ssh configuration (Plan 00246 X21/X22, DESIGN-C 3.7.6 item 2).
5. A coordinator agent asking for a seat for another seat: only through Plan 00264's request spool
   (O2), never by giving agents sudo. Not designed here; it overlaps Plan 00264 Q1 and should be
   decided there.

**Reused, not rebuilt:** `proto.ParsePrefix` / `Prefix.Numbered` (grammar), `guestfacts.RepoName`
(the LXC repo rule, now exported), `declare/hostvars.Read` (the strict v2 host_vars reader, its
first opener), `teams/system.Here` and `PoolSeats` (the launcher's own checkout key and pool view),
`system.StatusRecord` (roster), `internal/sudo` `Ready` + `Capture` (password on the terminal,
streams unprinted), `teamchat-admin member add` unchanged, `placeissued.Place` (the same placement
`teamchat seat place-issued` runs), `gitx.RemoteURL`.

**Overlap with Plan 00264:** none in what is built. 00264 creates *teams* at runtime; this adds
*seats* to a team that exists. Both stop needing an IaC run for their step. Team creation stays as
00264 designs it; a runtime team's seats would be added by this same verb once 00264 exists.

**#415 (seat move):** not touched; it needs a lease on the bus and #410 first.

### Security boundary

- **Who may issue:** whoever can run `teamchat-admin member add` as root on the bus host, which is
  the owner through password sudo (C10). The verb adds no privilege, no sudoers rule and no
  NOPASSWD. An agent session cannot run it (no sudo in a container; a host `cc` session is denied
  sudo by its rules and has no password).
- **No secret in argv:** the owner's password goes to sudo on the terminal (`sudo -v`), then
  `sudo -n`; the argv holds only team, prefix, seat, kind, human-text and `password` as the
  credential *kind*.
- **The issued password never on a screen:** `member add`'s stdout is captured from a pipe
  (`teamchat-admin` writes the plain line, not the secret screen, as stdout is not a terminal), kept
  in memory, handed to `placeissued.Place` and cleared after. On any failure the verb prints
  `teamchat-admin`'s stderr only, never its stdout; the tests assert the answer reaches no stream.
- **Name not typed, so not spoofable by typo:** the handle comes from the checkout's origin, the
  declared site and the roster.

## 3. Questions only the owner can answer

1. **Seats on another machine.** When the team's homeserver runs on a different machine from the
   one launching, may `ccy-teams seats add` ssh to the bus host itself (your ssh keys and agent, the
   sudo password typed into the pipe, as the documented pipe does), or must that stay a pipe you run
   by hand?
2. **Seat creation inside the launch.** Should `ccy --teams <team>` with no free seat in the checkout
   create one itself (v1's behaviour, one sudo password at launch), or only offer the command? Only
   an attended launch could ask for the password; a restore or headless launch would still refuse.
3. **Agents asking for seats.** Should a coordinator be able to ask for a seat for a new worker with
   no password from you? If yes, it should go through Plan 00264's request spool and policy (its
   Q1 and Q2), not through sudo.
4. **Human text default.** A new seat takes human text by default (the protocol's default; the
   coordinator must have it). Is that right for every new worker seat, or should workers default to
   no human text?
5. **Name your seat.** v1 let you name a seat (`qa2@team`). Do you want `--seat <word>` for a named
   seat, or are numbers enough?

### 3.1 Answers relayed by the coordinator

- **Q4, answered:** a new worker seat takes no human text by default. Built: `--human-text` opts in;
  the default issues `--human-text false`. Safe because U2 makes the flag gate human free text only,
  so a worker still gets its coordinator's PEER messages.
- **Q2, answered yes (attended only), not built here:** U3 owns the launch chooser. It is a
  follow-on after U3 and U5 merge; it calls `seatadd.Adder.Add` in process (built for that).
- **Q1, Q3, Q5:** put to the owner (Q6, recommended yes to all three). Not shipped. Each is a small
  change: Q1 is a second `seatadd.Issuer` (ssh to the bus host) beside `SudoIssuer`, plus reading
  the remote roster for the number; Q3 is an `Issuer` that files a Plan 00264 request; Q5 is one
  function, `freeHandle`, accepting a seat word.

## 4. What was built

- `seatadd.Adder.Add(ctx, Request)` is the in-process API (team, checkout, host, human text in;
  handle, `<N>@<team>` and launcher out; progress through an optional `Note`). The issue step is
  the `Issuer` interface; `SudoIssuer` is the one implementation (local password sudo). `Cmd` is
  the CLI over an `Adder`.
- `ccy-teams seats add <team> [--host] [--human-text]` (`teams/seatadd/`): the handle derived
  (repo by `guestfacts.RepoName` from `git remote get-url origin`, else the checkout's directory
  name; site from the host_vars' `teamchat_site`, else `local`; type `podman`, or `host` with
  `--host`); the number the lowest one no pool seat of the checkout uses as its seat part and the
  roster keeps for no handle of the same prefix in any state; one password sudo; `member add --credential password`; its answer placed in memory by `placeissued.Place` into this checkout's
  pool; `N@team` on stdout and the launch line on stderr. A team with no status record on this
  machine is refused (78) naming the place-issued pipe; a failed issue prints teamchat-admin's
  reason (1); a seat issued but not placed names the exact `member reissue ... | teamchat seat place-issued --checkout <dir>` pipe (1).
- `guestfacts.repoName` exported as `RepoName`, so pool seats and LXC members share one repo rule.
- Wired in `teams/app.go`; `ccy-teams --help` (`teams/usage.txt`); docs
  `docs/agent-bus-cross-network.md` (new "A seat on the homeserver's own machine") and
  `docs/agent-bus.md` (the v2 cc paragraph).
- No change under `files/var/local/claude-yolo/`, so no CCY version bump. `ccy-teams` reaches the
  host through `play-claude-yolo.yml`, which is already in `CLAUDE/Plan/meta-deploy.list`.

**Departure from C 3.7.3, stated in the package doc:** the allocation lock is taken by the
placement, not held across the sudo call. A second checkout racing for the same number is refused
by `member add` (the handle is `enrolled`) and the verb reports it; it does not retry three times
as 3.6.3 suggests. Nothing is placed twice.

## 6. NOT proven

- No run against a real `teamchat-admin`, a real homeserver or a real sudo. The verb's argv is
  pinned against `memberFlags` by reading, and `placeissued.Place` is the code `teamchat seat place-issued` runs, but the end-to-end issue, place and launch has not been done on a machine.
  Proof wanted: on the bus host, in a checkout with no seat of a live team, `ccy-teams seats add <team>`, then `ccy --teams <N>@<team>` starts and `teamchat whoami` names the derived handle.
- `HostVarsSite` reads the host_vars named by ccy-teams' configuration; a host_vars file that is
  vault-encrypted as a whole (not inline values) would be refused as not YAML. Not seen here.
- The worktree case: origin is asked of git, so a linked worktree works; not run on one.
- A team whose status record lists the probe or a human handle: those never parse under the derived
  prefix, so they do not affect the number; covered by the prefix test only.
