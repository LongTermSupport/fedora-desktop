# U8: LXC containers on another host than the homeserver's (issue #425)

Branch `v2-smoke-u8-xhost-lxc`, from `v2-smoke`. Delivers Plan 00257 Task B.4 as far as the code
and the docs go; the live run is below.

## A1: the route

**Answer.** An LXC container on another host joins as an ordinary off-host client. It uses the
same seat layout, session line and unit as an LXC seat on the homeserver host. Only the
placement differs: the person who issues the seat pipes it into the container, and the
container places it itself. Nothing on the homeserver host reaches into the container, and no
`lxc-attach` crosses machines.

### Design

| What                                                             | Where                                                                                               | By whom                                                                                                                                                  |
| ---------------------------------------------------------------- | --------------------------------------------------------------------------------------------------- | -------------------------------------------------------------------------------------------------------------------------------------------------------- |
| The member kit (`teamchat`, static; plugin, hooks, settings)     | `/usr/local/lib/teamchat/kit/<digest>/` + `current`, and `/usr/local/bin/teamchat` in the container | the container's provisioner, copying the kit a `play-teamchat.yml --tags member` run assembles (owner question 1)                                        |
| The seat: `seat.json` and its token                              | `~agent/.config/teamchat/lxc/<key>/seats/<team>/`                                                   | `teamchat seat place-lxc`, run as the agent user, fed by the issuing pipe                                                                                |
| The desired membership (one seat, the key's session `lxc-<key>`) | `~agent/.config/teamchat/lxc/<key>/membership/desired.json`                                         | the same `seat place-lxc`                                                                                                                                |
| The session                                                      | the container                                                                                       | `teamchat run --claude --kind lxc --key <key> -- [wrapper] claude`, by hand, by the container's launcher, or by a unit of the same text as `unit.Render` |

- **Issued.** On the homeserver host:
  `teamchat-admin member add --team T --prefix <repo>+<site>.lxc --seat N --kind lxc --human-text true --credential token`.
  The credential is a token because this is an LXC guest seat. That matches the #248 ruling (a
  pool seat keeps a password, a guest seat a token).
- **Placed.** `| ssh <agent>@<container> teamchat seat place-lxc --user <agent> --checkout <dir>`.
  The verb works as follows:
  - It reads the member verb's answer or a bare bundle, through `placeissued.ReadWatched`.
  - It refuses a password, a handle not of type `lxc`, or a seat part that is not 1-9999.
  - It keys the seat as the lxc apply does: `LXCSeatKey(team, checkout, N)`.
  - It places the bundle exactly as `guest place-bundle` does (GU3).
  - It writes a one-seat desired membership, as `guest membership` does (GU4). The generation
    is the wall clock, so a running session takes a reissue.
  - It prints the key on stdout.
- **URL.** The seat reaches the team by the team's `url` (a name), with the team CA in the
  bundle. Who places a seat now decides its URL, not the seat's kind:
  - the lxc apply's joins get the bridge address (`ReachBridge`);
  - every member verb a person runs gets the team's `url` (`ReachURL`).
- **Launched.** `teamchat run --claude --kind lxc --key <key> -- claude`, or with the container's
  own wrapper (A3).

## A2: how a host-started LXC session signs in to Claude Code

From the code:

- teamchat sets no credential. `teamchat run` starts CMD with the environment it was given, plus
  `PATH` and the kit's variables (`keeper/loop.go` `startCmd`, `execx` Env adds to the
  parent's).
- The session unit (`host/lxc/unit/unit.go`) sets only `HOME`, `XDG_RUNTIME_DIR` and `PATH`.

So a unit-started session signs in with the agent user's own stored Claude Code login, from
`claude` `/login` run once as that user. A container that chooses a token per session starts
its sessions with its own launcher (A3), its wrapper exporting the token (never in argv), and
leaves `service` off. The docs say this ("Signing in to Claude Code").

## A3: a container repository's own launcher

**Yes.** The grammar (`member/cli/launch.go` `checkClaudeCmd`) accepts
`teamchat run --claude --kind lxc --key <key> [--resume-recorded] -- <wrapper> [flags] [--] claude [claude flags]`.
The rules:

- One argument is named `claude`.
- A bare `--` may appear only directly before it.
- Neither `--settings` nor `--plugin-dir` may appear anywhere. run appends them, and the resume,
  after the last argument, so the wrapper must pass every argument after `claude` through
  unchanged.

This is pinned by the new case `lxc by a container's own launcher` in
`TestTheDesignsLaunchLinesParse`. Before fix 1 the line parsed but was refused at launch. The
docs say this ("Starting a v2 LXC session by hand or from the container's own launcher").

## A4: a v2 `ccy-teams lxc-add`

This is not small, so it is designed here and not built.

- `ccy-teams lxc-add <team>` keeps its v1 flow (container, user, checkout pickers, read from the
  host's side) and branches on the team's system (`system.Resolve`).
- For a v2 team it:
  - asks the seat number, offering the lowest free one for (team, checkout);
  - drops the role question (v2 has none);
  - writes a `teamchat_lxc_members` entry `{team, container, user, checkout, seat, human_text, service}`;
  - adds the team to `teamchat_approve_teams` for this one run, after showing the entry and
    asking once (the entry is a security field: exit 70 without approval);
  - runs `play-teamchat.yml` scoped by `teamchat_only_teams`;
  - reads the `lxc apply` lines for the seat key and prints the start line.
- It only offers this host's containers. An off-host container is the A1 pipe, which needs the
  homeserver's sudo and has no ccy-teams step.

## Host runs and live acceptance

No host run is queued from this unit. The change is Go, and it reaches a machine when
`play-teamchat.yml` next deploys teamchat; that run is the coordinator's to queue with the
merge. Note that fix 1 is needed on the homeserver host's kit and in every LXC guest's kit, for
same-host LXC sessions as well.

**Live acceptance.** Needs a homeserver host X with a team whose `url` is a name the other
machine resolves inside `networks`, and a host Y running a privileged or unprivileged LXC
container with a non-root agent user whose uid no account on Y has.

1. Put the kit in the container. On a fedora-desktop host of the same architecture, run
   `play-teamchat.yml --tags member`, then copy `/usr/local/lib/teamchat/kit/<digest>/`, the
   `current` link and the `/usr/local/bin/teamchat` link into the container.
   - Accept: `teamchat version` runs as the agent user.
2. From a machine with ssh to both, run the A1 pipe with `member add ... --kind lxc --credential token`.
   - Accept: stdout is a 16-hex key.
   - Accept: `~/.config/teamchat/lxc/<key>/seats/<team>/seat.json` names the team's `url`, not
     an address of X's bridge.
3. In the container, as the agent user in the checkout, run
   `teamchat run --claude --kind lxc --key <key> -- claude`.
   - Accept: the session starts (no exit 78).
   - Accept: `teamchat status` shows the team linked.
   - Accept: a `say` from a seat on X arrives.
   - Accept: the team's status on X lists the handle (`online: false` is expected; the health
     tick cannot see Y).
4. Repeat step 3 with a wrapper:
   `teamchat run --claude --kind lxc --key <key> -- /path/wrapper claude`, where the wrapper
   exports `CLAUDE_CODE_OAUTH_TOKEN` and `exec "$@"`.
   - Accept: the session signs in with that token.
5. Same-host regression for fix 1, on X: run `teamchat-admin lxc start --member <container>/<key>`
   for a `service: true` seat.
   - Accept: the unit is active and its tmux session holds a running Claude Code.
