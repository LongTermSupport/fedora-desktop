# R39: a seat starts on its team's model

Register row [R39](../REGISTER.md#r39-a-seat-starts-on-the-accounts-default-model). Batch 8, ccy
3.124.52 (container unchanged, 2.84.80: `src-go/internal/teams` is not an image source; the
`ccy-teams` binary is rebuilt by `play-claude-yolo.yml`, which the queue already holds, so no
`meta-deploy.list` change).

## What was built

- **The setting**, `internal/teams/seatmodel`: one file, `<seat store>/models.json`
  (`{"teams":{"<team>":{"default":"<model>","seats":{"<handle>":"<model>"}}}}`, 0600, written
  atomically). The seat store is the owner's, per machine, outside every checkout and on no ccy
  mount (the launch's `Guard` keeps it off them), and every launch already reads it, so the
  model needs no network. A seat's own model wins over its team's default; with several seats
  in one launch the first seat (launch order) with a model decides and the others asking for a
  different one are named in the launch's note. A file that does not decode strictly (unknown
  key, a bad team id, seat name or model, trailing data) refuses the launch before any seat is
  taken, naming the file and the repair.
- **The verb**, `ccy-teams seats model`: no argument lists (`<team> team <model>`, then
  `<team> <handle> <model>`, sorted, on stdout); `<team> <model>|--clear` sets or removes the
  team default; `[--host] <seat>@<team> <model>|--clear` sets or removes a seat's own, the seat
  resolved in the working directory's checkout pool by the launchers' own `ChooseSeat` (podman
  for ccy, host with `--host`) and kept by its full handle. A model is checked only as one token
  (non-empty, no space or control character, no leading `-`). Bad arguments exit 64, a seat not
  found or an unreadable store 1.
- **The launch**, `teamchatlaunch.Launch.Take` (Run is now its run arguments): reads the models
  with the chosen seats, then
  - `ccy` (`internal launch-args`): appends `-e ANTHROPIC_MODEL=<model>` to podman's arguments;
  - `cc` (`internal cc-run`): puts `ANTHROPIC_MODEL=<model>` in the `teamchat run` child's
    environment, unless the person's environment sets one, which is kept and said;
  - both say `Model: <model>, team <team>'s model (a --model given to claude wins; ...)` on
    stderr (stdout stays the launcher's payload). A note that cannot be written fails the launch
    (cc: the session is ended and its seats released).

## Why this home, and the departure from `--model`

The brief's design passes the model as `--model <name>`. It is passed as `ANTHROPIC_MODEL`
instead, because claude ranks `--model` above `ANTHROPIC_MODEL` (and that above settings), so:

- a `--model` the person gives (`ccy --model x`, `cc --model x`, or replayed by a restore) wins
  without the launch reading claude's arguments (`--model`, `--model=`, after `--`);
- on ccy a project's `ccy.env` exporting `ANTHROPIC_MODEL` wins too (entrypoint.sh sources it
  after podman's `-e`), and on cc the person's own environment is kept;
- one Go function serves both launchers in `internal/teams`, so neither `ccy-start-claude`
  (`internal/ccystart`, an image source: a container bump and rebuild) nor the bash launcher (on
  the ratchet) changes. `cc-claude` was not used because the model is a fact of the seats, which
  only the launch that takes them knows.

Cost of the env route: claude's own child processes (a `claude -p` the session starts) inherit
`ANTHROPIC_MODEL` and so default to the team's model rather than the account's; and `ps` does
not show the model in argv (the stderr note does). If the owner wants the literal flag, the same
`Taken.Model` can drive a `--model` added by `ccy-start-claude` for ccy and by cc-run's argv for
cc, at the price of a container bump and argument parsing.

## Review fixes

- **Where it is kept:** the per-machine seat store, never the team's declaration; a model set on
  one machine does not follow the team to another (register row, `agent-bus.md`,
  `agent-bus-cross-network.md`, changelog).
- **The environment:** child claudes inherit `ANTHROPIC_MODEL`; on ccy a host-shell
  `ANTHROPIC_MODEL` does not reach the container (the launcher passes no such variable), only
  the seat's recorded model.
- **The multi-seat rule, as `seatmodel.Settings.For` implements it:** the first seat, in launch
  order, that has a model decides, and its model is its own, else its team's. A first seat with
  neither does not decide: a later seat's model is used. The docs state it this way, not as
  "the first seat's model".
- **A hot-seat join** (`ccy-teams session add`, `HotSeats.Join`) launches nothing, so the seat's
  model is not used. The join reads the models and, when the joined seat has one, says on
  stderr, before the take, that it is not used for this join and that the session keeps its
  launch's model; a note that cannot be written takes nothing. Test:
  `TestJoinSaysTheSeatsModelIsNotUsed` (`hotseats_test.go`); red: `HotParts.Stderr` undefined.

## Restore

`ccy-sessions restore` replays the person's recorded launcher arguments
(`lib/session-registry.bash`, `ccy_registry_replay_args`: a `--model opus` is kept as the value
of a flag ccy does not know; `--teams` is kept). The model a launch adds is in no argument and is
not recorded; the replayed launch runs `launch-args` or `cc-run` again, takes the same seats and
reads the same setting, so it starts on the same model. A setting changed in between applies at
the restore, as at any launch.
