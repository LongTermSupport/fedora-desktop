# U10: R41, `ccy-teams session add` on a running v2 session

Unit U10 of Plan 00265, register row R41. Branch `v2-smoke`.

## The cause, checked

The brief's cause holds, with one detail it did not name. `hot.resolve` looks for v1's
membership directory under `$XDG_RUNTIME_DIR` (`membership.DirOf`). A v2 launch never makes one:
`internal launch-args` calls `Membership` (v1's init) only for an agent-bus list, and for a
teamchat list writes generation 1 of `control/<session>/desired.json` in the owner's seat store
(`Launch.Run`). So on a v2 session `session add` did not write v1's file and miss: it stopped at
`resolve` with exit 78, "launched without the agent team bus kit (--no-bus, or a ccy older than
3.99)", which is wrong on both counts. Every other verb (remove, move, role, repair) stopped
there too.

## What the keeper reports

The keeper does report a held seat; nothing had to be proposed. Two signals, both readable on
the host:

- the seat lock `sessions/<session>/<team>/seat.lock`: `seat.KeeperOf` reads `KeeperRunning`
  once the keeper's `takeSeat` holds it (RC1's hot add);
- the seat's `report.json` beside it (`state.Report`): `desired.generation` and
  `desired.state` (`applied`, or `refused` with a code), and the seat. The keeper writes it
  once the link names the seat's handle.

The host waits for both: lock held, and the report naming the seat at the generation written,
applied. Until then it says which is missing; a refused generation names the keeper's code.

## The fix

- `teamchatlaunch/hotseats.go` (new): `HotSeats`, a running v2 session's seats. `Choose` (the
  seat given, which must be a pool seat; else the lowest free one, `seatchoice.Default` over
  `system.PoolState`, the launch chooser's rule), `Join` (the launch's own `choose` and
  `Taker.TakeAll` for the session, then the next generation with the seat), `Leave` (the next
  generation without it and with a `released` farewell, C 3.7.5), `Put` (a failed join put
  back), `Applied` (above), `Release` (`seat.Store.Release` with `Leaving: true`, which waits,
  bounded, for the keeper to free the lock, C 3.7.3). `WriteDesired` is now the one writer of
  desired.json; `Launch.Run` uses it for generation 1. `Verbs.HotSeats` opens it in a checkout's
  store, wired into `hot.Hot.Teamchat` in `teams/app.go`.
- `hot/teamchat.go` (new) and `hot/hot.go`: `resolve` asks for the v2 seats only when the v1
  directory is absent, so a v1 session takes exactly the path it took before. On a v2 session,
  add: seat chosen, asked, record first (`--teams`, so a restore replays it, H5), take, next
  generation, wait (the same `Waits.Apply`, the same "ended" check); a seat not held is put back
  (record, generation without it, seat released). Remove: record, farewell generation, release.
  Help text says what v2 supports.
- Not built for v2, and refused by name (exit 78, naming teamchat and the way on): `--role`,
  `--demote-current`, `--park`, `--coordinator`, `move`, `role`, `repair`. Each needs v2's role
  and park paths (teamchat-admin), which is a unit of its own.

## Defence Before Fix

- **Class:** a host verb that acts on one bus generation's membership file for a session of the
  other (or, as here, refuses it as if it had no bus at all).
- **A project rule cannot express it.** The defect is a missing branch: `hot` never asked whether
  the session was v2. A `go/analysis` rule sees calls, not the absence of a question; a rule
  "only package X may call `membership.Write`" would pass the faulty code unchanged.
- **The guard instead:** `TestEveryVerbOnAV2SessionActsOrRefusesByName` drives every verb and
  refused option on a v2 session and fails if any falls through to v1's "bus kit" text, exits
  other than 78, or writes v1's membership. A new verb added to `hot` without a v2 answer fails it.
- **Sweep (same class, other files), not fixed here, for the owner:** readers of v1's
  membership that do not see a v2 session: `hot/list.go` (`session list` shows no v2 session),
  `ops.SessionsIn` / `TakeOut` (a team removal does not take running v2 sessions out),
  `restart/jobs.go`, `board/collect.go` and `conversation` (v1 report). Each is a read, not a
  write, and each needs its own v2 source; they want their own rows.
- **Edges noted:** a stale v1 membership directory under the same session name (same boot)
  makes the session read as v1, as before; a host cc session launched on teamchat is left out
  (`t.cc()`): whether its desired.json lives in the same store was not checked in this unit.
