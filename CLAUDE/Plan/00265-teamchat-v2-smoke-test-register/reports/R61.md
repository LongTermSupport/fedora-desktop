## Where the lookup lives

In Go, `ccy-teams internal session-name <ccy|cc> <project> <seats> <checkout>`
(`src-go/internal/teams/sessionname`, expectation N7 in its package doc; `Takeover`). The
command reads the registry through `registry.Locate(...).ReadAll()` (wired in
`internal/teams/app.go`, `readRegistry`). The launcher's `ccy_tmux_next_name` passes `$PWD` as
the fourth argument. `tmux-session.bash` did not grow: its bash-limits measure is unchanged (one
`local` merged into another to pay for the `read` that splits the answer).

## The match rule

A record is taken over when all hold:

- its `prefix=` is the launcher's (`ccy` or `cc`) and its `dir=` is the launch's checkout;
- its `--teams` (read as `discover.RecordTeams` reads it: the launcher's own words, the last
  `--teams` wins) and the launch's seats are the same set once each is read as the seat check
  reads it (whitespace removed, `membership.ParseSeats`, sorted). No seats matches no seats. A
  list the check refuses (a team alone, as `cc --teams <team>`) matches nothing;
- its file is named for its `name=` (the launcher writes `<registry>/<name>`; taking a record
  whose file is named otherwise would leave the old file as a second record, #398);
- no tmux session of that name is running.

Exactly one such record: stdout is its name, stderr says it is taken over. Two or more: none is
taken, stderr names them, the new form (`<launcher>-<team>-<project>-<seat>`) is used. An
unreadable record is named on stderr and never taken. A registry that cannot be located or
listed is exit 1, so the launch stops.

## The re-attach offer

`ccy_tmux_offer` handles running sessions only (it lists tmux sessions started from `$PWD` that
share a seat with the launch, and offers the detached ones). The take-over only considers
records with no running session, so the two do not overlap: a declared session that is running
and detached is offered back; a declared record that is stopped is taken over.

## What happens to the declared record

The registry write at `tmux-session.bash` (the launch's record) writes the whole file, so before
this change a write under a declared name would have dropped:

- `fresh-if-no-conversation=yes`: now kept. `session-name` prints `<name> yes` for a marked
  record and the launcher passes `--fresh yes` to `ccy_registry_write`, as every other rewrite
  of a record already does (`docs/ccy.md`: "Every rewrite of the record keeps the mark").
- `compose=`: not kept by this write, as for any new launch; the launcher records the launch's
  own compose answer when it is given (`--compose`, or the question).
- the declared arguments (`--token`, `--ssh-key`, `--compose start` and so on): replaced by the
  launch's own, so a restore replays what actually ran. A terminal launch that omits `--token`
  or `--ssh-key` is recorded without them.
- `restore=`: the launch's (`no` only with `--no-restore`).

Consequences of using the declared name:

- When the session ends cleanly, the trampoline removes the record, as for a restored declared
  session; the next run of the provisioning `declare` writes it again (`DECLARED`).
- While it runs, a re-run of `declare` finds a record that is not the declared one (other
  arguments, or no mark) and fails ("is running"; `docs/ccy.md` already says the task "fails
  when it is not" the declared record). Before, it found its own record untouched and said
  `UNCHANGED`, beside the stray second one. A play that declares while the owner has the
  session open from a terminal therefore stops; `creates:` in place of `changed_when`, as
  `docs/ccy.md` suggests, avoids it. Open for the coordinator.
- A tmux start that fails removes the record it just wrote, now the declared one, so the next
  boot would not restore it until `declare` runs again.
