# R67: the status-line golden test reports a process that died as it was killed as outliving the render

Fixed on `v2-smoke`, batch 18 (`6b300c2a0`). Test-only change; no production code changed.

## What was seen

CI run 45703604400 ("QA (diff, go)", 25 Nov 21:32Z; the go test stage ran 7 minutes),
`TestStatusLineGolden`, subtests `cancel-sighup` and `cancel-sigint`:

```
golden_test.go:686: kill <pid>: no such process
golden_test.go:691: step 1: grandchild.pid: process <pid> outlived the render
```

A re-run passed.

## Cause

Each cancel scenario's inner command (`hang.sh`) starts `sleep 60 &` and writes its pid. The
render runs the inner as a new session and, on the cancel, sends SIGKILL to the whole group at
once (`execx` `killGroup`) before it returns. So by the time the test's `goneOne` looks, the
grandchild has been sent SIGKILL; the check only waits for the kernel to finish it.

`goneOne` polled `procend.Ended` 250 times, 20 ms apart (about 5 s), then, if the process was
still running, sent SIGKILL itself, reported a kill error with `t.Errorf`, and returned
"outlived the render" whatever the kill answered. On the loaded runner the grandchild ended
between the last check and the test's kill: the kill answered ESRCH. The process did not
outlive the bound in any sense that matters, yet the step drew two failures.

Zombies: `alive` (now the `ended` probe) is `procend.Ended`, which counts a zombie whose every
thread is gone as ended (issue #182), so a reaped-late orphan was never the cause. One narrow
window is left: a process seen with threads still exiting at the last check and a zombie by the
kill makes the kill succeed (a kill of a zombie is not ESRCH). With the bound below, that needs
a SIGKILLed process to take more than 20 s to end, which is itself worth a red.

## Fix

`goneOne` now calls `outlives(pid, procs)`, whose probes (`ended`, `kill`, `pause`) are fields,
so its decision is tested without real processes:

- ended at any check, including the last: no problem, nothing killed;
- still running after the last check, kill answered ESRCH: no problem (gone between the check
  and the kill);
- kill succeeded: outlived;
- any other kill error: outlived, and the error is reported;
- a status that cannot be read: an error, no verdict, nothing killed.

The bound is raised from 250 to 1000 checks: at least 20 s, since each check also reads
`/proc`. A passing step waits only until the process has ended, so the bound costs nothing on a
green run. It stays well short of the 60 s the grandchild sleeps, so a grandchild that escaped
the group kill still outlives it and is reported. The poll stays a counted loop with
`time.Sleep` outside a `select`, which `project_realtime_bound` does not judge (it "acts on
nothing by itself"), and the bound is a constant no test can shorten; no wall-clock read
(`project_testclock`).

## Can a go/analysis rule express it?

Not at a cost worth it, so none is built; this is an open note for the owner. A rule that flags
every kill whose error is checked without an `errors.Is(err, ESRCH/os.ErrProcessDone)` in the
same function would flag the six correct test sites above, where ESRCH is a real failure:
whether "already gone" is fine depends on whether the process may end by itself, which no
syntax tree shows. A narrower rule (a kill in the same function as a `procend.Ended` call whose
ESRCH is not distinguished) is expressible but matches only the instance just fixed: a rule
with one site in the tree and a fixture to maintain. The guard against a recurrence is
`outlives`' table test.
