# Task 4.1 (R78): run.bash's checkout gate

## Where it lives, and why

- `src-go/cmd/checkout-gate` (thin main) over `src-go/internal/checkoutgate` (the judgement,
  expectations G1-G15 in its package doc). The git questions are new `internal/gitx` methods
  (`upstream.go`): git is owned by gitx under the project rules.
- run.bash's `play_batch_gate` builds and runs it through `run_go_command`
  (`scripts/lib/go-tool.bash`) in a subshell, as the consumer and vault-list wrappers do. A
  new command, not an existing one: no command judges a checkout for run.bash, and the
  closest (`checkoutpin`) belongs to another seat's work and to ccy.
- Not deployed (it runs from the checkout), so `scripts/go-binary-suites.tsv` has a `qa-go` row.
- run.bash shrank: 2771 to 2769 code lines; statements unchanged (2714). The record was
  lowered by hand on the run.bash line only.

## Decisions

- Untracked files outside `.gitignore` count as uncommitted (G2): a play can read a new file.
- A failed fetch is refused (G6); `--force` passes it, because an offline machine must still be
  able to run a play. Forced, nothing is compared, and it says so.
- No upstream is refused (G5, fix `git push -u origin <branch>`). A detached HEAD is checked
  for uncommitted changes only (G4).
- A git fault is exit 1 even with `--force` (G13), as the gate cannot say what it would override.
- Gated: `--changed` when it has plays to run (before its question), `--rerun` before its menu,
  so a pick is never thrown away. `--force` without either is refused.
- Not gated: a single play. That is what meta-deploy's playbook entries, plan deploy scripts and
  the self-update cycle run, play by play. Gating it would fetch once per play and could stop an
  unattended run that is offline. Meta-deploy's `changed-plays` entry is gated. **Open for the
  owner:** whether single plays are gated too.
- The gate prompts for nothing: it is a gate (InteractiveScripts does not apply).

# Part 2: every play run is gated

R78's fix says "before any play"; part 1 gated only `--changed` and `--rerun`.

## What run.bash runs plays through, and what each now does

- Single play (`./run.bash <play>.yml`, a play's shebang): gated after the path is checked,
  before the play lock. Shares `--changed`'s preflight now (`play_preflight`, the renamed
  `play_batch_preflight`), which paid for the new calls on the ratchet.
- `--changed`, `--rerun`: gated as before, through `checkout_gate <checkout>` (was
  `play_batch_gate`).
- `--optional-only` (menu and headless list): gated once, before either; a missing checkout is
  left to the existing "run the full install first" refusals.
- Install main playbook: gated after the last `fd_checkout ... pull` (which already requires a
  clean tree) and before `hl_ssh_agent_stop`, since an SSH fetch may need the agent. A fresh
  install is just cloned, so level; a `RUN_BASH_GIT_REF` commit pin is detached (G4).
- Not gated: the self-update cycle (the one setter of `RUN_BASH_ANSIBLE_PLAYBOOK`). Its clone
  is on a signed release, behind the branch tip by design on the release channel, so the gate
  would refuse every cycle, and `update.py` already refuses dirty, strays, ahead and diverged.
  `--consumer`: `pull --ff-only` refuses dirty and diverged and brings it level; ahead needs a
  commit a consumer cannot make or push.

## The gate's command line

`checkout-gate [--force] <checkout> [run.bash argument...]` (G14). run.bash hands it the words
it was run with (`RUN_ARGV`). The refusal now repeats that command, quoted (`internal/shellword`),
with `--force` first: `./run.bash <play>.yml --force` would have handed `--force` to Ansible.
`--force` alone is no longer refused: a plain install is gated too.
