## 13:05 · action · T1.3   — ready-wait defence committed red

The defence for "a ready-wait that ignores its child's exit" is committed red, before
any instance is fixed. It is a new gate, `scripts/qa-ready-wait-rules.bash`, run by
`qa-all.bash` as `ready-wait-rules`, with its page in CLAUDE/QA.md under
`ready-wait-ignores-child-exit`.

- **Python:** a Semgrep rule, `.semgrep/ready-wait.yml`, proven against
  `.semgrep/ready-wait.py` on every run. It reports a sleeping loop in a function that
  starts a process (`subprocess.Popen`, `asyncio.create_subprocess_*`) when the loop
  never polls, waits on, or probes that process.
- **Bash:** `helpers/ready_wait/bash_ready_waits.py` with its unit tests, proven against
  `.semgrep/ready-wait.bash` on every run. Semgrep was tried first and dropped: its bash
  parser rejected 80 of the 371 tracked shell scripts (vmtest, wsi, ccy-sessions,
  claude-yolo among them), so a rule there would have passed over them unread.
- **No rule:** GNOME JS, Ansible, starts that daemonize (`lxc-start`, `virsh start`,
  `virt-install`), and a wait in a later run of a step script. The reasons are on the
  QA.md page; those instances are fixed by hand.

How the bash rule was calibrated, from the first draft to this one:

- At first it counted any background start in the file. That gave 24 findings, most of
  them false: monitors, interactive menus, and loops in files whose only `&` was a
  fire-and-forget `gdbus emit`.
- Now it reads events in order within each function and in the top level. A start
  (`cmd &`, or a call to a function that keeps a `$!`) arms the scope. A sleeping wait
  after it, or in a function called after it, is reported. A `wait` on the child or a
  `;;` disarms the scope.
- Two shapes stopped counting as waits: a loop that runs its whole course (a `for`, or a
  `while true` / `while ((SECONDS < end))`, with no break, return or exit), and a
  function started with `&`.
- The first lexer paired the inner quote in `"$( ... "x" ... )"` with the outer one and
  blanked the rest of `test-wsi-stop-grace.bash`, which hid instance #12. A test pins
  this case.

## 13:18 · action · T1.3   — ready-wait instances fixed, bar the originating one

Every ready-wait instance except the originating one (Task 2.1) is fixed. The gate now
reports only `files/home/.local/bin/wsi-stream:793`. The full sweep, comparing the rule
with the independent search, is in
`subagent-reports/261005-task-1-3-opus.md`.

Fixed, by search number:

- **#3, #4: `tmate-share`, `tmate-full`.** Each try reads tmate's liveness first, then
  the URL. A tmate that exited stops the wait at once with its status, and its own error
  is already on the terminal. Checked against a stub tmate that dies: exit 1 within a
  second, where the old loop took 15 s and then blamed the URL.
- **#5: the panel's launch debounce.** The extension now spawns recorders through
  `recorderLaunch.js` (`Gio.Subprocess` and `wait_async`). A recorder that fails before
  its first StateChanged ends the debounce at once, and the notice says how it ended.
  A clean exit before the report is only logged, because `wsi-article-window` hands a
  second launch to the window already open and exits 0. Tests are in
  `tests/extensions/test-stt-recorder-launch.mjs`. The play deploys the new file, and
  Plan 00148's acceptance checks it.
- **#6: `docker-in-lxc` `wait_for_container_network`.** Each try reads
  `lxc-info -sH`, and a container that is no longer RUNNING or STARTING is an error that
  names its state.
- **#7: `vmtest` `wait_for_ssh`, and the wait for the autologin session.** A new
  `guest_must_be_up` reads `virsh domstate` on every try, and "shut off" or "crashed"
  dies at once. `test-vmtest-reboot-dispatch.bash` cases 8 and 9 cover it. A control
  run against HEAD's `wait_for_ssh` fails case 9: 120 sleeps, then "did not answer SSH
  within 600s".
- **#9, #10: Ansible.** firewalld's readiness probe and the ydotool socket wait now run
  `systemctl is-active` in the same retried command. They stop at rc 3 with the unit
  status, and `failed_when` turns that into the failure.
- **#11 to #14: the test harnesses** (`test-self-update-cycle`,
  `test-wsi-stop-grace` `wait_for_recording_state`, `test-ccy-sessions-reboot`,
  `test-ccy-session-registry`). `kill -0` runs on every try, before the readiness
  check, so a child that is already gone fails the wait at once with its output.
- **#16: Plan 00055 `acceptance.bash`.** The spinner's `lxc-attach` pid is kept and
  checked with `ps -p` (it runs under sudo, and `kill -0` is refused on a root process).

Not fixed, with the reason:

- **#8: `helpers/vmtest/serial_console.py`.** It starts nothing. Once connected, a
  QEMU that dies closes the socket, and the read ends at once with a named stall. Only
  the connect retry (at most 60 s) cannot tell a QEMU that died from one between
  `bind` and `listen`. It ends with the socket's own errno, and telling the two apart
  would need the domain, which the helper is not given.
- **#15: Completed Plan 00111 `insulation-steps.bash`.** The start and the waits run in
  separate invocations of the step script, and the pid travels in a file. Several
  steps kill the fake terminal on purpose and then wait for the effects, so a generic
  liveness check in `wait_for` would be wrong for them. Each wait is bounded (15 to
  60 s) and names what it waited for. The plan is complete, and the script is kept as
  its record.

## 13:22 · action · T2.1   — wsi-stream names a server that died while loading

Task 2.1 is applied, and the ready-wait gate is green: 0 findings over 592 files.

The held draft was re-applied by hand to the current `wsi-stream`. Task 2.4's
`ModelNotDownloaded` path is unchanged: `resolve_model` runs before the wait and still
raises to its callers. The fix goes past the draft in two places, both found while
re-applying it:

- **The "already loading" path (search #2).** With no handle, the loop now asks
  `server_pid_alive()` (the server's flock) on every try. A server started at login
  that dies while loading is reported at once, like one this client started.
- **A start race.** `wsi-stream-server` exits 1 when another server holds the lock,
  and logs "Server already running" into the running server's log. The draft would have
  reported that loser's exit as a failure while the winner was still loading. Now, when
  the server it started has exited but the lock is held, the client waits for the
  winner. `server_failure()` skips the loser's line, so a winner that later fails is
  named by its own error.

`tests/speech_to_text/test_server_start.py` has 6 cases and is wired into
`test-wsi-stop-grace.bash`. A control run with `STT_TEST_BIN` pointed at HEAD's
`wsi-stream` fails 4 of them, all with "RuntimeError not raised". The two that pass
there are regression guards: a server that comes up, and the start race. All 6 pass
against the fix. `held/` is removed.
