## What checks out

- **Player identity.** M1 lists names, resolves each with GetNameOwner, and pauses or plays
  only by the unique name. M5 checks that the unique name is still in ListNames, which includes
  unique names, before Play. So a player that is restarted under the same well-known name is
  not resumed. Two names on one connection count as one player. Both cases are tested.
- **Only what it paused.** A player is paused only if it is Playing and CanPause. It is
  resumed only if it is still Paused. Stopped, Playing or gone is left alone, with a line on
  stderr.
- **Release before pause has finished.** `signal.Notify` runs first in main, and the channel
  has a buffer of 4. A TERM that arrives while players are still being paused waits in the
  channel, then resume runs at once. A TERM that arrives before `Notify` kills the process
  before it has paused anything, which does no harm.
- **Process lifecycle.**
  - The hold is spawned through `setsid`, which execs, so its PID is the real PID and its
    parent is GNOME Shell.
  - Escape's group KILL of a batch recorder does not reach the hold, which is in its own
    session.
  - The panel releases the hold on: every state that is neither starting nor microphone-open,
    Escape, the recorder's exit, a spawn failure, `_finish`, and `destroy()` (extension
    disabled).
  - The release is sent once, and never after the hold has exited, so a reused PID is not
    signalled.
  - If GNOME Shell dies, the 1 s `Getppid` poll resumes the players.
  - No processes are leaked.
- **The toggle.** Its GSettings key `pause-media-while-recording` defaults to true. It is
  written the same way auto-paste is and synced through the `changed` handler. It is read at
  each recording's start.
- **Continuous and unlimited dictation.** The state stays RECORDING through the interim
  pastes. In wsi-stream, TRANSCRIBING is sent only once the microphone has closed (stop during
  the model load, the finalise). So the release does not fire in the middle of a dictation.
- **Pause failure is reported and dictation goes on.** This is acceptable. Nothing fails
  silently: the error goes to the journal and to `Main.notify`. The dictation does not depend
  on the media, so stopping it would be wrong.
- **busctl parsing.** The `call` output is `{"type","data":[args]}`. The two-property
  `get-property` output is two JSON values in a row, read with one `json.Decoder`. The type of
  each value is checked, and a reply that is not busctl's JSON is a tested failure.
- **Acceptance.** It runs the installed binary and the real busctl against a fake player on a
  private bus.
  - `dbus-run-session` sets `DBUS_SESSION_BUS_ADDRESS`, and sd-bus's `--user` honours it before
    `$XDG_RUNTIME_DIR/bus`, so no real player is reachable.
  - It has the R1 bootstrap, `plan_require_host`, gather legs, usage and exit 64, and a
    `timeout 60` bound.
  - Plan-folder scripts are exempt from the bash limits.

## Findings (not blocking)

1. **Low/medium: one broken MPRIS player raises an error on every recording.** A player that
   fails GetNameOwner or get-property is reported by M6 and makes the run exit 1. Examples are
   a player with no `/org/mpris/MediaPlayer2` object, or one with no CanPause property (some
   Electron apps, or a GSConnect phone that has gone away). With exit 1, `mediaHold`
   shows an "STT Error" notification and sets `_lastError` on every dictation, for as long as
   that player is on the bus. Consider one of these:
   - report a player that cannot be read as stderr only, without exit 1;
   - only notify once per player name per session.
     A Pause or Play that fails should stay loud.
2. **Low: a stale status read can leave music paused after a very short recording.** Some
   players, Spotify among them, update PlaybackStatus after Pause has returned. If TERM arrives
   within milliseconds of the Pause, M5 can read a stale "Playing", leave the player alone,
   and then the pause takes effect. The music then stays paused. This needs a sub-second tap,
   so it is rare. A short re-read before deciding "left as it is" would close it.
3. **Low: two holds can overlap on back-to-back recordings.** Hold 1 may still be resuming
   when hold 2 lists the players. Hold 2 can then see "Paused", not remember the player, and
   hold 1 then plays it during recording 2. In practice this is unlikely: Insert is refused
   until recording 1's session ends (SUCCESS), well after the TERM at TRANSCRIBING. It is not
   tested and not documented.
4. **Low: `dbus-daemon` is installed on every host for the acceptance only.** It is there for
   `dbus-run-session`. `python3-gobject` is justified: `wsi-article-window` imports `gi` and
   the play was missing it. `dbus-daemon` is a test-only dependency in a production play.
   It is small and the play comment says why, so it is acceptable, but the PLAN could say so.
   The `systemd  # busctl` line has no effect, because systemd is always installed. It is
   harmless.
5. **Info: a screen lock resumes the music.** `destroy()` runs when the extension is disabled
   at a screen lock, and it resumes the music while the recorder may still run. This is
   documented as a decision, but the owner may find it surprising.
6. **Info: the panel side is checked only by hand.** Its release paths are covered by the Node
   tests. The acceptance exercises the real binary and busctl, and the owner's manual check
   covers the GNOME path. That split is appropriate.
