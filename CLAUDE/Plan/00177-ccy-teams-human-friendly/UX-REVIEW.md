# Plan 00177: ccy-teams critical UX review (Task 1.1)

A harsh pass over every verb, key, prompt, message and failure path of `ccy-teams`
(`files/home/.local/bin/ccy-teams.j2`) and its `create` helper
(`helpers/agent_bus/declare.py`), as built by Plan 00161 and first used by the owner on
the host. Each finding has a severity (**H** high: blocks or misleads a first-time user;
**M** medium: costs time or confidence; **L** low: polish) and the fix this plan makes.
F4 to F7, F10, F22 and F23 take in the owner's feedback, relayed during the work; where
it changed a fix, the owner's version is the one written here.

## What the owner's first run actually was

```text
$ ccy-teams
ccy-teams reads each team's members with sudo agent-bus list.
[sudo] password for <user>:
Sorry, try again.
[sudo] password for <user>:
Sorry, try again.
[sudo] password for <user>:
No agent teams on this machine. ccy-teams create declares one.
```

The plan's overview reads this as "three failed passwords, then a false 'no teams'". The
code says otherwise. The picker's first act was an unconditional `sudo -v`. When sudo
gives up after three wrong passwords it prints `sudo: 3 incorrect password attempts` and
exits 1. ccy-teams then printed "sudo refused, so the members cannot be read" and exited

1. Neither line is in the paste. So two passwords were wrong and the **third was
   accepted**. ccy-teams then found no team declared present in `agent_bus_teams` and no
   `agent-bus-hs@*` unit loaded. "No agent teams" was true. (Whether the host_vars really
   held no team is the owner's to confirm. A declared team is listed even when it is not
   installed, so the message cannot come from a team that is declared.)

That this host asked for a password at all also says the desktop profile's
`NOPASSWD: ALL` block (play-basic-configs.yml) is not in force there. ccy-teams cannot
assume passwordless sudo.

The real defects were that sudo was demanded **before anything needed it**, with no
reason the owner could weigh, and that a true "no teams" was a dead end. The class to
close is wider than this run: any path where a failed step can look like an empty or
normal answer. The sweep below found no live instance. A refused sudo exits 1 with a
message. A failed member read marks the team "members unknown". A failed host_vars read
or systemctl call exits 1. The class is now closed by construction rather than by luck.
Every sudo goes through one helper that explains first, tells a refusal apart from a
command failure, and exits non-zero with words for the refusal. A row whose members are
unknown says why. Tests pin "sudo refused is never 'no teams'".

## The sudo decision

**Chosen:** a scoped `NOPASSWD` sudoers rule, `/etc/sudoers.d/agent-bus-read-only`,
installed by `play-agent-bus.yml` with `validate: visudo -cf %s`. It covers two read-only
commands and nothing else, each pinned to an exact argument shape by sudo's anchored
regular expressions (sudo 1.9.10 and later):

- `/usr/local/bin/agent-bus list <team>`
- `/usr/local/bin/agent-bus human devices <team> <human>`

The team and human patterns use the protocol's character classes without its length bounds
(`[a-z][a-z0-9-]*`, `[a-z][a-z0-9_-]*`). A bound such as `{0,23}` would need its comma
escaped in sudoers, and `agent-bus` refuses an over-long name itself. Neither pattern can
start with `-`, so no option can be smuggled in, and the anchors refuse any extra argument.

**Why it is safe enough.** Both commands are read-only by construction (`cli.py`:
`list` is "members, roles and room membership; no tokens"; `human devices` prints device
IDs and last-seen times, nothing a client named itself). The `agent-bus` wrapper runs
them as the unprivileged `agent-bus` user through `runuser`, and their output holds no
secret. What a process running as the desktop user gains is the names of a team's
members and humans, their roles, and when the humans' devices were last seen. That is
less than the user can already read in the team room through Element. The rule grants
no write, no token, no password and no shell. On a desktop-profile host the user already
has `NOPASSWD: ALL`, so the rule adds nothing there. It matters only where full sudo
asks for a password, which this host does.

**Rejected:** a non-root-readable listing, such as a world-readable cache written by the
homeserver host or a group-readable state directory. It would mean changing the bus
(`/var/lib/agent-bus/<team>` is 0700, holding the admin token beside the registry), which
is a non-goal. It would also make the list stale between writes. Keeping sudo for every
read was also rejected: a password prompt to *look* at a table is what drove F1.

**Still behind a password** (when sudo needs one): setting a human's password, parking a
member, backup and restore. Each changes state, and each now explains itself before the
prompt.

## Deferred, by the owner's instruction

- **D1. Password storage, retrieval or a non-sudo route.** Today a human's password is
  set anew and printed once (it is stored nowhere), through sudo. Keeping it, fetching it
  again, or setting it without root each needs its own protection design: where the
  secret lives, who may read it, and how a stolen desktop session is bounded. That is
  not built here.
- **D2. create writing the Element profile entry too.** Next step 2 still asks for one
  line in `agent_bus_element_teams`. Adding it automatically needs declare.py to edit a
  second key. That is worth doing once the edit shape has settled; it is not in scope
  now.
