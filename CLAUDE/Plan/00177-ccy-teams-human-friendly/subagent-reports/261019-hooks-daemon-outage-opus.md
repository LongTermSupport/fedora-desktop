## Mechanism

### Proven (source and reproduction)

1. **One semaphore of 16 for the whole process, refuse instead of queue.**
   - `core/bounded_dispatch.py:60` sets `DISPATCH_MAX_INFLIGHT = 16`, and nothing in config changes it.
   - `chain.py:758` runs each event's whole handler loop as one dispatch.
   - `bounded_dispatch.py:243` does a non-blocking acquire, so call 17 is refused.
   - `repro_saturation.py` shows the refusal in 0.001 s.
   - Every refused chain that holds a SAFETY+BLOCKING handler is denied (`chain.py:799-804`). Other
     chains are "Chain skipped".
   - The ~0.2 s refusal times in the transcripts match an instant refusal.
2. **Stop is denied, which loops the agent.**
   - `cron_stop_enforcer` and `usage_pause_stop_gate` are SAFETY+BLOCKING, so the whole Stop chain
     fails closed.
   - This is the opposite of the client, which fails Stop OPEN on `socket_timeout` (`init.sh`, Plan 00177).
3. **No way out from inside a session.**
   - The client's recovery carve-out (`init.sh:160-161`, `_is_daemon_recovery_command`) applies only to
     transport failures.
   - A saturated daemon still sends a well-formed deny, so even the exact exempt command was denied
     (transcript, 09:11:25/09:11:32).
   - The Skill tool is gated the same way, so `/hooks-daemon health`/`restart` cannot run.
   - The skill's own `daemon-cli.sh restart` is not an exempt spelling at all.
4. **The watchdog does not cover this case.** `server.py:2156` self-restarts only on the straggler cap or
   on straggler age. If the 16 slots are held by live, slow chains, the straggler count can be zero.
5. **SIGKILL every time under load.** `server.shutdown` waits up to 5 s for active requests
   (`server.py:2192`). The CLI's SIGTERM grace is also 5 s (`Timeout.SOCKET_CONNECT`, `cli.py:1394`), so
   the request wait alone uses up the grace.
6. **The upgrade replaced the venv and source under a live daemon.** Upgrade output shows the in-place
   venv rebuild, and the old daemon detected the version change at 09:07:13.

### Inferred (consistent with evidence, not measured)

- **Root cause: ordinary concurrency, not a flood.** About 12 sessions shared one daemon, with parallel
  tool calls, PreToolUse + PostToolUse + PostToolBatch per call, plus status-line and Stop events. Chains
  took seconds under host load (Python GIL plus CPU contention). That alone keeps 16 chains in flight,
  so the cap of 16 is too small for this fan-out.
- **A cycle sustained it.** Slow chains, mainly subprocess linters (`lint_on_edit` with a 15 s Go lint
  timeout inside a 20 s budget), overran and kept running as stragglers using CPU. Refused agents
  retried at once ("Tool calls batched with this one may ALREADY HAVE RUN"). That explains why the
  09:12 restart re-saturated within 30 s and why the daemon showed 139% CPU 31 s after starting.
- **Two daemons at once: no evidence.** One socket per project path. Each restart reported a clean stop,
  or a SIGKILL, before the start.
- **Role of the upgrade: the trigger, not the cause.**
  - Latency was already at the budget at 09:04, before the upgrade began.
  - The upgrade then added CPU (venv rebuild), a cold daemon start (CLAUDE.md injection, asset deploy,
    retention sweeps, cold caches) and a reconnect from every session at once.
  - The owner's 09:14 restart probably "worked" partly because the load had eased: agents had stalled
    or finished.
- **The 09:09:24 restart:** the cause is unknown. A watchdog restart at straggler capacity is plausible,
  but its log was lost.

## Recommendations for this repo (proposed, not applied)

1. **Cap concurrent sub-agents at about 6 per daemon** while the host is loaded, and lower it further
   when other host workloads push the load average above the core count. 3.70.0's `spawn_rate_advisor`
   has a `max_concurrent` live-agent cap. Consider setting it in `.claude/hooks-daemon.yaml`
   (owner's decision; I did not edit config).
2. **Never upgrade or restart the daemon while agents are running.** Add a line to the upgrade procedure
   in project docs (`CLAUDE/AgentNotes.md`): let agents finish or pause them, then upgrade, then resume.
3. **Stagger heavy test suites across agents.** Run them one at a time where possible: the
   `subagent_full_qa_blocker` pattern already limits `qa-all`, and suites run per agent add to the
   same CPU load.
4. **Look at `lint_on_edit` timeouts.** Go lint taking 15 s inside a 20 s chain budget means one
   edit can use up the budget. Lower the per-linter timeout, or exclude worktree paths if they are
   linted twice. This is an owner decision because it weakens a guard.
5. **Recovery runbook while upstream is unfixed.** When "dispatch pool saturated" repeats, the owner runs
   the restart from a terminal outside the session; no in-session path works. This is the same as
   today, but it should be written down.
6. **Note:** the daemon start auto-committed a CLAUDE.md regeneration (7c617e40) straight onto F44 in
   the shared checkout during the upgrade. Owner may want to check that this is wanted.
