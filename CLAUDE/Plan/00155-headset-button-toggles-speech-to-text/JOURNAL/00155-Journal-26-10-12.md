> **Append-only activity log** for plan 00155. One file per day
> (`00155-Journal-YY-MM-DD.md`). `PLAN.md` tracks the plan (what/why,
> current state, tasks); this journal tracks what actually *happened* —
> findings, decisions, dead-ends, hand-off state — the linear lifecycle a plan
> document structurally cannot carry.
>
> **Entry grammar** — append new entries at the BOTTOM; NEVER edit earlier
> entries (corrections are new entries):
>
> ```
> ## HH:MM · category · REF   — optional short title
> ```
>
> - `HH:MM` UTC 24h (the date is in the filename, also UTC); times increase
>   down the file. A file with no sentinel line above predates this system —
>   its times are local, zone unrecorded (legacy; never rewritten).
> - `category` ∈ `action` | `finding` | `decision` | `thought` | `blocker` | `handoff`
> - `REF` = optional task/phase ref (`T1.2`, `P1`) or `—`.
> - Bodies may embed fenced logs/diffs/snippets — no size limit — with a
>   one-line takeaway above the fence.
> - End a working session with a `handoff` entry so the next agent's entry
>   point is the last entry of the newest day-file.

## 09:04 · finding · —   — Button: KEY_PLAYCD in A2DP, AT+CHUP in HFP (consumed by PipeWire)

Live capture on the host with the owner pressing the button (OpenRun Pro). Tools:
a read-only evdev reader on the headset's `(AVRCP)` node, and `btmon` (bluez,
already installed) for the raw ACL traffic. Raw captures stay under `untracked/`.

**A2DP (idle, music mode): detectable as a key.** Each single press arrived as an
AVCTP passthrough `PLAY` (op 0x44 pressed, 0xC4 released) and as `KEY_PLAYCD`
down/up on the evdev node. The headset sends `PLAY` both to start and to pause
music, so H1 is refuted in its alternating form: one code, `KEY_PLAYCD`, for every
single press. GNOME's media handling toggled the player as well.

**HFP (headset mic recording, i.e. during a dictation): not a key.** A press during a
dictation arrived only on the HFP RFCOMM link as `AT+CHUP` (hang up). PipeWire's
native HFP backend (inside WirePlumber) answered `ERROR`, because there is no call, and
nothing else happened. The evdev node received nothing. So F5 is confirmed, and the
stop press is invisible to any evdev listener.

Not yet captured: a double press and a long press. The owner's run covered single
presses in A2DP and one press in HFP.

Consequence for the design: a listener can start a dictation from evdev
(`KEY_PLAYCD`), but stopping one needs the `AT+CHUP` that WirePlumber consumes. Open
research: whether PipeWire 1.6's bluez5 backend exposes call-control commands
(its telephony D-Bus interface, or a WirePlumber hook), or whether `AT+CHUP` can be
observed by another supported route. Raw HCI monitoring needs root and is a last
resort.
