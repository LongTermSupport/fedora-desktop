# Plan 00169 — Journal 26-10-10

_Scaffolded by `mkplan.bash`; timestamps in this file are UTC._

> **Append-only activity log** for plan 00169. One file per day
> (`00169-Journal-YY-MM-DD.md`). `PLAN.md` tracks the plan (what/why,
> current state, tasks); this journal tracks what actually *happened* —
> findings, decisions, dead-ends, hand-off state — the linear lifecycle a plan
> document structurally cannot carry.
>
> **Entry grammar** — append new entries at the BOTTOM; NEVER edit earlier
> entries (corrections are new entries):
>
> ```
> ## HH:MM · category · REF   — optional short title
> ```
>
> - `HH:MM` UTC 24h (the date is in the filename, also UTC); times increase
>   down the file. A file with no sentinel line above predates this system —
>   its times are local, zone unrecorded (legacy; never rewritten).
> - `category` ∈ `action` | `finding` | `decision` | `thought` | `blocker` | `handoff`
> - `REF` = optional task/phase ref (`T1.2`, `P1`) or `—`.
> - Bodies may embed fenced logs/diffs/snippets — no size limit — with a
>   one-line takeaway above the fence.
> - End a working session with a `handoff` entry so the next agent's entry
>   point is the last entry of the newest day-file.

## 09:38 · finding · —   — Phase 1 passes on the host; image builds fail on agent-browser's Chrome download

Phase 1 passed on the host on 2026-10-10: triage before and after, the deploy, and acceptance at 24 of 24. The deploy rebuilt claude-yolo:latest as 2.50. In the repository with `extensions.relativeWorktrees` under `repositoryformatversion 1`, the image's git 2.39.5 refused it. The launch exited non-zero and printed git's "unknown repository extension" line and the entrypoint's "cannot read /workspace" line, and Claude never answered. In a plain `git init`, the launch exited 0, the entrypoint named the git that read /workspace, and Claude answered READY. The host's git is 2.55.0. The base image was the registry's current one, and `--pull` appears nowhere in the builds. Before that, the same run's 00165 deploy failed while building the same image, and so had the run before it. Both failures were in `agent-browser install`: all three of its attempts at the 190 MB Chrome for Testing zip timed out at 75 to 90 per cent. agent-browser's own download gives each attempt 120 seconds in total, hard-coded (cli/src/install.rs, `http_client`), so on a link below about 1.6 MB/s it can never finish. The 00169 deploy's build got through only because the link was faster at that moment. The Dockerfile now fetches the same Stable zip with curl, resuming across passes, into the folder `agent-browser install` checks; the install then reports it as already installed (container 2.51).
