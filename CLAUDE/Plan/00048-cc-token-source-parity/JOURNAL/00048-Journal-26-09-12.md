## 15:40 · finding · T4.3 — `cc` silently switches account when no token passes the guessed expiry stamp

Reported symptom, user's words: "the cc command on desktop does not seem to be
using ccy tokens for some reason", on a laptop freshly upgraded F43 → F44 with
`play-claude-code.yml` and `play-claude-yolo.yml` re-run.

Traced in the checkout and verified line by line. The two launchers answer
"no valid token" in opposite ways:

```
token-management.bash select_token()
  1043-1050  host mode, token dir missing  -> banner, SELECTED_TOKEN="", return 0
             container mode, same          -> return 1
  1093-1102  host mode, zero VALID tokens  -> banner, SELECTED_TOKEN="", return 0
             container mode, same          -> return 1
```

`cc:162-165` reads an empty `SELECTED_TOKEN` as "Desktop" and launches plain
`claude` against host `~/.claude/` OAuth. `claude-yolo:1099-1115` treats the
non-zero return as a hard stop ("You must create a new token") and exits 1.

So **`ccy` can never run without a named token; `cc` silently runs as a
different account.** No error, no non-zero exit, no prompt — only a banner that
scrolls past. That is the reported symptom exactly.

### Why it surfaced now

Validity is decided by a **guessed** date baked into the filename, not by the
token's real expiry:

```bash
# token-management.bash:741-746
# Use conservative 90-day expiry estimate
# NOTE: claude setup-token doesn't tell us when the token actually expires,
expiry_date=$(date -d "+90 days" +%Y-%m-%d)
```

and `is_token_valid` (`common-pure.bash:113-119`) treats `expiry_date < today`
**or `== today`** as expired. Tokens minted during this plan's June host work
(2026-06-10 / 2026-06-18) stamp out at 2026-09-08 … 2026-09-16. Today is
2026-09-12, so some or all of the pool has just crossed the stamp — while very
possibly still authenticating fine. `ccy` reacts by demanding a fresh token, so
it always ends up on a valid one; `cc` drops them from the menu and falls
through to Desktop.

A rebuilt `$HOME` on the new F44 install reaches the same branch by the other
route: `play-claude-yolo.yml:408-424` creates the token tree but never
populates it, so the pool is empty.

### The defect is a conflation, not the Desktop fall-through itself

An empty pool falling through to Desktop **is** designed — PLAN.md Goals ask
for exactly that ("Empty pool: Desktop is the only option and a one-shot banner
explains `ccy --create-token`"). The bug is that `1093-1098` cannot tell
"pool is empty" from "pool has tokens, all past a guessed stamp". The first
deserves the short-circuit; the second must not silently change account, and
the same Goals require Desktop to be "explicit, not silent".

Task 4.3 — empty-pool banner and Desktop fall-through — is the one Phase 4
check never executed. It is precisely this branch.

## 15:40 · handoff · T4.3 — awaiting a decision on the fix shape, immediate workaround available

**Immediate unblock for the user, no code change:** `ccy --create-token` mints a
freshly stamped token and the symptom disappears.

The code fix is a real choice and touches `select_token`, which **both**
launchers call — so a mistake breaks `ccy` too, and it cannot be tested in the
CCY container (no `claude` binary, no token pool). Deliberately not guessed.
Two shapes, both satisfying the Fail Fast rule:

- **A — hard stop (minimal).** In host mode, short-circuit to Desktop only when
  the pool holds no token files at all; when files exist but none pass the
  stamp, `return 1` as container mode does. `cc:86` calls `select_token` bare
  under `set -e`, so cc exits with the expired list and renew instruction
  already printed by `1071-1091`. ~6 lines, no menu changes, container mode
  untouched. Cost: Desktop becomes unreachable via `cc` while the pool is
  stamped out (plain `claude` still works).
- **B — Desktop as a keypress (better UX, more risk).** Render the menu with
  stamped-out tokens listed and selectable, plus Desktop as `d`. Because the
  stamp is a guess, a working token stays usable. Needs changes in the redraw
  loop from `1108` down, which is shared with container mode.

Either way: `CCY_VERSION` bump required in the same commit (lib change), then a
host deploy of `play-claude-yolo.yml` and `play-claude-code.yml`.

Three further hardening items found in the same read, none of them today's
symptom, all in `cc`: `$HOME/.claude` is hardcoded at `cc:56`/`cc:128` so a set
`CLAUDE_CONFIG_DIR` makes the credential parking target a file Claude Code is
not reading; the park at `cc:155-161` is never asserted, so a failed park
degrades silently to Desktop auth; and the self-heal at `cc:64-66` skips when
both files exist, after which `cc:156`'s `mv -f` destroys the parked Desktop
credential. Worth folding into whichever fix is chosen.
