## 07:33 · finding · T1.3 — redaction bug caught by testing, not by reading

`redact()` originally used `[A-Za-z]{2,}` in its email pattern. The container's
awk is **mawk 1.3.4**, which ignores `{n,}` intervals unless built with
`--re-interval` — so the pattern matched literally and the substitution did
**nothing**. A test email sailed straight through into the report:

```
$ echo "a@b.test" | awk '{ gsub(/[A-Za-z]{2,}/,"X"); print }'
a@b.test
```

Rewritten as `[A-Za-z][A-Za-z]+`, which mawk and gawk both honour. Worth
recording because the HOST is Fedora (**gawk**, where `{2,}` works) — the bug
would have stayed invisible had this only ever been reviewed by reading, or
only ever run on the host. This is the exact failure shape PlanTriage.md warns
about: assume your redaction is wrong and check it.

## 07:34 · finding · T1.3 — `paths(scalars)` silently drops null leaves

the optional field most likely to arrive null. Replaced with an explicit

now appears in the report.

## 08:10 · finding · T3.7 — an unreachable endpoint BROKE the whole menu

First implementation, tested with the stub server killed: the menu printed **no
token rows at all**. Chain: curl fails to connect → never creates its `--output`
file → `chmod`/`mv` on the missing file fail → subshell dies under `set -e`
before its `exit 0` → `wait` returns non-zero → `set -e` in the caller aborts
the render.

Exactly the failure the plan's Decision 2 forbids ("must never block a launch"),
and it only showed up because the failure path was actually exercised. Fixed by
making the worker record outcomes rather than raise them: both cache files are
always created, the worker unconditionally exits 0, and a failed `wait` is
explicitly handled and skipped.

## 08:14 · finding · T3.7 — jq, not the network, was the real cost

Cached renders were nearly as slow as uncached ones — 239 ms warm vs 268 ms cold
for 2 tokens, against a 71 ms feature-disabled baseline. Cause: `jq` was run once
per row at display time, ~40 ms each.

Restructured so the parallel worker parses and renders, and the cache stores the
finished line. The display path now runs no `jq`, no `curl`, and no subprocess
beyond two small file reads; `colorize_usage` finds its worst percentage in pure
bash (a here-string and a loop) instead of `grep | tr | sort | head`, which alone
was ~39 ms per token. Warm went 239 → 112 ms for 2 tokens.

Side benefit worth keeping: the raw response is no longer written to disk at all,
so account details in the payload do not outlive the fetch.

## 11:24 · action · T4.2b — triage.bash extended to settle F8

Three changes, all aimed at removing the ambiguity rather than arguing about it:

- **Sequential by construction.** The script loops tokens one at a time, so our
  own parallel burst is not a variable in its results.
- **Retry once on 429**, after a 5 s pause. A token that answers 401 on retry was
  always going to be refused; one that answers 200 was accepted and throttled.
- **`/api/oauth/profile` route discriminator** — status only, body never captured
  (it carries the account email, and there is no reason to put that on disk to
  answer this). Reading:
  - `profile 200 + usage 401` → valid on OAuth routes; `/usage` refuses it
    specifically.
  - `profile 401 + usage 401` → setup-tokens are not OAuth-route credentials at
    all. Q1 = no, unambiguously.
  - `profile 200 + usage 200` → it works; the 401s were something else.

Verified end to end against a stub for both routes. shellcheck-clean.

Recorded as Task 5.0: if Q1 is even partly yes, the parallel burst itself needs
revisiting — it may manufacture spurious `usage: rate limited` rows. The measured
fallback is a single `curl --next` chain (416 ms for 5 vs 203 ms parallel —
slower, but one connection and one request stream).

## 11:40 · finding · T4.2b — F9: DECISIVE. Q1 is NO, and the reason is a named missing scope

`triage.bash` run on the HOST. All four tokens, both routes, 403:

```
<token-a>  /usage 403   /profile 403
<token-b>  /usage 403   /profile 403
<token-c>  /usage 403   /profile 403
<token-d>  /usage 403   /profile 403
```

Body:

```json
{
  "type": "error",
  "error": {
    "type": "permission_error",
    "message": "OAuth token does not meet scope requirement user:profile",
    "details": { "error_visibility": "user_facing" }
  }
}
```

Three things settled at once:

1. **Q1 = NO.** Not "wrong credential type" — a setup-token *is* an OAuth token,
   it simply lacks `user:profile`, which both `/usage` and `/profile` require.
   The scope is fixed when `claude setup-token` mints it, so nothing client-side
   can obtain it.
2. **The 429 was ours.** Sequential probing returned 403 for `<token-c>`
   too. The parallel burst had tripped an IP throttle, exactly as the first of
   the two readings predicted. Good thing it was not called on 3-of-4.
3. **The route discriminator did its job** — `profile 403 + usage 403` is the
   "not authorised on OAuth routes at all" branch, distinguishing this from a
   `/usage`-specific refusal.

Deployment state in the same report confirmed lib 1.7.0, CCY 3.32.0, repo vs
deployed IDENTICAL — so the 403s are the endpoint's answer, not stale code.
