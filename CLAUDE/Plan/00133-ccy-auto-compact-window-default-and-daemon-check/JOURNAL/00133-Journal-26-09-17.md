## The 600k default was wrong, and the entry above is why it survived

`600k` was not a valid way to write 600,000 for this variable. Sessions launched with it
auto-compacted almost immediately — the behaviour of a 600-token window, consistent with
the suffix being dropped and the digits taken literally. 3.58.1 sets `600000` and sessions
run to normal length. The owner found this, from a session that was visibly broken.

The entry above is the interesting part of the failure, because it is not a case of
missing the principle. It states the principle correctly — presence is not force, only a
further check separates them — and then treats having stated it as discharging it. The
rigour went into the prose. Task 4.3 was left open and described as a bookkeeping
formality for the owner, when it was the step standing between a deployed default and a
session that could not hold a thought.

What was available and not used:

- **the session itself was the experiment.** It was running on the value under test and
  compacting constantly. That is not a subtle signal. It went unread because the check had
  been framed as something to *arrange* later on the host, rather than something the
  current session was already, involuntarily, performing;
- **the parse claim was never established, and was already documented otherwise.**
  `docs/ccy.md` asserted that `600k`, `600000` and `600` were "the same figure". That
  sentence was written from plausibility. Upstream's model-configuration page says the
  opposite in as many words: the `k`/`M` suffix belongs to the `/autocompact` command and
  the `--autocompact` flag, and *the environment variable accepts only the plain token
  count*. This was not an undocumented corner — it was one lookup away, and the lookup was
  never made. An invented spec is the root cause; every later check inherited it and none
  could contradict it, because they compared the environment against the launcher and the
  launcher against the invention.

The defect class this plan was written against is "a check whose clean result is
indistinguishable from a blind one". Task 4.2 turned out to be exactly that: it went green
on a value that was actively harmful, because what it compares is the environment against
the launcher — and both agreed. A check can only ever certify the thing it measures
against, so a check anchored to an unverified assumption certifies the assumption.

**Corrected**: 4.2 now records that its green result on 3.58.0 proved nothing about
correctness, and 4.3 is answered by behaviour rather than by the `/config` label —
behaviour being the stronger witness, since it separates "accepted" from "accepted and
parsed as intended", which is the distinction that actually bit. Tasks 4.4 and 4.5, the
override paths, remain owner runs and are now worth more than they looked: they are the
only remaining checks that exercise a value this project chose rather than inherited.
