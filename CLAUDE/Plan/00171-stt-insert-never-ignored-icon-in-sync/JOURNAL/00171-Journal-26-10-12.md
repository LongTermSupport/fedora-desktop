## 15:09 · finding · T5.10   — Insert while stuck stops the running recording

The stuck dictation (journal, 15:39 local): Insert cold-started client A; Insert ~11 s
later started client B instead of stopping A. B wrote its PID over A's in the PID file,
the server refused its START (`busy: recording`), and B removed the PID file at exit, so
the panel lost A and every later Insert started another refused client until A's 120 s
no-speech stop.

`wsi-stream` (server mode) now enforces one dictation at a time from the client side:

- A live recorder named in the PID file (`recorder_alive` checks `/proc/<pid>/cmdline`
  for an argument named `wsi-stream`; probed: the running `wsi-stream-server` is not a
  match, a `python3 .../wsi-stream --server-mode` argv is) is SIGTERMed (its graceful
  stop) and the new client starts nothing and leaves the PID file alone.
- A client whose stop has begun (grace, drain, paste) names itself in
  `/dev/shm/stt-stopping-$USER.pid` until it exits. Insert then only shows WAITING: a
  second SIGTERM in the grace would have cut it short (`GracefulStop.request` makes the
  stop due at once), so it is never sent.
- A START refused with `busy: recording` asks PROGRESS first: `stopping`/`draining`
  is left alone, `recording` gets STOP.

Open (Task 5.11): the owner's rule (Insert in the grace or while rendering is a no-op
with a blocked icon) conflicts with D1/D2 as built in `panelSession.js`: STOPPING is in
`MIC_OPEN`, so the panel's TERM in the grace stops at once, and a press while finishing
queues a start. Needs an owner decision.
