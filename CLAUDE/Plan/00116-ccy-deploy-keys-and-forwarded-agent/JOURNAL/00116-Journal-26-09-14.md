## 12:05 · finding · — — why ccy on a deploy-key box says "No github_ SSH keys found"

`discover_and_select_ssh_keys` lists `find ~/.ssh -name 'github_*'` and nothing else
(`lib/ssh-handling.bash:176`). A box provisioned headless with `RUN_BASH_GITHUB_ACCOUNTS=none`
has no such key by design. What it has, on the box that raised this: `~/.ssh/deploy_keys/<slug>`
(one per private repo, 0600) and a managed block in `~/.ssh/config` binding
`Host github-deploy-<slug>` to `ssh.github.com:443`, `User git`, that key, `IdentitiesOnly yes`.
The project's remote is `git@github-deploy-<slug>:owner/repo.git`. `parse_github_owner_repo`
does not recognise that form either (`:66-82`), so the push-permission probe would also skip it.

Even `--ssh-key ~/.ssh/deploy_keys/<slug>` would not have worked end to end: the probe runs
`ssh -F /dev/null` (correct — the isolation is the point) and the container never sees the
host's `~/.ssh/config`, so `git fetch` inside would fail to resolve the alias host.

The box also has no `gh` login (`gh auth status`: not logged in) — again by design — so after
the key warning, `build_ssh_mounts_and_validate` would reach the `gh auth token` fallback and
stop with "Not authenticated with GitHub CLI". A caller-supplied `GH_TOKEN` is already honoured
(`:719`); that is the way a token reaches such a box, and it is the provisioning side's job to
convey it per session.

## 12:20 · finding · T2.3 — SELinux: the socket file's label is not what blocks a forwarded agent

Measured on an Enforcing Fedora guest, rootless podman, the ccy image, an agent socket owned by
the launching user:

```
-v $SOCK:/run/ccy-agent            → ssh-add -l: Error connecting to agent: Permission denied
-v $SOCK:/run/ccy-agent:z          → file relabelled to container_file_t; connect STILL denied
--security-opt label=disable -v …  → ssh-add -l lists the agent's key
```

The denial is `container_t → unconfined_t : unix_stream_socket connectto`, a check on the
process at the far end of the socket, which no file label changes. So `--ssh-agent` must run the
container with `label=disable`, and the plan says so rather than pretending `:z` is enough. The
mount namespace still limits what the container can reach to what is mounted; what is lost is
the type-enforcement layer on those mounted paths.

## 12:25 · finding · — — the agent in a plain login session is local, not forwarded

On the same box, the login shell's `SSH_AUTH_SOCK` pointed at `~/.ssh/agent/s.*` — the socket
OpenSSH 10's `ssh-agent` now creates by default — holding one key: the box's own container key
loaded by the `.bashrc` prompt block that `play-git-configure-and-tools.yml` writes. That block
only starts an agent when `ssh-add -l` fails, so a *forwarded* agent with keys survives it. No
forwarded socket existed because the guest's sshd is `AllowAgentForwarding no`; enabling that is
the provisioning side's change and is a Non-Goal here.

## 12:30 · decision · — — resolve the alias with `ssh -G`, never by naming convention

`github-deploy-<slug>` is one provisioning system's convention. ccy is public and general, so it
asks ssh what an alias means: `ssh -G <alias>` prints the effective `hostname`, `port`, `user`
and `identityfile` lines from the user's own config, `~` already expanded. If `hostname` is
`github.com` or `ssh.github.com`, the alias is GitHub and the first existing identity file is
the project's key. Anything else is not a GitHub remote and ccy behaves as it does today.
