## 12:04 · finding · P0 — research log: mechanisms, rootless, CCY identity, tooling survey

Authoring context: inside a CCY container — `podman` is **not installed**
here, so no runtime probe was possible. Everything host-runtime below is

**Mechanism mapping.** The user's four verbs collapse to one rootless-capable
mechanism:

- `podman pause`/`unpause` = cgroup freezer. The stable podman-pause(1) page
  (docs.podman.io, fetched today) documents `--all` and `--filter` with
  filters `id, name, annotation, label, status, ancestor, before, since,
  volume, health, pod, network, restart-policy` — so **network-scoped bulk
  pause is native** (`podman pause --filter network=<net>`); the tool's job is
  selection UX + safety, not plumbing. Current stable docs list **no rootless
  restriction** on pause (older releases required cgroups v2 for rootless
  pause; Fedora has been cgroups-v2-by-default for years) → H1, verify on
  host.
- `podman container checkpoint`/`restore` = CRIU, **root-only**. Multiple
  sources agree rootless checkpoint is unsupported (CRIU needs elevated
  capabilities): podman.io/docs/checkpoint, criu.org/Podman, Fedora Magazine
  "Podman checkpoint", docs.podman.io checkpoint man page (web research
  today). Additionally CCY containers run `--rm` (claude-yolo:2944), and
  checkpoint documents rejecting `--rm` containers except with `--export`
  (H5, moot given the rootless block). → checkpoint/restore excluded as a
  non-goal; "suspend" == pause here. Frozen containers do not survive reboot.

**CCY identity.** `get_next_container_name()` (lib/common.bash:598) yields
`<project>_yolo[_N]` / `<project>_browser[_N]`. The `container_cmd run` call
(claude-yolo:2944) passes `--name` but **no `--label`**. The image carries
`LABEL claude-yolo-version="2.26"` (Dockerfile:36) and
`claude-yolo-dockerfile-hash` (Dockerfile:326); OCI containers normally
inherit image labels, so `--filter label=claude-yolo-version` *should* match
(H2, verify on host). Plan adds explicit run-time labels
(`ccy=true`, `ccy-project=<project>`) — CCY_VERSION minor bump required.

**Tooling survey** (test the "roll our own" suspicion rather than agree):

- **podman-tui** (containers org): the only Fedora-packaged Podman-native TUI
  (packaged in Fedora per packages.fedoraproject.org); needs the user
  `podman.socket`. Its docs list per-entity screens (containers, pods,
  networks, volumes, images, secrets) but do **not** enumerate container

- **lazydocker**: Docker-first (works via docker-compatible socket); not in

- **ctop**: single-container ops, largely dormant upstream; not in Fedora

- **Cockpit + cockpit-podman**: Fedora-packaged web GUI; per-container

None covers: network-scoped bulk freeze, a CCY-group verb, self-freeze

### Two facts nobody predicted — and they are the safety case

The triage was written to answer H1-H4. The container inventory it printed
answered something else:

- **A CCY container shares a user-defined network with a ten-container compose
  application stack.** Freezing "that network" to pause the app would also
  freeze a live Claude session.
- **Seven CCY containers sit on the default `podman` network.** Freezing that
  network freezes nearly every Claude session on the machine at once.

Neither is guessable from the network's name, which is exactly why the tool must
*show the resolved set before acting* rather than describe the selector back to
the user. This moves the preview from "good practice" to the feature the network
verb is unusable without, and it is now recorded as F11/F12 rather than left as
a design instinct.

Recorded as new facts rather than folded into the hypotheses table, because they
were not hypotheses — they were unknowns nobody had thought to be uncertain
about, which is the category triage is actually best at surfacing.

### Design points worth keeping

**The network verb is built around F15, not around the filter.** `podman pause
--filter network=X` already exists; what did not exist is seeing *what that
resolves to* before it happens. Every bulk path therefore resolves the set,
prints it as a table with a `CCY` column, warns with a count when live Claude
sessions are in it, and confirms `[y/N]` defaulting to No.

**A non-existent network is a hard failure, not an empty set.** `podman ps
--filter network=typo` exits 0 with no rows, which reads as "nothing is on it"
— an answer to a question that was never asked, and this repo's own defect
class. `select_network()` verifies the network exists first and lists the real
ones on failure.

**Field separator.** `podman ps --format` uses `|` rather than a literal tab: a
tab inside a Go template is invisible in a diff and easy to mangle on edit, and
neither a container name nor a network name may contain `|`.

**Acceptance cannot touch a real container.** Every state-changing check runs
against a throwaway container on a throwaway network created by the script. The
one check that must involve the real machine — that `--ccy` resolves the live
group — runs `--dry-run`. `--all` is never executed for real at any point.

**`--ccy` is checked as a contract, not by re-deriving the selection.** The gate
asserts that every running label-matched container appears in the resolved set
and that the (unlabelled, non-matching-name) throwaway does not. Recomputing the
tool's own union in the test would only prove the test agrees with itself.

**The gate refuses to vouch for a stale binary.** `acceptance.bash` `cmp`s the
deployed `~/.local/bin/podman-freeze` against the repo copy and aborts if they
differ — the Plan 00094/00076 failure mode, where the repo said "fixed" and the
machine ran the old build.

### A lint finding worth recording

shellcheck 0.9.0 reported the whole `cleanup()` body of `acceptance.bash` as
unreachable (SC2317). Probed it down to a minimal repro: with a `trap cleanup
EXIT` registered, the analyser loses the trap edge as soon as the script ends in
a **terminal `exit`** on every path. Verified in both directions — the same file
with a non-`exit` final statement is clean.

Fixed by making the final statement `[ "$FAIL" -eq 0 ]`, which yields the same
exit status. Deliberately not a `# shellcheck disable=` annotation: those are
blocked by the `qa_suppression` handler, and the annotation would have hidden a
real (if benign) analyser limitation instead of routing around it in a way that
keeps the code honest.

`deploy.bash` on the HOST: play recap `ok=4 changed=1 failed=0`, script deployed

The failing line:

```
### 9. freeze --ccy -n resolves the live CCY group
  OK   — every running CCY container is in the --ccy set
  FAIL — --ccy wrongly included the non-CCY throwaway podman-freeze-acceptance-3039955
```

**The tool was right and the test was wrong.** Two lines earlier the fixture
had printed:

```
started podman-freeze-acceptance-3039955 from localhost/claude-yolo:<project>
```

I wrote the candidate-ordering to *prefer* a `claude-yolo` image, on the
reasoning that it is certain to have a shell and so is the most reliable
fixture. It is also, necessarily, an image carrying `claude-yolo-version` — so
the throwaway container genuinely was part of the `--ccy` set, and the check
asserting its exclusion could never pass. The fixture violated the check's own
precondition.

That is a test reporting a defect that is not there, which is the same shape of
wrong answer this repo keeps finding in the other direction, and worth naming as
such rather than filing as a typo.

**Fixed** by partitioning local images with `podman images --filter
label=claude-yolo-version`, preferring unlabelled ones, and — when only labelled
images exist — making check 9's exclusion assertion `SKIP` with the reason
instead of failing. The fixture section now prints which of the two happened.

### F16, and a recommendation of mine that this reverses

The interesting part is what the accident demonstrated. `--ccy` selected a
container that was **not a Claude session** but **was built from the CCY image**,
because an inherited image label cannot distinguish the two. That is exactly the
weakness D4's first revision predicted in the abstract, now observed.

Earlier today I recommended dropping Phase 1 (the explicit `ccy=true` /
`ccy-project=` run-time labels) as YAGNI, on the grounds that the inherited
label already selected the group and nobody had asked for a per-project verb.
**That recommendation was wrong**, and this is the evidence: the inherited label
over-matches by construction, so `freeze --ccy` will pick up any CCY-derived
container on the machine. Phase 1 is re-promoted as the fix for a demonstrated
selection defect (F16, D6) rather than as a speculative nicety.

Not a blocker for shipping the tool: every bulk path already resolves the set,
prints it, and requires a `[y/N]` defaulting to No, so the failure mode is "you
are shown one extra container and can decline", not a silent freeze. But the
preview only protects a human who reads it, which is not a safety mechanism to
lean on permanently.

### Addendum — D6's rejection of option (a) was right for the wrong reason

Re-examined the D6 options while waiting on QA, because the rationale I first
wrote for rejecting (a) (narrow `--ccy` to the F4 name pattern alone) was
"the name pattern is the weaker handle", asserted with no evidence behind it.

It is not weaker. F4 comes from reading `get_next_container_name()`: CCY names
*every* container through it, so the pattern is exact by construction. On that
basis (a) looks strictly better than the union — it drops a demonstrably
over-broad signal and keeps an exact one.

The actual reason to keep the union is the **asymmetry of the failure modes**,
which the first write-up missed:

- the union's over-match is caught by the mandatory preview — you are shown one
  extra container and decline;
- (a)'s under-match is silent — a CCY session not matching the pattern would
  simply be absent, and you would believe you had frozen everything.

An invisible false sense of completeness is the worse failure, and it is this
repo's own defect class one level up. So the union stands until Phase 1
provides a signal that is both exact and positive. D6 updated to say that
instead; the decision did not change, only the reasoning that supports it —
which matters, because a right decision resting on a wrong argument does not
survive the next person re-litigating it.

## UX rework after first use — groups, derived verb, no confirm, looping menu

Four pieces of user feedback on the first build, all of them about the same
thing: the tool asked too much and offered the wrong things first.

> "forces per container selecting with tab / i wanted all ccy containers, all
> XXX network containers, all containers / i suspect most of the time i will
> want to freeze/unfreeze all at once"

> "forcing me to choose freeze/thaw is really not cool — there can only be one
> correct choice"

> "lets drop the y/n confirm, its just pointless"

> "the warning about frozen things are frozen — this is really pointless"

> "after freezing a container i should bounce back to the start screen, not get
> booted out and have to run the command again"

All five are right, and the second and third are worth recording as reasoning
rather than as compliance — see D7.

**Groups first.** The old no-arg path opened straight into a TAB-to-multi-select
container list. The group targets existed but were reachable only by knowing
`--ccy` / `--network` / `--all`, i.e. by reading `--help`. The menu now lists
all CCY containers, all containers, and each network that actually has
something on it, with per-container picking as the *last* entry. Networks come
from the inventory rather than `podman network ls`, so an empty network is
never offered — a choice with no possible outcome.

**The verb is derived.** For a given set there is exactly one sensible move, so
offering the other one is offering a mistake. Anything running gets frozen; a
set with nothing running gets thawed; the same choice twice therefore toggles.
Each menu row is labelled with what it will do *now* — `FREEZE 8`, `THAW 3`,
`nothing to do` — and `target_effect()` computes that label with the same rule
`infer_action()` uses, so the label cannot disagree with the outcome. An
explicit `freeze`/`thaw` on the command line still wins, because a script must
be able to say what it means rather than depend on current state; when one is
given, the labels are computed for *that* verb instead.

**No confirmation.** This one deliberately reverses the repo's usual
confirm-before-destructive reflex, and the justification is that the premise
does not hold: freezing is not destructive and not irreversible — it is undone
by running the same command again. Combined with the menu row already naming
the verb and the count before the choice, a `[y/N]` was guarding nothing.
`-y`/`--yes` is removed outright rather than left as an accepted no-op, because
a flag that does nothing is a lie in `--help`.

The consequence for F15 is worth being explicit about, since the preview was
originally justified *as* the protection against freezing a network containing
a live Claude session: that protection did not disappear, it moved earlier. It
is now in the menu row, which states the count before the choice is made, and
in reversibility. The printed set is now a record of what happened, not a gate.

**The "frozen things stay frozen" note** restated the definition of the verb.
Gone. The table's CCY column still marks which rows are Claude sessions; what
freezing one implies is left to the reader.

**The menu loops.** Act, re-read the inventory, re-offer. The re-read is the
load-bearing part — counts have to describe the machine now, not at startup,
or the second pass would be labelled with stale numbers. Backing out of the
container picker returns to the group menu rather than quitting, since it is
one level down and not a separate command. Cancelling the group menu is how you
leave, so it is a `quit` key rather than an error exit.

### A unit test, because the host cannot reach these states

The new logic is where subtle bugs live: splitting a comma-separated network
list, a container on two networks, a group that is half frozen, an empty CCY
group, an explicit verb overriding the derived one. Manufacturing those with
real containers is slow, and one of them — an empty CCY group — cannot be made
at all on a machine that is running CCY sessions.

So `unit-test-selection.bash` drives the functions directly against a synthetic
inventory. It is **not a copy of the logic**: it reads the real script and
sources its function region verbatim, cut at the `# Argument parsing` marker so
main does not execute. A missing marker is a hard failure rather than a silent
whole-file source, which would run the tool. It needs no podman, so it runs in
the CCY container, and `acceptance.bash` now runs it as check 0 — if the
selection logic is broken there is no point manufacturing containers to find
that out more slowly, and the failure names a function instead of a symptom.

18 assertions, all passing here, including the two that would have caught a
label/outcome disagreement: `target_effect` and `infer_action` are asserted to
agree on the same fixtures.
