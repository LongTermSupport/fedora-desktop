## Renumbered 00078 → 00079, after a plan-number collision

`git fetch` showed `origin/F44` two commits ahead with a **different** Plan
00078 — `Completed/00078-ccy-network-preflight-skip`, a `CCY_SKIP_NETWORK_PREFLIGHT`
opt-out for an egress-fenced CI runner — while this clone had been building
`00078-podman-container-control` under the same number. Branches were 13 ahead
/ 2 behind.

### Root cause, and why it will happen again

The authoritative plan counter is `hooksdaemon.latestPlanNumber`, held in
**`--local` git config**. Local config is not a tracked file and is never
pushed, so it does not travel with a branch. Two clones of the same repo each
read `78` and each handed out `00078` — neither did anything wrong, and neither
could have seen the other's allocation. `mkplan.bash`'s lock makes the
allocation atomic *within one clone*; nothing makes it atomic *across* clones.

The collision is therefore structural, not a slip, and it is worth recording
here rather than quietly renumbering: the next multi-clone session hits it
again. A durable fix would have to put the counter somewhere that syncs (a
tracked file, or a git ref that is pushed), which is a hooks-daemon change and
not this plan's business.

### Which one moved, and why

Theirs. Not mine — the other way round:

- Theirs is **pushed** and **Complete**, archived under `Completed/`. Renumbering
  it would rewrite a published, finished plan and break any reference to it.
- Mine is **local-only**, unpushed, and **In Progress**. Its number appears in
  six plan-local files and one README row, all of which I own.

So the plan that had not left this machine is the one that moves. Renamed the
folder and the day-1 journal file with `git mv`, replaced all 20 in-file
occurrences, and updated the README index row with a one-line note saying it was
renumbered and why — so anyone who finds a `Plan 00078:` commit message in this
branch's history can tell which plan it meant.

The three commits already on this branch keep their `Plan 00078:` subjects. They
are pushed nowhere yet, but rewriting them would mean an interactive rebase over
a merge, which trades a real risk for a cosmetic gain. The README note and this
entry cover it.

### The merge

`git merge --no-ff origin/F44` — a merge commit, never a squash (see
`CLAUDE/AgentNotes.md`). One conflict, in `CLAUDE/Plan/README.md`, and both
sides were pure additions: they added their Completed row for
`00078-ccy-network-preflight-skip`; this side had moved 00077 from Active to
Completed. Kept both Completed rows and dropped the stale Active row for 00077.

Worth noting for the next person who resolves a conflict in a `.md` file here:
the `markdown_table_formatter` hook reformatted the file **while the conflict
markers were still in it**, escaping them into `\<<\<<\<<< HEAD`, `\=======`
and `> > > > > > > origin/F44`. A `grep '^<<<<<<<'` then reports zero markers on
a file that is still conflicted — an absence of evidence read as evidence of
absence, which is this repo's own recurring defect class showing up in the
merge tooling. Found by grepping for `origin/F44` instead.

## Phase 1: the run-time labels, and then dropping the image label

Phase 1 was the fix for F16 — `--ccy` selecting a CCY-*derived* throwaway that
was not a session. `claude-yolo` now sets `--label ccy=true --label
ccy-project=<project>` at `podman run`; CCY_VERSION 3.39.0 → 3.40.0, with the
changelog entry.

Then the part that was not in the task list. D6 had said the tool should
"prefer `ccy=true` and keep the inherited label as the fallback for pre-Phase-1
containers", and writing it revealed that the fallback covers **nothing**:

- a session from CCY ≥ 3.40.0 has `ccy=true`;
- every older session is named `<project>_yolo[_N]`, because
  `get_next_container_name` constructs it that way and there is no other path;
- so the image label's only remaining contribution is the false positive F16
  demonstrated.

So it is dropped outright rather than kept. That is a narrowing, which is
normally the dangerous direction here — an over-match is visible in the printed
set, an under-match is silent — but the asymmetry argument only bites when the
narrowed selector might miss something, and this one provably cannot. D6 is
rewritten to say that rather than left implying a fallback that does not exist.

Knock-on: `acceptance.bash` check 9 had been enumerating the expected set with
`--filter label=claude-yolo-version`, which is now the *wrong* contract — it
would demand the tool include exactly the containers it is supposed to exclude.
Re-aimed at `label=ccy=true`. The elaborate fixture-image partitioning added
yesterday (prefer unlabelled images, SKIP the exclusion assertion when only
labelled ones exist) went with it: which image the throwaway comes from stopped
being load-bearing the moment the tool stopped reading image labels. Both the
comment and the code shrank, and the assertion is now unconditional.

## Then the user asked for identity labels

> *"i wonder if we can label ccy containers by key label and anthropic token as
> well? so could easily freeze all containers with github ID XXX"*

Yes, and cheaply — the values are all already in scope at the run site:
`GITHUB_USERNAME`, `TOKEN_NAME_FOR_CONFIG` (set for `save_launch_config` a few
lines earlier), and `SSH_KEYS`. Three more labels: `ccy-github`, `ccy-token`,
`ccy-ssh-keys`.

Three things worth recording about the shape:

**`none` rather than an empty value.** An empty label value is
indistinguishable from an unlabelled container at the filter, so "this session
has no GitHub identity" would read as "this container is not a CCY session".
Stating it costs four characters.

**`ccy-ssh-keys` is genuinely multi-valued** — more than one key can be
mounted — so membership is a word match on the label value, while the
single-valued axes compare whole. That asymmetry is a real bug surface: a
substring match would make `--ssh-key github` select a session whose keys are
`github_work github_personal`, silently widening the freeze. `identity_matches`
keeps the two modes explicit and the unit test asserts both directions,
including that a prefix is not a match.

**Rows are derived from the inventory, and only when they discriminate.** An
axis is offered only when it has ≥ 2 distinct values — with one GitHub account
on the machine, "github: <id>" and "all CCY containers" are the same button,
and a menu that says the same thing twice reads as more capable than it is.
Same rule the network rows already follow: never offer a group with no members.

Implementation note: the first cut used a bash **nameref** to pick which
associative array an axis reads (`local -n _lookup="$(...)"`). shellcheck
immediately flagged `INV_GITHUB`/`INV_TOKEN`/`INV_SSHKEYS` as unused (SC2034)
— correctly, because the indirection hides every read from static analysis,
which is exactly how a typo'd array name becomes a silently empty group. It
also tripped SC2155. Replaced with a `case` that reads the arrays by name; both
findings went, and the code got easier to follow rather than harder.

Unit test now at **37 assertions**, all passing, including the three that drive
`select_identity`'s failure path in a subshell — an unknown value must exit
non-zero, name the value, and list the known ones, never resolve to an empty
set and exit 0.

`acceptance.bash` gains checks 13 and 14. 13 asserts `--github` against podman
rather than against the tool's own idea of the set. It deliberately exercises
**only** the GitHub axis: all three share one code path, and the token label is
a private identifier that has no business being written into a log file, even a
gitignored one.

## H7: `podman` is one network, not one per container

User question: *"we have network podman listed — I suspect this isnt one single
network is it? does each container have a default network called podman but is
actually different? or are all ccy containers launching networked together
which would seem weird?"*

Answered from the existing triage log rather than from memory. `podman network
ls` lists it once, with a single NETWORK ID and the `bridge` driver — so it is
**one** shared bridge, not a per-container default. Seven CCY sessions were
attached to it at once, and an eighth (`<project>_yolo`) was on the app network
`mkt` instead, because that one was launched with `--network`.

So yes — every session launched without `--network` lands on the same bridge
together. That is podman's default, not something CCY chooses. Recorded as F17
because it changes how the menu reads: "network: podman" is approximately
"every session that did not join a project network".

What the log does **not** establish is whether they can actually address each
other, and I am not asserting it. Added an H7 probe — `network inspect` for the
subnet, plus the per-container attachments — so the next run settles it with a
subnet rather than with reasoning about rootless netavark from memory.

## D9: choosing a group now opens it

> *"can we have a way to drill into a grouping - eg select all ccy and drill
> into list - first option is "all" or its then possible to pick specific ones.
> i think this will be easiest and clearest"*

Built. A group row leads to a second screen listing its members with the verb
each will get, and the **first row acts on all of it**.

The thing to be careful about was not undoing D7. Yesterday's feedback was that
per-container tab-selection was *forced* and that group targets were
unreachable without knowing flag names. A drill-down could easily reintroduce
exactly that. It does not, because "all" is row 1 and bare ENTER takes it: the
whole group is still one keypress, and picking specific containers is now the
option rather than the obligation. What it adds is the one thing a group row
structurally cannot show — **its members** — which matters precisely because
F15/F17 mean "network: podman — FREEZE 5" can include a live Claude session
without saying so.

The standalone "pick individual containers…" entry is gone: drilling into "all
containers" *is* that screen, and two routes to one screen is worse than one.

Two implementation notes:

- The "all" row is keyed by a sentinel `*all*`, not the word "all". Podman
  container names must begin with an alphanumeric, so no container can collide
  with it; keying on the word would have been a latent bug waiting for someone
  to name a container `all`.
- `row_verb` was first written as `[ test ] && printf A || printf B`.
  shellcheck did not flag it (both printfs succeed), but that shape runs the
  third branch whenever the second one fails, which is the discarded-failure
  class the repo gates on. Rewritten as explicit `if`s — the linter's silence
  is not the standard.

Unit test 37 -> 43 assertions, all passing, including `row_verb` under an
explicit verb in both directions (an explicit `freeze` must render `-` against
an already-frozen row rather than claiming it will act).

## Run 3: PASS 21/0 — and the green tick hid a gap in check 9

`deploy.bash` redeployed and chained into acceptance: **PASS, 21 checks, 0
skipped**, up from 16 passed / 2 skipped. Checks 9 and 13 are real assertions
now — `--ccy` resolves the live session set, `--github` resolves the identity
axis, and the unlabelled throwaway is excluded from both. The D9 drill-down is
finally on the host and exercised.

Then read the log rather than just the verdict, and found F19.

**Check 9 builds its expected set from `label=ccy=true` alone.** It asserts that
every *labelled* running session appears in `--ccy`, and that the throwaway does
not. It never asserts that the **name-pattern fallback** works. On this host
that fallback is not an edge case: Plan 00080's triage just established that
**4 of the 6 live sessions are unlabelled**, so the majority of the real
population reaches `--ccy` through the exact path the gate says nothing about.
Break `CCY_NAME_PATTERN` tomorrow and check 9 still prints OK.

What makes this worth writing down is the timing. This is the *third* instance
of one shape in a single day — the truncated `grep`, triage's P4, and now check
9 — and the third was found only because the first two had trained me to go and
look. The tell is always the same: a check that verifies the path you were
thinking about, and is silent on the path that carries the load. The verdict
line reads identically either way, which is precisely the problem with trusting
a verdict line.

Also worth noting the check's own comment reasons carefully about *which* label
to use (run-time `ccy=true`, not the inherited image label, with the history of
why). It thought hard about label-vs-label and never asked about
label-vs-no-label. Careful reasoning inside too narrow a frame.

**Check 9b** now asserts the fallback directly: enumerate running containers
matching podfreeze's own pattern, subtract the labelled ones, and require every
remainder to appear in `--ccy --dry-run`. When every session happens to be
labelled it reports that state explicitly rather than skipping — a skip there
would be indistinguishable from the gap it exists to close.

One deliberate detail: 9b recomputes the labelled set instead of reusing check
9's `$ccy_live`. That variable holds podman's *error text* when its call failed,
and matching container names against an error string would silently misclassify
every session — the discarded-failure-signal class, one line away.

**9b has never run.** A gate that has never executed is not evidence of
anything, so it is tracked as Task 3.2b rather than counted as a fix.
