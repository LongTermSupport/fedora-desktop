## 14:35 · finding · — — the container cannot read the project, and the audit log says why

Plan 00116's first live proof on an Enforcing headless box (rootless podman, the ccy image):

```
-v "$PWD:/workspace"                head /workspace/README.md → Permission denied
-v "$KEY:/root/.ssh/key_0:ro"        head → Permission denied
copy of the key in /tmp, mounted     head → Permission denied
-v "$PWD:/workspace:Z"               readable
-v "$KEY:/root/.ssh/key_0:ro,z"      readable
```

`/var/log/audit/audit.log`: `denied { read } comm="head" tcontext=…:user_home_t tclass=file`,
the same for `ssh_home_t` and `user_tmp_t`, scontext `container_t`. Labels on the host:
project `user_home_t`, key `ssh_home_t`. `podman info`: `selinuxEnabled: true`, no `label`
override in any containers.conf.

The desktop this was launched from runs its ccy container as `container_t` (read from
`/proc/self/attr/current` inside it) and reads `user_home_t` without complaint — which is only
possible with nothing enforced. `docs/containerization.md` describes desktops as permissive
"configured by playbook"; no play in the tree sets it, and every kickstart says
`selinux --enforcing`. That question (should desktops be enforcing, and what set them
permissive) is recorded here and not answered by this plan.

The relabels applied during the measurement were reverted with `restorecon -RF` as root
(project back to `user_home_t`, key to `ssh_home_t`, zero stray `container_file_t` under the
account's home afterwards).

## 14:50 · decision · — — `:z` for the workspace, staged copies for keys, nothing for the rest

- Workspace: `:z` (shared), not `:Z`: ccy allows several sessions on one project, and a
  private relabel by the second would lock the first out mid-session.
- Keys: never relabel `~/.ssh/<key>` in place — that changes the person's own file. Copy into
  an owner-only tmpfs directory under `$XDG_RUNTIME_DIR`, mount it `:Z,ro`, remove it in
  `cleanup`. Per session, so `:Z` is right there.
- Config import (per-session temp dir): `:Z`.
- Not relabelled: tracked extra mounts (their documented no-relabel rule stands — relabelling
  a home directory affects every container on the machine) and display sockets (`connectto`,
  which no file label permits). The launch banner and docs say so.
- Decision is a pure verdict on `getenforce` + the engine's `SELinuxEnabled`, `unknown`
  relabels, same testing shape as the rootless guard.
