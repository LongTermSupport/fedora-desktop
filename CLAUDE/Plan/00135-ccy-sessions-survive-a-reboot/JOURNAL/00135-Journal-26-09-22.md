## 14:36 · decision · T1.1 — registry lives at `~/.local/state/ccy/sessions/`, not under `fedora-desktop`

PLAN.md flagged this as a decision, not an assumption. Chosen: the issue's path,
`${XDG_STATE_HOME:-~/.local/state}/ccy/sessions/<session-name>`, with `CCY_STATE_DIR` as a
test override. The `$XDG_STATE_HOME/fedora-desktop` convention (`helpers/play_ledger`) is
this repository's *provisioning* state — what plays have run on this host. The registry is
the *tool's* state: written by two launchers (`ccy`, `cc`), read by `ccy-sessions`, and it
means the same thing on a machine that installed ccy by other means. One rule carried over
from the ledger: a relative `XDG_STATE_HOME` is refused, because the registry would then be
wherever the launcher happened to be run from, and a restore would read an empty directory
and report success.

## 14:36 · decision · T1.2 — the trampoline owns the delete; the library owns the trampoline

The tmux pane runs `bash -c "<trampoline>" ccy-tmux <launcher> <args>`. The trampoline
already existed (hold the window on a non-zero exit); it now also removes the record the
moment the launcher **returns**, whatever the status. A returned launcher is an ended
session. A killed pane — reboot, power cut, `kill-session` — never reaches the removal,
and that asymmetry *is* the feature. The string is built by `ccy_registry_trampoline` in
`lib/session-registry.bash` so the delete and the write are in one file, and so the exact
bytes are testable: `scripts/test-ccy-session-registry.bash` runs the real trampoline
through `bash -c` for a clean exit, a failing exit, and a `kill -KILL`, and asserts the
record is gone, gone, and **present**.

## 14:36 · decision · Open decision 2 — replay filtered argv, and settle the prompt problem honestly

Considered restoring through the quick-launch path (`.last-launch.conf`) instead of
replaying argv. Rejected: the quick-launch path is a **prompt** (`Use same configuration? [Y/n]`), so it does not remove the interactivity problem, and it holds only token/ssh/network —
not `--engine`, `--github-443`, `--no-supervise` or anything meant for claude. So the
record holds the filtered argv, per the plan.

The honest position on prompts: a restored session is started **in a real tmux pane**, so
the launcher behaves exactly as it does interactively — if it would ask, it asks, in the
pane, and `ccy-sessions` shows the session waiting there. A launch with explicit flags
(`--token X --ssh-key K --network N`) asks nothing and comes back unattended. A launch that
answered prompts the first time will ask them again. That is the correct behaviour with no
new code path, and it is what Phase 5 has to observe on a real machine rather than assume.

Two consequences recorded: `--ssh-agent` is dropped (the socket path is different after a
reboot, so replaying it points at nothing); and a bare word before `--` is dropped as a
stale first message **unless** it follows a flag ccy does not know, when it is that flag's
value (`--model opus`). Cutting `opus` off `--model` would leave claude refusing to start.

## 14:36 · decision · T2.1 — `cc` gets `--continue` only; `--no-restore` is consumed before either launcher sees it

`cc` forwards its whole argv to `claude`, so `--supervise` (ccy's flag) must not be added to
a `cc` record's restore, and ccy's one-shot set means nothing there — a `cc` record replays
verbatim. `--no-restore` is stripped by `ccy_registry_launch_args` inside the insulation on
the way into tmux, and `cc` strips it again after `ccy_tmux_insulate` returns on the paths
where insulation does not apply, because anything left in `cc`'s argv reaches `claude`.

## 14:36 · decision · T2.4 — vanished directory is an error that does not stop the others; live name is a skip

`ccy_registry_restore` processes every record; a missing directory is reported with the
record path, counted, and the record is **kept** (deleting it would make the next boot
report success on a session that was never brought back). The run exits non-zero if
anything failed, so the unit shows `failed` in `systemctl --user status`. A record whose
session name is already live is skipped and said so — a hand-started session is ordinary.
If the live set cannot be read at all, nothing is started: restoring on top of an unknown
set could double every session.

## 14:48 · decision · T3.5 — `reboot-with-update`, asked for mid-implementation

The owner asked for one command that does the updates *and* handles the sessions.
Built as `shutdown-with-update` under a second name (a symlink, so they cannot drift),
branching on its own basename. Two choices worth recording:

- **The reboot is root's, not `ccy-sessions reboot`'s.** `ccy-sessions reboot` ends in
  `systemctl reboot` as the user, which polkit allows only from a local active session; a
  patch cycle is run over SSH as often as not, and it would have warned everyone and then
  been refused. So the root script uses the two `notify` halves for the warnings and
  reboots itself. The six-line countdown is duplicated on purpose rather than routed
  through the user-side helper.
- **The refusal is rehearsed before the updates.** `ccy-sessions reboot --dry-run` runs
  first; a session whose project has no daemon CLI stops the command before `dnf`, not
  twenty minutes later.

Not unit-tested: the script's body is firmware and package managers. Phase 5 gains a task
for it. This settles open decision 3 more usefully than "leave it": the operator's
deliberate bring-down path and the session warning are now one command.
