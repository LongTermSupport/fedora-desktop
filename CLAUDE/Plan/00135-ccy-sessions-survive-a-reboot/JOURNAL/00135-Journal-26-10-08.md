# Plan 00135 — Journal 26-10-08

_Scaffolded by `mkplan.bash`; timestamps in this file are UTC._

> **Append-only activity log** for plan 00135. One file per day
> (`00135-Journal-YY-MM-DD.md`). `PLAN.md` tracks the plan (what/why,
> current state, tasks); this journal tracks what actually *happened* —
> findings, decisions, dead-ends, hand-off state — the linear lifecycle a plan
> document structurally cannot carry.
>
> **Entry grammar** — append new entries at the BOTTOM; NEVER edit earlier
> entries (corrections are new entries):
>
> ```
> ## HH:MM · category · REF   — optional short title
> ```
>
> - `HH:MM` UTC 24h (the date is in the filename, also UTC); times increase
>   down the file. A file with no sentinel line above predates this system —
>   its times are local, zone unrecorded (legacy; never rewritten).
> - `category` ∈ `action` | `finding` | `decision` | `thought` | `blocker` | `handoff`
> - `REF` = optional task/phase ref (`T1.2`, `P1`) or `—`.
> - Bodies may embed fenced logs/diffs/snippets — no size limit — with a
>   one-line takeaway above the fence.
> - End a working session with a `handoff` entry so the next agent's entry
>   point is the last entry of the newest day-file.

## 11:36 · decision · —

Task 8.1 design: how a restored session is set going, grounded in what the pane and the
transcript actually show (fedora-desktop#88, body and the 2026-10-08 comment).

**Not inside the restore unit.** `ccy-sessions-restore.service` is a oneshot wanted by
`default.target`; targets order themselves after what they want, so the user manager does
not finish starting until the oneshot exits, and `user@UID.service` (no TimeoutStartSec of
its own, so the 90 s system default) and a desktop login both wait on that. Waiting minutes
for prompts to draw inside it would risk the user manager's start timing out and hold the
owner's login. So the wait is a second user unit, `ccy-sessions-set-going.service`,
`Type=exec` (started the moment it execs, so nothing waits on it), `After=` the restore and
pulled in by the restore's `Wants=`. Enabling the restore is the only switch; the new unit
has no `[Install]`. Its ExecStart is `ccy-sessions set-going`.

**Which sessions.** Only the ones this restore STARTED. A session the restore found already
running was started by a person and gets nothing typed into it. The manifest therefore
carries, per entry, what set-going did with it: format 2 adds `going=` (none for a session
found running, pending, compact, continue, untouched), `at=` (epoch seconds the keys were
sent), `detail=` (the context size, or the reason it was left alone) and `transcript=`.
Restore writes `pending`/`none`; set-going rewrites the entries as it decides, whole then
moved into place as before. One file, one strict reader; a format-1 manifest from an older
restore in the same boot is refused with that reason.

**When the prompt has drawn (pane).** Measured on Claude Code 2.1.293 in a pty (the text
with escapes stripped): the input box is a line beginning `❯` with a line of `─` box rules
directly above it and another below, then the footer (`⏵⏵ bypass permissions on`). The
same `❯` is the cursor in Claude's selection dialogs, but those are not framed by full rule
lines, so the test is a `❯` line whose line above starts with ten or more `─` and which has
a rule line after it. Busy is the input box plus `esc to interrupt` on screen (Claude's
spinner line while a turn or a compaction runs). The screen is read with the same
`capture-pane -p -t "=<name>:"` verify-restore uses. Pure function:
`ccy_claude_screen_state <screen>` -> `ready` | `busy` | `not-drawn`.

**Context size (transcript, not the pane).** Claude Code shows no context figure by default
(the `Context left until auto-compact` hint appears only near the limit, and a status line
is per-project). The hooks-daemon's `context_sidecar` handler writes `pct` per session, but
it is opt-in, exists only where the daemon is installed, and is written on status-line
renders. The transcript is always there: `--continue` resumes the newest `*.jsonl` directly
in the project's transcript directory and reuses its session id (`--fork-session` exists to
do otherwise). The directory is `<dir>/.claude/ccy/projects/-workspace/` for ccy (the
container's `/root/.claude` is `/workspace/.claude/ccy`, and claude's cwd is `/workspace`),
and `${CLAUDE_CONFIG_DIR:-~/.claude}/projects/<dir, each non-alphanumeric as ->/` for cc.
The size is that of the LAST main-thread (not `isSidechain`) entry that carries one:
an assistant message's `usage.input_tokens + cache_creation_input_tokens + cache_read_input_tokens` (what Claude Code's own context figure counts), skipping
`<synthetic>` assistant messages (error placeholders with zero usage), or a
`compact_boundary` system entry's `compactMetadata.postTokens` when a compaction is the
latest event. Observed shapes on a real transcript: usage 2 + 4543 + 203980 on the last
assistant message; compact boundaries with postTokens around 9k-13k. Read with jq (which
play-claude-yolo.yml already ensures). No such entry, no transcript, or an unreadable one:
the session is left untouched and named.

**The floor.** `ccy_restore_compact_floor_tokens`, default 150000, set per host in
host_vars and written into the set-going unit as `CCY_RESTORE_COMPACT_FLOOR_TOKENS`. At or
above it set-going types `/compact` (with a short instruction to carry on afterwards), below
it `continue`. 150k is the supervisor's own red line on a 200k-window model (context_tiers:
76 %), so a session that would already be compacting on the smaller window compacts before
its first cold turn, and on a 1M window (red at 400k) the restore compacts earlier than the
supervisor would: every restored turn re-sends the whole context with a cold cache, so the
first turn is the cheapest moment to shrink it. The supervisor's continue-after-compaction
(it acts on a human `/compact` too, via the PreCompact signal) carries a ccy session on. The
floor is a token count, not a percentage: the window is not in the transcript.

**How keys are sent.** No pane is typed into anywhere in the repo yet; this mirrors the
supervisor's `_perform_injection`: the text as one literal `send-keys -l`, then after a
0.2 s pause (its `_SUBMIT_DELAY_SECONDS`) a separate `Enter`. The epoch is taken before
sending, so any transcript entry the submission causes is at or after it.

**Bounded wait.** One deadline for the run, `CCY_SESSIONS_SET_GOING_WAIT` (default 1200 s:
an image rebuild after an update is the slow case), polling every POLL_SECONDS. Each session
is decided the first time its screen is `ready`. A session that is dead, waits at a ccy
prompt past the deadline, is busy when its prompt draws, has no readable context, or whose
keys cannot be sent is left untouched with a reason; each is named on stderr, the others go
on, and the run exits 1 if any was left untouched.

**Did it start (verify-restore, Task 8.3).** Submitted input lands in the transcript as a
main-thread `user` entry (a typed `/compact` and its `<command-name>/compact` expansion, or
`continue`), at the moment it is submitted; a line left sitting in the input box writes
nothing. So a session set going at `at` has started when its transcript holds a non-meta,
main-thread `user` entry timestamped at or after `at`. Until `CCY_SESSIONS_START_WINDOW`
(default 120 s) has passed it is `SETTING-GOING`; after, `NOT-SET-GOING <compact|continue>-not-started`. A session left untouched is `NOT-SET-GOING <reason>`;
`pending` is `SETTING-GOING`. Neither is OK.

**Settled (Task 8.4).** `verify-restore --wait` stops as soon as no session is in a
transient state (STARTING, SETTING-GOING) and the same report has been read twice running,
so a prompt glimpsed for one poll is not taken as final. `fedora-desktop-self-update verify`
passes a 1500 s ceiling (set-going's 1200 s plus the start window, inside the unit's
30 min TimeoutStartSec), and on a pass runs `systemctl reset-failed` on its own unit
(`fedora-desktop-self-update-verify.service`, the one the login banner lists from
`systemctl --failed`), so a by-hand re-run after the unit failed clears it.

## 12:56 · decision · —

Phase 8 review fixes (qa-reviewer FIX-BEFORE-MERGE on c08c1624, report in
subagent-reports/261008-qa-reviewer-phase8-opus.md). These correct the 26-10-08 design
entry above where it differs.

- **Merged F44 (Plan 00163, CCY 3.87.1).** This work is now CCY 3.88.0.
- **One session per conversation.** set-going sets going only the first session to resolve
  a conversation's transcript. Another session resolving to the same file is left alone as
  `shares-conversation-with-<name>`, and verify reports that as NOT-SET-GOING, so it is never
  judged on the other session's input.
- **`--resume <id>`.** The manifest now carries `resume` (from `--resume <id>`,
  `--resume=<id>` or `-r <id>`, parsed the way the launcher's flat loop walks its arguments)
  and `supervised`. set-going reads `<transcript dir>/<id>.jsonl` for that id. A missing or
  malformed id gives `no-transcript`; it never falls back to the newest file.
- **No supervisor** (cc, or ccy with `--no-supervise`, taken from the restore's own
  arguments). At or above the floor, set-going types `/compact` and records `compacting`.
  Once a main-thread `compact_boundary` timestamped after the send is in the transcript and
  the prompt is ready, it types `continue`. While a session is compacting, verify reports
  it as SETTING-GOING, not OK. A compaction that is not finished by the set-going deadline
  is left alone as `compaction-not-finished-after-Ns`.
- **Manifest locking.** Every manifest write holds an flock on `last-restore.lock`:
  - The restore merges its write. An entry for a session that is already live keeps the
    entry this boot's manifest already holds.
  - set-going re-reads the manifest each poll and updates one entry at a time by name, with
    compare-and-set on its previous `going`.
  - set-going runs one at a time (`last-restore.set-going.lock`), so a second restore's
    set-going waits, then finds the new entries pending.
- **Self-update verify.**
  - A failed verify (exit 23) keeps `owed-verify`. The next boot's unit, or
    `sudo fedora-desktop-self-update verify` run by hand, checks again, and a pass clears the
    owed check and the unit's failed state.
  - This changes the Plan 00137 contract; DESIGN-cycle.md is updated. A cycle with nothing
    new only reboots on an owed check from its own boot, so a stale owed check from an
    earlier boot does not trigger a reboot. A test covers this.
  - A `reset-failed` that fails is now its own exit code, 25, not a warning. The outcome
    stays `deployed`, with the reason in the detail.
- **Nits.**
  - **Busy.** Only `esc to interrupt` in the four non-blank lines above the input box counts.
  - **Ready.** The input box must hold no typed text. set-going captures with `-e`; the
    measured placeholder is a no-break space then dim (SGR 2) text, which counts as empty.
    An attached session is left alone as `attached`, and text in the box gives
    `input-box-not-empty`.
  - **No `Requires=`, decided against.** The restore exits 1 when a single record fails
    after starting all the others, and `Requires=` would then leave every healthy session at
    its prompt. Instead, when the restore wrote no manifest for this boot, set-going says so,
    names the restore's journal, and exits 1. The reason is recorded in the unit file.
  - **Read-back.** The play's read-back also requires the set-going unit to be pulled in
    where restore is opted in.
- **Tests.**
  - `test-ccy-session-registry.bash`: format, compare-and-set update, merge-keep, resume and
    supervised parsing, the screen states including the dim placeholder, `compacted_since`.
  - `test-ccy-sessions-reboot.bash`: shared conversation, resume, unsupervised continue,
    attached, typed, no manifest for this boot.
  - `test_cycle.py` and `test-self-update-cycle.bash`: the owed check stays owed, a re-run's
    pass clears it, and exit 25.
