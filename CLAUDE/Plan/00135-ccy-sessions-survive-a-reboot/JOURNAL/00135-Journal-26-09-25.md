## 19:13 · finding · T3.2   — reboot-with-update refused: a ccy-only project's daemon has no host venv

The owner's `reboot-with-update --in 2` ran its updates, then warned this repo's
project (on the host) and failed on project B: `resolve_venv: no usable venv found`
under that project's `.claude/hooks-daemon/untracked/`. It kept the machine up and
withdrew the warning from this project, which received `reboot-cancelled`. The withdrawal
to project B failed for the same reason.

Two defects in `ccy-sessions`:

- **Wrong place.** Each project's daemon CLI was run on the host. Most projects run only
  ccy, so their daemon's venv exists only inside the container. This repo worked only
  because the owner also runs `cc` here, which gave it a host venv.
- **Shallow check.** The "every project before any is signalled" check tested only that
  the CLI file was executable. So this project was warned before project B's failure was
  found.

Fix: for a project with a ccy session, the CLI runs inside that session's container
(`podman exec <container> /workspace/.claude/hooks-daemon/bin/hooks-daemon ... --project-root
/workspace`). The container is found the way `verify-restore` already finds it (now the
shared `session_containers`). A project with only cc sessions stays on the host. The daemon
writes the signal into the project's own tree, which the container and the host share, so
one delivery per project reaches every session. Before any warning, each route is asked for
`signal --help`, and a CLI that cannot run refuses with its own error. A withdrawal skips
that check and reaches every project it can.

`scripts/test-ccy-sessions-reboot.bash` gains 16 cases (156 in total), including a broken
host CLI and a ccy-only project reached through its container. 12 of them fail against the
previous `ccy-sessions`.

## 19:40 · finding · T5.3   — restore started the sessions, but each stopped at ccy's SSH key prompt

The machine rebooted with restore on. The owner reports that `ccy-sessions` did restart
the sessions, including this one. But each got no further than ccy's own startup: the
SSH key selection and the key's passphrase prompt. Neither has a safe automatic answer,
so no session could resume unattended, and the owner typed the passphrase by hand. This
session then resumed with its conversation intact.

So Task 5.3 fails as designed today. A ccy session that needs a passphrase-protected key
cannot come back by itself. Options for the owner to decide:

- Restored sessions sign and push through the login ssh-agent (ccy `--ssh-agent`), which
  holds the keys only after a graphical login unlocks them. Restore would then wait for
  login, not start at boot.
- Restore stops at the prompt on purpose, and says so: one notification naming the
  sessions that wait for a passphrase.
