## 14:19 · action · P9   — fedora-desktop#87: compose answer recorded and replayed; unanswerable questions

Phase 9 (fedora-desktop#87): a restored session never waits at the compose question. CCY 3.89.0.

**Mechanism.** The session record takes an optional `compose=started|declined|running`.
The reader tolerates its absence (REC_COMPOSE empty), so the header stays
`ccy-session-record 1`: bumping it would have made every record already on disk
unreadable, which is the failure this phase exists to remove. A ccy older than the key
refuses a record that has it, by name ("unknown key 'compose'"); only a downgrade meets
that. `ccy_registry_write` takes an optional leading `--compose <outcome>` (positional
signature unchanged), and the two existing rewrites (`forget_network`, `record_ssh_key`)
pass `REC_COMPOSE` back so neither drops it. `ccy_registry_restore_args` turns the outcome
into `--compose start` (started, running) or `--compose skip` (declined), before any `--`;
a record with no outcome gets no flag and the launcher asks. `--compose` is a drop-value
flag on replay: the record key is the one source.

The launcher: `--compose start|skip|ask` (default ask). Every compose question (the one in
`_do_compose_start`, the cross-engine one and the "compose files, no matching network"
one) goes through `ccy_compose_answer`. The compose code sets `CCY_COMPOSE_OUTCOME`
(started on a successful `up -d`, declined on no, running when the services were found up
with a compose file present), and the launcher hands it to the record once, after the
network section (`ccy_compose_record_outcome`). Under `--compose start` a failed `up -d`
ends the launch with the reason (decision: a session without its stack is not the one
recorded; the cost is that the trampoline removes the record, so that session is not
restored again until relaunched). A restore of a record with no answer asks in the pane,
printing why on the line above the question (verify-restore reads the last line).

**Inventory of launch-path reads, and what each does with nobody to answer**
(`ccy_nobody_to_ask` = `--headless` or stdin not a terminal; `ccy_launch_unattended` adds a
restore or a restart):

- migration (keep old session dirs): kept for nobody or a restore.
- quick-launch: restore and headless already took it; no terminal now takes it too.
- token-expired, token-none (both sites), token-select, token-recovery (and token-replace
  nested in it): refused by name with the flag or command that answers it.
- network-continue (saved network gone, compose not started): default Y for unattended.
- network-engine-conflict (and network-prune nested in it): refused (option 1 stops
  containers and removes networks: a person's choice).
- network-continue (engine mismatch, docker side): default Y for unattended.
- network-connect (both forms; network-pick nested): refused for nobody, naming
  `--network`/`--no-network`. A restore pane still asks: see below.
- compose-start, compose-start-saved: `ccy_compose_answer` (record, flag, or refuse).
- compose-stop (end of session): nobody leaves the services running; a restore or a
  restart still asks whoever ends the session.
- ssh-no-key: unattended continues without a key (the only answer that starts a session).
- ssh-passphrase-retry: refused for nobody.
- github-443: unattended takes Y (it already did for headless and no terminal).
- ssh-key menu: unchanged; EOF already fails by name ("Input closed before an SSH key was
  chosen"), headless never reaches it, and its test suite drives it through a pipe.
- relabel-fix (`common.bash`): already refused with no terminal.
- zombie and existing-container menus: already answered for unattended launches.
- not reachable by a restore: `--debug` reads, `--custom`/`--custom-docker`, `--top`,
  token create/export, `--connect`/`--disconnect` pickers (all dropped on replay).

**Still able to stop a restored session at a prompt** (in its tmux pane, so not "nobody";
verify-restore reports them as a failure): the network-connect question when the saved

## 15:27 · action · P9   — fedora-desktop#87 review: restore never ends on a failed stack; argv and record tests

Independent review of the fedora-desktop#87 PR (APPROVE WITH CHANGES) addressed. CCY 3.89.0 → 3.89.1 (3.89.0 was never released; the pre-commit gate needs a bump for every change).

- B1, NO DEGRADE: a restore whose `--compose start` stack would not start called `exit 1`, and the trampoline then removed the session's record, so it would never be restored again (F44 keeps it: the question waits in the pane). The previous entry's "the cost is that the trampoline removes the record" recorded a decision nobody approved. Now `ccy_compose_up` retries `up -d` three times, ten seconds apart, in a restore, then returns 2; every caller (the library's `_do_compose_start` and the launcher's two compose questions) asks the question again in the pane, with the reason on the line above. y retries; n carries on without the services and notes no `declined`, so the record keeps `compose=started` and the next restore tries again. `exit 1` stays only outside a restore (a person's launch, or one with no terminal and so no record). The record write after the network section warns and carries on instead of `|| exit 1`, for the same reason.
- B2: the argv parse and the record write were untested (both whole-feature breaks passed both suites). The compose suite now runs the launcher's own argument loop, taken from the file, on real argv, and runs `ccy_compose_record_outcome` against a record on disk. Proven by hand: `COMPOSE_MODE=ask` forced in the parse → 2 failures; `ccy_compose_record_outcome` made a no-op → 2 failures; the restore path made to `exit 1` → 5 failures. Each was put back and the suite returned to green.
- R1: `--headless` was not honoured by the old-session-directories question (it runs before the parse; it now scans the arguments with `ccy_args_headless`), by the relabel question (now `ccy_nobody_to_ask`) or by `--debug` (now refused with nobody to answer). The GitHub-over-443 decision moved into `ccy_github_443_answer`; the SSH no-key, passphrase-retry and 443 guards are tested.
- R2: the no-terminal compose refusal is kept, and named as a behaviour change in the changelog and docs/ccy.md.
- R3: F44 commit 1899e07a took `play-claude-yolo.yml` out of meta-deploy; 3.89.1 reaches a host only through Plan 00161's `deploy.bash` while 00161 is in the list. Task 9.4 says so. meta-deploy is not touched: the change is unmerged, and its run is covered once it is.
