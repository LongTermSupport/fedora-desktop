## 19:52 · finding · P1 — `--headless` is not the flag it sounds like

The single most important finding, and it inverts the obvious design. `ccy`
already has `--headless` (`claude-yolo:155`), so the natural assumption is that
unattended operation is mostly solved. It is not. `--headless` changes exactly
two things:

- `claude -p "$PROMPT"` instead of an interactive invocation (`2626-2628`)
- `-i` instead of `-it` on the container (`2694-2699`)

Both are about how *Claude Code* is invoked. The **launcher** still prompts:
**35** `read -rp` sites across `claude-yolo` and the libs, of which
`HEADLESS_MODE` guards exactly **one** (`lib/ssh-handling.bash:357`).

So `--headless` describes the payload, not the harness. Recorded as E1/E2 in
`PLAN.md`, and it is why Decision 2 makes `--non-interactive` a *separate* flag
rather than widening this one.

## 20:01 · finding · P1 — the prompt loops do not just prompt, they HANG

Escalates E2 from annoyance to blocker. At least ten of the 35 sites are
`while true` menu loops of this shape (`claude-yolo:2011` shown):

```bash
while true; do
    read -rp "Select option [1-4]: " cleanup_choice
    case "$cleanup_choice" in
        1) ... ;;
        4) ... ;;
        *) echo "Invalid choice. Please select 1-4" ;;
    esac
done
```

With no TTY, `read` returns non-zero **immediately** with an empty value, the
`case` falls to `*`, and the loop repeats — unbounded. I replicated the exact
shape with an injected counter and fed it `/dev/null`:

```
Invalid choice. Please select 1-4     (x4)
SPUN 5 TIMES ON EOF -> INFINITE LOOP CONFIRMED
```

Sites: `claude-yolo:1104`, `claude-yolo:2011`, `lib/docker-health.bash:162,369,486`,
`lib/network-management.bash:271`, `lib/dockerfile-custom.bash:37,117,157,718`.

Consequence: an unattended `ccy` does not fail, it **hangs** — which in CI burns
a runner slot until the job timeout and produces no diagnostic. This is why
Phase 2 (`--non-interactive`) is ordered before everything else: nothing later
can be verified unattended while this is true.

Note the contrast: `lib/ssh-handling.bash:357` and the `stty susp` guard at
`claude-yolo:2732` (`[[ -t 0 ]]`) show the codebase *does* know how to handle
absent-TTY correctly. The gap is coverage, not capability.

## 20:09 · finding · P4/P5 — two capabilities are genuinely absent, not merely weak

- **MCP: zero support.** Searched `mcp`/`MCP` across `claude-yolo`, all 7 libs,
  all 4 Dockerfiles and `entrypoint.sh` → **no matches at all**. So "inject MCP
  into a ccy session" is net-new capability, not a repair of something partial.
- **Egress: the flag that exists does the opposite.** `--network NETWORK`
  *attaches* the container to an additional podman network so it can reach
  compose services (`148`, `1801-1812`); default is `--network podman` (`2516`);
  and there is a **positive** connectivity probe fetching `http://google.com`
  that warns when it fails (`2529`). No proxy, no allowlist, no restriction
  anywhere.

The second is a naming hazard worth flagging early: `--network` and a future
`--egress` would sit on what looks like the same axis and act in opposite
directions. Task 5.1 has to resolve that rather than stack a second flag on top.

## 20:15 · decision · D1 — a variant IMAGE is justified; a variant LAUNCHER is not

The request floated "a `ccy-ci-runner`, a special version of ccy". Taken
literally that is a second launcher, and I do not think that is right — it would
be re-implementation #5 in this estate, and the two copies would drift across
all 35 prompt sites, the token path, the version gate and the podman argv.

What *is* justified is a variant **image**: CI needs MCP server binaries baked
in, and baking those into the desktop image is weight every workstation user
carries and never runs. The repo's existing `Dockerfile` already layers
`base` → `full`, so a `ci` stage is a third step in an established pattern
rather than a new mechanism.

So: one launcher, orthogonal opt-in flags, layered images. Recorded as
Decision 1 in `PLAN.md` with the rejected option and its reasoning, because the
rejection is the load-bearing part.

Corollary for the three options as posed: they are not alternatives to choose
between. A CI image, MCP injection and egress restriction are three of the
**four** things a CI mode needs — the fourth (non-interactivity) was not named
and is the prerequisite for verifying any of the others.

## 20:22 · blocker · T1.1 — cannot answer the `/dev/dri` question from in here

`claude-yolo:2773` passes `--device /dev/dri:/dev/dri` **unconditionally** — one
occurrence, no guard — while the GUI socket mounts right above it (`2704-2727`)
*are* properly guarded. On a headless server with no render node that looks like
a day-one failure.

I tried to settle it by running podman. That was a mistake and it produced a
false signal:

```
podman run --rm --device /dev/definitely-not-here:/dev/x alpine true
Error: copying system image from manifest list: ... potentially insufficient
UIDs or GIDs available in user namespace (requested 0:42 for /etc/shadow) ...
exit=125
```

Non-zero, and **nothing to do with the device check** — it died pulling the
image under this container's userns before argument validation. Had I read
"exit 125" as "podman rejects the missing device" I would have written a proven
finding that was not one. This is the same failure mode this estate keeps
hitting: a true statement about a check standing in for a stronger statement
about the world.

Owner confirmed the general rule: **do not test podman from inside a podman
container; write `triage.bash` and have it run on the host.** Done — probe D in
`CLAUDE/Plan/00066-ccy-ci-runner-variant/triage.bash` decides it either way, and
E6 stays marked UNVERIFIED in `PLAN.md` until it runs.

## 20:31 · finding · — — "✓ bash: 0 files OK" was the gate scanning NOTHING

Nearly banked a second false green. `./scripts/qa-all.bash` reported:

```
✓ bash: 0 files OK
✗ python: ruff not installed (sudo dnf install ruff)
ERROR: Missing required tools. Install them and re-run.
```

"0 files OK" in a repo full of bash is not a pass. Cause: this clone lives at
`/workspace/untracked/repos/fedora-desktop`, and `qa-bash.bash`'s discovery
carries `! -path "*/untracked/*"` (`scripts/qa-bash.bash:43`) to skip the repo's
own scratch tree — but the repo's **own path** contains an `untracked/`
component, so the exclusion matches every file in it. Confirmed directly: the
same `find` returns `0`.

This is an artifact of **where I cloned it**, not a defect in fedora-desktop —
at the normal `~/Projects/fedora-desktop` the exclusion behaves as intended. And
`ruff` is genuinely absent in this container, so the gate hard-fails at stage 2
by design regardless.

Net: **the project QA gate could not run here, and I am not claiming it passed.**
What I can claim, having run them directly, is that the one script this plan
adds is clean:

