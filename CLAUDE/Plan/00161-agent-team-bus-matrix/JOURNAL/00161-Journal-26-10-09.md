## 15:22 · finding · —

U23.lxc failed on a host run after M1 and M2.0-M2.10 passed. The LXC member joined, received a's review and acked it, but a's `pingbus recv` printed the expected ack PING plus two TIMEOUT lines, with `DROPPED 1 2 stale=2` on stderr, and `expect-ping` (exactly one PING line) failed. The TIMEOUTs named M2's worker seats as silent targets: the review member a sent seat accb in M2.1/M2.2 (the commit ref) and the review it sent seat accc in M2.3 (the path ref).

Cause: those reviews were answered. M2.2 and M2.3 each find the seat's ack (re = a's review) in the room. Member a never syncs during M2, though, so U23's recv is its first sync since then. By that time the acks are older than the ack timeout (900 s; spec §9 08p uses `ack_timeout_s` for verbs that expect none), so the syncer drops them as `stale` before `record_answer` sees them (`syncer._receive` only records answers from accepted events). The outbox then counts both targets as silent and owes a TIMEOUT for each. M2 has no defect: by design both reviews are acked. The effect sits in pingbus/the spec. A TIMEOUT can name a target whose answer was in the room before the deadline, just because the sender read it late. §10 says "no ack or nack from a target by its deadline", and an ack dropped as stale does not count as received. That is left for a separate decision; it is not changed here.

Fix (U23 only): a new `acceptance_check.py expect-ping-amid-timeouts`. It requires exactly one PING line with every field as `expect-ping` checks it, and allows other lines only when they are TIMEOUTs of the team whose silent target is not the member under test. A TIMEOUT naming that member, another team's TIMEOUT, or a HUMAN line fails. It prints the tolerated TIMEOUT lines, which `u23_ping` keeps as `members/a/recv-ack-<kind>.timeouts` and counts in the evidence line. M1's `expect-ping` stays exact. The member-side wait-review check stays exact too: a fresh U23 member has sent no ack-expected ping, so it cannot owe a TIMEOUT. The docker and VM legs share `u23_ping`, so the fix covers them as well. Whichever leg runs first takes the TIMEOUTs, and later legs see none.

## 15:28 · finding · —

The U23 tolerance from the previous finding (`acceptance_check.py expect-ping-amid-timeouts`, accepting TIMEOUT lines for other members beside the expected ack) has been dropped before it was committed. It would have hidden the bug it was working around. U23 is back on the exact `expect-ping`.

Root cause, fixed in pingbus: `syncer._receive` passed an answer to the outbox only if the event was still accepted after the local checks. An `ack` or `nack` the reader synced more than `ack_timeout_s` after it was sent was dropped as `stale` (§9 08p) and never counted, so a ping its target had answered in time came back as TIMEOUT. Now a stale-dropped answer is still not delivered as a PING line, but it is passed to the outbox. `Outbox.record_answer` decides "in time" from the answer's own `origin_server_ts` against the ping's deadline, never from when the answer was read.

Behaviour change: a late answer (sent after the deadline) no longer counts, even when it is read at once. Before this, a fresh late ack read before the TIMEOUT was printed suppressed the TIMEOUT, which contradicted §10's "by its deadline". So a TIMEOUT now means exactly "no answer sent by the deadline". docs/agent-bus-protocol.md §9 08p and §10 say so.

Tests: test_syncer covers an in-time ack read after the timeout (answered, not delivered, no TIMEOUT), and a late ack read at once and read stale (TIMEOUT stands either way). test_inbox covers the deadline boundary. ## 16:54 · finding · —

A qa-reviewer pass on dfdb4847 found that a stale `ack`/`nack` answered its ping without the checks a fresh one faces: `_local_checks` in helpers/pingbus/syncer.py returned `stale` before the flood and forge checks ran, and `_receive` counted the answer on `stale`. A stale `nack` with a `ref` that fails the forge check therefore cleared its ping's TIMEOUT.

Fix: `_local_checks` now returns staleness apart from the other verdicts. A stale answer (an `ack`/`nack` with `re`) still runs 09p (flood) and 10p (forge) and counts only if neither drops it; it is still dropped as `stale` and never delivered. Any other stale item stops at staleness as before.

Rate decision: a stale answer spends flood budget. It has an effect (it clears a TIMEOUT) and costs a forge call when it carries a `ref`, both of which the receive flood limit exists to bound; exempting it would let a sender flood forge calls with back-dated answers. Stale items that have no effect still spend nothing, matching §9's rule that an item with no effect never counts towards the flood limit.

Tests: a stale nack whose ref resolves answers; one whose ref fails the forge check leaves the TIMEOUT; a stale ack over the flood limit leaves the TIMEOUT. docs/agent-bus-protocol.md §9 08p and §10 now say so.
