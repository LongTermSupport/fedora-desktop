## 13:35 · decision · —   — Owner's answers: themed multi-host teams, human free text, first-class non-ccy members

Owner's answers to the design's questions (by voice), which change the design:

- Teams are themed around a project, not a repository or a forge organisation. Example:
  a team named after an infrastructure project whose members include that project's agent
  and this repository's agent. An agent may be a member of several teams.
- A member is one agent: its primary repository, the host it runs on, and its
  encapsulation (podman ccy session, the bare desktop, LXC, a data-centre server).
  Humans set teams up and decide membership.
- Members in docker, LXC and VMs are first-class from the first version, not deferred
  (D7 reversed).
- Humans may send free text into a room, aimed at specific agents, including from a phone.
  The discipline is the human's. This reverses issue #59's "human text never reaches an
  agent" rule and the design's control-room split (D27); agent-to-agent traffic stays
  pings only.
- Question 2 (a test VM as "another machine" for the reachability check): accepted.
- Question 5 (a handle names a checkout's seat): accepted.
- The event namespace must not read as tied to GitHub; awaiting a domain the owner
  controls, or a neutral label.

Consequence: members on other hosts (a data-centre agent) mean a team's homeserver cannot
be bound to the desktop's loopback. Asked the owner where it runs (an always-on server on
the private network with TLS, recommended, or the desktop with a tunnel) and which private
network the servers use. The build workflow was stopped before it built further on the old
rules; branches it finished are kept for reuse.

## 13:50 · decision · —   — Owner's answers: mixed homeserver placement, a Fedora installer, a non-domain namespace

Owner's second set of answers (by voice), closing Task 1.3:

- Where a team's homeserver runs: mixed. This repository ships a play that installs the
  homeserver, plus a standalone Bash installer that any Fedora desktop or Fedora server can
  run; Fedora only for now, so the play can configure it fully. The play installs it on every
  desktop; whether a desktop's homeserver is used is per team. Convention, to be documented:
  a team whose members are all on one laptop runs its homeserver there; a team that includes
  an agent elsewhere (a data-centre server) runs its homeserver beside those agents.
- Reaching it: the homeserver needs only an address the members can route to. Where a
  private network such as WireGuard carries it, that network is the access control; the
  human's Matrix account is still locked down as tightly as possible.
- Event namespace: the bus is entirely private, so domain-name conventions do not apply. The
  owner prefers a prefix that clearly is not a domain name.
- An infrastructure project that uses this repository will run its team homeserver on its
  own development server; that is filed on that project's tracker, not here.
