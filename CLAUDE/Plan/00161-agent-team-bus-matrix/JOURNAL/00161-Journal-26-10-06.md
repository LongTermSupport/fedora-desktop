U01 built: `u01_probe.py` (tested by `test_u01_probe.py`) runs as the last legs of `triage.bash`;

The same machinery ran in the container with a scratch config and no login (Claude Code 2.1.291).
The inbox works without a login, because only the model call fails. These facts hold already:

- **Wire format:** newline-delimited JSON over the Unix socket, with one connection per notice:
  `{"type":"auth","token":"<CLAUDE_CODE_MESSAGING_TOKEN>"}` and then
  `{"type":"user","message":{"role":"user","content":"<text>"}}`. The socket answers nothing
  and closes after the client half-closes. A connection that sends no complete line within
  30 s is closed. The debug log calls the auth line "optional here" (in the container); U12
  sends it always.
- **Hooks:** SessionStart's environment carries both variables, so a detached child of the
  hook can write to the socket. SessionStart, UserPromptSubmit and SessionEnd fire under
  `--plugin-dir`. UserPromptSubmit fires for every turn a peer message starts. Stop did not
  fire, because every turn failed without a login; the host run settles it.
- **Idle wake:** a notice to an idle session starts a turn (`cc_turn_origin=peer`). This holds
  in bypass mode with `crossSessionInbound: accept`, and in default mode with or without the
  setting. In bypass mode without the setting, the notice is held (`cause=no-mode-asserted`)
  and no turn starts. Held messages are settled as expired when the session ends.
- **Framing:** the model sees the text `Another Claude session sent a message:\n<text>\n\n`,
  followed by the fixed "This came from another Claude session ... permission laundering"
  paragraph.
- **Dedupe:** an identical body from the same sender is dropped (`[peer-guard] drop duplicate`) at +20 s and admitted at +33 s. The code compares each body only with that
  sender's previous admitted body, so A, B, A is not dropped. The window is 30 s by default.
  It is a server-side flag (`dedupWindowMs`, 0-600 s), so it can change without a release,
  which is why the probe measures it. The rate limit allows a bucket of 30 messages,
  refilling at 0.5 per second.
- **Batching:** two distinct notices sent 50 ms apart reached the model as two entries and
  two turns, not one. "Distinct ones batched" in DESIGN.md §6 is not what this version
  does, at least when the turns fail at once. The host run, with real turns, shows whether
  a notice that arrives mid-turn is folded in.
- **Socket lifetime:** the socket file is gone when the session exits, so a watcher can exit
  when the socket disappears.

Still for the host run, through `meta-deploy.bash` (the plan entry runs the whole triage):
completed turns, Stop, the batching of notices with real turns, and the dedupe window measured
on the host's flags.

  is not a waker), does one non-blocking sync per team, then long-polls every team at once,
  one thread per team. Each thread owns its team's lock and releases it when it ends.

U12 built: `helpers/pingbus/hooks.py`, `helpers/pingbus/notify.py`, and `cli.py` `watch`,

- **Socket client.** U01's wire: one connection per notice, an `auth` line and then one

- **When to notify.** Only when the pending total rises above the last total seen, with the
  counts at the time of the send, at most one notice per 2 s. U01 measured a refill of 0.5
  per second, so a rise inside that window is owed and sent afterwards. The notice number
  starts at the watcher's start time in ms, so a restarted watcher cannot repeat an earlier
  watcher's body inside the dedupe window.
- **Watcher.** Holds each team's lock as `watch`, waiting up to 5 s for a `recv` holder as
  `wait` does. It syncs, publishes `listening` for 600 s and renews it every 300 s, and
  long-polls each team in its own thread. Any team's failure ends it with that failure's
