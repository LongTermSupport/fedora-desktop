## Code: no defect found

I looked for each class the brief names and found none worth a change:

- **Python/Go parity of the colour reader (C12).** Both open with O_NOFOLLOW|O_NONBLOCK, fstat
  before reading (a FIFO or a directory is "not a regular file", never a hang), read limit+1,
  and give the same reason for ENOENT, ELOOP, ENOTDIR/EACCES ("cannot be read"), too large,
  not JSON and wrong shape. Go decodes through `pyjson`, so Python-only JSON (NaN, Infinity,
  duplicate keys where the last wins) gets the same verdict as `json.loads`. `v` must be the
  integer literal 1 in both (`type(...) is int` against `Number.IsInt(1)`: `1.0`, `true`, `1e0`
  are refused in both). Stored hex is `^#[0-9a-f]{6}$` in Go against `fullmatch` in Python
  (no trailing-newline difference). The order of stderr lines (role, then colour) is the same,
  and Go's cache stores the joined problem, so a cache hit repeats both.
- **Cache (C13).** `world.read` notes every path it opens, an absent one included, so the
  fingerprint covers `colour.json` appearing, changing (same size: `#60a5fa` to `#a78bfa`),
  being spoiled and going. `TestCacheShowsAColourChangeAtOnce` covers removal. The golden
  scenario `cache-colour-change` says "removed" in its `about` but never removes the file:
  the Go unit test covers it, so this is wording only.
- **Width with escapes (C10).** Both implementations measure the plain pieces (`_rows`,
  `rowsOf`) and add the escapes afterwards, so the 24-bit SGRs take no columns. The red notes
  still go through `_wrapped`/`wrapped`, so each row is still one span with its label.
- **Syncer.** A malformed, foreign or too-dark event gives no colour (`_colour_of`), and a 404
  or 403 gives none too. Neither costs trust. Any other error reading it propagates, as
  `_read_about` already does, which follows fail-fast. A limited sync re-verifies, and that
  re-reads the colour. `mark_untrusted` removes `colour.json`. The filter is sent inline on
  every sync, so no stored filter ID can hold an old type list.
- **Admin.** `_sync_colour` writes only on a difference, never creates `{}` for a team that
  never set a colour, and the test checks that the team record keeps only the old keys. Power
  levels: the main room's `state_default` is 100 and `agent_bus.colour` is not in `events`,
  so only the admin can write it. A human (HUMAN_POWER) cannot.
- **Team file.** `colour` reaches `team.json` only when set, so the config digest of every
  existing team is unchanged (no spurious "out of date"). `agent-bus-install` restarts only on
  `tuwunel.toml`, the drop-in, the binary or the unit, never on `team.json`, so C8's
  "restarts no homeserver" holds. An unquoted `colour: #60a5fa` loads as null and is refused
  with the C7 message, so it fails loudly.
- **Seated sessions (C18).** `config.resolve_home` and `load_bundle` go through
  `home/<team>`. The colour path is `home/<team>/state/colour.json`, which reaches the same
  seat bundle through the link.
- **Public repo.** No install-specific names in any added line. The palette, the
  `localhost.yml.dist` example and the plan text are generic.

## The two judgements asked for

### 1. Is `<team>: <member> (<c|w>)` with marks after it clear?

It is clear enough, and I do not propose replacing it.

- The colon is the right separator. It reads as "on alpha, I am fedora-desktop.2". It stays
  unambiguous however many dots or digits the repository and seat carry, and it does not
  collide with the comma between teams.
- The single-letter role is cheap in width. With two values it is learned at once, and the
  docs (R1) will state it. `(coordinator)` would cost 10 columns per team on a line that
  already wraps.
- The one weak point: team-level marks now sit after the member, so
  `alpha: fedora-desktop.2 (c) (down)` can be read as "this member is down" when it means the
  team's homeserver is. `alpha (down): fedora-desktop.2 (c)` would put team facts beside the
  team. That is arguably better, but not clearly enough to justify re-specifying C15 and C17
  and re-recording the oracle again. The marks keep one fixed order and the docs can say
  "marks are the team's". Leave it unless the owner finds `(down)` misleading in use.

### 2. Is the admin-written `agent_bus.colour` room state the simplest sound route?

Yes. An older member is in fact unaffected, for four independent reasons:

1. Its sync filter (`STATE_TYPES`/`TIMELINE_TYPES`, sent inline every sync) does not name
   `agent_bus.colour`, so the server never sends it the event.
2. Its gap fill uses `GAP_FILTER = {"types": ["m.room.message"]}`, so the event cannot arrive
   that way either.
3. If it did arrive, `protocol.validate_event` returns IGNORE/"type" and `_receive` skips it
   with no log line and no drop. `_read_room_state` acts only on membership and status.
4. Its trust checks read only CREATE, power levels, the team record and the rooms index, all
   unchanged. The admin test asserts the record still holds only the old keys.

The alternatives are worse. A record key would make every older member refuse the whole record
and lose trust: the reason the description already went to the topic. A kit file would reach
host and LXC members through the play but not a ccy image until its rebuild, nor a member on
another machine. It would also need its own install path. The room event reaches every member
through the bus it already trusts, and only the admin can write it. It costs one GET per
verification and a filter entry. It follows the established topic pattern exactly. Simplest
sound choice.
