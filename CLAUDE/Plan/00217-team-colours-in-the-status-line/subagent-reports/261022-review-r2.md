## The two judgements

### 1. Is `<team>: <member> (<c|w>)`, with the marks after it, clear?

Yes.

- The colon reads naturally as "on alpha I am fedora-desktop.2". It stays unambiguous with
  dotted repository names and seats, and it does not collide with the comma between teams.
- A one-letter role is learned at once with only two values, and the docs now define it. The
  full word would cost about ten columns per team on a line that already wraps.
- One ambiguity, already noted in round 1: `(down)` after the member can read as "this member
  is down" when it means the team's homeserver. `alpha (down): fedora-desktop.2 (c)` would put
  team facts beside the team. It is not worth re-specifying C15/C17 and re-recording the oracle
  unless the owner finds it misleading in use. The docs say the marks are the team's.

### 2. Is the admin-written room state the simplest sound route for the override?

Yes. The other routes are each worse:

- A team-record key would make every older member refuse the record and lose trust. That is
  the reason the description already travels as the room topic.
- A kit file would not reach a ccy image until it is rebuilt, nor a member on another machine,
  and it would need its own install path.

Room state reaches every member over the bus it already trusts. Power levels make it
admin-only (`state_default` 100, not in `events`). An older member never sees it: the type is
not in its sync filter, its gap fill asks only for `m.room.message`, and `validate_event` would
ignore the type anyway. It costs one GET per verification and copies the established topic
pattern. The receiver's rule (exact content from the admin only, otherwise no colour and never
a loss of trust) is the right strictness for informational state.
