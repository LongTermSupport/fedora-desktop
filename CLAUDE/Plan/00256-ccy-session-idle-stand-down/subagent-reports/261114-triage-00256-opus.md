## How each unknown is probed

1. **What the supervisor sees.** Leg `files` covers each project with a live ccy session. It
   reads `supervisor-status.json` (version, and each plugin with its state), the `supervise/`
   entries, and a histogram of `decision.log` line kinds, including the lines that mention
   plugin, idle, bus or pending. It also reads the context-sidecar kinds and keys, the
   thread-registry `agent_type` values, `background-processes.jsonl`, Claude Code's
   `tasks/`, `teams/` and recent main and sub-agent transcripts, and the ccy-lifecycle state
   directory. Leg `containers` runs `podman exec` with reading commands. It reports where
   PINGBUS_HOME is (under /tmp, on the mount, or elsewhere), the count of pending inbox files,
   the supervisor processes and whether they carry `--plugin`, and the process names under
   each `claude` process. A background Bash task shows there; a sub-agent does not.
2. **on_idle cadence.** Leg `sample` stats each live project's `supervise/` directory every
   0.25 s. The supervisor creates and removes `plugin-in-hook.<pid>.json` there on every plugin
   hook call. The leg reports the number of changes and the min, median and max gap between
   them. It also reports which plugins are loaded, because no plugin means no marker. The
   context-sidecar changes and the `decision.log` lines written during the window show whether
   a turn or a keystroke happened meanwhile. Caveats: `status-message.json` writes also change
   the directory, and several sessions in one project share it. The report gives each
   project's live-session count.
3. **list and notify.** Leg `listing` writes a scratch registry under the run directory. It
   holds one record whose name has no tmux session. The leg runs `ccy-sessions --list` and
   `ccy-sessions notify reboot-warning --minutes 1 --dry-run` with `CCY_STATE_DIR` pointing at
   it, and reports whether the record is named by name or by directory. It also checks the
   real registry's records that have no tmux session against the real `--list`.
4. **compose stop.** Leg `compose` reports `rpm -q` of the compose packages, and `version`,
   `stop --help` and `down --help` for podman-compose and docker-compose. It also runs
   `docker compose version` and `stop --help`, and `podman compose version`.

**Choice for item 4:** help and version output only, with no throwaway compose project.
PlanTriage.md says triage changes nothing, and a throwaway project would create, start and stop
real containers. A behaviour test of `stop` (containers kept, volumes kept) belongs in Task 4.1's
acceptance.bash.

## How it was tested (in the container, not on the host)

`bash -n` and `shellcheck -x` pass on both files. `--help` prints the usage. A bad `--sample`
exits 2. The full script refuses to run in the container (`plan_require_host`). Each leg was run
directly against a scratch registry under `untracked/scratch/`, with a tmux shim naming one live
session in this container's own project, and with podman and ccy-sessions shims for the
`containers` and `listing` parsing. Every leg produced its section. The `files` and `sample` legs
read this container's real supervisor files. Read only from code, and **not yet findings**:

- The supervisor's `idle` is keyboard idle, meaning no stdin byte for 2 s. It is not "no turn
  running".
- The supervisor ticks every 2 s.
- Plugins are asked `on_idle` when no built-in family claimed the tick and `can_inject` holds:
  keyboard idle, an empty box and confirmed focus. So `on_idle` may be called mid-turn.
- Pending bus items live in the container's PINGBUS_HOME, which the supervisor never reads.
- The lifecycle plugin's `on_idle` writes nothing per call.

The sample run here measured nothing, because this project's ccy-lifecycle plugin is in state
`disabled` (wedge in on_idle). That is an example of why the report prints the plugin state.

## Unclear, for the coordinator

- **On a host with no ccy session running, legs files, containers and sample fail.** They print
  COULD NOT ESTABLISH, so the triage exits 1. That is non-gating in meta-deploy. Item 2 needs a
  live ccy session with the ccy-lifecycle plugin **loaded and enabled**. The plugin is loaded
  only when `--max-age`, a deadline, or a bus is configured. Ask the host agent to leave such a
  session idle during the 180 s sample.
- **Whether pending bus deliveries can reach the supervisor at all depends on PINGBUS_HOME.** It
  sits under /tmp in this container, so the host cannot see it; the containers leg reads it
  through `podman exec`.
- **The decision.log normalisation is best-effort.** It strips paths, quoted text and the
  wrapper argv. Review the report before quoting it into the plan.
