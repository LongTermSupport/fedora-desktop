## 08:25 · decision · T1.1 — a bash library sourcing the existing engine, not a Python helper

Three candidates. The deciding constraint is this plan's own goal of **one detection engine**.

- **A Python helper under `helpers/`.** The repo's default for non-trivial logic, and the wrong
  answer here. The engine that exists — `hook_build_private_denylist`,
  `hook_scan_text_for_private` — is bash, and every consumer (`vmtest`, the plan scripts) is
  bash. Porting it would produce a second matcher and a second allowlist: precisely the failure
  this plan exists to avoid, two detectors that agree until the day they do not, with no gate
  able to notice the divergence.
- **Beside `secret-scan.bash` in `scripts/git-hooks/lib/`.** Wrong location. That directory is
  the git-hook implementation, and putting a run-log scrubber there implies the commit path
  calls it.
- **A new library under `scripts/lib/`, sourcing the hook library.** Chosen. Detection stays in
  one place and is reused rather than reimplemented; the scrubber adds only what is genuinely
  new — redaction by known value, and the verify-and-refuse pass.

Sourcing a `git-hooks/lib/` file from outside a hook is slightly odd, and worth naming rather
than glossing over: the functions are already used that way — the `qa-reviewer` that swept Plan
00063 called `hook_build_private_denylist` directly to build its leak denylist — so in practice
that library is a shared component which happens to live under the hooks tree. If the placement
starts to mislead, moving it is a rename plus two source lines, far cheaper than the divergence
a second implementation would buy.

Tests follow the repo's bash convention: a `scripts/test-*.bash` with explicit assertions and a
`passed: N` summary, wired into `qa-all.bash`, as `test-run-bash-ssh-agent-teardown.bash` does.

**The falsification fixture is decided with the design, not after it.** Task 1.3 is the task
this plan turns on, and the only thing that can show it works is an artefact where redaction was
deliberately incomplete — a secret the redactor was never told about, left in the file. If the
verify pass calls that clean, the scrubber is a check that cannot fail, and publishing on its
say-so would be worse than today's rule of never publishing at all.

## 09:10 · action · T1.2 T1.3 T1.5 — the scrubber, and the fixture it turns on

`scripts/lib/run-log-scrub.bash`, `scripts/test-run-log-scrub.bash` (14 assertions), wired into
`qa-all.bash`.

The design point worth keeping: **`scrub_verify` is the library, `scrub_redact` is the easy
half.** Redacting known values is mechanical. What makes the thing trustworthy is that nothing
publishes on the strength of a redaction — the artefact is re-read afterwards and the caller
gets a non-zero exit if any supplied secret survived. Without that pass, a scrubber is
fail-open: it writes a file it believes is clean, the belief is never checked, and a miss is
silent precisely where silence is most expensive.

Choices that each close a way it could have been wrong:

- **Bytes, not text.** A console log carries control codes and invalid UTF-8, and a secret is
  an opaque byte string. Decoding either would mangle the first and mis-match the second.
- **Literal, not pattern.** A secret containing regex metacharacters would both fail to match
  itself and match things that are not secrets. The test drives this with `a.b*c[d]`, which as
  a regex matches the innocent string `aXbbbcd` — the assertion that the innocent line SURVIVES
  is what catches a pattern-based implementation.
- **An empty secret file is refused, not skipped.** An empty needle matches at every position,
  so a permissive implementation either corrupts the artefact or redacts nothing and reports
  success — a scrub that cannot fail, on the one input where the caller most needs to be told
  something is wrong.
- **An unreadable secret file is a refusal too.** A secret that could not be checked has not
  been shown to be absent, and publishing anyway would be publishing on a check that did not
  run.
- **Atomic write.** `mkstemp` + `os.replace`, so a crash mid-write leaves the original rather
  than a part-redacted file that looks finished.
- **The refusal never echoes the secret.** It names the secret FILE. A message that quoted the
  value would leak it into a ticket while complaining that it leaked into a log.

Falsified on four mutants, each caught by its own assertion against a clean 14/14 baseline:

```
verify_always_clean  -> FAIL  a residual secret is REFUSED
regex_not_literal    -> FAIL  the literal secret is gone
                        FAIL  the non-secret a regex would have eaten survives
empty_secret_ok      -> FAIL  an empty secret file is refused  (+2)
first_occurrence     -> FAIL  every occurrence is redacted
```

Still open in Phase 1: Task 1.4, the pattern backstop over `hook_scan_text_for_private`. Known
values cover what a run was handed; the backstop is for a secret in a shape nobody anticipated,
and it is explicitly the second line of defence, not the first.

**Not changing the off-mount rule.** The scrubber existing does not earn `server-github-token`
a path onto the shared mount — it has no track record, and one miss builds the credential
channel the bridge exists to prevent. That stays a Non-Goal.

## 09:40 · action · T1.4 — the backstop, and two ways a wrapper around it would be wrong

`scrub_backstop` over `hook_scan_text_for_private`, sourced from the commit gate's library
rather than reimplemented. Phase 1 complete; 20 assertions in the suite.

The engine was already the right shape for this — it reports the denylist FIELD NAME of
anything it finds and never the value, which is exactly what a message about a leak must not
contain. What needed adding was two guards, and both are cases where a thin wrapper would have
produced a control that reports clean without checking:

- **An empty denylist is refused.** `hook_scan_text_for_private` returns 0 early when the
  denylist is empty. A wrapper passing that through scans zero tokens and reports clean — a
  backstop over nothing, wearing a security control's clothes.
- **The artefact is projected to printable text first.** The engine reads its input through
  `text=$(cat)`, and a command substitution drops NUL bytes. A console log always has some, so
  a naive wrapper piping the file straight in could let an identifier through. `tr -cd` first
  loses nothing that matters: a leaked identifier is printable by nature.

Both falsified. Removing the projection fails *"a binary artefact does not hide an
identifier"*; removing the empty-denylist guard fails *"an empty denylist is refused"*. Each
mutant also broke assertions beyond the one aimed at it, which is fine — the aimed assertion
failing is what the proof needs.

`scrub_build_denylist` wraps `hook_build_private_denylist` and turns its non-zero status into a
refusal, for the same reason: a denylist that could not be built is not an empty one to shrug
at, it is a scan that cannot run.

The denylist is passed as a **path**, not built inside `scrub_backstop`. That keeps the real
one and a test fixture interchangeable — a security control whose input cannot be substituted
cannot be tested against a case its author did not think of, and would have been exactly as
untestable as the gaps this plan exists to close.

**Phase 1 does not change the Non-Goal.** The scrubber working does not earn
`server-github-token` a path onto the shared mount. It has no track record on a real
PAT-bearing run, and one miss builds the credential channel the bridge exists to prevent.

## 10:05 · finding · T2.1 — the contract, and the three places it does not fit the code as built

Read 00110 `DESIGN.md:329-337` (off-mount artefacts), `:1553-1555` (the criteria), `:2084`
(the throwaway-secrets row) and §10 decision 4. Then read what is actually deployed, because
the design predates the code and three things have to move.

**1. A `planned` count puts a scenario on the BRIDGE allowlist automatically.**
`scenarios.py:113` defines `runnable` as `planned is not None`, and `:339` derives the
allowlist from `runnable` alone. So declaring `server-github-token` with a check count — which
it needs, or it is not runnable at all — would enumerate it to the sandbox. The design says
the opposite: `:2084` "It is not in the bridge's argument enumeration". Two concepts are
wearing one name. `runnable` (the host may run it) has to split from bridge-reachable (the
sandbox may ask for it), via a manifest flag.

**2. The host CLI enforces the same file, so excluding it there excludes it everywhere.**
`vmtest:860` requires `grep -qx "${scenario_id}" "${ALLOWLIST}"` before any run. That check is
right for every scenario built so far and wrong for this one: drop the scenario from the
allowlist and the human's own CLI refuses it too. The allowlist stays the bridge's authority;
the host path needs its own deployed enumeration rather than a hole in this one.

**3. The bridge would archive a PAT-bearing transcript onto the shared mount.**
`bridge_run.py:220-228` copies `transcript.log`, `response.json` and `console.log` into
`untracked/vmtest-bridge/archive/<run_id>/`. Today the *only* thing between that path and a
real credential is the allowlist file being correct. That is a single point of failure in a
deployed artefact a playbook writes — and "one gate, and it only ever permits" is the defect
class this plan exists to attack. `bridge_run` must refuse a host-only scenario from the
manifest it already reads (`:281`), independently of the allowlist.

Two things that already fit, and should not be rebuilt:

- **Host-CLI artefacts are already off-mount.** `vmtest:893` puts everything in
  `${RUNS_DIR}/<run_id>` = `~/.local/share/vmtest/runs/<run_id>/`, which is the exact path
  `DESIGN.md:330` names. Task 2.3 is therefore *not* a new logging route; it is proving the
  archive step is unreachable, plus running the scrubber over what is written.
- **run.bash generates the SSH key itself.** `run.bash:2076` runs `ssh-keygen -t ed25519 -f
  ~/.ssh/id -P "$HL_GITHUB_SSH_PASSPHRASE"` on the headless non-`none` path, so no key travels
  into the guest. The scenario supplies `RUN_BASH_GITHUB_ACCOUNTS=<user>`, a PAT file
  (`:351-353`) and a passphrase file (`:361-362`), and nothing else. The PAT needs
  `vars/github-required-scopes.yml` plus `admin:public_key`, because the run uploads the key
  it just generated.

**The token scenario cannot share `guest-acceptance-server.bash`.** Check 3 (`:93`) asserts
`github_accounts: {}` in `localhost.yml` — definitionally false when an identity is
configured. Reusing the script would produce a scenario that fails for the one reason that is
not a defect. It needs its own guest script and its own `planned`.

**`run_env` is the wrong channel and stays that way.** `RUN_ENV_KEYS` (`scenarios.py:70`) is a
closed set of three non-secret knobs, and its values travel through an SSH command line
(`:72`). Nothing about the token path may go through it. The secret files are host-local,
named on the host CLI, and delivered over the SSH channel — never cloud-init `user-data`, per
`docs/headless-provisioning.md:127-131`.

## 10:40 · action · T2.2 — two enumerations from one flag, and the bridge stops trusting the allowlist

`host_only` in the manifest. `runnable` (the host may run it) now splits from
`bridge_reachable` (the sandbox may ask for it), both derived from the one flag so
`allowlist()` and `host_only_list()` are disjoint by construction. Two hand-maintained lists
would agree until the day one was edited, and that day would be the one where a
credential-bearing scenario appeared on both.

**The bridge refusal does not read the allowlist.** `bridge_run.host_only_refusal` reads the
deployed manifest instead, before anything boots. The allowlist is one generated file, and a
control whose only input is a file something else writes fails open the moment that file is
wrong — which is the defect class this plan exists to attack. It fails closed on every
uncertainty: an unreadable manifest, an absent entry, and anything in `host_only` that is not
literally `false` all refuse. "We could not tell" is not "it is fine".

Five mutants, against a clean 99/99 baseline:

| Mutant | Caught by |
| --- | --- |
| `bridge_reachable` ignores `host_only` | *a host-only scenario is absent from the bridge allowlist* (+2 more) |
| `host_only` coerced with `bool()` instead of type-checked | *host_only must be a bool* — `host_only: "false"` would have enumerated it |
| `host_only_refusal` never refuses | *the vm never boots* (+4 more) |
| an unreadable manifest treated as not-host-only | *an unreadable manifest refuses rather than running* |
| the refusal moved to after the run | *the vm never boots*, *nothing is written to the shared archive* |

The last one is the realistic wrong implementation — the natural place to put this check is
next to the archive step it protects, and there it would already have left a real credential
in a booted guest before objecting.

Two changes beyond the task, both because leaving them would have been a defect:

- **`list-scenarios` no longer offers a host-only scenario.** It was returning the whole
  manifest, so the sandbox would have been handed the exact name to aim a request at. Offering
  a menu item the caller may not order is at best noise.
- **The OK marker reports `bridge=N` and `host_only=N`.** The playbook gated the allowlist on
  `runnable`, which now over-counts: a lab whose only runnable scenario was host-only would
  have tried to render an allowlist the validator refuses to produce. Counting it in the module
  that owns the definition beats subtracting in Jinja.

Five mutants, each caught by the assertion written for it, against a clean 19/19 baseline:

| Mutant | Caught by |
| --- | --- |

The fourth is the one worth having: `[[ ! -r f ]] || ! grep` to `[[ -r f ]] && ! grep` is a

- **A `--github-*` option on an ordinary scenario is refused, not ignored.** The caller

The leak check over refusal messages counts cases that did NOT refuse separately: with no
refusal there is no message, and "no message contains a secret" would then be true for the
emptiest of reasons.

## 12:20 · action · T2.2/T2.3/T2.5 — the scenario, its checker, and the count that was declared twice

`server-github-token` exists: the manifest entry (`host_only: true`), its own guest checker,
secret delivery, the needles round-trip, and the Phase 1 scrubber over the artefacts. The
manifest now reports `bridge=6 host_only=1` — declared, and absent from the bridge's
enumeration.

**It needs its own checker, not the shared one.** `guest-acceptance-server.bash` check 3
asserts `github_accounts: {}`, which is definitionally false when an identity IS configured;
reusing it would produce a scenario that fails for the one reason that is not a defect. The
new checker asserts the opposite half — that the credential worked (SSH remote, `gh auth
status`, a passphrase-protected key) and that nothing of it survived (no agent, no socket, no
askpass helper, no `/tmp/.github_ssh_pp`, no bytes in any process environment, in cloud-init
`user-data`, or on disk). It does not re-assert the general server checks: those are proved
on every `server-fast-provision` run against the same base.

**The secrets go back in, briefly, and that is what makes the scan mean anything.** "No secret
bytes survived" cannot be checked by a script that does not know the bytes. The host writes
them to a 0600 needles file in guest tmpfs; the checker's first act is to read them and
unlink it, and its last is to fail if that file still exists. The harness's own delivered
copies are removed *before* the checker runs, so a residue finding is about what `run.bash`
did, never about the fixture.

This is precisely the trap 00110 `DESIGN.md:1590-1596` names. On the default scenarios the
secrets were never supplied, so a green grep proves nothing. Here they were supplied, they
demonstrably reached the guest, and the assertion is that they are no longer anywhere they
should not be — `user-data` included, which is falsifiable exactly because the bytes DO exist
on the box, just not there.

**The count was declared in two places with nothing tying them.** `planned` in the manifest
and `PLANNED` in the guest script. The guest script asserts its own total — but only after a
whole VM has booted, so a mismatch surfaces minutes in as an `error` verdict. Adding a third
checker made that worse, so `qa-vmtest-manifest.bash` now ties them at commit time, resolving
the script the way `vmtest` resolves it (per-scenario, else per-profile) so the gate cannot
vouch for a file no run will use. It carries its own control: a deliberately mismatched
manifest must be rejected and must name the mismatch, or a check matching nothing would
report success.

**Two checks in the new script could not have failed, and QA caught one of them.** `find /tmp
… | wc -l` discards find's status, so a search that FAILED would report zero sockets and
pass; `find` also exits non-zero merely for stepping on another user's 0700 directory, so its
status was not usable as a success signal either. Both that check and the askpass scan are
now globs, which have no exit status to discard. The `bash-capture-discards-status` semgrep
rule found the first; the second was the same defect one line further on, found by looking.

**A deployment detail that would have failed at run time.** `run-log-scrub.bash` sources the
commit gate's engine at `../git-hooks/lib/secret-scan.bash`, so the play deploys both files
preserving that relative layout. Deploying either alone gives a scrubber that cannot load.
The CLI sources it lazily, inside `scrub_run_artefacts`: it is only needed by a host-only run,
and a CLI that refused to start over a missing optional file would break every ordinary
scenario. Absent when it IS needed is a hard failure, never a skipped scrub.
