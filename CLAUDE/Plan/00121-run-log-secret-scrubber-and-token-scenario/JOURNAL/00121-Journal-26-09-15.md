## 08:25 · decision · T1.1 — a bash library sourcing the existing engine, not a Python helper

Three candidates. The deciding constraint is this plan's own goal of **one detection engine**.

- **A Python helper under `helpers/`.** The repo's default for non-trivial logic, and the wrong
  answer here. The engine that exists — `hook_build_private_denylist`,
  `hook_scan_text_for_private` — is bash, and every consumer (`vmtest`, the plan scripts) is
  bash. Porting it would produce a second matcher and a second allowlist: precisely the failure
  this plan exists to avoid, two detectors that agree until the day they do not, with no gate
  able to notice the divergence.
- **Beside `secret-scan.bash` in `scripts/git-hooks/lib/`.** Wrong location. That directory is
  the git-hook implementation, and putting a run-log scrubber there implies the commit path
  calls it.
- **A new library under `scripts/lib/`, sourcing the hook library.** Chosen. Detection stays in
  one place and is reused rather than reimplemented; the scrubber adds only what is genuinely
  new — redaction by known value, and the verify-and-refuse pass.

Sourcing a `git-hooks/lib/` file from outside a hook is slightly odd, and worth naming rather
than glossing over: the functions are already used that way — the `qa-reviewer` that swept Plan
00063 called `hook_build_private_denylist` directly to build its leak denylist — so in practice
that library is a shared component which happens to live under the hooks tree. If the placement
starts to mislead, moving it is a rename plus two source lines, far cheaper than the divergence
a second implementation would buy.

Tests follow the repo's bash convention: a `scripts/test-*.bash` with explicit assertions and a
`passed: N` summary, wired into `qa-all.bash`, as `test-run-bash-ssh-agent-teardown.bash` does.

**The falsification fixture is decided with the design, not after it.** Task 1.3 is the task
this plan turns on, and the only thing that can show it works is an artefact where redaction was
deliberately incomplete — a secret the redactor was never told about, left in the file. If the
verify pass calls that clean, the scrubber is a check that cannot fail, and publishing on its
say-so would be worse than today's rule of never publishing at all.

## 09:10 · action · T1.2 T1.3 T1.5 — the scrubber, and the fixture it turns on

`scripts/lib/run-log-scrub.bash`, `scripts/test-run-log-scrub.bash` (14 assertions), wired into
`qa-all.bash`.

The design point worth keeping: **`scrub_verify` is the library, `scrub_redact` is the easy
half.** Redacting known values is mechanical. What makes the thing trustworthy is that nothing
publishes on the strength of a redaction — the artefact is re-read afterwards and the caller
gets a non-zero exit if any supplied secret survived. Without that pass, a scrubber is
fail-open: it writes a file it believes is clean, the belief is never checked, and a miss is
silent precisely where silence is most expensive.

Choices that each close a way it could have been wrong:

- **Bytes, not text.** A console log carries control codes and invalid UTF-8, and a secret is
  an opaque byte string. Decoding either would mangle the first and mis-match the second.
- **Literal, not pattern.** A secret containing regex metacharacters would both fail to match
  itself and match things that are not secrets. The test drives this with `a.b*c[d]`, which as
  a regex matches the innocent string `aXbbbcd` — the assertion that the innocent line SURVIVES
  is what catches a pattern-based implementation.
- **An empty secret file is refused, not skipped.** An empty needle matches at every position,
  so a permissive implementation either corrupts the artefact or redacts nothing and reports
  success — a scrub that cannot fail, on the one input where the caller most needs to be told
  something is wrong.
- **An unreadable secret file is a refusal too.** A secret that could not be checked has not
  been shown to be absent, and publishing anyway would be publishing on a check that did not
  run.
- **Atomic write.** `mkstemp` + `os.replace`, so a crash mid-write leaves the original rather
  than a part-redacted file that looks finished.
- **The refusal never echoes the secret.** It names the secret FILE. A message that quoted the
  value would leak it into a ticket while complaining that it leaked into a log.

Falsified on four mutants, each caught by its own assertion against a clean 14/14 baseline:

```
verify_always_clean  -> FAIL  a residual secret is REFUSED
regex_not_literal    -> FAIL  the literal secret is gone
                        FAIL  the non-secret a regex would have eaten survives
empty_secret_ok      -> FAIL  an empty secret file is refused  (+2)
first_occurrence     -> FAIL  every occurrence is redacted
```

Still open in Phase 1: Task 1.4, the pattern backstop over `hook_scan_text_for_private`. Known
values cover what a run was handed; the backstop is for a secret in a shape nobody anticipated,
and it is explicitly the second line of defence, not the first.

**Not changing the off-mount rule.** The scrubber existing does not earn `server-github-token`
a path onto the shared mount — it has no track record, and one miss builds the credential
channel the bridge exists to prevent. That stays a Non-Goal.
