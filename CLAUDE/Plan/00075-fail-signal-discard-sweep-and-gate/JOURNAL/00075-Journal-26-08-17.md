## 17:05 · context · why this plan exists

Two incidents in one session, same shape, one user-facing:

1. **`ssh-handling.bash`** — `gh api user --jq .login 2>/dev/null`, status
   discarded. GitHub answered 502, `gh` put the JSON error body on **stdout**,
   and the blob became "the account name". ccy refused to launch and told the
   owner their `github_accounts` mapping was wrong and to edit `localhost.yml`.
   It was not wrong. GitHub was down. Fixed in CCY 3.36.0 (`b770441`).
2. **`00074/prototype.bash`** — `$?` read after `fi`, which is always 0 (the
   `if` statement's own status, not its condition's). Every legitimate grep
   no-match was reported as `grep failed (exit 0)`. Fixed in `9c47921`.

Owner's instruction: sweep for it, and find **"defence before fix"** tooling —
something that prevents the class rather than catching it in review.

The class in one line: *a command's failure is silently converted into data,
and that data is then used to make a decision or reported as fact.* Worse than
an error, because an error points at the cause and a wrong answer points
somewhere else entirely.

## 17:50 · action · two new semgrep rules, self-tested against the real incidents

Added to `.semgrep/bash-conventions.yml`, both severity ERROR (and
`qa-patterns.bash` fails on *any* finding, so they gate a build):

- **`bash-status-after-block`** — `$?` consumed after `fi`/`done`/`esac`/`}`,
  skipping blank/comment lines between. Scoped to repo-owned trees.
- **`bash-capture-discards-status`** — `var=$(cmd … 2>/dev/null)` with no `||`
  fallback and not used as an `if`/`while` condition. Carries a
  `# FAIL-FAST-OK:` escape matching the repo's Ansible convention.

Both incidents are in the fixture as `ruleid:` cases, so **the gate is proven
against the bugs that motivated it** rather than merely plausible. `semgrep
--test` runs inside `qa-patterns.bash` before every scan, so a rule that stops
matching is a hard error.

Two rule defects the self-test caught immediately: the capture rule also matched
a pre-existing `|| echo` fixture line (fixed with a `pattern-not-regex` on `||`),
and the annotations were on the wrong lines — the multi-line match reports at the
`fi`, not at the opening `if`, so the `ruleid:` comment has to sit above the
terminator. Neither would have been obvious by reading.

## 18:30 · finding · the sweep-ccy report arrived after all — and it beat mine

The four agents eventually delivered. `sweep-ccy`'s report is deeper than the
sweep I ran by hand, and found things I did not.

### The headline: `bash-error-hiding-pipe-echo` has never worked

`pattern: $CMD || echo $MSG` — `$CMD` binds a bare command WORD. Verified
directly against the installed semgrep:

```
cmd || echo "x"                → DETECTED
cmd arg || echo "x"            → MISSED
git ls-files foo || echo "x"   → MISSED
v=$(cmd a b || echo "default") → MISSED
```

**Every real-world occurrence has arguments**, so all 16 sites in the ccy libs
were invisible for the rule's entire life. The rule reported zero findings and
that was read as evidence there were none — a gate whose green tick was the
whole output. Repaired with a regex, matching the sibling `|| true` rule that has
always worked for exactly that reason.

Repaired, it surfaces **15 previously-invisible findings**, including:

- **`common.bash:191`** — `tracked_files=$(git ls-files "$ccy_dir" 2>/dev/null || echo "")`
  then `[ -z "$tracked_files" ]` ⇒ "nothing tracked". This is the SECURITY gate
  that refuses to launch when session data is tracked in git. On a
  dubious-ownership repo (`safe.directory`), a corrupt index, or a broken
  `$GIT_DIR`, git cannot be asked and the failure became the all-clear value.
  Now fatal, with git's own message shown.
- **`scripts/lint` ×5** — `jq … || echo "0"`, so a parse failure made the linter
  print *"✓ No ansible-lint violations found!"*. A checker reporting clean
  because its own parser broke.

The repaired rule promptly flagged a **comment** quoting `|| echo` — caught by
the fixture, fixed with a comment-line exclusion. Any file documenting the
pattern would have tripped it.

## 18:35 · correction · my FAIL-FAST-OK on docker-health.bash:84 was wrong

I annotated it "emptiness is handled on the next line by printing unknown and
returning 1 — the failure is surfaced, not absorbed". That reasoning read the
function in isolation and was wrong.

All three callers do `stats=$(get_container_stats "$container")` — a plain
assignment inside a plainly-called function, so errexit is live. The `return 1`
did not produce the "unknown" row the fallback exists for; it killed the caller.
`ccy --top` printed its header and exited silently the first time podman could
not report on a container.

Fixed by making the contract total (`return 0` with the sentinel, documented),
and the annotation replaced with one that is actually true. Recorded because the
wrong annotation looked entirely sound.

## 18:40 · action · three errexit call-site bugs fixed in network-management.bash

These are the class's third face: not a discarded status, but a **meaningful
non-zero status destroyed by the call context**. No static rule finds them — they
need the call graph.

- `:232` — `get_expected_network_name()` returns 1 for "this network does not
  exist yet" while still echoing the name. As a plain assignment that aborted the
  function, so `ccy --connect` with no argument printed "Available networks:" and
  died without listing one — on exactly the projects someone runs `--connect` to
  set up.
- `:334` and `:378` — `error_output=$(container_cmd network connect … 2>&1)`
  followed by `exit_code=$?`. errexit killed the assignment before `$?` was ever
  read, so the "⚠ Already connected" branch, the error report and the summary
  were all dead code. Re-running `ccy --connect` on an already-connected
  container — the most common repeat invocation — exited silently.

All three now put the call in a condition, which suspends errexit and preserves
the status.

**The reviewable rule to carry forward** (from the report, since no gate can
catch this): a function that returns a meaningful non-zero status must say so at
its definition, and every call site must either be in a condition or read the
status.
