   no-match was reported as `grep failed (exit 0)`. Fixed in `9c47921`.

something that prevents the class rather than catching it in review.

The class in one line: *a command's failure is silently converted into data,
and that data is then used to make a decision or reported as fact.* Worse than
an error, because an error points at the cause and a wrong answer points
somewhere else entirely.

### The headline: `bash-error-hiding-pipe-echo` has never worked

`pattern: $CMD || echo $MSG` — `$CMD` binds a bare command WORD. Verified

```

cmd arg || echo "x"            → MISSED
```

## 18:40 · action · three errexit call-site bugs fixed in network-management.bash

These are the class's third face: not a discarded status, but a **meaningful
non-zero status destroyed by the call context**. No static rule finds them — they
need the call graph.

- `:232` — `get_expected_network_name()` returns 1 for "this network does not
  exist yet" while still echoing the name. As a plain assignment that aborted the
  function, so `ccy --connect` with no argument printed "Available networks:" and
  died without listing one — on exactly the projects someone runs `--connect` to
  set up.
- `:334` and `:378` — `error_output=$(container_cmd network connect … 2>&1)`
  followed by `exit_code=$?`. errexit killed the assignment before `$?` was ever
  read, so the "⚠ Already connected" branch, the error report and the summary
  were all dead code. Re-running `ccy --connect` on an already-connected
  container — the most common repeat invocation — exited silently.

All three now put the call in a condition, which suspends errexit and preserves
the status.

**The reviewable rule to carry forward** (from the report, since no gate can
catch this): a function that returns a meaningful non-zero status must say so at
its definition, and every call site must either be in a condition or read the
status.

### The measurement that changed the analysis

I asserted that a bare `var=$(cmd)` under errexit always aborts the enclosing
function. Wrong, and the first test I wrote agreed with me for the wrong reason.
Measured behaviour:

| Call context of the enclosing function | Failing bare capture inside it |
| -------------------------------------- | ------------------------------ |
| plain call — `fn args`                 | **aborts**                     |
| command substitution — `x=$(fn)`       | does NOT abort                 |
| process substitution — `< <(fn)`       | **aborts** (subshell dies)     |

So `get_container_stats()` never aborted internally — every caller invokes it as
`$(...)`. What killed `ccy --top` was the old `return 1` hitting the CALLER's
plain assignment. My replacement comment claimed the wrong mechanism and has been
corrected to say what was measured. Removing the `return 1` was the real fix; the
fallback is belt-and-braces so the total contract holds however it is called.

### The first harness was invalid and passed anyway

I wrapped the call under test in `if ... ; then` — which suspends errexit for the
command and everything it calls, disabling the exact mechanism being tested. It
reported PASS against known-broken code. Rewritten to call plainly and observe
the child process's exit status from outside. **A verification that cannot fail
is the same defect class as the code it is verifying** — this is the second time
that has bitten in this plan (the first was the `|| echo` rule that never
matched), and both times the green tick was the whole output.

### Verified pre-fix vs fixed, each with a reproduction

- **`ccy --top` render** — `show_container_top` is called plainly from
  `claude-yolo:749`. A container exiting between the `ps` and the `inspect` gave
  `rc=125` with no row printed: the table died. Fixed: `rc=0`, row rendered.
- **Zombie scan truncation** — with two containers listed and the first one gone,
  pre-fix reported `[]` — the second, a genuine TTY zombie, was silently lost.
  Fixed: `[ccy_alive_yolo]`.
- **`--connect` failure diagnostic** — pre-fix printed "Container networks:" and
  died at `rc=125`; the explanation never printed, on the *error-reporting path*,
  so the failure suppressed the report of the failure. Fixed: full diagnostic,
  `rc=1` as designed.
- **`get_container_uptime`** — returned the engine's status directly, so a plain

## 21:15 · action · Task 4.2 — widened to fedora-install, and the rule was broken

Measured first: widening everywhere gives 25 findings across 4 files. They split

### The rule itself was evadable

Before widening anywhere, probed whether the `FAIL-FAST-OK` exclusion actually
does the work. It does not — or rather, it did not need to. The regex anchored
`$` immediately after the closing paren, so **any** trailing comment evaded the
rule entirely:

```
naked=$(cmd 2>/dev/null)                 # flagged
commented=$(cmd 2>/dev/null)  # a note   # NOT flagged  <-- the bug
annotated=$(cmd 2>/dev/null)  # FAIL-FAST-OK: ...   # correctly not flagged
```

So the documented "annotate to exempt" convention was theatre: a stray comment
silenced it just as well. Fixed by allowing an optional trailing comment before
the anchor, verified with the probe (3 and 5 now flagged, 7 not), and pinned in
the fixture so it cannot regress. Second rule-integrity bug found in this plan,
after `bash-error-hiding-pipe-echo` never matching anything real.
