## incident · the deploy found a fourth-play failure, and three things that do not exist

Running this plan's own `deploy.bash` on the host failed at play 4:

```
sysctl: cannot stat /proc/sys/kernel/unprivileged_userns_clone: No such file or directory
```

That is not a transient. `kernel.unprivileged_userns_clone` is a **Debian/Ubuntu
downstream patch** that mainline — and therefore Fedora — has never carried. It
has been in `play-docker-in-lxc-support.yml` since the play was first committed
(`0d9e1f3b`), so this task has **never** succeeded on a Fedora host. It only
surfaced now because nothing had run the experimental play to completion.

Facts, all measured on the host kernel rather than recalled:

| Probe                                        | Result       |
| -------------------------------------------- | ------------ |
| `/proc/sys/kernel/unprivileged_userns_clone` | absent       |
| `/proc/sys/user/max_user_namespaces`         | `2147483647` |

So the *intent* of the setting — let unprivileged users create user namespaces,
which rootless Docker inside the container needs — is already satisfied by
Fedora's default. Only the knob was wrong.

### The part that matters more than the failed task

`ansible.posix.sysctl` **writes the line to the file before it reloads**, and
does not roll back when the reload fails. So the failed run leaves
`kernel.unprivileged_userns_clone = 1` sitting in `/etc/sysctl.conf`
permanently, and every subsequent `sysctl -p` fails — **including the `sysctl`
handler in `play-lxc-install-config.yml:417`**, which is a different play
entirely. One failed task quietly booby-traps a second play.

Simply dropping the entry from the loop would have left every already-affected
host broken forever, with nothing in the repo that would ever clean it. So the
fix removes the line actively (`lineinfile state: absent`, gated on a `stat`),
and does it **before** the sysctl task, because that task reloads and would
otherwise fail on the file it is about to fix.

### Not verified is not verified

The obvious move — delete the entry and move on — would have left the play's own
summary claiming `Sysctl parameters set: … user namespaces` for something it no
longer touches. "Nothing to set" must not silently become "nothing checked", so
the guarantee is now an assert on `user.max_user_namespaces` rather than a
speculative write of a value the kernel already picks correctly. Proven in both
directions with a throwaway play: the real value passes, a base64 `0` fails with
the intended message.

### Three things the feature pointed at that do not exist

Same family as everything else in this plan — a confident answer that is wrong:

1. `kernel.unprivileged_userns_clone` — the sysctl above.
2. `docker-in-lxc` told a user whose host was misconfigured to run
   `playbooks/imports/optional/common/play-docker-in-lxc-support.yml`. The play
   is in `optional/experimental/`. The remedy path was wrong.
3. It then offered `sudo /usr/local/bin/fix-docker-in-lxc` as a manual
   alternative. `rg` across the whole repo finds that string **exactly once** —
   in the `echo` that suggests it. Nothing has ever created it. It is also a
   manual fix, which CLAUDE.md's strict-IaC rule prohibits suggesting at all, so
   it is deleted rather than corrected.

### And the sysctl probe in the script had the class too

```bash
if [ "$(sysctl -n net.ipv4.ip_forward 2>/dev/null)" != "1" ]; then
    errors+=("sysctl: net.ipv4.ip_forward is not set to 1")
```

A missing or broken `sysctl` yields an empty string, which is `!= "1"`, so the
script reports a **specific claim about the value** when the truth is that it
could not read it. Now three distinguishable states, proven with a stubbed
`sysctl`: could-not-read (quotes what sysctl said), is-N-expected-1, and healthy.

## finding · the token menu was being eaten by the caller's `$()`

Pulling the thread on `docker-in-lxc` after the sysctl fix. `select_ccy_token`
ends with `cat "${valid_tokens[...]}"` — **its stdout is the token**, and the
caller reads it that way at line 595:

```bash

```

The multi-token menu above it printed to stdout. So the menu went **into the
variable**, not to the terminal. Two consequences, both live:

- the user was asked `Select token [1-2]:` with **no list visible** — `read -p`
  writes its prompt to stderr, so the prompt escaped the capture and the menu
  did not
- the returned token had the entire menu glued to the front of it

Proven by running the real function from `git show HEAD:` and from the working
tree, both through a pty, with the caller's exact `token=$(…)`:

```

                             Select Claude Code token:
                               1) home (expires: 2099-01-01)
                               2) work (expires: 2099-01-01)
                             TOKEN-AAA<<<
POST-FIX  CALLER RECEIVED >>>TOKEN-AAA<<<
```

This is three lines below the capture bug I fixed in `d24d0ee`. I corrected the
status handling and did not read on. The lesson from that commit was "check the
call sites"; the call site was right there and would have shown it.

### Also in the same function: an unbounded loop on EOF

`while true` with `read`'s status ignored. On Ctrl-D or a non-TTY, `selection`
stays empty, the test fails, `Invalid selection` prints, and it loops **forever**.
Now bounded to 3 tries, reading from `/dev/tty`, with EOF returning cleanly —
verified: EOF gives one line and rc=1; three bad entries give up and stop. The
explicit `^[0-9]+$` test also retired a `2>/dev/null` that was hiding `[`'s own
error message.

The destroy confirmation had the same missing `-r` and no EOF handling. Its
failure mode was already safe (anything but `yes` cancels), so this was only
tidying it to the same shape — checked all three ways: EOF cancels, `no`
cancels, `yes` reaches the destructive step.

## action · plan scripts now write their own log, like triage.bash always has

The operator pointed out that running a play directly produces no log I can
read. True — and it is equally true of `deploy.bash`, which streamed to the
terminal and captured nothing. So a failed deploy could only reach me by being
copy-pasted back by hand, which is exactly the workflow `PlanTriage.md` was
written to eliminate. The rule was already in the repo; the deploy and
acceptance scripts simply never followed it.

Both `deploy.bash` scripts and Plan 00101's `acceptance.bash` now do what
`triage.bash` does:

```bash
PLAN_DIR="$(cd "$(dirname "${BASH_SOURCE[0]}")" && pwd)"
mkdir -p "$PLAN_DIR/logs"
exec > >(tee "$PLAN_DIR/logs/deploy.log") 2>&1
```

`BASH_SOURCE[0]` rather than the repo root, so the path survives the move into
`Completed/`; and `CLAUDE/Plan/**/logs/` is gitignored (`.gitignore:82`,
confirmed with `git check-ignore -v`), so the log lives inside the repo — and is
therefore readable from the CCY container at the same path — without any of it
reaching this public repo. That matters: Ansible output names hosts, units and
home directories.

Placed **after** argument parsing and the `--list` branch, so `--help` still
answers without creating directories — verified, along with the container guard
still refusing with rc=1, and `shellcheck -x` clean on all three.

The case worth proving was the failing one, since that is when the log matters:
a script that writes to both streams and then `exit 1` preserves its exit code,
and the log contains stdout, stderr **and** the final `VERDICT:` line — the last
write survives the non-zero exit rather than being lost to an unflushed `tee`.
