## 20:55 · action · 3.2   — Element's install and keyring grant shared by both plays

Task 3.2, built on `feat/matrix-clients-element-install`: Element's Flatpak install and its keyring grant
(the secret-service override, which must be in place before a profile's first start) moved out of
`play-agent-bus-element.yml` into `tasks/element-desktop.yml`; `play-matrix-clients.yml` imports it and the
agent-bus play imports it too.

**Why a shared file and not the plain move the TODO describes.** `ccy-teams` runs `play-agent-bus-element.yml`
on its own after a team's play (`ops.go` says so to the user: "it installs Element Desktop (sudo) and writes the
Element profile"). With the install moved out of that play, a host that never ran the clients play would fail
that step. The two ways out are the owner's call: this (the install is written once and both plays import it,
`ccy-teams` unchanged), or the stricter one (the agent-bus play only checks that Element is installed and
granted, and `ccy-teams` runs the clients play first: a Go change to `ops.go`, its tests and its usage text).

**What was and was not checked.** `qa-changed` passes: the syntax gate parses both plays (parse only, it runs no
task), and the ansible-patterns, docs and version-pin gates and the `ccy-teams` command suite (395 checks, which
names the Element play) are green. `ansible-lint` is not installed where the edit hook looks for it, so the hook's
lint did not run; that is a dependency gap for IaC, not something worked around. No play was run (the container
never runs one), so the import chain has had no run, only a parse. The task
file's nested install is an `include_tasks`, the repository's usual shape for a task file that imports another,
which an isolated syntax check can evaluate; it means a tag selection would not reach the include's own tasks,
and nothing selects these tasks by tag (stated in the file). Nothing needs a host run: both plays are idempotent
and Element is already installed where it was wanted.
