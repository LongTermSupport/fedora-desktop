**What triggers a project image rebuild today** (launcher `claude-yolo:2084-2150`): it rebuilds when the project image is missing, when the md5 of `.claude/ccy/Dockerfile` changes, when `--rebuild` is given, or when the **image ID** of `claude-yolo:latest` changes. Three things about how that works out:
- **Claude Code's daily update rebuilds projects, not just ccy releases.** The update `podman commit`s a new `:latest`. So the first launch of a day by a project without its own Dockerfile makes every project with one rebuild in full on its next launch. This is likely the most frequent trigger. I worked it out from the code; the first host measurement (M1) confirms or refutes it.
- **Projects built `FROM claude-yolo:base` are also compared against `:latest`**, so they rebuild even when `:base` didn't change.
- **The version label is the second instruction of the base stage** (`Dockerfile:36`). On F44 it changed in 78 commits on 24 days in the last three months. Each change very likely rebuilds the whole base (apt, the Chrome download, the LSPs), and then every project from its first line. Whether buildah really treats a changed label as a cache break is measurement M2.
- **The base is only fresh by accident.** No build passes `--pull`, so `node:lts-slim` and `rust:slim` are as old as their first pull. Only the label's position near the top makes the apt layers run again.
- **The templates' cache mounts cache almost nothing.** They `rm -rf` the mounted apt lists and set `PIP_NO_CACHE_DIR`; Debian's `docker-clean` (if `node:lts-slim` has it, to be checked) also deletes the downloaded packages.
- **The `DOCKER_BUILDKIT` settings do nothing on podman.**

**Recommendation, best value for effort first:**
1. Rebuild a project when the base's *inputs* change (a label hashing the Dockerfile, the whole build context and the upstream digests), not its image ID. Compare against the image the project's own `FROM` names.
2. The freshness requirement (R-FRESH), landing before anything that removes a rebuild:
   - a maximum age on every cached layer (`--cache-ttl`);
   - `--pull=newer` on every build, and `apt-get upgrade` in the first apt layer;
   - a daily upstream digest check and a refresh timer;
   - a stale base named at launch and in the health report.
3. Move the version label to the end of the base stage and order the base from slow-changing to fast-changing.
4. Make cache mounts work, and have the daily prune bound them by age.
5. Document a multi-stage builder pattern for heavy projects, with a `claude-yolo-build-cache` label.
6. Only if heavy projects still pay too much after that: mount ccy's own files at run time, or put project layers between a slow base and a thin ccy top.

The project-Dockerfile contract stays the same for projects that do nothing. The multi-stage builder is opt-in.

**Interaction with the Plan 00235 self-prune:** its rule P1 would remove a multi-stage builder's cache a day after each build. So the prune has to keep images carrying the build-cache label until the maximum age, and also bound the buildah cache-mount directory. Both changes are designed together with Plan 00235, whose Q6 currently holds the prune off.

**Owner questions, with recommended defaults:**
- **Q1 Refresh cadence:** a 7-day maximum age on every cached layer, a daily upstream digest check, and an immediate base rebuild by the timer when a digest changes.
- **Q2 Who rebuilds:** the timer rebuilds the ccy base; each project rebuilds at its next launch, with a one-line notice.
- **Q3 Reporting:** one line on stderr at launch when the image is stale; a health report finding after 2 days' grace.
- **Q4 Upstream tags:** keep floating tags with `--pull=newer`, and record the digest each build used in a label.
- **Q5 Multi-stage contract:** advisory (template, examples, prompts, docs), not enforced.
- **Q6 Run-time mounts or the layer split:** neither now; decide after the second measurement.
- **Q7 Vulnerability scanning:** not in this plan.
- **Q8 Heavy project for the measurement:** a synthetic project-A fixture only (no real project named in tracked files).
