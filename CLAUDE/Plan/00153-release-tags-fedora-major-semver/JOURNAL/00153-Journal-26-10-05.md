## 08:38 · action · —   — Phase 2 built: release command, workflow, docs

Phase 2 built. Design consequence found while writing the tests: F44 takes changes only by pull request, so the release command cannot push a changelog commit to it. It is two steps: `prepare` makes the signed `Release <version>` commit on a release branch and opens the PR; `tag` runs after a merge-commit merge and signs the tag on that release commit rather than GitHub's merge commit. The self-update design already only asks that the tagged commit is reachable from the branch and owner-signed, so it needs no change.

The 42 cases drive the real script against a signed fixture repository with only `gh` stubbed (CI answers success, failure, pending or none). They cover each refusal, numeric ordering with a release-candidate tag ignored, the changelog contents, and that the tag lands on the release commit and is annotated, signed and pushed. The first run had one failing case, a fixture bug (the clone did not check out the branch); fixed in the test.

The first real release will also need F44's CI to be green: the last run on the branch failed at the wsi-stream unit tests, which need a `textual` package CI does not have. That comes from the speech-to-text work, not this plan, and is reported to the owner.

## 10:26 · handoff · P3   — Phase 3 built: self-update follows tags

What is in it. Tags are the default channel and `branch` is the explicit opt-in, chosen by one play variable (`self_update_channel`, rendered to a `CHANNEL` config key). `gate.py` gained `parse_release_tag`, `choose_release`, `branch_major` and `tag_signer`. `update.py` gained `--channel`: the tag fetch has no `+` and prunes, only the highest tag is judged (annotated, internal name equals ref name, `verify-tag` principal equals the pinned one, commit on the remote branch, commit owner-signed, Fedora pin), nothing falls back, and the exits are 20, 21 and 22. `--anchor` lands on the newest valid tag. `cycle.py` carries `SELF-UPDATE-TAG` into the result, the published copy, the status output and the owed marker.

Two additions to the design, both from the tests. First, the tag object's internal name must equal the ref name, otherwise a signed tag object re-pointed under a higher name would pass. Second, git is run with `LC_ALL=C` so a refused tag move is told apart from other fetch failures by git's wording.

Verification, each with a control that could fail. Mutating the code under test and re-running the named tests failed them for: dropping `--prune`, forcing the tag refspec, skipping the commit-signature check, skipping the reachability check, skipping the principal check, skipping the name check, skipping the Fedora pin, skipping the ahead check, lowest-wins ordering, string ordering, an unanchored tag regex, a branch default channel, a tags anchor that ignores tags, an anchor that moves to the wrong commit, dropping the tag from the verify result, the owed marker and the failed-play result, and a cycle that passes `branch` to update (25 end-to-end failures). Two mutations were NOT caught: removing the lightweight-tag check and removing the "good signature, other principal" check when the commit was also checked. In both cases a later check refuses the same input, so they are defence in depth rather than gaps. The principal test was rewritten so the tag principal check is the only thing that refuses it.
