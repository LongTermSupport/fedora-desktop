## 16:01 · correction · 14:12   — A review found two faults in Task 5.3; both fixed test first

Task 5.3 was recorded as built and ticked. A `qa-reviewer` pass over it found two faults that would have stopped the first real release. Both are fixed, test first, and the tick is back to 🔄 until a release has run.

**1. The `tag` job's CI check could never pass.** It needs a passing `qa.yml` run on the release commit, and that commit's only run is the push of `release-<version>`. `qa.yml`'s base job fails a branch that lacks the default branch's tip: always for the release branch of an older major, and for `F44` whenever anything merged during the approval. After one refusal R4 answered `tag` on every later push. The fix: `qa.yml` lets `release-*` through. `TestQAExemptsTheBranchesTheReleaseWorkflowPushes` reads the prefix `release.yml` pushes and requires the exemption; it was red on the real tree first and green after, and its fixtures show a missing or other-prefix exemption found.

**2. R4 counted any commit with a release subject.** A commit a contributor made, a rebased release, or the owner's own `release.bash` commit can never be tagged by the workflow (the signature check), so each would have made every later push ask for a tag that could not be made. The fix: the commit must be the head of a pull request merged into the branch from `release-<version>` of this repository, asked of GitHub (`GitHubPulls.MergedFrom`; a failed answer is an error, never "not merged"). Before building on it I tried the endpoint against the real repository: it returns the merged pull request from the pull request's head commit, with its head branch, base and merge state, for a default branch and a non-default one alike. A mutation that ignored the answer turned two tests red and was restored.

Also changed: the promise test pins each job's permissions exactly (it only checked that some were declared, while three documents said "least"), reads `pr-title.yml`, catches a secret in a job-level or workflow-level `env`, and requires the environment to be named `release`. The release documents say how to recover from a refused `tag` run, from a release pull request closed unmerged (its branch makes the next run say "already prepared"; the reason text now says to delete it), and that a required title check would wait for ever on the release pull request. A wrong comment about the concurrency group is corrected.

**Not verified:** whether GitHub signs the commits a rebase merge lands (the documents say only that a rebase lands new commits, not the signed release commit); and that the workflow runs at all, which still needs the owner's D5 objects.
