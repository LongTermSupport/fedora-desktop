## 09:41 · finding · #248   — issue 248: a token seat in a ccy pool is DESIGN-v2 7.1, declined at gate B

Issue 248 (place-issued refuses a token bundle for a ccy pool), with Plan 00209 gate B, INT6 and DESIGN-v2.md 7.1.

The finding is that this is by design and not a gap to build. The owner answered gate B on 2026-10-30 with the default (INT6 as built), so a pool seat keeps a password (DC16 (c'), DC19 (a)). DESIGN-v2.md 7.1 (d), a pool with no password, is not built. If it is ever chosen, it gets its own kind, `--credential pool_token`, and not `token`. Two reasons: a `token` issue writes the guest token copy, and the roster's `cred` is how a restore tells a guest seat from a pool seat. X23's "as for any seat" means the kind follows the seat: a pool seat is password, an LXC guest seat is token. `place-issued` and the launcher's take both open the store with `seat.Password`. If a token were stored in the pool, every take would send it to /login as a password and be refused.

Nothing was built. The intended path for a remote ccy seat is `member add|return|reissue --credential password` piped into `seat place-issued`.

These places say otherwise and are wrong: INSTALL-PATH.md "The gates" and X30 item 3, `x30-lab.bash` `issue()` (queued in meta-deploy.list; its place-issued step will exit 78), `docs/agent-bus-cross-network.md` (both pipe forms), and the help and stdout of `admin/rotate.go`. None of these was changed. They are left for the coordinator, as one Defence Before Fix change: a ccy bump for rotate.go, and a test that holds every place-issued pipeline's `--credential` to the pool's kind.

Recovery for a seat that was issued but never placed: get the handle from the main room's `added` notice or from the team's status record, then run `member reissue --team T --handle H --credential password | ... seat place-issued`. That is a password reset with device logout, so it kills the lost credential. The other route is `member park` now and `member return` later. Do not re-run `member add`: it claims a second handle. The cross-network doc's "run the command again" is wrong for the same reason.
