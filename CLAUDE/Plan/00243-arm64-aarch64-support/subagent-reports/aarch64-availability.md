# aarch64 availability of every x86_64-pinned artefact

Research for Plan 00243. Evidence was gathered on 2026-11-01 from the GitHub releases API
(`gh api repos/O/R/releases/tags/T --jq '.assets[].name, .digest'`), HTTP status checks
(`curl -sIL -w '%{http_code}'`), vendor repodata (`repomd.xml` -> `primary.xml.gz`), PyPI JSON
(`/pypi/<pkg>/<ver>/json`) and go.dev JSON (`/dl/?mode=json&include=all`). Where an API gave no
digest, the file was downloaded into `untracked/scratch/arm-avail/` and run through
`sha256sum`. In each case where a digest was computed for an x86_64 asset, it matched the
pin the repo already holds, so the method is sound.

Naming used below: `ansible_architecture` is `x86_64` or `aarch64`. A Debian-style map is
`{x86_64: amd64, aarch64: arm64}`.

## Suggested fix pattern

For each pinned download, one map keyed by `ansible_architecture`. A lookup on an
unsupported arch must fail, not fall through:

```yaml
vars:
  ouchVersion: "0.8.1"
  ouchBuilds:
    x86_64:  { triple: x86_64-unknown-linux-musl,  sha256: 866884b08ea69fbab80bd79162df408519068a8fa232c2055038a1e561ad8f4c }
    aarch64: { triple: aarch64-unknown-linux-musl, sha256: 9caf888aa6944887084b917c7872d16a439a82f6ca1754c89816cda5dc957546 }
  ouchBuild: "{{ ouchBuilds[ansible_architecture] }}"   # undefined key -> task errors (fail fast)
```

Better still, add an explicit `assert` that `ansible_architecture in ouchBuilds`, with a
message naming the play. Use the same shape for markless, ART, Ookla, cuDNN and
DisplayLink. RapidRAW needs the full filename in the map. For the QA tools in
`play-python.yml`, map the two different vocabularies (`aarch64` for shellcheck, `arm64` for
golangci-lint). `.qa-versions` can stay version-only because the release digests are
available from the API. If the gate wants pinned digests, add per-arch keys.

For CUDA, put one `when: ansible_architecture == 'x86_64'` block around the repo, key, toolkit
and cuDNN tasks, plus a `debug` that explains the skip. A silent skip is not acceptable under
fail-fast, so if `nvidia_install_cuda` is explicitly set true on aarch64, an `assert` must fail
and say: "NVIDIA publishes no CUDA toolkit for Fedora on aarch64 (fedora44/sbsa has none)".
Note also that RPM Fusion's `akmod-nvidia` on aarch64 is a separate question that was not
researched here.

The `check-pinned-versions.bash` / `update-versions` skill must learn to bump every arch's
sha256 together.
