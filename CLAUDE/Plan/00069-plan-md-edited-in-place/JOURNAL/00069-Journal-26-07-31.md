## 07:15 · finding · — — the numbers that caused this plan

The owner reacted to Plan 00068's `PLAN.md` being 131 KB. Measured rather than
estimated, it is worse than the headline:

```
total lines      : 1894   (137 KB)
blockquote lines :  953   (50%)  <- correction/commentary blocks
checkbox lines   :   56   ( 2%)  <- actual tasks
numbered D-blocks:   27
## Success Criteria section alone: 314 lines
the actual deliverable, reports/one-page-restatement.md: 83 lines
```

Growth was monotonic: 42 KB at creation → 137 KB across 34 commits, and **not one
commit ever made it smaller**. I contributed 6 KB of that this morning, so this is
not a finding about someone else.

Takeaway: the cause is a *correct* rule applied in the wrong place. "Corrections
APPEND, never rewrite" protects line-number citations and is right for `JOURNAL/`.
In `PLAN.md` it makes size a monotonic function of review effort — so the better a
plan is audited, the less usable its plan document becomes. That is a perverse
incentive, not a discipline problem.

## 07:50 · finding · — — "who says corrections append?" — nobody did

The owner asked where the append-only rule for `PLAN.md` comes from. I went looking
instead of defending it, and the answer is that **it does not exist**.

Every append-only statement in the tracked docs scopes itself to `JOURNAL/`:

```
CLAUDE/PlanJournalling.md:72-78  "A journal is append-only… Corrections are new entries"
CLAUDE/PlanWorkflow.md:230,:235  mentions it only to describe JOURNAL/
.claude/rules/*.md               no hits
```

The single source for applying it to `PLAN.md` is **Plan 00068's own Task 6.3**:

```
- [x] ✅ Task 6.3: Apply round-1 findings. Corrections append; never rewrite a
  section a reviewer has already reviewed, or their finding stops referring to a
  real document.
```

Self-imposed, inside the plan, and never challenged for 34 commits. Its stated
justification is also already solved: **`PLAN.md` is a living git-tracked
document.** A reviewer's finding does not stop pointing at real text when the
document is edited — it points at a commit, and git holds every prior state.
Appending to preserve history duplicates what version control is for, and pays for
it with a document nobody can read.

The owner's phrasing settles it: *"journal appends — plan is a living git tracked
document. As long as changes are tracked properly that's all we need."*

**I got the diagnosis wrong in this plan's first commit**, and wrongly in a
specific, familiar way: I wrote that the bloat was "the predictable output of a rule
the project already has… correct in its own place". There was no such rule. I
generalised a true statement about `JOURNAL/` into a false statement about the
project, then blamed the invention for my own choice. That is Plan 00068's signature
failure mode — *a true statement presented as a stronger statement about the world*
— committed at the level of process while writing the plan that exists to fix it,
and caught by the owner in five words rather than by me in three checks.

Overview, Goals, Tasks 1.1/1.2/2.2 and the Success Criteria are corrected **in
place** in `PLAN.md`, which is the behaviour this plan is about. The narration
stays here.
