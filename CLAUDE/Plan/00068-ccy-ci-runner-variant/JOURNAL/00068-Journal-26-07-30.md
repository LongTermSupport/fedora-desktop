## 09:35 — Task 7.2: the census was blind to an entire file, not merely undercounting

Re-ran the prompt census with a pattern matching `read -r -p` as well as `read -rp`, per review
finding C3. C3 predicted ~46; measured **46**, up from 37.

The count is the boring half. **All nine missed prompts are in `lib/token-management.bash`, and
the Round-1 pattern found ZERO there** — the file was not undercounted, it was unseen. It uses
`read -r -p` exclusively, so a pattern requiring `-rp` matched nothing and the census reported a
clean file. Nine blocking prompts on the default path rendered indistinguishable from none.

That is the same shape this estate keeps meeting, now inside the measuring instrument: a control
that silently becomes a no-op, and whose null result reads as a good result. A census reporting
"token-management: not scanned" would have been fine. Reporting `0` was not.

Then the worse finding, from reading the control flow at `:322`:

```bash
while true; do
    read -r -p "Token: " manual_token          # EOF -> returns non-zero, leaves it EMPTY
    if [ -z "$manual_token" ]; then
        read -r -p "Try again? (Y/n): " retry  # EOF -> retry is EMPTY
        if [ "$retry" = "n" ] || [ "$retry" = "N" ]; then return 1; fi
        continue                                # empty is neither -> spin
```

The loop's only exits are a valid token or an explicit `n`. EOF is neither, and EOF is the one
thing guaranteed on a runner. So it spins forever, emitting output, burning a JIT slot until the
job times out with no diagnosable cause. The `while true` also suspends `errexit`, so `set -e`
cannot save it. A hang is worse than a crash.

**This reorders a Task 7.4 item.** `create_token` is an irreducibly human OAuth flow and it sits
on the default path whenever no token is pre-provisioned. So accepting `CLAUDE_CODE_OAUTH_TOKEN`
**by value** is not one capability among six — it is the only thing that makes the default path
survivable unattended. Promoted to prerequisite.

A note to whoever re-runs this: the census pattern is now a known-fragile control. Assert it
against a file known to contain `read -r -p` before trusting a clean sweep, or it will lie the
same way twice.

```
grep -rcE 'read[[:space:]]+-rp' ...                                  -> 37  (Round 1)
grep -rcE 'read([[:space:]]+-[a-zA-Z]+)*[[:space:]]+-[a-zA-Z]*p' ... -> 46  (corrected)
every 'read -<flag>' call                                            -> 74  (the extra 28 are
```

## 10:05 — CORRECTION to the 09:35 entry: I had the spin mechanism wrong

The 09:35 entry, the Task 7.2 report and its commit message all said the `while true` ancestor
"suspends `errexit`", and attributed the EOF spin to `create_token:322`. **Both wrong.** Found
while starting Task 7.3, by executing bash instead of reasoning about it:

```
f() { while true; do read -r -p "x: " v; ...; done; }
( f )      < /dev/null   -> rc=1, ZERO iterations   ABORTS
f || { … } < /dev/null   -> "SPUN 5x"               SPINS
```

A loop **body** does not suspend errexit — only a **condition** context does. What actually
decides spin-vs-abort is the **call context of the enclosing function**.

So the real spinner is **`select_token:610`**: `claude-yolo:1004` and `:1117` invoke it as
`select_token "$TOKEN_DIR" "container" || { … }`, and that `||` suspends errexit through the whole
function body. An EOF-failed `read` leaves `selection` empty, the loop prints
`Invalid selection: (empty)` and `continue`s, forever.

`create_token` called bare (`claude-yolo:897/:907/:970/:1000/:1015/:1111`) does the opposite — it
**aborts**, and aborts with no message about why, which is C4's *other* class. Reached via
`select_token` (`token-management.bash:639/:656`) it inherits the suspension and spins.

**The same source line is a spin or an abort depending on the path that reached it.** That is the
real Task 7.3 finding, and it means "classify each site" cannot be done by looking at the site —
the classification is a property of the call graph. Sharper than what I first wrote, and it only
surfaced because I distrusted my own sentence enough to test it.

What survives unchanged: the census numbers (37 → 46), that all nine missed prompts are in
`token-management.bash`, that the file was invisible to the Round-1 pattern, and that there IS an
EOF spin on the default path inside that file. The headline conclusion was right; the mechanism
and the line were not.

Corrected in `reports/prompt-census-round2.md` (with an explicit CORRECTION block, since the
original text was already committed and pushed) and in PLAN.md's Task 7.2 entry. This journal
entry is the append-only record — the 09:35 entry above is left exactly as written.

Lesson, and it is the same one this estate keeps relearning: I asserted a bash semantic from
memory in a report, a plan and a commit message before testing it. The test took one command.

## 09:20 — Task 7.3: the classification, and a parser bug that would have silently corrupted it

Classified all 46 prompt sites. Report:
[reports/prompt-classification-round3.md](../reports/prompt-classification-round3.md).
Reproducible: [analysis/classify-prompts.bash](../analysis/classify-prompts.bash).

**The task's own premise was wrong.** Task 7.3 said the discriminator is "errexit suspended by
an `if`/`while` ancestor". A loop *body* does not suspend errexit — only a *condition* does. The
discriminator is the **call context of the enclosing function**, and it propagates transitively:

```
outer() { inner; }            # bare call
( outer )   < /dev/null  ->  rc=1, ZERO iterations   ABORTS
outer || …  < /dev/null  ->  "SPUN 5x"               SPINS
```

The `||` suspends errexit through `outer`'s whole body *and* through the bare `inner` beneath
it. That is exactly `claude-yolo:1004` → `select_token` → `create_token`. Corrected the task
text in PLAN.md rather than leaving a wrong premise in tracked config.

**Verdicts**: 32 abort-only, 6 spin-only, 6 spin-or-abort *by path*, 1 falls through, 1 guarded.

**Three things I did not expect:**

1. **All 20 `claude-yolo` prompts are at TOP LEVEL** — the file is 2848 lines with 9 functions
   and 2592 top-level lines. So for 20 of 46 sites the phrase "call context of the enclosing
   function" has no referent at all; they are governed by the script's own `set -e` (line 41).
2. **Five spin paths across four functions, not "the two spinning TUIs"** the task assumed.
   The extra ones came from `check_zombie_containers_startup` and
   `check_project_containers_startup` being invoked as `if ! …` (suspended), and
   `_do_compose_start` reached through two different `if`-guarded callers.
3. **`ssh-handling.bash:357` is the ONLY guarded prompt of all 46.** It detects
   non-interactivity, announces the inference, and proceeds. The correct pattern is already in
   the codebase, used once out of 46 opportunities. So "never *silently* infer" needs no new
   mechanism — just application of the existing one.

**The parser bug is the part worth remembering.** My first block tracker reported an unclosed
`if@2626` in `claude-yolo`. I could have shrugged at one leaked block; instead I looked, because
site `:2818` sits after it and would have been misclassified. Cause: `claude-yolo` builds its
startup banners as multi-line double-quoted strings, and the PROSE inside contains the words
`if`, `for` and `done` —

```
    STARTUP_INFO+="
    …
The container will automatically rebuild if the Dockerfile changes.
```

A per-line stripper reads that `if` as a keyword. Same shape as the `grep`-has-no-`\t` defect:
syntactically fine, silently wrong answer, and no tool reports it. Only an invariant that could
fail (block stack must balance at EOF) exposed it.

So every measurement in the driver now carries a check that can fail, and I mutation-tested the
checks themselves rather than trusting green:

- 63/63 function bodies re-parse under `bash -n`; truncating each by one line makes 63/63
  *reject*, so the check has teeth. (Extending by one does NOT break it — the next line is
  usually blank — so the end is pinned from the other side by asserting it is a closing brace.)
- Reintroducing the multi-line-string bug in a copy makes the driver exit 1. Removing it makes
  it exit 0. Both directions confirmed, mutation copy deleted.

Also caught the driver contradicting itself: it printed "all 9 files balance at EOF" immediately
after reporting that one did not. Fixed to print the actual count — the exit code and the text
must agree (bash-standards §9).

and they touch the launcher (CCY version bump + HOST QA). Left as 🔄 with explicit subtasks

**Statement 2 is where the work is, and it collides with C1.** "CI need safety" cannot be
delivered by the mechanism statement 1 endorses, and the reason is structural rather than a
matter of effort. Recording the spine now, before I have finished verifying it, and flagging
which parts are still unverified:

- `ccy` has **three** layers, not two: the **image**, the **launcher** (`claude-yolo` + 7 libs,
  on the host), and the **entrypoint** (`entrypoint.sh`, which is `COPY`d into the image at
  `Dockerfile:184` and set as `ENTRYPOINT` at `:215`).
- The owner's "normal way" is an **image** mechanism. It therefore delivers **tooling**, which
  is exactly what it was built for, and what it is genuinely perfect at.
- The permission posture (C1) lives in the other two layers: the launcher hardcodes
  `--dangerously-skip-permissions` (`claude-yolo:2792`) and the entrypoint pre-accepts the
  bypass dialog (`entrypoint.sh:245`). Neither is reachable from a project Dockerfile.
- **The sharp bit, which I do not think Round 1 stated:** the entrypoint is *inside* the image.
  So taking the base image "in the normal way" also takes `entrypoint.sh` — the `GH_TOKEN` hard
  requirement, the `gh auth login`, the `/root/.claude` → checkout symlink, the trust flag —
  whether or not the caller wants them. That is not a thing a project Dockerfile opts out of by
  adding packages. It is why the consumer had to `--entrypoint`-override rather than configure
  (fable §2, quoting `run-sandbox.sh:375-402`).

So "adhoc or full blown customisation" resolves per-capability, not globally:

| Capability             | Ad-hoc (stock image + runtime config) | Full (project Dockerfile) | Verdict                             |
| ---------------------- | ------------------------------------- | ------------------------- | ----------------------------------- |
| Tooling                | partly (`CCY_EXTRA_MOUNTS`)           | **yes — already works**   | owner is right; nothing to build    |
| MCP                    | wiring is net-new (E4: zero matches)  | binary can be baked       | both routes viable, both need E4 work |
| Safety (permissions)   | **no**                                | **no**                    | needs a launcher/entrypoint change  |
| Safety (egress)        | plausible                             | no (runtime property)     | ad-hoc only                         |

That table is the Round-2 thesis in miniature: **two of the four rows are unreachable from the
mechanism the steer endorses**, and saying so is the honest answer rather than stretching the
steer to cover them.
