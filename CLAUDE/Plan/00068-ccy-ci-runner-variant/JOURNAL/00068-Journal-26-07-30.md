**This one moved, not the other, for two reasons.** The ftp-camera plan is already merged into
the default branch, so renumbering it would rewrite shared history; and the owner asked for this

**What the counter did and did not do.** `hooksdaemon.latestPlanNumber` read 67, which is
consistent with both 00066 and 00067 having been handed out. The counter is per-clone git config;
it serialises allocation *within* a checkout and cannot see a number another branch took. So this
is not a case of the counter being ignored — it is the counter working as designed and the design
not covering concurrent branches. Worth recording rather than filing as operator error.

## 09:35 — Task 7.2: the census was blind to an entire file, not merely undercounting

Re-ran the prompt census with a pattern matching `read -r -p` as well as `read -rp`, per review
finding C3. C3 predicted ~46; measured **46**, up from 37.

The count is the boring half. **All nine missed prompts are in `lib/token-management.bash`, and
the Round-1 pattern found ZERO there** — the file was not undercounted, it was unseen. It uses
`read -r -p` exclusively, so a pattern requiring `-rp` matched nothing and the census reported a
clean file. Nine blocking prompts on the default path rendered indistinguishable from none.

That is the same shape this estate keeps meeting, now inside the measuring instrument: a control
that silently becomes a no-op, and whose null result reads as a good result. A census reporting
"token-management: not scanned" would have been fine. Reporting `0` was not.

Then the worse finding, from reading the control flow at `:322`:

```bash
while true; do
    read -r -p "Token: " manual_token          # EOF -> returns non-zero, leaves it EMPTY
    if [ -z "$manual_token" ]; then
        read -r -p "Try again? (Y/n): " retry  # EOF -> retry is EMPTY
        if [ "$retry" = "n" ] || [ "$retry" = "N" ]; then return 1; fi
        continue                                # empty is neither -> spin
```

The loop's only exits are a valid token or an explicit `n`. EOF is neither, and EOF is the one
thing guaranteed on a runner. So it spins forever, emitting output, burning a JIT slot until the
job times out with no diagnosable cause. The `while true` also suspends `errexit`, so `set -e`
cannot save it. A hang is worse than a crash.

**This reorders a Task 7.4 item.** `create_token` is an irreducibly human OAuth flow and it sits
on the default path whenever no token is pre-provisioned. So accepting `CLAUDE_CODE_OAUTH_TOKEN`
**by value** is not one capability among six — it is the only thing that makes the default path
survivable unattended. Promoted to prerequisite.

A note to whoever re-runs this: the census pattern is now a known-fragile control. Assert it
against a file known to contain `read -r -p` before trusting a clean sweep, or it will lie the
same way twice.

```
grep -rcE 'read[[:space:]]+-rp' ...                                  -> 37  (Round 1)
grep -rcE 'read([[:space:]]+-[a-zA-Z]+)*[[:space:]]+-[a-zA-Z]*p' ... -> 46  (corrected)
every 'read -<flag>' call                                            -> 74  (the extra 28 are
                                                                        pipe/heredoc reads, not
                                                                        blockers — counted to
                                                                        confirm 46 is not itself
                                                                        an undercount)
```

Claimed by inspection only: that the prompts exist and that `:322` spins on EOF by its control
flow. Nothing executed — `ccy` needs a real engine and the earlier nested-podman attempt failed
for an unrelated userns reason. Empirical confirmation belongs to the HOST triage run.
