**What was written.** `probe-label.bash`, wired in as `triage.bash`'s third leg, so the same host
run the owner already owes settles group F too. It measures rather than asserts:

- Three throwaway `FROM scratch` label carriers: **no labels**, **one unrelated label**, **both
  canonical keys**. The first two are separated deliberately — an image with no labels at all may
  hand the Go template a nil map, which is a different code path from a non-nil map that lacks the
  key, and only the second is what a real pre-convention project image looks like. A probe that
  built only the empty case could answer F1 correctly and still say nothing about production.
- It records **exit code and byte count**, not "empty". Length is the fact; "empty string" is a
  description of it.
- It **executes both comparison shapes** — the naive one, to see whether the two-empties no-op
  actually reproduces, and the prescribed non-empty-assertion one. Reproducing the failure is worth
  more than asserting it.
- A **positive control** with a known label value, because a reader returning empty for
  *everything* would make every row above it meaningless. That is `bash-standards.md` §9: a control
  that fires is not necessarily a control that discriminates.

**Two things I had to be honest about rather than tidy away.**

`triage.bash`'s header said *"READ-ONLY: nothing is built, installed, pulled or written outside the
run directory."* Adding a leg that builds images makes that false. A document asserting a property

**refuses to run rather than reuse or overwrite a tag that already exists** — cleanup deletes what

## 04:05 — C3 too: the baselines are the probe, not the combination

Having found group F unrunnable, I checked the other groups rather than assuming F was the only
gap. Group A turned out to be substantially covered already — `probe-engine.bash`'s provenance
section prints exactly what A1, A2 and A4 ask for. Group C was not covered, and its **C3** is
flagged in the checklist as *"the one to re-measure first"*: it is the only borrowed claim that
drives a **hard failure** rather than a warning, since Task 5.1 specifies an error on the strength
of it. It was measured by a consumer on its own runner and never under ccy's container shape.

`probe-network.bash` measures it. The part worth recording is the experimental design, because the
obvious version of this probe is wrong:

Running `--network pasta:-T,3128 --network podman` and observing a non-zero exit would be
*consistent with* exclusivity — and equally consistent with pasta not being installed, the image
being unusable, or the engine being too old. The mundane explanation is usually the true one. So
the probe runs **each flag alone** as a baseline, and only treats a failing combination as evidence
of exclusivity when **both singles succeed**. If a baseline fails it reports C3 **UNANSWERED**,
explicitly noting that this is not a refutation. It also runs **both orderings**, because
"rejected" and "last flag wins" are different behaviours that a single ordering cannot tell apart —
and last-flag-wins is a third possibility C3 does not describe and Task 5.1 does not account for.

The branch I made sure to write out is the one where the flags turn out **not** to be exclusive.
That would invalidate Task 5.1's specification, and it is the outcome most worth having; a probe
whose report only reads well when it confirms the prior is not a probe.

**C1 and C2 are left open on purpose.** Both need a listener on the host to mean anything, and a
probe that opens host sockets stops being read-only. Recording them as still-borrowed is the honest
outcome — closing them with a probe that measured something adjacent and easier is the failure mode
this plan is named for.

Two probes now, both lint-clean, both verified to refuse the container and leave no report behind,
both **unrun**. The host run the owner already owed for Task 1.1 now settles groups C and F as
well, at no extra cost to them.

## 04:20 — Recording the groups that get no probe, and why

Having covered C and F, the temptation is to stop and let the remaining groups be quietly absent
from `triage.bash`. An unexplained gap gets re-derived by every later reader, and worse, gets
mistaken for a decision — so the checklist now carries a coverage map naming every group, its probe
if it has one, and the reason if it does not.

**Group B is the one that matters, and it is genuinely not automatable safely.** I worked out how
I would write it before concluding I should not:

- The discriminating signal is **not the exit code**. A spin bounded by `timeout` exits 124 — and
  so does a run that did *not* spin, instead launched a real Claude session, and got killed by the
  same `timeout`. Telling the two apart needs the captured output, which means the probe must
  actually launch a real container and a real session on the owner's machine, burning quota and
  producing side effects, to learn anything at all.
- B1 and B2 need a **specific token-file population** — at least two files for B1, exactly one for
  B2. Creating or removing those means a script manipulating the owner's credential store, which
  this plan will not do under the same rule that keeps it away from plaintext credentials.

So group B is an interactive investigation with the owner, not a hand-over script. That is a real
remaining gap and I am not dressing it as covered: B1 and B4 are the two the checklist itself
identifies as able to change a decision if they come back the other way.

**Group D is premature rather than hard** — it specifies the proof battery required before egress
may be *called* a control, against a proxy nobody has built. A requirement on a future
implementation, not a measurement available on today's host.

That is the end of what I can usefully do without the host or the owner. Both probes are written,
linted, wired in, committed and pushed; the standing blockers from yesterday are unchanged.

## 08:30 — D29: one of exactly two deliverables had no specification

Third time today I reported "blocked on human input", third time it was wrong. The external
blockers **are** real and I verified them rather than assuming: no `triage-runs/` (the host run has
never happened), `lts-infra` still absent, no new commits, branch level with origin. What was wrong
again was the leap from *the audit is blocked* to *the plan is blocked*.

The check that broke it: the plan says `ccy` owes CI **exactly two things**, so I compared them
side by side instead of restating the pair. Deliverable 1 has a 189-line `label-convention-spec.md`
— keys, algorithm, writer, reader, comparison. Deliverable 2 had no specification document at all.

**What existed for deliverable 2 was a mechanism, and it is genuinely good**: `Dockerfile.ci` ships
the entrypoint as a file, does not make it the default, selection is the caller's, it carries its
own version label. None of that says what the file *contains* or what it is *called*. The tell was
sitting in Round 2's own prose: `--entrypoint /opt/claude-yolo/<ci-entrypoint>` — a literal
placeholder, because the name did not exist, and the wrong directory besides (the desktop
entrypoint is in `/usr/local/bin/`, `Dockerfile:184`).

Round 4 then recorded it in bold as *"well specified"* and *"the one half of 'the two things' that
is not hand-waved"*, on evidence covering only shipping and selection. **A true statement about the
mechanism presented as a stronger statement about the deliverable** — this plan's signature defect,
operating one level up from a citation. And structurally it is D27 again: two siblings named as a
pair throughout, work done on one.

**How it went missing, precisely.** `round2-restatement.md:329` lists what remains open and names
"`Dockerfile.ci` **contents**". Task 3.1 closed exactly that — what the image layer adds and must
not add. The CI **entrypoint's** own contents were never on that list, or any list. So the item was
not neglected; it was never tracked, and the adjacent item's closure read as covering it.

**The second finding is the one that would have bitten.** Task 5.3 says the CI entrypoint *"prepares
nothing and authenticates nothing"*. That was derived as an **allowlist** claim and is correct as
one — it makes no network call, so the boot allowlist is empty. It has been carried forward as a
**behaviour** claim, and there it is false: preparing local state needs no network.
`entrypoint.sh:240-263` writes `hasCompletedOnboarding`, `bypassPermissionsModeAccepted` and
`projects["/workspace"].hasTrustDialogAccepted`. An entrypoint that genuinely prepared nothing
leaves a TTY-less CI job blocking on onboarding and trust prompts — **the group-B spin this plan
exists to prevent, reintroduced by its own specification.** "Empty boot allowlist" had become
"empty boot behaviour".

The propagation grep found **three** sites, and the third was the worst: `phase45-mcp-and-egress.md:188`
said *"prepares nothing, authenticates nothing, and asserts nothing about trust"* — naming trust
explicitly, which is exactly the clause that breaks it. One command, run because the countermeasure
this plan wrote down and then failed to run fifteen times says to run it.

**`tini`.** Specifying the artifact surfaced a defect in the mechanism the plan endorses.
`Dockerfile:215` is `ENTRYPOINT ["/usr/bin/tini", "--", "/usr/local/bin/entrypoint.sh"]`, and
`--entrypoint` replaces the **whole vector** — so "selection is the caller's, explicitly" silently
drops `tini`. Cost: no zombie reaping, and no signal forwarding, so a cancelled CI job hangs until
the runner's hard kill. Invisible in a short job, which is why it has to be written down rather than
discovered. The spec publishes the required caller form and **rejects** the tempting fix of having
the script re-`exec` itself under `tini` — that hides a process-model change inside a script and
double-wraps a caller who already did the right thing.

**What I did not do.** No `ci-entrypoint.sh` and no `Dockerfile.ci` were written — that is
implementation, forbidden by this plan's Non-Goals, and it needs a CCY version bump and host
testing. Review reports were left exactly as written: `fable-review-4.md` and `-6.md` are testimony
about what a reviewer concluded at the time, and rewriting them would destroy the audit trail that
makes D29 legible. PLAN.md and the design documents are current-state and were corrected **in
place**, per the owner's ruling that PLAN.md is a living git-tracked document.

**Honesty about the new material**: G1–G3 are unproven claims, recorded as such. G1 (`--entrypoint`
drops `tini`) is OCI-documented behaviour I have not measured; it is cheap and read-only and is the
natural fourth leg of `triage.bash` — deliberately **not** wired in now, because the owner has not
yet run the three legs that exist, and adding legs to an unrun script is churn, not coverage. G2 and
G3 are group-B-shaped and inherit group B's conclusion: distinguishing "blocked on a prompt" from
"killed by `timeout`" needs captured output and real quota, so they are an interactive investigation
with the owner, not a script.

Sixteen instances of the propagation defect, and fourteen of the meta-bug. The pattern in today's
