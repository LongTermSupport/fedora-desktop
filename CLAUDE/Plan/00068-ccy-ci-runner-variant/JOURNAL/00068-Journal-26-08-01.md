## The thing I was not looking for

Checking the `--network` collision surfaced the internet preflight at `:2518-2593`:
`podman run --rm --network <net> alpine wget http://google.com`, then a bare `exit 1`. It
needs an unpinned image pull and egress to `google.com` — neither of which a squid-allowlisted
runner grants — and it is on the path of every launch. Same defect class as `--device
/dev/dri`, so requirement 2 now names both, and the risk table records that this class has
materialised twice.

Recorded as **E7, read not measured**. `triage.bash` cannot settle it: the desktop has open
egress and a warm cache, so it passes there and says nothing about the runner. Filed against
lts-infra Plan 00030 as open question 2, where the runner can actually be measured.

Phase 4 left open on purpose — Task 4.1 is gated on the owner decisions, two of which change
what gets built.

## Later same day — the owner reversed both retirements, and was right

Correction to the entry above. MCP and `--egress` should not have been retired.

- **MCP**: `runner.yml:210-211` names *"the MCP GitHub server"* as something the runtime
  allowlist exists to serve, and `:251-253` keeps `registry.npmjs.org` allowlisted specifically
  so it can be fetched. The estate had already provisioned for the thing I declared unnecessary.
  My Decision 7 also proposed the checkout's own `.mcp.json` as the mechanism — which the
  deleted spec had already rejected with a reason (`--strict-mcp-config` exists precisely
  because the checkout controls that file). Restored as `reports/mcp-and-egress.md` with its
  three dead premises marked.
- **`--egress`**: my reasoning was factually wrong, not merely mis-weighted. I claimed the
  runner's layers already covered the container. squid binds `127.0.0.1:3128` and the fence
  drops podman's subuid range (`60-runner-egress-fence.nft.j2:54`) — so the container reaches
  neither the proxy nor the internet. `--egress` would have been its *only* route in.

  The owner then dropped it anyway, for a better reason: ccy structurally needs unfettered
  egress at launch (npm auto-update, Docker Hub, the preflight), and the allowlist buys little
  against a targeted adversary who necessarily has `github.com`. Decision 8 now records that
  reason, and hands the runner's own posture back to lts-infra as an open question.

Both errors have one cause: I audited against this plan's working rule and never against the
owner's steer, whose governing text says *"CI need safety and MCP etc"*. That is the failure the
risk table already lists as materialised three times. Now four.

**New scope from the owner**: Decision 9 — CI runs with a restricted tool surface, read-only
w.r.t. the repo, no `--dangerously-skip-permissions`. Reverses Decision 4 for CI. The sharp edge
is E8: if an ungranted tool *prompts* rather than refusing, a TTY-less job hangs — the exact
failure this plan exists to prevent, reintroduced by the safety feature. Unverified, and it
gates Task 4.1.

**Concurrency**: the owner asked whether jobs could be forced to one and queued. Yes, and it
fixes more than the container-name race I found — `runner_instances: 4` against one checkout per
repo means concurrent jobs for a repo check out different SHAs into the same tree. Filed as
lts-infra Plan 00030 Task 2.8, with a per-repo `flock` preferred over `runner_instances: 1`.
