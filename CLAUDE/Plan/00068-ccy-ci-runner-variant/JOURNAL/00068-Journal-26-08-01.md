## Requirement 5 added — ccy cannot be handed a GH_TOKEN

Owner: *"look at how ccy launches, the UX where human choose the claude key and the github
account"*. I had been reasoning about GitHub's API in the abstract and had told them a
per-project deploy key was unnecessary because tokens work over HTTPS. Reading the launcher
instead:

ccy is **SSH-first, and the SSH key IS the identity mechanism**. Key 0 is primary
(`ssh-handling.bash:321-326`); ccy SSH-probes `git@github.com` and parses `Hi <user>!` to learn
which account the key belongs to (`:304`, `:341`), failing outright if it authenticates to
nothing (`:382-394`); the key's *filename* carries the alias, `github_<alias>` →
`gh-token-<alias>`, and **that** function yields `GH_TOKEN` (`:425-457`), cross-checked against
the probed user (`:475`).

So per-project GitHub account selection **already exists and is already flag-driven** — that was
the owner's point, and my "N accounts, N seats" objection was answering a proposal nobody made.

The genuine gap: `build_ssh_mounts_and_validate` runs unconditionally (`claude-yolo:870`; only
discovery is gated on `--no-ssh`), and the only two sources of `GH_TOKEN` are the alias function
and `gh auth token` (`:496`) — the box's ambient account. **Neither accepts one from the
caller.** A runner that has minted a per-repo one-hour token cannot hand it over. The plumbing is
there (`:2751`, `-e GH_TOKEN`); honouring an already-set value is what is missing.

Noted in the requirement rather than glossed: supplying a token does not remove the SSH key,
because the key is also the identity probe. A CI mode has to say what happens to that.

## Token-first, and the OAuth exposure is global not CI

Owner: *"maybe ccy can opt to be token first, specially in CI mode?"* and, separately, that
dodgy dependencies reading the Claude OAuth token is *"a global weakness not ci specific"*.

**Token-first is smaller than "ccy is SSH-first" implies, because the container already tolerates
it.** `entrypoint.sh:39` guards the identity cross-check on `[ -n "$GITHUB_USERNAME" ]` and `:59`
guards SSH setup on `[ -n "$SSH_KEY_PATHS" ]` — both skip when empty, and nothing in the image
requires a key. `GITHUB_USERNAME` can come from `gh api user --jq .login`, which **ccy already
calls** at `ssh-handling.bash:475` as a cross-check; token-first promotes it from verification to
source. So the entire blocker is launcher-side, at `claude-yolo:870`. No image or entrypoint
change. Also the better story for any desktop without `play-github-cli-multi.yml`, so it goes in
as a general capability that CI defaults to — Decision 3's principle.

**On the OAuth token: correct, and it is not CI-specific.** `claude-yolo:2750` exports it and
`:2771` passes `-e CLAUDE_CODE_OAUTH_TOKEN`, so any process in the container can read it. The
desktop is exposed identically — same var, same `--dangerously-skip-permissions`, and desktops
run `npm install` constantly. It is not fixable by hiding: Claude Code must hold the credential.
The env-not-argv choice at `:2745-2749` closes the other-user hole via `/proc`, not this one.

The control that exists is blast radius, and ccy already has the mechanism — a pool of named,
dated tokens with expiry surfaced. A dedicated CI token means revocation without killing desktop
sessions. Provisioning decision, not code. Recorded in PLAN.md as an accepted stated risk so it
is a decision rather than an oversight; CI raises likelihood (unattended, scheduled, unwatched)
without changing the mechanism.

## The framing correction — I invented a constraint and then designed under it

Owner: *"what i think we keep forgetting — i suggested a long time ago that we engineer a CI
flavour for ccy. ccy functionality is up for grabs, we can change it, we can have a special ci
mode that is special and different to normal mode."*

Correct, and this is the root of several days of distortion. Two constraints were being
conflated, and the wrong one enforced:

- **"Do not build a parallel CI product beside ccy"** — real, and it is all Decision 1 ever said.
  The abandoned design removed the project's own `Dockerfile`, which is the seam.
- **"Do not change ccy's behaviour"** — **never the instruction.** I wrote it into the plan as
  *"the only permitted changes are the two above"* and then treated it as given.

The clearest symptom is requirement 1: `ci-required-config.md` specified a fail-fast guard at
each of **46 prompt sites**. That number is an artefact of insisting CI walk the desktop's
interactive discovery path. A CI flow — resolve image, resolve credentials from what it was
handed, run, exit — never reaches most of them. The census is still the right inventory; it was
the wrong deliverable.

Symptom two: I kept justifying each CI need by its desktop generality ("token-first is also
better for desktops without the multi-account play") rather than by CI needing it. True, and
sometimes a good reason — but it was doing the work of getting past a rule that did not exist.

New Task 3.5 makes the CI flow the deliverable, listing what it reuses (image build, token store)
and what it deliberately never touches: network auto-detection and compose negotiation
(`:1789-2498`), `save_launch_config` (`:2607`), the leftover `rm -f` (`:2741`), `stty`
(`:2726-2729`), the post-run teardown (`:2789+`). Requirement 1 gets re-derived against it.

Corrected in place, with the old text quoted: the Standing principle section, the Goals, the
