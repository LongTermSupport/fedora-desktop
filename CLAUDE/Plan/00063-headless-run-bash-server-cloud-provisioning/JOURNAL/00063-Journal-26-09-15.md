## 00:40 · correction · a closure built on two false premises, withdrawn

The owner reported the headless path is in production, provisioning the hosts of a separate
infrastructure repository, and asked whether that closed the plan. I marked it Complete. The
mandatory `qa-reviewer` pass came back **FIX-BEFORE-MERGE**, and it was right on both counts
that mattered — the closure rested on two things I had asserted and not checked.

**"The lab structurally cannot reach Tasks 3.3 and 3.4" is false.** I told the owner that
waiting for a lab run to cover the token and SSH paths was waiting for something that could
never arrive, and closed on that basis. 00110's own design says the opposite:
`DESIGN.md:1554-1555` assigns both criteria to the opt-in, human-gated `server-github-token`
scenario, which is designed and simply not built. The correct statement is that the **default
six** scenarios cannot reach them, because each hardcodes `RUN_BASH_GITHUB_ACCOUNTS=none` —
a property of those scenarios, not of the lab. The plan tree already knew this and I argued
against it from memory rather than reading it.

**"The missing-value aborts are not covered by a test" is also false.** This plan's own
`acceptance.bash:79-129` already mechanises them with ten asserted gates, cited by Task 2.8.
I proposed building what existed, and offered the owner that work as an option.

Both errors pointed the same way: they made closing-on-assertion look better than it was.
Status reverted to In Progress, Tasks 3.3 and 3.4 reopened with the route named.

**Production use does not prove what 3.4 asks.** A real deployment proves the clone works. It
does not prove the agent was torn down, the transient askpass helper removed, or the secret
files unlinked — none of which is visible from a run that succeeded. I had deleted the
enumeration naming those obligations in the same edit that ticked them, which is how a plan
stops being able to tell you what it has not done. Restored, each as its own line.

## 01:05 · finding · the teardown this plan was going to certify was itself broken

Found while reasoning about what Task 3.4 actually owes. `hl_ssh_agent_stop` treated a
non-zero `ssh-agent -k` as one state and it is two:

- the agent was **already gone** — harmless, the function is idempotent and `hl_cleanup` may
  have got there first;
- the kill **failed** and the agent is still running, with an unlocked key reachable through
  `$SSH_AUTH_SOCK` for every remaining step of the run: ansible-galaxy, the main playbook,
  each optional playbook, the reboot.

It warned on both and returned 0. So the one outcome the function exists to prevent was
reported as the harmless one and carried past — a skip-and-warn on the security-relevant path,
and precisely the obligation Task 3.4 was about to be ticked for.

Fixed at `run.bash` v1.21.0: `/proc/<pid>` discriminates — it answers without signalling
anything and without a redirect that would hide the answer — and a survivor aborts through
`headless_fail`, naming the pid and the exposure. `HL_SSH_AGENT_PID` is deliberately left set
on that path so the `hl_cleanup` EXIT trap still gets its attempt at the agent this one could
not kill. Minor rather than patch, because a run that previously succeeded with a warning now
fails.

`scripts/test-run-bash-ssh-agent-teardown.bash`, ten assertions, wired into `qa-all.bash`. It
uses the awk-extract-and-source pattern `test-run-bash-headless-localhost-yml.bash` established,
because run.bash provisions on load and a test must never start that. Falsified against a copy
carrying the previous body: 5 of 10 fail, decisively on *"a surviving agent aborts the run —
want 1, got 0"*.

**A defect in my own test, caught while writing it.** The first draft asserted that the abort
leaves `HL_SSH_AGENT_PID` set by checking the parent shell after calling the function in a
**subshell** — where `unset` cannot propagate regardless, so the assertion would have passed
whatever the code did. A check that cannot fail, inside the test written to close one. It now
asks `headless_fail` what the variable held at the moment it was called.

Two smaller things the review raised and I have not yet acted on: `hl_cleanup:421` uses
`rm -f` while its comment and the help text both say "shred", and `hl_resolve_secret:134-140`
accepts a literal secret on a non-cloud box — which is half of why the "no secret bytes"
criterion cannot be ticked from the environment side alone.
