## 23:10 · finding · P1 — the reported session log refutes the obvious explanation

User reported `ftp-camera` "not working at all" on Airbnb WiFi, with the
implied cause being a weak/congested public network. The pasted session output
does not support that.

The wrapper's log-display awk has an explicit red branch for both failure
classes:

```awk
/FAIL LOGIN/  { printf "  %s[fail]%s %s\n", r, n, $0; ... }
/FAIL UPLOAD/ { printf "  %s[fail]%s %s\n", r, n, $0; ... }
```

**Not one `[fail]` line appears in the entire 8-minute session.** Every login
succeeded and every transfer vsftpd saw completed — `sort` fires exclusively
off the `OK UPLOAD` log line (`async_monitor_loop`), and it fired 8 times.

A weak or lossy link produces aborted data connections and `FAIL UPLOAD`
entries. This log has neither. What it has instead is the *same frame*
(`DSC06824`, .JPG x4 and .ARW x4) transferring successfully over and over
while no second frame ever arrives.

So the question is not "why is the network dropping transfers" — it is "why is
the camera re-sending frames that already landed".

## 23:14 · thought · P1 — H1, and why it is not being treated as fact

The mechanism that best fits: async mode moves the file out of the camera's
chroot the instant the upload completes. `sort_one_file()` does
`sudo mv "$file" "$dest_dir/"`, relocating `/DSC06824.JPG` to
`photos/2026/07/26/JPG/`. A camera that verifies its own upload — `SIZE`,
`LIST` or `MLSD` on the path it just stored — would be told the file does not
exist, conclude the transfer failed, and re-send.

That also accounts for two details a pure network story leaves dangling:

- overlapping camera sessions (`CONNECT` 22:53:27 while the 22:53:06 session
  was still live) mean concurrent retries `STOR` the same path, interleaving
  writes — which explains the ARW that arrived with no readable EXIF at
  22:58:17, since a Sony ARW carries its date in the leading TIFF IFD and a
  merely-truncated file would still parse.
- the loop never advances, because the verification failure is deterministic.

This is a strong hypothesis. It is **not** being promoted to a cause, and no
fix is being written against it yet. `CLAUDE/AgentNotes.md` records exactly
this failure mode from Plan 00062 — a confident-sounding cause was invented,
then repeated as fact across a playbook, journal and commit messages, and sent
the whole fix in the wrong direction. The competing explanation (H2:
camera-side timeout waiting on the `226`) fits the same observations and is
not yet excluded.

## 23:20 · decision · T1.2 — how to separate H1 from H2

Both hypotheses predict identical upload-side behaviour, so no amount of
staring at the existing log resolves them. What does resolve them is the FTP
verb stream: H1 requires the camera to issue a post-`STOR` check and get a
negative answer; H2 requires no such check at all.

vsftpd emits that stream under `log_ftp_protocol=YES` (which is honoured only
when `xferlog_std_format=NO` — the deployed config already sets that).

Rejected: templating `files/etc/vsftpd/vsftpd.conf` behind a debug variable.
That persists into deployed state and needs a playbook round-trip to toggle.

Chosen: a `--debug-ftp` wrapper flag appending to `/run/vsftpd-camera.conf`.
The wrapper already synthesises that runtime file to inject `pasv_address`, so
the mechanism exists; `/run` is tmpfs, so the setting cannot survive a reboot
or drift into the Ansible-managed `/etc` copy. The wrapper itself is
Ansible-deployed, so this stays inside the IaC boundary.

Credential note: the `PASS` verb carries the FTP password as its argument.
Rather than rely on vsftpd masking it, both the live display awk and
`triage.bash` drop `FTP command:.*"PASS` explicitly — `triage.bash` writes to
a file, so a leak there would be durable.

## 23:26 · finding · P3 — the hotspot failure is confirmed from source, no triage needed

`ftp-camera --hotspot` failed with `NetworkManager connection 'Hotspot' not
found`. Root cause is readable directly in `play-ftp-camera.yml` — the play
only ever *tuned* the profile:

```yaml
when: ftp_camera_hotspot_connection in ftp_camera_nm_conns.stdout_lines
```

and when absent, printed a `debug` telling the user to create it by hand in
GNOME Settings. That is a manual system change, which
`CLAUDE/InfrastructureAsCode.md` prohibits outright. The profile therefore
never existed on this machine, and `--hotspot` has never been able to work —
it is not a regression, it never worked.

This one needs no host data, so it is fixed in this pass: the play now creates
the AP itself (`nmcli connection add`, vaulted WPA2 PSK, `ipv4.method shared`,
autoconnect off), and still tunes a hand-made profile if one exists.

Two deliberate choices in the AP config:

- `pmf 1` (Protected Management Frames disabled) and `proto rsn` +
  `pairwise/group ccmp` — plain WPA2-CCMP, no WPA3 transition. Sony camera FTP
  clients are WPA2-only; leaving PMF at the NM default is a known association
  failure on newer wpa_supplicant.
- `autoconnect no` — the AP must come up only for a camera session, because on
  Intel CNVi the radio cannot be client and AP simultaneously.

That last point is a real UX consequence and is now documented in the play
summary and `--help`: the laptop loses its own internet while the hotspot is
up. `--async-copy` survives it — files land in the local rclone VFS cache and
drain to the remote on reconnect — so it costs latency, not data.

## 00:20 · finding · P1 — CORRECTION 2: F3 was over-read too, and it lets the network back in

Having been caught overstating once, I went back over the retry-loop
reasoning looking for the same defect. It is there, and it is worse, because
this one propagated into the commit message and the README.

The 23:10 entry called F3 (zero `FAIL LOGIN` / `FAIL UPLOAD`) "the
load-bearing fact" and concluded the weak-WiFi explanation "does not survive
contact with the log". That inference does not hold.

`OK UPLOAD` is written when the **data** transfer completes. The
`226 Transfer complete` that tells the *camera* so goes afterwards, on the
**control** connection. Those are different sockets. If the control socket is
already dead by then — a congested AP reclaiming an idle connection while the
data channel is busy with an 80 MB ARW, a NAT timeout, client power-save —
then vsftpd logs `OK UPLOAD` and the camera never learns the transfer worked.
It retries. Zero failure lines. On a genuinely bad network.

So F3 rules out **data-channel** failure only. It says nothing about the
control channel, and therefore does not exclude a network cause at all. I
took "no FAIL UPLOAD" to mean "the network is fine", which is a strictly
stronger claim than the evidence carries — the same move as before, just
harder to spot.

The sound version is narrower and still useful: *the camera is re-sending
frames whose data reached the server.* Why it does not know that is the open
question, and there are now three live answers, not two:

- H1 — the file is moved out of the chroot before the camera can verify it.
- H2 — camera-side timeout waiting on the 226.
- H2b — the control connection dies before the 226 can be delivered.

H2b deserves weight I did not give it. It fits F8 (the camera keeps opening
*new* control connections instead of reusing one, which is what a client does
when its previous one went away), it fits F6 (2-15 s auth latency on a
congested link), and it fits the owner's report that the identical setup works
on other networks — which a purely code-side cause does not explain at all,
since the code is the same everywhere.

Also logged three unverified premises my own analysis leaned on without
noticing: that more frames were even waiting (the "never progresses past the
first frame" framing assumes a second frame existed — nothing establishes
that); that Sony's FTP client verifies uploads at all (H1 requires it and
nothing here demonstrates it — if false, H1 collapses); and that the camera's
own FTP menu settings were unchanged.

The `--debug-ftp` probe survives all of this unchanged, which is reassuring
about the design if not about the reasoning: the verb stream discriminates all
three. H1 predicts a post-`STOR` SIZE/LIST/MLSD getting a negative answer.
H2b predicts the session going silent after `STOR` with no further verbs. H2
predicts the camera dropping the connection at a consistent interval.
