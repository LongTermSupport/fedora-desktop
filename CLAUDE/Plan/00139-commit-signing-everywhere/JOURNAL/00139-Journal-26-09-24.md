## 16:50 · decision · —   — Why, and the owner's ruling on agents signing

The owner asked for commit signing to be rolled in, because another system of theirs is
starting to assume it for this repo. Their reference clone was fetched and is current on
all 8 branches. At its pushed state, nothing there checks commit signatures on this repo:
it pins a commit and digest-checks `run.bash`. This repo's GitHub rulesets do not require
signatures either. The owner chose to build signing anyway, ahead of need.

is still a huge security win - we get commits verified by ME or something from MY MACHINE /
the goal is not to prevent MY OWN AGENTS from being able to push stuff". That overrules
Plan 00137 D3, and it gives this plan's D2 to D4.

What it did:
- `play-git-configure-and-tools.yml` generates `~/.ssh/id_ed25519_git_signing` with no
  passphrase when it is absent. It asserts the key is 0600 with its `.pub`, and that it
  loads with an empty passphrase. It sets `gpg.format`, `user.signingkey`,
  `commit.gpgsign` and `tag.gpgsign` globally, and removes the XDG keys Plan 00137 wrote.
- CCY 3.66.0. `stage_git_signing_key` (in `lib/ssh-handling.bash` 1.5.0) copies the key
  into the gitconfig copy's directory. That directory is already mounted read-only and
  relabelled, and it is removed by the launcher's EXIT trap. The function repoints
  `user.signingkey`, and refuses a launch that has signing on but no usable key.
- A new gate, `ccy-git-signing`, passes 19 of 19. It fails against the old library.

Task 1.3 is decided as an owner step. The play does not register the key through `gh`,
for two reasons. Adding `admin:ssh_signing_key` to the shared required scopes would fail
every account's scope audit until each was refreshed. And the key belongs on one account
only, the one whose verified email is `user_email`. Acceptance reads the public
`users/<login>/ssh_signing_keys` endpoint, which needs no scope.

QA in the main checkout after the merge: `ccy-git-signing` passes 19. Three gates fail, all
because of this container's tools, not the code:
- ruff is 0.16.4 here, against the 0.16.8 pin in `.qa-versions` (another session raised

The Dockerfile already installs both, so a container rebuild clears all three.
