## 07:58 · decision · T1.3   — how git picks an account's key, and how ccy carries it

Measured with git 2.39 in a scratch HOME before building on it:

```
git@github.com-work:o/r.git      -> /work     (pattern git@github.com-work:*/**)
git@github.com-work:o/sub/r.git  -> /work
ssh://git@github.com-work/o/r    -> /work     (pattern ssh://git@github.com-work/**)
git@github.com:o/r.git           -> /machine
git@github.com-workx:o/r.git     -> /machine
```

`git@github.com-work:**` did NOT match an scp-style remote: a `**` not beside a slash is
a `*`, which stops at the `/` in `o/r.git`. So the play writes `:*/**`.

- The includeIf file is included from a managed block at the END of `~/.gitconfig`, after
  the machine key in `[user]`. `helpers/github_signing check-selection` then proves the
  pick in a scratch repository, so a later top-level `user.signingkey` fails the play.
- The machine key goes on the account holding `~/.ssh/id.pub` as an auth key, which is
  the identity plain `github.com` remotes push as. None or two such accounts is a refusal.
- ccy asks `git -C <project> config --get user.signingkey` on the host, stages that key,
  and APPENDS a `[user]` section to the gitconfig copy. The last value wins, so it
  overrides both the machine key and the includes. Rewriting the existing entry would
  not: `git config --file` edits `[user]` in place, before the include.

## 09:44 · finding · T1.3   — the owner's meta run hung in gh-account-setup's SSH test, and Ctrl-C could not stop it

The owner ran meta-deploy. Leg 0 went as designed for the first account: it lacked only
the signing-key scope, one device-code authorisation granted it, and its existing SSH key
was found registered. Then it stopped at `Testing SSH: github_<alias>...`, and repeated
Ctrl-C did nothing.

The cause is `verify_ssh`, which runs
`timeout 15 ssh ... -T git@github.com` with the terminal as stdin:

- Without `--foreground`, `timeout` puts itself and ssh in a new, background process
  group.
- ssh reads stdin, so at a terminal it is stopped by SIGTTIN.
- Ctrl-C goes only to the terminal's foreground group, so it never reaches them. The
  shells above wait on `timeout` before acting on the interrupt.

Reproduced under a pseudo-terminal with the committed function and a stub ssh that reads
stdin: a 15-second stall, the reply lost, and "inconclusive". That is also why the test
could never pass at a terminal. Why the owner's run went on past 15 seconds is not
established; the owner was asked for the `ps` line.

The owner was given the commands to end the stuck pair from a second terminal: a `ps`
line to capture its state, then `pkill -KILL`. The file was held at its committed bytes
until the running script had read it, because bash reads a script as it runs.
