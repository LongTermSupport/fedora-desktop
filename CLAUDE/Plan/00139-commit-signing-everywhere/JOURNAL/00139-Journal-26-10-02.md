## 10:28 · decision · T3.1   — the server trusts every signing key, not one

Task 3.1's owner step pointed at one key (`self_update_signing_public_key`), but this plan's D5
signs ccy commits with the session's account key and host commits with `~/.ssh/id`, so a server
needs both. Plan 00137 Task 4.8 makes the server trust a list, `self_update_signing_public_keys`.
The HOST sub-item now names the list, and `deploy.bash`'s closing note prints every `.pub` to put in
it: `~/.ssh/id.pub` and the key each `~/.config/git/github-signing-<alias>.gitconfig` names.

## 14:14 · correction · 26-09-25/15:27

T1.4 — the 26-09-25 15:27 entry said the `gh-<alias>` wrappers "already put the active
account back". They did not: `gh-<alias>` and `clone-<alias>` switched afterwards to the
saved default (`~/.config/gh/default-account`), and `gh-token-<alias>` and
`gh-<alias>-token-phpstorm` never switched back at all. That is what left run.bash on the
wrong account at the config step on 26-10-02, after `gh-lts` ran in between.

Fixed at both ends. run.bash 1.29.1 and 1.29.2 read the config repo with the primary's own
token (`gh_primary`), so they no longer depend on the active account. In
`play-github-cli-multi.yml`, every wrapper that switches now goes through
`_gh_as_account`, which puts back the account that was active, and `gh-token-<alias>` reads
the token by name without switching. Gates: `scripts/test-run-bash-config-repo.bash` and
`scripts/test-gh-alias-wrappers.bash`. The play waits in meta-deploy.
