## 15:14 · finding · — — where CCY state actually lives (corrects the framing)

The request assumed CCY "maps the Claude projects folder into the container".
It does not. `entrypoint.sh:195` does `ln -sf /workspace/.claude/ccy /root/.claude`,
so **all** container Claude Code state is written *inside the project working tree*
at `.claude/ccy/` (gitignored) — not into the host `~/.claude/`. The host
`~/.claude/projects/` is still used by **desktop** (non-container) Claude Code.

So there are two distinct plaintext stores, and any design that only covers one
leaves the other open.

Current footprint in this repo alone:

```
62M	.claude/ccy
68 	*.jsonl transcripts under .claude/ccy/projects/-workspace/
5.7M	largest single transcript
```

Implication: the blobs are per-project and inside a git working tree, which
changes the risk picture (accidental commit / sync exfiltration) as well as the
encryption options available.

## 15:41 · finding · P1 — research phase returned 5/5; premise is half-wrong

Headline results, several of which invert the design space. **Independently
re-verified by hand** (not taken on an agent's word) — the permission and
retention numbers below are from my own `stat`/`find` run in this container:

```
755 .              <- .claude/ccy itself
700 projects       <- the dir the user wants to encrypt is ALREADY protected
755 file-history   <- 251 files at 644 = verbatim pre-edit file bodies
755 shell-snapshots
600 history.jsonl
879 of 978 state files are other-readable
oldest transcript 2026-07-15 (29 days) -> cleanupPeriodDays=30 IS working
```

1. **Anthropic officially documents this exact gap.** `code.claude.com/docs/en/claude-directory`
   has a "Plaintext storage" section stating transcripts are not encrypted at rest
   and OS permissions are the only protection. Prescribed mitigations: lower
   `cleanupPeriodDays`, `CLAUDE_CODE_SKIP_PROMPT_HISTORY=1`, deny-rules on
   credential reads. The canonical feature request for keychain-backed
   encryption at rest (issue #50014) is closed **not planned** — no upstream path.
2. **The host is already LUKS-encrypted** (`/dev/mapper/luks-…`, btrfs). So
   at-rest encryption buys nothing against the stolen-powered-off-disk case;
   it only addresses a logged-in attacker, backup exfil, or another local user.
3. **FUSE in the CCY container is impossible as configured** — no `CAP_SYS_ADMIN`,
   no `/dev/fuse`, no `/dev/loop*`, no `fusermount`. Host-side gocryptfs inside
   `$PWD` also fails twice by default (podman `-v` is non-recursive `private`
   propagation, so the submount is dropped; FUSE denies other users without
   `-allow_other` + `user_allow_other`).
4. **btrfs has no merged fscrypt support**, so per-directory FS encryption is out
   on this machine specifically.
5. **The hooks daemon reads transcripts by byte offset** (`core/transcript_reader.py`,
   `load_tail`/`read_incremental`) — whole-file encryption breaks it.
6. **The genuinely open hole is not where the user pointed.** `projects/` is the one
   directory already at 700; the world-readable material is `file-history/` (verbatim
   pre-edit file bodies) and `shell-snapshots/`. Nothing sets a umask in
   `entrypoint.sh`.
7. **`history.jsonl` is never swept** — 2,177 prompts, retained indefinitely, outside
   `cleanupPeriodDays`.
8. **No prior art solves this**; the four published camps are encrypted *sync/archive*
   (local plaintext untouched), redaction hooks (all document bypasses, notably
   `@file` inlining), offensive tooling proving the loot is real
   (`xFreed0m/ghosttype`, TruffleHog-backed, targets `~/.claude/projects/**/*.jsonl`
   by name), and Anthropic's own config knobs.
9. **The threat is not hypothetical**: the TrapDoor supply-chain campaign (May 2026,
   34+ malicious npm/PyPI/crates packages) and an SEO-poisoning infostealer campaign
   both explicitly enumerate `~/.claude`.

## 15:43 · finding · P1 — methodological trap worth remembering

The recon agent's first secret-scan returned all zeros and was **wrong**: `grep` in
this container is a shell function wrapping `ugrep --ignore-files`, which honours
`.gitignore` — and `.claude/ccy/.gitignore` is `*`, so every recursive grep of the
transcript tree silently matches nothing. Re-run with `command grep`, the result is
0 live credential markers but **27 `$ANSIBLE_VAULT` ciphertext blobs across 7
transcripts** — proving the capture mechanism is real even though no live plaintext
key is presently sitting in the archive. Risk is prospective, not yet realised.

Also: `.claude/ccy/` is **not** wholly gitignored — `ccy.env`, `claude-supervise.py`,
`Dockerfile` and `.gitignore` are tracked, and `ccy.env` is read by the launcher on
the **host, before the container starts**. So the encryption boundary cannot be
`.claude/ccy/` itself without breaking bootstrap.

## 16:02 · decision · P1 — recommendation: hygiene first, encryption gated

Workflow finished 11/11, 0 errors, ~1.74M subagent tokens. Both judges converged
independently on the same answer, which is **not** the design the request asked for:

- **Security judge**: "Hygiene amended, plus tmpfs gated on triage, rejecting CryptView."
- **Operability judge**: scored C=8, A=6, B=4.

Decision: **ship blast-radius reduction (C) unconditionally; gate live-state
encryption behind a HOST triage run.** Reasons, in order of weight:

1. C fixes the only exposure that is *measured and open today* (879 other-readable
   files). Every encryption proposal leaves that hole — a FUSE mount with default
   permissions reproduces the same 755 dirs.
2. C cannot break `transcript_reader.py`'s byte-offset reads, which the Stop
   handlers this repo mandates depend on.
3. C's sealer is **asymmetric** — sealing needs only a public key, so the common
   launch path has no prompt, no secret in RAM, no argv exposure, and nothing that
   can fail on a human. Only *unsealing* prompts.
4. CryptView (host gocryptfs) dies on a structural objection: `user_allow_other` in
   `/etc/fuse.conf` is a permanent host-wide widening imposed to protect one
   directory. Not a reversible per-project trade.
5. SEALSTORE's *shape* (tmpfs plaintext) is adopted; its bespoke log-structured
   segment/manifest/compaction engine is rejected — it introduces a silent
   data-loss surface that append-only plaintext JSONL does not have today.

The deciding unknown for Phase 2 is **whether anything actually backs up or syncs
the project tree** (Task 0.3). Copy-exfiltration is the one scenario where
encryption genuinely beats the LUKS already present; if nothing syncs, most of the
Phase 2 value evaporates and Phase 1 alone is the honest answer.

## 16:28 · finding · T0.1 — triage.bash caught its own false-clean, twice

Wrote `triage.bash` and ran it immediately. Two defects surfaced on the first run,
one of them the exact failure class the script exists to prevent:

1. `bc: command not found` → the byte total printed empty. Switched to `awk`.
2. **`find … -exec command grep` reported `0 file(s)` for every secret pattern** —
   a clean bill of health that was entirely fictional. `command` is a shell
   builtin, so `find` cannot exec it. The self-test PASSED at the same time,
   because it used `command grep` directly in the shell — i.e. **the self-test
   exercised a different code path than the census it was vouching for**.

Fixed by making the self-test call the real census function `scan_count_files()`.
That immediately caught a *third* instance: `xargs -0 -r command grep` fails the
same way. Final fix is `GREP_BIN="$(type -P grep)"` — `type -P` searches `$PATH`
only, so an interactive shell's ugrep wrapper cannot win, and the result is a real
executable that `find`/`xargs` can actually exec.

Lesson worth keeping: **a self-test that does not run the production code path
proves nothing.** The canary design was right; the wiring was wrong, and only
running it exposed that.

## 16:35 · action · T1.1/T1.2 — repair proven on this repo, then baked into IaC

**Corrected the proposed shape before running it.** A blanket `chmod 600` would
have stripped the execute bit from **129 files** in this store (plugin and skill
scripts, plus backups of executable files). The safe form strips only group/other
and leaves owner bits untouched — and is idempotent, because a repaired entry no
longer matches:

```bash
find "$S" \( -type f -o -type d \) -perm /077 -print0 | xargs -0 -r chmod go=
```

`-type f -o -type d` deliberately excludes symlinks (there is 1 in the tree):
`chmod` on a symlink applies to its target, which may lie outside the store.

Measured before → after on `/workspace/.claude/ccy`:

```
files: 887 of 990 group/other-readable  ->  0 of 990
dirs:  331 of 348 group/other-readable  ->  0 of 348
owner-executable files: 129             ->  129   (preserved)
store root: 755 -> 700 ; file-history 755 -> 700 ; shell-snapshots 755 -> 700
```

Post-repair checks: second run is a no-op (idempotent), the live session transcript
kept growing (mode 600, still being appended), and the hooks daemon stayed RUNNING.

Baked in as three pieces:

- `umask 077` in `entrypoint.sh` (container) and `files/var/local/claude-code/cc`
  (desktop) — so new state is correct by construction. The desktop half matters
  most: that store has no container boundary at all.
- `playbooks/imports/play-claude-state-hygiene.yml`, imported from
  `playbook-main.yml` *after* both launchers. Uses `command:` + `argv:` rather than
  a shell pipeline, so Ansible 2.19's `split_args` never sees find's parentheses.
  Ends with an `assert` that zero entries remain — a repair that silently left
  files exposed would be worse than none, because the report would claim success.
- A launcher preflight in `claude-yolo` for the *current project's* store, because
  only the launcher knows the project directory. **Advisory by design**: it reports
  and repairs but never blocks, since this is the path every session traverses.

Rejected the declarative `file: recurse: yes, mode: "u=rwX,go="` alternative: it
chmods through symlinks and gives no count of what it changed.

Versions bumped per `CLAUDE/ContainerRules.md`: CCY 3.30.2 → **3.31.0**,
container/Dockerfile label 2.25 → **2.26**. QA green (431 files), zero shellcheck
findings in any changed file.

**Not yet done — HOST work.** The repair above only touched this project's store,
which is what the container can see. The desktop `~/.claude` store is untouched
until the playbook is run on the host, and the container rebuild (2.26) is what
