# Plan 00071 — Journal 2026-08-14

## 06:50 — Second upstream daemon defect found while chasing a stray file mode

Session resumed with an unexplained dirty file: `scripts/git-hooks/README.md`
showing `mode change 100644 => 100755`. Not mine — no edit in this plan touches
`scripts/`, and the state-repair sweep only *clears* group/other bits, it never
adds owner-execute.

**Cause**: the daemon's `git_hooks_executable_fixer` handler. This repo sets
`core.hooksPath = scripts/git-hooks` (a *tracked* directory), and the handler
chmods **every** non-`.sample` file it finds there — including documentation
git will never execute. The two real hooks were already `100755` and needed
nothing; the only file it changed was the one that should not have been touched.

**Second defect, found by accident while confirming the first**: the handler's
`matches()` is a bare substring test (`"not set as executable"`) against *any*
Bash command's combined output. Grepping the handler's own source printed its
`get_claude_md()` text, which contains that phrase — so the handler fired and
undid the `chmod 644` I had issued seconds earlier in the same turn. No git
command was involved and no hook had been skipped. A **read** caused a **write**.

That second one is the more interesting bug: for an advisory handler a loose
match is harmless, but this handler mutates the filesystem, which raises the
bar on a false positive.

**Evidence captured** (all reproducible):

- `git config --get core.hooksPath` → `scripts/git-hooks`
- `git ls-files -s scripts/git-hooks/` → README tracked `100644`, hooks `100755`
- `git diff --summary` → `mode change 100644 => 100755 scripts/git-hooks/README.md`
- `core.fileMode` → `true` (so the drift is visible, not masked)
- handler source v3.51.0: `_make_hooks_executable` lines 155-177 (`.sample` is
  the only exclusion), `matches` lines 73-77 (bare substring)

**Written up**: `untracked/hooks-daemon-hooks-chmod.md` (242 lines). Proposes
matching against the githooks(5) name set — or better, parsing the hook name out
of git's hint and fixing only that file — plus tightening `matches()` to the
full `hint: The '<name>' hook was ignored…` shape, which fixes both defects at
once. Two regression-test cases suggested. Identifier scan clean (0 hits for
emails, home paths, private IPs, session UUIDs).

Nothing under `.claude/hooks-daemon/` was edited — vendored upstream, read-only.

**Repo state**: README restored to `644`; working tree clean. The restore is not
durable — any later Bash output containing the trigger phrase reverts it, and
that phrase now appears in the report itself. Not worth engineering around
downstream; it is upstream's to fix.

## 13:15 — Deploy landed; and the acceptance gate was measuring the wrong thing

The owner deployed and relaunched. Host run of `acceptance.bash` came back with
check 5 (desktop store) PASS and check 3 (archive dir 700) PASS, but check 2
FAIL: *23 entries under the project `.claude` are group/other-accessible*.

Measured from inside the container rather than reasoning about it:

- container `umask` is now **0077** (was 0022) ⇒ CCY 2.26 is live
- 23 open entries: 19 under `.claude/ccy`, 4 under `.claude/hooks-daemon`
- **every ancestor directory is 0700** — `.claude`, `ccy`, `file-history`,
  `hooks-daemon`, `untracked`

### F-1: the file modes are irrelevant; the directory chain is the control

Reaching a file needs search (`+x`) on every ancestor. With `.claude` at 0700
root:root, no other local user can traverse in, so a 0666 file beneath it is
**unreachable**. The 23 "open" files are contained, not exposed. The posture
the plan set out to achieve is already correct.

### F-2: `file-history/` preserves the SOURCE file's mode

The 19 ccy files are 0644 and 0755 — not 0600 — despite being created at 13:09,
*after* umask 077 was in force. So they are not umask-derived. Verified by
content-matching two of them back to their sources:

| snapshot            | mode | source                          | source mode |
| ------------------- | ---- | ------------------------------- | ----------- |
| `278a3a6cbb6b05d4@v4` | 755  | an `ansible-playbook` play      | 755         |
| `119e68fa203340df@v3` | 644  | `docs/ccy-changelog.md`         | 644         |

Claude Code copies the pre-edit body preserving the source mode. `umask` masks
*default* creation modes and cannot override an explicit one, so no umask we set
will ever change these. This is arguably the *right* behaviour: the snapshot
inherits exactly the sensitivity of its source (a 0600 secret snapshots 0600).

### Consequence: my acceptance gate was wrong, not the system

The gate failed on any group/other **file** bit. Two writers recreate such files
continuously and neither is umask-governed — `file-history/` (F-2) and the hooks
daemon (`os.umask(0)`). So check 2 could **never pass on a live session**, while
reporting exposure that does not exist. That is the same class of defect the
qa-reviewer exists to catch, authored by me: a check that does not measure the
thing it vouches for.

Rewritten to gate on **directories** (the real control) and report open files as
`[NOTE]`. Negative-tested rather than assumed: a single 0750 directory planted
under `.claude` ⇒ check 2 FAIL, exit 1; removed ⇒ PASS, exit 0. A gate that
cannot fail is worthless, so the fail path was exercised explicitly.

Gate now: **PASS — 6 checks, 0 failures**, with 23 contained files noted.

This does **not** weaken the upstream daemon report: its central evidence is a
**0777 directory**, and a world-writable directory contains nothing. Directory
containment being decisive is precisely why that bug matters.
