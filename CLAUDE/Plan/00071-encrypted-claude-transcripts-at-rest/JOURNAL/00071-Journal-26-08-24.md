# Plan 00071 — Journal 2026-08-24

## Upstream removed the third store's writer — daemon 3.51.0 → 3.54.0

Not plan work: a `/hooks-daemon upgrade` (3.51.0 → 3.54.0) whose truth-change
reconciliation step landed squarely on this plan's third in-scope store.

**What changed upstream, both in daemon 3.53.0:**

- The `transcript_archiver` handler is **removed**. Nothing writes to
  `.claude/hooks-daemon/untracked/transcripts/` any more. Upstream's argument for
  removing rather than fixing it: the archives never preserved anything that was
  not already preserved — compaction does not delete the original transcript, the
  original sits on the same storage, and nothing in the daemon ever read an
  archive.
- The daemon daemonizes under `umask 0o077` instead of `os.umask(0)`. The three
  known-sensitive artefacts additionally pass an explicit mode at their create
  site, so the guarantee survives a future regression of the umask line.

**What that does to this plan.** The third store stops being a *live writer* and
becomes a *migration*. A umask governs creates and retro-fixes nothing, so every
file the old daemon already wrote keeps its `0666` — which is exactly the state
this plan's repair pass was built for. So:

- The launch-time repair pass still earns its place, but the justification in the
  Overview ("a writer exists that re-creates world-writable files continuously")
  is no longer the reason. Corrected in `PLAN.md` today.
- `acceptance.bash` check 3 now measures leftovers rather than an active writer.
  Its **skip** branch was the part worth fixing: "no `$ARCHIVE` (nothing archived
  yet)" reads as *not yet* when the truth is *never again*, and an absence that
  reads as a pending state is the same silent-misreading class this repo keeps
  finding. Reworded; the mode assertions are unchanged and still correct.
- New tool available for the migration half: `hooks-daemon check-permissions`
  lists the leftovers and `--fix` tightens them, exiting 1 while findings remain.

**Not verified here.** This is the CCY container; nothing was run against the
host store. Whether any `0666` leftovers actually remain on the host is an open
question for the next `acceptance.bash` run there — the removal of the writer is
upstream fact, the state of the leftovers is not.

**Incidentally reproduced** while reading the 26-08-14 entry: `head`-ing that
day-file printed its quotation of the daemon's `"not set as executable"` string,
which the `git_hooks_executable_fixer` handler substring-matches against *any*
Bash output — so it chmod'ed `scripts/git-hooks/README.md` to 0755 again, from a
pure read. The defect recorded on 26-08-14 is still live in 3.54.0.
