## 12:34 · finding · T1.1 — logind handles the lid as an EVENT, not a state

`man logind.conf`: "Only input devices with the power-switch udev tag will be
watched for key/lid switch **events**". The lid had been closed since the
previous day, so the abort produced no new transition and `HandleLidSwitch`
never fired. This is the actual gap — the abort itself is unremarkable.

The same man page gives the precedence as docked → external-power → plain, with
`HandleLidSwitchDocked=` defaulting to `ignore` and **not** set by our playbook.
So the branch that applied on the earlier lid close was probably `Docked`, not
the `HandleLidSwitchExternalPower=ignore` line we deploy. Logged as premise P1 —
it changes which knob a fix should target, so Task 2.2 settles it on the host.

## 12:38 · finding · T1.1 — ruled out: GNOME is not overriding logind

The man page warns that desktop environments commonly take a `handle-lid-switch`
low-level inhibitor, which would make our `laptop-lid.conf` inert. Checked:

```
gsd-media-keys  handle-power-key:handle-suspend-key:handle-hibernate-key  block
```

`gsd-media-keys` blocks the power/suspend/hibernate **keys** only; nothing holds
`handle-lid-switch`. So logind does own the lid and the drop-in is live. Every
`sleep` inhibitor present was `delay`, not `block`, so none of them blocked the
11:40 suspend either.

## 12:41 · finding · T1.1 — the battery safety net is unmanaged drift

`sleep-inactive-battery-type` is `'nothing'`, and a repo-wide grep finds it in
**no** playbook, template or var file. GNOME's own default is `suspend`, so this
was set outside IaC and nothing here would ever restore it. Its AC sibling *is*
managed — deliberately, by `play-prevent-ssh-suspend.yml:51-67` — which is what
made the absence easy to miss.

## 12:46 · decision · — — primary fix is the setting, not a resume hook

First instinct in session was a `system-sleep` post-resume hook that re-suspends
when the lid is still closed. Rejected as the primary: it is more code than
restoring the GNOME default, and it covers strictly **less**, because it only
fires after a resume. If H1 holds (undock a lid-closed machine, never request
suspend at all) the hook never runs and the bag scenario returns unchanged.

Recorded as Decision 1 in `PLAN.md` with the option that was rejected, since it
is the tempting one. The AC→battery udev approach is parked behind a decision
gate in Phase 3 rather than built now — H1 is not yet demonstrated.

## 13:05 · finding · T2.2 — my own probe would have written a misleading empty section

Went to verify P1 rather than leave it as an inference. Two results.

The good one: logind exposes a readable `Docked` property, so the lid branch
does not have to be inferred at all. With the dock detached:

```
Docked: b false
connected output count: 1   (eDP-1 only)
```

The bad one: the probe I had written for this used

```
systemctl show systemd-logind --property=HandleLidSwitch ...
```

which returns **nothing** — logind does not publish the `Handle*` settings as
unit properties. That probe would have emitted a silently empty section, and an
empty section reads as evidence of absence. This is precisely the failure
`CLAUDE/PlanTriage.md` names ("never write a misleading empty result"), written
into the triage script by the same session that quoted the rule.

Fixed: `show_logind_config` now states the limitation in the report instead of
implying a reading, and a new `show_lid_branch_inputs` probe captures the two
values that actually answer the question. P1 drops from "needs investigation" to
"needs one observation with the dock plugged in".

Recorded as F14 in `TRIAGE-EVIDENCE.md`, including the negative result, since
"this command cannot answer it" is itself worth not rediscovering.

## 13:40 · finding · T2.1 — power is direct, so the two variables are separable

Operator reports mains power goes **direct** to the laptop in both home and
away setups, never through the dock, so the dock can be powered down
independently. Recorded as F15.

This reframes the incident: it was **two** disconnections, not one. Unplugging
the dock alone would not have changed AC state, yet the journal shows the USB
storm *and* an NVRM power-source event a second later — packing up, so dock out
then mains out.

Usefully, it also means the AC branch and the display-count branch can be tested
**separately by hand**, which is what makes a mains-only test legitimate rather
than partial. No dock is needed to settle the AC half.

Built `probe-power-transition.bash` + `triage.bash --watch-power` for it: polls
for a live AC transition, snapshots lid/dock/display/power state either side, and
captures the logind/upower/kernel journal delta across it. Polling rather than
prompting, so it can be run mid-work — unplug and replug whenever. Verified the
timeout path fails loudly and writes no section, rather than emitting an empty
one.
