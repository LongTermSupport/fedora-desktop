## Refuted or needing change (most consequential first)

**C2 (partly REFUTED): "a creation that times out leaves a half-made, locked worktree, and the agent is still sent to work in it."**
The installed handler does not hand a failed creation to the agent, and it does try to clean up.

- `worktree_create_handler.py:243-245`: on `returncode != 0` it calls `_undo_failed_add` and then raises `_WorktreeAddError`. The handler's own docstring says it "fails LOUDLY (raises)" so there is no path to return.
- `utils/git_repo.py:229-230`: `run_git` turns `subprocess.TimeoutExpired` into a `CompletedProcess` with `GIT_TIMED_OUT`, a non-zero code. So a timeout takes the same failure path.
- `_undo_failed_add` (lines 248-269) runs `git worktree remove --force <path>`, `git worktree prune`, and `git branch -D <branch>` (unless the branch pre-existed). Cleanup failures are only logged as warnings (lines 264-269).
- CHANGELOG.md:189 cites Plan 00512 for the worktree-event budget. The undo code is labelled Plan 00512 in the source.
- Consequence: Cause 1a's "agent is still sent to work in it" is unsupported for the installed daemon. Either the incident ran on an older daemon without this undo (UNVERIFIABLE-HERE: the daemon version at incident time is not recorded), or the failure mode is different. Candidates: git killed mid-checkout; the timeout kill left the `initializing` lock; or `worktree add` returned 0 on a partial checkout.
- Likely real gap, not proven here: `git worktree remove --force` given a single `--force` is documented to refuse a LOCKED worktree (a locked one needs `--force` twice). A killed `git worktree add` leaves the `initializing` lock. So the cleanup would probably fail, be logged only as a warning, and the following `branch -D` would fail because the branch is checked out. That would leave a locked leftover, but the caller gets an error, not the path. This git behaviour is from git's documentation as I know it. The man page is not on disk, so it is UNVERIFIABLE-HERE and should be tested in a scratch repo.
- Change to the plan: reword Cause 1a and Task 1.5. The claim should be "the cleanup may fail on a locked worktree, leaving a leftover", not "the agent is sent into it". Task 1.5 must first establish the daemon version at incident time and how the agent reached a partial worktree.
