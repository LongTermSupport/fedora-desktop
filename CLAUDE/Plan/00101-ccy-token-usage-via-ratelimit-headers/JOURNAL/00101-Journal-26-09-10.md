# Plan 00101 — Journal 2026-09-10

## Q3 raised: ccy shows no Fable allowance, and the header for it may already be arriving

Reported in use: *"ccy token usage doesnt current show fable limit usage — is
this possible?"*

The display has a 5-hour bar, a weekly bar, and a `binding limit:` line. There
is no Fable row, and until today nobody had checked whether that is because the
figure is unavailable or because ccy discards it.

### Read the client rather than guessing, and it cost nothing

No token is mounted in the CCY container, so a live probe was not available.
The installed bundle was, and it is the same code that renders `/usage` and the
status line. Byte-offset dumps rather than a wide regex: the file is 217 MB and
`grep -aoE '.{300}…'` over it does not terminate in useful time, while
`grep -abo <literal>` then `dd skip=<offset>` returns in milliseconds.

The decisive find is the bucket table:

```js
oL = [["five_hour","5h"], ["seven_day","7d"],
      ["seven_day_overage_included","7d_oi"], ["overage","overage"]]
```

paired with the label map, where `seven_day_overage_included` is spelled
**"Fable limit"** in as many words. So the Fable figure should arrive as
`anthropic-ratelimit-unified-7d_oi-utilization` on the very request
`_usage_fetch_one` already makes — and `_usage_extract` matches five exact
header names and lets everything else fall through its `case`.

Full excerpts in [RESEARCH-bucket-headers.md](../RESEARCH-bucket-headers.md);
F18–F22 in PLAN.md under Q3.

### Two side findings worth more than the main one in one respect

**Q2 is now proven, not inferred.** The bundle computes
`Math.floor(utilization * 100)`. Task 5.3 flipped the default to `fraction` on
eight samples and recorded, correctly, that eight samples all `<= 1` is not
proof. It is proof now. `_usage_scale_conflict` stays: it was built to catch a
wrong inference and it now guards a server-side contract change instead, which
is a better job for it than the one it was hired for.

**The buckets are not symmetric.** `seven_day_opus` and `seven_day_sonnet` are
in the label map and in the values `-representative-claim` can take, but they
are **not** in the bucket table, so they have no utilisation header at all.
Fable has one and Opus does not. Any task phrased "add the per-model buckets"
was never one piece of work. The Opus and Sonnet numbers live only in
`GET /api/oauth/usage`, which Plan 00100 closed as 403 on scope — and the
richer payload found today does not reopen it, because the payload was never
the problem.

### What is still unknown, and why it is worth one run to settle

Everything above is a reading of a minified bundle. It says what the client is
prepared to parse, which is not what the server sends. Two hypotheses, leading
to different work:

- **H3** — a Haiku probe carries the `7d_oi` pair. Parser change only; the bar
  costs nothing beyond the request ccy already makes.
- **H4** — only a Fable probe carries it. Then the bar costs a Fable request,
  which Decision 3 deliberately avoided, and that cost belongs in the menu text
  rather than in a default.

### Task 6.1 — the probe, and why it is a second triage script

`triage-buckets.bash` + `probe-bucket-headers.bash`, built on `_planlib.inc.bash`
per PlanScriptStandards. Deliberately **not** folded into the existing
`triage.bash`: that script answers the scale question out of the cache and
spends nothing by default, and bolting a quota-spending probe onto it would
blur a distinction this plan has been careful about since Decision 1.

Two lint findings shaped the code rather than being suppressed (R11):

- A `cleanup()` invoked only by `trap` reads as unreachable (SC2317). Fixed by
  creating one pair of temp files for the whole run and inlining the trap, so
  there is no indirectly-invoked function. The files are truncated per model
  instead, because curl may leave the output file untouched when a response has
  no body and a stale body would be read as the next model's.
- A comment beginning `# shellcheck -x reports…` parses as a directive
  (SC1073). Reworded.

Verified in-container as far as is honest: `bash -n` and `shellcheck -x` clean,
`--help` renders, `qa-all.bash` green, and `plan_require_host` refuses the run
here naming `/run/.containerenv` — which is the guard working, not a failure.
**No request has been made and no quota spent.**

Task 6.2 is the gate. It needs a host run against a Fable-entitled account, so
the plan is blocked on that and on nothing else.

### Noticed in passing, folded into Task 6.3

`triage.bash` does `IFS=$'\t' read -r u5 r5 u7 r7` against what became a
five-field record in lib 1.12.0. `read` puts the unconsumed remainder in the
last name, so `r7` currently holds `<epoch>\t<claim>` and the 7-day reset it
prints is wrong. Harmless where it lands today, and exactly the kind of thing
that becomes load-bearing later.

## Host run 1 — the Haiku arm answered, the Fable arm did not

Owner ran `triage-buckets.bash` against account-1 of 4. Two requests, both
recorded. Facts as F23/F24 in [FINDINGS.md](../FINDINGS.md).

The Haiku response is clean and complete, and `7d_oi` is **not** in it:

```
anthropic-ratelimit-unified-5h-utilization: 0.02
anthropic-ratelimit-unified-7d-utilization: 0.69
anthropic-ratelimit-unified-representative-claim: five_hour
anthropic-ratelimit-unified-overage-status: rejected
anthropic-ratelimit-unified-overage-disabled-reason: out_of_credits
```

A free corroboration of F20 fell out of it. `0.69` as a fraction is 69% of the
weekly allowance — a plausible mid-week figure on a machine running ccy all day.
As a percentage it would be 0.69%, which it plainly is not. Q2 now has an
argument from the client's arithmetic *and* a second independent sample.

The Fable arm returned **429 `rate_limit_error` with no `anthropic-ratelimit-*`
headers whatsoever**. Not a single one — so the rejection happens before the
unified header machinery attaches anything. The plan had assumed, in
`_usage_fetch_one`'s own comment, that "a 429 is precisely when the numbers
matter most, and it carries them too". On this path it does not.

### The probe could not answer the question it was built to answer

Two readings survive F24 and I cannot choose between them:

1. account-1 has **no Fable entitlement**, so the 429 is about access and says
   nothing about buckets;
2. account-1 **has exhausted** its Fable allowance, so `7d_oi` exists and simply
   was not reported to a *Haiku* request.

These lead to opposite conclusions about H3. The discriminator is the error
**message**, which the probe threw away — it recorded the type only, and
`rate_limit_error` is common to both. That was my error in the first draft: I
treated the type as sufficient without asking what would distinguish the cases
it covers.

Amended rather than worked around: the probe now records the message,
`retry-after`, `request-id` and `x-should-retry` on any non-200, and takes
`PROBE_ACCOUNT=all` so the pool can be swept without re-probing Haiku on every
account. The message is screened for credential-shaped strings before it is
written, same as the header dump.

Pairing is flattened to one `account|model` list rather than nested loops, which
kept the diff at one indent level. Verified by extracting the selection logic and
running it standalone: `1`, `3`, `all`, `bogus` and an out-of-range `9` all
behave (`all` on a four-account pool expands to eight probes; the last two are
rejected with exit 64). Message extraction tested against a realistic
`rate_limit_error` body carrying an apostrophe.

Task 6.2b is the new gate: `PROBE_ACCOUNT=all PROBE_MODELS=claude-fable-5-1`,
four requests, which finds the Fable-capable account and reads the refusal reason
on the ones that are not.

## F25 from the owner: account-1 IS Fable-entitled, which kills the easy reading

Owner: *"can confirm this account has fable entitlement"*.

That removes the innocent half of F24's ambiguity. The 429 is not the API
saying "you cannot use this model" — it is refusing a request the account is
permitted to make. So H3 weakens (the one Haiku response seen did not carry
`7d_oi`) and H4 is favoured.

More usefully, it promotes a mechanism I had recorded as a curiosity rather
than a hypothesis. The bucket is called `seven_day_overage_included`, and the
*same* Haiku response that omitted it carried:

```
anthropic-ratelimit-unified-overage-status: rejected
anthropic-ratelimit-unified-overage-disabled-reason: out_of_credits
```

Filed as **H5**: Fable is metered against the overage-included weekly bucket,
so an account out of credits is refused Fable *and* has no `7d_oi` bucket to
report. Both observations in hand are exactly what H5 predicts. I had these two
facts side by side in the first run and did not connect them, because I was
looking for a header and reading `overage-*` as noise.

**If H5 holds, the original framing of this work was wrong.** The task is not
"parse a header ccy discards". For an account in this state there is no figure
to display at all, and the honest row says why. Filed as Task 6.2c —
`overage-disabled-reason` is already in the response ccy fetches, and is
discarded by the same `case` statement that discards `7d_oi`, so the reason is
as available as the number would have been. A blank row is not honest here and a
0% bar would be an outright lie: it would read as "you have used none of your
Fable allowance" when the truth is "you cannot spend it".

Still a hypothesis. The discriminator is the 429's **message** — "out of
credits" versus a plain weekly Fable limit — which is precisely what the probe
was amended to capture an hour ago, for a different reason.

Task 6.2b now earns its four requests twice over: it finds any account that gets
a 200 from Fable, which is the only way a `7d_oi` header will ever be observed,
and it reads the refusal reason on the ones that do not.

## Sweep 2: H3 refuted, and the Fable arm was my own bug all along

Owner: *"your triage should enumerate all ccy tokens and test them all"* — right,
and the single-account default was a bad one that had already produced a
misleading answer. Changed to sweep the pool. Eight probes, four accounts, Haiku
and Fable. Facts F29–F33 in [FINDINGS.md](../FINDINGS.md).

**H3 is dead.** Three clean Haiku 200s across three different accounts, and
`7d_oi` absent on every one. A Haiku probe does not carry the Fable bucket, so
the cheap route to a Fable bar does not exist.

**The sweep also handed me a control I had not designed for.** account-2's
*Haiku* probe came back 429 — a genuine weekly limit, `7d-utilization 1.0`,
`7d-status rejected`, `surpassed-threshold 1.0`, `retry-after 121933`, and a real
message. So a true rate-limit rejection carries the full header set, exactly as
`_usage_fetch_one`'s comment claims.

Set that beside the four Fable rejections, which returned:

```
message: "Error"      (no error_code, no disabled_reason, no retry-after)
x-should-retry: true
(zero anthropic-ratelimit-* headers)
```

Two rejections in one run, one rich and one degenerate. That is not two flavours
of the same system. I had been reading the Fable 429 as a credits refusal for
two commits.

### The actual cause, and it is mine

Fable 5.1 carries the capability `rejects_disabled_thinking`, and the bundle
pairs that capability with a **2048-token thinking budget**. `max_tokens` must
exceed a thinking budget.

My probe sent `max_tokens: 1` and no thinking block. **The Fable arm has never
made a valid request** — not in sweep 1, not in sweep 2. Every Fable "finding"
so far is an artefact of asking the question wrongly.

That retracts a chain I had built with some confidence: F24 read as a real
refusal, then H5 promoted to "the likeliest mechanism", then a whole Task 6.2c
designed around displaying "no usage credits". F26 and F27 are still true —
Fable *is* gated on credits and there *is* a `credits_required` error code — but
nothing observed here shows that is what happened. I connected a true mechanism
to an unrelated failure because both involved the word "Fable".

F32 was the evidence against me and I had it in hand: `overage-disabled-reason`
is `out_of_credits` on accounts 1–2 but `org_level_disabled` on 3–4. Four
accounts in two different overage states, all failing Fable **identically**.
A credits fault does not predict that. A malformed request does.

### Fixed

Fable and Mythos now get `max_tokens: 2100` with
`thinking: {type: enabled, budget_tokens: 2048}`. Haiku and friends keep the
1-token body. The report now records the **request body verbatim** — sweep 1 and
2 cannot be audited for this, because what they sent was only implied by the
script version at the time, and that is the whole reason this took two runs to
catch.

Cost goes up slightly and honestly: a Fable probe may now generate real thinking
tokens rather than being capped at one. Documented in both scripts.

Task 6.2e re-runs the Fable arm. It will be the first valid Fable request this
plan has made.

## H5 struck: I had been reading a different bucket entirely

Owner, on my write-up of the `overage-disabled-reason` values: *"ah ok you are
talking about API overage — this is not what we are talking about"*, and then
*"where claude can switch to API billing when the account usage has run out — it
is never used"*.

Correct, and it is a sharper correction than the one I made an hour earlier. I
had already retracted H5 as *unsupported by the evidence*. It is worse than
that: it was a **category error**. The bundle's own bucket table has these as
two separate rows —

```
seven_day_overage_included  ->  "Fable limit"
overage                     ->  "usage credit limit"
```

— and I let the shared substring "overage" carry an argument between them. The
`overage-*` headers describe the API-billing fallback for when subscription
usage runs out. The Fable window is a subscription window. Different subject.

The statusline contract settles it in the bundle's own words (F35):

> Per-window usage for the session (5-hour), weekly (7-day), and
> overage-included weekly (per-model bucket; present only for accounts whose
> responses carry that window) **subscription** rate-limit windows

Three things fall out, and the third changes the design:

1. It is a subscription window. "overage-included" names *which* weekly
   allowance, not a credits balance.
2. It is **per-model** — stated outright — so F29's Haiku-carries-nothing does
   not prove these accounts have no Fable window. H4 survives; H3 does not.
3. **"Present only for accounts whose responses carry that window."** An absent
   window is a NORMAL state, declared as such by the contract.

Point 3 kills Task 6.2c, which I had designed to show `overage-disabled-reason`
on a row labelled "Fable limit". That would have printed API-billing state under
a subscription heading — actively misleading, and built on the same conflation.
The correct handling is the plain one: when the window is not reported, say the
window was not reported. Do not invent a reason for it.

F34 is kept but explicitly fenced as out of scope, because a future reader will
otherwise re-derive it and may repeat my mistake.

Two corrections to the same hypothesis in one afternoon, the second finding a
flaw the first had missed. The first retraction was driven by evidence not
fitting; this one by the owner noticing I had been arguing about the wrong
noun. Worth recording that the evidence-driven retraction did not surface the
category error — I fixed the conclusion and kept the confusion.

Also dispatched: web research on the documented ways to check a Fable limit,
since everything this plan knows comes from reading a minified bundle, and an
official answer may make most of it unnecessary.

## The documentation reframes the whole plan: there is no separate Fable limit

Research filed at
[subagent-reports/260910-fable-limit-research-opus-5.md](../subagent-reports/260910-fable-limit-research-opus-5.md).
Facts F36–F39.

**F36 is the one that matters.** Anthropic documents that on Max, Fable is
included **up to 50% of the weekly usage limit** — and the help article is
explicit that this is a **ceiling inside the one weekly allowance, not a second
allowance**. Other models draw from the same pool; you can never exceed the
weekly limit in total.

So the question that started this plan — "ccy token usage doesn't show Fable
limit usage" — has a blunter answer than any hypothesis I had entertained.
**There is no separate Fable limit to show.** Fable spends the same weekly pool
that ccy has been displaying all along. The bar was never missing a limit; it
was missing a *breakdown*.

What is genuinely absent is how much of that pool went to Fable, which is a
sub-cap gauge rather than a second window. That now looks like what `7d_oi` is
for, and it fits on three independent counts: F35 calls it a per-model bucket,
the name says "overage-included" (the part included before overage), and F36
supplies a ceiling for it to gauge. Still unobserved, so still H4.

### Two corrections to the research, and one to my own record

The report states that `seven_day_overage_included` "does not appear in any
source, official or community" and should be "treated as unverified". Half
right, and the half it gets wrong matters: it is **undocumented**, not
**unattested**. I read it first-hand out of the shipped bundle — the suffix
table that builds the header name, and the statusline contract that describes
the window. Filed an editor's note on the report saying so, rather than editing
its body, so the research stands as what the research found.

The distinction it was reaching for is real and I have kept it: **no response
has yet carried that header**, and an undocumented internal surface can change
without notice. Promoted to Decision 5 — absence is a normal state, and no row
is ever synthesised from a neighbouring header, which is precisely the mistake
H5 would have shipped.

Second correction, to F39: there are **open Claude Code bugs** where Fable is
refused with "requires usage credits" on Max despite remaining Fable quota. So
even the corrected Fable probe may hit a known defect rather than a real limit.
Worth knowing before reading its result as gospel.
