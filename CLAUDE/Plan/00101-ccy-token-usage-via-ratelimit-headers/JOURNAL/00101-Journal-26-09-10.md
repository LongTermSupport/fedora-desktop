# Plan 00101 — Journal 2026-09-10

## Q3 raised: ccy shows no Fable allowance, and the header for it may already be arriving

Reported in use: *"ccy token usage doesnt current show fable limit usage — is
this possible?"*

The display has a 5-hour bar, a weekly bar, and a `binding limit:` line. There
is no Fable row, and until today nobody had checked whether that is because the
figure is unavailable or because ccy discards it.

### Read the client rather than guessing, and it cost nothing

No token is mounted in the CCY container, so a live probe was not available.
The installed bundle was, and it is the same code that renders `/usage` and the
status line. Byte-offset dumps rather than a wide regex: the file is 217 MB and
`grep -aoE '.{300}…'` over it does not terminate in useful time, while
`grep -abo <literal>` then `dd skip=<offset>` returns in milliseconds.

The decisive find is the bucket table:

```js
oL = [["five_hour","5h"], ["seven_day","7d"],
      ["seven_day_overage_included","7d_oi"], ["overage","overage"]]
```

paired with the label map, where `seven_day_overage_included` is spelled
**"Fable limit"** in as many words. So the Fable figure should arrive as
`anthropic-ratelimit-unified-7d_oi-utilization` on the very request
`_usage_fetch_one` already makes — and `_usage_extract` matches five exact
header names and lets everything else fall through its `case`.

Full excerpts in [RESEARCH-bucket-headers.md](../RESEARCH-bucket-headers.md);
F18–F22 in PLAN.md under Q3.

### Two side findings worth more than the main one in one respect

**Q2 is now proven, not inferred.** The bundle computes
`Math.floor(utilization * 100)`. Task 5.3 flipped the default to `fraction` on
eight samples and recorded, correctly, that eight samples all `<= 1` is not
proof. It is proof now. `_usage_scale_conflict` stays: it was built to catch a
wrong inference and it now guards a server-side contract change instead, which
is a better job for it than the one it was hired for.

**The buckets are not symmetric.** `seven_day_opus` and `seven_day_sonnet` are
in the label map and in the values `-representative-claim` can take, but they
are **not** in the bucket table, so they have no utilisation header at all.
Fable has one and Opus does not. Any task phrased "add the per-model buckets"
was never one piece of work. The Opus and Sonnet numbers live only in
`GET /api/oauth/usage`, which Plan 00100 closed as 403 on scope — and the
richer payload found today does not reopen it, because the payload was never
the problem.

### What is still unknown, and why it is worth one run to settle

Everything above is a reading of a minified bundle. It says what the client is
prepared to parse, which is not what the server sends. Two hypotheses, leading
to different work:

- **H3** — a Haiku probe carries the `7d_oi` pair. Parser change only; the bar
  costs nothing beyond the request ccy already makes.
- **H4** — only a Fable probe carries it. Then the bar costs a Fable request,
  which Decision 3 deliberately avoided, and that cost belongs in the menu text
  rather than in a default.

### Task 6.1 — the probe, and why it is a second triage script

`triage-buckets.bash` + `probe-bucket-headers.bash`, built on `_planlib.inc.bash`
per PlanScriptStandards. Deliberately **not** folded into the existing
`triage.bash`: that script answers the scale question out of the cache and
spends nothing by default, and bolting a quota-spending probe onto it would
blur a distinction this plan has been careful about since Decision 1.

Two lint findings shaped the code rather than being suppressed (R11):

- A `cleanup()` invoked only by `trap` reads as unreachable (SC2317). Fixed by
  creating one pair of temp files for the whole run and inlining the trap, so
  there is no indirectly-invoked function. The files are truncated per model
  instead, because curl may leave the output file untouched when a response has
  no body and a stale body would be read as the next model's.
- A comment beginning `# shellcheck -x reports…` parses as a directive
  (SC1073). Reworded.

Verified in-container as far as is honest: `bash -n` and `shellcheck -x` clean,
`--help` renders, `qa-all.bash` green, and `plan_require_host` refuses the run
here naming `/run/.containerenv` — which is the guard working, not a failure.
**No request has been made and no quota spent.**

Task 6.2 is the gate. It needs a host run against a Fable-entitled account, so
the plan is blocked on that and on nothing else.

### Noticed in passing, folded into Task 6.3

`triage.bash` does `IFS=$'\t' read -r u5 r5 u7 r7` against what became a
five-field record in lib 1.12.0. `read` puts the unconsumed remainder in the
last name, so `r7` currently holds `<epoch>\t<claim>` and the 7-day reset it
prints is wrong. Harmless where it lands today, and exactly the kind of thing
that becomes load-bearing later.

## Host run 1 — the Haiku arm answered, the Fable arm did not

Owner ran `triage-buckets.bash` against account-1 of 4. Two requests, both
recorded. Facts as F23/F24 in [FINDINGS.md](../FINDINGS.md).

The Haiku response is clean and complete, and `7d_oi` is **not** in it:

```
anthropic-ratelimit-unified-5h-utilization: 0.02
anthropic-ratelimit-unified-7d-utilization: 0.69
anthropic-ratelimit-unified-representative-claim: five_hour
anthropic-ratelimit-unified-overage-status: rejected
anthropic-ratelimit-unified-overage-disabled-reason: out_of_credits
```

A free corroboration of F20 fell out of it. `0.69` as a fraction is 69% of the
weekly allowance — a plausible mid-week figure on a machine running ccy all day.
As a percentage it would be 0.69%, which it plainly is not. Q2 now has an
argument from the client's arithmetic *and* a second independent sample.

The Fable arm returned **429 `rate_limit_error` with no `anthropic-ratelimit-*`
headers whatsoever**. Not a single one — so the rejection happens before the
unified header machinery attaches anything. The plan had assumed, in
`_usage_fetch_one`'s own comment, that "a 429 is precisely when the numbers
matter most, and it carries them too". On this path it does not.

### The probe could not answer the question it was built to answer

Two readings survive F24 and I cannot choose between them:

1. account-1 has **no Fable entitlement**, so the 429 is about access and says
   nothing about buckets;
2. account-1 **has exhausted** its Fable allowance, so `7d_oi` exists and simply
   was not reported to a *Haiku* request.

These lead to opposite conclusions about H3. The discriminator is the error
**message**, which the probe threw away — it recorded the type only, and
`rate_limit_error` is common to both. That was my error in the first draft: I
treated the type as sufficient without asking what would distinguish the cases
it covers.

Amended rather than worked around: the probe now records the message,
`retry-after`, `request-id` and `x-should-retry` on any non-200, and takes
`PROBE_ACCOUNT=all` so the pool can be swept without re-probing Haiku on every
account. The message is screened for credential-shaped strings before it is
written, same as the header dump.

Pairing is flattened to one `account|model` list rather than nested loops, which
kept the diff at one indent level. Verified by extracting the selection logic and
running it standalone: `1`, `3`, `all`, `bogus` and an out-of-range `9` all
behave (`all` on a four-account pool expands to eight probes; the last two are
rejected with exit 64). Message extraction tested against a realistic
`rate_limit_error` body carrying an apostrophe.

Task 6.2b is the new gate: `PROBE_ACCOUNT=all PROBE_MODELS=claude-fable-5-1`,
four requests, which finds the Fable-capable account and reads the refusal reason
on the ones that are not.
