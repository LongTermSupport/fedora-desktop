## What M6 builds

- **H31, the membership.** cc's `cc_teams_command` writes the desired membership first, with
  `ccy-teams internal membership-init --kind=cc <session> <checkout> <seats>`, into
  `$XDG_RUNTIME_DIR/pingbus/membership/<session>/` (`kind: cc`), and starts `pingbus seat exec`
  with `PINGBUS_MEMBERSHIP` pointing at it. `<session>` is the pane's
  own name on ccy's tmux server (`cc-<id>`, as its record is); a cc outside ccy's tmux gets
  `cc.<pid>`, which follows the file but which no host command finds.
- **H32.** The system prompt names no team (`CC_TEAMS_PROMPT`, the spec's sentence plus the
  pingbus pointer). `describe-seats --sentence` is removed. `cc --bus` starts a session on no
  team after the consent alone (`choose-teams --type=host --bus`); cc refuses `--bus` with
  `--teams` (64).
- **Inbound (Decision 7, the coordinator's safer default).** `cc --bus` adds
  `crossSessionInbound: refuse` to its settings; its keeper reports no inbound, as a ccy
  keeper on no team does (pingbus is unchanged: no new flag). cc has no supervisor to relaunch
  it, so its first `session add` keeps the seat, the desired file and the record and exits 1,
  saying plainly that cc must be ended and started again from `ccy-sessions`, which starts it
  in that seat, accepting. A re-run says the same. "Accept from launch" is the owner's
  alternative.
- **ccy-teams.** `hot` resolves a session as a container session, else as a cc session (its
  pane on ccy's tmux server). The keeper is found in the process tree under the pane; the
  route check runs on the host (`pingbus reach`). `add`, `remove`, `move`, `role` and `list`
  work on cc sessions. `repair` refuses (78): a cc keeper ends with its claude, and one started
  from the host would outlive the session. The list says `unguarded: end it and start it again from ccy-sessions` for a cc session with no keeper. The record follows each change:
  `registry.SetCCTeams` writes `--teams <seats>`, or `--bus` with no seats.
- **The picker (M5).** `hot.Sessions` adds the running cc sessions (`runningCC`, over
  `discover.RunningCC`). A cc row is controllable and never `Unguarded`, so the picker offers no
  Repair for it. No UI change.

## Fable's FIX-FIRST, and what was done

- **B1, a membership left under a reused tmux name.** Fixed in Go, not in cc's bash (`cc` and
  `cc-teams.bash` are at their allowlist records): each launch rewrites the record of its name,
  so `discover.Current` keeps a membership only while that record carries the bus (a cc
  record with `--teams` or `--bus`, a ccy record without `--no-bus`). `session list`, the
  picker, `SessionsIn`, the board, `claimsElsewhere` and every `session` command use it; a
  command on such a session exits 78. This covers what Fable's prescribed bash fix would
  (a plain cc under a reused name) and also a pane killed before any cleanup could run. There
  is no `test-cc-teams` case because cc's bash did not change for it; the Go tests (discover,
  hot, board) were seen red first, and acceptance M6 (d) proves it on the host.
- **The same class for `ccy --no-bus`**, in its own commit: the launcher removes its name's
  directory (`agent-bus-membership.bash`, within its limits; test-ccy-teams red then green),
  and the Go rule above ignores one meanwhile.
- **Minor.** The acceptance removes each driver's `cc-teams.XXXXXX` home; `PINGBUS_SEATS` is
  removed from pingbus (`seat exec` refuses a launch without `PINGBUS_MEMBERSHIP`); ACCEPTANCE
