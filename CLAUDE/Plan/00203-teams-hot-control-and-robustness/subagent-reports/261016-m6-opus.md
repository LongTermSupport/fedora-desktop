# Plan 00203 M6: cc sessions hot-controlled (Opus)

Branch `feat/hot-control-m6`, from F44 at 342fae6f. CCY 3.99.12, container 2.77.

## What M6 builds

- **H31, the membership.** cc's `cc_teams_command` writes the desired membership first, with
  `ccy-teams internal membership-init --kind=cc <session> <checkout> <seats>`, into
  `$XDG_RUNTIME_DIR/pingbus/membership/<session>/` (`kind: cc`), and starts `pingbus seat exec`
  with `PINGBUS_MEMBERSHIP` pointing at it and `PINGBUS_SEATS` unset. `<session>` is the pane's
  own name on ccy's tmux server (`cc-<id>`, as its record is); a cc outside ccy's tmux gets
  `cc.<pid>`, which follows the file but which no host command finds.
- **H32.** The system prompt names no team (`CC_TEAMS_PROMPT`, the spec's sentence plus the
  pingbus pointer). `describe-seats --sentence` is removed. `cc --bus` starts a session on no
  team after the consent alone (`choose-teams --type=host --bus`); cc refuses `--bus` with
  `--teams` (64).
- **Inbound.** cc's settings already accept cross-session inbound, so `seat exec --accepts-inbound` (and `seat keep --accepts-inbound`) makes the keeper report `inbound` with
  no team: `cc --bus`'s first join is hot. That is an owner call: PLAN.md Decision 7.
- **ccy-teams.** `hot` resolves a session as a container session, else as a cc session (its
  pane on ccy's tmux server). The keeper is found in the process tree under the pane; the
  route check runs on the host (`pingbus reach`). `add`, `remove`, `move`, `role` and `list`
  work on cc sessions. `repair` refuses (78): a cc keeper ends with its claude, and one started
  from the host would outlive the session. The list says `unguarded: end it and start it again from ccy-sessions` for a cc session with no keeper. The record follows each change:
  `registry.SetCCTeams` writes `--teams <seats>`, or `--bus` with no seats.
- `discover.ReadDesired` reads both kinds of directory and refuses a kind that does not match;
  `discover.RunningCC` lists cc sessions with a membership whose pane runs.
