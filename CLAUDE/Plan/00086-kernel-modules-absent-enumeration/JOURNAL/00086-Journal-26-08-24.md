## 16:04 · finding · T1.1 — confirmed via triage: kernel-modules is genuinely absent, not a half-install

Ran a read-only diagnostic play against a real Fedora guest (lts-infra Plan
00045's guest): `rpm -qa` for the full kernel-family package set returned only
`kernel-core` and `kernel-modules-core` (3 versions each, matched). No
`kernel-modules`, `kernel-modules-extra`, `kernel-devel`, `kernel-tools`, or
`python3-perf` present at all — confirmed with both a targeted list and a
`kernel*` wildcard. This is a minimal/cloud-style image, not a half-installed
kernel in the sense `play-AB-dnf-upgrade.yml`'s comment describes.

Then probed `rpm -q kernel-modules --queryformat '%{VERSION}-%{RELEASE} '`
directly (the exact invocation used by the play) against the same guest:
rc=1, stdout=`package kernel-modules is not installed`, stderr=empty. Cross-
checked against a package name that cannot exist by any definition
(`this-package-name-does-not-exist-anywhere`) — identical shape. This
confirms rc=1 + that exact stdout substring is rpm's stable "not installed"
signal, safe to key a `failed_when` exemption on.

## 16:10 · decision · T1.1/T1.2 — probe-then-fail, not a blanket failed_when: false

Per this repo's fail-fast doctrine (`failed_when: false` prohibited without a
same-line `# FAIL-FAST-OK:` annotation, and the "probe-then-fail" pattern —
register + explicit check): added `failed_when: false` with an inline
FAIL-FAST-OK annotation to the kernel-modules enumeration task, followed by a
new `ansible.builtin.assert` task that only tolerates rc=0 or
(rc=1 AND stdout contains "is not installed") — any other failure shape
(permissions, rpm db corruption, etc.) still hard-fails the play.

Also fixed the difference computation two tasks later: it was doing
`kc_versions.stdout.split() | difference(km_versions.stdout.split())`, which
on the not-installed path would have split the literal string
"package kernel-modules is not installed" into words and fed them into the
difference as if they were installed versions — silently corrupting the
half-installed-kernel list rather than just leaving it empty. Fixed to
substitute an empty string for `km_versions.stdout` whenever
`km_versions.rc != 0`.

## 16:40 · finding · T1.5 — independent review returned BLOCK on two findings

Dispatched a peer review agent against this PR. Verdict: **BLOCK**, two
independent findings, both real:

1. **Destructive regression.** The difference computation
   (`kc_versions.stdout.split() | difference(km_versions...)`) was unchanged
   from before this plan — still diffing only against `kernel-modules`, never
   `kernel-modules-core`. On the exact host class this plan targets
   (`kernel-modules` genuinely absent, only `kernel-core` +
   `kernel-modules-core` installed), `km_versions` contributes `[]`, so the
   difference is *every installed `kernel-core` version* — all now classified
   half-installed, feeding the unconditional `dnf state: absent` removal task
   two steps later. Nothing excluded the running kernel or guaranteed at
   least one bootable kernel survives. The original bug (hard-fail, zero
   changes made) was safe-but-broken; this fix as first written was
   broken-but-unsafe — it would have run to completion and destructively
   removed kernel packages, plausibly including the booted one, on precisely
   the minimal/cloud-image population the plan exists to fix. Caught before
   any live run exercised it (Plan 00045's harness never got this far due to
   the unrelated self-clone-pin limitation it hit first — see that plan's
   journal).
2. **Private hostname leak.** The JOURNAL entry above named the real VM
   hostname of the downstream consumer estate's dev guest. Confirmed via
   `git log --all -S` that this exact leak class (a real infra hostname
   committed to this public repo) had already happened twice before
   (`676a7d74`/`cae9a0ca`, "Redact internal infra hostnames from this public
   repo") — both times fixed with a content-only forward redaction commit,
   explicitly NOT a history rewrite (per that commit's own message: "the same
   strings remain in older commit messages in this repo's history"). Followed
   the same established precedent here rather than treating it as a novel
   incident requiring GitHub-support-level history purging.

## 16:55 · action · T1.7 — fixed both findings

Finding 1: replaced the always-diff-against-kernel-modules logic with a
host-type-aware check — the half-install heuristic (and therefore the
removal path) only runs when `kernel-modules` exists on the host at all
(`km_versions.rc == 0`); when it is genuinely absent, `half_installed_kernels`
is unconditionally `[]`. This is the correct semantic fix, not just a
safety guard: a host that never carries `kernel-modules` by design (a
minimal/cloud image) is complete for its own package set — nothing is
"half" about it. Considered diffing against the union of `kernel-modules` +
`kernel-modules-core` instead, but rejected it: the ORIGINAL bug this play
was written for (2026-05-21, header comment) is exactly a host where
`kernel-modules-core` IS present alongside `kernel-core` but `kernel-modules`
is missing — a union-based diff would silently stop detecting that pattern,
which is a regression against the play's own documented purpose. Also added
an unconditional exclusion of the running kernel's version
(`running_kernel.stdout.rsplit('.', 1)[0]`, matching kc_versions' `%{VERSION}-%{RELEASE}` format) from the removal candidates, as
defense-in-depth against ever targeting the booted kernel regardless of what
the detection computes — this is a pre-existing hazard in the play, not
introduced by this plan, but cheap to close while already in this code.

Finding 2: redacted the private hostname in place in the 16:04 entry above,
replacing it with a generic description ("a real Fedora guest"), matching
the exact wording style already used in this repo's two prior redactions of
the same leak class.

`ansible-playbook playbooks/imports/play-AB-dnf-upgrade.yml --syntax-check`
clean after the fix. `./scripts/qa-all.bash` next, then re-review before
merge.
