## 13:04 · finding · —   — DSCP queue faults, controller ownership and on-demand timings

Why this tooling exists: OpenSSH marks its packets DSCP EF by default (IPQoS ef cs0), and a Wi-Fi radio that has stopped serving one WMM queue drops every packet marked for it while unmarked traffic to the same host passes. ssh then times out at the TCP connect on any port while curl, bash /dev/tcp and rootless-container traffic (re-originated unmarked by pasta) connect. wifi-dscp-probe.bash shows such a queue as one column of 100% loss. The host-side defence is IPQoS none (play-basic-configs.yml, and ccy's GitHub probe, which runs ssh with -F /dev/null).

Controller findings that shaped the play: data written under a /etc/subuid range the account no longer has is unreachable to rootless podman (the play now reclaims it, only with MongoDB stopped); resetting the owner of mongodb/data under a running stack aborts MongoDB with WiredTiger EACCES (the play now creates the container-owned directories only when missing); a new install has no admin until the setup wizard runs (the admin login is the play's last step).

Measured: a cold controller start answers an API login after about 15 s and a stop takes about 5 s, so tooling can start it on demand and stop it afterwards. Install-specific findings are kept in the private config repo, not here.
