## 09:05 · action · —   — Play ledger skips a play outside the repo root

The play ledger no longer marks itself BROKEN over a private play outside the repo root
(the 10-12 entry's "not fixed here"). On 10-12 the private play was run from a linked
worktree, so its path, in the main checkout's untracked/, was outside that worktree's root,
and `RunCollector._resolve` raised.

- **Fix.** `_resolve` returns the bare path for a play outside the root, and `on_play_start`
  opens no record for it and returns one `LEDGER-PLAY-NOT-TRACKED` line naming the play,
  which the callback prints to stderr. Nothing was widened: no exception is caught, so a
  symlink loop, an unreadable play or anything unexpected still raises and the callback
  still marks BROKEN. Tests: the old "refused" case is now "skipped", plus a sibling path
  sharing the root's prefix, results after a skipped play folding into nothing, and an
  OSError and a ValueError from path resolution still raising. A real `ansible-playbook`
  run of a play in a temp dir, from the repo, prints the line once and writes no sentinel.
- **Decision: a private play under the main checkout's untracked/ stays in scope.** It is
  inside the root, so its row is answerable against that checkout (commit, dirty,
  play_sha256), and `check_freshness._drop_never_tracked` drops it later as never tracked,
  as `changed_plays` ignores it. The boundary is the root, not git tracking: asking git per
  play would add a failure mode, and would also skip a new, not yet committed play, which
  is what `dirty` and `play_sha256` exist to catch. So the two cases differ in the ledger
  (a row in the main checkout, none from a worktree) but agree in every report: neither is
  ever reported.
- **Clearing the 10-12 marker.** meta-deploy takes no bare command, so
  `clear-ledger-broken.bash` in this plan runs `check_freshness --clear-broken`, queued in
  meta-deploy.list. Safe: that worktree is gone and the cause is fixed.
