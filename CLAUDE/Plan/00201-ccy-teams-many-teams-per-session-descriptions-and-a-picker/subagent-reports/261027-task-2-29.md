## (a) and (b): one cause

The board (`board.Collector`) knows a checkout only while a session record, a live ccy or cc
tmux session or the working directory names it. When a session ends, its trampoline removes the
record, so the checkout drops out of the board:

- its seats stop being seat rows and show as the team's roster rows (KIND `ccy` or `host`,
  STATE `active`, SESSION `-`, WHERE the role): (b);
- shutdown's plan then sees a roster member of kind `host` with no checkout and lists it as
  "not a session on this host's ccy tmux ...; end it where it runs", which fails the run: (a).
  That was the cc host seat of step 09, whose session had ended before step 12.

STATE `active` means the member is on the team's roster and not parked; it says nothing of a
session. SESSION `free` is a seat row of a known checkout with no session and no lock. So a
released seat is `free` on the board only if its checkout is still known.

Fix: `src-go/internal/teams/seatcheckouts`, a list of the host checkouts that hold seats, at
`seat-checkouts` beside the session registry (`~/.local/state/ccy/seat-checkouts`), one absolute
path a line, mode 0600, append only (two writers adding the same line read as one; a bad line is
an error naming the file and line). Writers:

- the launch block, `ccy-teams describe-seats --block` (and `choose.Block` for `session add` and
  `move`), which both launchers run right after `agent-bus seat take`, so every launch with
  seats adds its checkout. A write that fails ends the block, and the launch with it.
- every board pass, for each checkout it sees with a seat directory, so the seats of sessions
  running at deploy time are listed before they end.

Readers: the board's `collectSessions` notes every listed checkout. `readSeats` already skips a
checkout with no seat directory, so a checkout that has gone costs nothing and is no failure. A
list that cannot be read is said on stderr and marks the board incomplete.

Shutdown: a seat row of a known checkout that is free and that no live session names is now SD5a,
"No session running, nothing to shut down": in the preview, and in the result as
"`<seat>@<team> (<handle>)`: no session running, nothing to shut down". It is not in the count
line and does not fail the run. A member whose checkout is still unknown (seats taken before the
deploy and never relaunched, or a deleted checkout) stays "not reachable", which is honest:
without its checkout its lock cannot be read, and a session outside ccy's tmux (headless, a
non-terminal launch) might hold it.

SPEC-shutdown.md: a new fact (where a seat is once its session has ended), SD5's known
checkout, SD5a, SD15 and SD16 amended.

## (c): a decline exits 0

The convention, found in the code: a No at a confirmation exits 0 in shutdown (SD8), restart,
wind-down, `session` add/remove and the picker's offers. Esc and Ctrl-C are the cancel, 130, and
from the picker 130 ends the picker while 0 goes back to the list. So a deliberate Stop is a
decline: exit 0, not 130.

The sweep of every `Confirm`, `AskYes` and `Choose` in `internal/teams` found the class "a
person's decline reported as failure" in six places, all fixed:

- `lxcadd`: the Stop at "Update entry / Stop", the No at the review ("Nothing was added."), and
  the No to the apply of a member declared as answered.
- `create`: the No at the review. From `ccy --teams` (`RunForChooser`) that exit 1 ended the
  launch; a decline now goes back to the chooser's list, as Esc does.
- `ops` remove: "Leave it running", and the No to taking the team's sessions off it first.

Left at 1, with reasons: remove's typed name that is not the team's (a refused answer), and the
`cc --teams` consent decline (documented exit 1: the launcher must not start). `ccy-teams --help`
now says a No or Stop exits 0. DBF judgement: the class is not a syntax shape (which No is a
refusal the caller must stop on is meaning), so it is recorded in GoProjectRules.md "Defect
classes that cannot be a rule", held by each flow's decline tests.
