# Review: Plan 00211 (agent bus reports and questions rooms), design only

Reviewed: `CLAUDE/Plan/00211-agent-bus-reports-and-questions-rooms/{PLAN,SPEC}.md` at commit
c9f11737 (branch base dead9482; F44 differs only in `play-basic-configs.yml`, so every code
citation was checked against the current tree).

**VERDICT: FIX-FIRST.** The design is close to what the owner asked for, and most of its research
holds up. But some code paths it would break or route around are missing from the spec, and the

## A. Blocking findings

### A1. Inbox revalidation would silently drop every unaddressed questions-room HUMAN item

`helpers/pingbus/inbox.py:380-421`: `pending()` runs every stored inbox file through
`protocol.validate_event(event, ctx, self_user_id, human_text=...)` again. That function knows
nothing about rooms, and a stored sync event has no `room_id`. A questions-room human message
does not mention the coordinator, and nothing in it marks it as coming from that room. So on
revalidation `_human_outcome` (protocol.py:798) returns `IGNORE not-addressed`, and `pending()`
counts it as `rejected`. `recv`, `wait`, the hook path (`hooks.py:563`) and `cli.py:1169`,
`:1686`, `:2269` all read `pending()`, so the coordinator would never see the owner's answer,
although the syncer accepted it.
SPEC §6/§8.3/§11.1 never mention `inbox.py`. **Fix:** the inbox item must record its room or
purpose (part of the file name or a wrapper key), revalidation must take it into account, and
§11.1 needs an `inbox` test for a stored unaddressed questions-room item.
`syncer._history_item` (syncer.py:555-575) has the same blind spot for `history --room questions`.

### A2. Task 2.4 would break every ccy-teams consumer at deploy 2

`src-go/internal/agentbus/parse.go:167-180` reads `agent-bus list` with
`marker.Fields(out, "HUMAN", 3)` and `("MEMBER", 5)`. `src-go/internal/marker/marker.go:22`
treats any other field count as an error. Its callers are the board, choose, seats, picker,
winddown and hot, all through the roster parse. Task 2.4 ("`agent-bus list` reports each human's and the
coordinator's membership of each room") ships in deploy 2, and the Go change is Phase 3, *after*
it. If 2.4 appends fields to HUMAN or MEMBER lines, every ccy-teams view fails on
"HUMAN line has 4 fields, want 3". Protocol §15's "fields only appended" promise is not what
this consumer implements. **Fix:** the spec should say 2.4 adds a *new* marker kind (for example
`ROOM\t<user>\t<purpose>\t<membership>`, which old parsers skip), or the Go parser change should land and deploy
first. The spec should name the format either way.

### A3. Deploy 1 as written may not reach LXC members (top priority)

Task 1.10 says deploy 1 "is the software play only". In `play-agent-bus.yml` every task is
tagged `agent-bus`, and the LXC kit copy (`members.py:1228-1231`, `_sync_kit`) runs only in the
"Join the LXC members declared present" task (`play-agent-bus.yml:373-381`), after the team
installs. If "software only" means the `software` step, no LXC container gets the new pingbus.
SPEC §5.4 assumes the opposite ("deploy 1 reaches every running container"). **Fix:** say that
deploy 1 runs the whole `play-agent-bus.yml`, with old admin code still on F44. This means
**Phase 1 must merge to F44 before any Phase 2 code**, and the plan should say so in those
words.

### A4. "Deploy 2 waits for LXC/coordinator upgrade" is not true as designed

§5.4 says "deploy 2 waits for that (the acceptance checks it)", but A4 runs *after* deploy 2.
Also, A4 checks the in-container `pingbus version`, which is the file on disk. The coordinator's
long-running watcher (`cmd_watch` with `--supervise`, cli.py:1926) keeps the old code loaded
until its session restarts, and it is that old process that rejects the questions invite with
`POST /leave` (syncer.py:367-379). **Fix (fail fast):** deploy 2's first `plan_deploy_leg` is a
pre-flight check that refuses to proceed while any declared coordinator, LXC included, runs an
old pingbus. The check should use the version the running watcher reports (status/room view), not the file.
A down LXC container should be refused loudly there, not discovered by A4 afterwards.

### A5. A coordinator whose bundle has `human_text: false` drops every questions-room message

`_human_outcome` (protocol.py:784-785) drops all human text as `sender` when the bundle has
`"human_text": false`. That flag is a supported LXC member option (`members.py:456`,
`--no-human-text`). The spec gives this no rule. Such a coordinator would be invited, and would
silently drop all of the owner's answers. **Fix:** `_sync_questions_members` must refuse to
invite such a coordinator, or `set_role` must refuse to make one coordinator. Either way the
refusal is an `AdminError` that names the cause, with a test.

### A6. Plan scripts break PlanScriptStandards R7 and the task order

- Task 0.1 `triage.bash` is `plan_mode gather`, but it creates a throwaway team on the host's
  Tuwunel and posts to it. That changes state, so it must be `plan_mode deploy` with
  `plan_deploy_leg`. It also needs a stated cleanup and a statement of how the team is made
  (through the admin tool or play, not by hand, per the IaC rule).
- `acceptance.bash` is `plan_mode gather`, but A3 takes and releases a seat and posts a
  report, and A4 posts a report. Those are mutations: the script needs `deploy` mode for those
  legs, or they move into `deploy.bash`. `--fake` "runs anywhere" contradicts an unconditional
  `plan_require_host`. Say that the host requirement is skipped under `--fake`.
- Task 2.5 has deploy 2 "end with `acceptance.bash`", but `acceptance.bash` is not written
  until Task 4.1. Move 4.1 before 2.5. R9 lets acceptance be separate when a human step comes
  between, so state that A5 is the `--after-owner` exception.

## B. Significant findings (fix in the spec)

### B1. D4 contradicts D2's own argument

D2 enforces read-only reports because "a human's post there would reach nobody, silently." D4
then creates a questions room for a team with no coordinator, where the humans hold power 50 and
nobody syncs. It is also outside the main room's "unheard" logging
(`protocol.reached_no_agent`, :889-903). That is exactly the silent failure D2 forbids. **Fix:**
either (a) do not create it without a coordinator, or (b) hold humans at 0 there until a
coordinator exists (the trust check already takes power levels per purpose). The board and
health should then show it as unread. A topic that says so is a convention, not enforcement.

### B2. Edits (D6) and reactions are lost in the one room where every message is a decision

- An edit in Element is the usual way to correct an answer ("not 5, 50"). D6 drops it as
  `edit`, and the skill's fix ("ask the human to resend if an edit shows in the drop counts")
  depends on a count that does not identify the message.
- The questions room uses `expected_power_levels`, so humans may send `m.reaction` (50,
  protocol.py:1029), and a thumbs-up on "Options: 1." is a natural answer. It is never delivered.
- **Fix:** in the questions room, deliver an edit as a new HUMAN item marked as an edit of
  `<event>`, and deliver a reaction to a question. If either is not wanted, give the questions
  room `m.reaction` 100 so Element does not offer it. The room is low volume, so this costs
  nothing in noise.

### B3. Go-vs-Python rule (D9) needs the owner's explicit decision, not a default

CLAUDE.md: "a standalone Python CLI is ported to Go when it is next reworked." This plan adds
four subcommands, multi-room sync, new trust types and an inbox format change to `pingbus`
(a standalone zipapp CLI). That is a rework by any reading. D9's reason, that Plan 00209 is
porting it, is a real one. But it overrides a hard rule, so it must be an owner decision. It
also adds to 00209's porting burden (the plan admits its corpus must grow). Mark D9 "needs owner
sign-off", not "defaulted".

### B4. Side-room idempotency gaps

- **Create-then-crash window:** `createRoom` succeeds but `room_id.reports` is not written.
  The re-run creates a second room. The main room has the same window (admin.py:570-579), but
  here the index can recover it: if the ID file is absent and the index names an `admin`-created
  room whose back-link matches, adopt that room rather than create one. Test it.
- **Removed humans:** `bootstrap` kicks a removed human only from the main room
  (admin.py:642-644 → `_remove_account(api, room, …)`). §5.1 never removes them from the side
  rooms. Once the power levels are rewritten without them, a removed human in reports falls back
  to `users_default` 10.
- **More than one coordinator:** the record can list more than one coordinator
  (`coordinators()`, `role_worker_many`), but `_sync_questions_members` invites "the
  coordinator". Say "every coordinator" or refuse.
- `park_member` is listed as a caller of `_sync_questions_members`, but parking keeps the role,
  so the call does nothing. Drop it or say why it is there.

### B5. A new coordinator misses earlier answers

`_after_join` (syncer.py:381-390) deliberately skips the history of a room it has just joined.
At a handover, human replies that arrived between the kick and the join are never delivered.
`pingbus questions` covers this only if the coordinator runs it. Add
"run `pingbus questions` at start" to `role_coordinator` (§10.2). `questions` should also show
replies that have not been dispatched, not only the states.

## New findings

### R1. The capability beacon: reasonable, but not a proof, and the pre-flight duplicates it
The beacon is the eager reports-room join that a new syncer makes on reading the index. That
join is cheap and also removes the earlier "join on first `report`" path, so it costs no new
event type. That much is the simplest workable signal: today nothing reports a running
watcher's code version (`agent_bus.status` keys are only `v`, `state`, `until`).

But SPEC §5.3 calls it "the proof, which no file on disk gives". That holds only for ccy, whose
code comes from the image. Host `cc` and LXC members are upgraded **in place**, and short-lived
commands sync too: `recv` "sync[s] once when the lock is free" (`cli.py:1245-1259`), and `wait`
does the same (`:1419-1438`). So a new-code `recv` can join reports while the session's
long-running watcher is still old. The invite then reaches whichever process syncs next, and an
old watcher rejects it with `POST /leave`. The beacon then reports a coordinator as ready when
its watcher is not.

This is not silent: A2 ("every coordinator is joined to questions") fails loudly afterwards.
Two simplifications are open:
- **Simplest sound option:** drop "proof" from the wording and keep the beacon purely as the
  invite gate (it still prevents most rejections). Make deploy 2's wait leg wait for the
  coordinator's **questions** join, the event the hazard is about, instead of the reports join.
  Name the restart on timeout. That makes the gate and its check the same fact.
- **Drop the pre-flight "every coordinator is a held seat" check.** The wait leg already names
  any coordinator that is not running, so the check adds nothing. It also blocks the whole
  deploy whenever any team's coordinator is merely idle, and "held seat" is a ccy/cc seat
  concept the spec does not define for LXC service members. Keep the pre-flight's LXC
  "container up, kit new" check: containers can stop between deploys.

`held`, the second play run and the bounded wait are otherwise the minimum needed for
convergence inside one meta-deploy run, so I do not count them as YAGNI. The 180 s default
borrows Plan 00209 R14, which is unmerged. State the number here instead.

### R2. Say exactly how the inbox records the room, so old readers stay safe
Items are stored as the event's `STORED_KEYS` subset (`inbox.py:340`). SPEC §6 says the purpose
goes "into the stored item's wrapper". During the deploy-1 coexistence window (in-place upgrade,
old watcher, new `recv`), an old reader re-validates items that new code wrote. If "wrapper"
means the event becomes nested, the old reader drops main-room items as `schema`, silently.
**Fix:** say that the room is a new top-level stored key, written **only for questions-room
items**. Main-room items stay byte-identical, and old code never produces or reads a
questions-room item. Add one test: an old-format reader accepts a new main-room item.

### R3. "Every sync refuses (exit 78)" is too blunt
If a role change makes a `human_text: false` member coordinator, every sync failing exit 78
takes that member off the bus entirely: it gets no pings and no main-room traffic. Refuse where
the role is assigned instead. The admin tool's `set_role`/`add_member` and `members.py` are
already listed. If the admin tool cannot see the bundle flag, record `human_text` in the
registry at `add_member`. The member side should then decline the questions invite (already in
§4.4) and report the reason in `status` and hook context. That is loud, and it does not disable
the member.
