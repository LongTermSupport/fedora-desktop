# Plan 00068 — Journal 2026-08-10

## E8 is measured, and it does not need answering — the dilemma dissolves

E8 asked whether an ungranted tool **refuses** or **prompts** without
`--dangerously-skip-permissions`, because a prompt in a TTY-less job hangs. It is listed as *the
load-bearing unknown*, gating Decision 9 and Task 4.1.

Measured directly against the real CLI, by pointing `ANTHROPIC_BASE_URL` at a dead port so the
session initialises and stops, then reading the `system`/`init` event it emits before it fails:

| flags passed                                      | `permissionMode`    | tools | `Bash`/`Edit`/`Write` |
| ------------------------------------------------- | ------------------- | ----- | --------------------- |
| (none)                                            | `default`           | 29    | present               |
| `--dangerously-skip-permissions`                  | `bypassPermissions` | 29    | present               |
| `--dangerously-skip-permissions` + `--disallowedTools Bash,Edit,Write` | `bypassPermissions` | 28 | **ABSENT** |
| `--allowedTools Read,Grep`                        | `default`           | 31    | present               |

**Row 3 is the answer, and it is not one of the two E8 offered.** `--disallowedTools` **composes
with** `--dangerously-skip-permissions` — the tools are gone from the session while the permission
mode stays `bypassPermissions`. So a CI invocation can keep `--dangerously-skip-permissions`, which
removes the hang risk entirely, *and* remove the tools it must not have.

That refutes the premise Decision 9 rests on, quoted from PLAN.md:

> `--dangerously-skip-permissions` (`claude-yolo:2792`) *bypasses* an allowlist rather than
> composing with it, so CI must not pass it.

True of `--allowedTools`. **Not true of `--disallowedTools`.** The two flags do different jobs:
`--allowedTools` governs *permission* (what may proceed without a prompt) and `--disallowedTools`
governs *availability* (whether the tool is in the session at all). Only the second survives
skip-permissions, and the second is the one Decision 9's intent actually needs.

E8 therefore stops gating anything. Worth keeping as a measurement rather than deleting, because
the reason it stopped mattering is a fact about the flags that the next reader will otherwise
re-derive.

**Row 4 is the other half, and it is why the allowlist-only shape restricts at all.** Asking for
two tools yields **31** — more than the default 29. `--allowedTools` adds nothing and removes
nothing; it suppresses prompting. In headless `-p` mode there is no human to answer a prompt, so an
unlisted tool is refused **by default rather than by decision** — which works, and is one CLI
default away from silently failing open.

**One counter-intuitive detail worth recording, because it breaks the obvious sanity check.**
29 − 3 = 26, but row 3 reports **28**. Diffing the tool lists: removing `Bash` *adds* `Glob` and
`Grep`. The CLI substitutes narrower tools for a withdrawn capability. So sizing a restriction by
counting tools gives a wrong answer, and any assertion written against a count will be wrong for a
reason nobody will look for.

## Decision 9's intent stands; its mechanism does not — and the attribution is why that is hard to see

Decision 9 is recorded as **"Owner's decision, 2026-08-01"**. Checked this plan's own journal for
what the owner actually said. The entry of that date records:

> **New scope from the owner**: Decision 9 — CI runs with a restricted tool surface, read-only
> w.r.t. the repo, no `--dangerously-skip-permissions`.

and, in the same entry, names the only verbatim owner text on the subject:

> the owner's steer, whose governing text says *"CI need safety and MCP etc"*

Those two are not the same size, and the gap is the whole point:

- **"CI should be more locked down" is the owner's** — *"CI need safety"* supports it directly.
  Decision 9's **intent** is correctly attributed and should not be weakened.
- **"no `--dangerously-skip-permissions`" is a derivation, not a quote.** It is a mechanism this
  plan reasoned to from that steer, and it is recorded in the decision as though the owner chose
  it.

This is not bookkeeping. A mechanism labelled *owner's decision* cannot be revised by an agent — it
has to go back to the owner. So the label is what stops a reader reaching for the composing option
in row 3, and the wrong attribution converts a **correctable technical claim** into a **settled
human decision**. That is a strictly worse failure than an unattributed restriction, because the
evidence needed to fix it now looks insufficient by construction.

Correcting it makes the decision *stronger*, not weaker: the intent keeps the owner's authority,
and the mechanism becomes revisable on evidence — which is what just happened to it.

This plan already lists *"this plan invents a constraint the owner never set"* in its own risk
table, recorded as having materialised three times, then four. This is the fifth, and it is the
first one where the invention was labelled with the owner's name.

## The intent is already implemented downstream, in a stronger form

Recorded so this plan does not specify something that exists. The consuming estate's CI action
already derives three layers from a single per-class tool list, pins the model explicitly per
class rather than taking the account default, and asserts at startup that the CLI it is about to
run actually exposes each of nine security-carrying flags (`--allowedTools`, `--disallowedTools`,
`--permission-mode`, `--settings`, `--strict-mcp-config`, `--mcp-config`, `--model`, `--print`,
`--system-prompt`, `--output-format`) — hard-failing on any that is missing, because a CLI silently
lacking one would run with a weaker boundary than the design states.

That last part is the honest answer to *"ccy auto-updates the CLI daily so it can change underneath
us"*, and it is better than the version pin that concern usually produces: it asserts the property
on the build about to run, rather than a proxy for it.

It also carries an argument worth lifting back here, because it generalises beyond CI: it keeps
**no per-class MCP denylist on purpose**, on the grounds that a denylist over a large server-side
tool surface fails **OPEN** on a typo. That was not theoretical — earlier revisions denied several
tools that do not exist under those names, while the real write primitive was not listed at all.
An allowlist fails closed on the same typo. Anywhere this plan reaches for a denylist over a
vocabulary it does not control, that asymmetry applies.
