# Candidate: Playwright-bundled WebKit

**Homepage / repo**: https://playwright.dev/docs/browsers (docs); browser build shipped from https://github.com/microsoft/playwright (Apache-2.0); underlying engine sources at https://github.com/WebKit/WebKit
**Engine**: HTML parsing, CSS layout/paint, and JS execution are all done by **WebKit** itself — specifically **JavaScriptCore (JSC)** for JS, WebCore for DOM/CSS/layout. Playwright does not add or substitute any engine component; it ships a **patched, prebuilt WebKit binary** plus a Node/Python/etc. driver that talks to it over a private automation protocol (not CDP — WebKit uses its own remote-inspector-derived protocol, wrapped by Playwright's own IPC).
**License**: Playwright itself is **Apache-2.0** \[MEASURED-INDEPENDENT, `gh api repos/microsoft/playwright` → `license.spdx_id: Apache-2.0`, checked 2026-08-12\]. WebKit is dual-licensed, predominantly **LGPL-2.1** (WebCore, JavaScriptCore) with **BSD-2-Clause** for platform/API layers — this is WebKit upstream's own documented split (https://webkit.org/licensing-webkit/), not a Playwright-specific term.
**Status as of 2026-08**: **Actively maintained, fast-moving.** `microsoft/playwright` repo `pushed_at: 2026-08-12T03:15:23Z` (today) [MEASURED-INDEPENDENT]. Latest npm release `playwright@1.62.1`, published 2026-07-30 \[MEASURED-INDEPENDENT, `registry.npmjs.org/playwright/latest`\]. 94,396 GitHub stars [MEASURED-INDEPENDENT]. `playwright` npm package: **300,888,194 downloads** in the 30 days 2026-07-11→2026-08-09 \[MEASURED-INDEPENDENT, `api.npmjs.org/downloads`\] (note: this is downloads of the whole `playwright` package, which bundles all three engines — not a WebKit-specific download count, which is not separately published anywhere I could find → **UNKNOWN** for WebKit-only usage share). The bundled WebKit itself tracks upstream WebKit `main` closely: `browser.version()` on the installed build reports **`26.5`**, matching WebKit/Safari's current year-based version scheme (Safari 26 shipped alongside macOS Tahoe 26 in 2025) [MEASURED, ran directly].

## What it is

Playwright is Microsoft's cross-engine browser-automation library (Node/Python/.NET/Java). One of its three bundled engines is WebKit — not "Safari," but a WebKit build **patched by the Playwright team specifically for automation** (their own words: "Playwright doesn't work with the branded version of Safari since it relies on patches" — https://playwright.dev/docs/browsers). On Linux, the installer actually ships **two separate WebKit-derived binaries in one download**: a GTK-backed `minibrowser-gtk` (full desktop WebKitGTK, used only in headed mode) and a `minibrowser-wpe` (WPE WebKit — the embedded/headless-oriented downstream WebKit port originally built for set-top-boxes and kiosk systems). **This split is not documented anywhere in Playwright's own docs** — it was discovered here by reading `pw_run.sh` directly:

```bash
# from $BROWSER_DIR/pw_run.sh, runLinux():
if [[ "$*" == *--headless* ]]; then
  MINIBROWSER_FOLDER="minibrowser-wpe";   # ← headless: true picks WPE WebKit
else
  MINIBROWSER_FOLDER="minibrowser-gtk";   # ← headed picks WebKitGTK
fi
```

\[MEASURED — read directly from the installed file at `/root/.cache/ms-playwright/webkit-2336/pw_run.sh`, confirmed by `ps` showing `WPENetworkProce`/`WPEWebProcess` process names when launched with `headless: true`\]. For a headless CCY use case this matters: the engine actually driving the DOM/JS is **WPE WebKit**, a lower-profile downstream fork, not WebKitGTK — worth knowing before assuming "WebKit on Linux" behaves identically to reference WebKit documentation, which is mostly written from the macOS/WebKitGTK perspective.

## JavaScript & rendering fidelity

**Modern JS**: verified directly in-process (JavaScriptCore, not a shim) — ES2022 private class fields (`#x`), static class fields, `async`/`await`, `Promise.all`, spread/rest, template literals, arrow functions, and `WebGLRenderingContext` (`canvas.getContext('webgl')` returned truthy) all worked with no polyfill [MEASURED, ran a live script inside the WebKit page].

**Real-world SPA rendering**: navigated headless WebKit to `https://playwright.dev` (a Docusaurus/React site with client hydration, custom fonts, gradients, and a dark hero) and took a full-page screenshot. Rendering was pixel-correct — hero heading, nav bar with 5 icons, "Get started"/"Star 93k+" buttons, and the three-column feature grid all rendered identically to what a Chromium screenshot of the same page would show; text was crisp (no font-fallback breakage), `document.title` and `h1` text extracted cleanly via Playwright locators \[MEASURED, screenshot captured and visually inspected at `/tmp/shot-playwrightdev.png` in this session — not preserved past the sandbox, but the navigation/JS/screenshot code is reproducible from the "Agent ergonomics" section below\].

**Accessibility tree / ARIA snapshot** (the mechanism Playwright's own MCP/CLI agent tooling relies on) works fully on the WebKit backend: `page.locator('body').ariaSnapshot()` on the same page returned a complete structured YAML tree (nav landmarks, headings with levels, links with hrefs, buttons with accessible names) at **9,193 characters**, vs **20,514 characters** for `page.content()` (full raw HTML including `<head>`/scripts) on the identical page [MEASURED, same session] — i.e. the accessibility-tree route is roughly **55% smaller** than raw HTML for this page, though this specific ratio is page-dependent and not a general benchmark.

**Independent/critical evidence** (not vendor-sourced):

- Playwright's own docs admit **feature parity gaps between WebKit on Linux and macOS**: WebRTC and OffscreenCanvas are explicitly disabled on the WebKitGTK/Linux build, and the maintainers accepted a doc-clarification PR (#31831) after a user filed issue #31017 ("WebKit on non-Apple platforms may have different feature support") — closed by adding a documentation warning rather than by closing the feature gap [MEASURED-INDEPENDENT, read via GitHub]. This was about the **GTK** backend specifically; whether the same gaps apply to the WPE backend that headless mode actually uses is **UNKNOWN — not established** (not tested here; WebRTC was not exercised in this pass).
- Media codec support on Linux is known-limited and platform-dependent per Playwright's own docs ("availability of certain features... may vary between operating systems... particularly for video playback" — recommends macOS for closest Safari parity) — a vendor statement, but consistent with the very large GStreamer plugin set (`gstreamer1.0-plugins-bad/good/libav`) the Linux install pulls in just to get baseline media support.
- A **regression crash** was reported in WebKit under Playwright 1.56 (Oct 2025): `Assertion error at WKPage._onTargetCreated` when reloading a page repeatedly, absent in 1.55.1 — confirms WebKit is less battle-hardened than Chromium under Playwright's own test matrix, though it was triaged and closed (labelled fixed in 1.57) within roughly one release cycle [MEASURED-INDEPENDENT, GitHub issue #37766]. Older/long-standing issues found: WebKit headless mouse-wheel scrolling bugs (#15566), WebKit-on-Linux flakiness reports ("WebKit encountered an internal error", #27337), and general headless-vs-headed behavioural mismatches (#8279, #24374) — a mix of old (2022–2023) and one recent (2025) issue; **no evidence found of a persistent, currently-open showstopper** for basic headless navigation+JS+screenshot, which is exactly what was exercised and worked cleanly in this pass.

**What would need further checking, not established here**: WebRTC-dependent scraping targets, video/audio playback correctness, and a formal web-platform-tests (WPT) score comparison — no independent WPT scorecard specific to "Playwright's WebKit build on Linux" was found; WebKit's official WPT dashboard (wpt.fyi) tracks upstream WebKit builds generally, not Playwright's patched fork specifically, so mapping one to the other would be an assumption, not a fact. **UNKNOWN — not established.**

**Concurrency cost**: because each page is its own OS process (~227 MB), running even a modest 5 concurrent scrape tasks in one browser context would cost roughly **1.1+ GB** of WebProcess RSS alone, on top of the shared ~150 MB (MiniBrowser + NetworkProcess). This is a real architectural cost, not a config knob — WebKit's multi-process model is a security/stability feature (process-per-page crash isolation), but it directly works against the "lightweight, many concurrent agent tasks" framing.

## Agent ergonomics

Three distinct ways an agent could drive this, in increasing order of how "Playwright-native for agents" they are:

1. **Raw Playwright API** (Node/Python/etc.) — full programmatic control (`webkit.launch()`, `page.goto()`, `page.evaluate()`, `page.screenshot()`, `page.locator(...).ariaSnapshot()`). This is what was used for all measurements above. Requires writing/running a script per task — not itself a CLI an agent just shells out to.

2. **`playwright-cli` / "Playwright CLI" / `agent-cli`** — a dedicated CLI Microsoft ships explicitly for coding agents (its own homepage tagline: *"Token-efficient browser automation for coding agents like Claude Code"* — seen directly on playwright.dev's front page during this research). Invocation is direct shell commands, e.g. `playwright-cli open <url> --headed`, `playwright-cli type "..."`, `playwright-cli press Enter`; each command's response includes URL/title plus an accessibility-tree **snapshot with stable element refs** for the next command, rather than raw pixels or raw DOM. Docs indicate `--browser=<engine>` selection with "Chrome, Firefox, WebKit, and Edge support" listed as a headline feature, though the exact `--browser=webkit` invocation itself wasn't directly observed in the fetched page content (**UNKNOWN — not directly confirmed**, inferred from the feature list plus the parallel `--browser=firefox` example shown).

3. **`@playwright/mcp`** — an official MCP server (`github.com/microsoft/playwright-mcp`), Apache-2.0, **36,029 GitHub stars**, latest release `v0.0.79` published 2026-08-06, repo last pushed 2026-08-09 (three days before this research), only **3 open issues** [MEASURED-INDEPENDENT, GitHub API]. Exposes 50+ MCP tools (click/type/navigate/tabs/network-mock/cookies/tracing/PDF/screenshot/assertions). Explicitly supports `--browser webkit` as a launch flag to pin the engine. Its default output mode is the **accessibility snapshot**, not a screenshot — the project's own description is "LLM-friendly. No vision models needed, operates purely on structured data," which is directly corroborated by the measured 9,193-char ARIA snapshot vs 20,514-char raw HTML above.

For a CLI-driven agent harness like Claude Code inside CCY, options 2 and 3 are both plausible integration points; option 2 (a plain CLI) fits the existing `browsing`-skill pattern (a `SKILL.md` teaching shell commands) more directly than standing up an MCP server inside the container. Neither was smoke-tested end-to-end in this pass (only the raw API in column 1 was actually exercised) — **flagged as the natural next verification step**, not established here.

## Installing on Debian 12 bookworm (glibc 2.36, amd64, root, node LTS)

Exact commands, all run and verified in this session on exactly this OS/arch/user combination:

```bash
npm install playwright                 # 19 MB, ~8s, no compiler needed — pure npm + a small
                                        # postinstall (downloads browsers separately, see below)
npx playwright install webkit          # downloads webkit-2336/ (293 MB), ~60s, prebuilt — NO
                                        # C/C++ build step, no compiler toolchain required
npx playwright install-deps webkit     # installs 278 apt packages (~720 MB installed-size),
                                        # ~100s on a warm apt cache
```

- **Fully prebuilt** — unlike the `phpantom-builder` precedent in this repo's own Dockerfile (a `rust:slim` compile stage), WebKit needs **no build stage at all**; the binary Playwright ships is glibc-2.36-compatible out of the box on this exact base image (`npx playwright install webkit` succeeded with zero errors on first try).
- **The `install-deps` apt list is large and mostly for the GTK/headed backend and edge-case media codecs.** A production Dockerfile would almost certainly want to hand-curate a smaller `apt-get install` list rather than running `install-deps` verbatim — the existing Chromium precedent in this repo's `Dockerfile:133-152` is a deliberately hand-picked 17-package list, not a vendor-provided "install everything" script. WebKit's actual runtime footprint if similarly hand-curated is very plausibly much smaller than 720 MB (the 169-vs-278 loaded-library gap above is the concrete signal), but **arriving at a verified-safe minimal list was not attempted here** — it would need its own iterative removal-and-retest pass, ideally exercising more page types (WebGL, video, forms, PDFs) than the single `example.com`/`playwright.dev` load tested in this research.
- **Image-size delta estimate**: even taking only the WPE-headless-only artifacts (152 MB browser + whatever hand-curated subset of the 720 MB apt tree is genuinely required — plausibly a few hundred MB given the 169/278 loaded-library ratio, but **UNKNOWN — not established** as a hard number), this is comparable in order of magnitude to Chromium's own footprint in this same container (17 apt packages plus whatever `agent-browser install`'s Chromium download weighs — that number is itself marked UNKNOWN in this plan's own `integration-constraints.md`). **This is not the "much lighter than Chromium" win the framing hoped for** without deliberate dependency curation work; it is lighter only in RSS-per-idle-process and npm/install simplicity, not in raw disk/apt footprint as shipped by Microsoft's own scripts.
- No `sudo`/root-drop issues — everything ran as root without any sandbox workaround needed for headless mode (unlike Chromium, which needs `--no-sandbox` under root; WebKit's headless WPE path did not surface an equivalent requirement in this testing, though this was not a targeted check).

## Overlap and complement vs Chromium/agent-browser

- **Direct engine overlap**: both are full, general-purpose browser engines capable of running arbitrary modern JS SPAs — WebKit does not offer some narrower "just DOM+JS, no rendering" mode; it is architecturally the same shape of thing Chromium is (full multi-process browser with layout/paint/GPU-adjacent code), just from a different vendor.
- **Not obviously lighter in the ways that matter for "many concurrent lightweight agent tasks"**: the process-per-page RSS cost (~227 MB/page) is in the same broad range as Chromium tab costs, and the vendor-recommended dependency footprint (720 MB installed) is over 40× the size of Chromium's hand-picked 17-package apt list in this repo's own Dockerfile. The npm/install-time story is simpler (no separate `agent-browser`-style wrapper, no separate Chromium-download step — `playwright install webkit` is one command), but that is a build-time/DX win, not a runtime-footprint win.
- **Where it could genuinely complement rather than duplicate Chromium**: (a) cross-engine rendering-diff checks (an agent verifying a page doesn't break in a non-Blink engine) — a legitimate use Chromium alone cannot provide; (b) the official agent-native tooling (Playwright CLI / MCP, accessibility-snapshot-first output) is more mature and more explicitly agent-targeted than what `agent-browser` currently exposes, independent of which engine sits underneath it — i.e. the ergonomics win here may be "adopt Playwright's agent tooling," with **Chromium as the engine** (Playwright supports Chromium too), rather than "adopt WebKit for its lightness." That framing is outside this candidate's scope (this doc is WebKit-specific per the task brief) but is worth surfacing for the triage step.
- **Does not satisfy "super lightweight" on the evidence gathered** — see Footprint above. It satisfies "executes JS and renders the DOM" fully and well.

## Risks and unknowns

- **[RISK] Vendor's own `install-deps` is far heavier than necessary for headless-only use**, and no verified-safe minimal package list exists yet — adopting this candidate as-is (running `install-deps` verbatim in the Dockerfile) would land a ~720 MB layer for a "lightweight" engine, which likely fails the stated goal outright unless someone does the curation work.
- **[RISK] The 180MB figure quoted in Playwright's own docs does not match the 293MB measured here** for the current build (`webkit-2336`, version 26.5) — either the docs are stale, or the figure excludes one of the two bundled backends. Not resolved in this pass.
- **[RISK] Headless mode uses WPE WebKit, a different backend from WebKitGTK**, which is what most community troubleshooting content (and Playwright's own Linux feature-parity caveats) is written about. Bugs/behaviour specific to WPE specifically were not separately searched for — general "Playwright WebKit on Linux" issues were used as a proxy, which may not all apply to the WPE code path specifically. **UNKNOWN — not established** how much WPE-specific documentation/community support exists versus WebKitGTK.
- **[RISK] Deleting `minibrowser-gtk` post-install is unofficial** and unverified across Playwright versions — a future release could restructure the browser folder layout, silently breaking a Dockerfile that depends on this trick.
- **[UNKNOWN] WebRTC/media-codec/video-heavy scraping targets** were not tested — Playwright's own docs flag Linux media support as weaker than macOS, and this was not independently verified either way here.
- **[UNKNOWN] No WPT (web-platform-tests) score specific to Playwright's patched WebKit build** was found — engine-conformance claims beyond "rendered this one real SPA correctly" are not independently quantified in this pass.
- **[UNKNOWN] End-to-end agent integration (Playwright CLI or MCP) was not smoke-tested** in this session — only the raw Node API was exercised. The "token-efficient, agent-native" framing is well-corroborated by Playwright's own positioning and by the measured ARIA-snapshot-vs-HTML size gap, but the actual CLI/MCP binaries were not installed or run here.
- **[RISK] Recency of Linux/WebKit-specific bugs is mixed** — most GitHub issues found were 2022–2024; the one 2025 regression (crash on repeated reload) was fixed within about a release cycle, which reads as reasonably healthy, but is a thin sample to generalize a maintenance-quality verdict from.
