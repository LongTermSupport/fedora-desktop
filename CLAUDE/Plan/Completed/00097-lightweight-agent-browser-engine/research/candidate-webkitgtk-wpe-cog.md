# Candidate: WebKitGTK / WPE WebKit + Cog

**Homepage / repo**: https://github.com/Igalia/cog (launcher) · https://wpewebkit.org/ (engine) · https://github.com/WebPlatformForEmbedded/WPEWebKit (downstream engine mirror)
**Engine**: WebKit (Igalia's WPE port). Parsing/layout/paint = WebKit's own engine (WebCore); JavaScript = JavaScriptCore (JSC), the same JS engine Safari uses. Cog is not itself an engine — it is a ~6 KB-of-C "minimal launcher" (`libcogcore` + the `cog` binary + the `cogctl` D-Bus remote-control tool) that embeds WPE WebKit as a single-window, chrome-less web-application container. [Cog GitHub README/overview](https://github.com/Igalia/cog/blob/master/docs/overview.md)
**License**: Cog — MIT. WPE WebKit itself — mixed LGPLv2 (code inherited from KHTML) and BSD-2-Clause (new WebKit code), same licensing as the WebKit project generally. `libwpe` and `WPEBackend-fdo` are both BSD-2-Clause. [WebKit Licensing docs](https://docs.webkit.org/Other/Licensing.html), [WPE FAQ](https://wpewebkit.org/about/faq.html)
**Status as of 2026-08**: Actively maintained but **the specific stack this candidate names (libwpe + WPEBackend-fdo + Cog) is scheduled for deprecation next month.** WPE WebKit stable is at 2.52.5 (2026-07-13), dev branch 2.53.90 (2026-08-08), released roughly every 2-4 weeks — genuinely active. [wpewebkit.org/release](https://wpewebkit.org/release/). Cog itself: last push 2026-06-11, 337 stars, 83 forks, 142 open issues, MIT, actively developed on `master` — but its **last tagged stable release is 0.18.5 (2025-05-29)**, over a year old at time of writing. [GitHub API for Igalia/cog]. Igalia has announced a **new GObject-based `WPEPlatform` API going stable in September 2026, at which point "the legacy API will be officially deprecated" — explicitly naming libwpe, WPEBackend-fdo, and Cog as the deprecated components.** ["Building a Custom HTML Context Menu with the New WPEPlatform API", Igalia blog](https://blogs.igalia.com/klee/building-a-custom-html-context-menu-with-the-new-wpeplatform-api/)

## What it is

WPE WebKit is a WebKit "port" purpose-built for embedded/low-resource Linux devices (set-top boxes, infotainment, digital signage, appliances) — unlike WebKitGTK it has no GTK dependency at all and abstracts graphics/input out-of-tree via replaceable "backend" plugins. [wpewebkit.org overview](https://wpewebkit.org/blog/02-overview-of-wpe.html) Cog is Igalia's reference embedder: a tiny launcher that takes a URL, boots one WPE web view full-screen/borderless, and exposes a D-Bus control surface (`cogctl`). It targets kiosk/appliance use, not general browsing. Real-world WPE deployments cited by Igalia include set-top boxes, automotive, and in-flight entertainment systems. [Igalia WPE project page](https://www.igalia.com/project/wpe)

## JavaScript & rendering fidelity

- JS engine is JavaScriptCore, the same engine in Safari — this is a real, modern, spec-tracking JS engine, not a toy. [various]
- WebKit/JavaScriptCore was reported ahead of Chrome/V8 on Speedometer 3 (+17%) and JetStream 3 (+7.3%) in one independent 2026 comparison — **but that comparison is Safari-on-macOS vs Chrome, not WPE-on-Linux**, and one of the same search results explicitly notes "the performance gap varies significantly by platform, with WebKit struggling on Linux" — no WPE-specific, Linux-specific benchmark number was found. [tech-insider.org Safari-vs-Chrome piece — treat as a general-web secondary source, not verified against primary benchmark data] Flag this as **UNKNOWN for the actual candidate** (WPE on Linux specifically) rather than assume Safari's numbers transfer.
- WPE WebKit MiniBrowser is one of the browsers wired into the **web-platform-tests (WPT)** project's own test runner (`wpt --product wpewebkit`), meaning it is tested against the same standards-compliance suite used by Chromium/Firefox/Safari upstream — a real independent-ish compliance signal exists, but no aggregate WPT pass-rate score for WPE was found in this research (would require actually running `wpt` locally). [web-platform-tests.org WPE MiniBrowser docs](https://web-platform-tests.org/running-tests/wpewebkit_minibrowser.html)
- Because WPE shares WebCore/JSC with desktop WebKit/Safari, it should render modern SPAs (React/Vue-style DOM+JS apps) — this is architecturally credible, but **no independent third-party trial of WPE specifically (as opposed to Safari) against a real SPA was found** in this research pass. Treat SPA fidelity as inferred-from-shared-codebase, not independently measured.
- Known reliability defect, independently filed (not vendor-reported): WPE WebKit **2.38.6 — the exact version Debian 12 bookworm ships** — has an open, unresolved bug where the WebProcess's GC "stops functioning" after ~7 days of idle uptime and memory grows past configured limits. Filed 2025-10-01, still open, no assigned fix as of this research. [WPEWebKit issue #1569](https://github.com/WebPlatformForEmbedded/WPEWebKit/issues/1569) For an ephemeral per-task agent-browser invocation this is low-risk; for a long-lived daemon process it is a real concern.

- **[UNKNOWN]** No independently-measured RSS, startup-latency, or install-size numbers for WPE/Cog were found in this research pass. Any footprint number for this candidate would need to be **measured directly** (e.g. `ps`/`smem` RSS after `cog https://example.com` under the target container) rather than sourced from research; none was available to cite.

[packages.debian.org/bookworm/libwpewebkit-1.1-0]
- Concurrency/scaling numbers: **[UNKNOWN]** — not established in this research.

## Agent ergonomics

- **No CLI designed for scripted extraction.** `cog`'s own CLI takes a URL and rendering flags (`--scale`, `--bg-color`, `--platform`, `--webprocess-failure=...`) — it opens a window/surface and runs; it has no "print rendered text", "dump DOM", or "save PNG" flag. [cog(1) manpage](https://manpages.debian.org/bookworm/cog/cog.1.en.html)
- **`cogctl`** (D-Bus remote control) is genuinely minimal: `open <URL>`, `next`/`previous` (history), `reload`, `ping`, `quit`, `appid`, `objpath`. No `screenshot`, no `get-html`, no `eval-js`. [cogctl(1) manpage](https://manpages.debian.org/bookworm/cog/cogctl.1.en.html) This is materially thinner than agent-browser/Playwright's CDP-driven surface.
- **No CDP.** WPE WebKit's automation story is the **WebKit Remote Web Inspector protocol**, not Chrome DevTools Protocol — the two share ancestry (CDP forked from the WebKit inspector protocol when Blink split from WebKit in 2013) but are not compatible today. Enabled via `WEBKIT_INSPECTOR_SERVER`/`WEBKIT_INSPECTOR_HTTP_SERVER` env vars for a remote/headless target. [Igalia remote-inspector docs](https://people.igalia.com/aperez/Documentation/wpe-webkit/remote-inspector.html)
- **WebDriver (Selenium) support exists and is Debian-packaged**: `wpewebkit-driver` implements the **W3C WebDriver** protocol for WPE, and is a standard `apt`-installable package on bookworm (`libwpewebkit-1.1-0`, `libicu72`, `libsoup-3.0-0`, etc. as deps). [packages.debian.org/bookworm/wpewebkit-driver] This is the most credible existing automation path — a Selenium client could drive WPE the same way it drives geckodriver/chromedriver — but it means adopting **Selenium**, not the CDP-based tooling (Playwright/agent-browser) already used elsewhere in this stack, so it would not share code/patterns with the existing `agent-browser` skill.
- **No MCP server, no maintained scraping/markdown wrapper was found.** Searches for an MCP server, a "get clean markdown from a WPE page" tool, or an existing agent-oriented wrapper around Cog/WPE turned up nothing — every 2026 "MCP web scraping" result names Playwright/Puppeteer/Firecrawl/Browserbase-style Chromium tooling, never WPE/Cog. Building an agent-ergonomic layer (extract text, return markdown, screenshot-on-demand) on top of Cog would be **from-scratch engineering**, either via WebDriver (bolt on a Readability-style HTML→markdown step yourself) or via raw WPE C/GObject API (write a small custom launcher, per the pattern in the [minimal-launcher blog post](https://www.simonpena.com/blog/2026/03/20/getting-started-with-wpe-webkit/), which shows a working WPE embed in "barely 10 lines of code").
- A forthcoming **GObject-Introspection-based `WPEPlatform` API** (stabilizing September 2026, superseding Cog) is explicitly pitched by Igalia as bringing "easy language bindings via GObject Introspection... works with Python, JavaScript, and more" — i.e. **the successor to this exact candidate is designed to be more agent/scripting-friendly than Cog is today**, but it is not shipped yet. [Igalia WPEPlatform blog post, cited above]

## Installing on Debian 12 bookworm (glibc 2.36, amd64, root, node LTS)

**Path A — `apt` from bookworm main (fast, but stale + carries a known bug):**

```bash
apt-get update
apt-get install -y cog wpewebkit-driver libwpewebkit-1.1-0
```

- `cog` bookworm package: **0.16.1-1**. [Debian package search result for cog in bookworm]
- `libwpewebkit-1.1-0` / `wpewebkit-driver` bookworm package: **2.38.6-1** (source `wpewebkit`). [packages.debian.org/source/bookworm/wpewebkit] This is the **exact version with the open, unresolved 7-day-idle GC/memory bug** cited above — a materially stale, specifically-flagged-buggy version, not just "old".
- No `bookworm-backports` package exists for `wpewebkit` (checked; only `webkit2gtk` — the GTK port — has a backport, at 2.46.1). [search result, backports.debian.org check]
- Runtime deps pull in ~30 shared libraries transitively (GStreamer stack, ICU, HarfBuzz, Cairo, libwebp, libseccomp, xdg-dbus-proxy for its bubblewrap-based sandbox, etc.) — this is a real apt-layer weight addition, comparable in kind (if not necessarily in size) to the existing Chromium runtime-lib layer.
- **GPU/EGL is a real open risk in a container.** WPE's `fdo` backend (the one `cog`/bookworm's stable release uses) needs a working EGL context and, in practice, a Wayland compositor; independently-filed issues show it failing outright in minimal/GPU-less Docker setups (`EGLDisplay Initialization failed: EGL_NOT_INITIALIZED`, closed "not planned" — i.e. accepted as unsupported) [WPEWebKit issue #625], and even where it does start, hardware-acceleration can silently fail to engage, leaving animations at ~2 fps despite a capable GPU [Igalia/cog issue #321]. CCY already forwards the host Wayland socket for Chromium/ozone, which may or may not be sufficient for WPE's fdo backend — **untested, not established** in this research.
- Cog also ships a **`headless` platform backend** (`platform/headless/cog-platform-headless.c`, in the repo since before the last stable tag) that renders via `wpe_fdo_initialize_shm()` — shared-memory software compositing, not EGL/GPU — and exports frame buffers through callbacks rather than needing a display at all. \[Igalia/cog GitHub, `platform/headless/` directory + source\] This looks like the right escape hatch for a GPU-less container, **but**: (a) it ships no built-in "dump PNG to disk" or "dump text" tool — a caller has to write code against `on_export_shm_buffer()` itself; (b) a separate secondary source describes an Igalia "headless Cog" use case as "no rendering at all and no GPU needed" for an audio-only (Apple-Music-style) app — it's unclear from public docs alone whether that refers to this same SHM backend or a different, non-visual headless mode; this needs to be resolved by testing, not assumed.

**Path B — build newer WPE from source (currently the only way to get near-current, e.g. 2.5x, WPE on bookworm):**

- Debian **unstable/sid** carries the current stable line (`libwpewebkit-2.0-1` at **2.52.5-1**, matching upstream's 2026-07-13 stable release) [packages.debian.org/sid/libwpewebkit-2.0-1], but mixing sid packages into a bookworm base is exactly the kind of dependency-hell path this repo's IaC discipline would reject — not a real option for a pinned, reproducible image.
- Building from source needs the full WebKit build toolchain: CMake, Ruby, Perl (IDL→JS-binding codegen), ICU, bison, flex, gperf, autotools, a C++ compiler, plus WebKit's usual large third-party dependency set (GStreamer, libxml2/libxslt, sqlite, etc.). \[WPEWebKit `install-dependencies` script + Introduction.md\] This is a genuinely heavy build stage (WebKit is one of the largest C++ codebases that regularly gets compiled from source) — **no concrete build-time or peak-RAM number was found in this research** for WPE specifically; it is known from general WebKit-build folklore to be multi-hour/multi-GB, but that claim is not independently sourced here and should be flagged UNKNOWN pending an actual timed build. Igalia does maintain a `webkit-container-sdk` Docker-based build environment specifically because building WebKit natively is heavy enough to want containerizing. [github.com/Igalia/webkit-container-sdk]
- Net effect: **there is no prebuilt-binary path to a current (2.5x) WPE WebKit on Debian 12** found in this research. The only prebuilt path (bookworm `apt`) is 2.38.6 with a known open bug; the only current-version path is a from-source build with a heavy, uncertain-length compiler stage.

## Overlap and complement vs Chromium/agent-browser

- **Total capability overlap, near-zero ergonomic overlap.** Both execute JS and render the DOM, so for "does this SPA render" they are redundant. But agent-browser already gives Claude Code a CDP-driven, Playwright-backed, actively-maintained automation surface; WPE/Cog would add a *second, incompatible* automation protocol (WebDriver, or raw D-Bus/`cogctl`, or hand-rolled GObject/C code) that shares no code, patterns, or skill documentation with the existing `browsing` skill. Any adoption would need its own skill and its own extraction tooling built from scratch — nothing off-the-shelf plugs into "return markdown to the agent" the way Playwright-family tooling does.
- **Where it could genuinely be lighter**: if the goal is literally "execute JS, get me the resulting DOM/text, no visual chrome, no full browser process model" (Chromium runs separate GPU/renderer/utility processes even headless), WPE's smaller process footprint is architecturally plausible — but **this research could not confirm it with a real number** (see Footprint section — the one independent comparison page 404'd, and no substitute was found).
- **Where it is a downgrade**: Chromium/agent-browser already works, is already in the image, has a maintained skill, and uses the industry-standard CDP that essentially all 2026 agent-scraping tooling (Playwright, Puppeteer, Browserbase, Firecrawl, MCP scraping servers) targets. WPE/Cog would be swimming against that ecosystem current.

## Risks and unknowns

1. **Timing risk is the single biggest finding of this research**: the exact stack named as the candidate (libwpe + WPEBackend-fdo + Cog) is being deprecated by its own maintainer next month (September 2026), in favour of a not-yet-stable `WPEPlatform` API. Building on Cog today means building on a stack whose upstream owner is actively telling new projects not to. [Igalia WPEPlatform blog]
2. **The only apt-installable version on the actual target OS (bookworm) is 2.38.6, which has an open, unresolved, independently-filed idle-memory/GC bug** — and Debian's `wpewebkit` package has not been updated in bookworm's lifetime to a version past this. No backport exists.
3. **GPU/EGL viability inside the CCY container is unverified.** Multiple independently-filed issues show the standard `fdo` backend failing or under-performing in GPU-less/minimal container setups; the `headless` SHM backend looks like the right answer but has no documented output tooling and its exact semantics (does it truly need zero GPU, always?) were not confirmed from primary docs.
4. **No agent-facing tooling exists today** (no MCP server, no markdown-extraction wrapper, no CDP). Everything beyond "open a URL and look at a raw HTML dump via WebDriver" is unbuilt.
5. **No independently-measured footprint numbers were obtainable** in this pass — the one Igalia comparison page that historically had them returned 404. Any "lightweight" claim for this candidate is currently a vendor/architectural inference, not a measurement.
6. **Building a current version from source is a real Dockerfile cost** (compiler stage, large dependency set, uncertain but reputationally "heavy" build time/RAM) that partially undercuts the "lightweight" pitch at the image-build layer even if the runtime footprint turns out small.
