# Candidate: eLinks

**Homepage / repo**: https://github.com/rkd77/elinks (this rkd77 fork is the active upstream — the original elinks.cz/elinks.or.cz project "lost interest"; rkd77's tree is what all current packaging and this research target)
**Engine**: Its own C HTML parser plus NetSurf's `libdom` (DOM tree) and `libcss` (CSS parsing/cascade) for markup+style; a *pluggable* ECMAScript engine chosen at build time — SpiderMonkey (`mozjs-140`), QuickJS (via `quickjs-ng`), or MuJS — runs `<script>` content; "layout" is eLinks' own text-flow renderer (no visual box model — this is a terminal text browser, not a graphical layout engine)
**License**: GPL-2.0-only (per `COPYING` — the project explicitly rejects GPLv3 as its own default policy; a few build/config helper files under separate permissive/GPL-or-later licenses, none of which end up in the installed binary) \[primary source: `COPYING`, https://raw.githubusercontent.com/rkd77/elinks/master/COPYING]
**Status as of 2026-08**: Actively maintained. Latest release **v0.20.0**, published 2026-07-26 (confirmed via GitHub Releases API). Previous releases: v0.19.1 (2026-02-07), v0.19.0 (2025-12-25), v0.19.0rc1 (2025-12-06), v0.18.0 (2024-12-26). Commit activity is real and recent — last push to `master` was 2026-08-06, with commits as recently as Aug 1–6 2026 (Python 3.12 build-detection fix, quickjs property-enum leak fix, a merged community PR). Repo stats: 628 stars, 61 forks, 120 open issues, 8,060+ commits total, single primary maintainer (rkd77) plus community PRs. \[Sources: `https://api.github.com/repos/rkd77/elinks`, `https://api.github.com/repos/rkd77/elinks/releases`, GitHub commit log\]

## What it is

eLinks is a text-mode (terminal/TUI) web browser descended from Links, with tabs, frames, table rendering, cookies, a config-file/menu UI, and protocol support beyond HTTP/HTTPS/FTP (Gopher, NNTP, Gemini, Spartan, SMB, BitTorrent, finger). It has had rudimentary ECMAScript scripting for a long time (originally aimed at "help you get into your banking account, pass through ignorant JS redirects"), and underwent a real architecture upgrade starting around 2023: it adopted NetSurf's `libdom`/`libcss` libraries for a proper DOM+CSS-cascade model (replacing an older, more ad-hoc HTML/CSS handling) and added a second and third selectable ECMAScript backend (QuickJS, then MuJS) alongside the original SpiderMonkey backend. In 2026 it added SVG support (#423) and moved from vanilla QuickJS to the community-maintained `quickjs-ng` fork. It is not a browser engine library or an embeddable component — it is a standalone end-user terminal application (config files in `~/.config/elinks/`, a menu-driven options UI, vi-ish/lynx-ish keybindings).

## JavaScript & rendering fidelity

**The project's own documentation is explicit that this is not "real" JS support.** From `doc/ecmascript.txt` (unchanged in substance for years, still current as of 0.20.0):

> "Yes, there is some ECMAScript support in ELinks. There isn't anything we could call complete, but some bits could help with the most common ECMAScript usage cases — help you (and then us ;) get into your banking account, pass through those ignorant page redirects done by JavaScript code snippets and so."

And, added "As of 2024" and still the operative caveat block:

> - Spidermonkey (mozjs128). Passed tests, but **segfaults occur, especially on shutdown**.
> - QuickJS. Tests also passed. For machines with limited resources... **Not all memory is released on shutdown.**
> - MuJS. For fans of MuJS. **Not all tests passed. I don't know how to implement missing bits.**

There is no engine that is simply "the good one" — every option ships with an admitted defect class, in the maintainer's own words. The doc also describes the DOM/HTML coverage tested by the project's own test suite as "small subset of DOM HTML is 'covered'", and offers `allow.txt`/`disallow.txt` as a documented workaround for "ELinks might crash, or slowdown" on some sites — i.e. per-site JS blocklisting is a first-class, expected mitigation, not an edge case.

**No layout/CSS box model in the graphical sense** — eLinks renders to a terminal character grid. `libcss` gives it real CSS *parsing* and *cascade* (selectors, specificity, some inheritance), and community sources describe the practical result as "meagre" CSS support: colours, `text-decoration`, `font-weight`, backgrounds, `visibility:hidden`, some positioning-adjacent behaviour — not flexbox/grid layout, not viewport-based reflow, nothing that would let a modern SPA's CSS-dependent show/hide or layout logic resolve correctly. \[Source: community summaries corroborated by `doc/ecmascript.txt` and the CSS option wiring in `meson.build`; independent CSS-property enumeration via LinuxLinks/ArchWiki-adjacent write-ups, not project marketing\]

**Independent, real-world trial reports agree it does not render modern JS-heavy sites usably.** A first-hand 2020s blog account (thinkmoult.com) reports that GitHub repo/issue pages, Discourse forums, and Reddit comment threads come out "horrific or completely broken", and that the author's own eLinks config disables JavaScript entirely with the comment "Just give up on JavaScript" — falling back to launching Firefox (`E` key) for anything JS-dependent. This is a browser configured and used daily by an enthusiast, not a hostile review, and it still abandons JS.

**Independent, open crash reports corroborate the instability the docs admit to**, specifically triggered by real-world sites and by the JS engines themselves (not synthetic bugs):

- [#229](https://github.com/rkd77/elinks/issues/229) "ELinks crashed if i want to open whatsmybrowser.org" — open since 2023-04-30, backtrace attached, build has `ECMAScript (mujs)` enabled.
- [#351](https://github.com/rkd77/elinks/issues/351) "Segfault with libmozjs even though ecmascript is disabled" — open since 2025-01-02; notable because the crash fires from the SpiderMonkey backend *even with `ECMAScript.enable=0`*, i.e. merely linking the engine is enough to destabilize the binary in some code paths.
- [#361](https://github.com/rkd77/elinks/issues/361) "Failing tests when ECMA scripting enabled" — open, consistent with the maintainer's own "not all tests passed" admission for MuJS.
- [#418](https://github.com/rkd77/elinks/issues/418), by contrast, is a JS/iframe NULL-deref crash on GitHub that *was* fixed and shipped in 0.19.1 (2026-02-07) — evidence the maintainer does respond to and fix concrete crash reports, just that new ones keep surfacing from real sites.

**No independent JS-conformance benchmark exists** (no web-platform-tests score, no Test262 pass-rate published anywhere found). UNKNOWN — not established. The project's own "tests" referenced in `doc/ecmascript.txt` are its own small internal DOM/JS assertion suite (`meson -Dtest=true -Dtest-js=true; ninja test`), not a standardized conformance suite, and the doc itself calls the DOM coverage "small".

**Verdict on fidelity for agent use**: does not run a modern SPA in any meaningful sense (no framework hydration, no fetch-driven re-render expectation met, no real layout/visibility resolution to key off), is explicitly pitched by its own maintainer as good for "pass through ignorant JS redirects" and login-wall JS, not content rendering. Screenshots are not applicable — there is no visual/pixel output at all (text-mode only), so any workflow needing a rendered image is out of scope regardless of JS fidelity.

## Footprint

- **Binary/library dependency weight**: [MEASURED-INDEPENDENT, but STALE/NOT REPRESENTATIVE] A 2011 text-browser RAM comparison (kmandla.wordpress.com, using a custom Python memory-measurement script on a 120MHz test box) recorded eLinks at ~2.2 MiB RSS. This measurement necessarily predates essentially all of the JS/DOM/CSS work described above (the multi-engine ECMAScript rewrite and libdom/libcss adoption both postdate 2011 by over a decade) — it reflects a JS-less, CSS-less classic eLinks build, not the browser being evaluated here. Treat it as informative only for the "core text renderer" floor, not for a JS-capable build.
- **JS/DOM-enabled build RSS or startup latency**: UNKNOWN — not established. No independent benchmark of a JS-and-libdom-enabled eLinks build was found in this research pass.
- **Install size**: [VENDOR CLAIM / self-built, not independently audited] The project's own Alpine static-build recipe (`docker/alpine-static/mes_static_js.sh`) produces a single statically-linked, `strip`+`upx`-compressed `elinks` binary with QuickJS enabled — i.e. the maintainer's own reference build deliberately optimizes for a small standalone artifact. No absolute size figure is published in the repo; not independently measured here.
- **Debian package size (non-JS build)**: [MEASURED-INDEPENDENT] Debian bookworm's own `elinks` package (0.13.2-1+b4, from 2018-era upstream — see Installing section) is 582.4 kB download / 1,742.0 kB installed on amd64 (packages.debian.org). This package predates JS/libdom/libcss entirely and is not representative of the browser being evaluated.
- **Concurrency**: UNKNOWN — not established; no data found on running multiple eLinks instances/tabs concurrently under agent-driven load (e.g. many parallel fetches).

**Conclusion**: no reliable current footprint numbers exist for the JS-capable configuration that would actually matter here. This is a real gap, not a favorable-but-unquantified claim.

## Agent ergonomics

- **No CDP, no MCP server, no JSON/structured API of any kind.** eLinks' only IPC surface is a bespoke, Mozilla-`-remote`-inspired Unix-socket protocol (`~/.config/elinks/socket`), documented in `doc/remote.txt`. Its command set is small: `ping()`, `openURL(...)`, `xfeDoCommand(openBrowser)`, `addBookmark(...)`, `infoBox(...)`, `reload()`, `search(...)`. **Critically, this protocol can drive navigation but has no command to extract page content, DOM state, or JS-evaluated results** — it is a "control an already-open window" API, not a scraping/automation API. The doc also warns that `-remote` "can cause ELinks to become unresponsive" because remote actions steal key/mouse focus from whatever the interactive session was doing.
- **The actual extraction path is batch/dump mode**: `elinks -dump URL` renders a page non-interactively and prints the terminal-rendered text to stdout. This is the realistic agent integration point (spawn a process, capture stdout), not `-remote`. However: (a) it emits **plain rendered text**, not Markdown or any structured/semantic format — headings, links, and structure are conveyed only by eLinks' own text-layout conventions (indentation, `[1]`-style link footnotes if `-anonymous`/link-numbering options are set), so a caller wanting clean Markdown would need its own post-processing; (b) whether `-dump` reliably executes ECMAScript before dumping (vs. requiring the interactive event loop) is **UNKNOWN — not established** in this research pass; the docs describe JS execution in the context of interactive browsing (redirects, DOM tests) and do not explicitly confirm JS runs to completion in one-shot `-dump` invocations before the dump is taken. This is a load-bearing unknown for any agent workflow that needs JS-rendered dump output specifically.
- **Scripting hooks exist** (`~/.config/elinks/hooks.{js,lua,pl,py,rb,scm}` — Lua/Perl/Python/Ruby/Guile, plus `elinks.get_option()`/`set_option()`), but these hook *eLinks' own behaviour* (e.g. rewriting HTML before render, as the thinkmoult.com blog does with a Python+BeautifulSoup hook to fix "ELinks-unfriendly websites") — they are not an agent-facing extraction API either.
- **No token-budget-friendly output mode was found** beyond the plain-text dump itself, which for a text-mode browser is inherently much smaller than raw HTML — that part is a genuine structural advantage over shipping raw DOM/HTML to a model, independent of JS fidelity concerns.
- **How Claude Code would actually have to drive it**: spawn `elinks -dump [-no-numbering] <url>` as a subprocess and parse stdout; there is no session/state model across calls other than what `-remote` offers (and `-remote` doesn't expose content). This is closer to `lynx -dump`/`w3m -dump` than to anything Playwright/CDP-shaped.

## Installing on Debian 12 bookworm (glibc 2.36, amd64, root, node LTS)

**No usable prebuilt package exists for this target.** Debian bookworm's own `elinks` package is version **0.13.2-1+b4** (per `packages.debian.org/bookworm/elinks` and `sources.debian.org`) — this predates the entire libdom/libcss/multi-JS-engine rewrite described above by roughly five to seven years (that work starts appearing in the 0.17.x–0.19.x NEWS entries, 2023–2025). Installing `apt-get install elinks` on bookworm gets a JS-less, pre-libcss classic build, not the browser evaluated in this document. (Debian `sid`/`trixie` carry newer builds — 0.18.0 in trixie, 0.19.1-2.1 in sid — still not the just-released 0.20.0, and irrelevant anyway since the container is pinned to bookworm.)

**Building from source is therefore required**, and it is a real multi-library chain, not a single `./configure && make`:

1. **NetSurf libraries — none packaged on Debian at all.** `libdom` and `libcss` (searched for by eLinks' `meson.build` via pkg-config as `libdom >= 0.4.2` and `libcss >= 0.9.2`) return **zero results** on `packages.debian.org` for bookworm (confirmed by direct package-name search — only unrelated `libcss-*-perl` Perl modules exist, no C `libcss`/`libdom`). The project's own reference build (`docker/alpine-static/Dockerfile`) shows the real recipe: download and `make install` five NetSurf source tarballs in dependency order from `download.netsurf-browser.org` — `buildsystem` (their shared Makefile framework), `libparserutils`, `libwapcaplet`, `libhubbub` (needs `gperf`), `libcss` (needs `libpsl`, plus the repo carries a local patch `libCSS-restrict.diff`), then `libdom`. This is scriptable (plain `wget`+`tar`+`make install` with `PREFIX`/`LIBDIR`/`COMPONENT_TYPE` vars, no interactive configure) but is five extra from-source library builds with their own quirks (e.g. `CFLAGS=-Wno-error` is set in every step, implying these libraries do not cleanly build warning-clean on a current toolchain).
2. **JS engine — engine choice matters a lot here:**
   - **MuJS** *is* packaged in bookworm (`libmujs-dev`/`libmujs2`, 1.3.2-1) — this is the only JS backend installable via `apt` on this exact target. It is also the backend the maintainer calls the weakest ("Not all tests passed. I don't know how to implement missing bits.").
   - **QuickJS-ng**, the backend eLinks 0.20.0 actually ships as its default recommended engine, is **not packaged on Debian at all** (Debian's `quickjs` package tracks the unrelated original Bellard `quickjs`, not the `quickjs-ng` fork eLinks' `meson.build` looks for by pkg-config name `quickjs-ng`/`qjs`). It is packaged in Alpine (`quickjs-ng-dev`, used directly in eLinks' own Alpine Dockerfile) but would need to be built from source on Debian — quickjs-ng's own build is comparatively light (CMake, no exotic deps), so this is a much smaller lift than the NetSurf chain.
   - **SpiderMonkey** requires `mozjs-140` by exact pkg-config name (`dependency('mozjs-140', ...)` in `meson.build` — not a `>=` range). Debian bookworm ships only `libmozjs-102-0`/`-dev` (102.15.1) — five major versions behind what 0.20.0 requires, and pkg-config version-suffixed `.pc` files mean the older package will not satisfy the dependency at all. Building `mozjs-140` from source means building a large slice of Firefox's JS engine (Rust toolchain, `mach`/`moz.build`, historically GB-scale build products) — this is a categorically heavier install than the other two engines and is the backend the maintainer's own doc says segfaults on shutdown.
3. **eLinks itself** builds cleanly via Meson (`meson setup build -Dquickjs=true ... && meson compile -C build && meson install -C build`) once the above are satisfied; no packaging blocker on the eLinks side itself.
4. **Estimated image-size delta**: UNKNOWN — not established with a number. Directionally: MuJS-only is the cheapest path (mujs is a small single/few-file interpreter, ~1.3.2 apt package, no NetSurf-tarball JS-specific overhead beyond libdom/libcss which are required for *any* JS backend since `libcss` is auto-enabled by JS support per `meson_options.txt`); QuickJS-ng adds a light CMake build; SpiderMonkey adds by far the largest layer (comparable in spirit to building a slice of a Gecko/Firefox toolchain) and is explicitly discouraged by the project's own docker recipes, none of which build it.
5. The repo's own `docker/` directory (Dockerfiles for lin64, arm64, alpine-static, etc.) is **not a turnkey reference** for this exercise: the `lin64` Dockerfile is labeled `v0.1d`, targets the old Bellard `quickjs` (not `quickjs-ng`), and stops after cloning eLinks' source without ever building it; the `arm64` Dockerfile (`v0.1c`) is a partial cross-compile scaffold with no JS engine and no final eLinks build step either. Only the **`alpine-static`** Dockerfile is a complete, working, JS-enabled build recipe — and it targets Alpine (musl, `apk`), not Debian/glibc — so it would need porting rather than reuse verbatim.

**Net installation assessment**: feasible but non-trivial — a genuinely multi-stage source build (5 NetSurf libraries + 1 JS engine + eLinks itself) with no Debian package covering any of the browser-engine-relevant pieces (libdom, libcss, quickjs-ng) except the weakest JS backend (mujs). This is a meaningfully heavier build-stage lift than a single `apt-get install`, though the NetSurf chain is at least scriptable and precedented (eLinks' own CI/dev Dockerfiles do it, just not for glibc/Debian).

## Overlap and complement vs Chromium/agent-browser

eLinks and Chromium/agent-browser do not overlap much in capability — they overlap only in the broad category "fetch a URL and get something back". eLinks cannot do anything agent-browser's Chromium backend does well: no real layout, no screenshots, no CDP, no reliable modern-JS execution, no framework-hydrated SPA support. Its plausible niche is narrow and specific: static-content or classic server-rendered pages (docs sites, wikis, blogs, many marketing/news pages) where a full browser is overkill, *if* a workflow only needs a lightweight text extraction and does not need JS-dependent content — which cuts against the original brief's requirement of "still executing JavaScript and rendering the DOM" faithfully. Where eLinks explicitly does *not* help: any SPA, any JS-gated content, any page needing visual/layout fidelity or a screenshot, any workflow wanting structured (Markdown/JSON) output without a separate post-processing step, any workflow needing more than eLinks' seven-command remote-control surface (which itself can't extract content). It would sit alongside, not replace, agent-browser/Chromium — at best a "try the cheap path first, fall back to Chromium" role, and even that role depends on the unresolved question of whether `-dump` reliably executes JS at all before dumping.

## Risks and unknowns

- **Reliability**: the maintainer's own docs admit every JS backend has a known defect class (SpiderMonkey segfaults on shutdown; QuickJS leaks memory on shutdown; MuJS fails some of the project's own tests and lacks missing pieces the maintainer says he doesn't know how to implement). Independent open crash reports (#229, #351, #361) corroborate real, current instability tied to JS/real-world sites, including one (#351) where merely linking SpiderMonkey destabilizes the binary even with JS disabled.
- **Single-maintainer bus factor**: repo activity is real and current (commits into Aug 2026), but appears to be effectively one primary maintainer (rkd77) plus occasional community PRs — no evidence of a funded team or organizational backing.
- **License friction**: GPL-2.0-only is a copyleft license; if the CCY image or its distribution model has any constraint favoring permissive/MIT-style licenses for bundled components, this would need separate legal review (out of scope for this technical research doc).
- **Unverified**: whether `elinks -dump` actually executes ECMAScript to completion before producing its dump (load-bearing for the entire premise of using eLinks for JS-rendered extraction) — not confirmed either way from documentation found.
- **Unverified**: real RSS/startup-latency/concurrency numbers for a JS+libdom+libcss-enabled build — only a stale (2011), pre-JS data point exists.
- **Unverified**: actual image-size delta for a Debian/glibc build of the NetSurf library chain + a JS engine — no number established, only that it requires more from-source build stages than a typical single-library apt dependency.
- **CSS fidelity is qualitatively described** ("meagre", attribute-level rather than real layout) from secondary/community sources corroborated by the project's own framing, but no systematic property-by-property audit against a spec was found.
- **The repo's own Docker samples are inconsistent in maturity** — three of five sampled Dockerfiles are incomplete or stale (versioned `v0.1c`/`v0.1d`, referencing the wrong QuickJS fork, or not building eLinks at all) and only the Alpine-targeted one is a complete, current, working recipe — meaning any Debian-targeted build script would be assembled fresh rather than adapted from a maintained example.
