# Candidate: Chromium Headless Shell (`chrome-headless-shell`)

**Homepage / repo**: No dedicated repo — it is a build artifact of the Chromium project, distributed via [Chrome for Testing](https://developer.chrome.com/docs/automation-and-testing) (`https://github.com/GoogleChromeLabs/chrome-for-testing`) and re-distributed by Playwright's browser-install pipeline. Explainer: [Headless Chrome shell — Chrome for Developers blog](https://developer.chrome.com/blog/chrome-headless-shell). Playwright's docs: [playwright.dev/docs/browsers](https://playwright.dev/docs/browsers).

**Engine**: Full Chromium — Blink (layout/CSS/rendering), V8 (JavaScript), the same multi-process architecture as desktop Chrome (browser/zygote/gpu-process/network-service/renderer). It is **not** a different or reduced engine. Per Chrome's own blog: it is "a lightweight *wrapper* around Chromium's `//content` module" — the wrapper (browser UI, extensions system, some services) is thinner, the rendering/JS engine underneath is identical to regular Chrome/Chromium of the same version.

**License**: Apache License 2.0, per [`GoogleChromeLabs/chrome-for-testing/LICENSE`](https://github.com/GoogleChromeLabs/chrome-for-testing/blob/main/LICENSE) (verified 2026-08-12). Distributed as a Google-branded binary ("Google Chrome", `Copyright 2026 Google LLC`, per the `ABOUT` file inside the downloaded archive) intended specifically for automation/testing use — see [Chrome for Testing announcement](https://developer.chrome.com/blog/chrome-for-testing).

**Status as of 2026-08**: **Actively maintained and shipped with every Chrome release.** Verified directly against Google's live JSON endpoint on 2026-08-12: `stable` channel is Chrome **151.0.7922.138**, and `chrome-headless-shell-linux64.zip` is published for that version at `https://storage.googleapis.com/chrome-for-testing-public/151.0.7922.138/linux64/chrome-headless-shell-linux64.zip` (confirmed via `known-good-versions-with-downloads.json`). It ships on the same release cadence as Chrome itself (days/weeks, not months). Playwright's own packaging of it has churned — see [Risks](#risks-and-unknowns) — but the underlying Google-published artifact is current and healthy. Third-party adoption is happening in 2026: [Quarto (Posit) moved from Puppeteer-bundled Chromium to `chrome-headless-shell` in v1.9, released 2026-04-14](https://opensource.posit.co/blog/2026-04-14_chrome-headless-shell/).

## What it is

Chrome removed its original ("old") headless implementation from the main `chrome`/`chromium` binary in M132 and replaced it in-binary with "new headless" (which runs the real browser UI stack minus a visible window). The **old** implementation — architecturally simpler, fewer subsystems initialized — was not deleted, it was extracted into a **standalone binary**, `chrome-headless-shell`, published through the Chrome for Testing infrastructure since Chrome 120 ([Chrome blog](https://developer.chrome.com/blog/chrome-headless-shell)). Playwright bundles/downloads this exact Google-published artifact as one of its two Chromium flavors: a full `chromium` build (headed-capable) and `chromium-headless-shell` (headless-only), and defaults to the shell whenever a test runs headless without an explicit `channel` ([playwright.dev/docs/browsers](https://playwright.dev/docs/browsers)). `npx playwright install --only-shell` fetches only the shell and skips the ~190 MB headed build.

**Important framing correction**: Playwright does **not** expose `chromium-headless-shell` as a selectable `channel` string (channels are `chrome`, `msedge`, `chrome-beta`, etc.) — you get the shell automatically only by *omitting* `channel` and running headless, or by using `executablePath` to point at it directly, which Playwright's own docs caution against for anything beyond CI use ([independent trial write-up, pdf4.dev](https://pdf4.dev/blog/chrome-headless-shell-vs-puppeteer-chromium-pdf)).

## JavaScript & rendering fidelity

**[MEASURED — this research, 2026-08-12, Debian 12 bookworm x86_64, Chrome/chrome-headless-shell 151.0.7922.138]**: I downloaded the real binary from Google's CDN and ran it directly (no Playwright/Puppeteer wrapper) to verify JS execution independently:

- Served a local HTML page whose `<div id="root">` starts as `LOADING` and is rewritten by a `setTimeout` callback to `JS_EXECUTED_4` (i.e. the literal JS expression `2+2` evaluated at runtime, proving live script execution rather than static HTML parsing). Ran `chrome-headless-shell --virtual-time-budget=2000 --dump-dom <url>` — the dumped DOM showed `<div id="root">JS_EXECUTED_4</div>`, confirming full JS execution, event-loop/timer support, and DOM mutation.
- Took a real screenshot of `https://example.com` (`--screenshot=... --window-size=800,600`) with `DISPLAY` unset and no X server/D-Bus daemon running on the box — produced a valid 15,784-byte PNG on the first try, exit code 0.
- The CDP `/json/version` endpoint reports `"Browser": "HeadlessChrome/151.0.7922.138"`, `"V8-Version": "15.1.206.17"`, `"WebKit-Version": "537.36"` — i.e. driven exactly like normal Chromium over CDP, so any CDP/Puppeteer/Playwright automation code that works against full Chromium works unmodified against the shell.

Because the JS/CSS/layout engine (Blink+V8) is byte-identical to the full browser of the same version, there is no reason to expect it to fail on any modern SPA that full headless Chrome would render correctly, **and independent trial reports corroborate this** — the Quarto migration write-up frames the risk purely as *print-specific* fidelity (see below), not general JS/SPA rendering.

**Known gaps** (from an independent production trial, not vendor material): [pdf4.dev's chrome-headless-shell vs Puppeteer-Chromium PDF trial](https://pdf4.dev/blog/chrome-headless-shell-vs-puppeteer-chromium-pdf) found rendering divergence specifically in **print/PDF-generation paths**: advanced print CSS (`@page` rules, `break-inside: avoid`, running headers/footers, page counters), custom web-font loading timing, and complex multi-page print layouts (pivoted tables, embedded charts, watermarks). The author's explicit conclusion: *"almost certainly not [pixel-identical] for every print CSS feature, every custom font config, every complex layout"* and recommends mandatory pixel-diff testing before production migration — self-reported "looks the same" is called out as unreliable. This is a PDF/print-rendering-path concern; it says nothing against general DOM/JS/screenshot fidelity, which is what an agent scraping/reading task would use.

**Performance-correctness gap, not fidelity gap**: [chromedp/chromedp issue #1075](https://github.com/chromedp/chromedp/issues/1075) — an open, unresolved (as of the fetch) community report that PDF-generation and complex-AngularJS-site processing on `headless-shell` took **2–3× longer** than `google-chrome-stable`/full Chromium across VM, Docker, and GKE deployments, with no root cause identified by chromedp maintainers and no fix landed. This directly **contradicts** the "faster/lighter" framing for at least this workload class and is worth flagging as an open, unexplained risk rather than a settled trade-off.

**Process-model caveat**: the "shell" strips browser chrome/UI, the extension system, and some services — it does **not** collapse Chromium's multi-process model. Both binaries still fork a zygote, a GPU process (software-rendered via SwiftShader in this sandboxed run — no real GPU available), and per-frame renderer processes. The ~3.4× RSS reduction measured above is real and substantial, but a deployment expecting a single lightweight process (as e.g. a Rust-native engine would provide) will still see 5+ OS processes per browser instance.

**Concurrency, sustained-load RSS growth, GPU-available numbers**: **UNKNOWN — not established.** I measured a single idle instance for ~3 seconds; I did not measure RSS growth under many concurrent pages/tabs, under real (non-SwiftShader) GPU, or over a longer session. Treat the numbers above as a floor/idle baseline, not a capacity-planning figure.

## Agent ergonomics

- **No CLI of its own beyond flags** — `chrome-headless-shell` is a raw browser binary. It speaks the **Chrome DevTools Protocol (CDP)** over the `--remote-debugging-port` WebSocket, exactly like full Chromium. Verified: `/json/version` returns a standard CDP handshake (`Browser`, `Protocol-Version: 1.3`, `V8-Version`, `webSocketDebuggerUrl`).
- **No MCP server, no markdown/text extraction built in.** Whatever drives it — Playwright, Puppeteer, `@puppeteer/browsers` + raw CDP, or a hand-rolled WebSocket client — is responsible for DOM→text/markdown conversion, exactly as it would be for full Chromium. This candidate changes *which binary* is under the automation library; it does not itself provide agent-friendly output. It offers `--dump-dom` (prints outer HTML to stdout, verified working) and `--screenshot=path.png`/`--print-to-pdf=path.pdf` as convenience single-shot CLI modes, useful for very simple one-off captures without writing any driver code at all — but these are the *same* flags full `chrome --headless` supports, not something unique to the shell.
- **Driving it from Claude Code/CCY concretely** would mean one of:
  1. Installing Playwright (or just `@puppeteer/browsers`) as a Node dependency and using its page/DOM APIs — pulls in a JS automation library that doesn't otherwise exist in the CCY stack today (CCY's `agent-browser` is a pure-Rust CDP client with **no** Node/Playwright dependency — see [Overlap](#overlap-and-complement-vs-chromiumagent-browser)).
  2. Driving the raw CDP WebSocket directly (no framework) — more code to own, but zero new npm dependency.
  3. Using the binary's single-shot CLI flags (`--dump-dom`, `--screenshot`, `--print-to-pdf`, `--virtual-time-budget`) as a subprocess for simple capture tasks with no session/interactivity needed — cheapest integration path, verified working in this session, but no clicking/typing/multi-step interaction (those need CDP driving).
- **Token budget**: `--dump-dom` emits raw HTML (verified — includes the `<script>` tag source, comments, etc.), not markdown/plain-text. For agent consumption at scale this would need the same HTML→markdown reduction step `agent-browser`'s `extract markdown`/`extract text` commands already provide — the shell does not solve the token-budget problem on its own.

## Installing on Debian 12 bookworm (glibc 2.36, amd64, root, node LTS)

**Verified directly in this session**, on the actual target OS/arch (Debian 12 bookworm, glibc 2.36-9+deb12u14, x86_64):

```bash
curl -sL -o chs.zip \
  "https://storage.googleapis.com/chrome-for-testing-public/151.0.7922.138/linux64/chrome-headless-shell-linux64.zip"
unzip -q chs.zip
./chrome-headless-shell-linux64/chrome-headless-shell --version   # or use it directly, see below
```

- **Prebuilt binary exists** for linux64 — no compiler stage needed in the Dockerfile, no build-from-source.
- **`ldd` reported zero missing shared libraries** on this box — but this box already has the full Chromium runtime-library set installed (matching the CCY Dockerfile's existing "Install system dependencies for Chromium" apt block: `libnss3`, `libnspr4`, `libatk1.0-0`, `libatk-bridge2.0-0`, `libcups2`, `libdrm2`, `libxkbcommon0`, `libxcomposite1`, `libxdamage1`, `libxfixes3`, `libxrandr2`, `libgbm1`, `libasound2`, `libpango-1.0-0`, etc. — `/workspace/files/var/local/claude-yolo/Dockerfile` lines 132–151). The shell's actual link table (`ldd`, captured this session) needs `libglib-2.0`, `libgobject-2.0`, `libnspr4`, `libnss3`, `libatk-1.0`, `libatk-bridge-2.0`, `libdbus-1`, `libX11`, `libXcomposite`, `libXdamage`, `libXext`, `libXfixes`, `libXrandr`, `libgbm`, `libexpat`, `libxcb`, `libxkbcommon`, `libudev`, `libasound`, `libatspi`, `libXrender`, `libdrm`, `libwayland-server`, `libXi` — **this is a strict subset of libraries the CCY Dockerfile already `apt-get install`s for `agent-browser`'s Chrome**. Concretely: **no new apt packages would be needed** to run `chrome-headless-shell` in the existing CCY image, only the `fonts-liberation` package the shell's own `deb.deps` lists, which is also already a dependency of the existing headed-Chrome setup in most such images (not independently verified present in the CCY Dockerfile — worth a explicit check before shipping).
- **Install-size delta**: downloading only the shell costs **~115 MiB compressed / ~262 MB unpacked**, measured directly. This would be *additive* to the image, not a replacement — the CCY container's `agent-browser` already needs a full headed-capable Chrome for its primary (headed, Wayland-composited) use case, so shipping the shell as a second engine adds its full size on top rather than swapping anything out.
- No `npm install` of Playwright is required to obtain the binary — it can be fetched with a plain `curl`+`unzip` (as done here), or via `npx @puppeteer/browsers install chrome-headless-shell@stable`, entirely independent of whether Playwright is used to drive it afterward.

## Overlap and complement vs Chromium/agent-browser

**Material finding that revises the framing given in the task brief**: the brief describes the CCY container's existing browser as "`agent-browser` (npm, Playwright-based Chromium)". Checked directly against the actual CCY Dockerfile in this repo (`/workspace/files/var/local/claude-yolo/Dockerfile:154-164`) and the upstream project it installs (`npm install -g agent-browser` → [vercel-labs/agent-browser](https://github.com/vercel-labs/agent-browser)):

- `agent-browser`'s own README states plainly: **"No Playwright or Node.js required for the daemon"** — it is a **pure-Rust CLI + daemon** that speaks CDP directly, and by default downloads **full "Chrome for Testing"** (the same distribution channel `chrome-headless-shell` comes from) into `~/.agent-browser/browsers/`, not a Playwright-managed Chromium.
- `agent-browser` **already has a pluggable `--engine` flag** supporting `chrome` (default, Chrome for Testing via CDP) and **`lightpanda`** (a distinct, non-Chromium engine) — i.e. the tool the CCY container already ships has an existing extension point for exactly the "second lightweight engine" problem this plan is investigating, independent of whether `chrome-headless-shell` is chosen.

Given that, `chrome-headless-shell` and the CCY container's Chrome are:

- **Same engine, same distribution infrastructure** (Chrome for Testing/`storage.googleapis.com/chrome-for-testing-public`), **different build flavor** of the identical Chromium version. It is not a different rendering engine in any sense — see [Engine](#candidate-chromium-headless-shell-chrome-headless-shell) above.
- **Overlap**: near-total at the engine level (Blink/V8, CDP surface, JS/CSS fidelity) — anything the shell renders correctly, full Chrome renders correctly too, and vice versa, for non-print workloads.
- **Complement**: the measured ~3.4× idle-RSS reduction and ~40% smaller unpacked size mean it is a legitimate "cheaper mode" of the *same* engine for headless-only, no-GPU, no-extension, no-visible-window tasks — conceptually similar to giving `agent-browser` a `--headless-shell` engine variant alongside its existing `chrome`/`lightpanda` choices, rather than a genuinely separate technology stack.
- If the goal is a **architecturally different, non-Chromium engine** (smaller attack surface, different process model, genuinely different footprint class), this candidate does not deliver that — `lightpanda` (already referenced by `agent-browser`'s own `--engine` flag) or another non-Chromium candidate would be the one to research for that goal.

## Risks and unknowns

- **Playwright's *own* packaging of this artifact has been unstable across releases**, independent of Google's underlying artifact being fine: [GitHub issue #33885](https://github.com/microsoft/playwright/issues/33885) ("Cannot install chromium-headless-shell"), [#34508](https://github.com/microsoft/playwright/issues/34508) (reported entirely absent from `browsers.json` in Playwright 1.50.0, present in 1.49.1, closed "not planned" with no maintainer explanation found), and a real user-visible version-skew bug in `agent-browser` itself ([vercel-labs/agent-browser#107](https://github.com/vercel-labs/agent-browser/issues/107): `install` fetched build v1194 but `open` looked for v1200). None of these are fatal, but they show the Playwright-side packaging/versioning of this exact artifact is not rock solid — a reason to prefer fetching the Google-published Chrome-for-Testing artifact directly (as this research did) over depending on Playwright's re-packaging of it.
- **Unresolved 2–3× slowdown report** for PDF/complex-page workloads on `headless-shell` vs full `google-chrome-stable` ([chromedp/chromedp#1075](https://github.com/chromedp/chromedp/issues/1075)), open with no maintainer explanation — a caution flag on the "lighter is always faster" assumption for CPU-bound rendering work, even though this research's own idle-RSS and cold-start numbers looked favorable.
- **Print/PDF-path rendering fidelity gaps** documented by an independent production trial (see [JS & rendering fidelity](#javascript--rendering-fidelity)) — real for `--print-to-pdf`/complex CSS-print workflows; not established as a problem for general page-read/screenshot/scrape agent workloads, which is the more likely agent use case.
- **No CLI/MCP/agent-output layer of its own** — every ergonomics win has to be built by whoever drives it (Playwright, raw CDP, or the existing `agent-browser`), so adopting this candidate is an integration project, not a drop-in tool install.
- **Google-branded distribution, not stock open-source Chromium** — governed by the Apache-2.0 `chrome-for-testing` LICENSE plus (per the archive's `ABOUT` file) an implicit Google Chrome branding/ToS context ("chrome://terms" referenced inside the binary's own about page) since it ships as "Google Chrome" rather than unbranded Chromium. Not independently verified whether any Chrome ToS beyond the Apache-2.0 LICENSE.txt actually constrains automated/server use for Chrome for Testing builds specifically — [Google's own docs](https://developer.chrome.com/docs/automation-and-testing) state it exists "purely for browser automation and testing purposes," which is consistent with this use case, but the exact legal boundary is **UNKNOWN — not established** beyond that.
- **RSS/concurrency numbers above are a single idle-instance sample on a shared/virtualized box**, not a rigorous multi-run benchmark — good enough to show order-of-magnitude and relative comparison, not a capacity-planning number.
- **`fonts-liberation` package presence in the CCY image was not verified** — it's declared as a `chrome-headless-shell` runtime dependency in the archive's own `deb.deps` and was reported `MISSING` when checked on this research sandbox (which is a different image than CCY's own Dockerfile-built image); whoever implements this should confirm directly against CCY's actual built image rather than assume from this sandbox's package list.
