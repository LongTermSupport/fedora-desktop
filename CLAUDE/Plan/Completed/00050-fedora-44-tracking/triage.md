# Triage — Fedora 44 Migration (Plan 00050)

**Source**: 6-dimension multi-agent research sweep, 2026-06-12 (workflow `wf_fd40dad5-64a`; 6 Fable agents). Research only — no fixes made.
**Findings**: 55 total — 7 high, 14 medium, 25 low, 9 info.
**Research docs**: one per dimension under [research/](research/); each finding ID below links to its evidence section.
**Tracking plan**: [PLAN.md](PLAN.md). This phase deliberately stops at research + triage — no execution/action plan yet.

## Fedora 44 baseline (confirmed via live research)

- **Released** 2026-04-28 (GA compose 44-1.7), ~2 weeks late.
- **GNOME 50** "Tokyo" (Shell major `50`) — not 49. X11 session removed.
- **Kernel** 6.19.x at GA, rolled to **7.0.x** in stable updates by mid/late May 2026 — a June 2026 migration lands on 7.0.x.
- **Python stays 3.14** (the 3.14 jump was F43; no interpreter change in F44). PEP 668 EXTERNALLY-MANAGED marker still **not** shipped.
- **DNF5 migration complete** (PackageKit on libdnf5, system-upgrade built into dnf5). Toolchain: GCC 16.1, glibc 2.43, CMake 4.2.
- Third-party F44 availability (as of 2026-06-12): RPM Fusion published, Docker CE `44/` published, NVIDIA CUDA `fedora44` published (new GPG key), DisplayLink v6.2.0-1 ships fedora-44 RPMs, `ganto/lxc4` Copr has fedora-44 — **but `pgdev/ghostty` Copr has no F44 build**.

## How to read this

- **Severity** = migration impact: **high** breaks the F44 install or a core deploy/runtime flow; **medium** likely breaks or needs a deliberate change; **low** minor/verify-on-F44; **info** observation, no migration action strictly required.
- **Related** — the same root cause was independently surfaced by more than one agent (fix once, close both).
- Findings are forward-looking by nature: many are "verified available for F44, re-confirm at migration time" rather than known-broken today.

## Top themes

1. **The bump is one line — but hand-maintained duplicates drift silently.** `vars/fedora-version.yml` is the single canonical value and every gate reads it correctly ([VER-01](research/version-refs.md#ver-01-canonical-fedora_version-value-in-varsfedora-versionyml), [BOOT-01](research/install-bootstrap.md#boot-01-fedora_version-43-pin-gates-the-whole-bootstrap-and-hard-fails-on-f44)), so the primary change is `fedora_version: 44`. The danger is three ungated duplicates: `SETUP_BRANCH="F43"` in `ks.cfg` (untemplated on the build-iso path — [VER-03](research/version-refs.md#ver-03-hardcoded-f43-branch-literals-in-kickstart-and-iso-build-path)/[BOOT-02](research/install-bootstrap.md#boot-02-kscfg-hardcodes-f43-in-version-marker-and-setup_branch-with-no-substitution-on-the-build-iso-path)), `FEDORA_VERSION="43"` in `docker-in-lxc` ([VER-04](research/version-refs.md#ver-04-docker-in-lxc-duplicates-the-canonical-version-as-fedora_version-43)), and the f43-pinned darktable dist-git commit ([VER-08](research/version-refs.md#ver-08-darktable-build-pins-an-f43-dist-git-commit-while-gating-on-fedora_version)/[PKG-10](research/packages-repos.md#pkg-10-darktable-mock-build-chroot-must-move-to-fedora-44-x86_64)).
2. **GNOME 50 silently disables all three custom extensions.** Their `metadata.json` lists `shell-version` only up to `49`, and GNOME 50 enforces version validation by default → all refused as OUT_OF_DATE ([EXT-01](research/gnome-extensions.md#ext-01-custom-extension-metadata-lacks-shell-version-50-so-all-three-are-disabled-on-fedora-44)). The playbooks' enable/verify steps only read the gsettings list, so they report green while the extensions are dead ([EXT-05](research/gnome-extensions.md#ext-05-playbook-enable-and-verify-steps-cannot-detect-out_of_date-extensions)) — a fail-fast violation masking the break.
3. **dnf5 completion breaks two core-play flows.** `dnf config-manager --enable` is DNF4-only syntax that dnf5 rejects, halting `play-rpm-fusion` ([PKG-01](research/packages-repos.md#pkg-01-dnf5-rejects-config-manager---enable-in-play-rpm-fusion)); the `pgdev/ghostty` Copr publishes no F44 build, halting `play-terminal-emulators` ([PKG-02](research/packages-repos.md#pkg-02-ghostty-copr-pgdevghostty-has-no-fedora-44-builds)). dnf5 itself is otherwise compatible with the repo's toolchain ([PKG-12](research/packages-repos.md#pkg-12-dnf5-completion-in-f44-is-compatible-with-the-repos-ansible-toolchain)).
4. **Kernel versionlock + out-of-tree modules are the upgrade-window risk.** fc43 kernel versionlocks can block or half-install the fc44 kernel — the exact mechanism behind the repo's own 2026-05-21 ipu6 incident ([HW-01](research/hardware-kernel.md#hw-01-kernel-versionlock-from-previous-release-can-block-or-half-install-the-f44-kernel)). Around it: akmod-nvidia build-window risk on 6.19/7.0 ([HW-02](research/hardware-kernel.md#hw-02-akmod-nvidia-build-breakage-window-on-f44-kernels--gate-the-upgrade-timing)), the CUDA repo's new 610.x driver vs the exclude fence ([HW-03](research/hardware-kernel.md#hw-03-nvidia-cuda-fedora44-repo-now-ships-driver-610x-packages--re-verify-the-exclude-fence)), evdi vs kernel 7.0 ([HW-04](research/hardware-kernel.md#hw-04-displaylink-fedora-44-rpm-exists-but-evdi-11416-vs-kernel-70-needs-build-verification)), akmod-VirtualBox ([HW-07](research/hardware-kernel.md#hw-07-akmod-virtualbox-is-the-most-fragile-module-on-a-new-kernel-series)).
5. **NVIDIA CUDA repo exists, but the GPG key file changed.** The `fedora44` CUDA repo is live, but ships key `73CD9B30.pub` while the playbook hard-codes `1940C73E.pub`, which 404s under `fedora44/` — breaking the cuda-toolkit install after the bump ([PKG-03](research/packages-repos.md#pkg-03-nvidia-cuda-fedora44-repo-exists-but-the-gpg-key-file-changed)/[HW-03](research/hardware-kernel.md#hw-03-nvidia-cuda-fedora44-repo-now-ships-driver-610x-packages--re-verify-the-exclude-fence)).
6. **Branch-per-version process gap.** No F44 branch exists on origin yet, so no bootstrap entry point can succeed on F44 ([BOOT-03](research/install-bootstrap.md#boot-03-f44-branch-does-not-exist-on-origin-so-branch-per-version-bootstrap-cannot-start)); and the empty `optional/untested/` dir means a bump implicitly asserts every optional play works on F44 ([VER-10](research/version-refs.md#ver-10-runbash-dynamic-gate-and-the-untested-playbooks-branch-cut-process)).
7. **Docs are already a release stale.** README/installation still direct fresh installs to checkout **Fedora 42** ([VER-05](research/version-refs.md#ver-05-stale-fedora-42-references-in-core-onboarding-docs)/[BOOT-07](research/install-bootstrap.md#boot-07-stale-f43f42-version-examples-in-install-docs-and-usage-text)), plus a copy-paste-broken ISO example in `build-iso.bash`, and GNOME/version comments point future API checks at the wrong source tree ([EXT-06](research/gnome-extensions.md#ext-06-stale-gnome-version-references-in-docs-and-playbook-comments)/[VER-11](research/version-refs.md#ver-11-forward-safe-version-comments-that-need-re-verification-only)).
8. **No Python interpreter break.** F44 keeps Python 3.14, so pipx venvs and stdlib scripts survive ([PY-06](research/python.md#py-06-repo-python-consumers-are-stdlib-only-and-unaffected-by-the-f43-to-f44-python-transition)). The real Python risk is the GCC 16.1 toolchain hitting source builds: stale pyenv pins ([PY-01](research/python.md#py-01-stale-pyenv-version-pins-risk-source-build-failures-under-the-gcc-161-toolchain)) and the now-obsolete scipy==1.15.2 source-build workaround ([PY-02](research/python.md#py-02-pinned-scipy-1152-source-build-workaround-is-obsolete-and-fragile-on-f44)).
