## 09:20 · finding · T3.5 — CAUSE CONFIRMED: the play generates an EMPTY password

The acceptance report landed and named the bug by contradicting itself:

```
FAIL  credential file is missing RCLONE_RC_USER and/or RCLONE_RC_PASS
      keys present:
        RCLONE_RC_USER
        RCLONE_RC_PASS
```

Both keys ARE present. So the check was not testing presence, it was testing
non-emptiness via `[ -n ... ]` — one of the values is empty. Everything else in
the report is consistent with that and only that:

- unit config PASSED both checks — no `--rc-no-auth`, `EnvironmentFile` present,
  so the deploy DID run and DID render the new unit (`active since 10:37`)
- `config/dump` refused unauthenticated — but see the false-pass note below
- authenticated access could not even be attempted

**Root cause, read from the play, not inferred.** Two tasks in sequence:

1. `ansible.builtin.file` with `state: touch` created `.rc-pass` — **empty**.
2. `lookup('ansible.builtin.password', '.../.rc-pass', ...)` then ran.

The `password` lookup generates a value only when the store is **absent**; when
the file exists it reads the value back (that is what makes the credential
stable across runs). An empty store is read back as an empty password and is
never regenerated. So every deploy has rendered `RCLONE_RC_PASS=` with no value,
the mount started with `--rc-user` set and `--rc-pass` empty, and the RC refused
everything.

This also finally explains the 26-07-30 observation that the live RC "refuses
everything" — that was read at the time as the *pre-deploy* unit lacking a
credential. It is now clear the post-deploy unit does too, for a different
reason.

**Second bug found while fixing the first.** The final systemd task uses
`state: started`, which is a no-op on an already-running unit; `daemon_reload`
only re-reads unit definitions. So a changed `ExecStart` or a changed
`EnvironmentFile` sat on disk while systemd kept running the OLD command line
and the OLD environment until the next boot. Even with a correct password, a
re-run would not have taken effect. There were no handlers in this play at all.

Fixes to `play-rclone.yml`:

- deleted the pre-emptive `state: touch` — the lookup owns creation now
- added stat + `state: absent` recovery so an **already-empty** store is removed
  and regenerated (without this, re-running on this host would stay broken)
- pinned owner/mode on the store *after* the lookup instead of before
- added a hard `assert` that the store is non-empty — fail fast rather than
  deploy a mount whose RC refuses everyone
- added a `restart rclone mounts` handler, notified by both the unit-file copy
  and the credential copy, so a change actually takes effect

The handler restarts the mount, which interrupts the VFS write-back queue — safe
only because `deploy.bash` already refuses to run while `ftp-camera` is alive.

**Two defects in my own acceptance gate, fixed:**

- it collapsed "key absent" and "key present but empty" into one message, which
  is what produced the self-contradicting output above. Now reports per key,
  distinguishes the two, and prints the byte size of `.rc-pass` — the direct
  evidence.
- check 4 was a **false pass**. "Unauthenticated `config/dump` refused" is not
  evidence that auth is configured correctly: an RC that is simply broken
  refuses everyone and passes it. The gate now cross-checks and says so
  explicitly when the unauthenticated call and the authenticated call both fail.

`triage.bash` was not run — no `logs/rclone-rc-auth-triage.log` exists, and it
writes one unconditionally. Not needed in the end; the acceptance report plus
the play source were enough.
