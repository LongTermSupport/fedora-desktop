## 19:55 · decision · P2 — find the key by id, never by description

First cut of the helper matched installed keys on a summary substring
(`--match google`). Writing the play showed what that means in practice: the
verdict feeds `rpm -e`, and "any installed key whose description mentions google"
is not the same set as "the key this play manages". A host with a Google Cloud
SDK key would have had it deleted to make room.

Changed to derive the identity from the published key itself: take its primary,
take rpm's short id (`7721F63BD38B4796` → `d38b4796`), and match only packages
rpm named `gpg-pubkey-d38b4796-*`, anchored on the trailing separator so
`d38b4796ab` is not caught. Nothing in the invocation names Google any more.

That also changed the answer for a key sitting at that id with a *different*
primary — a short-id collision. It was `refresh`, i.e. remove it. It is now
`import`: our key is absent, and the one that is there is not ours to remove.

## 20:35 · finding · P3b — both safety claims were breakable, and the review broke them

`qa-reviewer` came back FIX-BEFORE-MERGE. I had asked it specifically to attack the
two things this plan asserts, and it demonstrated both rather than reasoning about
them. Neither was theoretical.

**1. A two-certificate published key refreshes for ever.** `key_ids` read the primary
from the first certificate but accumulated `sub:` records from every certificate in
the file. The reviewer drove three consecutive runs against a two-cert bundle with a
fully current installed key and got `refresh` every time, naming the second
certificate's subkey as "missing".

This is the precise failure the helper exists to prevent — the docstring's own
"removing unconditionally would report `changed` on every run for ever" — reintroduced
by the parser. And the trigger is the scenario `PLAN.md` already contemplates: a vendor
rotating a primary ships a transitional two-cert bundle. Worse, the test for this
shape existed and asserted only the primary half; its docstring even says "a keyring
export can hold several keys". The test named the risk and then checked the wrong half.

Google's file holds one certificate today, so this was latent rather than live — the
owner's laptop was never going to churn. Verified before saying so.

**2. The erase set was identity-checked for one member and erased in full.** With two
packages at short id `d38b4796`, `main` made exactly ONE description query
(`envelopes[0]`) and printed BOTH names as `RPM-KEY-ENVELOPE`, so both reached
`rpm --erase`. The whole stranger-at-the-same-id branch — the thing I wrote up as the
reason for identifying keys by id rather than description — only held when the
stranger happened to be listed first. `installed_envelopes`' own docstring says
multi-envelope is the EXPECTED state on an upgraded host.

So the module documented a safety property it did not have. The decision was right and
the plumbing did not implement it.

Fixed by moving the erase set into the verdict: `needs_refresh` now takes every package
found at the id, matches each against the published primary itself, and returns the
names to erase. Nothing downstream re-derives that list, so there is no second place
that could disagree with the thing that did the checking.

**3 (nit, but it drives the same failure).** Expired and non-signing subkeys were
counted. Five of Google's eight are expired — measured, not assumed — so a host missing
only those got an erase-and-reimport described as "missing signing subkey(s) … so it
cannot verify what the repo now ships", which is untrue of an expired key. gpg's
validity and capability fields are now read, which drops the count from 8 to 3 and
keeps the actual signer.

Verified after the fix, against the real key and a real two-cert bundle rather than
fixtures:

```
REAL published key
  usable signing subkeys: 3 of 8 records
  signer FD533C07C264648F retained: True
  expired ones dropped: True
TWO-CERTIFICATE BUNDLE
  pub records in input: 2
  subkeys attributed: 3 (equals the single-cert count)
  three consecutive runs -> ['none', 'none', 'none']
```

## 20:38 · decision · T3.4 — the play had no post-condition, so give it one

The reviewer's sixth point is the one I would have missed longest: nothing asserted the
re-import actually took. The erase reports success, the import reports success, and if
the installed key still lacks the subkey afterwards the next run simply finds the same
deficiency — erase, import, green, for ever.

That is not hypothetical here. rpm stores the key as a `%{description}`, and if that is
a normalised re-export the difference might never close. Task 4.2 was the only thing
standing between that and silence, and Task 4.2 is a human remembering to run something
twice.

So the play now re-asks the helper after the import and fails unless the answer is
`none`. It costs one command and converts a silent forever-loop into a first-run
failure with a reason attached.

## 21:05 · action · T3b.4 — the triage script rebuilt, and its own claim made true

The review's third finding was the sharpest, because the defect was in the thing
written to prevent that defect. `probe()` existed specifically to separate "command
failed" from "ran cleanly and found nothing" — its comment says collapsing them
"reports a host it never actually asked about" — and then collapsed them, because
grep exits 1 on no match and every non-zero exit was treated as failure. Section 3's
comment says "a MISSING key here is a real finding"; that finding was printed as a
broken command.

Fixed by making the caller declare what a non-zero exit means: `probe` for commands
where every failure is a failure, `probe_match` for grep and `rpm -q`, whose exit 1
means "ran fine, matched nothing". Exit ≥ 2 stays a failure either way, which is also
grep's own documented contract.

The rebuild also put it on `_planlib.inc.bash` — `plan_init`, `plan_gather_leg` per
section, `plan_start_log` — and gave it a real `plan_require_host` guard instead of a
HOST-ONLY comment, R2 being explicitly "a guard, not a comment". Verified firing

below comes from this host's rpm keyring, /etc/pki/rpm-gpg and dnf, none of which a

FIX-BEFORE-MERGE, 8 findings, report in `subagent-reports/260915-qa-reviewer-opus-5.md`.
All acted on. The destructive path — the `rpm --erase --allmatches` this plan exists to

That is the evidence those fixes needed and had not had.

**The finding that matters is about the package, not the play.** Chrome's own `%post`
re-adds its repository. From Chromium's packaging source: `chrome.spec.template` creates
`/etc/default/google-chrome` with `repo_add_once="true"` **if absent**, sources it, and
calls `install_yum()`; `rpm.include`'s `install_yum()` then unconditionally writes
`/etc/yum.repos.d/google-chrome.repo` with
`gpgkey=https://dl.google.com/linux/linux_signing_key.pub`. Nothing in the rpm path ever
sets the flag back to false.

Two things follow, and both were live:

- On any host where Chrome has never been installed — a **fresh F44 install**, which is
  issue #45's own scenario — run 1 installs Chrome and the scriptlet overwrites the repo
  file. Run 2's `Add Google Chrome Repository` reports **changed** putting it back, and
  so does every run after a Chrome upgrade. Task 4.2 asks precisely whether a second run
  is clean, so it would have failed as written, on the machine most likely to be tested.
- The comment justifying `gpgkey: file://` said it meant dnf "cannot end up validating
  against a different fetch of the key than the one this play reasoned about". After the
  scriptlet runs, dnf validates against a fresh network fetch. The comment described the
  intent; the state of the host decided whether it was true.

The fix is one task before the install: write `/etc/default/google-chrome` with
`repo_add_once="false"`. The scriptlet only creates that file when absent and only calls
`install_yum` when it reads true, so the play becomes the owner of the repo file rather
than a participant in a fight with the package.

### The second false statement was mine, in the triage

`probe-chrome.bash` told the operator that a key file differing from the published one
"does not by itself mean that task reports changed". False. `get_url` takes its
already-present early exit **only when `checksum:` is set**, and this task sets none —
so it issues a conditional GET with `If-Modified-Since` from the dest mtime, and a 200
replaces the file and reports `changed`. An operator following Task 4.2 would have read
a correctly self-healing refresh as a regression. Reworded to say so, and the prediction
table now names `Ensure gnupg2 Is Available` (the task's actual name) and carries the
two repo-ownership rows, with a new section 2.4 that reads them.

### Marker literals: the mutation that all 40 tests survived

Renaming `ACTION_MARKER` left the whole suite green while breaking the playbook, because
every test reads the constant rather than the text the play greps for. There are now
three cases that read `play-browsers.yml` itself and assert the literals appear in its
`failed_when` and its erase-loop selector. Confirmed by running the same mutation: 2
failures where there were 0.

Also done: `tasks/ensure-gnupg2.yml` replaces two inline declarations that had already
drifted (`package` in one, `dnf` in the other, a `when:` on only one), following the
