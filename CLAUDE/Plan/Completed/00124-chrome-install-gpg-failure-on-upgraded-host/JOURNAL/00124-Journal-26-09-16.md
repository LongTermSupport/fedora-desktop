## 16:55 · action · deploy and acceptance written; idempotency is the second run, not a --check

Both scripts now exist, so this plan's HOST items are runnable rather than described.

**`deploy.bash` runs the play TWICE, and that is the design rather than caution.** A `--check`
re-run cannot stand in for the second real run: `--check` reports what WOULD change against the
current state, and the very tasks under test — a key erased from and re-imported into the rpm
keyring — are ones whose check-mode prediction and real second-run behaviour can differ. The
idempotency claim is a property of the second convergence, so the second convergence is what
the script does.

`acceptance.bash` carries eight COVERAGE-registered checks and proves the key WORKS rather than
that it is present: it fetches the package the repo ships and has `rpm --checksig` verify it. A
key sitting in the keyring is not evidence that anything verifies against it, which is the
shape of the original failure.

Two honest limits, both recorded rather than papered over. The dnf query-format tags could not
be confirmed here — this container has no `dnf` and no `rpm` — so check 6 degrades to
could-not-establish printing dnf's raw answer if the format is not what it expects, and keeps
that distinct from the real finding (dnf genuinely not offering the package from the
`google-chrome` repo, which is a FAIL). The first host run may need one iteration there. And
closing issue #45 is a `gh` action, not a check: the ACCEPTED message says so rather than
letting a green verdict imply it was covered.
