# Plan 00124 — Journal, 2026-09-17

## 08:43 · fix · the key was never missing; the helper was looking it up by a name rpm renamed

Task 4.2's deploy run aborted at `Verify The Imported Google Key Is Now Current`. The helper
exited 0 and printed `RPM-KEY-ACTION import` with the reason `no matching key is installed`, and
the post-condition requires `none`, so leg 1 stopped.

The verdict was wrong, and the post-condition was right to refuse it. Three facts settle it, and
none of them needed the host:

1. Google's published key still leads with primary `7721F63BD38B4796` — fetched and read here.
   There is no rotation, so `short_id` still derived `d38b4796` exactly as it always has.
2. The helper's reason was the branch it takes when the listing matched **nothing at all** — not
   the branch for a stranger sitting at the same id. So `rpm -qa gpg-pubkey` returned no line
   beginning `gpg-pubkey-d38b4796-`.
3. In the same run, `Import Google Chrome Signing Key` reported **ok**, not changed.
   `rpm_key` only reports that when `is_key_imported` finds the published key id in field 5 of a
   `pub:` line of an installed key's armour (read from ansible's own module source).

Facts 2 and 3 together say a key whose primary IS `7721F63BD38B4796` is installed, under a
package name that does not begin `gpg-pubkey-d38b4796-`. Task 4.1 corroborates it: Chrome
installed on this host with `gpgcheck` on, which is impossible unless Google's key is in the
keyring. **The key was present and working the whole time.**

So the defect is the helper's identity test. `installed_envelopes` selected packages by rpm's
`%{version}`, which is the primary's short id under rpm 4 and 5 and the key's **full
fingerprint** under rpm 6 — which is what Fedora 44 ships. Identity was being decided from a
string rpm is free to rename between major versions, and rpm renamed it.

The fix is to stop filtering by name. `installed_envelopes` now returns every installed
`gpg-pubkey` package, each one is opened, and `needs_refresh` decides identity from the primary
parsed out of its own armour — which is the one thing rpm cannot rename. `short_id` had no
caller left and is gone, along with the "stranger at the same short id" reason: with identity
taken from the armour, other vendors' keys are simply not ours, and the safety property they
existed to narrate (only a key whose primary matches can reach the erase set) is unchanged and
still tested.

`probe-chrome.bash` and `acceptance.bash` carried the same derivation, so both would have
vouched for the fix while checking the wrong thing. Both now select by armour too.
`acceptance.bash` already identified each envelope by its primary — it was only the pre-filter
that was wrong — and it counts other vendors' keys rather than narrating one line each, because
unfiltered that is dozens of lines burying the verdict.

**The play is unchanged, deliberately.** Its `failed_when` is not a wrong predicate and there is
no ordering bug: the import is at line 126 and the verify at line 136, and requiring `none`
after an import is exactly what catches an import that did not take. It did its job — it refused
to report success on a host its own gate said had no key. Nothing here weakens it.

One residual hazard, recorded rather than fixed: `rpm_key`'s presence test and the helper's are
still two different tests, and whenever they disagree with nothing for the erase loop to remove,
the play cannot converge — it fails identically on every run, which is what just happened. After
this fix both are identity-based over the whole keyring, so they agree; ansible's remains looser
(a substring match over every line, `sub:` records included). Replacing `rpm_key` with a gated
`rpm --import` would close it, but that is deploy-critical surgery on a path no container can
exercise, against a hazard this fix has already made near-unreachable. Left alone on purpose.

Evidence: the two new end-to-end tests drive a fingerprint-named package all the way through
`main` — one proving it is found and reports `none`, one proving a stale one reaches the erase
list under the name rpm actually installed. Both failed before the change. 1567 helper tests and
`qa-all.bash` (971 files, 82 playbooks syntax-checked) are green.

Not established here: the exact rpm 6 naming on the affected host. That a key with Google's
primary is installed under a non-short-id name is proven; that the name is the full fingerprint
is inference from rpm 6's behaviour. It does not change the fix — the fix stops depending on the
name in either direction — but `triage.bash` section 2 will now print the real names.

## 09:47 · finding · P4 — the inference above is now a measurement, and the plan closes

The entry above flagged one thing as inference rather than fact: that rpm 6 names the package
by the full fingerprint. The host batch settles it. Acceptance check [2]:

```
PASS  gpg-pubkey-eb4c1bfd4f042f6dddccec917721f63bd38b4796-570c8cd3
      carries Google's primary and signing subkey FD533C07C264648F
```

`…7721f63bd38b4796` is the primary's short id sitting at the *tail of a full fingerprint*,
under a package name a short-id lookup could never match. That naming **is** the defect: the
helper matched nothing and reported a missing key that was installed and verifying packages
throughout.

**Task 4.2, the plan's last blocking question, is answered.** `deploy.bash` runs the play
twice by design — leg 1 converges, leg 2 IS the second run the task asks for:

```
localhost : ok=14  changed=2  unreachable=0  failed=0  skipped=1
localhost : ok=14  changed=0  unreachable=0  failed=0  skipped=1
```

The second line is the load-bearing one. The refresh path **erases** a key and re-imports it,
so a broken idempotency gate would not fail — it would erase and re-import for ever while
reporting green every time. `changed=0` is what rules that out, and no container could have
shown it.

`COVERAGE: 8 of 8 checks executed (23 assertion(s) passed, 0 failed, 0 unestablished)` —
ACCEPTED. Check 7 closes the last criterion with `RPM-KEY-ACTION none` on the second leg,
which is precisely the run where an erase-and-reimport loop would have surfaced.
