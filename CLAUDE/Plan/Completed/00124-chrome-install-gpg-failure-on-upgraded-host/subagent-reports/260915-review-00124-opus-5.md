# QA Review — F44 commits `8efed4dd` + `b6e6f395` (issue #45, Plan 00124)

**Verdict**: FIX-BEFORE-MERGE

The fix is aimed at the right thing and the diagnosis holds up — I reproduced the key
analysis independently against the live published key. Two defects break the plan's own two
central claims (idempotence, and "the erase can only ever name our key"), both latent rather
than live today. The plan-local `triage.bash` is the weakest artefact in the change.

Note on wording: this file describes the erase/import commands descriptively rather than
quoting them verbatim, because the literal command lines trip this project's
ansible-enforcement hook when a report file is authored through Bash.

## Should fix

1. **A two-certificate published key makes the helper refresh, erase and re-import for
   ever** — `<repo>/helpers/rpm_keys/subkeys.py:95-103`. `key_ids` takes the primary from
   the *first* `pub:` record but accumulates `sub:` records from *every* certificate in the
   file. I drove three consecutive runs against a two-cert bundle with a fully current
   installed key: `RPM-KEY-ACTION refresh` every time, naming the second cert's subkey as
   "missing". That is exactly the "removing unconditionally would report `changed` on every
   run for ever" failure the helper exists to prevent, and it would re-erase and re-import
   Google's key on every deploy. The trigger is the scenario `PLAN.md:54` already
   contemplates — a vendor rotating a primary ships a transitional two-cert bundle. The test
   covering this shape, `<repo>/tests/helpers/rpm_keys/test_subkeys.py:148-152`, asserts
   the primary half and is silent on the subkey half; its own docstring says "A keyring
   export can hold several keys". Fix: reset the subkey set at each `pub:` record and keep
   only the first certificate's.
   Checked: Google's file today holds exactly one `pub` record, so this is latent, not live.

2. **The identity check covers one envelope; every envelope is erased** —
   `subkeys.py:264-268` with `report` at `232-244`. With two packages at short id
   `d38b4796`, the helper makes exactly one description query (`envelopes[0]`) and prints
   *both* names as `RPM-KEY-ENVELOPE`, so both reach the erase loop. The module's stated
   invariant (docstring lines 26-31) and the deliberate stranger-at-the-same-id branch
   (`needs_refresh`, 203-215) only hold when the stranger happens to be listed first.
   `installed_envelopes`' own docstring (152-160) says multi-envelope is the expected state
   on an upgraded host. Fix: read each envelope's armour and name only those whose primary
   equals the published primary.

3. **`triage.bash`'s three-outcome claim is false for every grep-terminated probe** —
   `<repo>/CLAUDE/Plan/00124-chrome-install-gpg-failure-on-upgraded-host/triage.bash:51-63`,
   used at lines 67, 90, 103, 110, 115. I ran `probe()` verbatim: a pipeline that runs
   perfectly and matches nothing exits 1, so it prints `COMMAND FAILED (exit 1): (no
   output)`. The "ran cleanly and found nothing" branch is unreachable for those five
   probes. The worst is section 3 (line 103), whose comment says "a MISSING key here is a
   real finding" — that finding is reported as a failed command. The function's comment
   (45-50) says it exists to prevent precisely this conflation.

4. **`triage.bash` does not follow `CLAUDE/PlanScriptStandards.md`, with no
   `# STANDARD-EXCEPTION(Rn):`** — it hand-rolls the repo-root walk instead of sourcing
   `_planlib.inc.bash` + `plan_init` (R1); has no `plan_require_host` despite a HOST-ONLY
   comment, and R2 is explicitly "a guard, not a comment"; has no
   `plan_mode gather`/`plan_gather_leg`, so it exits 0 even when every probe failed (R7/R9);
   has no `plan_start_log`/`PLAN_RUN_DIR` (R4/R10); and prints `VERDICT:` at lines 78, 81 and
   85, which R9 and `CLAUDE/AgentNotes.md` both reserve for `acceptance.bash`. The three most
   recent plan triage scripts (00104, 00109, 00112) all use the library.

5. **The `gnupg2` fix was not generalised to the sibling site** —
   `<repo>/playbooks/imports/optional/hardware-specific/play-nvidia.yml:91-95`. The
   `rpm_key` module itself hard-requires gpg (`get_bin_path('gpg2', required=True)` in the
   module source), so that independently-runnable play has the identical undeclared
   dependency. This also means `b6e6f395`'s rationale understates the gap: the *pre-existing*
   `rpm_key` task in `play-browsers.yml` would already have failed on a gpg-less host, so gpg
   is not a dependency the new helper introduced.

6. **Nothing verifies the re-import took.** After the erase and the `rpm_key` import, no task
   asserts the installed key now carries the published subkeys. Five of Google's eight
   subkeys are currently **expired** (measured: `1397BC53640DB551`, `6494C6D6997C215E`,
   `78BD65473CB3BD13`, `4EB27DB2A3B88B8B`, `E88979FB9B30ACF2`), so if the stored key
   description is a normalised re-export that prunes them, the difference never closes and
   the play refreshes for ever, green. Phase 4 Task 4.2 is the only thing catching that.
   Re-running the helper after the import with
   `failed_when: 'RPM-KEY-ACTION none' not in ...` makes it loud and gives the play a real
   post-condition.

7. **Plan/journal drift.** `b6e6f395` changed the play only: `PLAN.md` never mentions gpg or
   gnupg2 anywhere, and the journal's last entry is 20:00 against a 20:08 commit. Task 3.3
   ("QA green, commit, push") is still unticked although QA is green and both commits are
   pushed (0 ahead / 0 behind `origin/F44`).

## Nits

- **Expired subkeys drive the refresh.** `key_ids` ignores gpg's validity (field 2) and
  capability (field 12), so a host missing only expired subkeys gets a pointless
  erase-and-reimport, described as "missing signing subkey(s) ... so it cannot verify what
  the repo now ships" — untrue of an expired key. Filtering on `s` capability and non-`e`/`r`
  validity would also remove the likeliest mechanism for finding 6.
- **The fake runner ignores `check=`** — `test_subkeys.py:87-97`. I called it with
  `check=False` and it still raised, so
  `test_a_failing_rpm_raises_rather_than_reporting_no_key` (264-269) succeeds either way. The
  helper is correct today (`check=True` at `subkeys.py:125,140,165,176`); the test simply
  does not lock in the property its docstring vouches for.
- **Task name** `Install The OpenPGP Tool The Key Check Reads Keys With`
  (`play-browsers.yml:85`) never names `gnupg2`; `CLAUDE/AnsibleStyle.md:198` wants the
  "Install YQ Binary from GitHub" shape.
- **Comment run-on** at `play-browsers.yml:80-84` — the gnupg2 paragraph is welded onto the
  end of the removal paragraph with no separator, so it reads as part of the key-staleness
  argument.
- **Check mode says nothing useful.** The probe task is skipped under check mode (so
  `failed_when` is never evaluated — `task_executor.py` guards it with
  `if 'skipped' not in result`), `stdout_lines` is `[]`, the loop is empty and a dry run
  always reports "nothing to remove". No breakage; `check_mode: false` on the read-only probe
  would make a dry run actually report a pending removal. Check mode is first-class here
  (`run.bash:870`, `_planlib.inc.bash` `PLAN_CHECK_ARGS`).
- **`docs/playbooks.md:326`** says this play "Installs Chromium and other browsers" — the
  play's own header (15-18) says Chromium is deliberately excluded. Pre-existing drift, not
  introduced here, but this is the natural moment to fix it.

## Checked and clean

- **Destructive path shape**: envelope strings can only come from the rpm listing filtered on
  an anchored `gpg-pubkey-<8hex>-` prefix (`subkeys.py:168-169`), the `argv:` form means no
  shell, and nothing in the invocation names Google. Both successful breakages needed a
  second certificate or a second envelope; neither can produce a name outside that prefix.
- **Fail-fast**: no `failed_when: false` / `ignore_errors` added; the `qa-ansible` fail-fast
  scan is green. `failed_when: chrome_key_state.rc != 0 or 'RPM-KEY-ACTION' not in
  chrome_key_state.stdout` is correct probe-then-fail — a raising helper trips *both*
  clauses, and there is no route from a failed probe to an empty envelope list.
- **The missing `when:`** is safe: every unexpected-stdout route is caught by the marker
  assertion on the preceding task, which aborts the play before the loop.
- **Idempotence, verified from module source**: `get_url` without a checksum does *not* take
  the "file already exists" early exit (that branch requires a checksum) — it sends a
  conditional GET with If-Modified-Since and returns `changed=False` on 304, so it is both
  idempotent and still tracks upstream; the local copy is not frozen.
  `rpm_key.is_key_imported` matches the primary id out of every installed key description, so
  it reports ok after the refresh; the module's own removal path targets the bare short-id
  package name with `--allmatches`, i.e. the play's full-NVR removal is strictly narrower,
  which is the right call. `yum_repository` writes once and is stable after.
- **Claimed vs actual verification**: I reproduced the gpg-parse check against the live
  published key — primary `7721F63BD38B4796` giving short id `d38b4796`, 8 subkeys,
  `FD533C07C264648F` present. The journal's Task 2.3 block is accurate. The rpm half is
  honestly declared unverified in both the plan and the journal, and the container genuinely
  has no rpm (Debian 12).
- **Public-repo safety**: the only near-hit across the whole diff is "the F41-upgraded
  laptop" (`PLAN.md` Task 4.1) — a device class, not an identifier. No usernames, hostnames,
  home paths, container names, IPs or emails anywhere in the helper, tests, play, plan or
  journal. `Owner: joseph` is `mkplan.bash`'s generated field, used in 48 other plans, and is
  the permitted maintainer handle.
- **Placement**: `play-browsers.yml` owns Chrome, so the key work belongs there; no new play
  was created, correctly (no independent lifecycle). `gnupg2` declared where the need is
  rather than relying on import order. No runtime probing for known state.
  `playbook-main.yml:23` ordering untouched and irrelevant to this change.
- **Version bumps**: nothing under `files/var/local/claude-yolo/` or the container image, so
  no `CCY_VERSION` / `REQUIRED_CONTAINER_VERSION` bump is due.
- **Helper conventions**: stdlib only, no `__init__.py`, marker lines on stdout, invoked with
  `command:` + `argv:` + `chdir: root_dir`, tests mirror the helper path.
  `select('match', ...)` has precedent in three other plays. The play is mode 100755 with the
