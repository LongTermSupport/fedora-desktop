## 17:31 · finding · T1.1   — pipx install --force cannot replace a venv under uv

Root cause confirmed from source, then reproduced.

- `community.general.pipx` 13.x runs pipx as `<target python> -m pipx` (`module_utils/_pipx.py`),
  and with `force: true` passes `install --force`.
- pipx 1.15.0 `commands/install.py`: for an existing venv with `--force` it prints
  `Installing to existing venv`, then calls `venv.create_venv()` anyway. Under the uv backend
  (`backends/uv.py`) that is `uv venv --python <py> <root>`; current uv refuses an existing
  venv without `--clear`. On failure pipx's `remove_venv()` keeps a venv "not created in this
  session", so nothing changes and the task fails.
- The backend is chosen by `resolve_backend_name`: cli > the venv's recorded backend > env >
  uv when a `uv` binary is found. play-python.yml installs uv from dnf, so new venvs are uv.
- `pipx uninstall` has no pin check (only `reinstall` and `upgrade` do), so `state: absent`
  removes a pinned venv. `EXIT_CODE_INSTALL_VENV_EXISTS` is 0, so a non-forced install onto
  a venv that was NOT removed would "succeed" silently; the removal must precede it.

`reproduce-pipx-uv.bash` lifts the probe..pin tasks from the play unchanged and runs them
through ansible against pipx 1.15.0 and uv 0.12.19 in temp homes, with fake ruff/semgrep
wheels served offline. Against `fadc1eca`, semgrep at 9.0.1 with the pin at 9.0.2, pinned
or not, both fail exactly as seen live:

```
cmd: <pipx-python> -m pipx install --force semgrep==9.0.2
Installing to existing venv 'semgrep'
error: Failed to create virtual environment
  cause: A virtual environment already exists at: .
Not removing existing venv .../pipx/venvs/semgrep because it was not created in this session
```

The fresh case (nothing installed) passes before and after.

## 17:31 · decision · T1.2   — remove then install, not UV_VENV_CLEAR

Remove the off-pin venv (`state: absent`), then install without `force`, rather than making
`--force` work.

- Rejected: `UV_VENV_CLEAR=1` in the install task's environment. It couples the play to a
  uv variable and to pipx's current create-then-reinstall sequence, and leaves a pip-backed
  venv on the `--force-reinstall` path, which layers the new version over the old one's
  dependencies.
- Removal works whatever backend recorded the venv, is a no-op when nothing is installed
  (the module's `state_uninstall` does nothing then), and ignores the pin. The fresh
  install then picks the default backend.
- The removal uses the install's `when:` exactly: a tool whose probe failed (missing, or a
  broken venv after a Python upgrade) is also removed and reinstalled.
- The pin task already runs after the install; a venv made afresh is unpinned, so it
  re-pins. Its comment now says that.

## 17:51 · finding · —

T1.2 — the broken-venv case is not exercised by the reproduction; qa-reviewer (Task 1.4) flagged it.

The 17:31 decision entry says a tool whose probe failed (missing, or a broken venv after a Python
upgrade) is also removed and reinstalled. That follows from the removal and the install sharing one
`when:`, which `scripts/test-qa-tool-pin-converges.bash` evaluates for the "probe failed" case. It
is not demonstrated by `reproduce-pipx-uv.bash`: its cases are nothing installed, semgrep off-pin
unpinned, and semgrep off-pin pinned, and none has a venv whose interpreter is gone.

- Not proven: `pipx uninstall` removes such a venv without error, so the install that follows
  starts clean.
- Where it gets caught: Task 1.5's host run. On a host whose venv points at a missing interpreter,
  look for the removal task reporting `changed` and the install task succeeding.
- Nit recorded: remove-then-install is not atomic. An install that fails after the removal leaves
  the tool absent until the next run. The play stops loudly and `qa-toolchain.bash` reports the
  missing tool, so this is fail-fast, not a defect.
