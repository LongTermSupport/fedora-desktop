## Should fix

### 1. The play's only runtime fail-fast gate reads "the shell does not know this UUID" as "no session" — and now does it for all nine

`helpers/gnome/verify_extension.py:81-97`, specifically `:89-90`:

```python
    if result.returncode != 0:
        return False, None
```

Any non-zero exit from `gnome-extensions info` becomes `session_available=False`,
which `extension_state.classify:58-62` turns into `SKIP_NO_SESSION` → `exit_code` 0 →
`Verify Deployed Extensions Are Healthy` passes. `tests/helpers/gnome/test_verify_extension.py:92-95`
asserts exactly this (`info_rc=1` → rc 0, "no GNOME session"), so it is baked in.

**This commit is where the author establishes that the mapping is wrong.** The probe fix
in the same diff (`CLAUDE/Plan/00112-gnome-extensions-enabled-state-declared/probe-gnome-extensions.bash:59-67`)
carries the reason in its own comment:

> Naming a cause here instead — "no session" — would print the same string for a third
> cause: the shell not knowing this UUID at all, which is exactly the state Plan 00110 found.

That lesson was applied to the plan-local triage script and not to the production helper
six files away. It is the AgentNotes "a lesson written down beside the thing it fixed,
never generalised" shape — the `qa-python.bash` / `qa-bash.bash` precedent.

Why it matters more after this diff than before it: the loop went from one UUID to nine
(`play-gnome-shell-extensions.yml:201`), and the newly-added member is dash-to-dock, a
system extension a freshly-provisioned shell is least likely to have scanned. On a fresh
install the whole nine-iteration gate can report OK having judged nothing, and the play's
output is identical to a genuine all-clear. Plan 00112's own Goal 3 is that "a UUID the
shell rejects still fails the play through the existing verify helper".

**Fix**: split the two causes at the point they are produced — a bus/connection failure is
`session_available=False`; a non-zero exit that reached the shell and got "does not exist"
is a *result* and must fail. And make a pass say what it checked: the play currently prints
nothing that distinguishes nine OK verdicts from nine skips. A `COVERAGE: n of m verified
against a live session` line, asserted, is what the repo asks for everywhere else.

Upstream cause worth fixing at the same time (the predecessor's nit 2, still open): the two
helpers in this one play resolve the bus differently. `apply_enabled_extensions.resolve_session_bus:65-91`
now tries `DBUS_SESSION_BUS_ADDRESS`, then each runtime dir tested with `os.access`, then
`dbus-run-session`, and is unit-tested. `verify_extension._dbus_env:31-36` still
`setdefault`s a uid-derived path and never checks it is reachable. The applier's version is
the right one; the verifier should use it.

### 2. `deployed-extensions-active` passes as "0 of 0" when the declaration parses to nothing

`files<home>/share/vmtest/guest-acceptance-desktop.bash:199-220`

`expected` is derived from `declared` (`:203`) and nothing holds it against a floor.
Reproduced:

```
$ declared=""   # gnome_shell_extensions key renamed, or all three groups empty
expected=0
VERDICT: check pass deployed-extensions-active COVERAGE: 0 of 0 declared ACTIVE
```

Both routes are silent: `groups.get(group) or []` (`:186`) returns `[]` for a group that
is not there, and `(yaml.safe_load(handle) or {}).get("gnome_shell_extensions") or {}`
(`:184-185`) returns `{}` for a renamed top-level key. Neither raises, so the
`READ-FAILED` arm never fires and the check reports a clean pass.

The previous code compared two independently-derived numbers (`deployed_count` from disk
against `expected` grepped from the play). This version removed the only cross-source
comparison, so the population and the expectation are now the same list — which is
correct for the "declared, not discovered" goal but leaves nothing guarding zero. That
is the repo's highest-recurrence defect shape and the vars file's own header
(`vars/gnome-shell-extensions.yml:6-8`) is written against it.

**Fix**: a floor. `[[ "${expected}" -ge 9 ]]` is brittle; `[[ "${expected}" -eq 0 ]] &&
check fail ... "the declaration parsed to nothing"` is the minimum, and asserting the
three group names were all present would close the renamed-group case too.

The play itself is guarded here and I confirmed it: `--uuid` is `required=True`
(`apply_enabled_extensions.py:135-141`), so an empty declaration makes argparse fail the
task. Only the guest check is exposed.

### 3. The secret-scan change has no test, in a suite that exists for exactly this library and runs on every commit

`scripts/git-hooks/lib/secret-scan.bash:104-172` adds a new exemption path to a
public-repo security gate. `scripts/test-secret-scan.bash` is the unit suite for that
file and **is** wired into `qa-all.bash:158-172` — it printed `✓ secret-scan-tests:
passed: 17` on my run, the same 17 as before the commit. Nothing new is covered.

The journal (`JOURNAL/00112-Journal-26-09-14.md:191-194`) says "Proven both ways before
committing: the nine UUIDs pass, a real address is still flagged, and a line holding both
still reports the real one". I reproduced all three and they hold — but an ad-hoc proof at
commit time is not a gate, and this is the one file in the repo where a silent regression
is a leak rather than a bug.

Four cases, all of which I ran by hand and all of which belong in `test-secret-scan.bash`:

| case | measured |
| --- | --- |
| a declared UUID alone | filtered (exempt) |
| a real address alone | survives (flagged) |
| both on one line | line survives, per-token filtering intact |
| `user@example.com` (case-differing near-miss) | survives — the UUID entries use the case-sensitive arm, not `i:` |

Add a fifth: `hook_filter_match_lines "$PAT"` with **no** repo root must leave a UUID
flagged (it does — the exemption is simply absent), because that is the behaviour the
`${2:-}` default relies on.

Note also `scripts/test-secret-scan.bash:6-8` claims "It is not wired into qa-all.bash".
It is (`qa-all.bash:166`). Pre-existing, but an author touching this library reads that
line and concludes the suite is optional.

## Nits

- **`user_extensions_dir` was added and then not used twice.** `play-gnome-shell-extensions.yml:88`
  and `:110` still spell out `/home/{{ user_login }}/.local/share/gnome-shell/extensions` while
  `:10` now names it. The variable exists precisely to stop that string being repeated.
- **A comment orphaned from its task.** `play-gnome-shell-extensions.yml:56-58` (EXT-08, the
  dash-to-dock DNF rationale) sits indented inside `Install DNF packages` and describes
  `Install Gnome Shell Extensions Packaged by DNF` on the next line. Move it below the task
  boundary.
- **The allowlist emitter does not apply the repo's own UUID validator.**
  `secret-scan.bash:135-143` emits `"^" + re.escape(uuid) + "$"` for any string. A `uuid`
  containing a newline splits into two regexes; I measured the result — `ugrep`/GNU grep
  reject the dangling escape, `_hook_grep_v` returns 2, `hook_filter_match_lines` returns 1
  and the hook aborts. So the *direction* is right (the gate fails rather than widens), but
  the operator gets `grep exit 2: ^ok@fine\.com\` instead of a named error. This commit added
  `enabled_extensions.validate_uuid`, which rejects exactly comma/newline/CR/space — the
  emitter should skip-and-name, or the hook should reject, on the same rule.
- **The hook's own source is now only committable because of the file it reads.**
  `secret-scan.bash:105-106` cites `user@example.com` and `user@example.com`
  as examples; both are exempt solely because they appear in `vars/gnome-shell-extensions.yml`.
  Drop either extension and the scanner's own comment blocks the commit that drops it. Harmless
  and loud, but the examples would be better as `something@example.com`.
- **`test_duplicate_declarations_collapse` and the play's assertion disagree by design.**
  `resolve_declared` dedupes; `Assert Deployed Extension UUIDs Were Collected` compares against
  the raw declared length. A duplicated `uuid:` in the vars file therefore fails the play with
  a count message rather than a "duplicate declaration" one. Loud, so fine — worth one line in
  the fail_msg.

## Checked and clean

### The secret-scan change — the question asked first, answered in detail

**Can a real address pass that could not before? No.** I could not construct one.

- The exemption is emitted as `"^" + re.escape(uuid) + "$"` (`:143`) and consumed per TOKEN by
  the unchanged `hook_keep_unwhitelisted` (`:59-102`), which extracts tokens with `grep -oE`
  and filters each independently. Anchored + escaped + whole-token means the only string
  exempted is the UUID itself. Measured: a real address on the same line as a UUID still
  reports (test 3 above); a case-differing near-miss still reports (the UUID arm is the
  case-sensitive `*)` branch, not `i:`).
- Only the **email** pattern reaches this code. The `case "$pattern" in *@*)` arm keys on the
  pattern text, and of the 16 `SENSITIVE_PATTERNS` and 12 `MESSAGE_PATTERNS` only the email
  regex contains `@`. The exemption cannot leak into the token, credential or home-path arms.
- Of the nine declared UUIDs, five actually match the email regex; the other four
  (`blur-my-shell@aunetx`, `just-perfection-desktop@just-perfection`, `space-bar@luchrioh`,
  `workspace-names-overview@fedora-desktop`) have no dot after the `@` and never did.

**Failure modes — all measured, all correct:**

| condition | behaviour |
| --- | --- |
| vars file absent | `return 0`, empty list, no exemption applied → UUID stays flagged. Errs toward flagging. |
| vars file empty | same |
| YAML unparseable | Python traceback on stderr, non-zero → `hook_filter_match_lines` returns 1 → both hooks print `ERROR: whitelist filtering failed` and `exit 1`. Hard fail. |
| `gnome_shell_extensions` not a mapping | `SystemExit("...must be a mapping of groups")` → same hard fail |
| `python3` or PyYAML absent | non-zero → same hard fail. No new dependency: `hook_build_private_denylist:215` already imports `yaml` in the same file. |
| uuid with an embedded newline | grep rejects the broken ERE, `_hook_grep_v` returns 2 → hard fail (see nit above) |

**`${extension_res[@]+"${extension_res[@]}"}` under `set -u`** (`:171`): correct. I ran the
whole filter under `set -u` with an absent vars file (empty array) and it expands to nothing
without an unbound error. Both hooks pass `$REPO_ROOT`, defined at `pre-commit:15` and
`commit-msg:21`.

**Cost**: ~33 ms per invocation, once per staged file that has an email-pattern hit. Negligible.

**End-to-end**: I replayed the pre-commit email scan over the seven changed files at `HEAD`.
All pass — four have no hits, three are fully whitelisted. No file in this commit reaches the
hook as a flagged leak.
