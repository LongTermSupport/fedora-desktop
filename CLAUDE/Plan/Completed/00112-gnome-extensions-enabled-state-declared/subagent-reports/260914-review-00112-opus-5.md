## Blocking

### 1. The "deployed" population is discovered from the filesystem, not declared — so it is both too wide and too narrow, and the play now fails on state the repo does not own

`<repo>/helpers/gnome/enabled_extensions.py:131-176`,
`<repo>/playbooks/imports/play-gnome-shell-extensions.yml:129-145,169-186`

`discover_deployed_uuids(extensions_dir)` enumerates *everything* under
`~/.local/share/gnome-shell/extensions`. That directory is not the repo's — it is the
standard per-user install path for anything the user adds through the Extensions app,
browser integration, or the `gnome-extensions` CLI. The repo's own acceptance script says so
at `<repo>/files<home>/share/vmtest/guest-acceptance-desktop.bash:170-174`
("The population is the user extensions under `~/.local/share/gnome-shell/extensions`").

Three consequences, all new with this diff:

- **Too wide, blast radius.** `Verify Deployed Extensions Are Healthy` (line 169) used to
  run for exactly one UUID — the repo's own custom extension. It now loops over every
  directory in the user's extension tree. `extension_state.classify` returns `FAIL_ERROR` /
  `FAIL_VERSION` for `ERROR` and a genuine `OUT OF DATE`, `verify_extension` exits 1, and
  `ansible.builtin.command` aborts the play. One stale third-party extension the user
  installed themselves now blocks the whole provisioning run.
- **Too wide, silently overriding the user.** The merge is documented as "never removes what
  the user added" (`enabled_extensions.py:16-18`). The converse is not stated and is what the
  code does: an extension the user deliberately *disabled* but left installed is re-added to
  `enabled-extensions` on every deploy.
- **Too narrow, the partial case.** `--require` names 1 of 8 UUIDs (line 141-142).
  `gnome-shell-extension-installer`'s failure is exactly the swallowed `&&` this plan's own
  `PLAN.md:22-24` describes, so six of seven downloaded produces
  `GNOME-EXT-DEPLOYED <7 uuids>`, everything ACTIVE, and a green play. This is the AgentNotes
  "guard the empty case, miss the partial" shape verbatim — `nothing-deployed` guards zero
  (`apply_enabled_extensions.py:123-128`), nothing guards partial. The VM lab catches it
  (`guest-acceptance-desktop.bash:196-197` compares `deployed_count` against a count grepped
  out of the play), but a real host has no such gate.

**Fix** — the one AgentNotes prescribes: *derive the set from the declaration, not from a
directory listing*. The play already **is** the declaration of record: the vmtest check greps
`id: [0-9]+` out of it. Add a `uuid:` field to each of the seven loop entries at lines 62-82,
pass all eight (nine with dash-to-dock, see #2) as `--require`, and let
`discover_deployed_uuids` validate the declared set against disk rather than define it. That
removes the drift concern the journal raises, closes the partial hole, and stops the play
judging extensions it did not install.

### 2. dash-to-dock has the same defect and it is established evidence, not an open question

`<repo>/playbooks/imports/play-gnome-shell-extensions.yml:48,208-213`;
`<repo>/CLAUDE/Plan/00112-gnome-extensions-enabled-state-declared/JOURNAL/00112-Journal-26-09-14.md:58-69`

The journal defers dash-to-dock on the grounds that "nobody has read that session's
`enabled_extensions_live`". Somebody has. Plan 00110's journal records it twice, read through
both channels:

- `<repo>/CLAUDE/Plan/Completed/00110-vm-lifecycle-acceptance-testing/JOURNAL/00110-Journal-26-09-13.md:1546-1547`
  — "the live shell's enabled list — read both through `gnome-extensions list --enabled` and
  the settings key, over the session bus — holds only Fedora's stock background-logo"
- same file `:1576-1577` — "the session's `enabled-extensions` setting (read live and from
  gsettings) still holds only Fedora's stock background-logo"

A system extension is enabled by the same key. If the list held only `background-logo`,
dash-to-dock was off. So `Configure Dash to Dock - Hide Behind Any Overlapping Window`
(line 208) writes an `intellihide-mode` key for an extension that is not running — the fix
Plan 00102 shipped and recorded as accepted is a no-op on a fresh install.

Widening the applier here is not a guess; it is the second instance of the defect this plan
exists to remove. A second `--extensions-dir /usr/share/gnome-shell/extensions` invocation
restricted to the DNF-declared UUID, or an explicit
`--also-enable user@example.com`, closes it.

### 3. `disable-user-extensions` is neither declared nor asserted, so the play's success criterion is satisfiable with nothing enabled

`<repo>/helpers/gnome/apply_enabled_extensions.py:144-179`,
`<repo>/helpers/gnome/extension_state.py:78-84`

`org.gnome.shell disable-user-extensions: true` defeats every user extension regardless of
`enabled-extensions`. The applier reads and writes the sibling key in the same schema and
says nothing about this one. Downstream, `classify` returns `Verdict.OK` for **any** state
that is not `ERROR` or `OUT OF DATE` (line 78-84) — including `DISABLED`/`INACTIVE`. So the
whole path reports green while the session comes up with nothing enabled, which is precisely
the Plan 00110 outcome one key over.

The author clearly knows it matters: `probe-gnome-extensions.bash:96-97` probes for it. The
play then does nothing with the answer. Either declare `disable-user-extensions` false
through the same gsettings path the applier already writes, or fail the applier when it reads
true — but do not leave the plan's own goal unverifiable.

## Should fix

### 4. `docs/playbooks.md:526-534` states something the code does not do — in both directions

"every extension the play deploys is written into `org.gnome.shell enabled-extensions`". The
play deploys dash-to-dock (line 48, and the doc lists it under **System extensions** eighteen
lines above) and does *not* write it. Conversely, what is written is every extension in the
user's directory, deployed by this play or not. Both halves need correcting, and the
correction depends on how #1 and #2 land.

### 5. `loop: "{{ gse_deployed_uuids | default([]) }}"` makes the fail-fast verify gate vacuous whenever the fact is unset

`<repo>/playbooks/imports/play-gnome-shell-extensions.yml:186`

The `--check` fix in `e1591a08` is right in substance, but `| default([])` is a total answer
to a partial question: today the only path to an unset fact is check mode, but a `when:`, a
`--tags` selection, or a future edit to the applier task turns the repo's fail-fast gate into
a zero-iteration no-op with no signal. `when: not ansible_check_mode` on line 155 cannot be
repeated on the verify task, because Ansible templates `loop` before evaluating `when`. Add
the explicit assertion instead:

```yaml
- name: Assert Deployed Extension UUIDs Were Collected
  ansible.builtin.assert:
    that: gse_deployed_uuids | default([]) | length > 0
  when: not ansible_check_mode
```

### 6. `probe-gnome-extensions.bash` captures the error text and then narrates a cause it has not confirmed

`<repo>/CLAUDE/Plan/00112-gnome-extensions-enabled-state-declared/probe-gnome-extensions.bash:61-64,80-85`

```bash
if ! info="$(gnome-extensions info "${uuid}" 2>&1)"; then
    printf '(no session / gnome-extensions unavailable)'
```

`${info}` holds the reason and is discarded; the printed string asserts one of two specific
causes, and a third (the shell does not know that UUID — the exact state Plan 00110 found)
prints the same text. `declared_uuid` at line 80-85 does the same with the Python error. The
`probe()` helper eight lines above already does this correctly
(`UNREADABLE (exit %s): %s`) — use the same shape. This is a triage script, so a wrong
narrative here is what drives the Task 2.1 conclusion.

### 7. `verify_extension.py:42-45` now prints a wrong remedy for seven of eight extensions

The message says "Run the 'Deploy Custom Extension' play step before verifying." That was
accurate when the loop covered one copied extension; the seven from
`gnome-shell-extension-installer` have nothing to do with that step. Behaviour moved, message
did not.

### 8. Journal 09:00 entry rests on a premise the repo contradicts

Covered in #2. The entry is append-only, so the correction belongs in a new entry rather than
an edit — but leaving it as the standing rationale for deferring dash-to-dock is

## Nits

- `helpers/gnome/apply_enabled_extensions.py` is committed `100644` with a
  `#!/usr/bin/env python3` shebang and a `__main__` guard, while its siblings
  `verify_extension.py` and `check_extension_compat.py` are `100755`. It is invoked via
  `python3 -m`, so nothing breaks; the inconsistency is the nit.
- Bus resolution differs between the two helpers in the same play: the applier prefers
  `XDG_RUNTIME_DIR` (`apply_enabled_extensions.py:140`), `verify_extension.py:34` always
  derives `/run/user/{os.getuid()}/bus`. Under a sudo become that leaked a stale
  `XDG_RUNTIME_DIR`, the applier falls all the way through to `dbus-run-session` and the
  running shell never sees the change live, where the uid-derived path would have reached it.
  Falling back to `/run/user/{uid}/bus` before `dbus-run-session` costs one line.
- `discover_deployed_uuids` refuses a comma in a UUID (`enabled_extensions.py:170-174`)
  because the marker line is comma-separated, but not a newline, which would split the marker
  into two lines and break the `set_fact` parse the same way.
- No test covers a failing gsettings write propagating; only the read is covered
  (`test_apply_enabled_extensions.py:226-233`). Same `_gsettings` path, so low risk, but the
  write is the side effect that matters.
