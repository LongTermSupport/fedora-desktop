## 13:50 · finding · T4.5 — A works, and the objection that separated it from B applies to both

Task 4.5 has sat on "AWAITING A DECISION" between A (one scan per rule, measured) and B
(model `paths.include` in-gate). Before accepting either I went looking for a cheaper
*measured* option, on the grounds that a 14-second tax on every QA run is worth one hour of
checking. There isn't one — but the checking changed two things about the decision.

**`--time` is dead, and the recorded reason is right for a slightly different cause.** The
plan rejected it because a `match_times` of `0` means both "not targeted" and "targeted,
matched nothing". I had hoped the *presence* of a (rule, target) pair would discriminate
even when the value could not. It does not:

```
rules in the time block : 5
match_times list lengths across 70 targets : {5: 70}
```

Every target carries an entry for every rule whether or not that rule targeted it. Neither
the value nor its presence carries the information. Rejection confirmed.

**`--x-ls` is not a third option.** Its own help says it lists the selected targets *"before
any rule-specific or language-specific filtering"* — the union again, which is the number
we already have and already distrust. It is also flagged `[INTERNAL]` and documented as
liable to "change or disappear without notice", so it could not be built on regardless.

**`--include-rule-id` does not exist in semgrep 1.177.0.** My first timing attempt used it
and every invocation exited 2 with `unknown option`. The harness caught it and refused to
report the comparison rather than printing a 0.51s "result" that would have made A look
free:

```
5 separate scans : 0.51s
NOT COMPARABLE — --include-rule-id failed, so the per-rule runs did not do the work
```

So A has to be implemented by splitting the ruleset into temporary single-rule configs.

**Which means A needs PyYAML too — and that voids the objection as a discriminator.** The
plan records "needs a YAML parser = a dependency decision" as *B's* blocker, and correctly
notes it does not hold because PyYAML ships with ansible. What it does not say is that A
needs the same parser to split the ruleset. The only way to avoid that is five
hand-maintained single-rule config files sitting beside the real ruleset — two things that
must agree, maintained separately, which is the hazard this repo keeps being bitten by. So
the YAML question does not separate A from B at all. It is void for both.

## 14:05 · action · T4.5 — I got the discrimination test wrong twice before getting it right

Worth recording in full, because it is the trap waiting for whoever implements A.

**First attempt**, corpus `files/home/.local/bin/ scripts/`:

```
    70  bash-error-hiding-pipe-echo
    70  bash-capture-discards-status      ← identical
```

I read that as "`paths.scanned` does not discriminate per rule" and nearly wrote up that A
was unworkable.

**Second attempt**, corpus `scripts/ helpers/` — chosen because `helpers/**` is in two
rules' include sets and not the others':

```
union scanned: 56   Counter({'scripts': 56})
```

Also uniform. `helpers/` is **Python**; it contributes no bash at all, so the corpus still
could not span the difference. Two negatives, both mine, neither semgrep's.

**Third attempt**, corpus `scripts/ CLAUDE/Plan/` — plan folders hold real bash, and
`CLAUDE/Plan/**` is in the include set of `pipe-echo` and `status-after-block` only:

```
union: 150  Counter({'CLAUDE': 94, 'scripts': 56})
   150  bash-error-hiding-pipe-echo      {'CLAUDE': 94, 'scripts': 56}
   150  bash-status-after-block          {'CLAUDE': 94, 'scripts': 56}
    56  bash-test-discards-status        {'scripts': 56}
    56  bash-capture-discards-status     {'scripts': 56}
   150  bash-error-hiding-or-true        {'CLAUDE': 94, 'scripts': 56}
VERDICT: paths.scanned DOES discriminate
```

**A works.** A single-rule scan's `paths.scanned` is a real per-rule coverage measurement.

**The trap, stated plainly:** `files/**`, `scripts/**` and `fedora-install/**` are in EVERY
rule's include set, so a test corpus drawn from them is guaranteed to report uniform
coverage no matter what the implementation does. Only `CLAUDE/Plan/**` or `extensions/**`
span the difference. A test built on the wrong corpus passes while the gate reports the
same false uniformity Task 4.5 exists to remove — the defect reproducing itself inside its
own fix.

**Cost, re-measured on the discriminating corpus:**

```
combined  : 1.89s
5 split   : 9.19s   (+7.30s, 4.9x)
```

Consistent with the +14s already recorded against the full 157-file corpus.
