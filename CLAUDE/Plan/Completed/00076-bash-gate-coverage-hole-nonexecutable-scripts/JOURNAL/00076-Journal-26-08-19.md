# Plan 00076 — Journal 2026-08-19

## Tasks 4.3b / 4.3c / 4.4 — closed, and the framing that blocked them was wrong

Three attempts across two sessions failed to establish why semgrep could not
parse `rclone-tail`, `rclone-cache-status` and part of `ftp-camera`. All three
attempts shared one defect, and it is this plan's own class again.

### The harness was measuring the wrong thing

Semgrep parses a file **only when a rule's regex has already matched something in
it**. Measured across ten (file, rule) cells:

| file                  | rule                           | raw regex matches | parse error    | findings |
| --------------------- | ------------------------------ | ----------------- | -------------- | -------- |
| `rclone-tail`         | `bash-capture-discards-status` | 3                 | `Syntax error` | 0        |
| `rclone-tail`         | `bash-error-hiding-pipe-echo`  | 3                 | `Syntax error` | 0        |
| `rclone-tail`         | `bash-error-hiding-or-true`    | 0                 | —              | 0        |
| `rclone-tail`         | `bash-status-after-block`      | 0                 | —              | 0        |
| `rclone-tail`         | `bash-test-discards-status`    | 0                 | —              | 0        |
| `rclone-cache-status` | `bash-error-hiding-pipe-echo`  | 1                 | `Syntax error` | 0        |
| `rclone-cache-status` | the other four                 | 0                 | —              | 0        |

The correlation is exact: **matches 0 ⇒ no parse attempted ⇒ no error**. So the
earlier conclusion — "three of the five rules parse these files fine, therefore
parseability is a property of (file × rule)" — was reading an *absence of an
error* as evidence of coverage. The three rules had never been asked.

It also explains the other dead end: a solo copy at `./ftp-camera.bash` "reported
no error" because no `paths.include`-scoped rule matched that path, so nothing
ever tried to parse it. Not a property of the file at all.

**The fix to the harness**: a probe rule whose regex matches on every line
(`pattern-regex: 'echo'`), so the parse is always attempted. With that, results
became reproducible and leave-one-out worked first time.

### The construct

`rclone-tail`: removing `query_stats` (L133-180) took the file from
`Syntax error` to `PartialParsing`. `rclone-cache-status`: removing `query_cache`
(L187-225). Both functions contain the same shape:

```bash
if ! python3 - "$vfs_json" <<'PY' 2>/dev/null
...
PY
    then
        echo "ERR|parse failed"
    fi
```

A heredoc fed **directly to an `if` condition**, with `then` on the line after
the terminator. Minimal repro confirmed it: that form gives `PartialParsing` on
its own and escalates to a whole-file `Syntax error` in company; the same code
with the heredoc inside a command substitution parses clean.

Rewrote both to the substitution form. Both now `PartialParsing` only, and both
`bash -n` clean.

### What the blackout was costing: 4 real findings

With the files parseable, the ruleset immediately reported what it had never been
able to see:

- `rclone-tail` L263-265 — three `numfmt … 2>/dev/null || echo "?"`
- `rclone-cache-status` L332 — one, in `fmt_bytes()`

All four rewritten to the explicit-fallback form the rule's own message
prescribes (`var=$(cmd) || var="?"`). `SEMGREP_CANNOT_PARSE` is now empty.

### `PartialParsing` costs nothing — and the gate was saying it did

This is the correction that matters most, because it is a false statement I put
in the gate *yesterday*, inside the fix for false statements about coverage.

The report said `1902 of 2486 lines not analysed` for `ftp-camera`. Measured:

- probe regex `echo` over `ftp-camera` → **293 findings**
- raw `re.finditer("echo", …)` over the same file → **293 occurrences**
- 262 of those findings are on distinct lines **inside** the 585-2486 range

Every line was scanned. Every rule in `.semgrep/bash-conventions.yml` is
`pattern-regex`, and the regex engine reads raw text — the parse tree is never
consulted for a match. The single `pattern:` in that file is inside a comment.

So the previous wording was false in the *alarming* direction rather than the
reassuring one. That is not better; it is the same failure with the sign flipped,
and it would have sent someone into a rewrite of a 2,486-line script for nothing.

Gate now says `N of M lines outside the parse tree`, plus a standing note that
this becomes a real gap the day an AST `pattern:` rule is added. That is the
honest statement: the magnitude is worth keeping visible precisely because the
cost is currently zero and would not be forever.

### Negative controls

Run before trusting any of the above:

1. Unlisted whole-file `Syntax error` (the pre-fix `rclone-tail`, dropped into
   the plan folder) → **exit 2**, named, "NO rule ran on them".
2. Stale exception (`rclone-tail` re-added to `SEMGREP_CANNOT_PARSE` after the
   fix) → **exit 2**, "now parse fine … remove them from the list".
3. A file carrying only the heredoc construct → `PartialParsing`, gate stays
   green and **still reports** the `|| echo` on line 15 — which is the whole
   point, and the first control I ran, expecting exit 2 and being wrong.

Control 3 is worth recording as a wrong prediction: I assumed the construct alone
would produce a whole-file syntax error. It does not — it needs the surrounding
file. Had I not run it, the plan would have claimed a cause narrower than the
evidence supports.

`./scripts/qa-all.bash` green: 504 files, 154 bash, 154 patterns, exception list
empty.

## Task 4.5 — the three options, measured

Done while the host deploy was running, so 4.5 stops being a vague deferral and
becomes a decision with numbers.

### Option C looked free and is wrong

`semgrep --json --time` returns `.time.rules[]` and, per target,
`.time.targets[].match_times[]` — positionally aligned. That reads like a
per-rule x per-file coverage matrix from a single scan: no extra runs, no YAML
parsing, no new dependency.

It is not one. Probe: the same 3-line script placed at three paths with
different rule coverage.

| mirror path                        | match_times (pipe-echo, status-after-block, test-discards, capture-discards, or-true) |
| ---------------------------------- | -------------------------------------------------------------------------------------- |
| `files/home/.local/bin/probe.bash` | 0.0001841, 0, 0, 3.791e-05, 0                                                         |
| `helpers/probe.bash`               | 0.0001872, 0, 0, **0**, 0                                                             |
| `docs/probe.bash`                  | 0, 0, 0, 0, 0                                                                         |

`capture-discards` reads **0** on the `helpers/` file, which it genuinely never
saw (its `paths.include` is `files/`, `fedora-install/`, `scripts/`). It also
reads a non-zero on the `files/` path, where it did run. But
`status-after-block` reads **0** on that same `files/` path, where it definitely
ran and simply matched nothing.

So a zero covers both "not targeted" and "targeted, no match". `match_times` is a
timing array, not a targeting matrix, and reading a 0 as "did not run" would be
exactly the inference this plan exists to stop. Ruled out.

### Option B — the stated blocker does not survive checking

The deferral said reporting per-rule coverage without extra scans "needs a YAML
parser in a bash gate — a host/CI dependency decision".

Checked rather than assumed:

- container: `PyYAML 6.0`, in the same site-packages tree as `ansible`
- host: `qa-ansible-syntax.bash` already requires `ansible-playbook`, and ansible
  depends on PyYAML
- CI: the "Install QA tooling" step in `.github/workflows/qa.yml` already brings

PyYAML is already guaranteed everywhere this gate runs. There is no new

**But there is a better reason to hesitate**, and it is not the one that was
written down: Option B *models* semgrep's targeting rather than measuring it. A
hand-written glob matcher that disagrees with semgrep's `paths.include` semantics
would print coverage the scan does not actually have. Given that this whole plan
is a sequence of coverage claims that turned out to be false, a modelled number
is worth less than a measured one even at +14s.

## Plan 00077 — the negative control paid for itself on its first run

`ANSIBLE_INJECT_FACTS_AS_VARS=False` **does not exist**. The setting is reported
as `INJECT_FACTS_AS_VARS`, the ini key is `inject_facts_as_vars`, and the
environment variable is `ANSIBLE_INJECT_FACT_VARS` — no "AS", "FACT" singular.
From `ansible-config list`:

```
INJECT_FACTS_AS_VARS:
  env:
  - name: ANSIBLE_INJECT_FACT_VARS
  ini:
  - key: inject_facts_as_vars
    section: defaults
```

Ansible ignored the non-existent variable silently. The control play printed
`distribution is Fedora` and passed, and the run's own log even carried the
give-away: *"INJECT_FACTS_AS_VARS default to `True` is deprecated"* — still on
its default.

Without the control I would have run the positive case, watched
`play-rpm-fusion.yml` go green, and marked Task 2.2 proven. It would have proved
nothing whatsoever. This is the third time in two days that an absence of an
error nearly became evidence of success.

Confirmed both directions in the container:

```
ANSIBLE_INJECT_FACTS_AS_VARS=False ansible-config dump --only-changed   -> not listed
ANSIBLE_INJECT_FACT_VARS=False     ansible-config dump --only-changed
    -> INJECT_FACTS_AS_VARS(env: ANSIBLE_INJECT_FACT_VARS) = False
```

F2 re-confirmed at the same time: `ansible.cfg` does not set it.

The script gained a **check 0** that runs before any play: `ansible-config dump
--only-changed` must report the setting as False. One command, no play, and it
catches a wrong variable name instantly — the play-based control stays as the
end-to-end check, since a setting can be reported correctly and still not change
task-time behaviour.
