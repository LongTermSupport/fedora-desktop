## 09:27 · finding · T1.1 — the host never rebooted

## 09:28 · finding · T1.3 — the greeter was never configured, and the default is suspend

Second wrong turn, now corrected. I first blamed the battery: the machine reads
`AC online = 0`, discharging, and `sleep-inactive-battery-type=suspend` with a
900 s timeout, which fits. It is not the explanation.

`Gio.Settings.get_default_value()` shows the GNOME **schema default** for
`sleep-inactive-ac-type` is `'suspend'`. The human user has it overridden to
`'nothing'` by `play-prevent-ssh-suspend.yml`; `gdm` has nothing set and so
inherits `'suspend'`. The greeter suspends on AC. The arithmetic is exact —
greeter session opens 05:52:52, plus the 900 s timeout, equals 06:07:52, and
suspend is logged at 06:07:53. One second.

So whether the laptop was plugged in was irrelevant to the outcome. The battery
finding is real but was a red herring for *this* question.

## 09:29 · finding · T1.3 — the obvious greeter fix would be inert

## 09:30 · finding · T1.4/T1.5 — podman permits this by design, and it is still live

`podman-run(1)` on this host: `unless-stopped` retries "indefinitely" and only
`on-failure[:max_retries]` accepts a cap. Zero matches in the whole man page for
`backoff`, `restart-sec` or `restart-delay` — there is no delay mechanism to
configure. And podman registers containers as systemd **scopes**, which
`systemd.scope(5)` defines as managing "externally created processes", so
`Restart=`/`StartLimitBurst=`/`StartLimitIntervalSec=` never apply. systemd's
rate limiter was not bypassed by accident; it was never in the path.

Measured ~8,800 starts/hour overnight. **Still running during triage** — 66
starts in a 60-second sample.

## 09:30 · decision · P3 — defence before fix, and the live loop is the test case

The live crash loop is the only unsimulated instance of the defect available,
and stopping the container destroys it. So detection gets built and validated
against it *first* (true positive on real data), the loop is stopped second
(true negative), and fixes come third. Fixing first would leave a detection
defence that has never detected anything, which is not distinguishable from one
that does not work.

## 09:34 · finding · P3 — the compositor cannot be defended, so the workload must be

I had written off "losing the bus killed the compositor" as upstream and not worth
pursuing. That was too quick. The first half is verified — but it forces a defence I had
skipped rather than ruling one out.

`org.gnome.Shell@user.service` on this host:

```
# On wayland we cannot restart
Restart=no
OnFailure=org.gnome.Shell-disable-extensions.service gnome-session-shutdown.target
OnFailureJobMode=replace-irreversibly
```

Upstream declares the compositor unrecoverable on Wayland and tears the session down
deliberately and irreversibly when it fails. There is no session-layer defence to build,
and `org.gnome.Shell-disable-extensions.service` — the only automatic mitigation wired in
— was skipped on unmet condition during the incident.

The consequence is the actionable part: **if the session cannot survive, long-running
work must not live inside it.** The incident already demonstrates both sides. Every shell
inside a terminal emulator's pty died with the compositor, because the GUI process owning
the pty died. The container-hosted agent, being outside the session entirely, ran
straight through.

This repo already provisions the means: `play-tmux-sessions.yml` installs tmux, deploys a
system-wide configuration and verifies tmux accepts it, and tmux is present on the host.
A tmux server is its own process under the user manager, not a child of the compositor,
so a compositor death costs a reattach rather than the work.

So this is not a missing capability. It is that the work which was lost was not inside
the capability that already exists. That is a habit and default-path question — what a
long-running job is started *in* — and it is a fair thing for this plan to carry, since
the alternative is a host whose only defence against a lost session is that sessions
rarely die.

Recorded as Task 3.5 rather than specified here; it needs a look at how long-running work
is actually launched on this host before proposing anything, and this plan applies no
fixes.

declares byte limits of 1e9. The session broker actually runs with `--max-bytes` of 1e14

on evidence, not preference — and recorded as an accepted limitation rather than smoothed

## 10:57 · decision · T6.1 — detection has no teeth, and the plan was reading as though it did

Challenged on what the detection work actually buys. The honest answer is: **not
protection**. The watchdog's report is delivered to a logged-in human, and in this incident
nobody was logged in — which is not a detail, it is the incident's defining property. A
reporting-only defence would have watched the loop for ten hours, written a finding nobody
read, and watched the compositor die on schedule.

The plan did not say that anywhere. It now says it in the Overview and in detection-gap.md,
because a design whose central weakness is unstated reads as a design that does not have
one.

**Decision: automatic `podman stop` at 100 restarts within a rolling window.**

The margin is the justification, and it is not close:

| | |
| --- | --- |
| Restarts to exhaust the quota | ~85,000 (≈10 h observed) |
| Enforcement threshold | 100 |
| Proportion of the way to failure | 0.1% |
| Time to trip at ~130/min | ~45 s |

It acts roughly ten hours before the desktop would die, and the nearest legitimate
container on this host sits at 19 restarts for its entire lifetime.

**Windowed, not cumulative.** A cumulative bar of 100 would eventually fire on a container
that restarted slowly over months, which is normal operation rather than a storm.

**Two things I had to check rather than assume.**

First, plan 00055's D3 is *reporting-only*, enforced by a QA gate — so this cannot live
there. Reading the gate rather than the decision summary showed what it actually forbids:
signal kills (`os.kill`, `os.killpg`, `pkill`, `kill -<sig>`, `force_exit`) scanned across
`helpers/containerwatch/*.py` and the extension. D3 rejected hard-killing processes and
capping CPU as symptom-hiding. An orderly `podman stop` is a different act — reversible,
signal-free, and aimed at the loop's source rather than its symptoms. It still does not
belong in 00055's tree; home is 00079, which exists for container lifecycle.

Second, whether a stop even ends the loop. The offender's policy is `unless-stopped` with
`MaxRetry=0`, and `unless-stopped` means *restart unless explicitly stopped* — so a plain
`podman stop` is definitive and needs no policy edit, which also leaves the external
project's configuration untouched.

Two further layers recorded, deliberately NOT proposed:

- `cgroup_manager = "cgroupfs"` would stop podman registering every container as a
  `libpod-*.scope` with the user systemd manager (20 are live now), which is what generates
  the bus signals. **Unverified hypothesis.** It must not reach a play before a read-back
  proves it, which is the exact trap this plan has already fallen into twice.
- UID containment is the strongest option and the most disruptive. The broker accounts
  per-UID — "UID <uid> exceeded its 'bytes' quota" — and rootless podman runs as the
  desktop's own UID. A different UID could not exhaust the desktop's budget at all, with no
  threshold to tune and no dependence on having anticipated the cause.

## 11:16 · finding · T5.5 — the true negative found a defect the true positive could not

Authorised to resolve the podman issue manually pending the real fix, so the loop was
stopped. That was safe because the perishable evidence was already banked, and the loop can
be restarted later to prove the proper fix.

`podman stop` was definitive — the policy is `unless-stopped`, which means *restart unless
explicitly stopped*, so no policy edit was needed and the external project's configuration
is untouched. Churn went from ~50 starts per 40 s to **zero** and stayed there across a
45-second confirmation. Final count: **131,377** restarts.

Re-running the detector should have been a formality. It was not:

```
FLAGGED  container-L  ABSOLUTE (131377 cumulative, threshold 1000)
```

The rate test went silent correctly. The absolute test kept firing, because `RestartCount`
is cumulative and never resets — so as specified it would have alarmed **for ever** on a
container already dealt with.

That is worse than no alarm. An alarm that cannot be cleared trains the operator to ignore
it, and the thing they would learn to ignore is the exact signal this plan exists to
deliver.

Fixed by gating the absolute test on the container actually **running** — a container that
is not running cannot be looping. The count is still reported, just not flagged, so the
suppression is visible rather than silent:

```
ok       container-L  cumulative=131377 delta=0
Historic, deliberately NOT flagged:
  container-L has 131377 cumulative restarts but is not running -- historic, not looping
RESULT: no container flagged.
```

**This is the whole argument for the validation pair, in one incident.** The true positive
proved the detector fires. Only the true negative proved it also *stops*, and that is where
the defect was. Shipping after the positive alone would have shipped a permanent false
alarm. Task 5.1 now says port the running-gate, not just the thresholds.

One more thing from the final inspection, and it corrects the plan's vocabulary: the
container exits with code **0**. It was never crashing — it completed successfully and
`unless-stopped` restarted it regardless, which is precisely what that policy does.
"Crash loop" names the effect correctly and the cause wrongly.
