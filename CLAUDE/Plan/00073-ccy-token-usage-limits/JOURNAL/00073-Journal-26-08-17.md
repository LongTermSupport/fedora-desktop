## 07:33 · finding · T1.3 — redaction bug caught by testing, not by reading

`redact()` originally used `[A-Za-z]{2,}` in its email pattern. The container's
awk is **mawk 1.3.4**, which ignores `{n,}` intervals unless built with
`--re-interval` — so the pattern matched literally and the substitution did
**nothing**. A test email sailed straight through into the report:

```
$ echo "a@b.test" | awk '{ gsub(/[A-Za-z]{2,}/,"X"); print }'
a@b.test
```

Rewritten as `[A-Za-z][A-Za-z]+`, which mawk and gawk both honour. Worth
recording because the HOST is Fedora (**gawk**, where `{2,}` works) — the bug
would have stayed invisible had this only ever been reviewed by reading, or
only ever run on the host. This is the exact failure shape PlanTriage.md warns
about: assume your redaction is wrong and check it.

## 07:34 · finding · T1.3 — `paths(scalars)` silently drops null leaves

The shape probe first used `jq 'paths(scalars)'`. jq's `select()` treats a
`null` value as false, so every null leaf is dropped — and `scope` is exactly
the optional field most likely to arrive null. Replaced with an explicit
type filter that keeps nulls visible. Verified against a fixture: `scope = null`
now appears in the report.

Owner asked to try it on by default and fall back to human-triggered only if

## 08:10 · finding · T3.7 — an unreachable endpoint BROKE the whole menu

First implementation, tested with the stub server killed: the menu printed **no
token rows at all**. Chain: curl fails to connect → never creates its `--output`
file → `chmod`/`mv` on the missing file fail → subshell dies under `set -e`
before its `exit 0` → `wait` returns non-zero → `set -e` in the caller aborts
the render.

Exactly the failure the plan's Decision 2 forbids ("must never block a launch"),
and it only showed up because the failure path was actually exercised. Fixed by
making the worker record outcomes rather than raise them: both cache files are
always created, the worker unconditionally exits 0, and a failed `wait` is
explicitly handled and skipped.

## 08:14 · finding · T3.7 — jq, not the network, was the real cost

Cached renders were nearly as slow as uncached ones — 239 ms warm vs 268 ms cold
for 2 tokens, against a 71 ms feature-disabled baseline. Cause: `jq` was run once
per row at display time, ~40 ms each.

Restructured so the parallel worker parses and renders, and the cache stores the
finished line. The display path now runs no `jq`, no `curl`, and no subprocess
beyond two small file reads; `colorize_usage` finds its worst percentage in pure
bash (a here-string and a loop) instead of `grep | tr | sort | head`, which alone
was ~39 ms per token. Warm went 239 → 112 ms for 2 tokens.

Side benefit worth keeping: the raw response is no longer written to disk at all,
so account details in the payload do not outlive the fetch.
