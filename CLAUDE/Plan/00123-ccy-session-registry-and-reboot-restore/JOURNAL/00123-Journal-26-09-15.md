## 16:40 · finding · T1.1 — three of issue 44's premises are wrong, and the fourth hazard is unmentioned

Verified every claim against the code before designing anything. Full write-up in
`FACTS-ccy-mechanics.md`; the headlines:

- **Not one session per project.** `ccy_tmux_next_name` walks `ccy-<project>-2`, `-3`, and
  `docs/ccy.md:186` documents it. So a record cannot be keyed on the directory.
- **Arguments are not passed through verbatim.** `claude-yolo:523-645` is a hand-rolled
  parser that consumes every ccy flag; only post-`--` args are raw. More importantly the
  quick-launch path supplies token/ssh/network with an **empty argv**, so argv is the wrong
  thing to record at all — the resolved config is.
- **`cc` is not in this repo.** Only `alias ccy=` exists. Nothing here can register a `cc`
  session, so that is a stated non-goal rather than a silent absence.
- **The unmentioned hazard, and the biggest risk in the feature:** a detached tmux session
  still has a pty, so `[ -t 0 ]` passes and every one of the **seventeen** reachable
  interactive prompts in the launcher behaves as if a human were watching. The first of them,
  `Use same configuration? [Y/n]` at `:928`, fires on essentially every restore. A restored
  session would sit there for ever — visible in `ccy-sessions`, `claude` never started, the
  supervisor never running. Worse than no restore, because it looks like it worked.

Also confirmed the upstream blocker is real: the installed daemon's command list has no
`notify` and no signal-raising command of any kind, and `reboot-warning` appears nowhere in
the daemon tree or the supervisor. `inject-goal` is the nearest mechanism and is deliberately
NOT reused — it takes free text, and the issue's own security argument depends on the signal
carrying a fixed kind and an integer only.

## 16:55 · decision · T1.2 — one `read()` seam, not seventeen guards

Recorded as D6. Guarding each of the seventeen prompt sites individually leaves the
eighteenth unguarded, and its symptom is a silent hang. Instead: `CCY_UNATTENDED=1` plus a
function named `read` shadowing the builtin, fatal only when `-p` is present. `-p` *is* what
makes a `read` a prompt to a human, so the guard cannot go stale — the same "derive it, do not
enumerate it" lesson as the `CCY_HASH` incidents in `ContainerRules.md`. The seven non-prompt
`read` calls in the launcher (`read -ra` splits, `while read` over pipes) have no `-p` and
pass through untouched.

Closing stdin instead was considered and is worse: several prompts sit in `while true` loops
that re-prompt on an unrecognised answer, so EOF spins one at 100% CPU rather than hanging
quietly.

## 17:05 · decision · T1.2 — consuming the record kills the retry loop, so the attempt counter is dead weight

Designed a per-record attempt counter with a cap, then deleted it. Once the restore **moves**
the record to `attempted/` before starting the session, there is nothing left in `sessions/`
to retry, so the counter would have counted to one and never fired. A mechanism that can never
trigger is worse than none, because a reader believes it is protecting them. D2 keeps the
consume-first design and `Type=oneshot` with no `Restart=` as an independent second brake.

The cost is stated plainly rather than hidden: a failed restore loses the session. The record
survives in `attempted/` as evidence, the reason is in the journal, and `restore-status` names
the manual way back.

## 19:10 · finding · T2.2 — the test caught three defects the design would not have

Writing the test first was not ceremony; each of these was live code.

1. **`read -p` was not caught by the guard.** The glob `-[a-zA-Z]*p` requires at least one
   letter before the `p`, so `-rp` and `-rsp` matched and a bare `-p` fell straight through.
   I had hand-tested `-rp` and concluded it worked. Now a regex, `^-[a-zA-Z]*p$`.
2. **A repeated key in a record was silently resolved to the first line.** The test helper
   appended overrides after defaults, three cases quietly asserted against the default they
   meant to change, and the record was ambiguous to boot. The library now REFUSES a repeated
   key on write — both lines are individually well-formed, so nothing downstream could ever
   have noticed.
3. **The flag-derivation regex found zero flags and would have reported a clean pass.** The
   pattern carried a literal `$` from `"$arg"`, and in an ERE a `$` is the end-of-line
   anchor — so it matched nothing, every flag was trivially "classified", and the staleness
   guard was itself inert. The pattern now starts at `arg"` and carries no sigil at all.

The third is the one worth remembering: a guard that silently matches nothing passes louder
than one that works.

## 19:25 · finding · T2.4 — the read shadow must declare no locals of its own

`builtin read` assigns to the variable the CALLER named. A `local` in that same scope with
the same name swallows the value instead, and the corruption is silent — it would affect only
whichever caller happened to pick a colliding name. The guard's own variables are `flag` and
`idx`, so `read -r flag` anywhere in ccy would have quietly returned nothing.

Fixed by splitting the guard into `_ccy_read_guard` (which has locals) and `read` (which has
none and only calls the builtin). Pinned by three cases that read into `flag` and `idx`
specifically, attended and unattended.

## 19:50 · decision · T2.3 — no attempt-clearing in the launcher after all

PLAN.md's first draft had the launcher clear a per-project restore-attempt counter on a
successful start. Dropped: whether a restore attempt came up is DERIVABLE — the attempted
record carries the previous boot's id and the live record carries the current one, so
`restore-status` can see both for the same project and say so. Housekeeping in a launcher's
hot path is a failure with nowhere useful to go.

## 21:05 · finding · T4.3 — the reboot audit reported "nothing is running" when tmux was BROKEN

Found by actually running the smoke harness on a box with no tmux, rather than reading the
code. `audit_sessions` consumed its listing from a process substitution:

```bash
while read -r name dir; do ... done < <(live_sessions)
```

A process substitution's exit status is not observable, so `ccy_tmux_list` failing produced an
empty loop and the function printed `(no sessions are running)` and returned 0. On a real host
with a broken tmux, `ccy-sessions reboot --dry-run` would have told an operator a reboot was
safe while sessions were running — the exact "could not tell" / "nothing to do" collapse this
plan's D8 is about, in the one command whose whole job is to answer that question.

Fixed by capturing the listing first and propagating the failure, in all three call sites.
`ccy_tmux_list` already distinguishes "no server yet" (0, empty) from a real failure (1), so
the two were always distinguishable — the caller just was not looking.

## 21:20 · decision · T3.1 — boot-time code that cannot be run is code verified by reading

`ccy-sessions-restore` hardcoded its install paths, which made it untestable: it runs once at
boot, from a unit, with nobody watching, and what it does is start AI agent sessions. Both ways
it can be wrong are silent.

`CCY_LIB` and `CCY_LAUNCHER` are now `${VAR:-default}` so the real script can be driven through
every branch of its retirement tree against real git repositories
(`scripts/test-ccy-session-restore.bash`, 35 cases, wired into qa-all). Written down at the
definition as a testing affordance and explicitly not a privilege boundary — anyone who can set
those can already run anything as this user, and under systemd the unit owns the environment.

The alternative was a harness reimplementing the decision tree, which would have passed while
the real script was broken.

## 22:40 · finding · T6.2 — qa-reviewer round 1: 2 blocking, 5 fix-before-merge, 8 should-fix, 6 nits

All resolved. The two that mattered most were both cases of a control reporting a confident
wrong answer rather than failing:

- **`stale` retired exactly the sessions the feature exists for.** Age was measured from the
  record's mtime, which is when the SESSION STARTED — so a session running permanently for a
  fortnight was dropped as stale at the very reboot it was meant to survive. Now measured
  boot-to-boot via `/proc/stat`'s `btime`, which is the question that was always meant.
- **A registry listing failure was laundered into "nothing to restore"** in four places, the

a session and the pane inherits the SERVER's environment — so the variable would have arrived
for the first restored session and quietly not for any after it. Now delivered with `env` inside
the tmux command, and asserted against a recording stub.

## 22:55 · finding · T6.2 — `$(…)` strips NUL bytes, and it bit three times

My fix for the listing bug introduced a worse one: `listing="$(ccy_registry_list "$dir")"`
silently concatenated every record path, because command substitution drops NUL — the very
delimiter chosen precisely because a path may contain anything else. Two records became one
nonexistent path.

Same trap in the SSH-key decode fix minutes earlier, and the test harness hit it a third time
capturing NUL-delimited flags. Where both the data and the exit status are needed, the read now
goes through a temp file or a deliberate second pass, never `$(…)`. Written into
`DESIGN-failure-modes.md` so the next person does not rediscover it.

## 23:05 · finding · T6.2 — `--syntax-check` passed a playbook whose handlers had eaten 40 tasks

Adding a `handlers:` block mid-file put every subsequent task into the handlers list. Ansible's
`--syntax-check` returned rc=0, because handlers and tasks share a schema — so the play would
have parsed, run 21 tasks instead of 61, and executed the rest only on a notify that never came.

Caught by parsing the YAML and counting: 61 tasks / 1 handler is right, and the broken form

## 23:15 · decision · T6.2 — a stub that only exits 0 vouches for nothing

The restore tests stubbed `tmux` and `systemd-run` as `exit 0`, which meant the two properties
that live only in the constructed command — where `CCY_UNATTENDED` is delivered, and whether the
scope unit is unique per session — were asserted by nobody. The reviewer was right that the
test "asserts it nowhere".

The stubs now record their argv, the tmux stub remembers the sessions it creates and lists them
back, and `systemd-run` execs what follows `--`. That makes `ccy_tmux_next_name` do real
collision avoidance in the test, which is what exposed that a second session in one project
would have collided on the scope unit name and been lost after its record was already consumed.

## 00:10 · decision · T6.2 — `ccy-sessions` gets the same testability affordance, and a suite

The reviewer's sharpest point was procedural: three round-1 fixes landed in `ccy-sessions`, a
file with hardcoded install paths and **zero tests**, and were verified by reading — which is
precisely how the violations being fixed got in.

`restore-status` is the command that embodies this plan's central rule, and most of its states
only exist when something is broken: a masked unit, an unreachable user bus, a dangling `.wants`
symlink. None can be produced by asking nicely. So `CCY_LIB`/`CCY_LAUNCHER` became overridable
as they already were in the restore helper, and `scripts/test-ccy-sessions-status.bash` drives

Writing it immediately found two things: the `enabled-no-linger` advice split "will not run at
boot" across two lines so it never read as one sentence, and my unreadable-registry case was
vacuous — `chmod 000` does nothing to root, which is what this suite runs as. That case now
fails `mktemp` instead, which no uid is exempt from.

## 01:35 · decision · T6.2 — the shared global becomes a caller-named array

Round 3 noted `ccy_registry_list` had no production caller, which was true: it existed because
`ccy_registry_collect` filled a global that nothing in its own file read, and deleting the
wrapper would have left that global flagged as unused. Keeping a function alive to satisfy a
linter is a bad reason, and I had written it down as one.

`ccy_registry_collect <dir> <array-name>` uses a nameref instead. No global to clobber between
two consumers, no wrapper, and each caller names its own array. One caveat, now written into the
test: a nameref cannot write through `$( … )`, so the function must never be called inside a
command substitution — which is how the first version of the new assertion failed.

## 02:10 · finding · T6.2 — round 4: sorting the records quietly made the listing maskable

All eight round-3 findings confirmed fixed. The one new thing that mattered was caused by the
smallest change in the previous round: adding `| LC_ALL=C sort -z` for a stable order made
`find` stage one of a pipeline, so without `pipefail` a failing find is masked by a succeeding
sort and the listing returns success with no records. Measured: `set -euo pipefail` propagates,
`set -eu` returns 0 with an empty array — and `claude-yolo` runs `set -e` alone.

Not live, because both front-ends happen to set `pipefail` and GNU find's stderr is caught by
the secondary check. But the guarantee had gone from unconditional to conditional on an option
the caller happens to have set, in the one function whose entire purpose is that the guarantee
holds. `pipefail` is now set inside the subshell, and the probe that found it is repeated above
to confirm the fix.

Three of the four remaining findings were documentation that had fallen behind the code in the
same commit that changed it, and one was that F1's own fix had no test — raised, fairly, in the
commit about fixes verified by reading. The retention validation now has six cases.
