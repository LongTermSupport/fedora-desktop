## 14:42 · finding · the writer half is present and has exactly the shape the plan argued for

`v3.65.0` ships `hooks-daemon signal`. Readings, verbatim from the run:

```
W1  the 'signal' subcommand                 present
W2  accepted kinds                          {reboot-warning,shutdown-warning,reboot-cancelled}
W3a reboot-warning --minutes 5              exit 0, file written
W3b reboot-cancelled with NO --minutes      exit 0, file written
W3c reboot-cancelled WITH --minutes         exit 1  "takes no --minutes payload"
W4a reboot-warning with NO --minutes        exit 1  "requires --minutes N"
W4b reboot-warning --minutes 0              exit 1  "requires a positive integer"
W5  an unrecognised kind                    exit 2  (argparse, before the command runs)
W6b every key in the payload                kind,minutes,session_id,source,ts
W7  after a cancel                          same path, kind=reboot-cancelled
W8a --all-sessions, no live session          exit 1  "nothing to signal"
W8b --all-sessions, one sidecar              exit 0
```

Four of these matter beyond "it exists".

**The payload has no free-text field.** `kind,minutes,session_id,source,ts` — that is the
whole key set, enumerated rather than checked against a list of expected names, so a new
field would have shown up instead of being skipped. The issue's security note asked that the
helper "never composes a message; it only names a signal kind and a number", and the shipped
artefact makes that structural rather than conventional. The wording an agent sees is
composed on the reader side from fixed templates. So `notify` can be implemented without
inventing a local substitute, and without `inject-goal`'s free-text channel — the reason F7
gave for refusing to fake it is now moot rather than merely tolerable.

**W5 exits 2, not 1.** An unknown kind is refused by the argument parser before the command
runs; a well-formed-but-wrong request (W3c, W4a, W4b) exits 1. A caller that treats "non-zero"
uniformly throws away that distinction. Worth having written down before the seam is coded.

**W7: a cancel supersedes rather than accumulating.** Both kinds write the same
`<session>.operator-signal` path, so `reboot-cancelled` overwrites the warning instead of
sitting beside it. A called-off reboot therefore cannot leave a stale warning readable — which
is the behaviour wanted, but it is a property of the path, not of the payload, and nothing in
the payload would have revealed it.

**W8a is the one that shapes `reboot --in N`.** `--all-sessions` with nothing live exits 1
naming "nothing to signal", rather than succeeding vacuously. The header comment on
`ccy_reboot_signal_blocked` already reasons about precisely this case — it says the seam is
called once, unconditionally, before any per-session loop, so that a reboot on an idle machine
cannot exit 0 having warned nobody. That reasoning survives, but its consequence flips: the
real command FAILS on an idle machine, so `reboot --in N` has to decide deliberately whether
"no sessions to warn" is a reason to refuse to reboot or a reason to proceed. It is a design
question, not a detail, and it is now on the table rather than hypothetical.

## 14:48 · finding · the reader half is ABSENT on this branch, and only the reader probe could see it

This is the finding that justified building a script instead of reading the release notes.

```
A1  the supervisor script in this checkout   present
A2a load_operator_signal in the supervisor   NOT DEFINED — this checkout predates the capability
A3a kind strings the WRITER defines          reboot-cancelled,reboot-warning,shutdown-warning
A3b kind strings the READER defines          <none>
A3c do the two sets agree                    NO
A4  where the wording is composed            no renderer found in the reader
```

`.claude/ccy/claude-supervise.py` is **tracked**, so a branch carries whatever version its own
history has. This branch's copy predates the upgrade and has no reader at all. The writer is
reachable here — `.claude/hooks-daemon` is a symlink to the shared clone, so the CLI is
v3.65.0 — while the consumer is at the branch's commit. Half the channel.

**The failure shape is why this needed a probe.** `signal` exits 0 on a successful write and
knows nothing about whether anything ever reads the file. Implement `notify` against it on this
branch today and every command reports success, every test of the writer passes, and no agent
is ever warned about anything. There is no error to notice. A check that confirmed only "the
signal command works" would have been clean and blind at the same time — the class this repo
keeps rediscovering.

Two further points on how that check was built, because both were nearly wrong:

- **Defined is not wired in.** A2 counts call sites separately from the definition, because a
  `load_operator_signal` that exists and is never called consumes nothing while satisfying a
  grep for its definition.
- **The two sides are compared against each other, not against me.** The suffix and kind
  strings are duplicated by necessity — the supervisor is stdlib-only and cannot import the
  daemon package — so the probe extracts each side's own literals and compares the sets. A
  third copy hardcoded in the probe would have been one more thing to drift, and would have
  reported agreement with itself.

## 15:30 · action · the seam raises real signals now, per project

`ccy_reboot_signal_blocked` is gone; `ccy_reboot_raise_signal` replaces it and does the work.
Three things about its shape were decisions rather than transcription:

**Per project, not per session.** The daemon writes into the project's own context-sidecar
directory and its `--all-sessions` enumerates that project's sessions itself. So live sessions
are grouped by directory and each project's CLI is called once. That is fewer calls, but the
reason is correctness: it is the only form that reaches a session whose id this script never
learns. Two sessions in one project are one call, and there is a test asserting exactly that —
a per-session loop would warn the same sessions twice.

**Every project must succeed.** A project that could not be signalled fails the whole command,
on the ground `audit_sessions` already stated: a partial warning is worse than none because it
reads as complete. This is not a hypothetical branch — W8a showed the daemon exits 1 when a
project has no live session of its own, so a real machine reaches it.

**Nothing running is a success with a sentence.** There is genuinely nobody to warn, so it
exits 0 — but it says so, rather than being silent, because silence here is indistinguishable
from having warned everybody.

`shutdown-warning` is now accepted too; the daemon has always offered it and the script's kind
list was the narrower of the two. The minutes rules are enforced locally AND by the daemon,
which is a deliberate second copy: the local one exists for the message a human mistyping the
command should read. Its comment says so, and says the daemon wins if they ever disagree,
since the daemon is what writes the file.

## 15:38 · finding · the test stub could not have caught a wrong call, so it was replaced

The suite's fake project CLI was `#!/bin/sh\nexit 0\n`. That was sufficient while the seam only
ever refused. The moment the seam actually invokes it, a stub that exits 0 whatever it is handed
**cannot distinguish "called with the right kind and number" from "called with neither"** — so
every assertion I was about to write about what `notify` passes would have been green against a
command that passed nothing at all.

It now records its argv, and the assertions read it. Falsified with two mutants:

```
m1  drop the --minutes pass-through          → FAIL  passing the minutes through
m2  raise the warning on the refusing path   → FAIL  reboot --in signals NOTHING before refusing
```

Each killed by exactly the assertion written for it, and the suite went 59 → 82 cases. m2 is
the one I care about most: it proves the refusal happens *before* anything is signalled, which
is the property that stops `reboot --in N` leaving every session winding down for a reboot that
is not coming.

## 15:44 · handoff · what is done, and the one decision left

`notify` is complete and tested. `reboot --in N` still refuses — but for its own reason now,
not a missing dependency: **the countdown and the reboot call were never designed**, and no task
in this plan specified them. That is recorded as Task 4.5, an owner decision, with the two
options written out.

I deliberately did not implement it. Warning every session and then not rebooting is not a safe
subset of the behaviour, it is a new wrong state — so the choice is between doing the whole
thing and doing none of it, and the whole thing means adding a destructive host operation this
plan never scoped. `shutdown -r +N` is the obvious primitive if the answer is yes (it owns the
countdown, survives the terminal, and `shutdown -c` pairs with `notify reboot-cancelled`), but
picking it is not mine to do quietly while closing a task.

Still outstanding and unchanged: the HOST acceptance items. A5 from the triage — that a live
session is really interrupted and shown the sentence, within the supervisor's poll interval,
including one started before the signal — needs a host with a real session attached, and no
amount of work in this container establishes it.

## 16:05 · action · A5 is now one command, because "needs a host" is not the same as "needs a human to improvise"

`acceptance-signal.bash` establishes A5. I could not run it, but leaving A5 as a paragraph
asking someone to check by hand would have been the weaker half of a handoff: the assertions
are the part I actually know, and they are the part that goes stale in prose.

What it asserts, and why each is more than it looks:

- **[0] refuses to render a verdict with no live session.** `notify` exits 0 saying "nobody to
  signal" on an idle machine, so every later check would pass having exercised nothing — the
  same trap Plan 00099's check `[0]` exists for, in a plan that had not yet learned it.
- **[3] reads the supervisor's STATUS MESSAGE, not the signal file's absence.** The distinction
  is the whole value of the check: a file can be deleted without a word reaching anyone, so
  "consumed" is not "rendered". The status message is written from the supervisor's own fixed
  template, which makes its presence proof the sentence was composed.
- **[4] asserts the retraction renders too.** A cancel that is written and never shown leaves a
  session counting down to a reboot that was called off.
- **[5] asserts the host did not reboot**, from uptime. Stated rather than assumed, because it
  is the property an operator most needs this script to have kept.

It carries a COVERAGE line and REJECTS an incomplete run even with no failures — Plan 00099's
M2, applied here before anyone had to find it again.

Two properties that are deliberate rather than incidental. It **retracts on the way out via an
EXIT trap**, including on failure, so a failed test cannot leave a real session believing a
reboot is coming. And a timeout on `[3]` is reported as "not observed within the window" with
the reason named — the supervisor only reads a signal while the session is idle and in MONITOR
state — rather than as a failure of the channel, because those are different findings and only
one of them is a bug.

Verified as far as a container permits: it lints clean, and `plan_require_host` refuses to run
here, naming the marker it found. That refusal is the point — a green run in this container
would have been the confident wrong answer R2 exists to prevent.
