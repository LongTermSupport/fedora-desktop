## 06:15 · finding · — — there were TWO defects in the block, and I had flagged the lesser one

The recorded finding was the false negative: `grubby … 2>/dev/null | grep -q` reports
`No legacy cgroup configuration found` when grubby *fails*.

Reading the block to write that fix turned up a second one I had not seen. `error()` is:

```bash
error(){
  echo -e "${RED}${CROSS} $1${NC}"
}
```

**It does not exit.** So the removal-verify branch prints "Failed to remove cgroup configuration",
prints two lines of manual instructions, falls out of the `if`, and the installer carries on to
completion and exits **0** — on the one path where it has *positively established* that the box is
misconfigured.

That is the banned skip-and-warn pattern, and it is worse than the defect I had flagged. Defect 1
is ignorance mistaken for knowledge; defect 2 is knowledge discarded.

The generalisable bit: I had read the block well enough to characterise one defect precisely, and
still missed a second in the same fifteen lines — because I was reading for the thing I had already
named. Opening it to *fix* rather than to *describe* is what surfaced the other. An argument
against banking findings for later.

## 06:20 · decision · D2 — only a NON-ZERO grubby exit is fatal

The crude fix ("if the check cannot run, abort") would make any box where grubby misbehaves fail an
install that works today. That trades a false negative for a false positive, which is not obviously
progress.

The distinction the current code destroys is available for free once the pipe goes: **exit 0 with
no legacy args** is a real negative answer; **non-zero** is "could not look". Only the second is
fatal, so a box with unusual boot entries that still exits 0 behaves exactly as it does now.

Stated as open question 1 rather than buried: grubby is not installed in this container, so I could
not measure what it returns with zero boot entries. If that case exits non-zero, such a box would
newly abort. The message names precisely what happened, which is why I still think fatal is right —
but it is an unmeasured case and the owner should know that rather than discover it.

## 06:25 · decision · D3 — `fatal` exists because its absence is HOW the bug happened

`hl_abort` covers headless. Interactive has `error`, which prints and returns. So a fatal condition
reachable from both paths had **no correct call available**, and the interactive half degraded into
print-and-continue.

Worth naming: nobody decided to skip and warn. It was the absence of an easy way to do the right
thing. Adding `fatal` is therefore more than tidying — it removes the gradient that produced the
defect. Deliberately not retrofitted to existing `error; exit 1` sites; the plan carries an explicit
Non-Goal recording that other `error`-without-`exit` sites may well remain and have NOT been
audited, so nobody reads this as a sweep.

## 06:30 · finding · T1.1 — the RED run was honest and completely uninformative

All four legs failed. Correct — the function did not exist. But all four failed with the *same*
message:

```
[FAIL] check_legacy_grub_cgroup() not found in …/run.bash
```

That is the uniform-failure shape `bash-standards` §9 warns about by name: it proves nothing about
any individual leg, because all four would fail identically for any breakage. A RED run is not
automatically an informative RED run — this one only established "the function is absent".

## 06:35 · action · T1.2 — perturbation, and a clean diagonal

Rather than assert the legs work, each defect was reintroduced separately in a fixture copy:

```
as shipped (expect all PASS)           clean=PASS  legacy=PASS  stuck=PASS  broken=PASS
defect 1 back (expect broken FAIL)     clean=PASS  legacy=PASS  stuck=PASS  broken=FAIL
defect 2 back (expect stuck FAIL)      clean=PASS  legacy=PASS  stuck=FAIL  broken=PASS
control: msg text (expect clean FAIL)  clean=FAIL  legacy=PASS  stuck=PASS  broken=PASS
```

One perturbation, one failing leg, the right one, three times. The two working paths hold under
every perturbation that breaks a different leg — the inertness claim measured rather than asserted.

The perturber verifies its own rewrite landed. A replacement matching nothing yields a perfect copy
and would report "all legs still pass" — the exact false-green this script exists to detect, so it
had to be immune to it (`bash-standards` §5).

## 06:40 · thought · T1.1 — the stub is not a compromise here, unlike in Plan 00073

Worth distinguishing, because "tested with a stub" sounds like the same weaker-than-a-host trade in
both plans, and it is not.

Plan 00073: a container genuinely cannot show that a password obtains privilege. The stub proves
strictly less than a host, and Task 3.3 there is load-bearing.

Plan 00074: the state space is four states and the stub drives all four. **A real box exhibits
exactly one.** The stub therefore exercises strictly *more* than a host run. What a host adds is
confidence that real grubby output falls into the state the fixture models — a question about the
fixture's realism, not about the logic.

Same technique, opposite epistemic status. Conflating them would either overclaim 00073 or
underclaim this one.
