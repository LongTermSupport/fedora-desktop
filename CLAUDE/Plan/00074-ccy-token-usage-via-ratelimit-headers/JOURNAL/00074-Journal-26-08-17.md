## 12:10 · decision · T1.2 — direct curl, not `claude -p`, and why the ask was inverted

Owner asked to prototype with `claude -p --model haiku` and no tools, "so it's
as minimal as possible". Two findings invert that:

1. **`claude -p` cannot deliver the payload.** The payload here is the RESPONSE
   HEADERS. Grepping the binary, the only places the header names appear are a
   mock/scenario harness (`setScenario`, `addExceededLimit`, `setEarlyWarning`)
   that *synthesises* them for testing — plus the parser that consumes them.
   There is no debug or print path that emits them (F12). `--debug` was the one
   plausible route and nothing suggests it logs them.
2. **`claude -p` is the LESS minimal option.** Even with tools disabled it ships
   a large system prompt and the tool schemas as input tokens. A bare
   `POST /v1/messages` with `max_tokens: 1` and a one-character message is far
   cheaper.

So: curl is the mechanism. The `claude -p` arm is kept in the prototype as a
**control**, so "the CLI can't do this" is a tested claim rather than my
assertion — if it does surface the headers, the report will say so.

Haiku kept from the owner's instinct, and it is a good one: the weekly buckets
are per-model (`seven_day_opus`, `seven_day_sonnet`), so probing with the
cheapest model avoids spending the allowance that actually matters.

Also grounded F11: `anthropic-beta: oauth-2025-04-20` is the only oauth-dated
beta string in the binary, so that is the header the prototype sends.

## 12:14 · finding · T1.3 — floor division made the countdown a full unit wrong

Stub returned a 7d reset exactly 3 days out. Rendered as **`r2d`**. And a 5h
reset exactly 2 hours out rendered as **`r1h`**.

Cause: floor division. Two seconds after the header is issued, 259200s has
become 259198s, and `259198 / 86400 == 2`. The value is never *quite* the round
number by the time it is rendered, so it always drops a whole unit.

Fixed to round-to-nearest (`(delta + 43200) / 86400` etc.). Now `r3d` / `r2h`.

Worth noting this bug shape existed in the Plan 00073 jq renderer too — same
floor logic — and would have shipped there unnoticed had that plan survived,
because its fixtures used epochs already in the past, which render as empty.
The fixture choice hid it.

## 12:18 · finding · T1.3 — `$?` after `fi` is 0, not the condition's status

`grep_lines()` classified a legitimate no-match as a grep crash. Output was the
self-contradicting `ERROR: grep failed (exit 0)`.

Cause is a classic bash trap:

```bash
if out="$(grep ...)"; then
    return 0
fi
rc=$?          # <-- 0, ALWAYS. The `if` statement itself succeeded.
```

After `if cmd; then …; fi` with no else branch, `$?` is the status of the `if`
*statement*, which is 0 when no branch ran. The condition's status is gone.

Fixed by reading the status inside an `else` branch, where `$?` is still the
condition's. The distinction matters here rather than being pedantry: grep exit
1 (no match) is DATA — the header is absent — while exit 2 is a real failure,
and flattening the two is exactly the error-hiding this repo forbids.

Both bugs surfaced from testing the FAILURE paths, not the happy path. The happy
path had been green throughout.

**ARM 2 (`claude -p --tools "" --debug`): exit 0, 17,855-byte debug log, zero

### The header set is wider than the four we assumed (F15)

| Header (suffix after `anthropic-ratelimit-unified-`) | Shape observed         |
| ---------------------------------------------------- | ---------------------- |
| `status`, `5h-status`, `7d-status`                   | `allowed`              |
| `5h-utilization`, `7d-utilization`                   | **float** (`0.0`, `0.02`) |
| `5h-reset`, `7d-reset`, `reset`                      | epoch seconds          |
| `representative-claim`                               | `five_hour`            |
| `fallback-percentage`                                | float                  |
| `overage-status`, `overage-disabled-reason`          | enum strings           |

`representative-claim` is the useful surprise: the API states which bucket is
actually binding, so the menu can lead with that instead of inferring it from
whichever percentage looks worst. Straight into Task 3.3b.

### The catch — Q2, and why I am not shipping a renderer yet

Utilisation came back `0.0` and `0.02`. **I cannot tell from this sample whether
the scale is 0–100 or 0–1**, and the two readings differ by 100×: `0.02` is
either 0.02% or 2%. The probed account is near-idle, so both fit.

`%.0f` renders `0%` under either reading, which is why the stub tests never
surfaced this — the fixtures used `37` and `82.6`, values that only exist on the
0–100 reading. I chose those numbers assuming the answer.

**The discriminator is one-way and costs one request**: any value **> 1** proves
0–100, because a fraction cannot exceed 1. So the next probe must target a
*heavily-used* account, not another idle one. A value ≤ 1 there proves nothing
and means trying a busier account still.

Recorded as Q2 / Task 2.3. No renderer ships until an observed value settles it —
a usage display that is wrong by 100× is worse than no usage display.

### Two switches for the scale, and why the raw value is stored raw

- `CCY_USAGE_SCALE=percent|fraction` — read in `_usage_normalise()` and nowhere
  else.
- `CCY_USAGE_DEBUG=1` — appends `[API sent 0.02]` to each line.

First cut normalised at FETCH time. That was wrong twice over: under
`fraction` the "raw" debug value would have shown the *converted* number (a lie,
and the debug switch exists precisely to see what the API sent), and it would
have frozen the scale into the cache, so flipping the switch would need a refetch
— which costs quota. Normalising at display instead means **the switch applies to
data already in hand, with no extra spend**. Caught by reading the fraction-mode
output and noticing `[raw 2.0000]` where `0.02` was sent.

A wrong scale now renders absurdly (`9140%`) rather than clamping to 100%. That
is deliberate: a real API cannot send >100 under the correct reading, so an
out-of-range figure is a diagnosis rather than a silent wrong answer.
