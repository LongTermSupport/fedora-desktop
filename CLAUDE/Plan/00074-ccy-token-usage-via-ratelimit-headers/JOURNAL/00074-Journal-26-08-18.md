# Plan 00074 — Journal 2026-08-18

## Every account shows `<1%` — the question Decision 4 deferred has come due

Reported in use: all accounts, both buckets, `<1%`. Decision 4 shipped on the
unproven `percent` reading of `-utilization` precisely because Q2 could not be
settled without spending quota, and named this as the risk. It is now the
observed behaviour.

### What the code does, read end to end

The path is short enough to hold in one piece:

- `_usage_extract` pulls the four values out of the dumped response headers and
  stores them **exactly as sent** — deliberately, so `CCY_USAGE_DEBUG`'s "raw"
  stays honest and flipping the scale does not need a refetch.
- `_usage_normalise` is the only place that knows the scale: `percent` (default)
  passes the value through; `fraction` multiplies by 100.
- `_usage_pct_int` rounds with `printf '%.0f'`; `_usage_pct_label` turns a
  non-zero value that rounds to zero into `<1%` rather than `0%`.

So `<1%` requires a raw value that parses as a number, is greater than zero, and
is below 0.5. Under a 0-1 fraction scale that covers **0-50% of real usage** —
which is where four accounts would plausibly all sit.

### Two hypotheses, not one

**H1 — the scale is `fraction`.** Fits the symptom exactly. A single raw value
above 1 anywhere kills it outright, which is what makes it cheap to test.

**H2 — the numbers are right and the bucket is wrong.** The probe uses Haiku on
purpose: the header comment records that the weekly buckets are **per-model**, so
probing with the cheapest model leaves the Opus/Sonnet allowances alone. The
flip side is that the weekly figure displayed may be *Haiku's* weekly allowance,
which for a heavy Opus user is genuinely near zero. That would be a real reading
of the wrong thing, not a scale bug. H1 and H2 can both be true.

Not writing down which I believe. The last three sittings on this repo have made
the point that a plausible reading of code loses to a measurement.

### The cheap probe: the answer is already on disk

The important realisation is that **no new spend is needed**. The cache holds the
raw values as the API sent them, from the last time the user pressed `u`. So
`triage.bash` defaults to reading `~/.claude-tokens/ccy/usage-cache/*.summary`
and prints, per account and bucket:

    RAW (as sent) | AS PERCENT (what ccy shows today) | AS FRACTION (what it would show)

Side by side, because the scale question is answered by whether the fraction
column matches what the user believes they have used — a judgement only they can
make. The script renders no verdict; that is `acceptance.bash`'s job.

It refuses to print an empty section: no cache directory, or no `.summary`
files, and it exits 1 naming what to run (`ccy`, press `u`, quit) and stating
that this costs one billed Haiku request per account. An empty table here would
read as "the API sent nothing", which is a different and wrong finding.

`--headers` is the one active probe, behind a flag per the triage rules. It
spends exactly one request against the first account and dumps **every**
`anthropic-ratelimit-*` header — the cache cannot answer that, because it keeps
only the four values ccy displays, so whether other buckets or a status header
are also being sent is invisible from it. Token goes to curl via `--config` on
stdin (BSH-09). The dump is checked for credential-shaped strings and deleted
rather than logged if the check trips — the Authorization header is on the
request, not the response, so it should never be there, which is exactly the
kind of "should" that PlanTriage says to verify rather than trust.

Account names are reported as `account-1`, `account-2`, … The token filenames
are personal aliases, and the ordering is all the debugging needs.

### One thing fixed on the way past

`usage_render_block` dropped a bucket whose value was empty with a bare
`continue` — three lines below its own comment saying "a silently missing bucket
reads as 'this account has no weekly limit', which would be a lie". The comment
was right and the code did the other thing. Reachable in practice, because
`_usage_extract` succeeds when **either** bucket is present, so a response
carrying only the 5-hour figure would silently render an account as having no
weekly limit at all. Now it says so on its own row. lib 1.10.1.

Worth noting the shape: this is the same defect class as Plans 00075/00076 — an
absent fact presented as a confident statement about the world — and it survived
a review in which someone wrote the correct rule as a comment directly above it.
