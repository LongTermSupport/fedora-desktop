# Plan 00074 — Journal 2026-08-18

## Every account shows `<1%` — the question Decision 4 deferred has come due

Reported in use: all accounts, both buckets, `<1%`. Decision 4 shipped on the
unproven `percent` reading of `-utilization` precisely because Q2 could not be
settled without spending quota, and named this as the risk. It is now the
observed behaviour.

### What the code does, read end to end

The path is short enough to hold in one piece:

- `_usage_extract` pulls the four values out of the dumped response headers and
  stores them **exactly as sent** — deliberately, so `CCY_USAGE_DEBUG`'s "raw"
  stays honest and flipping the scale does not need a refetch.
- `_usage_normalise` is the only place that knows the scale: `percent` (default)
  passes the value through; `fraction` multiplies by 100.
- `_usage_pct_int` rounds with `printf '%.0f'`; `_usage_pct_label` turns a
  non-zero value that rounds to zero into `<1%` rather than `0%`.

So `<1%` requires a raw value that parses as a number, is greater than zero, and
is below 0.5. Under a 0-1 fraction scale that covers **0-50% of real usage** —
which is where four accounts would plausibly all sit.

### Two hypotheses, not one

**H1 — the scale is `fraction`.** Fits the symptom exactly. A single raw value
above 1 anywhere kills it outright, which is what makes it cheap to test.

**H2 — the numbers are right and the bucket is wrong.** The probe uses Haiku on
purpose: the header comment records that the weekly buckets are **per-model**, so
probing with the cheapest model leaves the Opus/Sonnet allowances alone. The
flip side is that the weekly figure displayed may be *Haiku's* weekly allowance,
which for a heavy Opus user is genuinely near zero. That would be a real reading
of the wrong thing, not a scale bug. H1 and H2 can both be true.

Not writing down which I believe. The last three sittings on this repo have made
the point that a plausible reading of code loses to a measurement.

### The cheap probe: the answer is already on disk

The important realisation is that **no new spend is needed**. The cache holds the
raw values as the API sent them, from the last time the user pressed `u`. So
`triage.bash` defaults to reading `~/.claude-tokens/ccy/usage-cache/*.summary`
and prints, per account and bucket:

    RAW (as sent) | AS PERCENT (what ccy shows today) | AS FRACTION (what it would show)

Side by side, because the scale question is answered by whether the fraction
column matches what the user believes they have used — a judgement only they can
make. The script renders no verdict; that is `acceptance.bash`'s job.

It refuses to print an empty section: no cache directory, or no `.summary`
files, and it exits 1 naming what to run (`ccy`, press `u`, quit) and stating
that this costs one billed Haiku request per account. An empty table here would
read as "the API sent nothing", which is a different and wrong finding.

`--headers` is the one active probe, behind a flag per the triage rules. It
spends exactly one request against the first account and dumps **every**
`anthropic-ratelimit-*` header — the cache cannot answer that, because it keeps
only the four values ccy displays, so whether other buckets or a status header
are also being sent is invisible from it. Token goes to curl via `--config` on
stdin (BSH-09). The dump is checked for credential-shaped strings and deleted
rather than logged if the check trips — the Authorization header is on the
request, not the response, so it should never be there, which is exactly the
kind of "should" that PlanTriage says to verify rather than trust.

Account names are reported as `account-1`, `account-2`, … The token filenames
are personal aliases, and the ordering is all the debugging needs.

### One thing fixed on the way past

`usage_render_block` dropped a bucket whose value was empty with a bare
`continue` — three lines below its own comment saying "a silently missing bucket
reads as 'this account has no weekly limit', which would be a lie". The comment
was right and the code did the other thing. Reachable in practice, because
`_usage_extract` succeeds when **either** bucket is present, so a response
carrying only the 5-hour figure would silently render an account as having no
weekly limit at all. Now it says so on its own row. lib 1.10.1.

Worth noting the shape: this is the same defect class as Plans 00075/00076 — an
absent fact presented as a confident statement about the world — and it survived
a review in which someone wrote the correct rule as a comment directly above it.

## Q2 answered: the scale is a fraction, and it cost nothing to find out

`triage.bash` ran on the HOST. Eight samples, four accounts, straight out of the
cache the user had already paid for — no new request:

    account-1   5h 0.14   7d 0.09
    account-2   5h 0.06   7d 0.04
    account-3   5h 0.08   7d 0.41
    account-4   5h 0.15   7d 0.13

Every value `<= 1`. Read as fractions: 14%/9%, 6%/4%, 8%/41%, 15%/13%.

### Why this is strong evidence and still not proof

The discriminator is one-way: a value **above 1** would prove the 0-100 scale
outright, because a fraction cannot exceed 1. **None appeared.** Eight values all
below 0.5 are *consistent* with the percent reading too — they would just mean
four accounts sitting at 0.04%-0.41% of their allowances.

Two things make that reading untenable rather than merely unlikely. The machine
runs ccy sessions all day, so "essentially zero usage on all four accounts" is
contradicted by what the box is doing. And account-3 shows 7d = 0.41 against
5h = 0.08 — a weekly figure five times the five-hour one, which is exactly what
accumulation across a week looks like and is meaningless at 0.41%.

So: flipped the default to `fraction`. But the honest position is an inference,
not a measurement, and the plan has already been burned once by shipping on the
unproven reading.

### The part that matters more than the flip

An inferred premise that cannot be contradicted is indistinguishable from a wrong
one. `_usage_bar` clamped `p` to 100 — so if the scale were wrong the other way,
a raw 34 would normalise to 3400, clamp to a full green bar, and look *fine*. The
error would be invisible by construction, exactly as `<1%` was invisible until
someone thought it looked odd.

`_usage_scale_conflict` makes the assumption self-refuting: a raw value the
assumed scale cannot produce — above 1 under `fraction`, above 100 under
`percent` — prints

    5-hour limit   SCALE MISMATCH — API sent 34, impossible under CCY_USAGE_SCALE=fraction
                     set CCY_USAGE_SCALE=percent and report it (Plan 00074)

rather than drawing a bar. If Anthropic ever switches the header to 0-100, ccy
says so on the first fetch instead of silently reporting 100% forever.

Verified all six cases against the deployed renderer, including the boundary:
raw `1.0` is exactly 100% and must **not** trip the guard. It does not — it draws
a full red bar, which is correct.

### On the triage design

The thing that made this cheap was the decision to store raw values in the cache
and interpret the scale at *display* time. That was made a day earlier for a
different reason — so flipping `CCY_USAGE_SCALE` would not require a refetch —
and it paid off here in a way nobody planned: the answer to a question that
looked like it needed fresh API calls was already sitting on disk, and the
default triage run spent nothing at all.

H2 (is the weekly bucket the Haiku one?) is untouched and unrefuted. It was never
in competition with H1 — it concerns *which* bucket the number describes, not how
to read it. Task 5.5 opened: the response carries `-representative-claim` naming
the binding bucket, and the extractor currently throws it away.

## H2 answered by asking the API instead of inferring — F15 finally used

H2 was "the numbers are right but the bucket is wrong": the probe uses Haiku
because the weekly buckets are per-model, so a heavy Opus user could sit near
zero on Haiku's weekly allowance while their real limit is elsewhere. It was
never in competition with H1 — it concerns *which* bucket the figure describes,
not how to read it — so answering the scale question left it exactly where it
was.

It turns out the API has been answering it all along.
`anthropic-ratelimit-unified-representative-claim` names the bucket the API
considers binding. It was written down as **F15** when the header set was first
mapped, with the note *"exactly what a one-line menu column should lead with"* —
and then the extractor was written to pull four values and drop everything else.
So the fact was recorded, judged important, and discarded in the same plan.

Now captured and shown:

    5-hour limit   ███░░░░░░░░░░░░░░░░░   14%   resets in 4 hours
    weekly limit   ████████░░░░░░░░░░░░   41%   resets in 5 days
    binding limit: 5-hour limit

A `seven_day_opus` claim states outright that the weekly figure above it is not
the allowance being reported against, which is H2 answered from data rather than
from reasoning about which model the probe used.

### Choices worth recording

**Unknown bucket names pass through verbatim.** The bucket set belongs to the
API. Mapping the four known tokens to friendly labels and dropping anything else
would mean a future `seven_day_haiku` silently vanishes — the display would show
two bars and no claim line, which reads as "no claim was sent". Passing the raw
token through is uglier and truthful.

**The new field is appended LAST.** A 4-field record from an older library reads
back with `claim` empty and renders exactly as before — verified. The reverse
(an older library reading a 5-field record) puts the joined tail into `r7`, which
fails the epoch regex and quietly drops the 7d reset text. That is a downgrade-
only cosmetic loss, and it is confined to one line because the field is last;
inserting it anywhere else would have shifted the utilisation values themselves.

**The claim value is checked for tabs and newlines** before it goes into a
tab-separated record. The API sends a bare token like `five_hour`, so it should
never fire — which is the reason to check rather than the reason to skip it. One
embedded tab would shift every field after it, and since it is the last field,
the corruption would be invisible until something else moved.

Seven stub shapes verified: full set, per-model weekly claim, no claim header,
the five label mappings, tab injection, 5-field render, 4-field render. The stub
practice has now caught bugs in every round of this plan that used it.
