# go-qa-ci: minor items the verifiers deferred (run 4: M5 to M12)

Each is non-blocking; to be picked up in a polish milestone.

- M5: docs/golangci.md:80-89 (8.2 recorded gaps): the self-gate turns off gosec G204 for the whole module and G306 for one test file (qa/golangci-overlay.yml), so the bundled Rule gosec::G204 is not active when the toolchain analyses itself. Both appear under 'Configuration exceptions' and in docs/record.md, but the 8.2 gap list does not name them. Add them to the list so the 9.2 record is complete.
- M5: tests/selfgate/selfgate_test.go merge() comment and docs/golangci.md:71 ('An overlay can add to the baseline but not change a value it sets'): this overstates what the code does. The overlay can still weaken the baseline by adding gosec.excludes or linters.exclusions.rules, because the baseline leaves those keys unset. Today it is held in check only by the exact-content pin in TestOverlayHoldsOnlyDocumentedExceptions. Reword the comment and doc so they do not imply the overlay can never weaken the baseline.
- M5: internal/tools/golangci.go (Config, 'project .golangci.* used as it is'): a consumer's own linters.exclusions rules or presets, new/new-from-rev baselines, or a narrowed linter set can hide findings without the project record seeing them. This needs to be covered by the M6 suppression detector. It is not recorded as a forward gap in docs/golangci.md.
- M5: internal/golangci/parse.go:17 codePrefixed: only five linters get linter::code identifiers. Other multi-check linters print the bare linter name. This is honestly recorded as a DETECTOR-SPEC 4.3 partial gap, so it is not blocking.
- M6: internal/suppression/directives.go:105 (disableProblem): a nolint directive naming `all` counts as a named rule. The tool reports it as unrecorded and a record entry with rule `all` licenses it, but it silences every linter just as a bare directive does. It should fail gqaci.suppression.bare (nolintlint require-specific treats `all` as non-specific). A record entry is still needed, so the record is not bypassed.
- M6: internal/suppression/golangci.go:203 (caps): leaving issues.max-issues-per-linter / max-same-issues unset is flagged as a suppression route. go-qa's own golangci run already forces both to 0 (internal/golangci/run.go:84), so the cap cannot hide anything from the defence. Every consumer with a minimal .golangci.yml gets two false findings, and to clear them must add the settings or record pointless exceptions. docs/suppression.md justifies this with 'the default caps hide findings', which is not true of go-qa's run.
- M6: internal/suppression/check_test.go:35: the 'unrecorded fails, recorded passes' table covers 10 routes. exclusions.presets, issues.new-from-merge-base, exclusions.paths, linters.disable and the staticcheck.conf whitelists are only tested for detection (golangci_test.go / staticcheck_test.go). Check() treats every route the same way, so licensing is proven in general, but the acceptance asks for a recorded/unrecorded pair for each route.
- M6: golangci.go:224 exclusionRules: entries without linters or text (for example several path-only or source-only rules) all become `exclusions.rules::*`, so one record entry licenses any number of them. This is documented, but it weakens the 'one decision per exclusion' property.
- M6: check.go:20: an unparseable file is reported under gqaci.suppression.unrecorded with no line number, although the parser error has a position. A separate identifier, or at least the line, would be clearer.
- M6: README.md:15-16 says the suppression tool 'fails every route'. That is a slight overclaim next to the gaps recorded in docs/suppression.md (README line 3 does disclaim conformance). docs/record.md: the table row added for fieldalignment is not aligned, and there is no blank line before '## Not yet built'.
- M6: Go tests in internal/golangci, internal/tools and internal/cli need golangci-lint on PATH. Without it they fail with a clear 'required tool' message, which matches the fail-fast intent. Recording this here in case CI is not set up to provide it.
- M6: Gaps recorded under 9.2 that will matter later: //go:build ignore, configurations passed with -c, golangci per-linter settings outside the closed list, and the bundled baseline's fieldalignment disable for consumers that have no config of their own.
- M7a: Part of the acceptance clause 'go-qa rules lists a project analyzer' is only proven in pieces. internal/cli/analyzers_test.go:19 lists gqaci_test, which comes from the test binary acting as go-qa. internal/vet/vet_test.go TestBuildProducesAVetToolFromTheProjectDriver lists project_nopanic, but it calls vet.Build directly. No CLI test sets [analyzers] driver and runs `go-qa rules`. I checked it by hand with the real binary on a scratch project that has a driver: `go-qa rules` printed 'analyzer  project_nopanic  forbids panic', rule-doc worked, `run -t analyzers` exited 1 with error[project_nopanic], a findings exception made it pass, and with the call removed the unused exception failed as gqaci.record.stale. A CLI test of that path would protect the wiring at internal/cli/analyzers.go:19.
- M7a: Findings exceptions whose rule is not a registered analyzer are never reported stale by any run. The cause is that internal/tools/analyzers.go:56 only judges registered names, and golangci findings staleness is also missing, which docs/record.md records as a gap. So a mistyped name or an analyzer removed from the driver leaves a dead entry. docs/analyzers.md could record this case explicitly.
- M7a: -p filters findings only after the whole module has been analysed (go vet ./... always runs). This is documented in docs/analyzers.md, but a single-file run costs as much as a full run (DETECTOR-SPEC 5.2 is met only in effect).
- M7a: In README.md, the new `go-qa rules` row of the commands table is wider than the other rows, so the table is misaligned (cosmetic).
- M7a: Without golangci-lint on PATH, `go test -race ./...` fails in internal/cli, internal/golangci and internal/tools. The failure is deliberate and loud (a required tool), and all tests pass with /workspace/untracked/tools/bin prepended to PATH. Noted so the gate command is always run with that PATH.
- M7b: driver/driver.go Main(extra...) passes only what the project hands it. A project that sets [analyzers] driver without also passing sensitiveformat.Analyzer quietly turns off a Blocking bundled defence, with no record entry. docs/analyzers.md describes this but does not list it as a gap. TOOLING-SPEC 2 says a Bundled defence is 'enabled by default in every Consuming project'. Consider having driver.Main always include the bundled suite (brief analyzers/suite All()), or list it under 9.2.
- M7b: analyzers/sensitiveformat/exposure.go holds(): the slog sink does not follow a pointer nested inside a value. slog's JSON handler marshals through nested pointers, so such a field is a missed finding there. The rule page's Limits line ('A pointer nested inside a value prints as an address') is only true for fmt.
- M7b: exposure.go slogSink: json.Marshaler and encoding.TextMarshaler are not accepted as redacting for slog, although the JSON and text handlers use them. Such types are false positives, and the workaround is a -redacting entry.
- M7b: The %q, %x, %X and %d verbs are not checked, though fmt prints struct string fields under them (%q quotes them; a bad verb still shows the value as %!d(string=...)). This is openly listed in the rule page's Limits, so it is not a conformance claim; it is still a hole worth closing later.
- M7b: go test ./... needs golangci-lint on PATH: without it, the internal/cli, internal/golangci and internal/tools tests fail with the fail-fast 'not found' message. This is by design, but it could be stated in the contributor docs.
- M8: README.md:3-6 and README.md:18-19 were not updated for M8. The gap index lists golangci.md, defences.md, suppression.md and analyzers.md but not docs/astgrep.md, which is the only place the ast-grep gaps against TOOLING-SPEC 4.2 and 5.3 are recorded (project rules are not listed and do not resolve through rule-doc). The Status paragraph still says every other tool engine is not built and fails as not implemented, which now misdescribes ast-grep.
- M8: ast-grep follows .gitignore files, including those of a parent repository. With the real binary (0.50.0), a fixture module placed under a gitignored directory produced no findings on a full run or a -p dir run, and the step reported 'passed' even though files contained matches. Passing an explicit file path did catch the match. The silent pass is not mentioned in docs/astgrep.md, and no test covers it. The same fixture in a non-ignored temp directory failed correctly.
- M8: internal/tools/astgrep.go:157-163: the project-rule scan does not pass scan_exclude as --globs. Only the bundled-pack scan applies it (astgrep.go:178). This may be intended, since sgconfig.yml has its own ignores, but docs/astgrep.md does not say that scan_exclude covers only the pack.
- M8: The tests that need the real binary (tests/astgrep) skip in CI and wherever ast-grep is missing. The skip states its condition and the gap is recorded in docs/astgrep.md. I ran them against ast-grep 0.50.0 from untracked/scratch and all 9 passed, as did the full go test -race suite with the binary on PATH. Nothing pins or checks the ast-grep version (already recorded as a gap).
- M9: docs/runners.md, table row for mutants: the command is still given as `gremlins unleash --threshold-efficacy N`. The fix commit 06a6cc3 stopped using that flag because gremlins ignores it, and the prose below the table says so. Only the table row was left uncorrected, so the page contradicts itself.
- M9: internal/runners/vuln.go ParseVuln: findings are deduplicated by OSV id plus module before the project record is applied, and the first trace is kept. Suppose one advisory is reached from two files and the record has an exception for the first file's path. The second call site is then never reported. A path-scoped exception ends up licensing the advisory everywhere in the module. Deduplicate after licensing, or key on OSV, module and call-site path.
- M9: The identifiers error[coverage], error[mod], error[test] and error[mutants] resolve to nothing: `go-qa rule-doc coverage` says dangling. docs/runners.md records the gap for GO-* and deadcode only. Runners are arguably not Defences under TOOLING-SPEC 4.2, but the dangling identifiers should either be recorded as a 9.2 gap or be given pages.
- M9: internal/runners/mutants_gremlins_test.go is the only real proof that the mutants threshold reaches gremlins. It skips when gremlins is absent (the skip is conditional and documented), and CI does not install gremlins, so CI never exercises the gate. The gap is recorded in docs/runners.md. It closes when gremlins joins the pinned toolchain (M12).
- M9: README says diff mode 'compares against the merge base with this ref', but the runner passes `--diff <base>` straight to gremlins. Whether gremlins diffs against the merge base or the ref tip was not verified, so the wording may overstate it.
- M9: Tests that call golangci-lint fail when /workspace/untracked/tools/bin is not on PATH. The failure is a clear 'not found on PATH' error, consistent with the rule that a missing tool is never a pass, and everything is green with that directory on PATH. Noted only so whoever runs the gates next does not misread it.
- M10: internal/stage/report.go:73 (ParseFindings) rejects a finding whose `file` leaves the stage `dir` (e.g. ../shared/b.ts). Argv deliberately passes such files that way (internal/stage/stage.go relativeToDir; stage_test.go TestFilesArePassedRelativeToTheStageDirectory expects ../shared/b.ts). So a findings stage with dir = "web" that lints a shared file fails as 'no usable findings'. Accept a file that resolves inside the root after path.Join(dir, file), not only one local to dir.
- M10: A status-output stage with no files_command and no {files} runs over the whole project under -p, and its output is shown unscoped (docs/stages.md 'A stage with no files_command runs whole'). That is a subset-run gap against DETECTOR-SPEC 5.2 / TOOLING-SPEC 4.4 for that stage, and docs/stages.md does not list it under 'Recorded gaps (TOOLING-SPEC 9.2)'. It should be recorded there.
- M10: A findings stage with no `rules` command never gets its findings exceptions checked for staleness (internal/tools/stages.go:100-108 passes an empty id list). docs/stages.md implies this but does not record it as a gap.
- M10: For a findings stage the record is applied even when the record itself is invalid. The run still fails through the `record` tool, so this is not a pass leak. It matches the other runners.
- M11: GitHub CI is red on HEAD 4346a96, but M11 did not cause it. The self-gate's vuln runner fails on stdlib advisories (GO-2026-4970, -6604, -4602, -6218, -4601) because CI installs Go 1.26.0 from go.mod's go-version-file; it has been red since 801f67c, before M11. The Public safety job also fails because the GQACI_DENYLIST repo secret is not set. In the same run the summary step passed, so the AGENTS.md region matches CI's golangci-lint.
- M11: .github/workflows/ci.yml:4: the header comment still says the self-gate runs 'every tool except summary and mutants'. Since M11 the summary tool is enabled through qa/go-qa.toml [summary] file and runs in the self-gate, so the comment is out of date.
- M11: internal/summary/summary.go:1-3: the package comment cites TOOLING-SPEC 5.3 for the agent summary. The clauses it serves are 7.1 and 7.2.
- M11: TOOLING-SPEC 7.1 (SHOULD) asks for each summary line to read as a standing instruction. golangci linter entries reuse the upstream descriptions instead ('Checks whether...', revive's 'Fast, configurable, extensible...'), which say what the tool does rather than what is forbidden. The 5.1 terse statement is technically present for each.
- M11: The tests in internal/cli/rules_test.go and internal/defences/defences_test.go (including the acceptance tests) fail when golangci-lint is not on PATH. That matches the earlier golangci tests and the 'absence is never a pass' rule, but it should be documented for contributors.

- M12: The 'Public safety' workflow has failed on every push since the repository was created, because the GQACI_DENYLIST repository secret is not set (.github/scripts/write-denylist.sh exits 1). Setting it is the owner's job, and the README says the workflow fails without it. Until it is set the denylist scan has never run in CI.
- M12: TOOLING-SPEC 9.1 grades the project level against the toolchain spec and also against section 7 of the method spec (Conforming defences, remediation docs, discoverable decisions). docs/CONFORMANCE.md's project level grades only TOOLING-SPEC sections 4-7. The level declares conforms=false either way, but one grading basis is missing.
- M12: scripts/install-tools.sh finds an installed tool with `command -v`. If an older copy sits earlier on PATH than GOBIN, the script installs the pinned version into GOBIN and prints 'installed', but never re-checks that the binary PATH actually resolves is the pinned one. A later --check would catch it, but the install run itself does not.
- M12: The artefact-level CONFORMANCE rows are almost all 'as the project level'. That is acceptable, but a consumer reads less evidence there than a separate grade would give.
- M12: Every commit (from M1 on, not new in M12) carries the owner's real git author name and email. The commit messages themselves are clean. Whether that identity is acceptable before publication belongs on the publication checklist.
- M12: The ast-grep step reports 'skipped' in the self-gate because the bundled pack is empty. This is documented in docs/astgrep.md, so it is not a hidden pass, but the summary line could say outright that no rules are bundled.
