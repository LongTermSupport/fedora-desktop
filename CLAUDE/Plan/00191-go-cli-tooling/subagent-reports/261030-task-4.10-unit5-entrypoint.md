# Task 4.10 unit 5: the image's GitHub host-key fetch says what failed (B4)

## What changed

`files/var/local/claude-yolo/entrypoint.sh`, between new `# >>> GITHUB-HOST-KEYS` /
`# <<< GITHUB-HOST-KEYS` markers. The fetch was
`curl -sL ... 2>/dev/null || github_meta=""` and then `jq -r ... 2>/dev/null || ""`, so a DNS
failure, a refused connection, a timeout, an HTTP 403 (GitHub's unauthenticated rate limit)
and an HTML or key-less answer were all one warning: "(offline?)".

Now:

- `curl -fsSL --max-time 5 ... 2>&1`: `-f` makes an HTTP error status a failure (before, a
  403 body went to jq), `-S` makes curl print its own cause, which is captured.
- `jq -er '.ssh_keys | .[]' 2>&1`: `-e` fails on an answer with no keys; jq's words are kept.
- The warning is `⚠ Could not fetch GitHub SSH host keys: <cause> — using
  StrictHostKeyChecking=accept-new for git/ssh`, the cause being curl's message (for example
  `curl: (6) Could not resolve host: api.github.com`, `curl: (7) Failed to connect ...`,
  `curl: (22) The requested URL returned error: 403`) or `malformed answer from
  api.github.com/meta (<jq's words, or "no ssh_keys">)`.

Versions: container 2.79.17 to 2.79.18 (Dockerfile label and `REQUIRED_CONTAINER_VERSION`),
CCY 3.104.9 to 3.104.10, a `docs/ccy-changelog.md` section above 3.104.9, and the
play-claude-yolo entry in `CLAUDE/Plan/meta-deploy.list` now says 3.104.10 rebuilds the image
and what changes.

## Decision 1: a failed fetch does not stop the container's start

Today's behaviour is kept, and it is not a guess. The step's only job is to spare the first
`git push` an interactive host-key prompt. When the keys cannot be had, the entrypoint does
not skip that job: it writes `StrictHostKeyChecking accept-new` for `github.com` into
`~/.ssh/config`, so git over SSH still works without a prompt, and it says so on stderr. Nothing
later depends on the pinned keys being present (the next steps write the ssh config stanza and
go on to the session), so the fail-fast rule's "never decouple dependent operations" is not
broken: the dependent operation (ssh to GitHub) has a working, announced path. Stopping the
start would make a GitHub API rate limit (60 unauthenticated requests an hour per address,
shared by every container on the host) or a DNS hiccup take a whole session down, for a step
whose fallback is safe enough that it was designed in. The defect was the dropped cause, and
that is fixed.

The trade-off to surface: accept-new trusts the first key it sees for github.com, so a
fallback start is trust-on-first-use rather than pinned. That was already the case; the
warning now says why it happened, which is what an owner needs to judge whether it matters.

## Decision 2: fixed in the entrypoint, not ported to Go

Units 1-4 moved launcher steps into the Go front, which runs on the HOST. The entrypoint runs
INSIDE the image, and the image has no Go binary of this project in it: a port would mean
building a new binary into the image (a build stage or a host-built artefact copied in, its
version kept in step with the image, its own tests), for a five-line step. That is
disproportionate to the defect. The fix stays inside the bash-limits ratchet: the entrypoint's
record went down (statements 443 to 437; code lines 440 and functions 5 unchanged; the `data`
flag was already grandfathered and the step still makes one jq call), recorded with
`scripts/qa-bash-limits.bash --update`. If the image ever carries a Go binary of ours, this step
is a natural one to move into it; until then, porting it is the owner's call, not this unit's.

## Tests (first, red then green)

`scripts/test-ccy-ssh-handling.bash` (gate `ccy-ssh-handling`) gained a section that cuts the
step out of the real entrypoint between its markers and runs it under `set -e` against a stub
curl, with HOME in a throwaway directory:

- DNS failure, connection refused, HTTP 403: the start goes on, accept-new is written, no
  known_hosts, and stderr carries curl's own message and not "offline?".
- curl is called with `-f` and `-S`.
- A non-JSON answer and JSON with no `ssh_keys`: the same fallback, "malformed answer".
- A good answer: the key is pinned in known_hosts, no accept-new, nothing on stderr.

Red before the fix: 6 failures (each fallback case said "offline?", and curl lacked `-f`/`-S`).
Green after: the suite passes in full.

A new suite of its own was not added, because a new gate would mean editing every
`src-go/qa/all/testdata` golden; the SSH-handling suite is the closest home.
