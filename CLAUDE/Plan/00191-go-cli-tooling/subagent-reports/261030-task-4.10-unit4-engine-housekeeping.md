# Task 4.10 unit 4 (B6, B7, B9): network removal, container stops and listings, in Go

## What the bash did

- **B9, the listings** (`lib/docker-health.bash`): the orphan scan, the stale-container
  cleanup, `ccy --top` and the existing-containers menu each ran `container_cmd ps ...
  2>/dev/null` with `|| containers=""` or inside `< <(...)`, so an engine that could not list
  was "no containers found". The stale scan's bare capture also aborted after its first
  failed `ps`, so the `status=created` half was never asked (visible in the goldens).
- **B7, the stops**: the orphan menu (`a`, `s`), the existing-containers menu (`s`, `m`) and
  `ccy --top` (`a`, numbers) ran `container_cmd stop NAME >/dev/null 2>&1`, printing
  "✗ (may already be stopped)" or a bare "✗" for any failure and going on; the orphan menu
  then said "All orphaned containers stopped" anyway.
- **B6, the network removal** (the cross-engine mismatch, option 1, `a`): `docker network rm
  NET 2>/dev/null && ... || echo "Could not remove (may still have containers)"` and went on.
  The same block's `docker stop` said "Some containers could not be stopped (continuing)"
  and its `network inspect` failure went on with no containers stopped.

## What changed

- **Go, `internal/engine` E13**: `Stop` (`stop NAME`) and `RemoveNetwork` (`network rm NAME`),
  each failure the engine's exit with its words. **`StoreHas` (Plan 00235) did not answer
  networks, and on docker answered nothing (`ErrPodmanOnly`).** It now answers `network`
  (podman's `network exists`) and, on docker, which has no exists question, `container` and
  `network` by the list filtered on the name (`ps --all --filter name=KEY`, `network ls
  --filter name=KEY`), there only when a line is KEY exactly (the filter matches substrings);
  a list that fails is an error, never a gone. Image and volume stay podman-only.
- **Go, `internal/ccylaunch` F20-F22** (`containers.go`), answered under CCY_LEGACY too
  (`bashQuestions` in front.go, which also replaced the chain of ifs in `ownFlag`):
  - `--list-containers ENGINE [--all] [FILTER...]`: names on stdout, exit 0 (none is empty);
    exit 1 "ccy: the containers could not be listed: <cause>".
  - `--stop-containers ENGINE NAME...`: a stderr line each, "✓", "already gone" (the stop
    failed and `StoreHas` says the store no longer has it) or "✗ <engine's words>" (also when
    the store could not be asked, with both causes); every one tried; exit 0 when all are
    stopped or gone, 1 otherwise.
  - `--remove-network ENGINE NETWORK`: exit 0 silent; 5 (`ExitGone`) "is not there any
    more"; 1 "could not be removed: <cause>". 64 on wrong arguments for all three.
- **Bash.** Every listing and stop in docker-health.bash is a front call; `find_stale_containers`
  went (one call ORs the two status filters, as both engines do for a repeated key), and
  `show_zombie_container_tui` takes the names its caller already found instead of scanning
  again. The launcher's mismatch cleanup stops with `--stop-containers docker` and removes with
  `--remove-network docker NET || [ $? -eq 5 ] || exit 1`. The bash's refusal of the front-only
  flags is one `[[ ]]` (so the parse-site derivation in test-ccy-session-registry still reads
  it) and names the three new flags, as does `CCY_REGISTRY_DROP_FLAGS`.

## Behaviour kept, and what changed (fail fast)

- Kept: "already gone" goes on, as "may already be stopped" meant to; the menus' answers,
  their unattended defaults and the stale cleanup's per-removal "✗ (cause)" and carry-on.
- **Changed:** a listing that failed now fails the launch (the menus return 2, which the
  launcher's `ccy_container_menu_exit` turns into exit 1; the stale cleanup returns 1 under
  `set -e`) or `ccy --top` (exit 1), with the engine's cause; before it was "none". A stop
  that really failed fails the menu (2) or `--top` (1) instead of launching beside a
  container the person asked to stop, and the orphan menu no longer says they all stopped. In
  the mismatch cleanup, a removal that really failed, a stop that failed and an inspect that
  failed stop with the cause instead of "(continuing)": the person chose the cleanup, and
  going on after it failed was the guess.
