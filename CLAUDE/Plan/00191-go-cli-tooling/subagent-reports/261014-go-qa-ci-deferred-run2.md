# go-qa-ci: minor items the verifiers deferred (run 2: M0 to M3c)

Each is non-blocking; to be picked up in a polish milestone.

- M0: The workflow can only go green once the owner sets the GQACI_DENYLIST secret, so that part of acceptance cannot be checked here. Without the secret, .github/scripts/write-denylist.sh exits 1 with an ::error:: line (the fork-PR case is the only one that warns and passes), but no test covers write-denylist.sh.
- M0: All four commits carry the owner's real author and committer email. This is the owner's git identity and is listed in docs/PUBLICATION-CHECKLIST.md step 3; the owner should decide on a no-reply address before the repo goes public.
- M0: scripts/public-safety-scan.sh --staged reports the line number in the diff output ('staged text line N'), not the file and line. Tree mode gives file:line as acceptance requires, but the pre-commit output is harder to act on.
- M0: The actions/checkout SHA pin (3d3c42e5..., commented v7.0.1) and the gitleaks 8.30.1 pin in .github/workflows/public-safety.yml could not be checked offline. Confirm both on the first CI run.
- M0: cmd/go-qa/main_test.go tests run() in-process. main() is just os.Exit(run(...)), so this is fine, but no test runs the built binary. A manual go run confirmed exit 0 for --version and exit 2 for an unknown subcommand.
- M0: .golangci.yml enables depguard with no rules configured. It is harmless now, but M5 should either give it the allowed-dependency list or drop it.
- M1: Table and key names match case-insensitively (go-toml field matching): `[Tools]\nFMT=false` is accepted and applied, so a key outside the documented schema gets through; `[tools] fmt=false` followed by `[Tools] fmt=true` silently ends with fmt enabled (internal/config/load.go:62-66, decode). Rejecting or normalising non-canonical key spellings would close this.
- M1: The record caps are not checked for negative values: max_total, max_per_rule, max_policy, max_review_days and the tier max_review_days/max_count can all be negative as long as the ordering checks pass (internal/config/load.go:109-125, problems). This should be tightened before M3b uses them.
- M1: Problem messages for record.path/docs_dir/summary.file and record.trust.models come out in random order because they come from map iteration (internal/config/load.go:110 and :127-134), so the same bad file can give differently ordered error text from run to run.
- M1: record.trust.models accepts the tier "unknown" (and "human") although the README documents `high | medium | low` (internal/config/config.go:151 Tier.Valid used for models; README.md Configuration).
- M1: An absolute --config path fails with 'path escapes from parent' (os.Root) rather than a clear message; the README does document --config as relative to the root (internal/config/load.go:41).
- M1: TestReadmeDefaultsMatchBuiltInDefaults (internal/config/config_test.go:50) catches a README value that differs from a built-in default, but not a README that leaves a default out. Every current field is listed today; a future field with a non-zero default could be left out of the README and the test would not notice.
- M2: Acceptance clause '-p on one file reports only that file': internal/cli/run_test.go TestRunScopesToOneFileRelativeToTheRoot only proves that the scope ['pkg/a.go'] reaches the executor Context and the summary 'scope:' line. No engine exists yet, so nothing yet filters diagnostics to that file. The engine milestones (M5 onward) must add a test showing that findings outside the scope are dropped and that Identifiers come through unaltered (TOOLING-SPEC 4.4).
- M2: internal/cli/run.go summary(): the stop notice reads 'detectors failed: runners were not started' even when only the format phase failed, because StoppedBeforeRunners is also set for a format failure. The wording should say 'format or detector failure'.
- M2: internal/cli/run.go DBFPointer says 'each failure names an identifier', but today's Pending failures ('not implemented yet') name none. This is harmless until engines exist, but the wording should match what is printed.
- M2: internal/pipeline/pipeline.go compare() breaks ties on Name, so two Steps with the same Phase and Rank but different Names are both kept. It does not matter for the catalogue, but it differs from the Rust Step identity (enum equality); worth noting when [[stage]] config is wired.
- M3a: internal/record/record.go:174 headerLines matches only a line whose trimmed text is exactly "[[exception]]". A header with a trailing comment (`[[exception]] # note`) or inner spaces (`[[ exception ]]`), both valid TOML, is skipped, so every later entry gets the wrong line. Verified: with `[[exception]] # first` on line 1, exception #1 was reported at qa/record.toml:6 (entry #2's header) and #2 got no line. The loader could take entry positions from the TOML decoder, or match the header with a regex that allows whitespace and a comment.
- M3a: internal/record/matcher.go:41 The matcher also matches entries that Validate rejects, for example a glob without policy. That is harmless for now, because the record tool fails the run first, but M5/M6/M7a should either skip invalid entries or rely on that ordering on purpose.
- M3a: TOOLING-SPEC 6.3: defences are listed with `go-qa tools` (text only), while the record has `record list [--json]`. These should become the same kind of operation once `rules [--json]` lands in M11.
- M3a: docs/record.md 'Not yet built' and 'gqaci.record.stale' correctly record the gaps (stale is not reported by any run until detectors exist, as planned for M7a; budgets and ratchet are M3b/M3c). Keep this wording until those milestones close.
- M3b: internal/record/policy.go:27 and docs/record.md:67 attribute the anti-bloat controls to 'TOOLING-SPEC 6.4'. Clause 6.4 only says a toolchain SHOULD state its own defaults. Budgets, tiers, co-sign and expiry are toolchain policy, not spec MUSTs. The citation should say they serve 6.4 through their documented defaults, or cite the brief.
- M3b: internal/config/load.go (problems): negative max_total, max_per_rule, max_policy, max_review_days and tier max_count/max_review_days are accepted without a config error. rust-qa-ci uses usize, so negative values are impossible there. In go-qa-ci a negative max_total makes every non-empty record fail with a confusing budget message instead of a config error (exit 2).
- M3b: internal/record/policy.go reviewBudget: entries with an unmapped model are counted under no tier's max_count, yet they are treated as low tier for the review horizon. Such entries are already gqaci.record.invalid, so the effect is small.
- M3b: Not ported in this milestone: the policy_test.rs ratchet cases (non-empty record without a ratchet, growth past high_water, signature, raise against history). docs/record.md 'Not yet built' records this as a gap, so it is not a conformance claim. It must land in a later milestone.
- M3b: internal/cli/record_test.go validRecord and the over-budget test use the real clock. They stay correct because the dates are relative to date.Today(), but they could flake if a run crosses UTC midnight between building the record and the check reading the clock.
- M3c: Gates are green: gofmt -l prints nothing, go vet is clean, go test -race -count=1 ./... passes, golangci-lint reports 0 issues. The working tree is clean and HEAD equals origin/main. The genericity grep over code and commit messages finds nothing.
- M3c: Every acceptance clause has a test that can fail, in internal/record/gate_test.go using tempdir git repos: TestAnUnsignedRaiseAgainstHeadFails, TestAStaleSignatureOnARaiseFails, TestACommittedRaiseIsStillCaughtAgainstTheMergeBase, and TestPruneRemovesEntriesAndLowersHighWater (also internal/cli/record_test.go TestRecordPruneRemovesNamedEntriesAndLowersTheCeiling). The CLI binary checked by hand gives the right results for a module in a repository subdirectory and for a newly created record with a stale signature (reported as raised from 0 to 1).
- M3c: Commit 5ba5122 fixes two behaviours but adds no test for either: history lookup for a module in a repository subdirectory (rev:./path, ls-tree from the module root), and 'a record absent at a resolving revision is a raise from zero'. Both work when checked by hand. A regression test would pin each.
- M3c: internal/record/gate.go:41-43: when HEAD cannot be resolved (no .git, for example a source tarball in CI, or no commits) the gate gives only a note and still exits 0, even with --ci. docs/record.md says 'that is a gap, not a pass', but in CI it is a pass. The unresolvable-history_base case was already made a CI failure; this case could be treated the same way for consistency.
- M3c: internal/record/gate.go:152-157: a committed record at HEAD that does not parse also comes out as previous == nil, which produces the misleading 'no committed history' note and leaves raises unchecked. Rare.
- M3c: internal/record/gate.go:153: history_base from config goes to `git merge-base <base> HEAD` as a positional argument without `--end-of-options` or a check that it does not start with '-'. The value is project-controlled, so the impact is low.
- M3c: README.md commands table has no row for `go-qa record prune <number>...`, and still says record check findings are only gqaci.record.invalid; it now also emits gqaci.record.ratchet.
- M3c: A raise that was signed fresh and committed on a long-lived branch becomes stale against the merge base after 14 days, so CI on that branch then fails until it merges. This is consistent with the brief (rust-qa-ci behaviour) but is not stated in docs/record.md.
