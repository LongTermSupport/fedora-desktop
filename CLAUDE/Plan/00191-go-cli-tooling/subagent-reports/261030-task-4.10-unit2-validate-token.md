# Task 4.10 unit 2 (B2): the token check, in Go, with three answers

## What the bash did

`validate_token` ran `podman run --rm -e CLAUDE_CODE_OAUTH_TOKEN --entrypoint claude IMAGE
--version` with all output discarded and read any failure as "token invalid". Reading it
turned up a worse fact than the referral named: `claude --version` never contacts the API, so
the check never tested the token at all. Its only possible failures were the engine's, the
image's or the container's, and every one of them was reported as an invalid token and sent
the person to token recovery.

## What changed

- **Go, `internal/engine` E11, `Engine.RunWithSecret`.** `run --rm --pull=never -e NAME
  --entrypoint ENTRY IMAGE ARGS...`, the secret an `execx.Secret` in `Cmd.Secrets` (by name
  only; a command whose argv holds it is refused). The image is never pulled, so a missing
  image is the engine's exit 125 with its "no such image" wording, returned as `ErrNoImage`;
  the container's own exits (curl's codes) pass through and are never read as a missing image.
- **Go, `internal/ccylaunch` F17, `checktoken.go`: `--check-token ENGINE IMAGE`, the token in
  `CLAUDE_CODE_OAUTH_TOKEN`.** In the image, `sh -c` pipes `printf` (a shell builtin, so no
  argv in the container holds the token either) into `curl --config -`, which sends the usage
  reader's own one small request (`usageRequest` and `defaultUsageEndpoint`, now shared with
  tokenusage.go; the `CCY_USAGE_*` endpoint, model and timeouts apply). Answers:
  - exit 0, silent: HTTP 200, or 429 (a token the API rate-limits is one it knows; usage is
    ccy-token-usable's question);
  - exit 3 (`ExitTokenRejected`): HTTP 401 or 403, or a value with a character outside the
    token grammar (never sent). Only this is the recovery case;
  - exit 1, `ccy: the token could not be checked: <cause>`: no token given, an engine name
    that is not podman or docker, a refused `CCY_USAGE_*` setting, the engine not starting,
    the image not built, an engine failure, curl's failure (with curl's words), or any other
    HTTP answer (5xx, 400, 000).
  Answered under CCY_LEGACY too (the bash asks it), as F16 is. The token never reaches stdout,
  stderr or an argv (tests assert it).
- **Bash.** `validate_token` is now one line calling the front (`$SCRIPT_DIR/claude-yolo`, as
  unit 1) with the token in that command's environment. The launcher's check reads 0 as
  validated, 3 as the "api" failure that leads to recovery, and anything else as "not
  checked (above); it is kept", exit 1. The recovery's second check and the two token
  creation paths (setup-token and manual paste) now say "its check failed, for the reason
  above" instead of "does not authenticate". The bash's own refusal of the front-only flags
  covers `--check-token`, and it is in `CCY_REGISTRY_DROP_FLAGS` beside `--read-launch-config`.

## Could-not-check stops the launch

Fail fast: if the check could not be made, nothing is known about the token, and going on
unchecked is the prohibited skip-and-warn. Stopping also costs nothing real: the session needs
the same engine, the same image and the same API, so a launch past this point would fail at the
session's own start or its first request, later and less clearly. What changes is that the
stop names the cause and the token is kept; it is no longer sent to recovery (which offers to
recreate or replace a good token). A headless or restarted launch stops the same way.
For token creation, a new token whose check could not run is still not saved (saving an
unchecked token would be the same skip), but the person is told why.
