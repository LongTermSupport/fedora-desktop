## 18:17 · finding · T3.10   — go-qa-ci diff-mode build fails on a test-only package; fixed in the clone

Fable found that go-qa-ci diff mode fails on a test-only package. Pin in use:
v0.0.0-20261015133126-7fc4547e92f2.

Cause: in a narrowed run, `runBuild` passes the changed packages and their importers by name to
`go build -o /dev/null <pkgs>`. `go build` rejects a named package that has no non-test Go file
("no non-test Go files in ..."), but `./...` skips it without a word, so the full run passes and
the diff run fails. Reproduced here: `src-go/internal/freeze/golden` holds only
`golden_test.go` and imports lxcfreeze. `go build ./internal/freeze/golden` exits 1, while
`go build ./internal/freeze/...` exits 0. Any change to lxcfreeze or podfreeze therefore fails
`qa-changed.bash` at the go stage.

Fix (go-qa-ci, branch `build-skips-test-only-packages`, commit `240fbf2`, on top of `7fc4547`,
not pushed):

- `internal/runners/build.go`: when patterns are named, `buildable` first runs
  `go list -e -f` with the build's own GOFLAGS environment. It drops each package that has no
  `.Error`, no GoFiles and no CgoFiles, but does have TestGoFiles or XTestGoFiles. Everything
  else stays in. If nothing is left, the build passes without running `go build`, so the empty
  list never turns into `./...`. If `go list` itself exits non-zero, the build fails with its
  output. A full run (no patterns) is unchanged.
- A named package that fails to load for a real reason still fails: a missing directory, a
  directory with no Go files, all files excluded by constraints, or a syntax error in a
  production file. `TestBuildNamingAPackageThatDoesNotLoadFails` covers these cases.
- Not handled by the build stage, by design: a syntax error in the test file of a test-only
  package. `go list` sets no `.Error` for it, and the build stage never compiles test files for
  any package. The test stage reports it.
- Tests: three runner tests and one diff-mode test
  (`TestDiffBuildPassesWhenATestOnlyImporterOfTheChangedPackageIsAffected`). That test failed
  with the exact "no non-test Go files" message while the fix was disabled, and passes with it.
- The clone's own QA passes: gofmt, go vet, `go test -race ./...`, golangci-lint (0 issues), and
  the self-gate `go-qa run --ci` (every step passed; ast-grep skipped as usual).
  `docs/runners.md` documents the behaviour.
- Checked on this repo's tree: the same `go list` filter marks `internal/freeze/golden`
  test-only and keeps freeze, freeze/app and freeze/cli.

Still to do: the coordinator reviews and pushes the go-qa-ci fix. After that, the pin in
`src-go/qa/go.mod` is bumped (Task 3.10 follow-up). Until then the defect remains here.

## 18:51 · action · T3.11   — diff-mode coverage fix ready in a go-qa-ci clone (6a352d6)

The defect, from go-qa-ci's source (confirmed by Fable): in diff mode `runCoverage`
(`internal/tools/runners.go`) applied the module-wide `fail_under_statements` to
`packagesOf(module)`, which is the changed packages plus their importers.
`testAndMeasure` (`internal/runners/coverage.go`) built one `-coverpkg` from all of them and
read the single `total:` line. So a change to a well-covered package failed on gaps in
importers it never touched. That is the 88.8% against the floor of 90.

Fix, in a clone of go-qa-ci at `8e17b43` (`untracked/repos/go-qa-ci`, branch
`coverage-diff-changed-only`, commit `6a352d6`, not pushed):

- `changed.Plan` gains `Changed`: per module, the packages that hold a changed file (or own
  a changed testdata or embedded file), without importers.
- `runners.TestAndMeasure` and `MeasureCoverage` take a `measured` list for `-coverpkg`,
  separate from the tested packages. An empty list means the tested packages, so full mode
  is unchanged.
- The executor's new `measuredOf` returns `Changed[module]` when narrowed. The coverage
  step skips a module that holds only importers. The shared test-and-coverage run uses the
  same split.
- The importers are still tested, because their tests may reach the changed code. A test
  covers this: with leaf's own test removed, a leaf change passes on mid's tests.

Edge case found while writing the tests: a changed test-only package (like
`src-go/internal/freeze/golden`) named in `-coverpkg` has no statements, so the total is 0.0%
and the floor fails. This happened before the fix as well. `Changed` now leaves test-only
packages out (`go list` GoFiles and CgoFiles empty), the same rule the build stage follows.

Test first: `TestDiffCoverageJudgesTheChangedPackageNotTheGapsOfItsImporters` failed before
the fix (statement coverage 40.0% is below 80, naming `mid.Gap`) and passes after, with and
without the shared run. Also added: the changed package's own gap still fails, importer tests
count, a test-only change passes, and plan tests for `Changed`. README's diff-mode table and
`docs/runners.md` are updated.

Clone QA: `go vet`, `gofmt`, `go test -race -shuffle=on -count=1 ./...` (all packages ok,
with the pinned tools from `scripts/install-tools.sh`), `golangci-lint run ./...` (0 issues),
and the self-gate `go-qa run --ci` (exit 0, every step passed, ast-grep skipped as it is
configured).

Next: review, push and merge in go-qa-ci, then bump the pin in `src-go/qa/go.mod` and repeat
the throwaway lxcfreeze edit. Possible follow-up, not this task: judge each changed package
against the floor on its own instead of judging their combined total.

## 19:22 · finding · —   — Task 3.12: CI setup-go installed Go 1.26.0 below the qa module floor

Task 3.12: GitHub Actions QA on F44 failed on the five latest runs at "Install QA tooling".
The error was `toolchain: go is older than src-go/qa/go.mod requires, need >= 1.26.9, found 1.26.0`.

Evidence:

- `gh run view 39307310286 --log`, step "Set up Go": `go-version-file: src-go/go.mod`, then
  `Setup go version spec 1.26.0` and `go version go1.26.0 linux/amd64`. setup-go v5 reads only
  the go directive. It ignored `src-go/go.mod`'s `toolchain go1.26.9` line, even though the
  workflow comment and Plan 00204's notes assumed it read it.
- `src-go/go.mod`: `go 1.26.0`, `toolchain go1.26.9`. `src-go/qa/go.mod`: `go 1.26.9`, set by
  f3c93b6a (Task 3.3, the go-qa-ci pin). The pin bumps since then left it there.
- qa-toolchain takes its floor from the higher go directive of the two modules, so it failed
  correctly. The gate was right; CI installed the wrong Go.

Options weighed:

- Raising `src-go/go.mod` to `go 1.26.9` passes `go build`, `go mod tidy -diff` and a byte
  comparison of `go mod vendor`. Rejected: the host build (`tasks/build-go-command.yml`, with
  `GOTOOLCHAIN=local`) would then need Fedora's golang at 1.26.9 or newer. `play-golang.yml`
  only makes sure golang is present, and that play runs on the unattended self-update path.
- Chosen: point setup-go at `src-go/qa/go.mod`. The CCY image has `GO_VERSION=1.26.9`, which is
  unchanged, and local QA already requires 1.26.9 through qa-toolchain.

Gate: `TestEveryWorkflowSetsUpTheGoFloor` in `src-go/qa/toolchain/pins_test.go`. It parses every
`.github/workflows/*.yml`. Each `actions/setup-go` step must take its Go from `go-version-file`
alone, and the go directive of that file must equal readGoFloor's. Red against the old workflow
(and against `src-go/go.mod` at `go 1.26.0`); green with the fix.

No GitHub issue existed. Issue text for the coordinator to file:

Title: CI QA fails: setup-go installs an older Go than the QA module requires

Body:
The QA workflow's "Install QA tooling" step fails with "toolchain: go is older than
src-go/qa/go.mod requires, need >= 1.26.9, found 1.26.0".

Cause: actions/setup-go took its version from src-go/go.mod, whose go directive is 1.26.0.
setup-go reads only the go directive, not the toolchain line, so it installed Go 1.26.0. The QA
module (src-go/qa/go.mod) has required go 1.26.9 since go-qa-ci was pinned as a tool, and the
toolchain gate correctly refuses an older Go.

Fix: setup-go reads src-go/qa/go.mod, the module with the higher go directive. A Go test in
src-go/qa/toolchain fails when any workflow's setup-go names a go.mod whose go directive is lower
than the Go floor, so the next go directive bump cannot turn CI red in this way.
