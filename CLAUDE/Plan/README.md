# Implementation Plans Directory

This directory contains implementation plans following the claude-code-hooks-daemon plan workflow.

## Plan Workflow

**IMPORTANT**: All non-trivial implementation work should follow the planning workflow documented in [PlanWorkflow.md](../PlanWorkflow.md).

### Quick Reference

Plans use numbered prefixes for sequential organization:

- `001-description/` - First plan
- `002-description/` - Second plan
- etc.

Each plan directory contains:

- `PLAN.md` - Main plan document with tasks, goals, and progress tracking
- Supporting files (implementation, tests, documentation)

### Task Status Icons

Use these Unicode icons in plan documents:

- ⬜ `TODO` - Not started
- ✅ `DONE` - Completed successfully
- 🔄 `IN_PROGRESS` - Currently working on
- 🚫 `BLOCKED` - Cannot proceed (dependency/issue)
- ❌ `FAILED` - Attempted but failed (requires rework)
- ⏸️ `PAUSED` - Temporarily suspended
- 👁️ `REVIEW` - Needs review/approval
- 💤 `DORMANT` - Paused indefinitely, blocked on an external/human decision

- [00074-ccy-token-usage-via-ratelimit-headers](00074-ccy-token-usage-via-ratelimit-headers/) - Successor to Plan 00073's Task 5.2, taking the one route 00073 left alive. `/api/oauth/usage` is unreachable with a stored setup-token (403, missing scope `user:profile`), but the same figures travel as **response headers on `/v1/messages`** — the scope an `oat01` token does hold. The critical difference is **who pays**: reading a status endpoint is free, reading response headers means a real billed request that itself consumes a sliver of the allowance it reports. So this is deliberately **not** automatic — it is a key the user presses in the token selector, which then redraws the menu with usage shown. Two findings inverted the original "use `claude -p` with haiku, minimal as possible" framing: the CLI **cannot** deliver the payload (the header names appear only in a mock/scenario harness and the parser — there is no debug or print path that emits them), and `claude -p` is the *less* minimal option since it ships a large system prompt and tool schemas as input tokens where a bare `max_tokens: 1` request sends one character. Haiku is kept, and the instinct was right: the weekly buckets are per-model (`seven_day_opus`/`seven_day_sonnet`), so probing with the cheapest model avoids spending the allowance that matters. `prototype.bash` runs both arms — curl, plus `claude -p` as a **control** so "the CLI can't do this" is tested rather than asserted — and renders the exact menu line ccy would show rather than a header dump. Verified against three stub shapes (headers present / 403 / 200-without-headers), which caught two bugs the happy path never would: floor division made every countdown a full unit wrong (a reset exactly 3 days out rendered `r2d`, 2 hours as `r1h`, because the value is never quite round by render time — the same latent bug sat in 00073's renderer, hidden by fixtures whose epochs were already past), and `$?` read after `fi` is **0** rather than the failed condition's status, so every legitimate grep no-match was reported as `grep failed (exit 0)`. **Shipped and deployed.** Q1 answered yes on the HOST: a bare `POST /v1/messages` with a stored setup-token returns 200 with the full unified header set, and the `claude -p` control arm confirmed empirically that the CLI never surfaces them (17 KB debug log, zero occurrences). The response also carries `-representative-claim`, naming the bucket actually binding. Display went through two rounds: the first shipped a compressed one-liner (`5h <1% r4h · wk <1% r6d`) which the owner rightly rejected as unreadable — *"i have no idea what r4h means"* — and was rewritten as aligned per-limit bars, coloured against a dim track, with reset times spelled out ("resets in 4 hours"). One question is deferred rather than answered: the **scale** of `-utilization` is undocumented and the probed accounts were too idle to discriminate, so `CCY_USAGE_SCALE` is a single switch and `CCY_USAGE_DEBUG=1` shows the value as the API sent it, applied at display time so flipping it costs no extra request.

- [00075-fail-signal-discard-sweep-and-gate](00075-fail-signal-discard-sweep-and-gate/) - One defect class produced two incidents in a single session, one of them user-facing and launch-blocking: **a command's failure silently converted into data, which is then used to make a decision or reported to the user as fact**. In `ssh-handling.bash`, `gh api user --jq .login 2>/dev/null` discarded the exit status, so when GitHub answered 502 the JSON error body — written to stdout — became "the account name", and ccy refused to launch while telling the user to go and edit `localhost.yml`. The mapping was correct; GitHub was down. In Plan 00074's `prototype.bash`, `$?` read after `fi` is always 0 (it is the `if` statement's status, not its condition's), so every legitimate grep no-match was reported as a failure. Both were caught by accident, which is the actual problem. This plan sweeps repo-owned bash, Python, and playbooks for live instances — including **QA gates that cannot fail**, the same defect applied to the safety net itself — and builds a gate that **fails a build** rather than advising. - [00073-ccy-token-usage-limits](Cancelled/00073-ccy-token-usage-limits/) - `ccy` stores one OAuth token per Claude account but its launch menu (`select_token()`) shows only name + expiry, so choosing the right account is guesswork and the usual failure mode is starting a long session on an account already near its limit. Claude Code itself knows the figure — established from the shipped native binary (v2.1.233, build `f8d5756`), not from memory: it fetches `GET /api/oauth/usage` with a 5 s timeout (`fetchUtilization`), each limit entry carrying `kind`, `percent`, `resets_at` and optional `scope.model.display_name`, with kinds `five_hour`, `seven_day`, `seven_day_opus`, `seven_day_sonnet`, `seven_day_overage_included`. A live probe confirms the route exists (unauthenticated `GET` → **429**, not 404), and there is **no** supported alternative: `claude --help` has no `usage` subcommand and the statusline `rate_limits` block is documented as populated only *after* a session's first API response, so it is useless pre-launch. **Gated on one unanswered question** the container structurally cannot answer (no token, no `~/.claude/.credentials.json`): does a stored long-lived `sk-ant-oat01` setup-token authenticate to that endpoint, or is it scoped to `/v1/messages`? A refusal **cancels** the plan rather than triggering a workaround. Ships `triage.bash` for the HOST run — probes every stored token, reports status plus a full JSON leaf-path/type map, passes the token to curl via `--config -` on stdin so it never reaches argv/`ps`, and destroys its own report if the redaction check fails. Building it caught two defects by *running* it rather than reading it: the email redaction used `{2,}`, which the container's **mawk** ignores, so a test address went straight through into the report (Fedora's gawk would have hidden this forever); and `jq 'paths(scalars)'` silently drops null leaves — precisely where the optional `scope` field lands. The plan originally sequenced an on-demand command ahead of menu integration to keep an undocumented endpoint off the hot path; the owner asked to try it **on by default**, which turned a judgement call into a measurable one, and the measurement settled it: parallel fetching costs about one round trip in total (5 requests — 815 ms sequential, 416 ms with TLS reuse via `--next`, **203 ms parallel**), so the menu now shows usage by default at **+371 ms cold / +80 ms warm** over a 142 ms baseline for 5 tokens. Exercising the failure paths then caught a defect that reading never would: with the endpoint unreachable, curl never creates its `--output` file, so `chmod`/`mv` failed, the worker died under `set -e` before its `exit 0`, `wait` returned non-zero and the caller aborted — **the menu printed no token rows at all**, exactly what the plan's own "must never block a launch" rule forbids. A second measurement found `jq`, not the network, was the real cost (a cache hit was nearly as slow as a cold fetch, 239 vs 268 ms, because `jq` ran per row at ~40 ms each), so parsing moved into the parallel worker and the cache now stores the finished line — the display path touches no `jq`, no `curl` and no subprocess beyond two file reads, and the raw response is never written to disk at all. Also established that a request carrying a `Bearer` header gets a real **401**, not the shared-IP 429 of an unauthenticated one, so the HOST run yields an unambiguous yes/no with no "can't tell" outcome.
