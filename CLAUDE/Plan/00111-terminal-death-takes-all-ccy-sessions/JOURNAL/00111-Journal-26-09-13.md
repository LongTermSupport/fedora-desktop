## 13:48 · finding · T1.1 — reported cause was wrong: not OOM

Every terminal died at 13:23:45. The presenting theory was the OOM killer.
Four independent checks say no: zero kernel OOM lines in 3352 kernel-ring
entries; `systemd-oomd`'s unit log is 2 lines, both its own startup; no
coredumps in 24 h; 73 GiB of 93 GiB available with zram swap at 0.8 %.

Worth recording *why this mattered* rather than just that it was wrong — an
OOM diagnosis leads to memory limits or reduced concurrency, which would have
degraded the workstation while leaving the real fault untouched.

## 13:48 · finding · T1.2 — Wayland protocol error killed Ptyxis

```
13:23:45  gnome-shell[6310]: WL: error in client communication (pid 13312)
13:23:45  ptyxis[13312]:     Error reading events from display: Invalid argument
13:23:47  systemd[2266]:     dbus-:1.2-org.gnome.Ptyxis@0.service: Main process exited, code=exited, status=1/FAILURE
13:29:31  systemd[2266]:     Started dbus-:1.2-org.gnome.Ptyxis@1.service
```

Order matters: mutter severed the connection *first*, Ptyxis then failed its
socket read and exited cleanly (`status=1`, no coredump — not a segfault).
`gnome-shell` pid 6310 has run since Sep 11 11:16:45, so the compositor never
restarted; one client was dropped, not the session.

Blast radius comes from Ptyxis being single-instance: one process owns every
window and tab, each tab's shell in a child `ptyxis-spawn-<uuid>.scope`. Six
scopes died in two seconds. First occurrence of this error across all five
recorded boots.

## 13:49 · finding · T1.3 — container survival is a red herring

Three of four CCY containers survived; `family-qnap_yolo` was killed and
removed. All four logged the same `Failed to write to remote console socket`,
so the console failure is not the discriminator — the foreground `podman run`
client is. The survivors' `conmon` has **ppid 2266 (`systemd --user`)** in its
own `libpod-*.scope`, already reparented clear of the tab. `family-qnap_yolo`'s
`podman` client (pid 3892681) was still alive in a dying tab and ran its normal
`--rm` teardown: kill, then remove. Podman destroyed it as instructed.

So survival was incidental, not designed. **And it bought nothing**: all three
survivors sit at `TTY = ?`, `Ssl+`, in `ep_poll` — alive with no pty and
nothing on their stdio, so `podman attach` reaches a process that cannot be
driven.

The chain shows why:

```
ptyxis-spawn-<uuid>.scope → bash → podman run → [container] → claude-supervise.py (pts/0) → claude
```

Decisive conclusion: **the pty is what must outlive the terminal, not the
container.** Detaching the container is ruled out as a defence.

## 13:50 · decision · P3 — tmux is the presumptive mechanism

The tmux *server* is a `systemd --user`-owned daemon that owns the pty, making
the tab a mere viewport. It is the only candidate that preserves the pty.
`systemd-run --user --pty` is the alternative but re-attaching after its client
dies is awkward. Recorded as presumptive, not final — Task 3.1 confirms.
