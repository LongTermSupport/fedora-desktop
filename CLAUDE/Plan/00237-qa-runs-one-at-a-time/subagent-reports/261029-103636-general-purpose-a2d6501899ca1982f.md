**Where the lock lives and why it is shared:** `<git common dir>/fedora-desktop-qa.lock`, found with `git rev-parse --path-format=absolute --git-common-dir` and held with flock(2).
- The main checkout and every worktree share the same git common dir. The CCY containers bind-mount that same checkout.
- An advisory flock belongs to the file itself (its inode), not the path. A bind mount shows the same inode, so on one kernel the host and every container see each other's lock.
- The kernel releases it when the holder dies, so a dead run never blocks the next one.
- Tested with two real processes, plus a hard link standing in for a second path to the same file. No unit test can set up a real bind mount.

**The wait line:** a second run prints this once to stderr, then `qa: still waiting for the QA run <pid> (<command>), <N>m so far` every minute:
`qa: waiting for the QA run <pid> (<command>, started <time>, in <worktree>)`
- The holder writes its own details into the lock file.
- `--no-wait` exits 2 at once, naming the holder. It works on qa-all and qa-changed, and as the first argument to `qa-go-qa.bash`.
- `QA_LOCK_TIMEOUT` (e.g. `30m`) sets a maximum wait; without it, a run waits as long as the lock is held.
- `--plan`, `--help` and a qa-changed with nothing changed take no lock.

**How nesting is handled:** qa-all and qa-changed both run `qa-go-qa.bash`, which takes the lock when run alone. A run that finds the lock held inherits it, instead of waiting, when the holder is one of its own ancestors in its own pid namespace.
- This is decided from the process tree, not an environment variable. The first commit used `QA_LOCK_HELD`; the reviewer pointed out that a gate which clears its children's environment would then make a run wait forever for its own parent.
- The pid namespace check stops the same pid number in another container from counting as an ancestor.
- One test runs the real chain: the holder runs an `env -i` shell, which re-runs a process that asks for the lock with `--no-wait` and must succeed.
- In the live qa-changed run, the Go gate went through `qa-go-qa.bash` under qa-changed's lock and printed no wait line.

**Priority mechanism:** in Go, nice and I/O priority are per thread, and new threads and child processes copy them from the thread that creates them. Lowering one thread of a running Go program therefore leaves the rest at normal priority.
- So at startup `proc.Priority.Ensure` lowers one thread (`setpriority` 19, `ioprio_set` idle) and re-executes the program from it. Everything the program then runs starts low.
- It does nothing if the run is already low, and a guard turns a failed re-exec into an error rather than a loop. `QA_FULL_PRIORITY=1` opts out.
- A real test checks every thread and a child process for nice 19 and ionice idle.
