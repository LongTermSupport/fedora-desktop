## 10:30 · finding · P1 — the tool we already ship has a second engine built in

While the research workflow ran, measured the live baseline in this CCY container rather
than assuming it. Three findings, all reproduced from commands, not inferred.

**1. `agent-browser --engine lightpanda` already exists.** Installed version is 0.31.1 and
its `--help` carries:

```
--engine <name>   Browser engine: chrome (default), lightpanda (or AGENT_BROWSER_ENGINE)
```

Probed it in three steps, each failure naming the next obstacle:

```
$ agent-browser --engine lightpanda read https://example.com
✗ Headed mode is not supported with Lightpanda (headless only)

$ agent-browser --engine lightpanda --headed false read https://example.com
✗ Custom Chrome arguments (--args) are not supported with Lightpanda

$ agent-browser --config <clean.json> --engine lightpanda read https://example.com
✗ Lightpanda not found. Install it from https://lightpanda.io/docs/open-source/installation
  or use --executable-path.
```

So the engine is wired in and reaches the point of looking for the binary; the only thing
missing is the binary itself. `agent-browser install` does **not** fetch it (`browsers/`
holds only `chrome-150.0.7871.115`).

This changes the likely shape of the answer: the plan may not need a second *CLI* and a
second skill at all — it may need a binary in the image plus a config change. That is a
much smaller, much more maintainable integration than adding a parallel tool. Not treating
this as decided: the research + triage still has to establish that Lightpanda is the right
engine and that its JS fidelity is real. But "add a whole second stack" is no longer the
default framing.

**2. Our own config.json actively blocks the alternative engine.** Both settings the
Dockerfile writes to `/root/.agent-browser/config.json` — `"headed": true` and the Chromium
`"args"` string — are rejected outright by the Lightpanda path. Any integration must
restructure that config, not just add a binary. Neither obstacle was visible from reading
the Dockerfile; both came from running it.

**3. Our `browsing` skill documents a CLI that no longer exists.** `SKILL.md` teaches
`agent-browser run "navigate …; extract text"` throughout. Against 0.31.1:

```
$ agent-browser run "navigate https://example.com; extract text"
Unknown command: run
```

The real CLI is verb-per-invocation (`open`, `read`, `snapshot`, `click`, `get text`) with
`&&` chaining and a daemon holding the session. So every agent that follows our skill
issues a broken command first. Worse, agent-browser now **ships its own version-matched
skills** (`agent-browser skills get core --full`) and explicitly tells agents to prefer them
over guessing from flag docs — which makes our hand-maintained copy both wrong and
redundant. This is drift of exactly the kind Plan 00069 catalogued, in a file whose whole
job is to be correct. It is in scope here because this plan has to touch the browsing skill
anyway.

**Measured Chrome baseline** (for the triage to compare against), `example.com`, cold after
`close --all`:

| Metric                        | Value                                        |
| ----------------------------- | -------------------------------------------- |
| `open` + `read` wall time     | 1581 ms                                      |
| Processes spawned             | 14 (`chrome` + 2 `chrome_crashpad`)          |
| Summed RSS across them        | 1,307,748 kB ≈ 1.28 GB                       |
| Chrome binary on disk         | 281,693,432 B ≈ 269 MB                       |
| `browsers/` dir               | 381 MB                                       |
| `agent-browser` npm package   | 78 MB                                        |

Caveat recorded so it is not over-read later: summed RSS **double-counts shared pages**
across the 14 processes, so 1.28 GB is an upper bound on real memory, not a clean figure.
It is still the right order-of-magnitude anchor — this is a full Chrome 150, on the
simplest possible page.

## 10:45 · finding · T1.5 — triage.bash written and run; Lightpanda matches Chromium on JS

Wrote `triage.bash` (plan-local, read-only, re-runnable, report to `logs/`) rather than
pasting probes into chat, per `CLAUDE/PlanTriage.md`. It answers the only question that
decides this plan: **does the cheap engine actually run the JavaScript?** Footprint is
worthless if it does not.

Eight fixtures, each rendering a marker string only if one specific capability works,
served from a local `python3 -m http.server`, opened in both engines with the same 1s
grace period. **Lightpanda 0.3.6 matched Chromium 150 on all eight**, including the ones
that separate a real engine from an HTML parser:

| Fixture   | Capability                                     | Chromium | Lightpanda |
| --------- | ---------------------------------------------- | -------- | ---------- |
| static    | plain HTML (control)                           | YES      | YES        |
| dom       | synchronous inline DOM write                   | YES      | YES        |
| defer     | `DOMContentLoaded` listener                    | YES      | YES        |
| timeout   | `setTimeout` 300 ms                            | YES      | YES        |
| fetch     | `fetch()` + JSON + render                      | YES      | YES        |
| modern    | ES module, `#private` field, optional chaining | YES      | YES        |
| shadow    | custom element + shadow DOM                    | YES      | YES        |
| react     | React 18 UMD from CDN, client-side render      | YES      | YES        |

Cost of one cold `open` + rendered-text extraction of `example.com`:

| Metric        | Chromium (headless) | Lightpanda | Ratio          |
| ------------- | ------------------- | ---------- | -------------- |
| wall time     | 1177 ms             | 379 ms     | 3.1× faster    |
| processes     | 15                  | 1          | 15× fewer      |
| peak RSS      | ~1345 MB            | ~25 MB     | ~52× lighter   |
| binary/disk   | 381 MB browsers dir | 153 MB     | 2.5× smaller   |

Real pages (`news.ycombinator.com`, a Wikipedia article, `react.dev`) returned comparable
extractions from both; Lightpanda actually returned *more* text on the Wikipedia article
(8173 vs 6640 chars) and on `react.dev` (8313 vs 6655), so the light engine is not
silently truncating.

**Three harness bugs had to be fixed before any of this meant anything.** Recording them
because each produced a confident, wrong-looking table that could have been believed:

1. **`agent-browser read <url>` does not render.** Its own `--help` says it fetches a URL
   as agent-readable text — an HTTP GET plus HTML-to-text extraction, no browser. The first
   matrix had **Chromium failing every JS test**, which is obviously false, and that
   absurdity is the only reason the harness got audited instead of the engines. The render
   path is `open <url>` then `get text` (or a bare `read` with no URL, which does read the
   active tab's DOM). Byte-identical output between two different engines was the tell.
2. **Memory sampled after the command returned**, by which point the single Lightpanda
   process had exited — reporting `0 kB`, i.e. a misleading empty result dressed as a
   measurement. Now sampled continuously during the run and the peak reported.
3. **`measure_engine` was passed the display label `"LIGHTPANDA"` as its engine key**,
   while `engine_prefix` dispatches on a case-sensitive `"lightpanda"` — so the row
   labelled Lightpanda silently ran **Chromium**. Caught only because RSS came back 0 for a
   pattern no chrome process matches. Fixed by separating the engine key from the display
   label, and the script now **hard-fails** on a 0 kB measurement instead of printing it.

The fidelity matrix and real-site rows were unaffected by bug 3 (they always passed
lowercase keys); only section 3 was wrong, and it has been re-run.

Numbers are honest about their limits: summed RSS double-counts shared pages across
Chromium's 15 processes, so ~1345 MB is an upper bound, not a clean figure. The ratio is
directionally safe — one process versus fifteen is not a rounding artefact.
