# Candidate: chrome-headless-shell (Chrome for Testing)

**Homepage / repo**: https://developer.chrome.com/blog/chrome-headless-shell (announcement/docs); binaries distributed via the Chrome for Testing dashboard https://googlechromelabs.github.io/chrome-for-testing/ and JSON API; upstream source lives in the Chromium monorepo, `//headless` (https://github.com/chromium/chromium/blob/main/headless/README.md); Debian repackaging at https://packages.debian.org/bookworm/chromium-headless-shell.
**Engine**: 100% real Chromium — Blink does HTML parsing/layout/CSS, V8 executes JS, same rendering pipeline as full Chrome. `chrome-headless-shell` is not a different engine or a reimplementation; it is Chromium's `//content` module compiled into a standalone binary with the full-browser UI/shell layer (windowing, extensions UI, most of `//chrome`) stripped out. Per Chrome's own docs it is "a lightweight wrapper around Chromium's `//content` module, and it therefore has substantially fewer dependencies" than the full browser [Chrome for Developers, chrome-headless-shell blog post].
**License**: Not a single license. Debian's package metadata lists the bundled-license set as BSD-3-Clause, LGPL-2.1-or-later, Apache-2.0, IJG, MIT, GPL-2.0-or-later, ISC, OpenSSL, and (MPL-1.1 OR GPL-2.0-only OR LGPL-2.0-only) [MEASURED-INDEPENDENT, Debian package metadata]. This is the normal Chromium license shape (BSD-3-Clause core + a long tail of vendored third-party library licenses), not something specific to the headless-shell packaging.
**Status as of 2026-08**: Actively shipped and actively maintained as a first-class artifact of the Chrome release train, not a side project. The Chrome for Testing dashboard shows the latest stable build as `151.0.7922.137` (revision r1654411), reported "last updated" 2026-08-12 — i.e. it tracks current Chrome stable releases essentially in lockstep \[MEASURED-INDEPENDENT, fetched from https://googlechromelabs.github.io/chrome-for-testing/ on 2026-08-12\]. Debian's `bookworm` (Debian 12) package is at `151.0.7922.108-1~deb12u1`, i.e. actively backported into the stable Debian 12 security/updates channel, not stuck on an old baseline [MEASURED-INDEPENDENT, packages.debian.org]. It also exists in Debian `trixie` and `sid` [MEASURED-INDEPENDENT, packages.debian.org]. Net: this is not a candidate at risk of staleness — it is re-cut on every Chrome release by Google itself, and separately packaged/patched by Debian.

One notable churn event: the **legacy headless implementation was removed from the main Chrome binary at M132 (~Jan 2025)**; before that, `chrome-headless-shell` and `chrome --headless=old` were two ways to get the same code path. Since M132, `chrome-headless-shell` is the *only* way to get that code path — `--headless=old` is a no-op [Chrome for Developers headless docs; developer.chrome.com/blog/removing-headless-old-from-chrome]. This is a maturing/consolidation event, not an abandonment signal — Google deliberately promoted this from "one of two implementations" to "the standalone artifact," and it is what several major projects (see below) migrated onto during 2025–2026.

## What it is

Chrome ships (has shipped since ~2017) with two ways to run without a visible UI:

1. **New headless mode** (`--headless`, default since Chrome 112): the actual full-Chrome binary running without a window. Most authentic/most feature-complete, but pays the cost of the full browser shell.
2. **Old headless mode**, now **only available as the standalone `chrome-headless-shell` binary** (since M132): a purpose-built headless binary built directly on Chromium's `//content` layer, bypassing most of `//chrome`'s UI/browser-shell code. Chrome's own docs frame the trade-off explicitly: "there's a trade-off between performance and authenticity" — shell is recommended for "automated screenshotting or web scraping," full new-headless for "high-accuracy end-to-end web app testing or browser extension testing" [developer.chrome.com/blog/chrome-headless-shell].

Precompiled `chrome-headless-shell` binaries have been published under Chrome for Testing since Chrome M118 [same source]. It is driven exclusively via the Chrome DevTools Protocol (CDP) — there is no separate "shell scripting" API; you either point `--remote-debugging-port` at it and speak CDP directly (e.g. via `chrome-remote-interface`), or drive it through a CDP client library such as Puppeteer (`headless: 'shell'` mode) [developer.chrome.com/docs/chromium/headless].

It also ships CLI flags for one-shot, non-CDP use: `--screenshot` (dump a PNG) and `--print-to-pdf` (render a PDF) [multiple independent how-tos, e.g. TecAdmin, Grio; not from a single authoritative doc, treat as commonly-documented behaviour rather than a single citation].

## JavaScript & rendering fidelity

Because the JS engine (V8) and layout/rendering engine (Blink) are byte-for-byte the same code as full Chrome — headless-shell strips *browser chrome*, not *engine* — JS execution and CSS/layout fidelity for headless-shell should in principle equal full Chrome for anything that doesn't depend on the browser-UI layer. This is stated as the design intent by Chrome's own docs (a "wrapper around `//content`," i.e. the rendering engine is untouched) [developer.chrome.com/blog/chrome-headless-shell], but note this is closer to a semi-authoritative vendor statement about architecture than an independent benchmark — I could not find an independent third-party fidelity study (e.g. web-platform-tests pass-rate comparison) specifically isolating `chrome-headless-shell` vs. full-Chrome-headless. **UNKNOWN — not established** by independent measurement; treat the "should render identically" claim as architecturally well-founded but not independently verified pixel-for-pixel.

What independent/practitioner sources *do* report as caveats:

- **PDF/print fidelity edge cases.** A third-party comparison (PDF4.dev, a PDF-generation-focused blog) that tested both binaries for PDF output specifically warns: "edge cases exist despite convergence" and recommends pixel-level diffing before switching a production PDF pipeline. It calls out advanced print CSS (`@page` rules, `break-inside: avoid`, running headers) and font-loading timing as areas where old-headless and new-headless/full-Chrome output can differ [pdf4.dev/blog/chrome-headless-shell-vs-puppeteer-chromium-pdf]. This is the single most concrete piece of independent "here's where it actually diverges" evidence found.
- **No GPU acceleration.** Remotion's docs (a video-rendering tool that ships both binaries as options) state that for GPU-bound rendering on Linux you must use full "Chrome for Testing" instead of headless-shell — headless-shell is "faster for CPU-bound rendering" but does not do GPU-accelerated rendering [remotion.dev/docs/miscellaneous/chrome-headless-shell]. For DOM/JS-execution/scraping use cases (the target use case here) this mostly matters only if a page relies on WebGL/canvas-GPU rendering to produce content that then needs to be scraped/screenshotted.
- **General headless-Chrome fragility folklore** (applies to headless Chrome broadly, not headless-shell specifically): one HN discussion characterizes headless Chrome generally as having comparatively "high" memory use, crashes/hangs on "heavy" pages, and API inconsistencies between headless and headed modes across platforms [news.ycombinator.com/item?id=14103503]. This is anecdotal/vendor-independent but old (2017-era thread) and not specific to the shell binary; it is included because it's the most relevant independent "problems" thread found, not because it's current or shell-specific.
- **Bot-detection fingerprint surface.** Headless Chrome (in general, including shell) exposes signals detectable by anti-bot services (`navigator.webdriver`, viewport defaults, etc.) [datadome.co explainer]. Relevant only if the agent's browsing target is adversarial to automation — not a rendering-fidelity issue, but worth flagging for "will this actually load the pages I point it at."

## Agent ergonomics

- **No CLI-first, agent-friendly interface of its own.** `chrome-headless-shell` speaks CDP and nothing else as its "real" interface (plus the two narrow one-shot flags `--screenshot` / `--print-to-pdf` for non-interactive single-page dumps). There is no bundled equivalent of `agent-browser`'s higher-level command surface — driving it interactively (navigate, click, wait-for-selector, extract text) requires a CDP client on top, e.g. `chrome-remote-interface` (raw CDP) or Puppeteer with `headless: 'shell'` [developer.chrome.com/docs/chromium/headless].
- **Playwright does not support it as a channel.** The PDF4.dev comparison explicitly notes "Playwright doesn't expose chrome-headless-shell as a supported channel" [pdf4.dev]. Since `agent-browser` (already in the CCY image) is Playwright-based, `chrome-headless-shell` cannot simply be swapped in as an alternate "channel" of the existing tool — it would need its own driving layer (most naturally Puppeteer, or raw CDP).
- **No built-in markdown/text extraction, readability, or token-budget-aware output.** It returns whatever the DOM/CDP gives you (raw DOM, screenshots, PDFs) — turning that into agent-digestible markdown/text (à la Readability.js-based extraction) is something the calling tooling has to do itself; it is not a feature of chrome-headless-shell. (The MCP/CDP ecosystem search surfaced several *third-party* MCP servers — e.g. `cdp-mcp`, generic "CDP" MCP servers — that layer Readability-based markdown extraction on top of a CDP-speaking Chrome; none of them are chrome-headless-shell-specific and none are evaluated here, but they illustrate that "markdown out" is a wrapper concern, not something the binary provides.)
- **No MCP server of its own.** Nothing in Google's or Chromium's docs indicates an official MCP server ships alongside chrome-headless-shell; any MCP integration would be third-party and built on top of CDP, same as with full Chrome.
- **Practical implication for this repo**: adopting chrome-headless-shell would mean either (a) writing/adopting a thin CDP or Puppeteer driver + a text/markdown extraction layer as new plumbing (a new `browsing`-skill-equivalent), or (b) using it only for narrow one-shot tasks via `--screenshot`/`--print-to-pdf` without a persistent CDP session. It is not a drop-in "lighter agent-browser" — it is a lighter *engine* that still needs an ergonomics layer built around it.

## Installing on Debian 12 bookworm (glibc 2.36, amd64, root, node LTS)

Two independent installation paths exist:

**1. apt (Debian's own repackaging) — the simplest, most "IaC-native" path for this repo:**

```
apt-get install -y chromium-headless-shell
```

This is a real Debian 12 bookworm package (version `151.0.7922.108-1~deb12u1`, confirmed present in bookworm, not just sid/trixie) [MEASURED-INDEPENDENT, packages.debian.org]. It pulls `chromium-common` and a long list of shared libraries (`libasound2`, `libatk1.0-0`, `libatspi2.0-0`, `libdav1d6`, `libdbus-1-3`, `libdouble-conversion3`, `libexpat1`, `libflac12`, `libfontconfig1`, `libfreetype6`, `libgbm1`, `libglib2.0-0`, `libharfbuzz-subset0`/`libharfbuzz0b`, `libjpeg62-turbo`, `libminizip1`, `libnspr4`, `libnss3`, `libopenh264-7`, `libopus0`, `libpulse0`, `libudev1`, `libx11-6`, `libxcb1`, `libxcomposite1`, `libxdamage1`, `libxext6`, `libxfixes3`, `libxkbcommon0`, `libxrandr2`, `libzstd1`, `zlib1g`, …) [MEASURED-INDEPENDENT, packages.debian.org dependency listing]. No compiler stage needed — it's a prebuilt binary package. No build-from-source required.

**2. Chrome for Testing distribution (Google's own binaries), via `@puppeteer/browsers`:**

```
npx @puppeteer/browsers install chrome-headless-shell@stable
```

or fetch directly from the JSON API endpoints Google publishes for automated tooling [developer.chrome.com/blog/chrome-headless-shell]. This path downloads Google's own build rather than Debian's repackage, and needs the same class of shared libraries present on the system (not bundled in the zip) — so apt-installing the dependency set above (or reusing what's already installed for agent-browser's Chromium) is still required even on this path.

**Estimated image-size delta**: apt path adds roughly **~88 MB of download / ~277 MB of installed size** for `chromium-headless-shell` + `chromium-common` alone [MEASURED-INDEPENDENT, sum of Debian package metadata above], **before** accounting for shared-library overlap with what's already installed for `agent-browser`'s Chromium. The image already carries "~17 Chromium apt runtime libs (libnss3, libgtk-3-0, libgbm1, …)" per this repo's existing Dockerfile — several names in chromium-headless-shell's own dependency list (`libnss3`, `libgbm1`, `libatk*`, `libx11-6`, `libxcomposite1`, `libxdamage1`, `libxext6`, `libxfixes3`, `libxrandr2`) visibly overlap with that existing set by name. **The actual net marginal apt download after de-duplication against already-installed packages is not independently measured here** — a real Dockerfile trial (`apt-get install --dry-run` against the existing image layer) would be needed to get a precise marginal number; this doc reports the package's own full weight, not the delta against this specific image.

## Overlap and complement vs Chromium/agent-browser

- **Same engine family, not a different one.** Both `agent-browser`'s Playwright-driven Chromium and `chrome-headless-shell` are Chromium/Blink/V8 under the hood. This candidate is not "a second, architecturally different rendering engine" — it is the *same* rendering/JS engine with the browser-UI shell removed. The pitch of using it alongside agent-browser is purely footprint/startup-cost reduction for tasks that don't need full-browser fidelity (interactive multi-tab sessions, extensions, some print/GPU edge cases), not engine diversity.
- **Driving-layer gap.** agent-browser is Playwright-based; Playwright does not support chrome-headless-shell as a channel [pdf4.dev]. So this candidate cannot reuse agent-browser's existing driver — it needs its own (Puppeteer or raw CDP), which is new integration surface, not a config flag on the existing tool.
- **Dependency overlap likely substantial but not measured.** Both draw from largely the same Debian Chromium-runtime-library family (nss, gbm, atk, x11 libs, etc.), so the *marginal* apt cost of adding chrome-headless-shell to an image that already has agent-browser's Chromium deps installed is plausibly much smaller than the ~277 MB "installed size" figure above, which counts the package in isolation. This is a reasonable inference from the dependency-name overlap, not an independently measured delta — flagged as **UNKNOWN — not established** pending an actual Dockerfile trial.
- **Complementary strength**: single-shot flags (`--screenshot`, `--print-to-pdf`) plus lighter, non-GPU CPU-bound rendering position it as a plausible "cheap, no-session-management" path for one-off "render this URL, get me a screenshot/PDF/DOM dump" agent tasks, distinct from agent-browser's persistent interactive session model.

## Risks and unknowns

- **No independent RSS/startup-time benchmark found** isolating chrome-headless-shell from full Chrome headless. All footprint/speed superiority claims trace back to Chrome's own docs' architectural reasoning ("fewer dependencies," "more performant") or downstream projects repeating that reasoning without new measurement (Quarto, Remotion, PDF4.dev) — none independently re-measured it.
- **No agent-facing tooling exists yet.** Unlike agent-browser (which already provides a CLI + skill), chrome-headless-shell would require building a driving/extraction layer from scratch (Puppeteer or raw CDP + some markdown/text extraction), which is real integration work, not a drop-in swap.
- **Playwright incompatibility** means it cannot piggyback on agent-browser's existing Playwright plumbing at all — a genuinely separate code path.
- **Print/PDF and GPU-dependent rendering have documented divergence** from full Chrome (font-loading timing, advanced print CSS, no GPU acceleration on Linux) — matters if the agent use case ever needs pixel-perfect print output or GPU-rendered canvas content, less so for plain DOM/JS-driven text scraping.
- **arm64 stable-channel status is unresolved** (conflicting sources, see Footprint table) — irrelevant to this repo's fixed-amd64 CCY container today, but worth re-checking if the container ever needs to target arm64.
- **Deprecation churn context**: the old-headless code path *did* get consolidated/removed from the main Chrome binary in M132 (Jan 2025) and now lives only as this standalone artifact — a sign Google is actively curating it as a distinct product, but also a reminder that its packaging story has already changed once in the recent past and downstream tools (Selenium, chromote, html2image, GitLab CI) all had real migration work to do when it happened [multiple GitHub issues cited above]. A repo adopting it should expect that history to potentially repeat.
- **Marginal install-size delta on top of the existing CCY image is not measured** — only the package's standalone footprint is (this doc's Footprint table), not the true incremental cost after de-duplicating against agent-browser's already-installed Chromium runtime libs.
