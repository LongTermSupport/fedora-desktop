T2.4 — root fetch bug reproduced: a failed fetch empties FETCH_HEAD and dates it now (Decision 2)

Lab in untracked/scratch (not tracked): bash-git-prompt cloned at upstream HEAD 4501746 and at
the commit before its April 2026 rework, a bare local remote one commit ahead, FETCH_HEAD
backdated two weeks, an interactive bash under `script` with the play's four bashrc lines.

- Remote needing no key: the prompt's fetch moves origin/main, in the checkout and in a linked
  worktree, both versions. In the worktree the fetch writes `.git/worktrees/<wt>/FETCH_HEAD`
  and upstream checks the common one, so it fetches at every prompt: the worktree lead is
  over-fetching, not the cause.
- ssh stand-in that asks on /dev/tty as ssh does with no key in the agent: the terminal shows
  `Enter passphrase for key:`, the read fails (background process group), the fetch fails,
  `&> /dev/null` hides it, origin/main stays stale, the prompt shows the green tick.
- After that failure FETCH_HEAD is 0 bytes and dated now. Same with a plain `git fetch`
  through the stand-in (git 2.39.5); git master's `do_fetch` truncates FETCH_HEAD before
  `transport_get_remote_refs`, so it holds in current git too.

So both bash-git-prompt's five-minute timer and git-fetch-age read a failing fetch as a fresh
one: the mark never shows in exactly #52's case.
