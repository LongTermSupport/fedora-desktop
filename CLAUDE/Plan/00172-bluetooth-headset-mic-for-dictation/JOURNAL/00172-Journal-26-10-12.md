## 08:29 · finding · —   — Headset mic works once it is the default source; the level is normal

Interactive triage with the owner at the screen.

- The two "Play HiFi quality Music" entries under GNOME's Input "Configuration" were
  the **laptop sound card's** profiles (`HiFi (… Speaker)` and `HiFi (… Headphones)`,
  the latter `available: no`), not the headset's. Choosing the Headphones one removed
  the laptop speaker sink, so the default sink fell back to the headset. That is why
  the owner's output moved. GNOME showed the headset's name as the input while
  offering the laptop card's profiles: the input it was really using was the laptop
  microphone.
- `wpctl set-default` on the headset's `bluez_input` node (what GNOME's selector
  should have done) became the default source at once. A no-target `pw-record` then
  linked to the headset's `capture_MONO`, and WirePlumber switched the headset card
  to `headset-head-unit` (mSBC) by itself. The laptop card stayed on the Speaker
  profile, so input on the headset with output on the laptop works.
- Level: 4 s captured through the headset, peak -5.5 dBFS, RMS -27.9 dBFS, source
  volume 100 %. A normal speech level. The "very low" level the owner saw was the
  laptop microphone. Phase 3 gain is probably unnecessary; confirm with a deliberate
  spoken test.
- After the owner then re-selected the headset in GNOME (Input: the headset; Output:
  the laptop speaker), the saved `default.configured.audio.source` is the headset's
  `bluez_input` node, the default sink is the laptop speaker, and the headset is back
  in A2DP while idle (auto-switch). GNOME's Input "Configuration" still lists the
  laptop card's profile with the headset selected. That looks like a GNOME display
  quirk for the loopback node, which belongs to no card profile; it is not a setting.
- Still open (Task 1.2): why selecting the headset in GNOME's Input list did not make
  it PipeWire's default source. The IaC fix is still owed: nothing so far stops the
  next connect from falling back to the laptop mic.

## 09:45 · finding · —   — WirePlumber restart stalls the connected headset mic until reconnect

**A WirePlumber restart with the headset connected stalls the headset mic until a
reconnect.** Seen twice now (after each `play-hd-audio.yml` run whose handler restarts
WirePlumber). After the restart the default source is still `bluez_input.<addr>`, but
`pw-record` for 4 s at 16 kHz mono s16 returns about 19 KB instead of about 128 KB, i.e.
the stream is starved. A Bluetooth disconnect and connect restores it (127 KB in 4 s).

Consequence: any play that restarts WirePlumber leaves dictation through a connected
headset silently broken. Candidate fix for this plan: the play's restart handler also
reconnects connected Bluetooth audio devices (or the restart is followed by a check that
fails loudly). To be triaged with a plan-local script before choosing.
