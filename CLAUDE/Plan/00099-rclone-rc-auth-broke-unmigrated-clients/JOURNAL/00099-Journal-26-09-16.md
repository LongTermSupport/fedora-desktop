**M2 — the verdict had no denominator, and this is what explains the record.**
`acceptance.bash` printed `ACCEPTED — $PASS check(s) passed` with no expected total anywhere,
and the pass count is data-dependent: check `[2]` emits two passes or one fail, `[3]` emits
one pass or N fails. So "10 passed" read identically whether 10 of 10 ran or 10 of 12 — which
is why `PLAN.md` said 9-failed-then-8/8 while the commit message said 10/10. The gate now
declares `EXPECTED_CHECKS`, registers each check as it runs, and prints

Not taken on trust. A harness runs the real gate against stubbed `findmnt`/`pgrep`/`rclone`

exact failure M2 describes:

```
control : COVERAGE: 9 of 9 checks executed   ACCEPTED   exit 0
mutant  : COVERAGE: 8 of 9 checks executed   NOT RUN: 5   REJECTED   exit 1
```

A coverage line that could not fail would have been decoration, and would have read exactly
the same as this one.

**m4 — the gate hardcoded port 5572, which the repo stopped guaranteeing.** Since `a68c99bb`
the unit template defaults each mount's RC port to `rclone_rc_port_base + mount_index`, so

process, the way every client this plan fixed already does, and aborts if the mount publishes

wrong port: it paired `findmnt | head -n1`'s filesystem with port 5572, so on a multi-mount
host it could ask one mount's RC to refresh another mount's remote. Address and remote are now
read from the same mount in `[0]` and used as a pair.

**m8 — the gate discarded the diagnosis it exists to surface.** Two `2> /dev/null`

defect one level up, inside the gate written to catch it.

**n1 — `awk -F= '{ print $2 }'` truncates a value at its second `=`.** Safe today only
because `play-rclone.yml` generates the password from `ascii_letters` and `digits`; nothing
links the parser to that constraint, and the library's own comment invites overriding
`RCLONE_RC_AUTH_FILE`. Both `rclone-rc-auth.bash` and this plan's `triage.bash` now use

```

after  : SAW_PASS=[pa55==w0rd=x]
```

The failure mode is worth naming: a truncated password surfaces as a 401, and in this

## 18:00 · outcome · T5.10 — round 2 came back BLOCK, and it was right twice

The closing review of the 17:25 fixes returned **BLOCK**: 2 blocking, 4 should-fix, and a

**B1 — I broke `ftp-camera --copy` while fixing the thing it was a symptom of.** The 17:25
work moved address discovery into `rclone_rc_addr_for_mount` and pointed `ftp-camera` at it.
`copy_to_mount` passes `find_mount_path`'s output, which is the mount target **plus the
remote's own path offset** — its header comment says so. The library matched the mountpoint
as it appears in the mount process's argv, where it is the last argument and carries no
offset. Those two strings can only agree when the configured remote has no path, which is not
the configured case and is most of the point of the tool. So `--copy` aborted at "could not
determine the RC address" on every run.

The bug I replaced was **latent** — the camera's remote is mount index 0, so the hardcoded
5572 was correct on this host. Mine was live. That is a worse trade than the one I thought I
was making, and the S3 note claiming the old code "would have bitten a user" was right about
the direction and wrong about which build bites.

Fixed in the library, not at the call site: it resolves its argument to the mount root with
`findmnt -n -o TARGET --target` before the cmdline walk, so a path inside a mount and the
mount itself give the same answer and no caller has to remember which it holds. Falsified
with a real process carrying the unit template's argv (a `bash -c 'sleep 30; :'` — the
trailing `:` matters, since `bash -c 'sleep 30' …` execs and the argv under test disappears
from `/proc/<pid>/cmdline`): mount root resolves, offset path resolves, and a path in no mount
still fails. Removing the normalisation gives `A=1 B=0 C=1` — mutant killed.

**The gate could not see any of it, which is the more interesting half.** Check [6] claimed to
run "the SAME function the deployed ftp-camera calls" but probed the address check [0]
discovered from the mount **target**, so it exercised the one input the client never computes.
Check [6] now resolves from a path *inside* the mount. `find_mount_path` itself is not
callable from the gate — it lives in a 2,475-line executable that runs its main on source and
needs `RCLONE_REMOTE` — so the gate uses `$rc_mount/.`, which carries the one property that
matters: inside the mount, textually not the root. Mutation-tested against a library with the
normalisation cut out: check [0]'s input still resolves, check [6]'s fails. The old gate
could not have failed; the new one does.

**B2 — `triage.bash` died on its own last line, every single run.** The `_planlib` conversion

**S-a — `triage.bash` had no `plan_require_host`.** Run in the container it did not fail; it

**S-b/S-c — the mode was declared and never used.** `plan_mode gather` was set, no
