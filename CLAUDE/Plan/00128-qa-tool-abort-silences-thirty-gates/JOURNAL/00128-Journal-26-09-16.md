## 13:12 · thought · T3.1 — why Phase 3 is worth doing under any of the three answers

Phase 2's decision is the owner's, but it does not gate Phase 3. None of the three options
makes it correct for one gate's missing tool to erase thirty other gates' verdicts. Even
under option A — a playbook installs the deps — the abort path stays reachable for the
other six `exit 2` guards, and the next missing tool would cost the same thirty verdicts.

This is Plan 00125's subject one level up. Its Task 4.3 fixed the equivalent for hard gate
*failures* and deliberately kept the seven tool aborts, so the suite still has one exit
path along which a clean-looking run says nothing about most of itself.

The assertion Task 3.2 needs is the one 00125's Task 4.3 used: mutate a gate's tool
precondition and assert the census still names every other gate. A count read off a
passing run cannot distinguish "thirty gates passed" from "thirty gates never ran", which
is the property.

## 13:35 · action · T1.1 T1.2 — 31, measured, and a contrast I did not expect

**Task 1.1 by clone, not by moving the directory aside.** `extensions/node_modules` is
gitignored, so a `git clone` into `untracked/scratch/` IS the population by construction —
and it leaves the working tree alone, which a mv-it-back probe would not guarantee if it
died in the middle.

```
fresh clone       7 distinct gates report   qa-all exit 2
this working tree 38 distinct gates report  qa-all exit 0
```

**31 gates lose their verdict.** PLAN.md said "roughly thirty" from reading the script;
the measured number is 31, and the static cross-check agrees from the other side — 29 gate
invocations sit after the js gate's line against 6 before it, the difference being gates
invoked more than once and names appearing in comments.

**The contrast in that one run is the real finding, and I did not go looking for it.**
`ansible-syntax` failed **83 times** in the fresh clone (no `roles/` — galaxy deps are not
vendored). Every one of those failures printed, the gate was named in the census, and the
run carried on. That is Plan 00125 Task 4.3 working, visible in the wild. Then the js gate
could not find a tool, printed two lines, and ended the run.

So in a single run: a gate that is comprehensively broken costs its own verdict and
nothing else, while a gate whose OPTIONAL dev tool is missing costs thirty-one other gates
theirs. The suite punishes the milder condition far harder than the severe one. That is a
better argument for Phase 3 than anything in the filed plan.

**Not over-claiming it.** The 83 ansible-syntax failures are not this plan's defect — a
raw clone is not a developer checkout after setup, and CI installs galaxy deps and writes
a vault placeholder first. Recorded in FINDINGS §3 so the 7-versus-38 figure is not read
as "a fresh clone is 83 ways broken". The 31 lost verdicts would be lost on a clone that
HAD `roles/`, because the abort happens after ansible-syntax either way.

**Task 1.2's census settles two things beyond the count of seven.** `qa-docs`'s `exit 2`
is not a missing tool at all — it means the checker produced no usable result, a branch
00125 added so a crash could not read as a clean run, and Phase 3 must not flatten it in
with the other six. And the js gate is the ONLY one whose missing input is dev-only: the
other five name tools any host running these plays has anyway. That is why the
CLAUDE.md-versus-comment conflict lands on this gate and nowhere else, and it narrows
Phase 2's decision considerably.

**One more thing nothing pins (FINDINGS §5):** the number is 31 rather than 1 purely
because of where the js gate sits in the file. No test asserts that ordering. So Phase 3's
fix must not be "move the js gate to the end" — that shrinks this instance to near-zero,
leaves the mechanism intact for the next missing tool, and makes the suite's correctness
depend on an ordering nothing checks.
