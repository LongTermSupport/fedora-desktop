## 01:08 · action · —   — Task 3.2 built: deploy.bash and acceptance.bash

Task 3.2 built. `deploy.bash` runs play-claude-yolo.yml, then `acceptance.bash` as its last leg;
exit 3 from acceptance (files deployed, image still old) is passed on as a note telling the
operator to start ccy once so it rebuilds. Acceptance (gather mode, host only, refuses root and
containers) compares the deployed launcher, every lib file and the Dockerfile with the checkout,
reads the `claude-yolo-version` label of `claude-yolo:latest` against the Dockerfile's, and in
throwaway containers checks the wrapper (with its 5 s guard), `/usr/bin/wl-paste` and `wl-copy`,
then that `wl-paste -l` over the read-only socket exits 0 or 1 (124 is a failure).

Not run here: there is no podman in the ccy container, so the script was exercised with a stub
podman, a fake deployed tree and a real unix socket, with only the host and root guards removed.
Four cases: a drifted lib fails; an old image is PENDING (rc 3); wl-paste rc 124 fails; a
current image with rc 1 (empty clipboard) passes. Meta-deploy now lists this plan folder.

## 01:21 · correction · 01:08   — Image is built by the play; exit 3 removed

The Task 3.2 entry above said the image is not rebuilt by the play and that an old image is
PENDING (exit 3), to be fixed by starting ccy once. That was wrong: play-claude-yolo.yml builds
claude-yolo:latest itself (the "Build Claude YOLO Container Image" and "Verify Container Image"
tasks), so after a deploy the label matches and a mismatch is a real failure. Exit 3 and the
PENDING path are removed; acceptance now also checks REQUIRED_CONTAINER_VERSION equals the
Dockerfile label.

The qa-reviewer also found that `wl-paste -l` returns rc 1 for a failed Wayland connection, not
only for an empty clipboard; rc 1 now passes only when the output lacks "Failed to connect".
deploy.bash runs acceptance through plan_deploy_leg and skips it under --check. Project images
(claude-yolo:<project>) are named as not covered.
