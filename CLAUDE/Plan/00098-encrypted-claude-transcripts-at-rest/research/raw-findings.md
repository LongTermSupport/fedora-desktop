# Raw research findings — Plan 00098

Five parallel research agents: local recon, Anthropic official guidance, prior art, Linux crypto mechanisms, adversarial threat model.

## Nobody has solved the exact problem the user poses — live, at-rest encryption of Claude Co…

Nobody has solved the exact problem the user poses — live, at-rest encryption of Claude Code's session state directory with the key supplied at launch. The closest published art splits into four non-overlapping camps, none of which encrypts the working `~/.claude/projects/*.jsonl` in place: (a) encrypted *sync/archive* tools that copy transcripts out to a remote and encrypt the copy while leaving the local plaintext untouched (tawanorg/claude-sync with age+Argon2, markmatsu/claude-logkeeper with age, hmennen90/claude-device-sync with Argon2id+ChaCha20-Poly1305, nicosuave/agentexport with AES-256-GCM for sharing); (b) redaction hooks that try to stop secrets entering the transcript at all (ShindouMihou/cc-redact, svn-arv/redacted, l-mb/claude-code-redaction-hooks) — all of which explicitly document bypasses, notably `@file` inlining that never touches a hook; (c) offensive/forensic tooling proving the loot is real (xFreed0m/ghosttype, 58★, TruffleHog-backed, targets `~/.claude/projects/**/*.jsonl` by name); (d) Anthropic's own knobs — `cleanupPeriodDays` (30d default, min 1) and `CLAUDE_CODE_SKIP_PROMPT_HISTORY=1`, which is all-or-nothing and kills `--resume`. Anthropic closed the canonical feature request (issue #50014, which asked for exactly "encryption at rest using the system keychain") as **not planned/stale**, so there is no upstream path. The threat model is not hypothetical: the TrapDoor supply-chain campaign (May 2026, 34+ malicious npm/PyPI/crates packages) and a large SEO-poisoning infostealer campaign both explicitly enumerate `~/.claude`, `~/.cursor`, Gemini CLI and Windsurf directories to steal "API tokens, conversation logs, source code, SSH keys". Precursor Security demonstrated TruffleHog flagging planted credentials in a `.claude` config dir immediately. Crucially for this repo, the CCY design is already *more* exposed than the default: session state lives at `.claude/ccy/` inside the project working tree, i.e. in a directory that is bind-mounted, likely inside the user's backup/sync scope, and sitting next to the git repo — so an unencrypted CCY is strictly worse than `~/.claude`, which raises the value of building this. The reusable building block is gocryptfs (`dnf install gocryptfs` exists on Fedora, actively maintained, AES-GCM/EME, passphrase-mounted) — but FUSE-in-rootless-podman has documented friction (`fusermount` EPERM, ACL EOPNOTSUPP under UID mapping), so the safer architecture is to mount the encrypted overlay on the **host** in the CCY launcher and bind-mount the decrypted view into the container, rather than mounting inside it.

## The premise is half-right, and the proposed design defeats almost nothing it is meant to d…

The premise is half-right, and the proposed design defeats almost nothing it is meant to defeat. Encryption at rest with a key supplied at CCY launch means plaintext exists for the entire session lifetime — which is precisely when every realistic attacker (infostealer, malicious npm/MCP package, prompt-injected agent, remote code-exec as the user) is operating. Those attackers run as the user with the key already loaded, so they read the plaintext exactly as Claude Code does. The only scenarios the scheme uniquely improves over existing LUKS FDE are the suspended-laptop case and the un-gitignored-sync case (rsync/Dropbox/Syncthing of the project tree, which `.gitignore` does not cover). Two premises are factually wrong: transcripts do NOT persist indefinitely — Claude Code's `cleanupPeriodDays` defaults to 30 and is demonstrably working here (oldest transcript is 29 days old) — and "the transcript directory" is the wrong scope, because `projects/` is already mode 700 while `file-history/` holds 344 verbatim file bodies (7.7 MB) at mode 644 inside a 755 directory, i.e. the genuinely world-readable leak is outside the directory the user wants to encrypt. Upstream documents this exact threat and prescribes three config-level mitigations (lower `cleanupPeriodDays`, `CLAUDE_CODE_SKIP_PROMPT_HISTORY`, permission deny-rules on credential reads) plus `claude project purge` — all trivially IaC-deployable. Against that, encryption carries a hard blocker: the hooks daemon's `core/transcript_reader.py` reads the `.jsonl` by byte offset (`load_tail`, `read_incremental`), so any whole-file or per-line encryption breaks the Stop handlers, `/resume`, and the daemon's core workflow enforcement. My recommendation: fix the 644/755 permission posture, drop `cleanupPeriodDays` to 1–7, add permission deny-rules for `.env`/credential reads, and only then consider seal-at-session-end archival encryption — which is the one encryption variant that actually shrinks the plaintext window without breaking the live read path.

### Findings

- **[confirmed]** Anthropic's own docs describe this exact threat and prescribe three config-level mitigations — none of which is encryption. The docs state plainly: 'Transcripts and history are not encrypted at rest. OS file permissions are the only protection. If a tool reads a .env file or a command prints a credential, that value is written to projects/<project>/<session>.jsonl.' Recommended: lower cleanupPeriodDays, set CLAUDE_CODE_SKIP_PROMPT_HISTORY, and use permission rules to deny reads of credential files.
  - evidence: https://code.claude.com/docs/en/claude-directory §'Plaintext storage' (lines 1559-1566 of fetched doc)
  - relevance: Three supported, upstream-maintained levers exist that a playbook can set in one line each. A bespoke encryption layer must justify itself against these before it is designed, not after.
- **[confirmed]** The premise 'they persist indefinitely' is FALSE. Claude Code's cleanupPeriodDays defaults to 30 days and is actively working in this very container: the oldest transcript is dated 2026-07-15 against today's 2026-08-13 — a 29-day rolling window, not indefinite retention. The setting is unset in settings.json, so the default is in force, and the documented minimum is 1 day.
  - evidence: find .claude/ccy/projects -name '*.jsonl' oldest = 2026-07-15; date = 2026-08-13; cat .claude/ccy/settings.json shows no cleanupPeriodDays; docs give default 30, minimum 1
  - relevance: The single highest-leverage change is a one-line Ansible-deployed settings.json edit (cleanupPeriodDays: 1-7) that cuts the exposure window by 75-97%. It costs nothing, breaks nothing, and needs no key management.
- **[confirmed]** HARD BLOCKER for encryption: the hooks daemon reads the transcript .jsonl directly and by BYTE OFFSET. core/transcript_reader.py implements load_tail(transcript_path, max_bytes) and read_incremental() using path.open('rb') with seeks. Whole-file encryption makes tail-seeking impossible; per-line encryption breaks json.loads(). 38 daemon source files reference transcripts, including the Stop handlers this project depends on (dismissive_language_detector, hedging_language_detector, auto_continue_stop).
  - evidence: /workspace/.claude/hooks-daemon/src/claude_code_hooks_daemon/core/transcript_reader.py:150 load_tail, :223 _parse_tail, :378 read_incremental, :239/:409 path.open('rb'); rg -l transcript over daemon src = 38 files
  - relevance: This is a design-killer for transparent at-rest encryption of the live transcript. Any scheme must either seal only AFTER session end, or the project loses its Stop-hook workflow enforcement — a guardrail CLAUDE.md treats as mandatory.
- **[confirmed]** The user is scoping the wrong directory. Transcripts in projects/ are already protected at mode 700 (dir) / 600 (files). But file-history/ holds 344 VERBATIM FILE BODIES totalling 7.7 MB at mode 644 inside a 755 parent — world-readable to any local user. 744 of the 969 files under .claude/ccy are mode 644, and the top-level dir is 755.

  - relevance: Against the 'another local user' threat, a chmod -R go-rwx deployed by Ansible closes a real, currently-open hole for zero complexity — while encrypting only the transcript directory would leave the actually-world-readable copies of file contents untouched.

- **[confirmed]** Encryption at rest is a category error against an attacker with code execution as the user. Transparent at-rest encryption 'was designed to defend against theft of physical or virtual storage media only'; an authorised process 'can gain access to sensitive data either by running a legitimate query or by scraping RAM', and the threat model 'assumes an attacker without access to a running system'.
  - evidence: https://scottarc.blog/2024/06/02/encryption-at-rest-whose-threat-model-is-it-anyway/ ; https://www.verygoodsecurity.com/blog/posts/threat-modeling-for-data-protection
  - relevance: Directly refutes the user's stated goal for 5 of 9 scenarios (live session, no-session code exec, malicious package/MCP, prompt-injected agent, root). A launch-time key is by definition present whenever the attacker's code is running as the user.
- **[confirmed]** Scenario-by-scenario verdict. NOTHING: (a) remote code-exec as user with session live — key is loaded, attacker reads plaintext; (b) malicious npm/pip/MCP package as user — same; (c) prompt-injected Claude session reading transcripts — the agent has the decrypted view by construction; (d) root on the same box — root reads the key from process memory or the ssh-agent-style store; (e) stolen laptop powered OFF — LUKS already covers this, encryption adds nothing. PARTIALLY: (f) remote code-exec as user with NO session live — helps only if the key is not cached on disk, and only until the next launch; (g) another non-root local user — but chmod 700 achieves the same for free. GENUINELY HELPS: (h) stolen laptop SUSPENDED with LUKS keys in RAM; (i) cloud sync / backup exfiltration of the project tree.
  - evidence: Synthesis of transcript_reader byte-offset reads, launch-time key lifetime, and the TDE threat-model sources above
  - relevance: The honest scorecard: 2 of 9 scenarios genuinely improved, and one of those (suspend) is better fixed at the LUKS layer. This is the core answer the user asked for.
- **[confirmed]** LUKS FDE does NOT cover the suspended laptop, and this got worse recently. Encryption keys remain resident in RAM across suspend-to-RAM, and a kernel regression dating to Linux 6.9 meant disk-encryption keys were never wiped from RAM on sleep — explicitly affecting Fedora among others. Mitigation is cryptsetup luksSuspend / systemd-level key wiping, not application-layer encryption.
  - evidence: https://pbxscience.com/two-year-old-linux-bug-left-luks-encryption-keys-exposed-in-memory-during-suspend/ ; https://github.com/systemd/systemd/issues/17887
  - relevance: This is the one scenario where the user's instinct is right — but the correct fix is at the FDE/suspend layer for the WHOLE disk, not a bespoke scheme protecting one directory while ~/.ssh, .env files and browser tokens on the same disk stay exposed.
- **[confirmed]** Git cannot leak transcripts, but sync/backup can. .claude/ccy/* is ignored by a self-excluding nested .gitignore (verified via git check-ignore), and only 4 deliberate files are tracked (.gitignore, Dockerfile, ccy.env, claude-supervise.py). However .gitignore is a GIT construct — it does nothing for rsync, tar, Dropbox, Syncthing, rclone or Time-Machine-style backups of the project tree, and .claude/ccy sits inside the working tree by design.
  - evidence: git check-ignore -v → .claude/ccy/.gitignore:17:* ; git ls-files .claude/ccy/ → 4 files only; cat .claude/ccy/.gitignore
  - relevance: Kills the 'transcript gets pushed to the public repo' fear (it cannot), and isolates the real exfil-by-copy risk to non-git sync — which is the second of only two scenarios where encryption genuinely helps.
- **[likely]** Observed secret density is lower than the premise assumes, but the mechanism is real. In a 5.7 MB transcript: zero GitHub tokens (ghp_/github_pat_), zero AWS keys (AKIA), zero private-key headers, zero Bearer headers. The 16 'sk-ant-' hits are all exactly 13 characters — i.e. pattern mentions like 'sk-ant-api03', not live keys. 6 of 14 transcripts carry ANSIBLE_VAULT ciphertext, which is already encrypted and low blast radius. What IS dense: '.env' 263×, 'password' 378×, 'passphrase' 127×.
  - evidence: grep -aoc over a07be25c-*.jsonl; awk length over sk-ant- hits → 16×13 chars; grep -al ANSIBLE_VAULT *.jsonl → 6 of 14
  - relevance: Argues against a costly encryption build and FOR cheap targeted controls: the leak vector is .env/credential-file READS, which the documented permission deny-rules block at source — preventing the secret from ever entering the transcript rather than encrypting it afterwards.
- **[confirmed]** Two upstream escape hatches exist that make the transcript problem disappear, at a cost. CLAUDE_CODE_SKIP_PROMPT_HISTORY skips writing transcripts and prompt history entirely in any mode; claude project purge deletes transcripts, auto memory, per-session tasks/debug/file-history, matching history.jsonl lines, and the ~/.claude.json entry, printing a deletion plan and confirming first.

## CCY state lives at `/workspace/.claude/ccy` via `ln -sf /workspace/.claude/ccy /root/.clau…

CCY state lives at `/workspace/.claude/ccy` via `ln -sf /workspace/.claude/ccy /root/.claude` (entrypoint.sh:195), which resolves through the `-v "$PWD:/workspace"` bind to the host project dir — currently 68 `.jsonl` files totalling 47,434,185 bytes, plus a 2,177-entry `history.jsonl` of every prompt ever typed. A critical methodological trap surfaced: `grep` in this container is a shell function wrapping `ugrep --ignore-files`, which honours `.gitignore`; since `.claude/ccy/.gitignore` is `*`, every recursive grep of the transcript tree silently returns zero hits. My first secret scan returned all-zeros because of this and was wrong — rerun with `command grep`, historical transcripts show 0 live-credential markers (no `sk-ant-` with entropy tail, no `ANTHROPIC_API_KEY=<value>`, no private-key bodies), but 7 files carry 27 `$ANSIBLE_VAULT` ciphertext blobs, proving sensitive file contents are captured verbatim. So the premise is half-confirmed: the mechanism to capture secrets is demonstrated, but no live plaintext key is presently sitting in the historical archive — the risk is prospective, not realised. Git exposure is well defended by three independent layers and is not a real risk. Two facts should reshape the design: the host filesystem is **already LUKS-encrypted** (`/dev/mapper/luks-…` btrfs), so this buys nothing against disk theft and only defends against a logged-in attacker, backup exfil, or another local user; and the container has **no CAP_SYS_ADMIN, no `/dev/fuse`, no `/dev/loop*`, no fusermount** — FUSE inside the container is impossible as configured, forcing any encrypted-mount design onto the host side. The launch flow already has an exemplary precedent for the passphrase: BSH-09 (claude-yolo:2756-2762) passes secrets by env **name** so values never enter `/proc/<pid>/cmdline`. Note Plan 00098 already exists and is In Progress for exactly this work.

## Two facts probed from inside the live CCY container reshape this whole question. First, th…

Two facts probed from inside the live CCY container reshape this whole question. First, the host root filesystem is **btrfs on `/dev/mapper/luks-<uuid>…`** — full-disk LUKS is *already* deployed, and btrfs still has no merged fscrypt support (v7 patches were still in review as of May 2026), so option (c) is off the table on this machine. Second, `.claude/ccy/` is **not** wholly gitignored: `ccy.env`, `claude-supervise.py`, `Dockerfile` and `.gitignore` are tracked files, and `ccy.env` is read by the *launcher on the host before the container starts* — so the encryption boundary cannot be `.claude/ccy/` itself without breaking bootstrap and showing four tracked files as deleted. Only gocryptfs is a credible mechanism here (Fedora 44 ships 2.6.1-5.fc44), but a host-side gocryptfs mount *inside* `$PWD` fails twice by default: podman's `-v` defaults to non-recursive `bind` + `private` propagation so the submount is silently dropped, and FUSE denies all other users unless mounted `-allow_other` with `user_allow_other` set in `/etc/fuse.conf` (podman#14488, confirmed by a podman maintainer). The cleaner architecture is to invert it — keep the ciphertext as an ordinary directory on the existing bind mount and mount gocryptfs **inside** the container (`--device /dev/fuse`, `--cap-add SYS_ADMIN`), so plaintext never exists in the host mount namespace at all and dies with the container. For key handling, rank: pipe the passphrase straight into `gocryptfs -extpass` and discard > kernel keyring (`keyctl`/`systemd-ask-password --keyname`) > systemd credentials > agent > env var, which is disqualified outright because `-e` persists into podman's on-disk container config and any inherited env is dumped into the very transcripts you are trying to protect. On the decisive question: **an always-mounted decrypted view does not defend against the stated threat.** While a session runs, plaintext is readable by exactly the same UID the attacker would have; the honest benefit is shrinking the exposure window from "forever" to "while mounted", plus protecting backups and other accounts on the box — which is real, but is not what "anyone who gains read access gets a goldmine" describes. Retention/shredding of old transcripts and sealing the *archive* with a key that never touches the box are higher-leverage than encrypting the live directory.

  - relevance: Strictly better threat properties: plaintext exists ONLY in the container's mount namespace, is never visible in the host filesystem namespace, and is destroyed when the `--rm` container exits — which structurally fixes the 'plaintext left mounted after a kill' failure. - **[confirmed]** `:Z`/`:z` relabelling cannot rescue a FUSE mount: FUSE filesystems generally cannot carry per-file SELinux labels, and gocryptfs's `-context` option requires root.
  - evidence: gocryptfs(1): "-context string: Set the SELinux context. Requires root"; SELinux mailing list: "FUSE filesystems (fusefs) do not support extended attributes, and so you cannot label files on them"; kernel commit "selinux: never allow relabeling on context mounts"; podman volume.md warns relabelling walks every inode and must not be used on system dirs
  - relevance: If the host turns out to be enforcing, the host-side-FUSE plan has no clean fix — you would need `--security-opt label=disable` (weakens the container) or a root-mounted `-o context=…container_file_t`. Another point in favour of mounting inside the container instead.
- **[confirmed]** gocryptfs encrypts file content in independent 4096-byte plaintext blocks, each with a 16-byte random nonce and 16-byte GCM tag (0.78% overhead); a corrupted or torn block fails authentication in isolation, not the whole file.
  - evidence: gocryptfs Documentation/file-format.md: header + blocks of up to 4096 bytes plaintext; "16 byte GCM IV + 1-4096 byte encrypted data + 16 byte GHASH tag"; "Overhead = (16+16)/4096 = 1/128 = 0.78125 %"; gocryptfs(1) `-force-decode` "forces decode of encrypted files even if the integrity check fails"
  - relevance: Crash durability for appending .jsonl is acceptable-but-worse-than-plaintext: an append is a read-modify-write of the final partial block, so a torn write costs at most the last ≤4 KiB, recoverable with `-force-decode`, and earlier lines still decrypt. Compare plaintext, where a torn append costs a partial line. Bounded tail damage, not whole-file loss.
- **[likely]** gocryptfs has measurable FUSE overhead concentrated exactly on small writes, and does not benefit from the buffer cache the way a native filesystem does (data is re-decrypted on re-read).
  - evidence: rfjakob/gocryptfs discussion #756: "For small blocksizes, like 1k, the FUSE overhead comes into play quite a bit"; techfindings.net Linux filesystem encryption performance: "gocryptfs fails to make use of the buffer cache, or at least the buffer cache is on the wrong side of the encryption. Thus if a file is read twice it is decrypted twice"
  - relevance: Directly on point for the workload: Claude Code appends many small records to .jsonl continuously. Current volume is 62 MB / 68 jsonl files / 48 MB of jsonl with a 5.7 MB largest file — small in absolute terms, so absolute latency should stay low, but this must be benchmarked on the host rather than assumed. A per-append RMW of a 4 KiB block plus a FUSE round trip is the cost.
- **[confirmed]** gocryptfs supports supplying the passphrase from a program's stdout (`-extpass CMD`), from a file (`-passfile`), or a master key on stdin (`-masterkey=stdin`), and can auto-unmount after inactivity (`-idle 2h45m`) and self-check with `-fsck` (exit 26 on corruption).
  - evidence: gocryptfs(1) manpage (man.archlinux.org/man/gocryptfs.1): -extpass "program should return the password on stdout"; -passfile "Read password from the specified plain text file"; -masterkey "Use '-masterkey=stdin' to avoid that risk"; -idle "automatically unmount the filesystem if it has been idle for the specified duration"; -fsck "If corruption is found, the exit code is 26"
  - relevance: `-extpass` is the correct integration point for the CCY launch prompt (alongside the existing SSH-key prompt): a tiny helper reads from /dev/tty per CLAUDE/InteractiveScripts.md and writes to stdout; nothing touches disk and nothing appears in /proc/*/cmdline. `-idle` is the backstop for the 'plaintext left mounted' failure that an exit trap cannot cover on SIGKILL.
- **[confirmed]** Environment variables are the worst place to hold the key: readable via /proc/<pid>/environ by any same-UID process, inherited by every child, and — specific to CCY — anything passed as `podman run -e KEY=…` is persisted into podman's on-disk container config.
  - evidence: systemd-devel 'Environment-variable security?': env vars are readable from /proc/$PID/environ and "propagated down the process tree by default, and almost nothing sanitizes env vars"; Cloudflare kernel keyring post: keyring "can limit exactly how passwords are propagated, and every access to them requires a privilege check"
  - relevance: Answers question 3's ranking with a CCY-specific kicker: an env var would be inherited by Claude Code itself, whose tool output and environment dumps are written into the very .jsonl transcripts being protected — a self-defeating loop. Same argument disqualifies command-line args (/proc/*/cmdline is world-readable).
- **[confirmed]** `systemd-ask-password --keyname=<name>` natively deposits the passphrase into the kernel keyring rather than the screen or logs, and `--accept-cached` retrieves it; keyring entries are ephemeral, access-checked per-process, and never written to disk.
  - evidence: systemd-ask-password(1): pushes collected passwords "into the kernel keyring of the root user as a key of a specified name"; `--accept-cached` retrieves cached passwords from the kernel keyring instead of querying; default cache timeout 2.5 minutes
  - relevance: The ranked #2 option for key custody. Note the 2.5-minute default timeout means it is a hand-off buffer between prompt and mount, not session-lifetime storage — which is the right shape anyway, since the mounted gocryptfs process holds the derived key thereafter and the passphrase should be discarded.
- **[likely]** A host-side gocryptfs mount is NOT torn down when the container is killed, and a gocryptfs process that dies without unmounting leaves a stale 'Transport endpoint is not connected' mountpoint requiring `fusermount3 -u`.
  - evidence: Architectural consequence of the mount living in the host mount namespace (CCY runs `--rm` containers; the mount is created by a separate host process). gocryptfs(1) documents `-idle` auto-unmount as the mitigation for exactly this class of problem.
  - relevance: Answers question 4's 'is plaintext left mounted' with a clear yes for the host-side design: a `kill -9` of the container, an OOM kill, or a terminal closing leaves the decrypted view readable indefinitely. - **[confirmed]** File-level encryption (age/gpg/sops) cannot provide at-rest protection for a file that Claude Code holds open and appends to for the whole session.
  - evidence: Structural: Claude Code owns the .jsonl write path and appends continuously (history.jsonl is 645 KB and growing; 68 jsonl files totalling 48 MB in .claude/ccy). age 1.3.1-4.fc44 and gpg operate on whole files, one-shot, with no transparent write interception.

That is genuinely useful and complements — but cannot replace — live-session protection. It also degrades gracefully (no mounts, no FUSE, no SELinux, no podman flags, no crash-time plaintext) and is by far the simplest thing to make IaC-clean.
- **[confirmed]** The tarball-to-tmpfs approach (option f) has the worst crash profile of all candidates: a power loss or container kill destroys the entire in-flight session transcript and breaks `claude --resume`.
  - evidence: tmpfs is volatile RAM; the re-seal step runs at exit and never runs on SIGKILL/power loss. Container /dev/shm is only 64 MB (`size=64000k` in mountinfo) against 62 MB of existing state, so it would additionally need an explicitly sized host tmpfs.
  - relevance: Disqualifies (f) for a tool whose transcripts are the session-resume mechanism. It also violates the project's fail-fast posture by design — the failure mode is silent data loss, not a loud error.
- **[confirmed]** Encrypting only the CCY path leaves the other half of the stated problem untouched: desktop (non-container) Claude Code still writes plaintext .jsonl to the host ~/.claude/projects/<slug>/.
  - evidence: Stated in the project context and consistent with the CCY design (entrypoint symlinks /root/.claude → /workspace/.claude/ccy specifically to divert container state away from ~/.claude)
  - relevance: Any proposal that only hardens CCY should say so explicitly rather than implying the transcript-leak problem is solved. The host ~/.claude case has no container boundary and would need a different mechanism (most plausibly the same gocryptfs + systemd user unit, or age-sealed archival).

### Gaps

- DECISIVE UNKNOWN: whether the host is SELinux Enforcing or Permissive. Evidence from inside the container (container_t successfully writing user_home_t with no :Z and no --security-opt) points to Permissive or a local allow rule, but this cannot be determined from inside — /sys/fs/selinux is not mounted in the container. Needs a HOST triage probe: `getenforce`, `sestatus`, `ausearch -m AVC -ts today`, `semodule -l | grep -i container`. Every SELinux answer in question 2 hinges on this.
- Whether Claude Code tolerates its entire state directory being a FUSE mount. .claude/ccy contains daemon.lock (flock), session-env/, file-history/, paste-cache/ and shell-snapshots/ — no SQLite databases were found, which removes the biggest risk, but flock/fcntl semantics over FUSE with allow_other were not tested. Needs an empirical trial before commitment.
- No measured performance numbers on this host. The FUSE small-write overhead claim is sourced from upstream discussion and third-party benchmarks, not from a benchmark on this btrfs-on-LUKS machine with this workload. A plan-local triage script should time a realistic append pattern against both plain and gocryptfs paths.
- Fedora 44 packaging for `rage` could not be confirmed — packages.fedoraproject.org/pkgs/rage/rage/fedora-44.html failed to fetch (socket hang up). `securefs` in Fedora 44 is only indirectly evidenced (it appears in a GUI-frontend package's description with results listed for f43/f44/f45/rawhide), not directly confirmed. `encfs` for Fedora 44 returned HTTP 404, which suggests but does not prove retirement.
- Whether Fedora 44's container-selinux policy permits container_t to open /dev/fuse without flipping the `container_use_devices` boolean, and whether gocryptfs mounted inside a rootless container's userns works without --security-opt label=disable. The 'mount inside the container' architecture is rated 'likely' rather than 'confirmed' for exactly this reason and needs a real trial on the host.
- Whether gocryptfs mlocks or otherwise protects the derived master key in its own process memory. Not verified — so the claim 'the key is safe once mounted' is deliberately not made. An attacker with the same UID can read /proc/<gocryptfs-pid>/mem regardless.
- No verification of how git tooling behaves with a ciphertext directory inside the working tree over time — in particular whether `git clean -xfd` would destroy the ciphertext store (the .gitignore rules suggest yes, since .claude/ccy/* is ignored), and whether the repo's pre-commit secret scanner reacts to base64-ish ciphertext filenames.
- The passphrase-loss recovery story was not researched: gocryptfs supports a master-key escape hatch (`-masterkey`) but no key-rotation or multi-slot design was evaluated, and there is no answer yet for what happens to months of archived transcripts if the user forgets the passphrase.
