# Plan 00266 Task C.3: verify-restore reports the LXC set

## What was built

- **`lxcstate.ReadRunningRecord`** returns the containers recorded at the last shutdown, plus
  whether the record exists at all. This tells "no record written" apart from "recorded none
  running". `ReadRunning` now wraps it.

- **The LXC set status** (`internal/teamchat/host/lxc/lxcset`, `paths.LXCSetStatusFile`,
  `/var/lib/teamchat-status/lxc-set.json`). The boot unit's verb, `lxc boot` or `lxc reconcile`,
  ends with `lxc.WriteSetStatus`. It compares `_lxc-running.json` with the containers at that
  moment and writes the result with this boot's id (`/proc/sys/kernel/random/boot_id`) and the
  time. The file is root's, mode 0640, group `teamchat_owner_group`, and is written atomically
  (`teamchat/state.WriteFile`). Each line is one of these kinds:

  - `UP`: recorded and running.
  - `DOWN <lxc-info state | ABSENT>`: recorded and not running.
  - `UNRECORDED`: running but not recorded.
  - `NO-RECORD`: no container; its why is the record's path. It comes first, when the record
    was never written.

  If the verb cannot read the record, the container list, a state or the boot id, it fails,
  names the step `set status`, and leaves the last file as it was. `lxcset.Read` and `Write`
  refuse a file in any other form (an unknown key, another version, a line in no kind's form).
  `lxc boot` still writes the status after a refused start, and names its error beside the
  refusal counts.

- **`systemd.UnitEnabled`** returns the word `systemctl is-enabled` prints, whatever its exit
  status. It is an error only when there is no word or systemctl cannot run.

- **`ccy-sessions verify-restore`** first checks `teamchat-lxc-boot.service`:

  - `disabled` or `not-found`: it says so on stderr and reads nothing.
  - any other word but `enabled`: it fails.
  - `enabled`: it reads the status file as the user, with no sudo, and compares its boot id
    with this boot's (`CCY_BOOT_ID_FILE`, the same file the restore manifest uses). It then
    prints `lxc:<c> RUNNING`, `lxc:<c> NOT-RUNNING <state>`, `lxc:<c> NOT-RECORDED` and
    `lxc NO-RECORD` after the session lines, and says on stderr when the boot unit looked.
    With no file it prints `lxc NO-STATUS`, and with a file from another boot `lxc STALE`.
    Both fail.

  The LXC lines are printed even when the sessions' half failed, and the exit is 0 only when
  both halves pass. `NOT-RUNNING`, `NO-RECORD`, `NO-STATUS` and `STALE` fail. `NOT-RECORDED`
  is said on stderr and passes. `--wait` shares one deadline with the sessions' half. It looks
  again only while the status is missing or stale, because the boot unit writes it once per
  boot. A file it cannot read (the user not in the owner group, or an invalid file) or no boot
  id is a failure, never a state.

- **`play-teamchat.yml`** installs no sudoers rule. One task, with no condition, removes
  `/etc/sudoers.d/teamchat-lxc-check-running` from any host where the first C.3 build put it.
  `teamchat-admin lxc check-running` and `files/etc/sudoers.d/teamchat-lxc-check-running.j2`
  are gone.

- **Why the first design was replaced.** C.3 first ran `lxc check-running` through a NOPASSWD
  rule for the owner group. That failed two gates, and both were right:
  `installplay`'s TestThePlayReadsNothingTheTargetLacks (the template read `root_dir` on the
  target), and `qa-ansible`'s sudoers-rule (a rule must name the fixed user `user_login`,
  never a group). Moving the rule to `user_login` would break the first gate again. A status
  file needs no privilege, so neither gate applies.

## Departures from DESIGN.md and the brief

1. **Root's view reaches the user through a status file.** DESIGN.md has the root verify
   unit report the LXC set. The brief has verify-restore report it. verify-restore runs as the
   user (`cycle.py` `_ccy_sessions` uses runuser), and both the record (root 0600) and the
   container list are root's. So the boot unit's root verb writes what it found to the
   owner-group status tree, which the user reads. The report is the set when the boot unit
   looked, not when verify-restore runs. A container started later by other means is still
   `NOT-RUNNING` until the next boot. This is right for "did the boot unit bring it back".
2. **NOT-RECORDED passes.** The boot unit promises at least the recorded set, and
   `lxc.start.auto` or a host's own IaC may start more.
3. **Seats are not judged here.** `lxc boot`'s reconcile lines in the boot unit's journal
   report them. The PLAN.md open item (a guest's systemd not ready when reconcile reaches
   it) still waits for the live reboot.
4. **A stale shutdown record still cannot be detected.** The status carries a boot id, so a
   status from another boot is a finding. But if the record unit failed at a shutdown, the
   `_lxc-running.json` left from the shutdown before still looks fresh, because the record
   itself carries no boot stamp. Possible follow-up: stamp the record too.
5. **The quiet pass now prints one line.** `TestVerifyRestorePassesWhenEverythingIsPastItsPrompts`
   expected an empty stderr. It now expects the one line that says the LXC boot unit is
   disabled.
