## What the code does today (read 26 Nov)

- The seat's unit text is written by `lxc apply` (`apply.go` `placeUnit`), not by `lxc start`.
  Its PATH is fixed in the text (`unit/unit.go:92`) and its command is the bare `claude`
  (`unit.go:72`), which `teamchat run` is handed after `--`.
- `lxc start --member` (`restart.go` `Start`) only calls the guest systemd's `ResetFailed` and
  `StartUnit` over D-Bus (`guestbus.Systemd`). It sends no environment and runs nothing in the
  guest.
- The only way the host runs a program in a container is `lxccmd.LXC.Guest`. It runs the host
  kit's own `teamchat` binary with one of the registered guest ops, under a cleared environment
  and a fixed system PATH. It refuses any other program by design (TB3). There is no route that
  runs the container user's shell.

## Q1: how does the resolved PATH reach one start without being kept in the unit?

systemd takes a unit's environment only from the unit, its drop-ins, an `EnvironmentFile=` or
the manager's own environment. `StartUnit` carries none. The plan says "neither the unit file nor
the recorded start command keeps the PATH", but names no carrier. The candidates, each a choice
with a different trust and lifetime:

1. **A runtime drop-in** the start writes through the guest root
   (`/run/systemd/system/<unit>.d/…conf`), followed by a reload. It lives until the container's
   next boot and is rewritten at every start. Is a `/run` drop-in "in the unit"?
2. **An `EnvironmentFile=` line** in the unit (fixed), naming a per-seat file under `/run` that
   each start rewrites. The unit text changes once; the PATH is never in it.
3. **The guest's own lookup at start:** ExecStart, or `teamchat run` inside the guest, asks the
   login shell itself. Then the host asks nothing, which departs from "the host asks".
4. The manager's `SetEnvironment`: global to every unit in the container. I would rule it out.

## Q2: through what route, and which shell mode, does the host ask?

- **Route.** Running the user's login shell from the host needs either a new guest op (the kit
  binary execs the shell and returns two validated paths) or a raw `lxc-attach` beside
  `Guest`. A raw attach breaks the TB3 rule that only the kit binary runs in a guest. Which one?
- **Mode.** The plan's own fact is that `~/.bashrc` loads nvm only in an interactive shell. A
  login shell that is not interactive (`bash -l -c`) sources `.bash_profile`, then `.bashrc`.
  The usual guard in `.bashrc` returns before the nvm lines, so the lookup would find nothing in
  exactly the case R77 is about. It likely needs `-l -i -c`, which runs the user's whole rc
  under the host's attach (as that user, not root). Is that accepted, and is the shell bash or
  the passwd entry's shell?
- **Validation** (I would assume this; please confirm): each answer must be one absolute,
  clean path by `paths.ValidUnitPath` before it reaches any unit or environment text, and the
  output is bounded. A guest byte never appears in an error.

## Q3 (smaller): does `lxc apply` also need the lookup?

If Q1 picks option 1 or 3, apply's unit text needs no lookup. If it picks 2, apply changes the
