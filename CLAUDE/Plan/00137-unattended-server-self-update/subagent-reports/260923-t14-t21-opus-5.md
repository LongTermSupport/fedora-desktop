# Plan 00137 — Tasks 1.4 (shared play lock) and 2.1 (unattended single play)

## Task 1.4 — the lock

**Path:** `$XDG_RUNTIME_DIR/fedora-desktop-plays.lock`, else `/run/user/<uid>/…`
(`helpers/play_lock/lock.py`).

Why this path and not the alternatives:

- **Not `/run/fedora-desktop/` via tmpfiles.d.** That needs a deployed entry before the lock
  can work, and the first thing a lock-taking `run.bash` ever runs could be the play that
  deploys it. `/run/user/<uid>` already exists for any user with a session or linger, and the
  server has linger (`play-systemd-user-tweaks.yml`).

- **Not in a checkout.** D4 puts the cycle in a deploy-only clone and humans in their own
  checkout. Both run plays against the same host, so the lock must be outside both.

- **Root can use it safely.** D5's orchestrator is root and serves the user, so it opens the
  file in a directory the user controls:

  - the lock is opened with `O_NOFOLLOW`;
  - it is created only with `O_CREAT|O_EXCL`, which refuses dangling links as well;
  - it must be a regular file owned by the user, and a file root creates is `fchown`ed to
    the user;
  - the runtime directory must be a real, user-owned directory that nobody else can write.

  Tests cover: a symlinked lock, a dangling symlink (nothing is created through it), a
  directory at the path, a missing, group-writable, foreign or symlinked runtime directory,
  and root creating a file for another uid (runs only when root; ran here).

- **Root cannot lock in its own directory by mistake.** Root must pass `--user`, because
  root's `/run/user/0` would serialise nothing.

**Holding it:**

- `run.bash` takes it with `flock -n` on a descriptor it keeps for its life, so its children
  inherit the hold.
- **Busy** → exit **75** (EX_TEMPFAIL), naming the holder. The holder writes
  `pid=… what=… since=…` into the lock file; a stale note is harmless, since it is only shown
  while the lock is held.
- **Delegation:** a holder exports `FEDORA_DESKTOP_PLAY_LOCK_FD=<fd>` and lets the child
  inherit that fd. `lock held` proves the claim before `run.bash` trusts it: the fd has the
  same inode as the lock path, and a non-blocking re-flock on that open file description
  succeeds. A claim that fails is an **error**, not a fallback to taking a second lock. This
  is how the root orchestrator will hold the lock across the whole cycle while `run.bash`
  runs each play inside it.
- **Bounded wait:** `acquire(fd, wait_seconds=…)` is library-only; the orchestrator will use
  it in-process. The CLI is `path` and `held` only; no `run` wrapper was built (YAGNI).

**Who takes it:**

- `run.bash` single-play mode, in both interactive and headless mode.
- `fedora-desktop-health --run-play` runs the play through its shebang and so enters
  `run.bash` single-play mode. It needed no change and is covered.
- The cycle (Task 4.1) will use the library.
- **Not covered:** a full `run.bash` provisioning run, and a bare `ansible-playbook`. The
  lock is cooperative.

**Known edge, not handled:** children inherit the lock fd. A play that started a
long-lived process as a direct child of `ansible-playbook` would keep the lock held after
`run.bash` exits. The next run would then refuse loudly with exit 75; it would not fail
silently. Services started through `systemctl` are children of systemd and do not inherit
it.

## Task 2.1 — unattended single play

**Flag: none new.** `--headless <play>.yml`, or `RUN_BASH_HEADLESS=1` through a play's own
shebang (`RUN_BASH_HEADLESS=1 ./playbooks/imports/play-claude-yolo.yml`), which used to be
refused ("a single play is interactive-only"), now runs one play unattended. This keeps to the
existing flag set and the `--help-run-headless` contract, and the shebang route works for
a timer without a new entry point.

- **Preflight:** `headless_play_preflight` refuses root and checks only sudo. The sudo
  decision is extracted from `headless_preflight` into `hl_sudo_credential`, so both
  preflights share one definition of a usable credential. There are no identity, GitHub or
  vault inputs and no first-install legs: dispatch happens before them, as it did for
  interactive single play.
- **Password (D5):** `RUN_BASH_SUDO_PASSWORD_FILE` may be `/dev/fd/N`. A root caller opens
  the root-only 0600 file and passes it down as an inherited descriptor, e.g.
  `runuser -u USER -- env RUN_BASH_SUDO_PASSWORD_FILE=/dev/fd/3 … 3<file`. The bytes are
  read once into the existing 0600 temp copy, proven with `sudo -k -A true`, handed to
  Ansible as `--become-password-file`, and unlinked by `hl_cleanup` on exit (tested: the
  copy is gone afterwards).
- **Run:** PATH gains `~/.local/bin`. `ansible-playbook … </dev/null` runs with no BECOME
  prompt and no issue-filing prompt, and its exit status is `run.bash`'s.
- **Interactive single play:** unchanged, except for the lock refusal when the lock is held.
- **Behaviour change, recorded in the changelog:** a piped single play with a `RUN_BASH_*`
  variable set used to be refused and now runs unattended.
- **Versions and docs:** `RUN_BASH_VERSION` 1.21.1 → **1.22.0**, `docs/run-bash-changelog.md`,
  `--help`, `--help-run-headless` ("ONE PLAY, UNATTENDED"), and a short
  `docs/headless-provisioning.md` section.

## Tests

- `tests/helpers/play_lock/test_lock.py`: 27 cases, all real flock on real files. Two
  holders, a bounded wait that is released and one that times out, delegation that is real
  or bogus (garbage, closed fd, another file, a non-holding descriptor of the same file),
  every unsafe-path refusal, and the CLI.
- `scripts/test-run-bash-single-play.bash`: 39 cases, wired into `qa-all.bash` and listed in
  `CLAUDE/QA.md`. It runs the real `run.bash` and the real helper in a throwaway checkout,
  with stubs for `ansible-playbook` (only in `~/.local/bin`), `sudo` and `whoami`. stdin is
  a pipe, so "stdin closed" proves `run.bash`'s own redirect.
- **Mutations:**
  - dropping `</dev/null` fails the stdin check;
  - dropping the `play_lock_take` call fails 11 lock checks.
