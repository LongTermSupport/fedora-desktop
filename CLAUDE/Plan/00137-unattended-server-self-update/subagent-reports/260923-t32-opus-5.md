These prompts cannot be reached on replay because the replay filter removes their flags:

- the `--debug` layer prompts;
- `--custom`;
- the token create, renew and export modes;
- the `ccy --top` Action prompt;
- the `>` sub-prompts inside the zombie and manage menus.

`ccy` still needs an interactive terminal. A restored pane always has one, so nothing
fails before the first prompt.

## What restore answers automatically, and why

`ccy-sessions restore` starts each pane as `env CCY_SESSION_RESTORE=1 <launcher> …`. The
`ccy` launcher accepts only an empty value or `1`; any other value is an error. It reads the
marker once and unsets it straight away, so neither the container nor `claude` inherits it.
`cc` unsets it at once, because it has no prompt with a single safe answer.

- **Quick Launch → Y.** The saved configuration is what this project last launched with,
  and it is the only evidence of what the user wants. Answering N would open the full
  question chain, which is exactly what an unattended boot cannot answer.
- **Zombie containers → ignore.** After a reboot, a running `ccy` container that has no
  terminal cannot be proved dead: something else started it, or it belongs to a sibling
  session that is still coming up. "Ignore" stops and removes nothing. Stopped containers
  were already removed by `clean_stale_containers_startup`, as before.
- **Existing project containers → continue alongside.** Restore brings back every session
  in a project together. Refusing to run beside a sibling would strand all but the first.

Each auto-answer is announced on stderr (`Session restore: …`), so an attached person can
see what was chosen.

Why the other prompts are left waiting instead of failing:

- These prompts have no safe answer: token choice, SSH key or passphrase, GitHub-over-443,
  network, compose, and migration.
- If the launcher failed, it would return. The trampoline would then remove the registry
  record and the session would be lost for good.
- A prompt keeps the record and lets a person attach. The verifier makes the wait visible.

## Verification: `ccy-sessions verify-restore [--wait SECONDS]`

Restore writes a manifest to `~/.local/state/ccy/last-restore` (`ccy_restore_manifest_write`
in `session-registry.bash`). The manifest:

- starts with a header line and the boot id;
- then holds one `name`/`prefix`/`dir` triple for each session it started or found already
  running;
- is written atomically, with umask 077;
- is also written, empty, when there is no registry;
- is not written on a dry run, or when the live-session listing fails.

`verify-restore` refuses to run when:

- there is no manifest;
- the manifest is malformed;
- the manifest comes from an earlier boot.

For each session it prints `<name> <STATE>` on stdout:

- `OK`
  - For `cc`: the pane is live and its last line is not a known prompt.
  - For `ccy`: the same, and the session's container is up.
- `STARTING`: a `ccy` pane with no container up yet. `--wait` polls until this resolves.
- `WAITING-AT-PROMPT <name>`: the last non-blank line of the screen starts with a known
  prompt text.
- `DEAD session-not-running`, `DEAD launcher-exited` (the trampoline's "Press Enter to
  close" line), or `DEAD unknown-launcher-<prefix>`.

Exit codes:

- 0 when every session is `OK`, or when the manifest has no sessions;
- 1 when any session is not `OK`, or when a probe fails;
- 64 for a usage error.

The judgement is made by a pure function, `ccy_restore_verdict`. `--wait N` polls every
`CCY_SESSIONS_POLL_SECONDS` (default 5) until every session is `OK` or the time runs out.

## Tests

- `scripts/test-ccy-session-registry.bash` covers:
  - the restore marker on started panes;
  - the manifest's location, contents and record order;
  - a dry run leaving the manifest untouched;
  - the empty manifest when there is no registry, and no manifest when the listing fails;
  - strict-read refusals;
  - a directory containing `=` round-tripping;
  - every verdict branch, built from the shared constants;
  - prompt names being unique and no prompt text being empty.
- `scripts/test-ccy-sessions-reboot.bash` covers `verify-restore` end to end, using a fake
  tmux (`list-panes`, `capture-pane` screens), a fake `ps` and a fake `podman`:
  - no manifest;
  - a manifest from an earlier boot;
  - an empty manifest;
  - a mixed set of sessions (OK, quick-launch, token-select, launcher-exited, not running);
  - all sessions OK;
  - STARTING with `--wait 0`;
  - a bad `--wait` value (exit 64);
  - an unreadable screen.
- Mutation check: disabling the prompt match inside the verdict fails 4 registry
  assertions and 2 reboot assertions. The mutation was reverted.

## Limits

- `cc` reports `OK` once its pane is live and not at a launcher prompt. The verifier cannot
  see whether `claude` itself is healthy past start-up.
- A `ccy` session is mapped to its container through the process tree
  (`ccy_session_containers`), then checked against `podman ps --filter label=ccy=true`.
- Run the check with `--wait`. Straight after boot, a healthy `ccy` session reads
  `STARTING` until its container is up.
- The verifier judges only the last non-blank screen line. A prompt that has scrolled off
  because output followed it is not a prompt the session is waiting at.
