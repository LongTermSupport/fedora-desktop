## Deviations from the dispatch, with reasons

1. **`commit.gpgsign true` / `tag.gpgsign true` are NOT set.** ccy copies the host
   `~/.gitconfig` into every container (`claude-yolo:1938-1940`, `entrypoint.sh:41-42`),
   and `cc` agents run on the host. A signing default would make every agent commit either
   fail (no key in the container) or be signed with the owner's key (host `cc`). The
   second defeats D3 outright. Instead:
   - the settings are written to `~/.config/git/config`, which ccy does not copy;
   - signing is explicit (`git sign-deploy`, an empty signed commit, or `git commit -S`);
   - the play asserts the key has a passphrase, so an agent without a terminal cannot
     sign.
2. **Removal on off removes the clone and the state directory too.** "Off is a real off"
   was read literally. Re-enabling re-clones.

## Contract gaps found (need the coordinator)

1. **D5's claim does not fully hold.** The become password file is unreadable to the
   user, but the plays run *as the user*, through the user's pipx `ansible-playbook` and
   `~/.ansible/collections`. The controller also holds the password in memory as the
   user. Any process running as that user, including a host `cc` agent, can alter that
   code, or read the controller's memory (same uid), and capture the password. The file
   permission alone does not keep the password from the user account.

   Options:

   - a root-owned Ansible install (system `ansible-core`) plus a root-owned collections
     path for the cycle. This narrows the code path, but not the same-uid memory read.
   - running the controller as root, which needs the plays to stop assuming they start as
     the user.
   - accepting that the user account is trusted, and making D5 about agents in
     containers only. Those do run as the user uid under rootless podman, but they see
     only their mounts.

   This needs an owner decision.

2. **Fact cache.** `ansible.cfg` caches facts in `./untracked/facts/`, root-owned in the
   clone. The orchestrator must override it; see `DESIGN-cycle.md`.

3. **host_vars are untracked**, so a fresh clone has none. The play copies them in
   (root-owned). An edit to host_vars reaches the cycle only when the play is re-run. The
   docs say so.

4. **Vault password** is untracked too. There is a root-only copy, passed on a
   descriptor; see `DESIGN-cycle.md`.

5. **git ownership.** The play adds the clone to the user's `safe.directory`. Otherwise
   the ledger callback's git calls fail in a root-owned repository.

6. **The verify unit carries no condition**, because the contract names no "owed" file.
   So `verify` must exit 0 when nothing is owed.

## Verify ordering

`After=`/`Wants=user@<uid>.service`. A system unit cannot order against a user unit.
`user@.service` reports ready once the user manager has finished starting
`default.target`, where `ccy-sessions-restore.service` (a oneshot) runs. That was
inferred from systemd's user-manager startup, not measured; it is a HOST check. The
panes the restore starts can still be launching, which `verify-restore --wait` covers.
