# Task 4.7 — D5 hardening in play-self-update.yml

These notes cover what the enabled path installs, what the disabled path removes, and
what is still open.

## What the enabled path adds

All of it goes in `playbooks/imports/optional/common/play-self-update.yml`, between the
deploy clone and the units.

1. **System ansible-core.** `dnf` installs `ansible-core`, `python3-jmespath` and
   `python3-passlib`. The two libraries match what `run.bash` injects into the pipx
   install (`pipx inject ansible jmespath|passlib`), because plays use `json_query`
   (`play-toolbox-install.yml`) and `password_hash` (`play-ftp-camera.yml`). The play
   then asserts that `/usr/bin/ansible-playbook`, resolved through any symlink, is
   root-owned and not group- or world-writable. It also asserts the version is at least
   2.20, the floor that `play-AA-preflight-sanity.yml` sets.
2. **The pipx pin.** The repo does not pin a pipx ansible version: `run.bash:2151`
   installs whatever `pipx install --include-deps ansible` resolves.
3. **Collections.** They go in `/usr/local/share/fedora-desktop/ansible-collections`
   (root:root, 0755 directories), installed by the system `ansible-galaxy collection install --force -r <deploy clone>/requirements.yml -p <dir>`. The install runs from a
   directory outside the clone, so no `ansible.cfg` shapes it, with
   `ANSIBLE_COLLECTIONS_PATH` set to the target directory. It reinstalls only when the
   sha256 of the clone's `requirements.yml` differs from the stamp in
   `…/ansible-collections.requirements-sha256`. Afterwards the play finds anything under
   the directory that is not root-owned, or that is group- or world-writable, and
   asserts there is nothing.
   - Collections installed: `community.general >=13.0.0,<14.0.0` and
     `ansible.posix >=2.0.0,<3.0.0`, as `requirements.yml` declares them.
4. **Config.** `ANSIBLE_COLLECTIONS_DIR=<that dir>` is written into
   `self-update.conf.j2`.
5. **ptrace.** `ansible.posix.sysctl` writes `/etc/sysctl.d/60-fedora-desktop-ptrace.conf`
   with `kernel.yama.ptrace_scope = 1`, sets the value live and reloads that file. The
   play then reads `/proc/sys/kernel/yama/ptrace_scope` and asserts it is `1`.

## What the disabled path removes

- The collections directory, the stamp and the ptrace drop-in.
- The live ptrace value is **not** reset. Lowering a hardening setting on a running
  machine is the owner's call, and the value returns to the distribution default at the
  next boot anyway. This is commented in the play and stated in `docs/playbooks.md`.
- The `ansible-core` package stays installed: the play cannot know whether it predates
  the cycle.

## Docs

`docs/playbooks.md` (the play-self-update entry) covers the root-owned ansible, the
collections path, and the ptrace note: `gdb -p` and `strace -p` of a process you did not
start stop working as your user, and running the tool as the parent, or with sudo,
still works.

## Gaps, for the coordinator

- **Roles.** `requirements.yml` also declares the role `lts.vault-scripts`, which
  `play-basic-configs.yml` uses. `ansible.cfg` points `roles_path` at `./roles/vendor`,
  relative to the clone. Nothing installs roles into the root-owned deploy clone, so an
  allowlisted play that needs a vendored role would fail. `play-claude-yolo.yml`, the
  only allowlisted play, uses no vendored role. If a role-using play is ever
  allowlisted, it needs either a root-owned roles directory plus an `ANSIBLE_ROLES_PATH`
  contract key, or galaxy installing roles into the clone as root. This task added
  neither.
- **The Fedora 44 ansible-core version is unverified.** This container is Debian, so
  `dnf info ansible-core` could not be run. The play asserts the 2.20 floor at deploy
  time and fails loudly if Fedora's package is older.
