# Plan 00137 Task 1.3: changed paths → affected plays

Written by the Task 1.3 worker. The plan and journal are left to the coordinator.

## What was built

- `helpers/self_update/affected_plays.py` is stdlib-only, with no YAML parser. Its public
  API is `play_inputs`, `affects`, `candidate_plays`, `load_allowlist`, `decide`,
  `changed_between` and `main`.
- `helpers/self_update/unattended-plays.json` is the D2 allowlist: a flat JSON list,
  seeded with `playbooks/imports/play-claude-yolo.yml`.
- `tests/helpers/self_update/test_affected_plays.py` has 40 tests: fixture repos, a git
  round trip, and the real checkout.

### Why the allowlist lives there

It sits next to the only code that reads it, the precedent being
`helpers/play_ledger/retired-plays.json`. `vars/` is Ansible YAML, which a stdlib helper
cannot parse. The allowlist is also refused rather than read around: an entry must be a
normalised path under `playbooks/imports/`, the file must exist, and a name may not
appear twice. A bad entry would otherwise either run a play nobody allowed or drop one
that was.

## CLI contract

```
python3 -m helpers.self_update.affected_plays --old SHA --new SHA
python3 -m helpers.self_update.affected_plays --changed PATH [PATH ...]
```

- **stdout** carries only these lines:
  - `RUN <play>` for each affected play on the allowlist;
  - `SKIP-NOT-ALLOWED <play>` for each affected play not on it;
  - `UNRESOLVED <play> <file>:<line>: <value>`.
- **Exit status**:
  - 0: answered.
  - 1: answered, but an allowlisted play has a reference the helper cannot follow, so a
    change could be missed. The orchestrator should refuse and alert.
  - 2: no answer (bad allowlist, git failed, or a ref starting with `-`).
- `--old`/`--new` run `git diff --name-only --no-renames -z OLD NEW --`, so a moved file
  names both of its paths.

## Idioms recognised

Only non-comment lines are read; a line starting with `#` is skipped.

1. **`{{ root_dir }}/<path>`** anywhere on a line. `{{ lookup('ansible.builtin.config', 'CONFIG_FILE') | dirname }}/…` counts the same way, since it is `root_dir`'s own
   definition and appears literally in `play-gnome-shell-extensions.yml`'s `vars_files`.
   The path becomes:

   - an **exact** input;
   - a **directory** input, when the path ends in `/` or is a directory in the checkout.
     `extension_src: …/extensions/<uuid>` is covered this way;
   - a **literal-prefix** input, when a template follows the path, as in
     `…/bin/{{ item }}`. This is conservative, because a regex cannot evaluate the loop
     that fills the template in. An empty prefix, or one that leaves the checkout, is
     UNRESOLVED.

2. **Transitive YAML.** Any exact input ending in `.yml` or `.yaml` that exists is walked
   with the same rules: task files from `include_tasks`/`import_tasks`, vars files, and
   imported plays. Variable resolution uses the including file's text as context too.

3. **`import_playbook: <relative>`**, resolved against the importing file's directory.

4. **`helpers.<pkg>`**, when `helpers/<pkg>/` exists. This is `python3 -m helpers.<pkg>.x`
   in an argv. The input is the whole package, followed transitively through
   `from|import helpers.<other>` and `from helpers import a, b` in its `.py` files. A
   rooted path under `helpers/<pkg>/` pulls the package in the same way. Tokens that are
   not packages are ignored: `helpers.yml`, `helpers.bash` and `helpers.github` all
   appear in the repo.

5. **Classifying `src:`, `file:`, `include_tasks`, `import_tasks`, `include_vars`,
   `import_playbook` and `vars_files` items.** These are **not** unresolved:

   - rooted values;
   - absolute host paths, including `/home/{{ user_login }}/…`;
   - URLs;
   - `{{ item… }}`, because the loop's entries are captured by rule 1;
   - `{{ var… }}`, where the file or its includer defines `var` as rooted, a host path or
     a URL;
   - `{{ registered… }}`, a registered result.

   Everything else is **UNRESOLVED**. A relative literal is looked up at `<dir>/`,
   `<dir>/files/` and `<dir>/templates/`, and is UNRESOLVED if found in none of them.

The candidate plays are every `*.yml` under `playbooks/imports/`, nested `optional/`
plays included. `playbook-main.yml`, which only aggregates them, and `playbooks/dev/` are
excluded.

## Over-approximation to know about

Prefix inputs are conservative, so some plays read as affected by changes they do not
deploy. The cost is only extra `SKIP-NOT-ALLOWED` lines, never a wrong `RUN`, unless such
a play is allowlisted.

- `play-basic-configs.yml` has `{{ root_dir }}/files{{ … }}`, which makes every file
  under `files/` one of its inputs. So a ccy lib change also prints
  `SKIP-NOT-ALLOWED playbooks/imports/play-basic-configs.yml`.
- `files/home/.local/bin/{{ item }}` in several plays does the same for `ccy-sessions`:
  `play-collaboration`, `play-container-watch`, `play-fedora-desktop-panel`,
  `play-network-tools` and `play-gnome-shell-extensions`.

If one of those plays is ever allowlisted, the fix is to resolve the `loop:` entries next
to the templated `src:`. That was not built here, because nothing needs it yet.

## Not covered, by design

- `ansible.cfg`, `callback_plugins/` and `run.bash` are how plays run, not what they
  deploy, so they map to no play.
- `environment/**/host_vars` is host configuration; D4's deploy clone does not track it.
- Helpers run from the checkout at runtime (host-health, the ledger) need no redeploy. A
  play is affected only if it names the package.
