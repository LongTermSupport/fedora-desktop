## 17:01 · finding · —

Task 1.4 regression on the host: play-agent-bus.yml failed with exit 78 at the LXC member kit step for an EL9 LXC member: "pingbus needs Python 3.11 or later; this container has 3.9.21". Members still run the old kit (the step failed before it replaced anything), but the play was blocked for every team change.

Cause: the kit carries the host's archive, whose first line is now `#!/usr/bin/python3`. In an EL9 member that is the 3.9 system interpreter. python3 on PATH there is a 3.13 in /usr/local/bin, which `env python3` used to find, and a packaged /usr/bin/python3.13 also exists. The review's F4 pointed here: its fix moved the guest scripts and the 3.11 gate to /usr/bin/python3, so the gate judged the pinned interpreter and refused.

Decision: option (a). The member step finds the member's newest python3.N of at least MIN_PYTHON in /usr/local/bin and /usr/bin, once per container and before any change. It fails naming what it found and what to install when there is none. The kit sync runs under that interpreter, so its gate checks the real version and not only the name. The sync rewrites the first line of the member's copy of pingbus to name it (zipimport finds entries from the end, so a longer first line is fine; a test runs the real archive after the rewrite). Every other guest script runs under it too. Option (b), a member copy with `#!/usr/bin/env python3`, was rejected because PATH would pick the interpreter again: a shim's cost, and nothing checked at install.

Host build keeps the /usr/bin/python3 pin. The ccy image keeps it too: its Debian /usr/bin/python3 is 3.11.2. The Dockerfile now fails the build below 3.11, and test_bundle holds that gate to MIN_PYTHON.

Red first: with only the fake EL9 root in place, test_members failed at "the member kit (README.lxc step 1): failed (exit 1): this is Python 3.9.21", the host's failure. Green after the fix.
