## Findings

### F1 (fix first): the golden `inner-environment` depends on what /bin/sh is

S9 runs the inner as `/bin/sh -c`. The record was made where /bin/sh is dash (CCY, Debian).
On the Fedora host /bin/sh is bash, which exports `SHLVL=1` and `_=/usr/bin/env` to `env`.
I reproduced both in this container (`bash -c 'env|sort'` and `dash -c 'env|sort'`). So
`capture.py check`, and the planned Go golden test, fail on the host for this scenario, with
no change in pingbus. The oracle has to give the same result on every machine it runs on.
Fix: print a fixed list of names (for example
`for v in HOME LANG PATH PINGBUS_SESSIONS_DIR PINGBUS_STATUS_LINE_INNER PWD; do ...`), or
filter out `SHLVL` and `_`. Then recapture. Also check the other `printf` scenarios with bash's
builtin printf. They looked compatible to me, but I did not run them.

### F2: capture.py's repo root breaks when the plan is completed

`REPO = parents[4]` is right only at `CLAUDE/Plan/00213-*/golden-capture/`. After the move to
`Completed/`, parents[4] is `CLAUDE/`. Meanwhile `src-go/CLAUDE.md` now points at this script
as the permanent recorder of permanent testdata. That is plan scaffolding doing a permanent
job (the transient-vs-persistent test in CLAUDE/Plan/CLAUDE.md). It also runs against the
"Tooling is Go" rule, which has no exemption for a standalone Python CLI in a plan folder. The
bash-limits exemption covers plan-folder bash scripts, not this.
Recommendation: acceptable as plan scaffolding while the Python is still the reference. Fix it
now with a `.git`-bounded marker walk (R1 in PlanScriptStandards). Before the plan completes,
either freeze the testdata and drop the recorder (once the Go is the implementation and
departures are pinned in deviations.json), or fold the re-recording into the Go golden test
behind an `-update`-style flag. Update the src-go/CLAUDE.md paragraph to match.

### F3 (fix first): test_the_archive_runs_with_no_python3_on_path is not hermetic

The test copies `os.environ` minus PYTHON\*/PINGBUS\*, so `HOME` and `CLAUDE_CONFIG_DIR` are
inherited, and `statusline.py:159` reads `$HOME/.claude/settings.json`. If whoever runs the
test has a user `statusLine` (the owner's host likely does), the inner runs with a PATH that
holds only the shim, and stdout is no longer `"\n"`. It passes here only because the
container's user settings have no statusLine. Fix: set `HOME` to the tmp dir and drop
`CLAUDE_*`.

### F4: Python version gate on LXC members probes the wrong interpreter

`members.py` KIT_SYNC_PY runs `python3 -I -c` (from PATH) and refuses anything below 3.11. The
zipapp now runs `/usr/bin/python3`, so the gate no longer checks the interpreter that will
actually run pingbus. A container whose PATH puts a newer python3 first (pyenv, /usr/local)
passes the gate and then runs an older /usr/bin/python3, or none at all. Step 6
(`pingbus config check` goes through `cli.main` and then `check_python`) still fails loudly,
so this is not a silent break. But the `status-line` fast path (bundle FAST_COMMANDS goes
straight to `statusline.main`) has no `check_python` at all; that was already true before
this branch. Fix: run the gate as `/usr/bin/python3`, and say so in README.lxc step 2.
Environments checked:

- Host: Fedora 44 /usr/bin/python3, fine.
- CCY image: node:lts-slim (Debian) apt `python3`, at least 3.11, fine.
- Nothing else in the repo runs the archive as `python3 pingbus`. test-agent-bus-install runs
  `python3 -I agent-bus.pyz` explicitly, which still works.
- The hooks and the seat guard `exec pingbus`, as the plan says.

### F5: 25 s versus the supervisor's 30 s window and 10 s margin

25 s is correct against `_DEFAULT_FRESHNESS_SECONDS = 30` (claude-supervise.py:1129), but it
leaves 5 s of headroom for render latency on a loaded host. The other cost: the 10 s
foreground-ambiguity margin (:1140) is sized at "roughly one refresh interval". At 25 s,
after an Agent-View thread switch, the ambiguity can last up to about 25 s, not a tick or two.
That only defers a compaction, so it is safe, but the drafted hooks-daemon request should
name the margin's actual effect. It already mentions the margin.

### F6: PLAN Task 2.1 has drifted from the SPEC

Task 2.1 says the cache is invalidated by "the mtimes of" desired/applied, the session
record, team.json and down marks. SPEC S33 is correct and wider: it uses lstat
dev/ino/size/mtime_ns/ctime_ns/mode/uid and also covers member.json, token and links.
Reword Task 2.1 to defer to S33. As written, it describes a cache that would fail the
oracle's `cache-token-mode-change` case (a chmod changes ctime, not mtime).

### F7: cache-down-ages-out may flake under load

The mark is placed at 294 s old, and the step sleeps 7 s. If step 1's render finishes more
than 6 s after the world is built, it records no `(down)` and differs from the record. Use a
wider gap (for example age 285 and sleep 16), or set the age when the step runs.

### F8 (minor): the agent-bus zipapp's change is not described

`bundle.SHEBANG` is shared, so `agent-bus.pyz` also moves to /usr/bin/python3. The changelog
and the Task 1.4 text mention only pingbus.

## S24 (must Go stderr match byte for byte?)

Recommendation: no byte-for-byte match for the role-diagnostic wording. Pin it by shape:

- exactly one line on stderr, only when a role failed
- the prefix `pingbus status-line: the role cannot be read (`
- the team names in order, separated by `; `
- stdout and exit stay byte-exact, and an empty stderr stays empty

Matching byte for byte would make the Go copy Python exception names such as `ValueError` and
`JSONDecodeError` (S37), which is leaked implementation detail, not a contract. Use a
structural stderr comparison in the Go golden test rather than `--ignore-stderr`, which would
also stop checking that stderr stays empty and the inner's stderr pass-through
(`inner-stderr-passes-through`). Pin the departure as a numbered S37 entry in deviations.json.
