## 12:10 · decision · — — freshness policy inverted: revision primary, TTL demoted to backstop

Team-lead review caught a real defect in the first draft. §4.3 had `refresh`
requiring the updates revision to have advanced **and** TTL-U to have expired.
That is wrong in both directions: it leaves a stale base in service inside an
unexpired window after a large update lands, and it schedules pointless
`dnf upgrade` cycles when nothing moved. Now: **the revision is the trigger,
TTL-U applies only when the revision cannot be fetched.** Same inversion for
TTL-R against artefact identity.

Adopted with one addition of my own, because pure revision-primary would
otherwise mean a near-daily base-sized write (the updates repo regenerates
frequently). A refresh is now **two steps with a gate between them**: boot and
`dnf -y upgrade`, then re-flatten **only if the transaction actually changed
packages**. A revision that advanced for packages this base does not have costs
a boot and a transaction check, not a rebuild.

T1.2 gains three tests that must each be shown to go red when reverted —
notably "an advanced revision yields `refresh` even inside an unexpired TTL-U",
because a test exercising only the expired-TTL case would have passed against
the *wrong* policy. That is `AgentNotes.md` row 14 in advance rather than in
hindsight.

Also folded in: the answering **mirror is recorded** alongside the revision, and
a revision that goes **backwards** is mirror lag — retry against canonical
`dl.fedoraproject.org`, and a persistent regression resolves to `unknown` and
blocks, never to `current`.

## 12:30 · finding · — — B1 confirmed verbatim: the bridge would have died silently, not throttled

Fetched `systemd.path(5)` upstream and the review is right word for word:

```
"Unlike other service failures, the error condition that the start rate limit is
 hit is propagated from the service unit to the path unit and causes the path
 unit to fail as well, thus ending the loop."

TriggerLimitIntervalSec= defaults to 2s, TriggerLimitBurst= to 200:
"If the limit is hit, the unit is placed into a failure mode, and will not watch
 the paths anymore until restarted."
```

So `StartLimitIntervalSec=60` / `StartLimitBurst=50` did not rate-limit a noisy
agent — it would have **killed the path unit**, leaving no oneshot to write the
"rejected, rate limited" response §10 promised, and no way for the sandbox to
distinguish that from "the bridge was never installed". The remedy would have
been a human typing `systemctl --user reset-failed`.

Worth naming the provenance: **this came straight from the published
host-action-bridge pattern and I copied it without checking what systemd does
with it.** A design that inherits a control from a proven article still has to
verify the control does what its name suggests.

Fixed in §6.4: the real limit is watcher-side (counted from the off-mount audit
log, writes a `rejected` response, exits 0); systemd limits are set high as a
last-resort loop breaker only. New §6.5 adds a **separate, non-path-triggered
timer** writing `diagnostics/bridge-heartbeat.json`, so a wedged path unit is
visible with its remedy rather than silent. T4.9 wedges the unit on purpose and
asserts the reader says "bridge wedged", not "timeout" and not "fail".

## 12:30 · finding · — — B2/B3: the spool is sandbox-controlled and the host wrote into it naively

The bridge assumed a mailbox. It is a directory tree the sandbox can restructure.
`rm -rf responses && ln -s ~/.ssh responses` and the host's `mv -f` lands the
file inside the link target **as the host user** — `mv -f` protects the final
component but nothing about a symlinked parent, and a transcript written with
`>` follows and truncates. Ownership checks cannot help: `claude-yolo:1946`
binds with a plain `-v "$PWD:/workspace"` under rootless podman, so container
root already maps to the host uid — the mapping that makes the bridge convenient
is the one that removes ownership as a control.

New §6.3 states the defence per directory: pinned spool-root dirfd,
`openat`/`renameat`, `O_NOFOLLOW|O_EXCL`, `realpath` containment, and a
**refusal** (not a quarantine) when a spool directory is a symlink — quarantine
implies recoverable malformed input; this is an attempt on the host account.

B3 folded in: the body is read **once** into memory, every check and the argv
build use that buffer, the file is never re-opened, and the filename verb must
equal the body verb. All of this becomes `helpers/vmtest/spool.py` (TDD'd,
stdlib-only) per `playbooks/CLAUDE.md` — which also removes the `jq` dependency

## 12:50 · decision · — — TriggerLimitBurst=0, and drain everything per activation

My round-2 fix set the systemd limits "high". Not sufficient: the trigger limit is enforced

## 21:05 · decision · T3.2 — the recipe digest is the build recipe, not the CLI

The first `vmtest run` was refused with `reinstall: recipe digest changed`. The
digest was sha256(vmtest CLI + guest-cleanup.bash), so every edit to the CLI —
including the parsing fix that made that refusal legible — invalidated every base.
The design's intent (§3.2: "a hash of the build script + kickstart + package list,
so a change to how the base is built invalidates it") is about how the base is
BUILT, and the CLI mostly is not that. Now: `recipe_digest = sha256("build-recipe-
version=N\n" + guest-cleanup.bash)`, with `BUILD_RECIPE_VERSION` a constant in
`vmtest` that must be bumped when the build procedure changes (disk size,
cloud-init options, the upgrade step, what is cleaned). Same trade as CCY's version
bump: a human-declared recipe version rather than a hash of incidental text. The
base was rebuilt once under the new formula (~6 minutes; guest revision still equal
to the probe's).

Also found by that run: the gate's verdict line was parsed with a grep that could
never match after the marker prefix, and under `pipefail` the miss became a silent
exit 1. `verdict_field` now strips the prefix and walks the tab-separated fields;
the probe-only read of the record goes through `freshness_gate --record-only`
instead of a placeholder hash that made the gate exit non-zero.

## 21:40 · finding · T3.2 — the first real run found a defect in run.bash's pinned-ref path

`server-fast-provision` came back `fail@provision` in under two minutes. The
transcript: preflight OK, clone over HTTPS, `checkout pinned at commit … (detached,

at `run.bash:2586` did not know about the ref, and a pinned commit leaves HEAD

commit would have failed there; the design's own §3.4 rule ("scenarios always pin a
