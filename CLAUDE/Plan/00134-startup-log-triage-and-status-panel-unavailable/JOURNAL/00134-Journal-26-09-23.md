## 19:10 · finding · T3.1 T3.2   — SELinux and DOCKER-USER facts from triage (after); fixes proposed, not chosen

**T3.1: the SELinux flood is CCY's designed path on a Permissive host.**

- `getenforce` reports **Permissive** on this host.
- 15 podman containers are running. Six are CCY sessions: this repo's own session and five others, `container-A`… `container-E`. The other nine form one project's compose stack, `project B`. No docker container is running.
- The AVC capture holds 142,802 records this boot. Triage (before), which started about 6.5 minutes earlier, counted 140,195, so denials are still accruing.
- Every one of the top-40 aggregates is `container_t` → `user_home_t` (`dir`/`file`, from `python`, `git`, `bash`, `rm`, `postgres` and `php`). Attributed by MCS pair:
  - the six live CCY sessions: about 120k (38.7k for this repo's session, 13.7k–17.7k for each of the others);
  - two MCS pairs that no running container carries: about 9.9k each. These are containers that exited earlier this boot. Their mix (`python` on `user_home_t` dirs) matches the CCY sessions;
  - `project B`'s stack: about 3.3k.
- Every CCY workspace bind is recorded as `rprivate,rbind` with **no `z`/`Z`**, and `security-opt=[]`, so there is no `label=disable`. The host label on every workspace root is `user_home_t`, and the config-import bind carries no `Z` either.
- **Cause, from the code.** `selinux_enforcing_verdict` (`files/var/local/claude-yolo/lib/common-pure.bash`) returns `off` for `Permissive`. `ccy_selinux_mode` then sets `CCY_MOUNT_RELABEL=""`, so on a permissive host the workspace is bound without `:z` by design. A `container_t` process touching `user_home_t` is a denial, which permissive mode allows and logs. So no relabel is skipped in some launch mode, and no host path reverts: every session takes the designed branch.
- **The hot inodes.** All of the 20 most-denied inodes belong to each session's checkout (about 4.5k each): the hooks daemon's `untracked/context-sidecar` and `untracked/thread-registry` directories, plus `.claude/hooks/status-line`. They are polled continuously. They carry `system_u:object_r:user_home_t:s0`, while the policy default and the checkout roots are `unconfined_u:…:user_home_t`. So a `system_u` container process created them inside a `user_home_t` parent, which permissive mode allowed. No path's type differs from policy, so nothing was restored or reverted.
- `project B`'s compose binds carry no relabel either. That stack is not this repo's.

Options, none of them chosen:

- **A. Relabel whenever SELinux is not Disabled.** `selinux_enforcing_verdict` gives `Permissive` the relabel verdict too, so workspaces carry `:z`. This stops the CCY part at its source, and it leaves the host already in the state an Enforcing switch needs (Plan 00118). Cost: a recursive relabel of every workspace at launch on a host where nothing is being blocked, which is exactly what the current `off` verdict avoids. Needs a CCY version bump.
- **B. Leave CCY alone and make the host Enforcing** (Plan 00118's scope). The existing `:z` branch then applies. Cost: `project B`'s binds need `:z` first, or that stack breaks.
- **C. Accept it.** Under Permissive these are log volume only. The criterion can then be explained but not bounded.

Recommendation: **A**. It goes at the source without changing the host's mode. The live CCY sessions alone account for 84% of this boot's records, and 98% with the two exited pairs.

**T3.2: DOCKER-USER is on the forward path, and the reconcile unit is not installed here.**

- Docker is 29.8.1 with `Firewall Backend: iptables+firewalld` (through iptables-nft 1.8.11), and there is no `/etc/docker/daemon.json`. This host is on Docker's iptables backend, **not** the nftables backend this task assumed.
- `FORWARD` jumps to `DOCKER-USER` first, before `DOCKER-FORWARD`. The nft counters on that jump read 1,767,758 packets and about 4.0 GB for IPv4, and 138 packets for IPv6. The chain is consulted, and it is empty.
- Docker owns no nftables table. Four base chains sit on the forward hook: firewalld's `filter_FORWARD`, `inet lxc forward`, `ip filter FORWARD` and `ip6 filter FORWARD`.
- `lxc-docker-user-iptables-reconcile.service` could not be found, in both triage runs. nat `POSTROUTING` holds only Docker's two MASQUERADE rules and none for `lxcbr0`. `lxcbr0` itself is up, and its NAT comes from lxc-net's own `inet lxc`/`ip lxc` tables. So the reconcile's rules are not live on this host at all. The play installs the unit only when `docker_daemon_check.stat.exists`. This run cannot say whether that gate was false or the play has not run since the step was added.
- firewalld logged 64 `COMMAND_FAILED` this boot, all in the same second at boot. Every one is Docker's own startup cleanup (`iptables -D/-F/-X` on `DOCKER*` chains that do not exist yet) passed through firewalld. There is also one `NAME_CONFLICT` for the existing `docker-forwarding` policy. The count is the same before and after the deploy, so it is per boot, not per operation.

Proposals, none of them chosen:

- The script's assumption holds on the iptables backend. The risk is a move to `firewall-backend: nftables`, where `DOCKER-USER` no longer exists. The script already fails when the chain is missing. A cheaper and clearer guard: `play-lxc-install-config.yml` asserts that `docker info` reports the iptables backend before installing the reconcile, so a backend change stops the play with the reason. Plan 00127 is unaffected.
- The owner re-runs `play-lxc-install-config.yml` once. That shows whether the unit appears, which settles which of the two causes above is true.
- The firewalld noise: leave it. It is Docker's per-boot cleanup and harmless. Silencing it means filtering firewalld's log, and that would hide real failures too. Add it to the research doc's not-actionable table.
