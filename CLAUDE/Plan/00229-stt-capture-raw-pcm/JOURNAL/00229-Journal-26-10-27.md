## 08:50 · finding · —   — Root cause: pw-record 1.6.10 writes an AU container to stdout

Root cause of "so so so" dictation, established on the host (read-only triage, then owner-approved test recordings, each deleted after measuring).

- Symptom: two dictations on the same morning pasted `speech-to-text:"So so so so so so"` and `"So so so so you so so so so so so"`. Per-segment journal: every VAD segment (3-9 s) decoded as "so", one as "you".
- Change: an unattended package upgrade (play-AB-dnf-upgrade.yml, "Upgrade all packages to latest available") moved pipewire 1.6.9 -> 1.6.10 the night before. The first `pw-record` started after it was the first failing dictation.
- `pw-record --rate 16000 --channels 1 --format s16 -` now writes a Sun AU container to stdout. First bytes: `2e 73 6e 64` (".snd"), header size 0x18, encoding 3 (16-bit linear PCM, big-endian), rate 0x3e80 (16000), 1 channel. Also seen on a capture from a silent output monitor, with no microphone involved. `pw-record --help` offers `-a, --raw`.
- `wsi-stream-server` reads stdout as raw native (little-endian) int16, so every sample is byte-swapped. Read that way, the stream measured peak 0 dBFS and rms -13 dBFS: loud noise that follows the speech envelope. The VAD still cuts at the pauses, and Whisper hallucinates "so"/"you" on noise. Nothing in the server checks the stream's format, so the wrong text was pasted as a success.
- Ruled out, with evidence:
  - The microphone (3 s clips taken straight from the source node: speech peak -11 dBFS, rms -33 dBFS, quiet floor -53 dBFS, L/R correlation +0.69).
  - Routing (an untargeted `pw-record` links to the built-in microphone).
  - Every level and mute (all at 100% / 0 dB, unmuted).
  - The model on CPU and on GPU (synthetic speech transcribed exactly, also at -33 dBFS).
  - The WirePlumber/PipeWire config (unchanged since weeks of good dictations).
  - A mixed-version PipeWire daemon (restarting it did not help).
- Also seen: the server leaves its `pw-record` child defunct after each dictation.
