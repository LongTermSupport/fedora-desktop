## Three judgement calls that differ from the brief — please sanity-check

### 1. `host-health-collect.timer` is the SERVER delivery, not the desktop one

The brief asked for "`host-health-collect.timer` is enabled and has run". On a desktop
profile `play-host-health-login-report.yml` explicitly **removes** that timer (task "Remove
The Server Delivery") and instead deploys and enables `host-health.service` wanted by
`graphical-session.target`. Asserting the timer on the owner's desktop would fail every
time, for a reason that is not a defect.

So checks 11 and 12 assert the desktop unit, and check 0 exits **2** on a server profile
with a message pointing at the VM scenario instead. This also removed a dead server branch
from the script: the profile is asserted once, not branched on nineteen times.

### 2. "`--check` adds nothing" is exercised with `--list-tasks`

`plugin_support._NO_OP_FLAGS` is `("check", "listtasks", "listhosts", "listtags", "syntax")`
— one guard, one flag set. `--list-tasks` still drives the play loop, so the callback really
is asked and really does decline, and it applies nothing. `--check` itself cannot be used
(see the deploy.bash refusal above), and `--syntax-check` would have been vacuous because it
never reaches the play loop. The check's own comment says exactly this.

### 3. Host findings are REPORTED, not failed

A genuinely drifted pin, a stale play or a failed unit is this plan **working** — the checks
ran, compared, and said so. A gate that rejected on them could never accept and the plan
could never close. So those are printed under `FINDINGS ABOUT THIS HOST (reported, not rejected)` and carried into the report file. What rejects is a check that could not run,
compared nothing, or gave no answer — the silence this plan exists to abolish.

A `CLEARED` ledger marker is a note for the same reason: it is a recorded, handled state
that never goes away, so rejecting on it would reject for ever. A `BROKEN` sentinel does
reject.

## Deviations from the skeleton, both annotated in the file

- **`plan_finish` is not the closer of acceptance.bash.** It exits 0 or 1, and this gate has
  a third answer; collapsing "could not establish" into "rejected" is the same conflation
  the plan exists to abolish. R10 still holds — `plan_list_reports` is called explicitly and
  the EXIT trap still drains the run log.
- **`read_field` assigns into a named variable instead of printing a value.** `x="$(f)"` runs
  `f` in a subshell, where `abort`'s `exit 2` would end only that subshell and the run would
  carry on with a half-rendered verdict — the "control that silently becomes a no-op"
  failure PlanScriptStandards exists to prevent. This was a real defect in the first draft
  and was fixed.
