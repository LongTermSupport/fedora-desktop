## 18:41 · decision · T4.6 — the panel icon stayed stuck at its login answer; refreshed after play runs and hourly

**Defect (owner report, verified):** the panel re-reads `host-status.json` every 300s, but
that document was written only by `host-health.service`, a oneshot wanted by
`graphical-session.target`. Nothing else triggered it, so fixing a finding (re-running a
stale play) never changed the icon until the next login. DESIGN-panel §4 had decided "a
timer is deliberately not added"; that decision was wrong and is superseded there.

**Change:**

- `helpers/play_ledger/health_refresh.py` (test first: `test_health_refresh.py`) restarts
  `host-health-collect.service` with `--no-block`. `callback_plugins/play_ledger.py` calls it
  from `v2_playbook_on_stats`, after the ledger records are written and only if that write
  succeeded.
- `host-health-collect.service` and `.timer` are now deployed on both profiles by
  `play-host-health-login-report.yml`. The timer template branches on `is_server`: daily
  unchanged on a server, `OnStartupSec=15min` + `OnUnitActiveSec=1h` on a desktop. The task
  that removed the collector from desktops is deleted.

**Decision, a failed refresh does not fail the play.** Ansible discards exceptions raised in
a callback, so raising would be silence dressed as a failure. The producer is reporting-only
and a missed trigger costs bounded staleness, not a wrong answer. Fail-fast is met by making
it loud: `request` returns a `HEALTH-REFRESH-FAILED` line that the plugin prints to stderr,
never an exception and never the ledger's BROKEN sentinel (the ledger is fine). A host with
no `host-health-collect.service` is skipped silently, because the report is an optional play.

**Alternatives rejected:** a systemd path unit on `runs.jsonl` fires on the first append of a
burst, before the last record lands, so the collector could read a partial ledger. `start`
instead of `restart` leaves a timer-started run in flight on the old ledger.

**Checked, not assumed, that no section is login-only:** post-boot health judges DKMS
against the running kernel and lists the units failed now; `is_boot_stale` only improves with
a fresher document; self-update reads `boot_id` and uptime at call time. The one hazard is
DKMS still building just after boot, hence the 15 minute start delay. The handoff file is a
fixed path and is overwritten, so periodic runs do not accumulate files. The login unit is
still the only one that notifies, so the timer adds no notification noise.

armed and that re-running a stale play moves `generated_at` and clears the icon.
