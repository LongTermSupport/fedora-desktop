## 12:40 · finding · T3.3 T4.2 — these were not blocked, and the gap was one key

Both of these were carried as open on a decision, so neither had been looked at. Reading
them together showed the reason the decision could not be taken: **the panel has no way
to know a handoff file exists.**

`login_report.main` writes it, prints `handoff.offer(path)` to stdout, and stops. The
panel's only data source is `host-status.json`, and `status_document.build` never carried
the path. So the question "what should a click do" had no answerable form — there was
nothing to click *with*. That is a producer gap, not a UX decision, and it is why the two
tasks stalled beside each other rather than one after the other.

## 12:55 · decision · T3.3 T4.2 — it copies, and it is not per-finding

DESIGN-panel.md §9 offered two options for what a click does (copy the command, as
`container-watch` does, or open a terminal running it) and framed it as per-finding rows
becoming reactive. Both halves are now answered in §9a, and the first answer is **no**.

**Not per-finding.** There is ONE handoff file and `handoff.write` takes the whole
flattened findings list, so it describes every finding. A clickable row per finding would
hand out the same command N times while implying each row had its own — a claim about
granularity the data does not support. The rows stay `reactive: false`, which is now a
decision rather than the absence of one, and the offer is a single row at the bottom of
the section.

**It copies.** Three reasons, and the first would simply break a launch: `claude` reads
the repository it starts in, and this diagnosis is about playbooks. The panel does not
know where the checkout is, and the document deliberately does not carry it — a host
state file naming a checkout path goes stale on a re-clone. A launch would open Claude
Code in the compositor's working directory, where it cannot see the thing it is being
asked about. Second, `container-watch` already copies its inspect hint and notifies, on
this same surface. Third, §8: the panel offers, a human decides — and §6's
terminal-launching mechanism belongs to Task 4.3, which has to choose it against ledger
evidence this task does not have.

## 13:10 · action · T3.3 T4.2 — the ordering rule, and the seam that makes it testable

`status_document.build` gains a `handoff` key: always present, `""` when there is none.
Always present because a key that appears only when a handoff was written makes "no
handoff" and "a document from before handoffs existed" the same observation — this plan's
own defect, one layer down in the file format.

**The handoff is written BEFORE the document that names it.** A path recorded first is a
path that may have no file behind it, which on this surface is a button that fails in the
user's hands. `main` had them the other way round, so the fix was not just an extra
argument.

That ordering had nowhere to be tested — it lived inline in `main`, which runs four real
probes. Extracted to `login_report.record_host_state`, following the rule `publish`'s own
docstring already states: *"A named function because this is the seam between two
separately tested modules, which is where this repo's defects live. Inline in `main` it
would have no tests."*

**Falsified.** Computing the path instead of taking the write's result:

```
FAIL: test_a_handoff_that_could_not_be_written_is_NOT_named
Ran 52 tests — FAILED (failures=1)
```

The assertion that matters OPENS the path the document names rather than comparing it to
an expected string — a path-equality check would pass without ever establishing the file
is there, which is the whole property.

## 14:05 · blocker · T5.4a — an owner's call, not code that is merely unwritten

Checked this rather than assuming it blocked, having already been wrong once today about
what needs the host. It is doable here — and it still should not be done here.

Nothing in the repo watches lock state. Two owners are viable and neither is determined:

- **The panel** gets `ActiveChanged` for no extra process at all, and Task 4.1's harness
  would make the wiring unit-testable to Phase 4's own standard. The cost is the contract
  its own header states — *"runs no check of its own, applies no fix, and launches no
  play"* — which spawning a recovery helper on unlock ends. "It is only a display refresh,
  not a play" is exactly the narrowing that erodes a boundary one reasonable exception at
  a time.
- **A user systemd unit** keeps the contract, and `files/home/.config/systemd/user/`
  already holds seven, so the path exists. But systemd has no unlock trigger — it would be
  a permanently resident D-Bus monitor bought to watch one signal the shell already
  dispatches.
- **A third small extension** keeps both, at the cost of a third custom extension with its
  own play, ESLint surface and Wayland logout. `play-container-watch.yml` is the
  precedent.

Recorded in DESIGN-panel.md §12 with a recommendation (C, then A) rather than decided.
This is different in kind from Tasks 3.3/4.2 earlier today: those had a determining
technical fact — `claude` reads the repository it starts in, and the panel does not know
the checkout — so the decision fell out of the evidence. This one is a policy choice
about what the panel is for, and the HOST item under Task 5.4 gates shipping it whichever
way it goes.
