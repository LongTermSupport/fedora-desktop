## 08:35 · finding · T3.1 — the enable task's `daemon_reload` can never see the symlink it exists for

The batch deploy PASSED and `acceptance.bash` then REJECTED with 9 of 21 assertions
failing. Diagnosed in full at
`untracked/agent-reports/260917-00109-acceptance-diagnosis.md`. Five of the nine are a
cascade, three are explained, and **one is a real code defect**.

`play-host-health-login-report.yml` enabled the unit like this:

```yaml
    - name: Enable The Login-Time Health Report
      ansible.builtin.systemd:
        name: "{{ unit_name }}"
        enabled: true
        daemon_reload: "{{ hh_unit.changed or hh_server_removed.changed }}"
```

The `ansible.builtin.systemd` module runs the reload **first** — it is the opening
statement of the module's main path, well before it touches the enabled state. So the
reload re-read a unit directory that did not yet contain the wants-symlink the same task
was about to create. The running user manager never learned about the unit.

Observed on the host, three minutes after a `changed` deploy:

```
systemctl --user is-enabled host-health.service            -> enabled
systemctl --user list-dependencies graphical-session.target -> does not name it
```

Those two disagree because they read different things: `is-enabled` reads the filesystem,
`list-dependencies` reads the live manager's in-memory graph. Both answers are correct
about their own source, and the pair is the signature of this defect.

**Lingering makes it worse, not better.** `play-systemd-user-tweaks.yml` enables linger, so
`user@UID.service` survives a logout — the stale graph does not clear by logging out and
back in.

Fixed: the reload is now its own task **after** the enable on the desktop branch. The
server branch gets two — one before, because that task also `state: started` and a start
must act on a manager that has already read the new files, and one after, for the
`timers.target.wants` symlink that the enable itself creates. Both orderings are deliberate
and commented; neither is expressible through the module's `daemon_reload:` parameter,
which always reloads first and so can only ever serve the second case.

Five `register:` declarations (`hh_unit`, `hh_server_removed`, `hh_collect_service`,
`hh_collect_timer`, `hh_desktop_removed`) existed solely to feed those `daemon_reload`
expressions. Grepped across every `*.yml` and `*.j2` in the repo: one occurrence each, the
declaration itself. Removed.

## 08:35 · finding · T3.1 — the other eight, and only one of them is ours

- **[1]–[5] status document missing** — pure cascade from [12]. `login_report.py` is the
  only writer and it runs from `host-health.service`, which has never started. Check [9]
  does invoke `login_report`, but with `--no-handoff`, which by its own documented contract
  writes neither the handoff file nor the status document — so re-running acceptance
  without a login reproduces these five identically. They clear when [11] and [12] do.
- **[6] the ledger BROKEN sentinel** — **independent, and already fixed in code.** The
  sentinel is dated 2026-09-15 and names the ansible-core 2.19 `ansible_pos` removal
  (issue #46); `plugin_support.py` reads the new `Origin` shape now. The proof it is stale:
  check [7] PASSED and the ledger holds 15 rows with `MALFORMED -`, one for every play this
  deploy ran. By design the sentinel never clears itself. Needs one human command in the
  checkout — `python3 -m helpers.play_ledger.check_freshness --clear-broken` — and no code
  change. It is also the sole cause of check [9]'s play-freshness finding.
- **[15] the panel extension is not loaded** — expected, and the play says so itself: on
  Wayland a logout is the only way to load new extension code. Checks [13] and [14] passed,
  so everything that can be true before a shell restart is true. Plan 00112 reported its 9
  extensions ACTIVE in the same batch because those were on disk before the session started;
  this one was written three minutes before the gate ran.

**A gate-design note worth carrying.** Check [15] as written is *unsatisfiable in the same
session as a first deploy*. A clean deploy+acceptance sequence can therefore never be green
in one pass, which is a property of the check rather than of the host. Not changed here —
the assertion is the right one and the plan's footer does say to log out and re-run — but a
gate that cannot pass on a correct first run should say that in its own output rather than
leaving the operator to infer it.
