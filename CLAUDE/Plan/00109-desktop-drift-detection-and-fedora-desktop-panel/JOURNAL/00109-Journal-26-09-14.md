## 09:35 · decision · T1.1 — the ledger designed, and two things in the task turned out to be wrong

[DESIGN-play-ledger.md](../DESIGN-play-ledger.md), summarised as Decision 2 in PLAN.md.

Two corrections to the task's own framing, both found by checking rather than accepting:

**The hash's justification was wrong.** Task 1.1 says `play_sha256` matters "because commit
alone cannot tell you whether *this play* changed". Given two commits, `git log -- <play>`
answers that precisely. The hash's real job is the case where **the commit is a lie**: a run
from a dirty tree, where a hand-edited play is otherwise indistinguishable from the committed
one and would be reported fresh for ever. That is a narrower claim and a better one, and it
changes what Phase 2 is allowed to conclude — freshness is driven by git history over the play
path, with the hash as the dirty-tree guard, not by hash comparison.

**Fail-fast cannot be done the obvious way.** Task 1.2 requires "a ledger write failure must not
silently produce a blank ledger". Ansible **catches exceptions raised inside a callback and
carries on**, so raising in the plugin gives a green run with nothing written — the precise
failure the requirement forbids, arriving through the mechanism meant to prevent it. The design
records the failure instead of raising it: a `BROKEN` sentinel, and Phase 2 refuses to answer
freshness questions while it exists. An unfailable hook becomes a failable check.

Confirmed at source: `ansible.cfg` declares **no** `callback_plugins` path and enables only
`ansible.builtin.default`, so this is a new mechanism here rather than an extension of one. The
plugin is close to unbypassable because every playbook's shebang `cd`s to the repo root before
exec, so a direct `ansible-playbook <path>` picks it up too — but `ANSIBLE_CONFIG` defeats it,
and §3 says so rather than claiming completeness the design does not have.

Task 1.3 is answered as a reporting rule, not a backfill: a play with no record has never been
run here and silence is correct for it, so nothing is invented about the past. The only thing
written at creation is a `genesis` record, so the ledger's own age is knowable and its silences
are unambiguous.

§5 is a table of what Phase 2 may and may not conclude. It exists because the tempting sentence
— "this play is up to date" — is one the ledger cannot support: `play_sha256` covers the play
file, and a play that imports `tasks/` or reads `vars/` can change materially with its own bytes
untouched.

## 10:08 · action · T1.2 — the ledger's pure half, test-first

`helpers/play_ledger/ledger.py`, 24 tests. Paths, record construction, validation, one-line
serialisation, the genesis record, and the fold to latest-per-play. No I/O; the append, the
sentinel and the callback plugin that drive them are the rest of Task 1.2.

Three decisions in it are worth naming, because each is somewhere a reader would expect
leniency and the design cannot afford it:

- **`fold_latest` decides by `finished`, not by position in the file.** The file is appended to
  by concurrent runs, so its order is not run order. Reading the last matching line would give
  the wrong answer exactly when two plays ran at once.
- **A corrupt line raises; it is not skipped.** A half-written record means the ledger has a
  hole, and a fold that skips it answers from a history it knows is incomplete — the
  silently-wrong-check failure this whole plan exists to catch on the host.
- **An unknown schema raises rather than being read anyway.** `schema` earns its place only if a
  reader actually refuses a shape it does not understand.

`dirty` is validated as a real `bool`, not merely truthy. The string `"false"` is truthy, so a
stringly-typed caller would record every run as dirty and make `play_sha256`'s entire reason for
existing unreadable — and nothing downstream would look wrong.

Next in Task 1.2: `store.py` (append, `BROKEN` sentinel) and the callback plugin, plus the
`ansible.cfg` `callback_plugins` path and `callbacks_enabled` entry — neither exists today.

## 10:12 · action · T1.2 — the ledger's filesystem half

`helpers/play_ledger/store.py`, 17 tests. Creation, appends, and the `BROKEN` sentinel.

Everything here raises on failure. The one caller that cannot afford to raise is the callback
plugin, and its job is to catch and call `mark_broken` — that asymmetry is the whole shape of
the fail-fast answer, so it is stated in the module docstring rather than left to be inferred.

Four details that are load-bearing rather than incidental:

- **`ensure_ledger` uses `O_EXCL`**, so two concurrent first runs cannot both write a genesis
  record. An existing runs file is left alone: a second genesis would reset the ledger's
  recorded age and make every silence ambiguous again, which is the one thing genesis exists
  to prevent.
- **`append_record` serialises BEFORE opening the file.** A record that cannot be serialised
  leaves the file untouched instead of half-written — and a half-written line is exactly what
  `fold_latest` refuses to read past.
- **`append_record` raises if the ledger is absent** rather than creating it. Creating it there
  would silently lose the genesis record.
- **`mark_broken` does not require the ledger to exist**, because "could not create the ledger
  at all" is precisely a failure that has to be recordable. It keeps the **first** reason: the
  first failure explains the hole, later ones are usually consequences of it, and overwriting
  would lose the cause.

`clear_broken` exists and is never called automatically. Clearing a recorded hole is a
deliberate act, and a sentinel something else can clear on its own is not a gate.

Remaining for Task 1.2: the callback plugin itself, plus `ansible.cfg` gaining a
`callback_plugins` path and a `callbacks_enabled` entry — it has neither today, so this is a
new mechanism in this repo rather than an extension of one.

## 12:58 — the hole was in the code whose subject is holes

Task 3.1's executor. Writing it surfaced a defect in the classifier I committed an hour earlier,
and it is this plan's own cardinal defect, one source down.

`build_report` took a `ProbeOutcome` for `dkms` — `ok`, text, error — so a missing `dkms` became a
finding. The two `systemctl` scopes were passed as plain **text**. A `systemctl` that cannot run
therefore contributed an empty failed-unit list, which is byte-identical to a host with nothing
failing. The design document I wrote alongside it says, in §3, "`dkms` absent, `systemctl`
unavailable, output in a shape the parser cannot read — each becomes a finding rather than a skip".
It covered one of the three. I wrote the rule and then implemented a third of it, in the plan whose
entire subject is checks that cannot fail.

What caught it was building the executor and asking what it would pass in. Not review, not a test —
the tests were green and stayed green, because they only ever passed strings for those two
arguments. A test suite that only exercises the shapes the author had in mind confirms the author's
mind.

The container turned out to be the right proving ground rather than a limitation. It has no `dkms`
and no systemd bus, so a real `python3 -m helpers.host_health.probe` run here exercises all three
probe-failure paths at once. Before the fix that run would have reported one finding; it reports
three, and the two extra are exactly what the hole swallowed. It also showed up a second thing the
unit tests could not: `systemctl` answers an unreachable bus in two lines, so the finding arrived as
two lines and would have reached the notification as a finding nobody wrote. Collapsed now, with its
own test.

I also cut a seam I had added out of habit. `main` took a `stderr` parameter nothing wrote to, and a
test asserted it stayed empty — which it always would. That is a check that cannot fail, sitting in
a file arguing against them. The parameter is gone and the test now redirects the *real* stderr,
which a stray `print` would actually reach.

Left undone deliberately: the login unit. It is a `--user` service `After=graphical-session.target`
and the pattern is already in `play-container-watch.yml`, so it is not hard — but a unit whose
output nothing surfaces is not a deliverable, and Task 3.2 owns the surfacing. There is a real
decision in the way, recorded in the design doc rather than guessed at: the freshness check answers
UNTRUSTWORTHY when its `git fetch` fails, and offline-at-login is ordinary. "I could not look must
never read as nothing is wrong" and "a check that speaks every login gets muted" point in opposite
directions there, and neither wins on its own terms.

## 13:58 — the control experiment found the bug in the gate that was checking for bugs

Task 2.2's manifest extraction. The pin manifest was a heredoc inside
`scripts/check-pinned-versions.bash`, so this plan's installed-vs-pinned check could only have
copied it — and two checks asking different questions of populations that can differ is how you
get one of them silently narrower than the other.

It is `vars/version-pins.yml` now, and both read it. I did not trust myself to transcribe nine
rows: the extraction is verified by taking the heredoc straight out of `git show HEAD:` and
diffing it against the rows the real validator emits from the YAML. Identical. That is a cheap
check and it is the difference between "I moved it carefully" and "it is the same manifest".

The gate needed to exist at all for a reason worth writing down. Neither consumer runs in
`qa-all` — the review tool needs an authenticated `gh`, the installed-vs-pinned check needs a
real host — so a manifest row that had drifted away from the playbooks would surface only when
somebody happened to run a review tool. And the specific rot is quiet: a row naming a var that
was renamed reports the old pinned value for ever, which reads as "up to date".

Eight mutations against a tree mirror, each caught: a renamed var, a missing playbook, a typo'd
key that would silently demote an automated pin to a manual one, a manual pin with no note for a
human to act on, a GitHub URL where `owner/repo` belongs, a duplicated row, a `|` inside a field
that would shift every later field by one, and the whole thing emptied.

Two of those eight caught something I had not mutated. They exited non-zero and printed
**nothing at all**. `$?` inside `if ! cmd; then` is the status of the negation — always 0 — so
every arm of the `case` that was supposed to say *which* row was wrong missed, and the gate
failed mutely. I had written the two distinct messages and then made both unreachable. A gate
that fails without saying why is barely a gate, and I would not have found it by reading the
code, because reading it is what produced it.

Then one more control, through `qa-all` itself rather than the gate standalone: break the real
manifest, run the suite, confirm it fails with the right message, restore, confirm the file is
byte-identical again. That one is not paranoia — a gate that fails alone and passes inside the
suite is a thing that has actually happened in this repo, and `CLAUDE/QA.md` still carries the
note about two gates that were documented and unrun for months.

## 14:40 — the pin I would have guessed wrong, and why the manifest now refuses to let me

Task 2.2's remaining half: resolve what is actually installed, and prove the check fails against
the incident it was built for.

I nearly wrote a generic rpm resolver. The evidence stopped me. The journal's own incident entry
records `Installed displaylink-1.14.16-2` against a `displaylink_version` pin of `v6.3.0-1` —
those are not the same versioning scheme at all. The pin is the displaylink-rpm *release tag*; the
installed rpm's version tracks *evdi*. A plausible-looking `rpm -q displaylink` resolver would
have reported that pin as drifted on every login for ever. A check that cries wolf gets muted
exactly as thoroughly as one that never speaks, and I would have shipped it believing it was the
careful option.

So resolution is declared per pin, and a pin with **no** `installed:` block is rejected outright.
Not defaulted to untracked — defaulting would turn a typo into a decision nobody made, and
silently stop comparing something somebody meant to watch. `untracked` is available, but it needs
a `why:`, because "untracked" with no reason is an omission wearing a decision's clothes.

That leaves 1 of 9 pins actually tracked, which is an uncomfortable number and is the point: the
gate prints `1 with install state tracked, 8 declared untracked` on every qa-all run. Eight rows
say "not yet established — needs a host". The gap is a number that stares back rather than an
absence that reads like a clean result.

The gate itself is asserted in both directions against the strings this plan's journal recorded,
not against invented ones. `evdi/1.14.16` versus a `1.15.0` pin is a finding. And
`evdi/1.15.0-1.github_evdi, 7.2.4-200.fc44.x86_64, x86_64: installed` — the real post-fix line,
release suffix and all — is **clean**. That second half took as much care as the first: a
comparison that could not see past `-1.github_evdi` would have reported drift on a healthy host
in perpetuity, and I would only have found out on a host.

`installed_from_dkms` reuses `probe_results.parse_dkms` rather than re-parsing the same format,
so the two halves of this plan cannot come to disagree about what a `dkms status` line means.
Where several builds of a module are listed it takes the highest **numerically** — as strings
`1.14.16` sorts before `1.14.9`, which is the trap `compare.py` already exists to avoid.

Smoke-run here, where `dkms` does not exist: the one tracked pin reports "could not be checked —
dkms: command not found", the eight untracked ones say nothing at all, exit 1. Both halves of the
intended behaviour, from a container, without pretending the container is a host.

## 15:06 — the question was posed wrongly, which is why neither answer worked

The open decision from this morning's design note: what should an offline login say when the
freshness check's `git fetch` fails?

Two rules this plan keeps invoking point straight at each other. *"I could not look" must never
render as "nothing is wrong"* says report it. *A check that speaks on every login gets muted* says
do not — offline at login is ordinary, a train, a hotel, a laptop that woke before the wifi did.
I spent a while trying to decide which rule outranks the other, which was the wrong exercise.

Neither wins because the question was wrong. **"Can I reach the remote right now"** is a fact
about the network, and this surface does not report on networks. **"How long is it since I last
could"** is a fact about this host, and that is the one worth having: a freshness verdict computed
from refs fetched an hour ago is worth reading, and the same verdict from refs three weeks old is
not. Once posed that way there is nothing to trade off — the check stamps each successful fetch,
stays silent while the stamp is recent, and reports the gap once it is not.

Three states, not two, and the third is deliberate: never-fetched gets its own message. A host
that has never successfully reached the remote has a different problem from one that last reached
it a month ago, and a single message would describe neither.

Two traps I only saw by writing the cases. A corrupt stamp has to degrade to "never fetched" — a
finding — and not to "fetched just now", which would be a silent pass by way of a parse error. And
a stamp in the *future* has to be a finding too, or a clock that ran backwards buys unlimited
silence.

This **reversed a ticked behaviour.** `check_freshness` already returned UNTRUSTWORTHY on a failed
fetch, with a test asserting exactly that and a docstring arguing for it. I rewrote the test to
pin the new rule rather than deleting it, and its docstring now says it previously asserted the
opposite and why. A reversal that leaves no trace is how a plan comes to contradict its own
history — and this plan has spent all day finding that shape in other files.

`EXIT_UNTRUSTWORTHY` stays, because it is still right for a `BROKEN` ledger and for a ledgered
commit that cannot be resolved — states where no verdict is available at all. What changed is
that a failed fetch alone stopped being one of them.

## 15:48 — the surface exists now, and two of its rules are about not trusting itself

Tasks 3.1 and 3.2's code. `login_report` runs the three checks this plan built, merges their
findings into one report, and notifies only if there is something to say.

The merge is the load-bearing part and it is deliberately not a chain. Each check is called
independently behind its own guard, so a raising one becomes a finding that **names itself** — "the
play-freshness check could not run: …" — and cannot suppress the other two. Chained, a broken
ledger would have hidden a dead DKMS module, which is this plan's own subject one level up.
Host-health findings sort first: something broken on this machine now outranks something that has
merely drifted.

The second self-distrusting rule: the notification is not the only channel. A failing notifier —
no session bus, `notify-send` missing — still leaves every finding on stdout, keeps the exit
status, and reports its own failure as a line. Otherwise a broken notifier silently converts a
broken host into a healthy-looking one, which is the failure mode wearing a different hat.

Two things I caught while writing the unit rather than after deploying it. `WorkingDirectory` was
a hardcoded `%h/Projects/fedora-desktop` in the first draft — a guessed path, in a public repo,
for a checkout location I have no way to know. It is a `.j2` templated from `root_dir` now. And
the sibling `play-container-watch.yml` writes `/run/user/{{ uid | default(1000) }}`; copying that
would have been the easy thing, but a wrong default there does not fail — it points the probe at
another user's runtime directory and the enable step then reports "no user manager" on a host that
has one. This play resolves the uid with `getent` and asserts it.

`SuccessExitStatus=0 1` because exit 1 means "there are findings", which is a *successful* run of
the check. Without it a drifted host would also show up as a failed service, and two alarms for
one fact is how both come to be ignored.

What is left here is a host: the play has to run, the unit has to fire at the end of a login, a
real notification has to arrive, and a clean login has to be genuinely silent. None of that is
provable from a container, and the unit tests deliberately do not pretend otherwise — they pin the
decisions, not the delivery.
