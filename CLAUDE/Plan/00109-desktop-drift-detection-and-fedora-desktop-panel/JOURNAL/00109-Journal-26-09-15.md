## 10:01 · delivery · T3.2 — the server route, and the one line that could have broken scp

Picked up as the only Task 3.2 sub-item that needed neither the host nor a decision: the
delivery half of the server route. `status_document.py` (producer) and `login_message.py`
(renderer) were already written and tested; nothing ran either of them on a server.

**Three artefacts.** `host-health-collect.service.j2` runs
`login_report --no-notify` — the same collection the desktop unit does, minus the
`notify-send` there is no session bus for. `host-health-collect.timer` triggers it.
`host-health-report.bash.j2` goes into `~/.bashrc-includes/` and prints what the timer
left. `play-host-health-server-report.yml`, `scope: server`, deploys all three.

### The cadence is derived, not chosen

The task said "cadence to be decided against `STALE_AFTER_DAYS`", and that bound
(`login_message.py:47`) is 14 days: past it, the consumer reports the document's own age
as a finding, because a clean document nobody has refreshed for a fortnight describes the
host as it was a fortnight ago.

Daily, therefore. It absorbs fourteen consecutive misses, so one failed run, one reboot or
a day powered off is not a false alarm, while a collector that has genuinely stopped is
reported well inside the bound. Weekly gives two attempts inside the same window — the
margin would be a single missed run, and the report would then be crying stale on a
healthy host or silent on a broken one depending on which way the miss fell. The
reasoning is written into the timer beside the value, because a number in a unit file
with no derivation is a number the next person will change without knowing what it was
balanced against.

`OnStartupSec=5min` as well. This plan exists because a reboot into a new kernel left a
DKMS module unbuilt and nothing said so; a purely calendar-driven collector would take up
to a day to notice that, which reproduces the incident with a delay.

### The interactive guard is the load-bearing line

bash reads `~/.bashrc` for a **non-interactive** shell too when sshd is what started it.
That is why a `.bashrc` that prints anything breaks `scp`, `sftp` and rsync-over-ssh with
a protocol error: the transfer parses stdout. This snippet is the first thing this repo
puts in `~/.bashrc-includes` that prints at all — the existing four only define aliases —
so the guard is new territory here, and a health report that breaks file copies to the
host it reports on is worse than no report.

`scripts/test-host-health-login-snippet.bash`, 12 assertions, renders the template and
sources it in both a real `bash -i` and a plain `bash -c`. Six mutants, all killed:

1. the interactive guard deleted → the non-interactive case speaks
2. `cd` into the checkout instead of `PYTHONPATH=` → the caller's `$PWD` moves
3. `PYTHONPATH` exported → it survives into the caller's environment
4. the missing-checkout guard deleted → an ImportError traceback at every login
5. that guard returning non-zero → a login shell under `set -e` would die
6. a bare `python3` instead of `/usr/bin/python3` → the pyenv shim, not the interpreter
   the play installs `python3-pyyaml` into

**The sixth survived the first run**, and the reason is worth keeping. The assertion was
`grep -q '/usr/bin/python3' "$RENDERED"` — and the snippet carries a comment explaining
*why* the interpreter is named by path, which contains the string. So the check was
satisfied by its own documentation while the invocation it vouched for had been mutated
to a bare `python3`. It now selects the non-comment line that names the module and tests
that, and fails if it does not find exactly one such line.

The guard against a findings document rather than a clean one matters for the same
family of reason: with a clean document the snippet is silent for the wrong reason, and
mutant 1 would have passed.

### Two smaller decisions

**The snippet asserts nothing about its own plumbing; the play does.** `~/.bashrc-includes`
and the loop that sources it belong to `play-basic-configs.yml`, which is in
playbook-main's core path. This play slurps `~/.bashrc` and asserts the marker is there,
failing with an instruction to run playbook-main first. Deploying a snippet into a
directory nothing sources would leave a host reporting as healthy while nothing read the
report — this plan's own defect, one layer down.

**The timer is started as well as enabled.** `enabled: true` alone writes the
`timers.target.wants` symlink and leaves the timer unarmed until the next boot. Starting
a *timer* arms the schedule; it does not run the collection now.

The HOST run. The timer arming, a document appearing, an interactive login showing

## 13:10 · finding · T3.2 — "no DKMS modules" is not "no DKMS", and Task 0.2 would have proved it

Round 5. H1 closed and the re-derivation verified across all four ledger states plus a
stock server. Three new findings, all real, all mine.

**H4 — the empty registry.** My skip condition was "the module list came back empty",
and the reviewer measured why that is wrong. The `dkms` rpm **owns `/var/lib/dkms`**, and
`play-displaylink.yml` installs `dkms`, so every host that ran that play has the
directory — and an empty registry there means the module was *removed*. That is exactly
what this axis exists to report, and **Task 0.2 of this plan is about to create that
state** by deleting orphaned DKMS trees. Its counterfactual is the part worth keeping: a
single unrelated module in the registry restored the correct finding, so the bug was
invisible on any host that happened to have one.

The deeper problem it named: the two consumers were reading the same value but needed
different facts. `build_report` required `dkms.missing AND registry == []`; `check_pins`
required `registry == []` alone. `probe_results.DkmsRegistry` now carries them apart —
`present` is a tri-state (no directory / present / could not tell), `modules` is what it
holds — so one read gives one coherent value and the two cannot hold inconsistent halves.
Verified: only "no state directory at all" is silent now.

**H5 — the BROKEN sentinel.** The ABSENT scoping leans on "an empty or unreadable ledger
is `ledger_presence`'s finding", and that holds everywhere except the one state where
`ledger_presence` returns `[]` *deliberately* — while the sentinel exists, because
`check_freshness` already prints the reason. So in the single state where this repo has
declared the ledger incomplete, `plays_run_here` read it anyway and would have suppressed
every ABSENT whose row was in the hole, with nothing saying so. It now returns `None`
there. The sentinel IS the declaration that the question is open.

**H6 — the resolver with no ABSENT branch.** `_rpm_version` catches "is not installed"
and returns `None`; `_command_version` was a bare `_run`, so a missing command raised,
the broad `except` turned it into an *unchecked* finding, and the original permanent
noise came back through the one resolver the ABSENT scoping cannot reach — it never gets
as far as `classify`. Not live today: the manifest has nine pins and the one tracked pin
is DKMS-kind. Invisible when that stops being true, which is the whole reason to fix it
now.

**The accepted consequence is now a decision (§5.3).** A host that ran a play and then
deliberately removed what it installed reports ABSENT for ever. That is correct rather
than tolerated — the repo declares the pin, so software the repo installs and the host no
longer has is drift — and the manifest already carries the remedy: declare the pin
`untracked` with a `why`. Suppressing it silently would make "I removed this on purpose"
and "this vanished" the same answer.

### Pattern worth naming

Three rounds, three variants of one mistake: a predicate that conflates two facts because
one value happened to represent both. `[]` for "no directory" and "empty directory"; the
population filter for "not installed here" and "never checked here"; `missing` present in
one consumer's condition and absent from the other's. Each time the fix was to stop
collapsing and start carrying the distinction in the data.

## The refactor moved the code out of set -e

qa-reviewer returned **BLOCK** on the commit above, and it was right.

Lifting the kernel step into a function moved it from script top level — errexit live —
into a function the caller invokes as `target_kernel="$(select_second_kernel …)"`. **Bash
switches errexit OFF inside a command substitution** unless `inherit_errexit` is set, and
this repo sets it nowhere. Measured on 5.2.15:

```
x="$(f)"   where f runs `false` then continues  ->  caller exits 0, f ran to the end
( f )      same f                               ->  subshell exits 1 at the false
```

So `sudo -n dnf -y install` had its status discarded. A failed transaction would either
die blaming `/boot` for a package failure — the exact defect I had just fixed for `rpm`,
now reintroduced one line below it — or, on a guest already carrying two kernels, **succeed
silently** with `PREPARED_WANTED_KERNEL` naming a kernel nothing downloaded.

`grubby --set-default` and `record` had the same shape. Found those myself while fixing the
one the reviewer named; all three now carry their own refusal, and the function's header
says plainly that `set -e` protects nothing inside it.

### Why fifteen cases did not see it

This is the part worth keeping. **The harness ran the function in a `( … )` subshell,
where errexit IS live.** It was testing semantics production never has. The test and the
code disagreed about the error model, and the test's version was the forgiving one.

`STUB_INSTALL_RC` had been sitting in the stub file since the first draft, unreachable —
a knob advertising exactly the coverage the harness could not have. I wrote it, looked at
it several times, and never asked why nothing set it.

`run_case` now calls the function in a command substitution, exactly as the fixture does.
That one change made two new cases expressible: a failing package transaction and a
bootloader that refuses the selection.

Thirteenth instance of the shape, and again inside a fix for the previous one.

### What else the review found

**Every stubbed version list was written newest-first**, so both `sort -Vr` calls could be
deleted and all twelve cases still passed — the first line was already the answer. Neither
dnf nor rpm promises an order. The lists arrive oldest-first now, and a mutant deleting
both sorts dies.

**Two refusals shared one message.** An empty `repoquery` and a `repoquery` offering only
the running kernel both said *"every kernel-core the repos offer is X"* — false in the
first case, and it sends a reader hunting for a kernel when the fault is the repository
configuration. The same "predicate that does not make a distinction" shape, in a message
rather than in a branch. Two causes, two messages, and case 4 now FAILS if it sees case 3's.

**`--showduplicates` was missing, and its absence was unfalsifiable.** repoquery answers
with the newest build per `name.arch` without it — and a guest built from a current image
*is* that build, so the case the lab is likeliest to produce would have found only itself
on offer and refused. The stub ignored its arguments, so no test could have caught it. The
stub now honours the flag, and dropping it fails the suite.

That one is also the honest version of a disclosure I had already made badly: §8.2 said
dnf's output *format* was unverified, but said nothing about its *multiplicity*, which
case 1 rested on entirely. Both assumptions are now stated.

## Round 3: the stubs were the only thing between this gate and the host

Round 3 also ran a commit behind, so its list of open items was already closed. Its new
finding was not.

`eval "$STUB_PRELUDE"` discards its status, inside a subshell with errexit off. Those
stubs are the *only* thing standing between this suite and the host's real tools — and
this gate runs on the user's own Fedora machine, where `dnf` and `grubby` exist and sudo
may be passwordless. A prelude that stops defining what it should means the names fall
through to PATH.

Reproducing it found the realistic rot is worse than a syntax error. An unterminated
`rpm() {` **still parses**: the following `grubby() {` is swallowed as a nested definition,
so the eval succeeds, `grubby` is simply never defined, and the run finds the host's one.
My first attempt to demonstrate the hazard used exactly that mutation and reported "not
reached" — I had written a mutant that wasn't the mutant I claimed, for the second time
today.

Three layers now, and I made myself prove each rather than accept the comfort:

```
eval status judged        ->  unparseable prelude  ->  HARNESS: the stub prelude did not parse
collaborators are functions ->  renamed stub       ->  HARNESS: the prelude did not define dnf
PATH holds sort and cat only ->  all guards stripped, fake host grubby on PATH:
                                  restricted    -> dies "no grubby in this guest"
                                  unrestricted  -> the fake was EXECUTED
```

That last row is the one worth the effort. I nearly shipped the PATH restriction as an
unfalsifiable comfort — a line that looks prudent and might do nothing. It took stripping
the other two guards to show it does something, and what it does is stop this suite
running the host's bootloader tool. The fake grubby's own output turned up inside the
refusal message: `--set-default` and `--default-kernel` were really invoked.

A green-suite mutant could never have found that, because the effect only exists once the
earlier layers have failed. Defence in depth is exactly the thing mutation testing cannot
see, and "I could not construct a failing case" is not the same as "it does nothing".

`exit 97` from any layer stops the whole suite rather than failing a case: verdicts from a
run whose stubs were not installed would be reporting on whatever the host happened to have.
