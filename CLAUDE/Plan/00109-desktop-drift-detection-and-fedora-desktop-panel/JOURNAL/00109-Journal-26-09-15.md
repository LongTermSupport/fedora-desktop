## 10:01 · delivery · T3.2 — the server route, and the one line that could have broken scp

Picked up as the only Task 3.2 sub-item that needed neither the host nor a decision: the
delivery half of the server route. `status_document.py` (producer) and `login_message.py`
(renderer) were already written and tested; nothing ran either of them on a server.

**Three artefacts.** `host-health-collect.service.j2` runs
`login_report --no-notify` — the same collection the desktop unit does, minus the
`notify-send` there is no session bus for. `host-health-collect.timer` triggers it.
`host-health-report.bash.j2` goes into `~/.bashrc-includes/` and prints what the timer
left. `play-host-health-server-report.yml`, `scope: server`, deploys all three.

### The cadence is derived, not chosen

The task said "cadence to be decided against `STALE_AFTER_DAYS`", and that bound
(`login_message.py:47`) is 14 days: past it, the consumer reports the document's own age
as a finding, because a clean document nobody has refreshed for a fortnight describes the
host as it was a fortnight ago.

Daily, therefore. It absorbs fourteen consecutive misses, so one failed run, one reboot or
a day powered off is not a false alarm, while a collector that has genuinely stopped is
reported well inside the bound. Weekly gives two attempts inside the same window — the
margin would be a single missed run, and the report would then be crying stale on a
healthy host or silent on a broken one depending on which way the miss fell. The
reasoning is written into the timer beside the value, because a number in a unit file
with no derivation is a number the next person will change without knowing what it was
balanced against.

`OnStartupSec=5min` as well. This plan exists because a reboot into a new kernel left a
DKMS module unbuilt and nothing said so; a purely calendar-driven collector would take up
to a day to notice that, which reproduces the incident with a delay.

### The interactive guard is the load-bearing line

bash reads `~/.bashrc` for a **non-interactive** shell too when sshd is what started it.
That is why a `.bashrc` that prints anything breaks `scp`, `sftp` and rsync-over-ssh with
a protocol error: the transfer parses stdout. This snippet is the first thing this repo
puts in `~/.bashrc-includes` that prints at all — the existing four only define aliases —
so the guard is new territory here, and a health report that breaks file copies to the
host it reports on is worse than no report.

`scripts/test-host-health-login-snippet.bash`, 12 assertions, renders the template and
sources it in both a real `bash -i` and a plain `bash -c`. Six mutants, all killed:

1. the interactive guard deleted → the non-interactive case speaks
2. `cd` into the checkout instead of `PYTHONPATH=` → the caller's `$PWD` moves
3. `PYTHONPATH` exported → it survives into the caller's environment
4. the missing-checkout guard deleted → an ImportError traceback at every login
5. that guard returning non-zero → a login shell under `set -e` would die
6. a bare `python3` instead of `/usr/bin/python3` → the pyenv shim, not the interpreter
   the play installs `python3-pyyaml` into

**The sixth survived the first run**, and the reason is worth keeping. The assertion was
`grep -q '/usr/bin/python3' "$RENDERED"` — and the snippet carries a comment explaining
*why* the interpreter is named by path, which contains the string. So the check was
satisfied by its own documentation while the invocation it vouched for had been mutated
to a bare `python3`. It now selects the non-comment line that names the module and tests
that, and fails if it does not find exactly one such line.

The guard against a findings document rather than a clean one matters for the same
family of reason: with a clean document the snippet is silent for the wrong reason, and
mutant 1 would have passed.

### Two smaller decisions

**The snippet asserts nothing about its own plumbing; the play does.** `~/.bashrc-includes`
and the loop that sources it belong to `play-basic-configs.yml`, which is in
playbook-main's core path. This play slurps `~/.bashrc` and asserts the marker is there,
failing with an instruction to run playbook-main first. Deploying a snippet into a
directory nothing sources would leave a host reporting as healthy while nothing read the
report — this plan's own defect, one layer down.

**The timer is started as well as enabled.** `enabled: true` alone writes the
`timers.target.wants` symlink and leaves the timer unarmed until the next boot. Starting
a *timer* arms the schedule; it does not run the collection now.

The HOST run. The timer arming, a document appearing, an interactive login showing

make. Recorded as the remaining ⬜ under Task 3.2.

## 10:30 · finding · T3.2 — a fresh document can be entirely about the previous boot

Found while checking whether `RandomizedDelaySec=30min` weakens the `OnStartupSec=5min`
trigger. It does, by up to half an hour — but chasing that turned up something worse
sitting underneath it.

**The desktop route cannot hit this and the server route can.** `host-health.service`
re-runs the producer at every graphical login, so the document always describes the boot
the reader is in. The timer route does not: a host reboots, the document from before the
reboot is minutes old, well inside `STALE_AFTER_DAYS`, and says `ok`. Every DKMS module
on the box can be unbuilt for the kernel that actually booted and the login report stays
silent.

That is this plan's founding incident with the delivery mechanism I had just built in
front of it. Staleness does not cover it — age and boot are independent, and the document
can be one minute old and still be about a different kernel.

The document already carried `kernel`; nothing compared it to anything.
`login_message.render` now takes `running_kernel` and reports a mismatch in its own
right, in the not-checked group — nothing is known to be *broken*, what is known is that
these results do not describe the running kernel.

**Required keyword, not a defaulted one.** The precedent is `ledger_present` on
`collect_sections` (26-09-14): a default makes nineteen existing call sites pass
untouched and lets any future caller silently omit the check. Here it cost five call
sites in the test file and one in `main`.

Four mutants, all killed: the comparison forced false, the `and running_kernel` guard
dropped (so "could not tell" would render as "they differ"), the mismatch reported as a
fault rather than as not-checked, and the message naming only the running kernel instead
of both.

### The bash suite caught its own fixture

`test-host-health-login-snippet.bash` went 9/12 the moment this landed, and it was right
to. Its documents were stamped `kernel: "0.0.0-test"`, so with the new rule in place
every case spoke — including the three written to prove the snippet stays *silent*. The
fixture now stamps `uname -r`. Worth recording because the failure was the gate working:
an invented value in a fixture stopped being inert the moment something started reading
it, and the three silent-case assertions would otherwise have quietly become assertions
about nothing.

`./scripts/qa-all.bash`: 878 files green, 1,260 helper tests, snippet suite back to 12/12
with all six of its own mutants still dying.

### Left alone

`RandomizedDelaySec=30min` stays. The post-boot window it opens is now covered from the
other end: whatever the document says during it, the reader is told it predates this
boot.

## 11:20 · review · T3.2 — the qa-reviewer pass, and the finding that mattered

Report: `subagent-reports/260915-qa-reviewer-00109-t32-opus-5.md`. Verdict
FIX-BEFORE-MERGE, no blockers, six things. All six are now fixed; the reasoning that
outlives this entry moved to [DESIGN-server-route.md](../DESIGN-server-route.md).

### The one that decided whether the surface was usable

**A healthy server would never have been silent** — and the reviewer measured it rather
than inferring it. `dkms` is installed by exactly two plays, both optional and both
desktop hardware, so a stock server has neither the command nor a module tree, and both
the health probe and the pin check emitted a permanent unchecked finding because of it.
Every interactive SSH login would have printed "fedora-desktop: this machine needs
attention" plus two lines that could never become actionable. That is the exact failure
`login_message.py`'s own docstring says the surface exists to avoid, shipped inside the
thing built to avoid it.

Two different answers, because the two checks ask different questions:

- The probe now treats *no dkms command **and** no registered module tree* as an answer.
  A host with no DKMS subsystem cannot have a module missing a build. Command gone with
  trees still registered is reported, and is worse than either half. An unreadable state
  directory answers `None` and still reports — the tri-state matters, and folding it into
  `[]` would let a permissions problem buy permanent silence on the axis the incident
  happened on.
- The pin check now takes applicability from the **play ledger**. A pin belongs to a
  play; a play this host has never run installs nothing here for the pin to be about.
  That is not a new policy — it is Task 1.3's rule ("a play with no record has never been
  run here, and silence is correct for it") applied to the axis that had missed it. The
  zero-coverage guard counts applicable pins, or it would simply replace the noise the
  filter removed.

Verified end to end in the container, which has no dkms and no ledger: both sections now
return nothing.

### The one I disagreed with, and did not silence

The timer's `git fetch` has no credentials, so an SSH-remote checkout reports "never
reached the remote" on every login, permanently. The reviewer called it the same class as
the first finding. It is not: unlike a DisplayLink pin on a headless box, this names a
real gap in *this host's* setup with a remedy the operator can apply. Silencing it would
be the mistake. It is documented in the unit, in `docs/playbooks.md` and as a HOST item
instead — and deliberately without an `Environment=SSH_AUTH_SOCK` pointing at a socket
that may not exist, which would trade a clear finding for a confusing one.

### The play was a copy, and merging it dissolved a second finding

Four byte-identical tasks and five comment blocks differing only by line-wrapping.
`play-host-health-login-report.yml` is now `scope: general` with two profile-gated
delivery blocks, and `play-host-health-server-report.yml` is gone. That also made
`CLAUDE/AnsibleStyle.md:240` true again — it says no play is `scope: server`, which the
deleted file had falsified.

`qa-ansible.bash` then caught something worth keeping: a task named "Scope guard —" on a
general-scope play. It was right. The assert stays because both branches key on

### The QA inventory is derived now, not re-enumerated

`CLAUDE/QA.md` claimed seventeen gates and ten non-merged ones; the real numbers are

### Three assertions were comparing the wrong thing

`sourcing leaves PYTHONPATH unset` and the two exit-status checks captured the snippet's

happened to be silent — which is why the kernel-mismatch change broke them earlier today

marks its answer and the probe extracts that line; a missing marker returns

some of these. The fixture also builds through `status_document.build`/`write_atomic`
now, so it tracks the schema instead of restating it.

## 11:55 · finding · T3.2 — the kernel-mismatch rule contradicted itself

Round 2 of the same review. Verdict still FIX-BEFORE-MERGE, and the finding is a good
one: the rule closes a real gap and then makes the report say something false in the
exact scenario it was written for.

Reproduced before touching anything:

```
  - evdi: no DKMS module installed for the running kernel 7.1.9-200.fc44.x86_64
  Not checked — these are NOT clean results, nothing is known about them:
  - these results were collected under kernel 7.1.9-… and this host is now running 7.2.4-…
```

Two consecutive lines, two different values for "the running kernel", and the first
presented as a known fault about now. `dkms_findings` bakes the collecting kernel into
its text, which is written at collection time and read later — so before this rule the
line was simply never shown after a reboot, and making the report speak surfaced a
latent contradiction rather than creating one.

**And a test of mine asserted the pairing and recorded it as correct**, which is the part
worth remembering: the assertion said "the mismatch is reported *alongside* real
findings", which is true and was the wrong property to pin. Nothing would have found it
later.

**Fix: demote, do not repeat.** On a mismatch the boot-scoped section's findings move
into the not-checked group, under the explanation that causes them. Which section that is
is now `status_document.BOOT_SCOPED_SECTION`, declared beside `SELF_SECTION` rather than
in the producer — a *consumer* is what needs to recognise it, and two spellings would let
the two disagree silently. `login_report.HEALTH` reads it from there.

Scoped deliberately. Only `post-boot-health` is boot-scoped; the ledger, play freshness
and installed-vs-pinned survive a reboot unchanged, so demoting them would be the mirror
image of the same overclaim. The wording was narrowed for the same reason — "nothing here
describes the running kernel" was false about three sections out of four.

Four mutants, all killed: the demotion disabled, *every* section demoted, the explanation
appended after what it explains, and the wording reverted to the overclaiming form.

### The two nits were already fixed, and I checked rather than assumed

The reviewer was reading an intermediate tree — before `7fa9edef`. `uname -r` is gone
from the fixture (it builds through `probe.running_kernel()` now), the three assertions
already extract a marked line rather than comparing whole stdout, and the scope-guard
error it flagged in `qa-all.bash` was the same intermediate state. Verified all three
against the current files.

### The recognition assert stays, and now says why

The reviewer read `AnsibleStyle.md`'s "a general play carries **no** guard" as requiring
the assert deleted. That rule is about the two-task `meta: end_play` block, which would
be wrong here — this play has work for both profiles and `qa-ansible.bash` rejects that
block on a general scope. What the assert validates is an input a **human types**:
auto-detection can only yield desktop or server, but `-e provisioning_profile=…` is the
documented override and takes highest precedence, so a typo would leave `is_server` false
and quietly deploy the notify-send unit to a box with no session bus. The play now
records that distinction instead of leaving it to be re-litigated.
