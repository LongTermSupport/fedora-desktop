## 11:16 · finding · T0.1 — the incident: DKMS build failure against kernel 7.2

Retrospective entry (the failure predates the plan). Laptop rebooted into kernel
7.2.4; both DisplayLink monitors dark. `modinfo evdi` → not found. DKMS had evdi
built for 7.1.5 and 7.1.8 only. The autoinstall ran at boot and failed:

```
Sep 11 11:16:10 dkms[1433]: Autoinstall of module evdi/1.14.16 for kernel 7.2.4-200.fc44.x86_64
Sep 11 11:16:12 dkms[1433]: Autoinstall on 7.2.4-200.fc44.x86_64 failed for module(s) evdi(10).
```

Real kernel API break, not a toolchain problem — 7.2 changed the DRM atomic
helper callback signatures:

```
evdi_modeset.c:183: error: initialization of 'void (*)(struct drm_crtc *, struct drm_atomic_commit *)'
                    from incompatible pointer type 'void (*)(struct drm_crtc *, struct drm_atomic_state *)'
```

Dock itself was healthy throughout — `17e9:602b DisplayLink StarTech DK31C3HDPD`
enumerated fine. No driver, so no heads.

## 11:40 · thought · T5.1 — a number I asserted and then doubted

I told the user the large wallpaper costs ~131 MB of texture *per monitor*, ~520 MB
across four. On reflection mutter likely caches the decoded image by filename
(`MetaBackgroundImageCache`) and shares one texture, scaling per-monitor on the GPU —
which would make the true cost paid once, not four times.

Dispatched research to settle it from the mutter/gnome-shell sources rather than
guess twice. Recorded here because the fix in T5.3 (per-monitor pre-scaled cache)
only makes sense if the per-monitor reading is true, and it probably is not. The
oversized wallpaper is still worth fixing for decode time on every background
reload; the *reason* needs to be the real one.

## 12:08 · thought · P5 — do not oversell what scaling fixes

Related to the above, and worth stating before T5.2 is built: the research found
**two open upstream mutter bugs** (`#4767`, `#4935`) that produce the same black
background independently of image size, plus an apparently unreported sticky
variant. Scaling the wallpaper only shortens the decode (342–466 ms → ~73 ms) and
so improves the odds on *one* GC race. It is a mitigation, not a fix, and the plan
should not claim otherwise — if the backgrounds still blank after T5.2 deploys,
that is consistent with the upstream bugs, not evidence that T5.2 failed.

## 12:35 · finding · P5 — the discriminator was already answered in the first report

Asked the user to run a test — "open the Overview, does the background come
back?" — whose answer was in their original description of the symptom:

> It shows when you press the overview and you can drag windows into the
> monitors, but the desktop background doesn't show on some of the monitors.

They pointed this out. The information was in hand and went unconnected, costing

The answer is decisive, and stronger than the proposed discriminator. The
Overview and the desktop draw from the **same** `MetaBackground`, so a correct
Overview render *proves the texture exists and is valid* — ruling out a cache
miss, a slow decode and a NULL texture in one go, since each would be black in
both views.

Consequence: **image size is irrelevant to this symptom.** The whole scaling line
(T5.2, T5.3) aimed at shrinking a GC-race window that is demonstrably not what is
failing. Cancelled before any code shipped. Correcting the 12:08 entry above: the
decision does not wait on a deploy, because the evidence to settle it already
existed.

What remains is a rendering failure in the `MetaBackgroundContent` paint path for
the desktop view — the `mutter#4767` clip family, or the sticky
`CHANGED_BACKGROUND` variant. Both upstream, both open, neither fixable here.
Which one cannot be settled from the journal: that failure path calls
`g_clear_object()` and returns NULL without logging anything.

The workaround profile matches either: force a genuine `bg-changed` by toggling
`picture-uri` — the only signal that re-sets `CHANGED_BACKGROUND`. Another
`monitors-changed` does not recover it, and `updateResolution()` refreshes only
the animation. Caveat: `gnome-shell#9188` reports a ~57 MB per-monitor leak if
toggled while the session is locked.

New T5.4 covers it. Likely home is `helpers/displaylink_recovery/`, which already
fires on dock events via a udev rule and a suspend service — noting it currently
recovers *wedged heads*, a driver-layer fault, so this is a different failure at
the compositor layer sharing one trigger.

## 12:50 · finding · T5.1 — ran the check the research named; evidence converges on mutter#4767

The 12:35 entry said which variant it is "cannot be settled from the journal".
That was too quick — the research named a check that had not been run, and it is
informative even though the failing branch itself logs nothing.

**1. No Cogl/Mesa-level errors this boot.**

```
journalctl --no-pager -b --user -u gnome-shell \
  | grep -iE 'cogl|framebuffer|texture|GL error|out of memory|EGL'
→ (nothing)
```

The sticky variant originates in an **FBO allocation failure**. Allocation
failures of that kind normally surface a Cogl/Mesa error somewhere even though
mutter's own branch is silent. Nothing logged is evidence against that variant —
not proof, since the path is silent by construction.

**2. Version matches the unfixed bug exactly.** `mutter-50.4-1.fc44`,
`gnome-shell-50.4-1.fc44`. The research places `mutter#4767` verbatim in 50.4.

**3. The colour is wrong for the other variant — worth checking with the user.**
`primary-color` here is `#30307171aeae`, a dark slate **blue**, not black. The
sticky variant paints `color_texture`, i.e. that flat blue. The clip bug **skips
the paint entirely**, leaving a cleared framebuffer, i.e. **black**. The user
consistently says "black". If that is literal rather than loose, it points at the
clip bug and away from the flat-colour path.

Convergent, not conclusive. All three are consistent with `mutter#4767`: the
texture is valid (Overview renders), allocation is not failing (no Cogl errors),
the version carries the bug, and nothing is being painted rather than the wrong
thing being painted.

Practical consequence for T5.4: the `picture-uri` toggle should still recover it,
since a genuine `bg-changed` forces `mark_changed()` and a full repaint. But if
this is the clip bug, the recovery is treating a **damage/clip** fault, so it may
recur on the next monitor change rather than being a one-time repair — the
automation should assume recurrence, not a single fix at dock time.

## 13:05 · finding · T5.4 — Plan 00056's recovery has never run on this host

Went to add the background refresh to the dock recovery and found the recovery
itself inert. Three separate faults, each verified on HOST, all fixed in
`9a79dd7`.

**1. The deploy has always failed.** `ansible.builtin.copy` does not create
parent directories for a file destination, and nothing created
`/usr/local/lib/displaylink-recovery/`. The play aborted at the first recovery
task with exit 2, so the udev rule and `displaylink-dock-recovery.service` after
it were never deployed. `displaylink-suspend.service` *was* present from an older
deploy, enabled, pointing at a `WorkingDirectory` that did not exist — failing on
every resume, which is why its journal identifier had never logged a line.

**Correction to my own reporting**: the first `play-displaylink.yml` run this
session was reported here and to the user as completing successfully. It did not
— it exited 2 at this same task. The command ended in a hardcoded
`echo "PLAY EXIT: 0"` instead of echoing `$?`, so the claim came from the string I
wrote, not from the play. The evdi fix was real and independently verified
(module built, signed, loaded, heads enumerating), but the play never finished.
Never print a hardcoded status next to a command whose status is the question.

**2. The wedge signature was always true.** `os.path.getsize()` on a sysfs EDID
attribute returns **0 regardless of content** — the inode carries no size, the
file has to be read. Measured here:

```
card1-eDP-1     stat=0  actual_read=384
card2-DVI-I-1   stat=0  actual_read=256
card3-DVI-I-2   stat=0  actual_read=256
card4-DVI-I-3   stat=0  actual_read=0     (genuinely disconnected)
```

So `edid_bytes` was always 0, `wedged_heads()` returned every connected head on
every system, and `decide()` would have run service-restart → USB-reauth →
module-reload against perfectly healthy monitors at every dock event. Confirmed
before the fix: `--dry-run` on a working desktop said `action=restart_service`.

The 13 existing unit tests passed throughout, because they hand-build `HeadState`
with explicit `edid_bytes` and never touch sysfs. A tempfile fixture would not
have caught it either — tempfiles report an honest `st_size`. Only real sysfs
reproduces it, so the new test asserts against real sysfs and skips where there
is none.

**3. dconf writes were silently discarded.** `sudo` sanitises the environment it
hands the child, so `DBUS_SESSION_BUS_ADDRESS` set through subprocess `env=` was
dropped. dconf fell back to autolaunching a private bus, failed with
`Failed to execute child process "dbus-launch"`, and lost the write — while
exiting zero. The address now travels *through* sudo via `env`. `_notify()` had
the identical defect, so its desktop notifications have never reached a session
either.

Verified after fixing: play exits 0 (`changed=10` the first time, the artefacts
that had never deployed), deployed helper byte-matches the repo, a real run
prints `refresh_background` then `none` with no dconf warnings, and
`picture-uri`/`picture-uri-dark` are unchanged afterwards.

**Not yet verified**: that the refresh clears the black background when the fault
is actually present. It has only been exercised against a healthy desktop.
