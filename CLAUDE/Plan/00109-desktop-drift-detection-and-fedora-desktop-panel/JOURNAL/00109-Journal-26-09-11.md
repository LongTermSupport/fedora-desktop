## 11:16 · finding · T0.1 — the incident: DKMS build failure against kernel 7.2

Retrospective entry (the failure predates the plan). Laptop rebooted into kernel
7.2.4; both DisplayLink monitors dark. `modinfo evdi` → not found. DKMS had evdi
built for 7.1.5 and 7.1.8 only. The autoinstall ran at boot and failed:

```
Sep 11 11:16:10 dkms[1433]: Autoinstall of module evdi/1.14.16 for kernel 7.2.4-200.fc44.x86_64
Sep 11 11:16:12 dkms[1433]: Autoinstall on 7.2.4-200.fc44.x86_64 failed for module(s) evdi(10).
```

Real kernel API break, not a toolchain problem — 7.2 changed the DRM atomic
helper callback signatures:

```
evdi_modeset.c:183: error: initialization of 'void (*)(struct drm_crtc *, struct drm_atomic_commit *)'
                    from incompatible pointer type 'void (*)(struct drm_crtc *, struct drm_atomic_state *)'
```

Dock itself was healthy throughout — `17e9:602b DisplayLink StarTech DK31C3HDPD`
enumerated fine. No driver, so no heads.

## 11:20 · finding · T0.1 — the repo already had the fix; the host never got it

Installed `displaylink-1.14.16-2`. Playbook pinned `v6.3.0-1` / evdi **1.15.0**,
bumped in `588d1ae` (Plan 00058). Upstream evdi 1.15.0 release notes (2026-07-01):
*"Preliminary support for linux kernel 7.2"*.

So this was **deployment drift, not a repo bug**. Verified before running anything:
GitHub's latest release is `v6.3.0-1` (so the play's version assert would pass), and
`mokutil --test-key` confirmed the MOK key is already enrolled (so no Secure Boot
reboot dance needed).

## 11:24 · finding · P2 — why every QA gate stayed green

The thing worth keeping from this incident. Two gates exist and both were correct:

- `check-pinned-versions.bash` — **does** track displaylink (manifest rows for
  `displaylink_version` and `evdi_version`), but compares repo pin vs *upstream
  latest*. Pin was current, so: PASS.
- `qa-deployed-drift.bash` — compares repo scripts vs deployed copies, scoped to
  `files/home/.local/bin/`. Packages are out of scope entirely: PASS.

Nothing compares the repo pin against **what is installed on this host**. That is
the axis that failed, and it is unwatched.

## 11:40 · thought · T5.1 — a number I asserted and then doubted

I told the user the large wallpaper costs ~131 MB of texture *per monitor*, ~520 MB
across four. On reflection mutter likely caches the decoded image by filename
(`MetaBackgroundImageCache`) and shares one texture, scaling per-monitor on the GPU —
which would make the true cost paid once, not four times.

Dispatched research to settle it from the mutter/gnome-shell sources rather than
guess twice. Recorded here because the fix in T5.3 (per-monitor pre-scaled cache)
only makes sense if the per-monitor reading is true, and it probably is not. The
oversized wallpaper is still worth fixing for decode time on every background
reload; the *reason* needs to be the real one.

## 12:05 · blocker · T5.2 — wrote a local hardware fact into a public repo; reverted

Drafted a wallpaper-scaling block for `play-gsettings.yml` carrying:

```yaml
    # Generous headroom over the widest panel this laptop drives (3072px), so the
    # GPU is never upscaling. Raise it if a larger display is added.
    wallpaper_max_geometry: "3840x2560"
```

The user caught it before deploy. It is a **host-specific runtime fact written
down as a repo constant**, in a public repo that provisions arbitrary Fedora
desktops — anyone with a display wider than 3840 gets an upscaled, blurry
wallpaper generated for them by our own play. The comment states the defect
outright ("this laptop"), which is what makes it a good marker for the class:
*if the justification for a literal names this machine, the literal is wrong.*

Reverted; `play-gsettings.yml` is byte-identical to HEAD and was never deployed.

Correct design when T5.2 is picked up:

- Target geometry is **derived on the host at run time** from the connected
  outputs, never a literal. An explicit override var may exist, defaulting to
  auto-detect — the default must not be a number.
- Enumerating `/sys/class/drm/*/status` + `modes` is looping and parsing, so per
  `playbooks/CLAUDE.md` it belongs in a stdlib-only TDD'd helper under
  `helpers/`, invoked via `command:` + `argv:` — not an inline shell block.
- Placement is open: the block also added `ImageMagick` to a **core** play, so
  every fresh install pays for a wallpaper feature. An optional play is the
  likelier home. Unanswered by the user at time of writing.

## 12:08 · thought · P5 — do not oversell what scaling fixes

Related to the above, and worth stating before T5.2 is built: the research found
**two open upstream mutter bugs** (`#4767`, `#4935`) that produce the same black
background independently of image size, plus an apparently unreported sticky
variant. Scaling the wallpaper only shortens the decode (342–466 ms → ~73 ms) and
so improves the odds on *one* GC race. It is a mitigation, not a fix, and the plan
should not claim otherwise — if the backgrounds still blank after T5.2 deploys,
that is consistent with the upstream bugs, not evidence that T5.2 failed.
