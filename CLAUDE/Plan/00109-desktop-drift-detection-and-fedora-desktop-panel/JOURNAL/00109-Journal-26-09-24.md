## 07:59 · finding · T3.x   — third VM run passes dnf, stops at a doubled-/boot grubby readback

The third run of `server-host-health-kernel-change` got past dnf: the dnf5 fix holds. Prepare
then stopped at the grubby readback. The bridge returned this reason:

> grubby reports /boot/boot/vmlinuz-<target> as the default, not /boot/vmlinuz-<target>

`grubby --set-default /boot/vmlinuz-<target>` succeeded, so the entry was found and
selected. It is the readback that differs. Where `/boot` is on the root filesystem, the
boot entry's own path already starts with `/boot`, and grubby prefixes it again when it
prints. So the doubled path is the same entry spelled another way, not a wrong one.

- **Fix:** the fixture accepts exactly the two spellings of the selected entry,
  `<boot>/vmlinuz-<target>` and `<boot>/boot/vmlinuz-<target>`. Anything else still
  refuses. The recorded `PREPARED_DEFAULT_KERNEL` keeps grubby's own words.
- **Tests:** in `scripts/test-vmtest-kernel-selection.bash`, a stub mode now models the
  doubled readback.
  - Case 8b, the doubled form of the selected entry, was RED and gave the guest's exact
    message. It is GREEN after the fix.
  - Case 8c, the doubled form naming another kernel, is refused.
  - The suite passes 17 of 17.
- **What still proves it:** check 7, the guest rebooting into a different kernel.

Next: `play-vm-test-lab.yml`, run by this plan's deploy in `meta-deploy.bash`, then the

failure stops the play instead of reading as unowned. The rpm probe runs in check mode
too, so a `--check` run lists what would go. Versions are discovered, not listed.
