## 17:06 · decision · — — a sibling tool, not a flag, and the owner picked the axis

Asked for by the owner mid-session: "i want a way to freeze/thaw lxc containers — exact
same concept as podfreeze — could even try to combine into podfreeze as another group
maybe?"

Established before offering options, rather than assumed:

- This repo runs **classic LXC 4.x** from the `ganto/lxc4` Copr
  (`playbooks/imports/play-lxc-install-config.yml`), **not** LXD or Incus. So the verbs
  are `lxc-freeze` / `lxc-unfreeze`, not `lxc pause`.
- It is **rootful**. `files/var/local/docker-in-lxc` — this repo's existing LXC tool —
  uses `sudo lxc-info`, `sudo lxc-start`, `sudo lxc-stop` throughout, and the install
  play's own `lxc-ls` sanity check runs under `become: true`. Podman here is rootless and
  `podfreeze` never escalates.
- **Both** `play-lxc-install-config.yml` and `play-podman.yml` are core imports of
  `playbook-main.yml`, so on any host that has run main, both engines are present. That
  is what decides the deployment question in Task 3.1: neither tool needs a guard the
  other does not, so one play owns both rather than two plays copying four tasks each.

Three options went to the owner with the trade-offs named: combine and rename to
`cfreeze`; combine and keep the `podfreeze` name; or a separate `lxcfreeze` sharing a
library. **Chosen: the separate tool.**

The deciding cost was not the name but the `sudo`: a group row cannot print `FREEZE 3`
without first reading `/var/lib/lxc`, so a combined tool would prompt for root on every
menu open — including for someone who only wanted Podman. Keeping them apart keeps
`podfreeze` rootless and keeps the name honest.

## 17:38 · finding · T1.2 — errexit arrives by sourcing, and the suite passed by luck

`scripts/test-lxcfreeze.bash` sources the shipped tool to reach its functions. The tool
carries `set -euo pipefail`, and sourcing applies that to the test's shell — so the suite
runs under errexit regardless of its own `set -uo pipefail`.

It passed anyway, and that is the part worth recording: every negative case happens to
sit inside an `if` condition or a `$( )` substitution, both of which errexit exempts. So
the suite was green for a reason nobody had chosen. Plan 00109 lost a day to the same
exemption in the other direction — a function moved into a command substitution and its
failure stopped being fatal.

Turning errexit back off was the obvious fix, and `R-ERROR-HIDING` blocks it, correctly.
The better fix was the opposite one: keep errexit, check that it arrived — which also
catches the tool losing its fail-fast prelude — and write the constraint down where the
next case gets added. The mutant "lxcfreeze loses its fail-fast prelude" is killed by
that check and by nothing else.

## 20:05 · finding · T4.1 — podfreeze cannot be sourced, and cannot be run either

Both obvious routes into `podfreeze` are closed, which is why this suite looks different
from `test-lxcfreeze.bash`:

- **Sourcing it whole** is out. It has no `BASH_SOURCE[0] == $0` dispatch guard, so its
  argument loop and main body run at top level — a `source` would parse the SUITE's
  arguments, fall into `assert_on_host` and exit.
- **Running it as a subprocess** is out too. `assert_on_host` dies when
  `/run/.containerenv` exists, which it does in here. Black-box CLI testing is not
  available on this machine at all.

So only the definitions are sourced: everything above the first executing statement, which
is the `while [ "$#" -gt 0 ]; do` line. The cut is found by matching that line's own text
with awk, never by line number — a number slides onto the wrong side of the boundary as the
tool grows, and the failure mode of that is sourcing real execution, silently. The extracted
prefix is run through `bash -n` before it is sourced, so a cut that landed mid-function is a
named failure rather than a syntax error hundreds of lines into a temp file.

## 20:31 · finding · T4.1 — two defects in the suite, both found by mutants not by the run

183 cases went green on the first run, which proves nothing on its own. 15 mutants were
built against a scratch copy of the tool, and two of them exposed defects in the SUITE:

- **`select_network` mutated to `exit 1` killed the run silently.** The probe that
  distinguishes return-from-exit was written as `net_probe="$(…)"`, and a bare assignment
  whose command substitution fails takes its status — so errexit aborted before any report
  printed. The `$( )` exemption the header warns about applies to an ARGUMENT, not to an
  assignment. Fixed by wrapping it in `if !`, and by gating the cases that call the function
  in *this* shell behind the probe's result, so a tool that exits produces a named failure
  and a printed summary instead of a dead run.
- **`inventory_index_of` mutated to substring matching corrupted its own report.** `notok`
  let the predicate's stdout reach the terminal, so a failing case printed
  `0  FAIL  a prefix of a real name does not match` — a failure report that breaks its own
  format, and would break any parser reading it. Stdout now goes to a file and is reported
  as a detail line.

The other 13 were killed cleanly, each by cases that name the right thing: the cardinality
proxy `identity_axis_discriminates` warns about, `unlabelled_ccy_names` keyed on empty

## 20:36 · finding · T4.1 — two things pinned that look like bugs, and are not fixed

Recorded as current behaviour with the case commented as pinned-not-endorsed, because this
task is a statement of what the tool does today and Task 4.2 is the place to change it:

- **`select_network`'s existence check is a REGEX match.** `grep -qx -- "$net"` with no
  `-F`, so `podfreeze --network 'podma.'` matches a network called `podman` and passes the
  check. `select_identity` does the same job three hundred lines later with `grep -qxF`. The
  user-visible effect is that a typo'd network with a metacharacter in it reaches the filter
  query and comes back empty, so they get "Nothing in that group" instead of the "no such
  network" error with the list of real ones.
- **`identity_matches` word-splits the ssh-key haystack unquoted.** `for word in $have` is
  pathname expansion as well as word splitting, so a label value of `*` expands against the
  working directory and every file there becomes a key that session appears to hold. Pinned
  in a controlled temp directory so the case does not depend on where the suite is run.

## 20:55 · decision · T4.1b — fix the two defects before the extraction, not after

Both bugs the pin found sit in functions Phase 4 is about to move. Fixing them first
costs nothing and buys a much stronger guarantee for Task 4.2: the extraction becomes a
pure move, whose claim is "no behaviour change at all" rather than "no behaviour change
except these two, which changed for unrelated reasons". Mixing a behaviour fix into a
refactor is how a refactor stops being reviewable.

Reproduced both before touching anything, rather than taking the report on trust:

```
'podma.' matched 'podman'            (grep -qx, no -F -> regex)
-F correctly did not match
one label value of '*' became 2 'keys'  (unquoted for-loop, in a dir of 2 files)
```

`grep -qx` -> `grep -qxF`, matching what `select_identity` already did. The unquoted
`for word in $have` -> `read -r -a words`, which splits on IFS without pathname
expansion. Checked the replacement against an empty haystack under errexit before
committing to it — `read` returns 0 on a here-string, so the function does not abort
the shell on a session with no keys.

**The pins were flipped, not deleted.** Each case now asserts the fixed behaviour, and
each gained a companion proving the fix tightened the check rather than broke it: the
literal network name is still accepted, and a genuine multi-key label still matches its
first and last members and still refuses one it does not hold. A fix that made
`identity_matches` always return 1 would pass the glob case and fail these.
