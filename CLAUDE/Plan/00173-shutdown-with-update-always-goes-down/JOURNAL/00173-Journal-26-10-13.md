## 11:25 · finding · —

Why the cc session in this repo was not shown the shutdown warning: by design, nothing on the host shows it. Not a regression from this plan.

The chain, read from the code:

- `shutdown-with-update` warns through `ccy-sessions notify going-down`, which lists the sessions on CCY's tmux server (ccy and cc both run there) and runs each project's daemon CLI once: `hooks-daemon signal <kind> --minutes N --all-sessions`.
- The daemon's `signal` (`utils/operator_signal.py`) only writes one `<session>.operator-signal` file per session that has a context sidecar in the project's `untracked/context-sidecar/`. A host cc session in this repo has one (the status line writes it), so a file was very likely written for it too.
- The only reader of that file is the ccy supervisor (`.claude/ccy/claude-supervise.py`, `load_operator_signal`), which ccy's entrypoint wraps claude in. It reads only signals for its own sessions. `cc` (`files/var/local/claude-code/cc`) runs `claude "$@"` with no supervisor. So no process on the host ever reads the signal or shows it to the agent.
- A `claude` started outside `cc` is not on CCY's tmux server, so its project is not even signalled unless a ccy or cc session is open in it too.

What was wrong on our side: the code and docs claimed otherwise. ccy-sessions said one delivery per project reaches "ccy and cc alike", and shutdown-with-update's help said it warns "every running ccy/cc session". Neither is true for cc.

Fix, on this branch: each warning from ccy-sessions (and so shutdown-with-update's rehearsal and both warnings) now names every cc session on stderr, under "Not shown the warning", so the person running it knows to finish or hand off in those themselves. Delivery is unchanged: the project is still signalled, which reaches any ccy session in it, and strict mode does not refuse over a cc session (it never did). The comments, the --help text and docs/ccy.md now say what actually happens. Tests: scripts/test-ccy-sessions-reboot.bash has a new section and one new desktop check, all passing.

Showing the warning in a cc session needs a reader on the host. Two routes, neither small, both for the owner to choose: run the project's supervisor in cc the way ccy's entrypoint does (it carries ctrl+z and plugin behaviour, so it is a feature in itself), or a daemon handler that shows a pending operator signal on the session's next hook event (an upstream daemon change, and it only reaches a session when it next does something, which an idle one does not).
