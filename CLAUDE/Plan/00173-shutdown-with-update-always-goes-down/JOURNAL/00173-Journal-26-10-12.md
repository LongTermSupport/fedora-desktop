## 08:52 · finding · P1   — root cause and fix

Root cause: `shutdown-with-update` rehearses `ccy-sessions notify going-down --dry-run`
before updating and exits on its failure. `check_projects` counted every tmux session on
the ccy server as live, including a `ccy-*` session with no container (still at ccy's
startup prompts). With no container to route through, it fell back to the project's host
hooks-daemon CLI, which has no venv for a ccy-only project, so `signal --help` failed and
the whole run refused before `dnf`.

Fix: `check_projects` now reads the container table once and leaves out any `ccy-*`
session with no container, naming it on stderr. `shutdown-with-update` reads the
provisioning profile (recorded by `play-basic-configs.yml` from the existing
`provisioning_profile` variable): desktop goes ahead past failed or hung warnings
(`timeout` on each ccy-sessions call) and forces past inhibitors; server or
`--strict-sessions` keeps the strict behaviour.

Assumed for the owner: a failed `dnf upgrade` still stops the run on a desktop.
Tests: `scripts/test-ccy-sessions-reboot.bash` passes in full, with new desktop and
strict cases.

## 09:30 · decision · T1.5   — a failed update step does not keep a desktop up

The open question on a failed `dnf` is settled by the owner's original words: "shutdown
with update by default should ALWAYS do a shutdown — it can wait a grace period or
whatever, but it MUST do the update and shutdown ... desktop mode should do what I tell it
to do."

On a desktop every update step now goes on past a failure, `dnf` included. Each failure is
printed to stderr and recorded with `logger -t shutdown-with-update -p user.err`, and a
one-line summary of the failed steps is printed and journalled just before the power
action. A firmware step's exit 2 (nothing to do) is not counted as a failure. A strict run
(server profile, or `--strict-sessions`) still exits 1 on a failed `dnf` with the machine
up. The startup refusals stay fail-fast.

Tests added for a desktop with a failing dnf (powers off, journals the failure and the
summary), a server and `--strict-sessions` with a failing dnf (exit 1, nothing goes down),
and a clean run (nothing journalled).

## 09:51 · action · —   — shutdown-with-update problems reach the panel after the next boot

Task 1.6, shutdown-with-update problems reach the fedora-desktop panel after the next boot.

Mechanism chosen: the existing host-health post-boot probe, not a new state file. The
panel already renders `post-boot-health` from the status document that
`host-health.service` writes at each graphical login, and that section is the one the
document marks boot-scoped. `probe.collect` now also runs
`journalctl -b -1 -t shutdown-with-update -p err -o cat` and turns any lines into one
finding (all lines joined, plus `journalctl -t shutdown-with-update -b -1 --no-pager`).
Previous boot only: a failure shows for the boot after it and then goes, with no state to
clear.

A second probe, the previous boot's newest PID 1 line, guards the empty answer. A user
outside the groups that may read the system journal gets exit 0 and no lines, which is the
shape of a clean run, so an empty PID 1 answer makes the shutdown check unchecked rather
than clean. A host with no previous boot in the journal (first boot) is unchecked too.

Script side: a `refuse` helper journals every refusal that leaves the machine up (startup
refusals, strict dry-run, strict dnf, strict warning failure, strict reboot refused,
shutdown not forced), and the EXIT trap, now armed from the start, journals any other
non-zero exit by its status (a forced power action that failed). Usage errors (64) and
Ctrl-C (130) are not journalled. The trap still withdraws the warning once sessions were
warned, and journals a withdrawal that could not be delivered.

Deploy: the script through `play-basic-configs.yml`, already in this plan's deploy.bash.
The collector runs from the checkout, so it needs no play.

Tests: scripts/test-ccy-sessions-reboot.bash gains journal checks for each refusal path, the
trap path, and a usage error that journals nothing (283 passed, 0 failed).
tests/helpers/host_health/test_probe_results.py and test_probe.py cover the classifier and
the probe argv (all host_health suites pass).
