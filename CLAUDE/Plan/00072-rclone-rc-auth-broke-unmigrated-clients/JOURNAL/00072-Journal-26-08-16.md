## 09:17 · finding · P1 — the premise Plan 00067 was built on is false

Reported symptom: "ftp camera copy does not seem to be working, I think recent
changes have broken rclone rc". Confirmed in one probe. The mount's RC refuses

```
$ rclone rc --url=http://localhost:5572 core/stats
{
	"error": "failed to decode response: json: cannot unmarshal number into Go value of type rc.Params: 401 Unauthorized",
	"path": "core/stats",
	"status": 401
}
```

Plan 00067's own comments — repeated in `play-rclone.yml`, `ftp-camera` and
`rclone-cache-warm` — assert the opposite:

> It also bought very little: vfs/stats and core/stats — which is all
> ftp-camera --copy, rclone-tail and rclone-cache-status need — are served
> WITHOUT auth. Only vfs/refresh (rclone-cache-warm) and core/stats-reset are
> gated […]

rclone gates the whole rc surface once `--rc-user`/`--rc-pass` are set. That
single wrong belief is why only one of four clients was migrated.

Nothing is wrong with the mount, the credential, or 00067's *deployment* — the
authenticated call returns 200 and the unit has been up since 08-08. The
breakage is entirely on the client side.

## 09:25 · decision · T2.1 — one sourced library, not a fourth copy of the block

The defect IS the divergence, so pasting the credential block into the two
missing scripts would reproduce its cause. New sourced library
`files/home/.local/bin/rclone-rc-auth.bash` owns the lookup; all four clients
call `rclone_rc` through it.

Two deliberate choices inside it:

- **No unauthenticated fallback.** `ftp-camera` previously built an empty auth
  array when the credential file was unreadable and called the RC anyway. That
  is exactly the shape that turned a 401 into "remote control not responding".
  A missing credential is an IaC gap: fail, and name the play.
- **Credentials via `RCLONE_USER`/`RCLONE_PASS`, not argv.** Verified on the
  host that rclone's client honours the env form, so the password no longer
  appears in `ps` output. (Server side stays `RCLONE_RC_USER`/`RCLONE_RC_PASS`
  — the two are differently named and easy to confuse.)

## 09:31 · finding · — — deploy.bash's in-flight guard had a false positive

00067's `deploy.bash` guards with `pgrep -af 'ftp-camera'`. That is a bare
substring match against every process's full command line, so it matches any
shell that merely *mentions* ftp-camera — including the one invoking the
deploy, and any terminal or agent discussing the problem. Hit it live: the
guard fired with nothing running.

00072's copy anchors the pattern to a path component or line start
(`(^|/)ftp-camera([[:space:]]|$)`) and excludes `$$`/`$PPID`. The archived
00067 script still carries the loose form; noted rather than edited, since
that plan is Complete and its script will not run again.

## 09:45 · finding · — — 82 files from 08-15 are local-only

Not a claim about *this* plan's fix, a fact about the library. Comparing the
sorted upload tree against the mount, per day:

```
2026/08/03   local=482   remote=482
2026/08/07   local=44    remote=44
2026/08/09   local=14    remote=14
2026/08/13   local=58    remote=58
2026/08/14   local=100   remote=144
2026/08/15   local=82    remote=0
```

Everything through 08-14 reached the remote; the 82 files from 08-15 did not.
`--copy` does not delete its source, so files remaining under
`/srv/ftp-camera` is normal and not itself evidence of failure — the remote
count is.

Note the earlier days landed *despite* the RC being broken since 08-08: the
`--async-copy` per-file path writes through the filesystem and never touches
the RC, and `--push` uses `rclone copy` directly. Only `--copy` (and
`--async-copy`'s final wait) needs the RC. That is consistent with the user
noticing "copy" specifically.

Deliberately NOT shipping them automatically: `--copy` does an unconditional
`cp -r` of the whole 780-file tree through the mount, so it would re-upload
everything, not just the 82. That is a bandwidth and cache decision for the
user, not a side effect of a bug fix. `--push` (incremental `rclone copy`)
would ship only the missing 82.

  change; left unstaged rather than committed or reverted.

The should-fix items worth recording, because most are the SAME defect class
this plan is about — verification vouching for more than it tests:

- `acceptance.bash` checks 4 and 5 **passed blind**. Both `rclone-cache-status`
  and `rclone-tail` print "No rclone mounts found." and `exit 0`, so on a host
  with no mount the checks would have reported PASS having made no RC call at
  all. Now: a `[0]` precondition aborts without a mount, and each check demands
  positive evidence (`cache:` figures; a per-mount state word) rather than mere
  absence of an error.
- Check 3's bypass regex `(^[[:space:]]*|[;&|(]|\$\(|!…)` missed `&& rclone rc`,
  `|| rclone rc` and `; rclone rc` — the separator had to be immediately
  adjacent. Moved the whitespace after the separator class and pinned it with a
  10-case fixture table (6 must-match, 4 must-not, all green).
- `rclone-cache-warm` was migrated but only **grep-covered** — and `vfs/refresh`
  is the one endpoint 00067 correctly identified as gated, so it is exactly the
  call a grep would vouch for while it was broken. Added check `[6b]`, a real
  authenticated `vfs/refresh` (read-only: it re-reads directory listings, moves
  no data).

And three genuine bugs in the new code:

- `deploy.bash` aborted **silently** under `set -euo pipefail` when the pgrep
  filter emptied — i.e. in the normal case where only self/parent matched. The
  `grep -v` exits 1, the assignment fails, the script dies with no message and
  no plays run. Reproduced in isolation, then guarded on the status explicitly.
  Note this is a bug I introduced *while fixing* 00067's loose guard.
- `qa-deployed-drift.bash` had no linked-worktree escape hatch: reviewing a
  branch in `.claude/worktrees/` would compare that branch against whatever the
  main checkout deployed — an unclearable hard failure, since you cannot deploy
  a review branch to satisfy QA. Now skips when the git dir differs from the
  common git dir.
- `owning_play()` only matched a literal `src:` path, so loop-deployed scripts
  (`src: …/{{ item }}` + `loop: [lan-scan, qnap-finder]`) were reported as
  "may be orphaned" — pointing the reader away from a play that does exist.
  Added a second tier; verified it now resolves `lan-scan` and `qnap-finder` to
  `play-network-tools.yml`.

Also fixed: `--help` died before printing when the library was absent in the
three rclone helpers (InteractiveScripts rule 10 — help must work on the broken
machine that needs diagnosing); all four now use `ftp-camera`'s stub pattern,
verified by running each from a directory with no sibling library (4/4 rc=0).
`triage.bash` passed the RC password in argv, visible in `ps`; switched to the
env form the library already uses. The stderr scratch file in `ftp-camera`'s
wait loop leaked on Ctrl+C (the `--copy` path clears the script's EXIT trap
first); given a local `INT`/`TERM` trap. `qa-all.bash` swallowed the drift
gate's success line — a gate whose only visible output is a failure is
indistinguishable from one that is not running, which is this plan's own theme.

Corrected a claim in `PLAN.md`: the risk table said a fifth RC client would be
