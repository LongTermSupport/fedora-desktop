## 23:29 · decision · T3.1 — a denylist, not an allowlist, and why the difference matters

The runner's `card1-Virtual-1` is `connected`, advertises modes, and has an `edid` that
reads zero, so it satisfied every condition the scan tested. The fix is not to excuse a
zero read — it is that the test's inference was never sound for that connector. "Connected
and advertising modes ⇒ it has an EDID" is a statement about a **physical display link**:
the EDID comes from the monitor across it. A `Virtual` connector is a framebuffer the
driver invents; there is no monitor and no link. Production never looks at one —
`_drm_head_states()` globs `card*-DVI-I-*`, the evdi heads — so the unsound inference is
the test's alone.

Two ways to express that, and the choice is load-bearing:

- an **allowlist** of link-carrying types (DP, HDMI-A, eDP, DVI-I, …) — an unrecognised
  type is skipped, so a machine with only new connectors runs a test that checks nothing
  and says OK;
- a **denylist** of linkless types (`Virtual`, `Writeback`) — an unrecognised type is
  asserted against, so a new linkless type reddens CI and someone looks at it.

Took the denylist. The allowlist is the "skip and warn" shape one level of indirection
away, and this plan's own Risks section already names the hazard: *"a skip that widens too
far restores that hole."* A red CI run is a cost; a green one that checked nothing is the
thing being fixed.

The skip also names what it ignored, rather than skipping silently:

```
skipped 'no connected DRM connector with a display link under /sys/class/drm;
         ignored linkless connector(s): .../card1-Virtual-1'
```
