### Ruled out, recorded so Task 1.3 does not repeat it

The two `host_health` failures looked like they had an obvious cause — a runner has never run a
play, so the empty-ledger finding fires and the machine is not "clean". `login_report` resolves
the ledger through `ledger.ledger_dir(os.environ, home)` with `home = os.path.expanduser("~")`,
so pointing the environment at an empty sandbox should reproduce it:

```
env HOME=$tmp XDG_DATA_HOME=$tmp/share XDG_STATE_HOME=$tmp/state \
  python3 -m unittest -v <the two tests>
→ Ran 2 tests ... OK
```

Both still pass. The hypothesis is wrong and the cause is something else. Worth saying plainly
because the CI failure text quotes the empty-ledger message verbatim, which makes the wrong
answer look like the right one.

### The two that ARE explained

`session_bus.current()` reads `os.environ` directly and returns `source="environment"` whenever
`DBUS_SESSION_BUS_ADDRESS` is set. The test unlinks a socket inside its own temp runtime dir but
never clears that variable, so on a machine that has one the production code takes the
environment branch and the `dbus-run-session` fallback the test asserts is never reached. The
test passes here only because this container happens to have no session bus.

The DisplayLink pair intends to skip in CI — its docstring says so. The runner defeats the guard
rather than the guard being absent: `card1-Virtual-1` reports `connected`, has modes, and has an
`edid` file, so it satisfies every condition `_connected_connectors_with_modes` tests, and then
reads zero bytes. That is the shape the widened predicate in Task 3.1 has to recognise, without
also excusing a real connector that reads zero — which is the defect the test exists to catch.

### Why the docs half cannot ever pass in CI

`helpers/docs/link_check.py` lists `.claude/hooks-daemon/` in `_EXCLUDE_PREFIX`, which keeps
files *in* that tree out of scope. The existence check for link targets does not consult that
list, so eight tracked `.claude/rules/*.md` pointers into the tree are checked for a target that
is gitignored and therefore absent from every clean checkout. Those pointers arrived in
`0015c886`, five days after the last green run — so they are a second cause layered on top of
whatever broke it first, which Task 1.2 still has to name.

## 23:15 · finding · T1.3 — both host_health failures, and a bomb due in thirteen days

Delegated to a qa-reviewer with the falsified hypothesis stated up front so it would not be
re-run. Both causes determined and reproduced byte-exactly. **Neither is the ledger, and
neither is a production defect** — both are tests reading host state they should have been
given. Production is doing its job in each case: reporting a kernel mismatch and reporting
that systemd could not be asked is what these modules exist for.

**`test_login_message`** hardcodes `KERNEL` and `NOW` into its fixture while `main` read
`os.uname().release` and `repo.utc_now()`. Every other test in the file passes both through
`render()`; `main` was the one entry point that could not be given them. On a runner the
kernel differs, `is_boot_stale` fires, and the output is the CI string.

And in the same test, independently: `NOW` against the real clock means the document ages.
`STALE_AFTER_DAYS = 14`, the stamp is `2026-09-14`, so **this was going to go red on every
machine on 2026-09-28** — CI, container, host, all of them. That is not a CI problem at all;
it was thirteen days out and nobody was looking for it.

Both fixed by giving `main` the same two seams the rest of the module already has, defaulting
to the real clock and the real kernel. Two new cases assert the branches that were being taken
by accident: a document from a different boot is not clean, and one past the staleness window
is not clean. Verified by running the class with `probe.running_kernel` faked to
`6.11.0-1018-azure` and `repo.utc_now` faked to `2026-12-25` — 5/5 pass, where before either
fake alone reproduced the failure.

**`test_handoff`** asserted the prose `"could not run"`, which in this container comes from the
two systemctl probes failing because there is no systemd here. Its sibling case says so
outright: *"This container always has findings — no dkms, no systemd bus — which is what makes
it a usable fixture for the write path."* True here, false on a runner: `ubuntu-latest` has
systemd as PID 1 with no failed units and no `/var/lib/dkms`, so both probes take their
deliberate silent branches and the prose never appears. The class now supplies its own finding
through a patched `probe.collect` and asserts on that, which is what
`TestTheSplitDoesNotGuessFromWording` in the same file already argues for. Verified against an
emulated runner: systemctl ok, dkms absent, foreign kernel, future clock — 3/3 pass.

That accounts in full for the `helper-tests` half of the CI redness. The remaining three
failures are the DisplayLink pair and the dbus fallback, which are Tasks 3.1 and 3.2 and are
untouched — as is Cause A, the docs gate, which is still behind the Task 2.1 decision.
