### Ruled out, recorded so Task 1.3 does not repeat it

The two `host_health` failures looked like they had an obvious cause — a runner has never run a
play, so the empty-ledger finding fires and the machine is not "clean". `login_report` resolves
the ledger through `ledger.ledger_dir(os.environ, home)` with `home = os.path.expanduser("~")`,
so pointing the environment at an empty sandbox should reproduce it:

```
env HOME=$tmp XDG_DATA_HOME=$tmp/share XDG_STATE_HOME=$tmp/state \
  python3 -m unittest -v <the two tests>
→ Ran 2 tests ... OK
```

Both still pass. The hypothesis is wrong and the cause is something else. Worth saying plainly
because the CI failure text quotes the empty-ledger message verbatim, which makes the wrong
answer look like the right one.

### The two that ARE explained

`session_bus.current()` reads `os.environ` directly and returns `source="environment"` whenever
`DBUS_SESSION_BUS_ADDRESS` is set. The test unlinks a socket inside its own temp runtime dir but
never clears that variable, so on a machine that has one the production code takes the
environment branch and the `dbus-run-session` fallback the test asserts is never reached. The
test passes here only because this container happens to have no session bus.

The DisplayLink pair intends to skip in CI — its docstring says so. The runner defeats the guard
rather than the guard being absent: `card1-Virtual-1` reports `connected`, has modes, and has an
`edid` file, so it satisfies every condition `_connected_connectors_with_modes` tests, and then
reads zero bytes. That is the shape the widened predicate in Task 3.1 has to recognise, without
also excusing a real connector that reads zero — which is the defect the test exists to catch.

### Why the docs half cannot ever pass in CI

`helpers/docs/link_check.py` lists `.claude/hooks-daemon/` in `_EXCLUDE_PREFIX`, which keeps
files *in* that tree out of scope. The existence check for link targets does not consult that
list, so eight tracked `.claude/rules/*.md` pointers into the tree are checked for a target that
is gitignored and therefore absent from every clean checkout. Those pointers arrived in
`0015c886`, five days after the last green run — so they are a second cause layered on top of
whatever broke it first, which Task 1.2 still has to name.
