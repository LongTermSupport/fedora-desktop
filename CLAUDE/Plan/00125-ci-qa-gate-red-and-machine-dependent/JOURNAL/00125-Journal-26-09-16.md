## 01:03 · finding · T3.4 — the skip count read the whole capture, and both decoys beat it

The round-3 prompt I wrote asked one question about my own round-2 fix: the skip count came
from `[[ "$helper_out" =~ skipped=([0-9]+) ]]` against the **entire** captured output, and
`=~` takes the first match anywhere. A line earlier in the capture containing the text would
win the match ahead of `unittest`'s result line. I wrote in the prompt that I had not tested
it. Measured both ways before changing anything:

```
OLD code, decoy warning line : 99 (should be 2)
OLD code, decoy skip reason  : 42 (should be 1)
```

Reachable, then — and by the most ordinary route imaginable. A skipped test in this suite
prints its own reason, and this plan's Task 3.1 *wrote three of those reasons*. One of them
mentioning a count would have silently replaced the number on the stage line. The failure
mode is the one this whole plan is about: a line that looks like a measurement and is not,
with nothing to distinguish it from the real thing.

The count now comes from `unittest`'s own `^(OK|FAILED)` result line — the only place it is
authoritative — and is only then matched:

```
OK                                                         -> 0
OK (skipped=1)                                             -> 1
OK (skipped=1, expected failures=1)                        -> 1
FAILED (failures=1, skipped=3)                             -> 3
decoy: warning line says skipped=99, result says 2         -> 2
decoy: a skip REASON contains skipped=42                   -> 1
```

Six shapes, four real and two adversarial, all correct. A real local run still reports
`helper-tests: Ran 1456 tests, 1 skipped`, so the hardening is not paid for with a
regression.

**The decoy fixtures test the impossible direction.** I fixed `helper_test_summary` with a
"last match wins" rule and three fixtures that put the decoy BEFORE unittest's summary.

```
1: .
3: Ran 1 test in 0.000s

=> helper_test_summary said: Ran 3 tests   (truth: Ran 1 test)
```

unittest writes its summary to **stderr**; a test's `print` goes to **stdout**, which Python
**block-buffers** to a pipe and flushes at process exit. `qa-all.bash` captures through a

described a world where a stdout decoy arrives early, which cannot happen — the exact defect
this plan is named after, committed by me inside the test written to prevent it.

Neither first nor last is right: a *stderr* decoy arrives before, a *stdout* decoy after.
What holds is unittest's own structure — the `Ran` line most recently seen **when the result
line arrives**, which anchors on the same `^(OK|FAILED)` that `helper_skip_count` already
trusts. Both readers now depend on one fact about the format instead of two. Three fixtures
replaced with the real orderings, plus the mirror case for `helper_skip_count` (a
result-shaped decoy flushed after the real one). Gate: 23 cases.

Three comments claiming *"unittest does not buffer stdout"* were the same error stated as

## 03:10 · decision · T4.4 — three revisions chasing a match rule, when the fix was to stop merging the streams

Round 6: no blocking findings, and it broke my ordering fix twice. Both reproduced here
before acting.

**"A stdout decoy can never precede the result line" is false, and I should have seen it.**
Block buffering flushes when the buffer is FULL, not only at exit. So:

```python
print("Ran 3 tests in a scenario"); print("OK (skipped=99)"); print("X" * 9000)
```

pushes the decoy past the 8KB boundary and it lands *ahead* of unittest's summary. Measured:
`helper_skip_count` answered **99** for a run whose real answer was **0**. The fixture I
added last round passed only because the real result line happened to carry a count; against
a bare `OK` the decoy wins.

And the two readers had drifted apart — `helper_test_summary` effectively used the *last*
result line, `helper_skip_count` the *first*. On the capture above they disagreed with each
other, which is a worse state than either being wrong.

**The fix is not a cleverer rule. There isn't one.** A small decoy flushes at exit and lands
after; a padded decoy flushes early and lands before. Both are reachable, so no first-or-last
rule over a merged stream can be right. I spent three revisions looking for one.

`qa-all.bash` captured with `2>&1` and created the ambiguity itself. unittest writes its
summary to **stderr**; `qa-helper-tests.bash` writes its progress line to **stdout**; a
test's `print` goes to stdout. **Parsing stderr alone deletes the entire class.** On stderr
unittest's summary is always last — a test writes during the run, the summary after every
test finishes — so "last match wins" becomes sound, and both readers can use it, symmetrically.

The same attack against the new code:

```
stderr-only capture:  Ran 1 test in 0.000s / OK
helper_test_summary: Ran 1 test   (truth: Ran 1 test)
helper_skip_count  : 0            (truth: 0)
```

The decoy is not defeated; it never enters the parse stream.

**And I introduced a leak while fixing it.** My first version added
`trap 'rm -f "$helper_err_file"' EXIT` — a second `trap ... EXIT` **replaces** the first in
bash rather than adding to it, so the seven jq temp files would have leaked on every run.
Caught by reading the script rather than by any gate, which is worth noting: nothing in QA
checks for a clobbered trap. Folded into the single existing trap with a comment saying why
there is only one.

Round 6 also confirmed, independently, that the masking figures at `4ada2342` are right — it
computed **all 21 intermediate values** rather than the two named commits, and found the
series monotonic 5→25 with maximum 25. So the arc stands. `"born unexecuted"` is supported by
11 CI runs across the window, all aborting at the same gate; it is evidence, not a flourish.
Option (d)'s coverage line is confirmed necessary — the bidirectional inventory is

labelled `cedc9426~1`, the high-water mark, rather than by a phrase that implied something

## 03:58 · decision · T4.4 — the fifth reader is not a reader: the counts were never in the text

I dispatched round 7 and then, while it ran, went to check its first question myself —
whether "unittest's summary is always last on stderr" is actually true. It took one attempt
to break. A test that does `atexit.register` on a function printing to `sys.stderr` puts its
text *after* unittest's summary, because atexit handlers run at interpreter shutdown:

```
Ran 1 test in 0.000s
OK
Ran 3 tests in 9.999s
OK (skipped=99)
```

Both readers then answered `Ran 3 tests` / `99` where the truth was `Ran 1 test` / `0`. The
fourth revision fails in exactly the way the first three did.

What I got wrong was not the match rule, four times over. It was the belief that there was a
match rule to find. A test can write anything to either stream in any order — that is the
whole population, and no rule over it can be sound. Last round I thought separating the
streams was structural rather than another guess; it was narrower than a guess about
ordering, but it still rested on an ordering claim, and the claim was false.

So the scrape is gone. `helpers/qa_environment/unittest_counts.py` runs the named modules
itself and takes `result.testsRun` and `len(result.skipped)` off the `TestResult` object —
where both numbers exist exactly, and where nothing a test prints can reach them — then
writes `tests=N` / `skipped=N` to the path `qa-helper-tests.bash --counts-file` is given.
`qa-all.bash` reads that file. No stream is parsed anywhere in the path now.

Verified the result object first rather than assuming it: across a module holding a plain
pass, a decorated skip, a runtime skip, an expected failure, an unexpected success and a
subTest loop, the object's numbers match unittest's own printed summary exactly —
`testsRun=6 skipped=2 expectedFailures=1 unexpectedSuccesses=1`, against
`Ran 6 tests … FAILED (skipped=2, expected failures=1, unexpected successes=1)`. Including
that `testsRun` counts the two skips, which is the original blindness, confirmed at source.

Two bugs died with the design rather than being fixed. The two readers had drifted into
opposite match rules and disagreed with each other about the same capture (round 6's
finding) — there is one reader now, so they cannot. And the decoy class is not defended
against, it is unreachable: the regression test fires a padded stdout decoy, a stderr decoy
and an atexit decoy at a real subprocess, and asserts both that the counts are right *and*
that the forged text really did reach the streams, so the case cannot pass by the attack
failing to run.

Mutation-tested both halves before believing either: 6 mutations of the runner (skip count
hardcoded to zero, derived from testsRun, each key dropped, failure reported as success,
counts file never written) and 8 of the reader (missing key answers zero, missing file reads
as a clean run, unknown and duplicate keys ignored, digit check dropped, skip count dropped
from the payload, pluralisation frozen, last line dropped). All 14 caught.

One real bug found by the reader's own tests rather than by me: `while read` drops a final
line with no trailing newline. The runner always writes one, so it was unreachable — but a
reader that silently ignores part of its input is precisely the shape this library exists to
avoid, so it reads all of it now.

## 04:31 · review · round 7 reviewed both designs, and found four holes in the new one

Round 7 was dispatched against `27d7b342` and I messaged it mid-flight to say I had already
broken its first question, so it reviewed the **replacement** as a design as well. That was
the right call and it paid: it confirmed the core claim and then found four holes.

It independently verified the premise rather than taking my word: one run with every
category present, `TextTestRunner`'s text against the object, agreeing exactly — including
that a `subTest` skip is counted by both, and that `expectedFailures` and
`unexpectedSuccesses` are separate lists contaminating neither figure. It also flagged, in
advance of my writing it, that the exit code must come from `wasSuccessful()` and not from
`failures or errors`, because an unexpected success leaves both lists empty while unittest
reports FAILED. My implementation already used `wasSuccessful()`; the comment now says why,
because the wrong version turns a red suite green and looks identical.

**Hole A — `testsRun` and `skipped` are not commensurable.** `testsRun` counts test methods;
`skipped` counts skip events, and one method with three `subTest` skips gives
`Ran 1 test … 3 skipped`. Faithful — unittest prints the same — but `CLAUDE/QA.md`'s
argument that the four machine shapes give four distinct counts quietly assumed the skip
count was bounded by the test count. Documentation corrected, and the reader now has a case
asserting it must NOT clamp a file that is faithful to its run.

**Hole B — an unimportable module is reported as a test that ran.** unittest substitutes a
`_FailedTest`, so testsRun inflates by one. Worth recording that this cannot produce a
silently-wrong green line: the placeholder is an error, `wasSuccessful()` is False, the
runner exits 1 and `qa-all.bash` aborts before the stage line is printed. The review's
concrete instance (1464 → 1465) was my own new test module arriving, not an import failure.
The **module count** it proposed is still worth having, for a different and better reason:
a machine that COLLECTED a different set of modules is this plan's own subject one level up,
and the test count alone cannot show it. The line now reads `Ran 1482 tests in 65 modules`.

**Hole C — the counts file is not unreachable, and I said it was.** Its path travels in
`argv`, so a test can read `sys.argv` and overwrite it — and this module's own tests are
collected by the runner they test. "No stream a test can write to is parsed" was true and
insufficient; the claim I actually made was wider. `qa-all.bash` now passes a
`--counts-token` that only that run knows and the reader requires it back, so a clobbered
file FAILS the gate instead of reporting a number nobody questioned. Stated honestly in the
code: that is a detector for an accident, not a lock against a test that is trying. The
streams, by contrast, could be hit with an ordinary `print`.

**Hole D — a hard exit leaves an empty file and exit code 0.** Reproduced: a test calling
`os._exit(0)` skips atexit, the runner never returns, nothing is written, and the
interpreter exits 0, leaving the zero-byte file `mktemp` created. The reader already refuses
it (`tests= is missing or not a number`, exit 1) — the one property round 7 said must
survive the rewrite did survive. Added as a named case rather than left as a coincidence.
