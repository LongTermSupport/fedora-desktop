## 01:03 · finding · T3.4 — the skip count read the whole capture, and both decoys beat it

The timestamp problem the previous day-file's closing entry admitted resolves itself here:
this is a new day-file, so the first honest stamp has nothing to overshoot. `date` reads
01:03 and that is what this says. Yesterday's file ends with entries stamped 01:02–01:04
that were invented; they stay as they are, because the journal is append-only.

The round-3 prompt I wrote asked one question about my own round-2 fix: the skip count came
from `[[ "$helper_out" =~ skipped=([0-9]+) ]]` against the **entire** captured output, and
`=~` takes the first match anywhere. A line earlier in the capture containing the text would
win the match ahead of `unittest`'s result line. I wrote in the prompt that I had not tested
it. Measured both ways before changing anything:

```
OLD code, decoy warning line : 99 (should be 2)
OLD code, decoy skip reason  : 42 (should be 1)
```

Reachable, then — and by the most ordinary route imaginable. A skipped test in this suite
prints its own reason, and this plan's Task 3.1 *wrote three of those reasons*. One of them
mentioning a count would have silently replaced the number on the stage line. The failure
mode is the one this whole plan is about: a line that looks like a measurement and is not,
with nothing to distinguish it from the real thing.

The count now comes from `unittest`'s own `^(OK|FAILED)` result line — the only place it is
authoritative — and is only then matched:

```
OK                                                         -> 0
OK (skipped=1)                                             -> 1
OK (skipped=1, expected failures=1)                        -> 1
FAILED (failures=1, skipped=3)                             -> 3
decoy: warning line says skipped=99, result says 2         -> 2
decoy: a skip REASON contains skipped=42                   -> 1
```

Six shapes, four real and two adversarial, all correct. A real local run still reports
`helper-tests: Ran 1456 tests, 1 skipped`, so the hardening is not paid for with a
regression.

**`TOOL_ABORT` re-verified against the source rather than against my memory of it.** Round 2
found the `no-run-summary` guard refusing `qa-all.bash`'s `exit 2` paths. The fix added a
pattern, and a pattern is worth only what it matches, so it was checked against every
`ERROR:` string the script can actually print — grepped out of `qa-all.bash`, not recalled:

```
True  ERROR: Missing required tools (ansible-playbook). Install them and re-run.
True  ERROR: Missing required tools (node / extensions node_modules). Install them and re-run.
True  ERROR: Missing required tools (semgrep). Install with: pipx install semgrep
True  ERROR: Missing required tools for ansible check. Install them and re-run.
True  ERROR: Missing required tools. Install them and re-run.
True  ERROR: docs gate could not produce a result (zero-file scan or checker crash).

overlaps a stage line? False False
unrelated ERROR ignored? True
```

All six terminal states recognised, no overlap with a stage verdict in either direction, and
an unrelated `ERROR:` line still leaves the capture judged truncated — which it would be.

## 01:09 · finding · T2.1 — the decision gate had three options and only one of them was real

Task 2.1 has sat as "the owner's call between (a), (b) and (c)" since Phase 2 was written.
Before leaving it there any longer I checked the arguments I had recorded *for* the owner,
because a decision gate presenting options that are not available is not a decision gate —
it is a delay with a table attached.

The docs gate **passes here** (`✓ docs: 71 files OK`) and reports 8 findings in CI. That
alone is worth stating plainly: the gate this plan has been calling "Cause A" is itself
machine-dependent, which is the plan's own subject rather than an exception to it.

All 8 CI findings are one line repeated — `.claude/rules/*.md:15` →
`../hooks-daemon/CLAUDE/DirectoryRoles.md` → `target does not exist`. Then the fact that
narrows everything:

```
8   .claude/rules/*.md files carrying <!-- hooks-daemon-rule-version -->
8   findings reported by CI
```

The same eight. Of fifteen tracked rule files, the seven this repository hand-wrote
contribute nothing; every finding is content the daemon's installer generates
(`install/directory_role_rules.py`, via `directory_roles_link()` and re-deployed by
`sync_directory_role_rules()`).

That kills **(c)** more firmly than "it would regress at the next upgrade" — the installer
re-renders the link on every sync, and the daemon's own `docs_qa` `rules-file-shape` check
enforces the pointer-only contract the edit would break, so it would be fighting a check
for as long as it survived. And the daemon's module docstring records the reasoning
deliberately: the target exists "at a fixed, predictable path the moment the daemon itself
is installed", because a client install clones the whole daemon repo. **The link is not
broken. Its premise is false in CI** — `.claude/hooks-daemon/` is gitignored
(`.gitignore:53`) and no file in `.github/workflows/` mentions the daemon at all.

**(b)** was already on thin ice and the repo's own rule names the shape: "Missing
Dependencies — Fail Fast, Fix in IaC" prohibits "make the script tolerate the missing tool
(skip-if-absent, `|| true`, advisory-only mode)". A link check that stops checking when the
tree is absent is that, one indirection away, and it would pass a genuinely broken link in
the only environment that cannot tell.

So **(a)** — install the daemon in CI before QA — is what is left, and it is what the
Missing-Dependencies rule prescribes: the daemon is a real dependency of the docs graph and
CI does not have it.

**Not implemented, deliberately.** What the rules settle is which options are admissible;
what they do not settle is whether every QA run should depend on an external repository's
installer being reachable. That is a real cost and it is the owner's to weigh, so the gate
stays open — but it is now a one-option confirmation rather than a three-way study, and the
work is ready to land the moment it is confirmed. `FINDINGS.md` carries the citations.

`qa-all.bash`: exit 0, 914 files, `✓ docs: 71 files OK`. `PLAN.md` 17,382 bytes, back under
the 18,000 advisory — the Task 2.1 block now points at `FINDINGS.md` instead of restating it.

## 01:39 · action · T4.4 — round 3, and the line that had been wrong twice now has a test

Round 3 came back FIX-BEFORE-MERGE with 2 blocking, 3 should-fix and 3 nits. Its Blocking 1
was the uncommitted `qa-all.bash` — already landed as `698f7548` before the report arrived.
The rest, each verified here before acting rather than taken on the reviewer's word.

**Blocking 2 — my `podfreeze` comment stated a mechanism that does not hold there.** It
claimed `assert_on_host "$@"` would feed the tool's argv into the container-marker slots.
Reproduced both shapes:

```
podfreeze shape  (top-level shift loop, then the call): 0 arg(s): []
lxcfreeze shape  (main "$@", parse_args shifts a copy): 2 arg(s): [freeze somename]
```

The reviewer is right. `podfreeze`'s arg loop shifts every branch, so `$#` is 0 by the call
— the remedy there is *meaningless*, not dangerous. `lxcfreeze`'s call is inside `main()`,
whose positionals survive `parse_args "$@"`, so its comment was accurate and mine was a copy
of it that did not apply. The conclusion (stay bare) holds in both; the reason differs, and
now each says its own. Also dropped *"no caller supplies them"* — `test-freezelib.bash`
supplies both at four call sites, which is the sentence immediately before it. A comment a
reader can falsify in thirty seconds discredits the ones around it.

**Should fix 2 — the host instruction would have sent the owner to one play when two are
needed.** `tasks/deploy-freeze-lib.yml` deploys only `freeze-common.bash`;
`play-podfreeze.yml:75` and `play-lxcfreeze.yml:91` each deploy their own binary and merely
*include* the shared task. All three files changed, so "either freeze play" leaves the other
binary drifted and the host still red — 28 hard gates short, since the drift gate aborts
before `helper-tests`. Corrected to name both.

**Should fix 1 — the coverage denominator traded a false 100% for a false alarm.** Round 2's
fix counted symbols with an unanchored `search` on the raw line, which counts a symbol
*mentioned* rather than a line that *is* a verdict. Measured on the real shape
`qa-patterns.bash:362` emits:

```
✗ patterns: 2/260 files failed
  ✗ scripts/a.bash          <- counted
  ✗ scripts/b.bash          <- counted
=> 1 of 4 ... 2 unrecognised

have manufactured evidence of this parser being broken. Now anchored with a permissive

malformed timestamp still lands in the denominator while indentation and prose do not. ANSI
