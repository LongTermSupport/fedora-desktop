## finding · the execute bit decides whether a file is linted at all

`semgrep/target_manager.py:1024`:

```python
elif not path_has_permissions(path, stat.S_IRUSR | stat.S_IXUSR):
    return None
```

`get_shebang_line()` refuses to read a file that is not owner-executable. For a
file with no recognised extension the shebang is the *only* language signal, so
no execute bit ⇒ no language ⇒ never scanned. `git ls-files -s` gives the mode:

| File                                       | Mode     | Scanned |
| ------------------------------------------ | -------- | ------- |
| `files/var/local/docker-in-lxc`            | `100755` | yes     |
| `files/var/local/claude-yolo/claude-yolo`  | `100644` | **no**  |
| `files/var/local/claude-yolo/entrypoint.sh`| `100644` | yes — the `.sh` extension carries it |

`qa-bash.bash` has the same hole from the other direction: its two `find` passes
are "named `*.sh`/`*.bash`" **or** "`-type f -executable` with a shell shebang".
A mode-644 extensionless script is in neither, so it gets no `bash -n` either.

27 tracked scripts are in that state. The census (`shellcheck -S style`) is in
PLAN.md; the number that matters is **SC2155 ×19**, because Task 4.1 of Plan
00075 raised the shellcheck bar to `warning` *for that code specifically* and
then fixed 12 instances. The raise was real; its reach was not.

## progress · `|| true` cleared: 15 → 0, and two more wrong answers found

`bash-error-hiding-or-true` has **no `FAIL-FAST-OK` escape by design**, so every
one had to be rewritten rather than annotated. Several already carried careful
comments explaining why the status was safe to drop — and those comments were
right about the *expected* case and silent about every other one, which is the
whole problem. `|| true` cannot tell "there was nothing to do" from "I could not
do it".

**Two were live wrong answers**, both in `nord remove-all`:

```bash
echo "$connections" | while read conn; do
    nmcli connection delete "$conn" 2>/dev/null || true
    count=$((count + 1))
done
echo "Removed all nordvpn connections"
```

The loop body ran in a **pipeline subshell**, so `count` never survived it — and
nothing read it anyway. Each delete's status was discarded. So the closing line
announced *"Removed all nordvpn connections"* whether every delete succeeded,
some failed, or all of them did. Now a here-string keeps the loop in this shell,
each failure is counted and named with what nmcli said, and the summary reports
the real numbers and returns non-zero when any removal failed.

**The teardown cases got something better than compliance.** `pkill -P` returning
1 when a process has no children was the documented reason for `|| true` in
`ftp-camera`'s cleanup — the bug that once left the FTP server running after
Ctrl+C. Asking `pgrep -P` **first** keeps that fixed *and* leaves a genuine pkill
failure fatal, which `|| true` could not: it discarded both outcomes identically.
Verified with a live process tree that the no-children path skips cleanly under
`set -e`.

The rest: `read … || true` on two delete-confirmation prompts became explicit
EOF-declines (`reply=""`, same safe answer, now stated); `shift || true` became
`if [ "$#" -gt 0 ]`, which also retired a `2>/dev/null` that was hiding shift's
own message; `wait` statuses are captured and logged rather than dropped; and
`exiftool … | awk … || true` — a function whose stdout **is** its return value —
now says in a branch that an empty result is the answer.

### Caught myself inventing an API

Writing the `ftp-camera` teardown I called `_dbg "..."` to log the wait status.
There is no `_dbg` in that script — I had imported a habit from `wsi`. In a
`set -e` cleanup path a command-not-found would have aborted teardown: precisely
the failure the surrounding comment exists to prevent. Found by grepping for the
function instead of assuming it, before it was committed. The line is gone; the
branch now says what it means without inventing output.
