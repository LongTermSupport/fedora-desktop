## finding · the execute bit decides whether a file is linted at all

## The gate I had just written was making the same claim it was built to catch

`ftp-camera` came back from the widened semgrep scan with **zero findings**, and

is the point: the check was one level too shallow, and the number it produced
looked exactly like success.

Checking `.errors[]` turned up **14** affected files in two distinct classes:

- **`Syntax error` ×3** — the whole file failed to parse, so **no rule ran on any
  line**: `ftp-camera` (2,475 lines), `rclone-cache-status`, `rclone-tail`. The
  last two are executable, so the **old** gate scanned them too and reported them
  passing. This hole is older than the one this plan opened with, and independent
  of it.
- **`PartialParsing` ×11** — parsed apart from named ranges. The recurring
  construct is `${var:-(text)}`, parentheses inside a default value, which is
  **my own idiom** from Plan 00075's error-reporting fixes. Also extglob
  (`${str##+([[:space:]])}`) and some arithmetic. Worst of these:
  `scripts/git-hooks/pre-commit` has an unparsed span of ~86 lines — a secret

### Calibration, and why not simply "make it fatal"

All 14 pass `bash -n`. Whether semgrep's grammar accepts a given piece of *valid*
bash is a property of semgrep, not of this repo, so "rewrite until the parser
copes" is not automatically the right answer — it would mean changing working
production code to suit a tool.

So the two classes are treated differently, on what they actually mean:

- **`Syntax error` → gating.** 0% analysed is indistinguishable from not scanning
  the file, and calling that a pass is the lie.
- **`PartialParsing` → reported, not gating.** Every rule ran on everything
  outside the named ranges, and the affected files are printed, so the gate
  claims nothing it did not check.

The three current whole-file failures are listed in `SEMGREP_CANNOT_PARSE` with
their reason, and the list is **self-expiring in both directions**: an unlisted
file that cannot be parsed fails the gate, *and* a listed file that starts
parsing fails the gate until it is removed. A stale exception would hide the next
regression behind it.

Every run now prints its coverage — `N NOT ANALYSED`, `N analysed EXCEPT for some
ranges` — above the `✓ patterns: 153 files OK` line, pass or fail. A summary
consisting only of a green tick and a file count is the format that let all of
this sit unnoticed.

Finding the actual constructs is Phase 4.3/4.4. One method already ruled out:
**bisecting by truncation is invalid** — a prefix cut mid-function is unparseable
in its own right, so the search converges on where truncation first hurts rather
than where the parser breaks. It produced three confident, confounded answers
before I noticed the isolated `numfmt` probe had already contradicted them.

## One `case` on one line cost 2,475 lines of coverage

Task 4.3, with a method that is actually valid. Bisecting by truncation was
wrong; **leave-one-out on complete top-level chunks** is not. Split each file
into whole function-sized segments, write each variant as its own file, and scan
them all in **one** semgrep run — the parser's verdict is then per file, with no
mid-construct cuts to confound it.

`ftp-camera` reduced to a single 45-line function, and from there to one line:

```bash
case "$src" in "${remote_name}:"*) echo "$mnt"; break;; esac
```

Not the `case` by itself — that parses. Not the quoted-expansion pattern — that
parses. It is a **one-line `case … esac` nested inside a `while` inside a command
substitution**; written across lines, the identical bash parses fine. One line,
and 2,475 lines of a script that runs a camera workflow were invisible to every
pattern rule.

this connection" and "this connection is not shared" were the same empty string,

**`SEMGREP_CANNOT_PARSE` is down to two**, which is the list behaving as designed.

- `only_2` — parses
- `only_5` (or `only_4`) — parses
- `pair_2_5` (and `pair_2_4`) — **Syntax error**

So it is not a construct. Neither function is individually unparseable; the
grammar fails on the two of them in combination. That points at a parser
complexity or error-recovery budget rather than a missing rule, which is the next
hypothesis to test — and it explains why three construct-shaped theories all died
on isolated probes.

**A wrong reading on the way there, worth recording.** My first pass said each
segment failed individually, which contradicted the earlier chunk run. It was a
bug in my throwaway analysis `jq`:

```jq
.paths.scanned[] | "\(.): \(if ($bad|index(.)) then ...)"
```

After `$bad |`, `.` rebinds to `$bad` — so `index(.)` asks whether `$bad`
contains itself, which is truthy for every file. Every scanned file came back
"SYNTAX ERROR" and I believed it long enough to write it down.

Checked immediately whether the **shipped** gate shares the defect. It does not:
`qa-patterns.bash` reads `.path` off the error object inside `select(...)`, and
its `$seen[.]` lookup is inside a `map`, where `.` is correctly the element. The
bug was confined to a scratch command. Verified rather than assumed, because a
gate that names the wrong file is worse than one that names none.

## Phase 5 — the review, done inline, and it found the gate doing the thing again

Three attempts to delegate the full-diff review died: the first with a
server error mid-response, then two narrower ones (gate machinery / shipped
scripts, split precisely because a whole-diff pass had already died once) with
API 529s within twenty seconds of each other. That is an outage, not a scope
problem — respawning would have hit the same wall — so the review was done
inline instead.

### Defeat vectors, checked rather than reasoned about

The predicate is shared between discovery and the coverage assertion, which is
the design's strength and also its blind spot: anything the predicate does not
recognise is invisible to *both*, so the assertion cannot report it. That makes
the predicate's edges worth measuring rather than arguing about. Measured:

- `#!` followed by a **space** (`#! /bin/bash`, valid POSIX) — the regex is
  anchored `^#!/`, so it would not match. **None in the repo.**
- **CRLF** shebangs — `^#!/.*bash` survives a trailing `\r` because it is not
  end-anchored, but the two `sh` comparisons are exact equality and would not.
  **None in the repo.**
- **Tracked symlinks** — `find -type f` skips them while `git ls-files` lists
  them, so a symlink to a shell script would trip the assertion. There is one,
  `scripts/vault`, and it points at a vendored *directory*, so the `[[ -f ]]`
  test drops it. Correct today, and it fails loud rather than quiet if that ever
  changes.
- Non-bash, non-`sh` shebangs — **none** outside python/node/ansible.

All four are latent rather than live. Writing them down because "no instance
exists" is a fact about today, and the next one to appear would be silent.

### Finding 1 — the mirror could lose a file, and nothing would notice

`dir/foo` and `dir/foo.bash` both mirror to `dir/foo.bash`. The second `cp`
overwrites the first; the map is merged from one JSON object per file, so the key
keeps one value. The overwritten script is then **neither scanned nor missed** —
the assertion iterates the map's *values*, and the lost file is not among them.
It would not be reported as failing, it would not be reported at all, and the
gate would print a pass covering it.

That is this plan's thesis committed inside the fix for this plan's thesis. Now a
hard failure naming both files. Negative control: dropped `scripts/zz-collide-probe`
next to `scripts/zz-collide-probe.bash` → `rc=2`, both named; probes removed.

No collision exists today, which is exactly why it was worth adding — a check
that only earns its keep after someone makes the mistake is the kind that never
gets added.

### Finding 2 — "analysed EXCEPT for some ranges" hid its own size

The partial-parse report printed a list of filenames. So this:

    files/home/.local/bin/ftp-camera
    files/var/local/claude-yolo/claude-yolo

described 1,902 skipped lines and 1 skipped line in the same shape. The report
now prints the union of the skipped ranges against the file's length:

    files/home/.local/bin/ftp-camera — 1902 of 2486 lines not analysed (first gap from 585, last to 2486)
    files/var/local/claude-yolo/claude-yolo — 1 of 3021 lines not analysed (first gap from 1252, last to 1252)

Union, not sum, so overlapping ranges are not double-counted — `wsi` reports 2
lines from 4 ranges.

### What that immediately exposed — Task 4.3a claimed too much

`ftp-camera` was moved out of `SEMGREP_CANNOT_PARSE` this session on the strength
of "it parses now", and the plan recorded it as fixed. With the magnitude
printed: **1,902 of 2,486 lines are still unanalysed** — one range from 585 to
the end. It went from 0% covered to 23% covered, not to covered.

That is a smaller error than the ones this plan is about, but the same species:
a true statement ("it parses") standing in for the one that matters ("its rules
ran"). Corrected in PLAN.md rather than quietly amended, and Task 4.3c opened for

Every other partial file is 1-5 lines except `scripts/git-hooks/pre-commit` at

## Task 4.3c — three premises killed, and a bigger hole found behind them

Went after `ftp-camera`'s remaining 1,902-line gap with the method that worked
for 4.3a. It did not find the cause, but it destroyed three assumptions I would
otherwise have carried into the next attempt.

**Dead premise 1 — `${ext,,}`.** The range starts at line 585,
`verify_file_complete()`, whose first real statement is
`case "${ext,,}" in`. Bash-4 case-conversion expansion inside a `case` head is an
obvious suspect for a parser that mostly targets POSIX. Written as a minimal
file, it parses fine. Cheap to test, dead in a minute.

**Dead premise 2 — the function itself.** Lines 585-671 extracted whole, with a
shebang, parse clean. So the cause is contextual, exactly like 4.3b.

**Dead premise 3, and this is the one that mattered — "the file is unparseable".**
Copied the real, unmodified `ftp-camera` to `./ftp-camera.bash` on its own and
scanned it: **no error at all, and zero findings.** The chunk-bisect harness said
the same thing in its own words — "whole file breaks? False" — which I first read
as a bug in my chunker. It was not. The whole file, reassembled from all 61
top-level chunks, genuinely does not error.

So the partial parse is not a property of the file. Two candidates: a timeout
under batch load, or something about the run.

**Not a timeout.** Full mirror with default per-rule timeout: 12 partial files.
With `--timeout 0`: 12 partial files, same set. Deterministic.

**It is per rule.** Split the ruleset into one file per rule and scanned the
mirror five times. Only `bash-capture-discards-status` and
`bash-error-hiding-pipe-echo` produce the 585-2486 range. Both are
`paths.include`-scoped to `files/**` among others — which is why the solo copy at
`./ftp-camera.bash` saw no error: at that path, neither of those rules applies,
so nothing that triggers the failure ever ran.

That is a real narrowing. But the per-rule scan produced something worth more
than the thing I was chasing.

### The scan counts are not equal, and the summary line implies they are

| rule                           | files scanned |
| ------------------------------ | ------------- |
| `bash-error-hiding-or-true`    | 154           |
| `bash-error-hiding-pipe-echo`  | 120           |
| `bash-status-after-block`      | 120           |
| `bash-test-discards-status`    | 90            |
| `bash-capture-discards-status` | 90            |

The gate prints `✓ patterns: 154 files OK`. That is the union across rules, and
it reads as "every rule ran on 154 files". Four of five did not.
`bash-capture-discards-status` — the rule for the precise defect class Plan 00075
exists to catch — sees **90 of 154**.

The narrowing is deliberate; the rule says so and Plan 00075 tracks widening it.
That is not the complaint. The complaint is that it is deliberate *in a YAML
comment* and invisible *at the point where the pass is claimed* — which is the
same failure the partial-parse report had this morning, and the same one the
whole plan is about. A number that is true of the union, presented as though it
were true of each part.

Not bolting a fix on. Reporting per-rule coverage without paying for N extra
scans means matching `paths.include` globs statically, which needs a YAML parser
inside a bash gate — `yq` is present in this container but that is a dependency
decision for the host and CI, not a tweak. Task 4.5 opened with the measurements
in it, so the next person starts from numbers rather than from my summary of
them.

## The gate was asserting something false about its own exception list

Followed the per-rule finding straight into Task 4.3b, because if partial
parsing was per-rule then whole-file "Syntax error" probably was too.

It is. Both `rclone-tail` and `rclone-cache-status`, copied unmodified:

- at `./rclone-tail.bash` — **no error**, 2 files scanned
- at `files/home/.local/bin/rclone-tail.bash` — **Syntax error**, 2 files scanned

Per rule, at the erroring path:

| rule                           | syntax-error files |
| ------------------------------ | ------------------ |
| `bash-error-hiding-pipe-echo`  | 2                  |
| `bash-capture-discards-status` | 1                  |
| `bash-status-after-block`      | 0                  |
| `bash-test-discards-status`    | 0                  |
| `bash-error-hiding-or-true`    | 0                  |

Three of the five rules parse these files **perfectly**. Two of those three are
`paths.include`-scoped to `files/**` as well, so they genuinely applied and
genuinely succeeded.

Which makes this line, printed by the gate on every run, false:

    ⚠ patterns: 2 file(s) NOT ANALYSED — semgrep cannot parse them

They were analysed, by most of the ruleset. The true statement is that **at least
one rule** could not parse them. And that is as precise as it gets from a normal
run: semgrep's error objects carry `code`, `level`, `message`, `path`, `type`,
`spans` — **no rule id** — and the combined run dedupes to one entry per file. So
"which rules" is not recoverable without re-scanning per rule, which is five
times the cost.

Corrected the wording rather than inventing attribution I cannot compute:

    ⚠ patterns: 2 file(s) some rules could not parse — those rules ran on NO line of them:
        ...
        Semgrep does not say which rules, so treat these as partially covered, not covered.

Kept it **gating**, and that is the deliberate part: "some unknown subset of the
ruleset did not run on this file" is not a pass anyone can rely on, even though
it is less bad than "nothing ran". Findings are unaffected either way —
`.results` is independent of `.errors`, so a rule that did parse still reports.

### The part worth keeping

The error was in the safe direction — it understated coverage rather than
overstating it — and I would not have looked for it, because a gate being too
pessimistic does not hurt. It surfaced only as a by-product of chasing something
else. That is three false statements found in this gate today, all of the same
species and none of them lies about *findings*: every one was a claim about how
much had been looked at.

It also retroactively reframes both earlier 4.3b sittings. Every theory tested
there — the function pair, the Python heredoc, the size budget — was answering
"what in this file cannot be parsed", and the question was malformed. The file is
fine for three rules. Whatever is going on is an interaction between one rule and
the file, which is a different search and a much smaller one.
