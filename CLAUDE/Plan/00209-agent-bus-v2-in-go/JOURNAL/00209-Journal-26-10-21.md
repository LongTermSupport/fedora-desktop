# Plan 00209 — Journal 26-10-21

_Scaffolded by `mkplan.bash`; timestamps in this file are UTC._

> **Append-only activity log** for plan 00209. One file per day
> (`00209-Journal-YY-MM-DD.md`). `PLAN.md` tracks the plan (what/why,
> current state, tasks); this journal tracks what actually *happened* —
> findings, decisions, dead-ends, hand-off state — the linear lifecycle a plan
> document structurally cannot carry.
>
> **Entry grammar** — append new entries at the BOTTOM; NEVER edit earlier
> entries (corrections are new entries):
>
> ```
> ## HH:MM · category · REF   — optional short title
> ```
>
> - `HH:MM` UTC 24h (the date is in the filename, also UTC); times increase
>   down the file. A file with no sentinel line above predates this system —
>   its times are local, zone unrecorded (legacy; never rewritten).
> - `category` ∈ `action` | `finding` | `decision` | `thought` | `blocker` | `handoff`
> - `REF` = optional task/phase ref (`T1.2`, `P1`) or `—`.
> - Bodies may embed fenced logs/diffs/snippets — no size limit — with a
>   one-line takeaway above the fence.
> - End a working session with a `handoff` entry so the next agent's entry
>   point is the last entry of the newest day-file.

## 19:07 · decision · P0   — A team's stable id (TID), and a long v1 name migrates (INT3)

**TID, defaulted, the coordinator agreed**: a team has a stable id, `^[a-z][a-z0-9-]{0,21}$`, fixed
at creation, and a display name (1-64 characters, default the id) that is display only. The id is
in the `server_name`, the unit, the dynamic user, every path, lock and record, the bundle, the
roster and the envelope; the name is in the room names, the Element launcher, the board and
`status`. A rename edits the name and runs the play: nothing restarts and no account, token,
bundle, path or unit changes (C44, C 3.5.2). This answers Plan 00201 Task 2.16, which v1's R4 (the
name is the unit and the data folder) made hard. The coordinator puts it to the owner in its next
digest, flagged IRREVERSIBLE.

The 22-character limit lets `teamchat-<team>` fit systemd's 31-character user name.

**INT3, corrected in this integration (0b498397).** The first integration had M0 refuse a v1 name
over 22 characters, because a migrated team's id was its v1 name. That refusal came only from
deriving the id from the name, which TID no longer requires. Now such a team migrates: its move's
declaration in `teamchat_migrations` carries an `id` (ccy-teams proposes the name cut to 22
characters with trailing hyphens removed; the owner may change it; ccy-teams and M0 refuse one that
fails the grammar or collides), the v1 name stays its display name, and the set record names each
team as a pair of v1 name and id. The one resolving function (D 3.9) maps the v1 name to the id
once the set is committed, so `<seat>@<v1 name>` strings keep working. A v1 name of 23 or 24
characters can never be a v2 id, so no string resolves two ways. Edited: D 3.5, 3.9, 5.1, 5.3,
5.4, 5.10, 12; C 3.8; DESIGN-v2.md sections 2, 5, 7 and 9. Not yet reviewed: the N0 review checks
it.
