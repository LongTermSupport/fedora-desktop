> **Append-only activity log** for plan 00209. One file per day
> (`00209-Journal-YY-MM-DD.md`). `PLAN.md` tracks the plan (what/why,
> current state, tasks); this journal tracks what actually *happened* —

> **Entry grammar** — append new entries at the BOTTOM; NEVER edit earlier
> entries (corrections are new entries):
>
> ```
> ## HH:MM · category · REF   — optional short title
> ```
>
> - `HH:MM` UTC 24h (the date is in the filename, also UTC); times increase
>   down the file. A file with no sentinel line above predates this system —
>   its times are local, zone unrecorded (legacy; never rewritten).
> - `category` ∈ `action` | `finding` | `decision` | `thought` | `blocker` | `handoff`

> - Bodies may embed fenced logs/diffs/snippets — no size limit — with a
>   one-line takeaway above the fence.
> - End a working session with a `handoff` entry so the next agent's entry
>   point is the last entry of the newest day-file.

## 16:28 · correction · 16:15   — SessionEnd has two limits, 6 s and 8 s, both kept

The 16:15 entry's "`hooks.json:50` sets the SessionEnd timeout to 6 s, where DESIGN.md 8.2 says
8 s" is a misreading, caught by the M0 review (finding 2). There is no mismatch: two different
limits exist.

- `"timeout": 6` in `hooks.json:50` is the plugin's pingbus SessionEnd hook's own limit.
- `CLAUDE_CODE_SESSIONEND_HOOKS_TIMEOUT_MS: 8000` (`optional/agent-bus/settings.json:9`,
  `seat.py:83`) is the session-wide SessionEnd budget written into a seated session's settings.
  DESIGN.md 8.2's "the 8 s setting stays" means this one, and is right.

The stage-2 spec states and keeps both values; the Go goodbye must finish inside 6 s.
RESEARCH-python-scope.md and the bookkeeping report (finding 06) now say so.

## 16:51 · decision · P1   — Owner direction: v1 is a prototype, only the contract binds

Owner direction, binding: the Python is a prototype and a first draft, not a golden archetype.
The Go version fixes and improves it, and only the compatibility contract binds while v1 and v2 run
side by side: the shared on-disk formats and locks, wire protocol 1, and the CLI output that agents
and scripts parse. A parity oracle checks that contract only, never the Python's internals, wording
or process structure. Each improvement is a numbered departure with its reason, and a bad contract
is recorded as a departure too, to change at stage 8 or through a versioned format v1 tolerates.

Recorded in PLAN.md ("Owner direction: v1 is a prototype"). The same "contract only" wording is now
in Task 3.1, in DESIGN.md's intro and its section 11, in BUILD-BRIEF.md, and in src-go/CLAUDE.md's
"How a port is built". That section now covers ports from Python as well as bash.

Still open: Plan 00213's status-line golden requires stdout identical to the Python's, which is
stricter than the contract. Later status-line improvements come in as numbered departures that
re-record the golden.
