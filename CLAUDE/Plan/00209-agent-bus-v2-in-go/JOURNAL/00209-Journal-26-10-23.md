## 03:01 · decision · —   — n3b-D1: an offline LXC member never fails anything

n3b-D1 (SPEC-n3 section 10, rules per step in section 3.1): an offline LXC member is the normal lifecycle, never a failure. This is the owner's rule and it is not negotiable.

- A member whose container is stopped, frozen or missing, is stopping during the phase, or whose unit is down is shown as offline. That is LXC record status `offline`, renamed from C 3.9.3's `stopped`.
- It never makes a play, deploy, acceptance run or tool fail, refuse or wait. `lxc apply` places the members it can reach and exits 0 for the team. The L3 probe answers `Stopped`, and the notice stays a notice.
- It is an error, 69, only when the operator targets that one member: `lxc apply --member`, or `lxc restart --member`.
- A running container's wrong facts stay failures.
- This overrides C 3.9.1-3.9.4 and LX2, LX4, LX6, LX8, GU2, SU2 and LP1 wherever they said fail.
- n3b-D3 adds a refinement: when an offline error sits beside any other error, the other error decides the exit. A refusal is never hidden behind "offline, try later".

## 03:01 · decision · —   — n3b-D2: any number of members per LXC container

n3b-D2 (SPEC-n3 section 10): one LXC container may hold any number of members. This is the owner's requirement, relayed by the team coordinator: "it absolutely should be, no limits".

- An LXC member is (team, container, checkout, seat), and its user is only who runs it. That tuple is the duplicate key, replacing (team, container, user).
- `seat` is required in every entry, because it is part of the member's identity and must be declared and stable.
  - `lxc apply` never uses `--seat next`.
  - The tool that adds an entry (`ccy-teams lxc-add`) picks the next free seat when it writes the declaration, which then records it. That is the lead's ruling.
- A member's role comes from DC6's team `coordinator`, one per team; there is no `role` key per entry.
- A seat lives in one container: equal handles are refused.
- There is one `teamchat-session-<...>.service` per seat.

## 06:30 · decision · —

n3e-10 merged into n3e (b2bafaa9c), with n3e-watchleak's fix.

QA on the merge found leakcheck reporting proof.(*watcher).run. It was a test fault, not a leak: one test registered leakcheck.Check twice, and the later check judged while the other world still ran. Rule project_leakcheck_once found 6 instances in 5 tests, matching the independent search, and all are fixed.

Deviation from Defence Before Fix: the rule's red was proved in the work tree, not in a commit. The merge resolution and the fix were staged together, and the merged tests do not compile against the pre-merge engine, so a red commit could not sit between them. The rule's analysistest fixture holds red and green.

Lesson for the lead: before a fixer works in a staged merge, commit the merge, or have the fixer work on a branch from the merge commit, so the red commit has a place.
