# n3c fix3: review round 2 fixes

Branch `feat/bus-v2-n3c-fix3`, from `feat/bus-v2-n3c` f5ba2eb65. The brief is
`261022-n3c-review-2.md`. Every fix has a test that fails without it. Each red was run against
the code with the fix taken out.

## N1: Return wakes the waits (`member/engine/recv.go`, `settle`)

**Choice: wake on return, not the EOF cancel.** The wake is three lines in one place, on the
state goroutine, where `Persist` already wakes the waits. It covers every return: a dead
waiter's write, an ack that never came, a failed write. The EOF cancel would need a second
reader on every connection during Serve, racing the hand-out's own ack read, and it would
still leave the lost wake after any other return. With the wake in place, fixb's decline of
the EOF cancel holds, as the review says.

**Fix:**

- `settleStore` now returns the items that left pending, and whether any went back to pending.
  "Changed" is now derived from those two.
- `settle` calls `e.wake()` once, after the loop, when a store took a return and wrote it.

**Test:** `TestAReturnWakesAWait`.

1. A recv hands out the only item. This is the abandoned waiter.
2. A wait registers and finds everything handed.
3. `Return` gives the item back.

The test checks that the wait's own `woken` channel is closed when `Return` returns, and that
the wait is then handed the item. No new Persist is made. Red: "the wait still sleeps after the
return".

## N2: the keeper deletes the store on every removed (`member/keeper/seats.go`, `onRemoved`)

**Fix:** `deleteStore` now runs on every `removed`, not only on one with no user id. It runs
under the seat lock, and ENOENT is ignored, so it does no harm when the link has already
deleted the store. This also closes B2's PARTLY.

**Test:** `TestRemovedWithAStoreLeftBehind`. A `removed` carries the agent's user id while the
store file still exists. Afterwards the store must be gone and the seat no longer held. Red:
"the store or the seat outlived the removal".

## N3: close closes the connections before the cancel (`member/link/server.go`, `close`)

**Fix:** `close` now takes the lock, marks closed, closes every connection, releases the lock,
and only then closes `stopping`. Any answer a cancelled Serve writes lands on a closed socket,
so the client sees the link gone. This is the first of the review's two options. It is one
reorder and needs no new check in `handle`.

**Test:** `TestCloseClosesTheConnectionBeforeTheCancel`.

- The fake engine gained a `cancelled` hook, which runs when a blocked request's context ends.
- The test holds `srv.mu` and then calls `close()` in a goroutine. Without the fix, the cancel
  comes while the lock is still held. With the fix, close is held at the lock before it can
  cancel.
- After the lock is released, the client must read nothing: no done.

Red, three of three runs: "the request was cancelled before its connection was closed". With
only the lock-free order check, the first version of the test passed without the fix, so that
version was replaced.

The test waits 100 ms for a cancel that must not come. `time.After` is already used for bounds
in this file.

## G1: the busfailpoints test stage (`src-go/qa/go-qa.toml`)

**Why go-qa.toml changes:** this is the review's finding G1, a nit in its section 4 and its
findings table. The `teamchat-failpoints-test` stage ran `go test -race` without the built-in
runner's `-shuffle=on`, so the failpoint build's tests never had their order checked. The
review asked for `-shuffle=on`, and for a comment explaining why `-count=1` stays out.

**Fix:**

- Added `-shuffle=on`. It costs nothing when the test cache hits.
- A comment says why there is no `-count=1`. No stage takes `{files}`, so qa-changed runs the
  stage whole for any `src-go` change, and go's test cache is what keeps that within bounds.

This is the only change to a shared file, and it is in its own hunk.
