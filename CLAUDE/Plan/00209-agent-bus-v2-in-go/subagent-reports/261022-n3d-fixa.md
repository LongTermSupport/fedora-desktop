## Major

### M1. The recovery took an earlier identical event for a tried send

**Fix.** `recordPosted` now also sets `outbox.last_sent` (the event id) in the same store write
that removes the entry. `last_sent` is a new store key: a nullable event id, checked by the
store's decoder. The recovery (`newerThan`) reads main backwards a page of 100 at a time. It stops
at `last_sent`, or after 5 pages. Only events newer than `last_sent` are considered, oldest
first, so `last_sent` ends at the newest recovered event.

`matchTried` pairs a tried entry with an own message by `unsigned.transaction_id` when the event
carries one (the server gives it only to the device that sent it). An event that carries another
txn is a different send. Only an event with no transaction id (sent from another device) is
matched by content. The `since_ms` comparison is gone. `Outbox.check` now refuses a ping id that
appears twice ("the outbox holds a ping id twice").

**Red.** `TestN3dD4TheRecoveryIsAnchoredOnTheLastPosted` runs the reviewer's scenario: two
identical queued "ok" sends 61 s apart, the first posted, the second's PUT failing transiently,
then a recovery. It runs once on the same device and once on a new device. Both subtests failed:
`last_sent = "", want $…`. In `TestStoreRules`, `ping same id twice` and `last sent bad id` both
failed with `encode = <nil>, want ErrInvalid`.

**Green.** Both subtests pass: main holds both sends and `last_sent` is the second one. The store
rules pass.

### M2. A 403 on a queued send neither stopped the team's sends nor reached the agent

**Fix.** A refused token or a forbidden send at a PUT now sets `held.sendStop` to the code, then
publishes. `held.shown()` reports that stop as `Stopped`, and four places read it:

- `stoppedErr`: later sends exit 21 or 22;
- `mayPost`: no PUT on later syncs;
- status rows and `status.json` `failed`;
- the team record, which shows the team down.

**When the stop clears.** The lead's rule says the stop clears "when teamsync next reports a
healthy run". teamsync calls `SetHealth` on every sync answer, so clearing on any healthy health
would bring back one PUT per sync. I took it to mean the team's next run. The stop clears in two
cases:

- `RecoverSends`, which teamsync calls at a session under a new pair;
- a `SetHealth` that brings the team out of a stop or out of down.

Consequence: a 403 that the sync does not share (a kicked or muted member) stays stopped until a
new pair, a teamsync stop that clears, or a link restart. Please confirm or change this reading.

**Red.** `TestSD3_8cA403StopsTheTeamsSends` failed: `a send after the 403 = {Exit:0 …}, want forbidden`.

**Green.** It passes: the next send exits 22, status and `status.json` show the stop, a later sync
makes no PUT, and once the stop clears the send is posted by the same txn.

Two existing tests changed to match:

- `TestSD3_8A401AnswersTheWaitingOp` now expects 21 while the 401's stop stands. It calls
  `w.recover`, the team's next run, before the 403 case.
- `TestSD3_10TheRecoveryFindsTriedSends` sends its "held" event from another device, so the
  match is by content (on the same device the txn decides).

### M3. A token reissued within one run re-PUT a tried send under a new device

**Fix in teamsync (the minimum).** In `session.go`, the `sendsRecovered` bool is replaced by
`recoveredPair *bundle.Pair`, and the recovery runs when the session's pair differs from it
(`reflect.DeepEqual`, as `current()` does). The change is the condition, the assignment and the
`reflect` import. The field is in `teamsync.go`.

**Fix in the engine.**

- `RecoverSends` first sets `recovered = false`, which holds the sender and makes a new send
  answer `queued`. It also clears the send-side stop.
- `held.postMu` serialises a post with a recovery, so neither can run during the other.
- The SHA-256 of the token the last recovery ran under is kept in memory only. It is never logged
  or written.
- Before each PUT, `post` compares the current token's digest with it. If they differ, the sender
  recovers again itself before posting. This covers the window between the token changing on disk
  and teamsync's next session.
- `post` checks again, under the lock, that the entry is still waiting and the team is recovered.

**Red.**

- `TestN3dD4ANewTokenRecoversBeforeTheRetry` (engine): three client tries land and lose their
  answers, then a new device, then the retry. It failed: `main holds 2 own events, want the send once`.
- `TestN3dD4ANewPairRecoversAgain` (teamsync): a hot reissue. It failed: `recovers 1, want one per pair`.

**Green.** Both pass. The existing `TestN3dD4RecoverSendsOncePerStart` (the same pair after a
suspend does not recover again) still passes.
