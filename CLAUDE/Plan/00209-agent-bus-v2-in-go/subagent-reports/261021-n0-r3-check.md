## New findings (all minor)

### 1. minor: the kinds table and two prose lines still spell a launch that `run` refuses (B 2.11 kinds table LXC and host rows, C 3.9.4 line ~1747, D ~158)

Round 3 added `--claude` to the ccy row of B 2.11's kinds table. It left the LXC row
(`teamchat run --kind lxc`) and the host `cc` row (`teamchat run --kind host`) without it, and the
same holds for C ~1747 and D ~158 (`teamchat run --kind <kind>`). B 2.4.1 step 5 says "exactly one
of the two is given, else exit 64".

The host `cc --teams` launch is spelled nowhere in full. It is also not in the list the parser test
covers ("B 6 C3, C 3.9.4, D 12").

Scenario: `cc --teams` is built from the kinds table. Every host launch exits 64, and no named test
parses that line.

Fix: add `--claude` to those rows and lines, spell the host launch line once (B 6 or C), and add it
to the parser test's list.

### 2. minor: C's ccy and host callers do not skip a `launch_failed_ms` run (C 3.7.3 release step 3, C 3.7.5 launcher, crash and sweep, D 12, against B 2.5 and 2.11 the rule)

B says the host posts nothing for a free lock file that records `launch_failed_ms`. C 3.11.2 step 6
applies this for LXC. The ccy and host callers test only that the file "names a run id", and a
launch-failed file does name one.

Scenario: a ccy relaunch's `--resume <id>` makes Claude Code exit before its SessionStart. `run`
exits 78, the container ends, and the session record remains. The launcher's call (or the next
sweep) sees a free lock that names a run id. If the check is not inside `seat disconnected` itself,
it posts a false `disconnected` once, which costs the coordinator a turn. The same transaction id
prevents a second post.

Fix: add "and records no `launch_failed_ms`" to each C/D caller condition, or state in B 2.2.1 /
2.11 that the `seat disconnected` verb makes this check itself.

### 3. minor: the LXC tick can still announce a launch-failed run when a later run has rewritten the lock file (C 3.11.2 step 6)

Step 6 skips a run "whose free lock file *still names it* with `launch_failed_ms`". Scenario:

1. A tick lands in the second or so in which a quickly failing run R holds the lock, and records R.
2. Within 10 s the unit starts R2, which rewrites the file with R2's id and then fails too.
3. At the next tick the lock is free and the file names R2, not R, so the exception does not apply.
4. The child posts `disconnected` for R.

The start limit bounds this to about one false notice per crash-loop episode, and it is rare.

Fix: the tick also records `launch_failed_ms` from the file when it sees a run held. Or the keeper
writes a per-run marker the next run does not overwrite. Or the text names this race as accepted.
