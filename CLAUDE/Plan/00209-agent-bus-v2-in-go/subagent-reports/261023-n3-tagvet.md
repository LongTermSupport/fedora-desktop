# n3-tagvet: project rules over the tagged builds

## Red (the gap)

Planted a rule violation (exec.Command, WaitDelay without ErrWaitDelay) in a file tagged only
for each tag. The driver built from `qa/driver`, run as the analyzers stage runs it:

- Untagged `go vet -vettool=<driver> ./internal/teamchat/...`: rc=0, plants unseen.
- With `-tags busfailpoints` and with `-tags tuwunel`: rc=1, the plants reported
  (`exec.Command outside internal/execx ...`, `WaitDelay set and exec.ErrWaitDelay never named ...`).

## Stage (src-go/qa/go-qa.toml, phase detectors)

One stage, `project-rules-tagged`: builds the driver once, then runs
`go vet -vettool=<it> -tags <tag> <packages>` for each pair of an array in the snippet
(busfailpoints and tuwunel over `./internal/teamchat/...`, ccyteamstest over `./internal/teams/...`,
difftest over `./cmd/claude-yolo/...`), printing a line naming the pair first. A failing pair does
not stop the rest; the stage exits non-zero if any failed.

Not covered: `teamchatrelease` (one test file, member/cli; run by the install build).

## Proof

- Earlier, with four separate stages: each failed on a plant in its tag and passed without.
- The single stage with one plant (ccyteamstest): FAILED, the plant reported under the
  `-tags ccyteamstest` line, the difftest pair still run after it (`tagvet-red5.log`).
- Without the plant: passed, all four pairs run (`tagvet-green5.log`).

## Genuine findings, fixed

- `tuwunelhs.Start` ran a binary named by BinEnv: a `dynamicNames` row in `qa/rules/table.go`
  (the env var is the design).
- `presenceTimers` in `matrix/tuwunel_test.go` used time.Now/time.Since: now an `over` timer
  as a select case and an `early` timer read non-blockingly once offline is seen.
- ccyteamstest and difftest builds had no findings.
- `go vet -tags tuwunel ./internal/teamchat/...`, `go test -tags tuwunel -run XXX ./internal/teamchat/matrix/`
  and `go test ./rules/` in qa pass.
