## Round 2 findings

1. **Fixed (major, chmod through a link).** `mkdirMode` (`host/dirs.go:47-61`) now opens the
   name with `O_RDONLY|O_DIRECTORY|O_NOFOLLOW` and runs `Fchmod` and `Fchown` on that
   descriptor. A link in the last part fails the open (ELOOP), and a FIFO or device fails with
   ENOTDIR before any open blocks. The parent parts cannot be steered:
   `/var/lib/teamchat-ctl` sits in root-owned `/var/lib`, so only the last part is the control
   user's. That user can still swap in another real directory, but moving a directory to a new
   parent needs write access on it. So the only directory it can swap in is one it can already
   write, and root's 0700 and chown to `teamchat-ctl` give it nothing new. `fchown(-1,-1)` is a
   no-op, so the call for the 0755 directories and `root/<team>/` is safe.

   - Every root directory make in `host/` goes through this code: `files` (`apply.go:454,456`),
     `writeDropIn` (`:646`), `MkdirStatus` (`:840` and `admin/verbs.go:509`).
     `lockDirectory` (`lock.go:103`) is the one exception. It works under root's own
     `/run/teamchat-admin`, makes no chmod and refuses a link, so it is out of scope.
   - The purge's `os.RemoveAll` of `ctl/<team>/` (`remove.go:198`) works through `unlinkat` and
     `openat(O_NOFOLLOW)` from the parent's descriptor, so it cannot be steered either.
   - The test (`dirs_test.go:85-94`) covers a link that is already there. The race is closed by
     construction: every chmod and chown goes through the descriptor, never through the name.

2. **Fixed (`--seat next` stuck behind a deactivated number).** `admit` (`member.go:184-201`)
   records a deactivated free number as `retired`, saves, and loops. The loop is bounded:

   - Each pass adds a roster member, so `nextSeat` moves on, up to `maxSeatNumber`, where
     `addTarget` refuses.
   - It applies only to `add` with seat 0. An explicit seat is refused with no write, the probe
     handle is refused earlier by `addTarget`, and humans are a separate namespace.
   - A crash after the save leaves a retired handle and no pending record, which is harmless.

   A deactivation that is only transient (an account an operator later reactivates) is retired
   for good. That is n2d-D17's stated rule ("only `retire` deactivates"), and I accept it. D17
   also catches a pending `return`, not only a claimed add: see new finding 2.

3. **Fixed, with a defect in the error path.** A roll-forward that retires a handle is now a
   note, and the caller's verb runs (tested). But the check `errors.Is(err, errDeactivated) && Pending == nil` also passes when the save that clears `pending` failed. See new finding 1
   (major).

4. **Fixed (the guest token copy).** The child writes the copy itself through
   `Deps.GuestDir = paths.GuestTokenDir` (`ctl/<team>/guest/`, its own tree, made 0700), and
   the file is 0600 through `state.WriteFile` (fchmod on an `O_EXCL|O_NOFOLLOW` temporary file,
   rename, then a sync of the directory).

   - The copy is written before the roster save that records the issue. A crash between the two
     leaves `pending` at `credential`. The same verb asked again then resets the password and
     overwrites the copy, and any other verb's roll-forward revokes the credential and removes
     the copy.
   - A password issue, a revoke, `park` and `deactivate` each remove the copy (tested).
   - The child is the only writer. No root or host code names `GuestTokenDir`, and a purge
     removes the copy with `ctl/<team>/`.
   - An empty `GuestDir` fails the step loudly rather than skipping it. D18's "the production
     `Opener` sets it" is a promise for the slice that wires `Sys`.

   The one gap is new finding 2.

5. **Fixed (the drop note).** `claim dropped` is gone, and the retirement path emits
   `member <h> retired`, which MO8 lists. See new finding 3 for the line MO8 still lacks.

## New findings

1. **major: a roll-forward that retires a deactivated handle hides a failed roster save, and the
   verb exits 0.** `apply/member.go:501` with `:386-390`.

   - Evidence: `account` returns `errors.Join(deactivated(h), r.clear(StepAccount))`. `clear`
     sets `Pending = nil` in memory *before* it saves. If the save fails, `rollForward` still sees
     `errors.Is(err, errDeactivated)` and `Pending == nil`, adds its note, and returns nil, which
     drops the save error.
   - Probe `TestProbeR3DropSaveFailureSwallowed` breaks the roster path while the pending handle's
     account is read, so the save fails. Then `member set --human-text true` on an active member
     answers `err=<nil>`, `changed=[member myrepo.3+desk.podman retired]` and the note. The roster
     on disk still holds `myrepo.3` as `claimed` with `pending: member.add`, `step: account`.
   - The play and ccy-teams are told that a retirement and a cleared pending record are done when
     neither was written. That breaks the fail-fast rule and MO8 ("a failure keeps what changed
     before it"). The next verb redoes the work, but this one has already exited 0.
   - The same `Join` also misclassifies the caller's own retry: errors.AsType finds the refusal
     first, so a save failure there exits 70 (refused) instead of failing as an I/O error.
   - Fix: in `account`, save first and refuse after:
     `if err := r.clear(StepAccount); err != nil { return err }; return deactivated(p.Handle)`.
     Then make the check in `rollForward` the deactivated refusal alone. Add the probe as a test,
     with a save that fails.

2. **minor: the D17 retirement leaves a guest seat's token copy and its recorded credential.**
   `apply/member.go:496-501`.

   - Evidence: the `account` step runs for `return` as well as `add`. A pending `return` of a
     `lost` member whose account is found deactivated is retired, but `guestCopy(..., "")` is
     never called, and `m.Cred` and `CredSeq` stay as recorded. n2d-D18 says the copy is removed
     "with the credential (... deactivate)".
   - The token is dead, because the account is deactivated, so the health tick only fails its
     post. But the file outlives the member.
   - It is not reachable in this slice: no code here sets `lost`, and `refuse` catches the
     caller's own `return` first. Only a roll-forward of a return already in progress meets it.
   - Fix: call `r.guestCopy(StepAccount, p.Handle, "")` in that branch, and record the member
     through `r.revoked(m)`.

3. **minor: `member <h> account adopted` is not one of MO8's `CHANGED` forms.**
   `apply/member.go:503`.

   - This is the same class as round 2's finding 5. MO8's list (`claimed|account created|issued|revoked|parked|retired|deactivated|human_text <bool>`) has no `account adopted`, and the play and ccy-teams parse these lines.
   - The line is emitted on every add retried after a crash between `CreateAccount` and the save.
   - Fix: add `account adopted` to MO8 (and to C 3.6.3's line grammar, if it has one).
