## What was built

- `declare`: a `teamchat_teams[]` entry takes `colour`, optional, read by `colour.Parse` (a palette
  name or a legible `#rrggbb`), kept as lower-case stored hex in `Team.Colour`. A refusal is a
  `FieldError` at `teamchat_teams[i].colour` whose problem is C7's text; a non-string is refused
  too. `Team.Canonical()` (`team.json`) writes `"colour"` after `trust` only when set, and
  `DecodeTeamFile` and `DecodeInput` read it back.
- `rooms`: `Team.Colour` goes into `proto.Desired`, so a stored hex adds the main-room event
  `{"colour":"#rrggbb"}` (created as initial state for a new room, else written only when it
  differs or comes from another sender). `planColourClear` writes `{}` when no colour is declared
  and the admin's event says anything else; a team that never had one gets no event (n3e-3 D1),
  and a member's event is neither cleared nor trusted.
- `apply` and `health/view` pass `Team.Colour`, so the view reports a declared colour main does
  not hold as a problem and a converged team has none.

## Decisions

- **D1. `colour` sits last in `team.json`**, after `trust`, so a team file without it stays
  byte-identical to before.
- **D2. The clear is decided in `rooms`, from the room as read**, not in `proto.Desired`, which
  stays as n3e-3 built it.
- **D3. `declare check` is `Decode`/`Approve`**: no separate check was added. The playbook
  documentation of `colour:` is Task 3.3's, and no play or variable file changed.
- **D4. No OF1 test:** this part is host side and talks to one homeserver per call, so there is no
  second team to stop beside it.
