## New finding

### 1. Medium: a member can stop its own removal, so its token is never retired

`lockprobe.go:34-48`, `release.go:93`, `take.go:196` and `release.go:118`.

The probe turns a refused `seat.lock` into an error, and both callers return it. Step 2
renames a directory the member can chmod. Every one of these happens before step 4, the
`Retire`, and the take's `clearHeld` runs the same code. None of them is cleared when the
session ends, because the directory stays.

Exploit: the member plants one of these in its mount and exfiltrates `token`:

- `seat.lock` made a link (`ln -s /dev/null seat.lock`) or a FIFO;
- the seat directory made `chmod 0000` or `chmod 0500`;
- the seat directory made `chown` to another mapped uid, where the user namespace lets it.

The owner then runs `member remove`. Each case was reproduced, and each ends the same way:

| Plant                  | Error                                          |
| ---------------------- | ---------------------------------------------- |
| link                   | `seat.lock: too many levels of symbolic links` |
| FIFO                   | `the seat lock is not a regular file`          |
| `chmod 0000`, or chown | `seat.lock: permission denied`                 |
| `chmod 0500`           | the step-2 rename: `permission denied`         |

In every case the remove stops, the release after the session ends stops, and a take of the
seat by `s2` stops. The token stays alive on the homeserver until someone mends it by hand,
because the remove never reaches step 4 and no take reaches ST6's re-login. The removed member
keeps a working credential for the seat's Matrix user. That widens what the member can do.
Round 3 called the FIFO case "by design" only for refusing to read the file. The design never
meant the refusal to block revocation.

Fix:

- **Release step 1 and `sessionHolds`.** A probe that cannot open the lock, or opens something
  that is not a regular file, is free and names no run, and the release goes on. The member
  gains nothing by it: deleting `seat.lock` already reads as free (`lockMissing`). Also,
  `Restorable`, which is host state, still holds a live session's seat.
- **Step 2.** Rename within `sessions/<session>/`, which is host-owned, for example to
  `sessions/<session>/.released-<team>-<claim>`. A same-parent rename needs write permission
  only on the host-owned parent, never on the member's directory, so no chmod or chown can
  stop it. Then move it to `released/` by renaming its host-owned parent, or leave it there for
  the prune. Alternatively, `fchmod` the directory to 0700 by fd under the lock. That covers
  chmod but not chown.
- Reword SX1, SD3 and SD4 to match: "refused" means not read, never "stops the release".
- Add the five plants above as tests that are red now. Probes that drop capabilities are
  needed for the mode cases, as uid 0 bypasses them.

## Open items in 261022-n2c.md: are they safe to carry?

- **The rest of the round-3 low (open item 1): safe to carry.** It needs this holding's take
  to have died before step 5, and then a take of another seat of the team into the same
  session. The member cannot cause the first: `sessions/<session>/` is host-owned, and the
  mount does not exist yet. The worst outcomes are an ErrBusy on a leave, or an ended
  session's dead copy moved into the wrong quarantine. The other holding's release then finds
  no directory, posts no notice, and still retires its own token. No token is left live.
- **n2c-D13, the double notice: safe to carry.** M22's transaction id stores it once, and the
  failed `notice.json` replace is retried. No member input is involved.
- **n2c-D13, the broken `released.json`: safe to carry.** It is in the host-owned pool
  directory, so no member can break it. The worst outcome is a refusal that needs a hand mend,
  which fails fast and loudly.
