## Findings

01. **major: a crashed `member add --seat next` asked again claims a second seat, and the
    first is left as an orphan that the next verb makes active, and the coordinator if it was
    declared.** `src-go/internal/teamchat/apply/member.go:140-148` (with `nextSeat`, 207-217).
    `target` works out the handle before it looks at `pending`. The pending add's handle is in
    the roster as `claimed`, so `nextSeat` skips it, `p.Handle == handle` is never true, and the
    retry is handled as "another verb".
    Evidence (probe `TestProbeSeatNextRetry`): an add crashes at the Invite, then the same
    `add(0, token)` runs again. The retry answers `myrepo.2`. `myrepo.1` is left `active` with
    `needs: reissue` and promoted to coordinator. The notices are
    `added myrepo.1, role myrepo.1:coordinator, added myrepo.2`. C 3.6.3 says `--seat next` is
    `lxc apply`'s, and a retry is that caller's normal path, so each crash of an LXC bring-up
    leaks a handle and a seat number (and the coordinator role) to an account nobody runs.
    Fix: when the request is `add` with seat 0 and `pending` is a `member.add` whose handle has
    the requested prefix, treat it as the same verb for that handle (resume with the caller's
    credential). Add a test that crashes at each step and retries with `--seat next`.

02. **major: the same verb on the same handle with different arguments is taken as a retry, so
    the new arguments are dropped and the answer is a success.**
    `src-go/internal/teamchat/apply/member.go:144-148`. Evidence (probe
    `TestProbeSetRetryOtherValue`): `set --human-text false` crashes at its rooms step. Then
    `set --human-text true` answers ok (`room main state teamchat.roster`), but the roster keeps
    `human_text false`. The same happens to `add`'s `--human-text` and `--kind`. The caller is
    told it changed something it did not change.
    Fix: after resuming, run the request fresh when it is not an issuing retry (`set`, `park`,
    `retire`: refuse and start again, and `start` already does nothing when the value is
    equal). For `add`/`return`, refuse with 70 when the resumed record differs from the
    request (kind, human_text), naming the pending op.

03. **major: a refusal that comes after `pending` is written blocks every verb of the team for
    good.** `src-go/internal/teamchat/apply/member.go:279-283` with `account`, 398-401. `start`
    writes `pending` and only then does the `account` step check for an account that is there
    but deactivated (refused, 70). Each later verb runs `rollForward` first and hits the same
    refusal.
    Evidence (probe `TestProbeRefusalAfterPendingWedges`): `add` of a handle whose account
    exists deactivated fails with `member.add, step account`. After that, `member set` of
    another member fails with "member.set, step account: ... deactivated", and so does
    `role apply`. `team apply` rolls the record forward in `load` (apply.go:185) and so fails
    too. No verb clears the record, so the team is stuck until someone edits the roster by hand.
    That breaks MO3 ("refusals before any change") and the no-manual-fix rule.
    Fix: look up the account and refuse a deactivated one in `refuse`, before `start`, for
    `add` and for `return` of a `lost` member. Also, a pending record whose step refuses
    (Drift) must not block other verbs: drop an add still `claimed` that has no account, or
    name a way out. Add a test where a refused step leaves no `pending`.

04. **major: root uses the child's `handle` and `credential` to build the bundle without
    checking them against the request.** `src-go/internal/teamchat/admin/verbs.go:250-263`.
    The answer is "the one thing root parses that a less-privileged process wrote" (C 3.3).
    `validate` checks only the handle's form. A `teamchat-ctl` child that is wrong, or has been
    taken over, can name another prefix's or another repository's handle. Root then calls
    `Bundles.Bundle`, the seat side's placement of `seat.json`, for that handle. It also builds
    a bundle for a credential answered to `park`, `retire`, `set` or `role apply`, and for a
    kind other than the one asked for. This is the same class as n2c's two holes.
    Fix: in `underLock`, require that `a.Handle` equals `--handle` (for add: the prefix
    numbered by `--seat`, or any number of that prefix for `next`). Require a credential only
    on `add`, `return` and `reissue`, and with the kind asked for. Anything else is a failed
    answer (1) and no bundle. Add tests with a lying in-process child.

05. **major: a crash in the middle of `mkdir` leaves a directory that is never repaired. The
    worst case is `ctl/<team>/` owned by root, which the child cannot use.**
    `src-go/internal/teamchat/host/dirs.go:24-30, 41-53`. `mkdirMode` runs `Mkdir(0700)` and
    then `Chmod`, and `mkdirOwned` then runs `Lchown`. A directory that is already there is
    accepted as it is. If the process dies after the `Mkdir`, the next first apply (still first,
    because there is no `server-name`) accepts `ctl/<team>/` as root:root 0700. Every child op
    then fails (78) and no verb fixes it. In the same way, a status or drop-in directory stays
    0700 (the board cannot read the status directory). This breaks HS6's "every directory's
    mode is set after the mkdir" for the crash case. Ownership is also never checked (the
    lock directory too, lock.go:111).
    Fix: converge a directory that is there: Lstat it, refuse a link or a non-directory, and
    chown and chmod it to what it should be (or refuse when the owner is not root or the
    intended uid). Add a test that pre-creates each directory with the wrong mode or owner.

06. **minor: when a roll-forward fails, the error names the caller's op instead of the pending
    one.** `member.go:114-119` (`withOp`) sets `e.Op = req.Op` on any `*Error`, so the failure
    in finding 3 reads "member.set, step account". MO8 says a failure names the op and the
    step. Fix: set Op only where it is empty, and set the pending op's name inside
    `rollForward`/`resume`.

07. **minor: a verb that fails after printing a bundle exits 1 (n2d-D11).** `verbs.go:246-263`.
    A failed status refresh exits 1 although a valid credential is on stdout. The usual reading
    of a non-zero exit is that stdout is not trusted, and once the bundle is dropped the handle
    is `active`, so `add` refuses it and only `reissue` recovers. Fix: when a bundle was
    printed, report the refresh failure as a `notes` line (the tick rewrites the record within
    minutes) and exit 0. Or record in C 3.3 that a member verb's document must be read whatever
    the exit code, and have ccy-teams' contract say the same.

08. **minor: stdout carries the "one JSON document" only when the child answered.**
    `verbs.go:130-139`. 64, 75 (TestVerbBusy pins `stdout == ""`), team not applied (70) and a
    child that did not start (1) print nothing on stdout. n2d-D10 reads as if every failure
    prints its document. Fix: either print `{"v":1,"changed":[]}` on every member-verb failure,
    or state in SPEC CV3 and C 3.3 that stdout is empty when no child answered.

09. **minor: `team approve` on a fresh host fails when `/var/lib/teamchat-status/teams` does
    not exist.** `verbs.go:458` makes only the team's own directory, while `writeStamp`
    (host/apply.go:840) makes both levels. Approve runs before the first apply. The admin
    world hides this by pre-creating `StatusRoot/teams` (`admin/world_test.go:105`, and with
    mode 0700). Fix: make both levels as `writeStamp` does, and drop `teams` from the fixture's
    pre-made directories.

10. **minor: `startForBackup` starts the drop-in that is installed even when it names a
    different Tuwunel version from `units.json`.** `host/apply.go:621-641`. C 3.5.2 step 6 and
    HS8 say the inactive homeserver is started "on the version `units.json` records". After an
    upgrade whose start failed (drop-in new, `units.json` old), the backup step starts the new
    binary, which may migrate the database before the backup. While the pin stays on the new
    version, the apply cannot get past step 6. Fix: when `units.json` is there and its version
    differs from the installed drop-in's, write the old drop-in from `units.json` first (as
    for a missing one). Or record the deviation as a decision.

11. **minor: `createOnly` does not fsync the directory after the link.** `host/dirs.go:84`.
    `server-name` and the first `config.toml` can disappear on power loss after the
    homeserver has written a database under that name. That is the C3 property step 4 exists
    for. `state.WriteFile` fsyncs the directory (S15). Fix: open the parent and fsync it after
    `os.Link`.

12. **minor: CV6 is only part built.** There is no `-tags tuwunel` round trip of
    add/role/retire, although CV6 requires one (the handoff lists it as optional). Crash and
    roll-forward tests exist only for add and for some park and retire steps. There are none
    for `return` (`lost`: account created), `reissue`, `set` or `role.apply` at each step. The
    same-verb retry tests check that the new credential works but never that the credential
    issued before the crash is dead (C23: at most one valid credential, after a `LoginDevice`
    that landed). `TestVerbInputRefusals` checks only `code != 0`, so a bad stdin's exit code
    is not pinned. Fix: add these, the Tuwunel run included, because fakehs's device logout on
    a password reset is exactly what C23 depends on.

13. **minor: a deviation from the design is not recorded in the SPEC.** C 3.6.3 says the
    child "keeps a copy of the token as `ctl/<team>/guest/<handle>.token` (0600)" for a token
    credential. The handoff moves this to "the seat side's or `lxc apply`'s", but SPEC-n2d's
    decision table has no row for it. The seat side runs as root or the owner, and the health
    tick reads the copy. Fix: write the copy in `credential`'s token branch (the child owns
    `ctl/<team>/`), or add an n2d-D row and a design-text fix.

14. **minor: a revoke leaves `cred`/`cred_seq`/`cred_ms` pointing at a dead credential.**
    `member.go:423-428`. A roll-forward revoke sets `needs: reissue` but keeps the issuing
    write's `cred_seq`, and a restore decides by `cred` and `cred_seq` (C 3.6.1, 3.12.2). The
    same goes for `park`'s revoke (447-454). Fix: either clear `cred` and raise `cred_seq` on a
    revoke, or state in C 3.6.1 that `cred_seq` is meaningful only when `needs` is null.
