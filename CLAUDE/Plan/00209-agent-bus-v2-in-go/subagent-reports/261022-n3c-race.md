## The cause, in one paragraph

The failure was in the product code, not in the test harness. `back` (EN4,
`member/ends` `Back`) runs in its own goroutine, which `teamsync`'s `sess.ends` starts at the
run's start. It reads main for the member's latest own lifecycle notice and posts `back` if
that notice is `disconnected`. Nothing ordered that read and post against the link's other
lifecycle posts for the same team: `finish` calls `Ends().End` (the run's `disconnected` or
`left`) and a removal calls `Ends().Leave`. Under load, the back goroutine's read came after
the run's own end had posted `disconnected`. It found that `disconnected`, posted `back` after
it, and main said the member was back when it had gone. The tests check that main's latest
notice is `disconnected`, so they waited out the whole 30 s bound. This was a real defect, not
a slow run. pidfd, getppid, LN1 and T20 are not involved: the link saw the death and posted
its end each time.

## Evidence

- **Reproduced under load** (`untracked/scratch/race/starve.bash`, not committed): six copies
  of the two tests and the whole `./internal/teamchat/...` suite pinned to one CPU with
  `taskset -c 0`. One failure in 120 runs: `e2e_test.go:129: not within 30s: me's notices: back, disconnected` (newest first). That is the reviewer's message exactly. Each test is a
  fresh world with a single run, so the only `disconnected` in main was this run's own. A back
  posted after it can only have read main after the end posted.
- **Reproduced deterministically**, in `member/ends/turn_test.go`, against the code before the
  fix (the seams added, no ordering):
  - `TestABackAfterTheEndPostsNothing`: `main, newest first: [back disconnected disconnected]; back sent 1`.
  - `TestAnEndWaitsForABackMidRead/end`: `the disconnected went ahead of back's read`.
  - `TestAnEndWaitsForABackMidRead/leave`: `the left went ahead of back's read`.
  - `TestATurnWaitEndsWithItsContext`: `turn: <nil>, ran true`.
- **`TestE2EKeeperKilled`**: no capture of its notices exists, because the busfailpoints
  stage's output gave only the FAIL line. It makes the same assertion (main's latest notice is
  `disconnected`) after the same end path (`finish` with `keeper-died`), so the same race
  produces it. This is inferred, not captured. Another cause would give a different signature:
  an end whose 5 s bound (`endWait`) expired before its post would log
  `end the session: context canceled` in link.log, and would fail the test's own 5 s check
  first only if the notice came late, not never. No run here showed that.

## Defect and class

- **Originating instance:** `src-go/internal/teamchat/member/ends/ends.go`, `Back`
  (`notice.LatestOwn` at the old line 118 and `post` at the old line 122). It is started from
  `member/teamsync/session.go` `sess.ends` (`wg.Go(... t.back ...)`).
- **Class:** a member's lifecycle notice decided from a read of main and posted later, not
  ordered against the run's other lifecycle posts for the same team in the same process
  (check-then-act across goroutines).
- **Hazard:** main's latest lifecycle notice is wrong. Every reader of the member's state
  takes that notice as the truth: the host's health checks, a peer, and the next run's Close
  and Back.

## Rule

- **Detector:** the project's `go/analysis` rules. File `src-go/qa/rules/lifecycleturn.go`,
  identifier `project_lifecycle_turn`.
- **Message:** `project_lifecycle_turn: lifecycle notice read or posted outside the team's turn: <name>`.
- **Documentation:** the rule's doc string and `CLAUDE/GoProjectRules.md#project_lifecycle_turn`.
- **Width:** inside `internal/teamchat/member/ends`, every use (call or method value) of
  `notice.LatestOwn`, `notice.Disconnected` or `notice.Client`'s `Messages`/`Send` (and so of
  `team.Notices`) must be inside a function argument of the package's `turn`. So must every
  use of a package function that reaches one outside a turn, followed through any chain of
  helpers.
  - A goroutine started by `go` or by a method named `Go` is outside the turn, even when it is
    written inside one.
  - Uses are reported in exported functions and in functions nothing in the package uses, so
    a helper is judged where it is called.
  - It covers the posting partners (End, Leave) as well as the deciding read (Back, Close).
    Either side of the race carries the hazard: an unordered post is the one that comes
    between.
  - `RoomState` (the roster read) is deliberately excluded: it decides no lifecycle notice.
- **Next wider rule considered:** every read-then-post of a lifecycle notice anywhere in
  teamchat. It was not built. The only other posters are the host's `notice.Disconnected`
  callers (`admin/serveview.go`, `member/client/seat.go`), and they run in other processes,
  where no in-process turn can order them. The run's transaction id (`tc-disc-<run>`) makes
  them safe, which is a different defence for a different hazard.
- **Not caught** (written in the doc): that `turn` itself serialises per team and refuses a
  back after an end, which the ends tests hold. Also not caught: a read or post through
  another package's function other than the named ones.

## Fixes

- **All four functions were examined individually.** Each now runs its reads and posts inside
  `e.turn(ctx, team, fn)`, a one-slot channel per team that is waited on under the caller's
  context.
  - `End`: marks every team it is given as ended before waiting for its turn, then posts in the
    turn, only for this run's teams, as before.
  - `Leave`: marks the team ended, then posts in the turn.
  - `Back`: in its turn, posts nothing once the team is ended.
  - `Close`: runs in the turn unchanged.
- **The ended mark is set before the wait.** It is held under the turns' mutex, not inside the
  turn. Without that, an end whose bound ran out while back held the turn would let a later
  back post after the run's end. The conformance review found this (finding 4), and
  `TestAnEndThatCouldNotWaitStillStopsBack` reproduces it: red, `Back: <nil>, sent 1; main [back disconnected]`, then green after 05663fd06.
- **Nothing was suppressed and no instance was left.** After the fix, `go vet -vettool=driver ./...` over `src-go` exits 0.

## Decisions referred to the owner

None. Every instance is fixed, and the rule is merged at full width.

One behaviour is new and worth the lead's eye. An end that arrives while back holds the turn
now waits for back's read and post, inside the end's own 5 s bound (`endWait`). Back holds
the turn for one `Messages` page and one `Send`, and possibly one roster read. Cancelling
back instead would not be safe, because a cancelled send can still land after the end.

### What the load runs show, and what they do not

On this machine the race fired once in 750 pre-fix runs. So a clean 960 runs after the fix is
consistent with the fix, but is not by itself strong statistical evidence: it is about 72%
confidence at the observed rate. The strong evidence is deterministic:

- The e2e failure's signature (`back` newest, over the run's own `disconnected`) is reproduced
  exactly by `TestABackAfterTheEndPostsNothing` against the unordered code.
- The mid-read orderings are reproduced by gated reads, not timing.
- All of these tests are red before the fix and green after.

The qa-reviewer's own runs (a load average near 70) were heavier than anything reproduced
here. The lead's next full qa-all (`-shuffle=on`, the busfailpoints stage) is the natural
confirmation at that load.
