## What was built

New package `internal/teamchat/member/statusline`, the `teamchat status-line` verb:

- `statusline.go` holds `Main`, the run, the signal relay and the stdin read beside the cancel.
- `inner.go` holds the inner line: the settings lookup and the `/bin/sh -c` run.
- `segment.go` holds the team segment: one read, one probe, the pieces, the red forms and
  notes, and the wrapping.
- `src-go/qa/rules/table.go` gets one `shellStrings` row, for `deps.runInner` in its own hunk.
  `project_seam_commands` refuses a shell `-c` string without it.

The verb is not registered. `status-line` stays on `cli`'s `unbuilt` row, and n3e-12 wires it
in `cmd/teamchat` as `"status-line": statusline.Main`.

## Exported API as built

```go
package statusline
func Main(e cli.Env, _ cli.Invocation) term.ExitCode // a cli.RunFunc; takes no arguments
```

Nothing else is exported. The status line reads `state.Status`/`StatusTeam` from n3e-3 (`Member`,
`Colour`, `Stalled`, `Desired`, `UnusableHookStdin`, `WrittenMS`) and the n3e-4 functions
`client.Runtime`, `client.ReadDown` and `Down.{State,Kind,Session}`. It writes nothing.

## Behaviour (as tested)

- **The inner line.**
  - It is skipped while `TEAMCHAT_STATUS_LINE_INNER` is non-empty.
  - The project is the first absolute of `workspace.project_dir`, `$CLAUDE_PROJECT_DIR` and the
    payload's `cwd`. A payload over 1 MiB, or one that is not a JSON object, is none.
  - The command is looked for in `settings.local.json`, then `settings.json`, then
    `$CLAUDE_CONFIG_DIR/settings.json` (or `$HOME/.claude/settings.json` when HOME is absolute).
    A blank command, a non-string, a missing statusLine object, `teamchat status-line` and
    `…/teamchat status-line` are all passed over.
  - A file that is missing is skipped. A file that exists but cannot be read stops the search
    with red `status line: <path> cannot be read`; that covers a directory, a FIFO (opened
    `O_NONBLOCK` and never waited on), a file over 1 MiB, a file that is not UTF-8, and a file
    without read permission. A file with bad JSON, trailing junk included, stops it with
    `<path> is not valid JSON`.
  - The command runs as `/bin/sh -c` in the project, when that is a directory. It gets the
    payload on stdin, `TEAMCHAT_STATUS_LINE_INNER=1` added to its environment, its own session,
    and the status line's stderr.
  - Its stdout keeps the first 64 KiB, has U+FFFD for each invalid byte, and loses its trailing
    `\n`s.
  - A non-zero exit draws `<text> ESC[31m(status line exit N)ESC[0m`, with N negative for a
    signal. A command that cannot be started draws `(status line could not be run)`.
  - At 10 s on the injected clock the group is killed, and the output is only the timeout note.
    A grandchild that left the group and holds stdout is let go after a 1 s grace; it is tested
    with `setsid`.
- **The cancel.** SIGTERM, SIGINT or SIGHUP gives 128+n with nothing on stdout. This holds
  before the start (during the stdin read) and after it, when the group is killed and the child
  reaped (the test checks `kill(pid, 0)` is ESRCH).
- **The segment.**
  - With no TEAMCHAT_RUNTIME (or a foreign one) there is no segment.
  - Otherwise the status line opens the run directory (`homefs.Private`) and makes one
    `lock.Probe(link.lock)` and one `state.Read(status.json)`.
  - **Link held:** each team is drawn as `<team>: <member|member?> (<c|w|p|role?>)`, then its
    marks in the order `(down) (stalled) (missing) (failed)`. Every piece but the last ends
    with `,`, and each piece is one `colour.SGR(Colour)…colour.Reset` span. When teams are
    held and `written_ms` is more than 90 s behind `WallMS`, a red `teamchat not answering`
    follows. Exactly 90 s is fresh, and a time ahead of the clock is fresh.
  - **Link free:** one red form from `ReadDown`:
    - `teamchat restarting`
    - `teamchat starting`
    - `teamchat stopped: ccy-teams restart <session>` (ccy and lxc)
    - `teamchat stopped: relaunch this session`
  - Red `teamchat membership refused` and `teamchat hook input unusable: <n>` are drawn with
    or without teams, with the link up or down.
  - Held, with no team and no note, there is no segment.
- **The wrapping.** The label is `👥 ` (3 columns), and a continuation row is indented 3
  spaces. Rows wrap greedily at `COLUMNS` (1-6 digits, above 0; anything else is one row)
  between words, and escapes are not counted. A team piece is one word, and a red note is one
  word per space. Each span is one escape and one reset, and the row's label or indent sits
  inside its first span, so a red-only row is one `ESC[31m` span with the label included.
- **OF1.** One team `(down)` beside a running one is drawn, and the exit is 0. A status.json
  that is missing, over 64 KiB, undecodable or another run's draws the red stopped form while
  the link is down, and no segment while it is held. A run directory that cannot be opened
  draws the stopped form. A failed stdout write still exits 0.

## Decisions

01. **The inner command runs through `execx.Runner.Run` with `NewSession`, not
    `Starter.Start` (15a).** `execx.OS`'s session run was built for this command (its doc names
    SPEC-status-line S9-S12), and v1's Go port runs on it. It kills the group at cancel or at
    the deadline, and waits a bounded grace for a pipe held outside the group. Nothing new was
    needed in execx. The deadline is a `clock.AfterFunc` cancel, so the tests drive it on the
    fake clock. The "bounded pipe read" is a writer that keeps 64 KiB and drains the rest.
02. **The grace is 1 s** (`execx.OS{Grace: time.Second}`), not execx's 3 s default. After the
    10 s kill, a grandchild holding stdout delays the render by at most this.
03. **The settings files follow links, as Claude Code does, and their owner is not checked.**
    The open is `O_NONBLOCK|O_CLOEXEC`, so a FIFO is never waited on, and only a regular file of
    1 MiB or less is read. The command found is the one Claude Code itself would run from the
    same file, so the status line runs nothing the session would not.
04. **The JSON of the payload and the settings is read with `encoding/json` (`UseNumber`), not
    `proto.Parse`.** These are Claude Code's files, not teamchat's records. A strict A 2.1
    reading (no repeated key, ±2^53 integers) would turn a settings file Claude Code accepts
    into a red "not valid JSON". UTF-8 is checked first: invalid UTF-8 is "cannot be read",
    and trailing junk is "not valid JSON".
05. **Where the comma and the label go.** The comma is inside its team's span. The label (or
    the indent) sits in the first span of its row, so a team row's label takes the first team's
    colour, and a red row is one span. Two teams of the same colour are still two spans.
06. **The notes' order** is the team pieces, `not answering`, `membership refused`, then
    `hook input unusable`. While the link is down, the stopped form comes first and the two
    status.json notes follow it, when status.json reads.
07. **The width counts bytes.** Every drawn word is ASCII: team ids, `<repo>.<seat>` names,
    session names and the fixed texts. The label alone is counted as 3 columns. No width table
    is imported (`internal/ui` would bring Charm into the member binary).
08. **status.json counts only when it is this run's** (`run` equal to the run directory's
    name); any other run's file is treated as unreadable.
09. **A held link.lock with an unreadable status.json draws no segment** (the brief: "the red
    stopped form or no segment"). The link is up and will write the file.
10. **A ccy or lxc failure with no session name** cannot pass keeper.json's codec, but it would
    draw the `relaunch this session` form.
