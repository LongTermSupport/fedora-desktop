## Findings

### F1. BLOCK: a join that a failed phase made is never recorded, so removing the entry never revokes the token

- Where: C 3.9.2 step 10 (`DESIGN-v2-C-host.md:1845`, "only after the phase succeeded"); SPEC-n3
  n3-D12 (`SPEC-n3.md:916`, "the present phase only after it succeeded"); the reissue rationale
  at `DESIGN-v2-C-host.md:1769-1772` relies on that rule.
- Scenario: team T has entry A in container c1 and entry B in c2, both running. In the present
  phase A is joined at step 06 (now `active`), its bundle is placed at step 07 and its membership
  written at step 08. B's `place-bundle` exits 78 in c2, which is still running, so the phase
  fails and step 10 writes no record. The owner then deletes A's entry, or sets it to
  `state: absent`. The absent phase finds the leavers from record entries and from `absent`
  entries that have a recorded handle. A has neither, so nothing is parked. A's guest still holds
  a valid token and keeps reading and posting in T. If c1 stops before the next run, A's line is
  `DEFERRED` with no known handle, and the gap stays open. A `SIGKILL` between step 06 and step 10
  leaves the same gap in any design that writes the record only at the end.
- Built code: the WIP `apply.go:141,969-988` (`finish`) writes the record after every phase,
  failed or not. So the text and the code it is meant to describe already disagree. The rework
  file does not mention record timing at all.
- Fix: under the team lock, record each entry's handle (status `deferred`) as soon as its step 06
  join returns, and before step 07. Write the record at the end of every phase, whether it failed
  or succeeded. Say this in step 10, in n3-D12 and in LX9, and add a rework item. Keep "`active`
  with no record entry is `reissue`" only for a restored record. Add a test: a phase fails in
  another container after a join, the entry is removed, and the absent phase parks the handle.

### F2. MAJOR: n3b-D3 (with an OfflineError and another error, the other error decides the exit) is written nowhere

- Where: SPEC-n3 section 10 (`SPEC-n3.md:934-935`): n3b-D1 says a targeted offline member is 69,
  and nothing says what happens when another error comes with it. No chapter, no spec and no
  rework item mentions n3b-D3. A grep of every worktree finds the ID nowhere.
- Scenario: `lxc apply --member c1/<k1> --member c2/<k2>`. c1 is stopped, so its member is an
  `OfflineError`. c2 is running and its `.git/config` has an `insteadOf` rewrite, which is
  refused. The WIP `Apply` returns `errors.Join(r.errs...)` (`apply.go:142`), and the admin side
  that maps an error to an exit code is not built yet (p4's handoff, step (d)). A mapper that
  tests `errors.As(*OfflineError)` first exits 69, "offline, try later", and hides a real refusal
  (70) that will never fix itself. The absent phase (`absent.go:205`) and `restart.go` have the
  same problem.
- Fix: add an n3b-D3 row to SPEC-n3 section 10: an exit of 69 only when every error is an
  `OfflineError`, otherwise the class of the first error that is not offline decides. Point
  C 3.9.3 or LX2 at it. Add a rework item for the admin wiring, with a test that joins an
  OfflineError and a refusal and expects 70.

### F3. MAJOR: two users on one checkout fail the phase, against "any number of entries per checkout"

- Where: C 3.9.2 step 03 (`DESIGN-v2-C-host.md:1760-1762`, "each checkout once, however many
  seats name it ... `.claude/ccy/ccy.env.local` (owned by the agent user's uid, else refused)");
  SPEC-n3 LX4 (`SPEC-n3.md:285`); 3.9.1 (`:1611-1614`) promises any number of users and
  checkouts.
- Scenario: in one container, `alice` runs the coordinator seat and `bob` a worker seat on
  `/srv/repo`, whose `ccy.env.local` is owned by alice. The file is read once, then checked
  against which uid? If it is checked against each entry's uid, bob's entry is refused, and since
  "any refusal here fails the phase", every team's members fail on every run. A user move on an
  existing checkout meets the same refusal until someone changes the owner by hand.
- Fix: say who must own the file when entries of several users share a checkout. For example: it
  is owned by one of the agent uids that the checkout's entries declare, and is not group- or
  other-writable. Or refuse a checkout shared across users by name at step 01, and say in 3.9.1
  that a checkout belongs to one user. Add a rework item and an LX1 test either way.

### F4. MAJOR: a user move whose old user is gone from the guest never finishes

- Where: C 3.9.2's absent phase (`DESIGN-v2-C-host.md:1863-1872`, steps 2-5 "under the old user
  from the record"); SPEC-n3 LX8 (`SPEC-n3.md:347-353`).
- Scenario: the owner renames agent user `u1` to `u2` in the container, or deletes `u1`, and
  changes the entry's `user` to match. Steps 2 and 5 run `teamchat guest` as `u1` through
  `lxc-attach -u <uid>`, whose uid and home come from the guest's `/etc/passwd`, but `u1` is not
  there. The text does not say what happens. If it fails the phase (a running container's fact),
  every play fails until someone edits by hand. If it is `DEFERRED`, the record entry stays
  `left` under `u1`, and the new user's seat is held back as "the seat's files under its old user
  are not yet removed" on every run, for ever.
- Fix: if the record's user has no `/etc/passwd` entry, it has no guest files to clean that the
  host can reach, and its token is already dead. So run steps 1 and 3 (root removes the unit),
  skip steps 2, 4 and 5, delete the host copy, and rewrite the record entry for the declared user
  (`deferred`, handle kept). Add an LX8 test.

### F5. MINOR: a missing container drops a user move's record entry, so the handle is derived again

- Where: `DESIGN-v2-C-host.md:1911-1913`, against `:1868-1872` ("a user move keeps its handle").
- Scenario: a user move is pending, and the container is deleted and re-created from the same
  name. The absent phase drops the entry, and the next present phase derives the handle again
  from the guest. If the re-created checkout's origin changed, a new account is made instead of
  meeting step 03's refusal.
- Fix: when a missing container's leaving entry is a user move, rewrite it for the declared user
  (`deferred`, handle kept) instead of dropping it, as step 5 does.

### F6. MINOR: the key-collision rule reads as refusing an entry against its own record entry

- Where: the names table (`DESIGN-v2-C-host.md:1635`, "Two entries of one container (any team,
  declared or in a record) with one key are refused"); step 01 (`:1725-1727`); LX1
  (`SPEC-n3.md:251-252`).
- Scenario: a declared entry and its own record entry always share a key. Read literally, every
  converged member is refused at step 01.
- Fix: say "two entries with different (team, checkout, seat) whose keys are equal, which is a
  hash collision".

### F7. MINOR: a newcomer's equal handle fails the whole play when an old container starts

- Where: `DESIGN-v2-C-host.md:1774-1779`.
- Scenario: a hand-edited entry in stopped container c1 (never joined) and a joined entry in c2
  derive the same handle. While c1 is stopped nothing is compared. The day c1 starts, step 03
  refuses both and fails the phase for every team, until the owner edits the declaration. A
  container start turns into a play failure, and the refusal names both entries when only the
  entry with no handle is wrong.
- Fix: when one of the equal-handle entries holds the handle in the record, refuse only the other
  (the one with no handle) by name, as that entry's failure. Or keep the phase failure and say so
  as a deliberate exception to the offline rule.

### F8. MINOR: step 05's text was reworded but still contradicts n3b-D1

- Where: `DESIGN-v2-C-host.md:1809-1813` ("Any failure in a container still running fails the
  phase"). n3b-D1's handoff, section 2a (`261022-n3b-handoff.md:467,488`), and the WIP
  (`apply_test.go:371-372`) make `gh` and `reach` offline for that member.
- Scenario: a builder working from C alone fails the phase on a guest that cannot reach GitHub.
  With n3b-D2's check once per (user, team), the offline result also covers every seat of that
  user in that team, and the text does not say so.
- Fix: in step 05, say that `gh` and `reach` make every seat of that (user, team) offline
  (n3b-D1), and that the other codes fail the phase.

### F9. MINOR: the rework file misses changes the specs require

- Where: `subagent-reports/261022-n3b-d2-rework.md`.
- Missing: the record-write timing (F1); n3b-D3's exit mapping in the admin wiring (F2); the
  checkout ownership rule (F3). In `apply.go`, the step 01 key check needs the records of teams
  outside `--only-teams` too. The WIP `validate` reads only the acted teams' records
  (`apply.go:163-176`), while step 01 says "across every team's entries and LXC record entries".
- Fix: add these items to the `apply.go` and admin sections.
