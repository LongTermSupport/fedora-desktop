`DecodeHookArgs` refuses an op that is not a hook op. It also refuses:

- a payload that is neither `ok` nor `unusable`;
- an `unusable` reason that is given without an unusable payload, or missing from one, or
  outside the closed set;
- an unusable payload that carries payload fields;
- a field that belongs to another hook: `source` off session-start, `stop_hook_false` off
  stop, `reason` off session-end;
- any field over its byte bound.

## What the tests prove

- **HK1, the payload:**
  - exactly 1 MiB is used, and 1 MiB + 1 is `size`;
  - `\xff` is `utf8`;
  - `[]`, `"x"`, two objects, trailing junk, an empty stdin and a float are `json`, and so is a
    stdin that fails to read;
  - every case still sends the socket and the token;
  - a field of the wrong type or over its bound is absent, not unusable;
  - `stop_hook_false` is set only by the JSON literal `false`.
- **No `TEAMCHAT_RUNTIME`** (unset, or naming no session): `{}`, exit 0, and the dial seam
  counts no dial.
- **A link that answers:** its line is printed byte for byte; the request carries the op, the
  kit and a deadline of boot + 300 ms.
- **A link that never answers:** at 300 ms on the fake clock, SessionStart and
  UserPromptSubmit print the recovery for each reading, and Stop and SessionEnd print `{}`.
  The readings are: restarting with its seconds, starting, failed ccy and failed lxc (each
  naming `ccy-teams restart work-1`), failed host, `keeper.json` missing, and the keeper gone.
  Every exit is 0, and the run directory's listing is unchanged.
- **Malformed answers fall back too:**
  - a close before any line, or before the done;
  - an answer that is not an object, or not JSON;
  - a done with no answer, or a malformed done;
  - a done with a failing exit, or an ack, after the answer;
  - a line over 1 MiB.
- **No `link.sock`:** the hook answers at once, without waiting for the deadline.
- **OF1:** one team stopped and one down beside a running team's pending count make one answer
  line, printed whole, exit 0.
- **The token** reaches the link and never stderr, stdout or any `fmt` verb of the request or
  the args (`%v %+v %#v %s %d %x %q`).
- **Exits:** a failed stdout write keeps exit 0. An event outside `kit.Hooks` is 64, and the
  parser refuses it first. `kit.Hooks`, `cli.HookEvents` and the op table agree.
- **hooktext:**
  - every answer is ASCII with no control character, and parses strictly;
  - every `teamchat` command in `All()` parses with `cli.Parse`;
  - a test reads `hooktext.go`'s syntax tree and fails when a `tmpl*` const has a fixed part
    that no sample shows; the template count (20) and the sample count (15) are pinned.

## Decisions

01. **The runtime check comes before the stdin read** (the brief lists them the other way).
    With no session, the hook answers `{}` without reading stdin, so a stdin left open cannot
    hold it. The 300 ms deadline starts after the read.
02. **A refusing done is told as its message.** When the link answers only a done carrying an
    error (for example, the wrong kit), SessionStart and UserPromptSubmit show that error's
    message through `Recovery`; Stop and SessionEnd get `{}`. The message comes from the
    link's own fixed template, and `ReadDown` would misreport a running link as "starting".
03. **A request that cannot be framed is `{}`** (for example, a binary built with no digest).
    No reading of `keeper.json` describes that fault.
04. **Field bounds keep a request under the 64 KiB `MaxRequest`.** A payload string or an inbox
    variable over its bound is absent, and so is an inbox variable that is empty or not
    UTF-8. The link judges the contents (`AcceptFacts`).
05. **The answer shapes are hand-built with `proto.EscapeASCII`**, so every answer line is
    ASCII with no control character (C1 and DEL included), as `inbox.UserLine` is.
    `hooktext` uses its own small fill instead of `exits.Format`, because `exits.Fill` exposes
    no text.
06. **Three template choices:**
    - the frame calls a role outside the roster's set `member`, with no role line;
    - an invalid description is left out;
    - a delivery mode other than socket or wait gets the `none` line ("run teamchat recv to
      read them").
07. **`StopPending` gives the same five-part breakdown as `Pending`.** B 2.8 writes it as
    `(...)`; the brief listed two parts.
08. **`Missing(1)` is singular** ("1 item is pending again"), from its own template.
09. **`Recovery` takes the message string**, as correction 15a gives it. It passes the
    message through when it is one clean line of 512 bytes or less, and otherwise gives a
    fixed line.
10. **Redaction covers both types.** `Request.String` shows the args with any non-null
    top-level `token` member redacted, and only the size of stdin. `HookArgs` keeps no
    `MarshalJSON` override, because its JSON is the wire.
