## Defect and class

Originating instance: `src-go/internal/teamchat/member/link/hooks_test.go:229-235` (as it was):
`armed := w.clk.Waiters()`, a goroutine that dials the link socket and then writes a hook
request whose deadline is `w.clk.Boot() + 300ms`, `w.clk.BlockUntil(ctx, armed+1)`,
`w.clk.Advance(hookDeadline)`, then an unbounded `<-got`.

What happened: the link server arms its read limit (`server.go`, `readLimit`, 5 s) on accept,
before it reads the request, and stops it once the line is read. Under load, the dial was
accepted and the read limit armed before the hook goroutine had built its request, so the
count reached `armed+1` on the read limit; the test advanced 300 ms; the goroutine then read
the advanced boot clock for its deadline, so the server armed the op's deadline 300 ms past the
advance, and nobody advanced again. `serveHook` sat in `AwaitPID` and the test in `<-got` until
the binary's timeout; `announceTeams` and the engine's loops in the dump were idle, not stuck.

Class: a test that synchronises with a fake clock by the number of armed waiters and then
advances it. Hazard: a count says how many timers are armed, not which; the code under test
arms, stops and re-arms its own timers on its own goroutines, so the count can be made by a
timer the test did not mean, the test advances too early, and the timer it meant is armed
afterwards at the new time and never fires (a hang), or the test passes on a different timer
than the one it describes.

## Rule

`project_fakeclock_count` (`src-go/qa/rules/fakeclockcount.go`, registered in `rules.All()`),
documented in its `Doc` and in [GoProjectRules.md](../../../GoProjectRules.md#project_fakeclock_count).
Message: `waits on a count of the fake clock's waiters (<method>): wait for the timer with AwaitDue`.

Width: a fake clock is any type whose method set has `Advance(time.Duration)`, so a second fake,
a value receiver or an interface holding one is judged too. Flagged: any use (call or method
value) of its method that takes a `context.Context` and an integer (a count wait, whatever it is
called), and a call of its no-argument `int` method inside a `for` statement or in a `return` of
a function literal (a poll). Excluded as hazard-free: a count asserted once (`if clk.Waiters() != 0`, in a range loop or a `t.Run` body), an integer method with no context (`StepWall(ms)`),
a reading that is not an `int` (the first sweep flagged `WallMS() int64` in fakehs's `Now`
closure in `teamsync/world_test.go:75`, a wall reading and no wait; the rule was narrowed to an
`int` result, and that case is a clean line of the fixture).

Next wider rule considered: flag every read of a fake clock's waiter count, assertions
included. Not built: an assertion after the code has finished (`Waiters() != 0` once a sleep
returned) carries no advance and no race, and the fake's own tests need it.

The fix the rule points at is new API: `clock.(*Fake).AwaitDue(ctx, d)` returns once a waiter
due `d` from the fake's present reading is armed, so a test names its timer by when it is due.
`BlockUntil` is deleted.

## Fixes

Every instance examined individually (the helper callers by reading each call's timer):

- `link`: the hook op (the original, below); the adds wait (`addsWait`) twice; the link lock's
  50 ms retry; the server's deadline (moved from 5 s to 3 s so it is not readLimit's 5 s), its
  read limit and its ack wait.
- `client`: the reconnect backoff steps (1, 2, 4 s, the 5 s cap) and the grace timer.
  `TestWaitAcrossARestart` listened before the fourth backoff, so the count was met by either
  the 5 s sleep or the post-dial grace timer; it now waits for the 5 s sleep, then listens.
- `engine`: `armed(n)` became `awaitDue(d)`; `dworld.advance(d)` waits for the timer due `d`, and
  `short(due, d)` for an advance that falls short of it (the 1 ms-before cases).
  `TestTrailingFactsAloneOnceAMinute` advanced 2 s on the count of the loop's minute hold (no
  2 s pace is armed there); it now waits for the minute and advances 2 s short of it.
- `keeper`: `advance(d, also...)` waits for the timer due `d` and each one in `also` (the stop's
  TERM and KILL; the restart backoff and the owed notice's 30 s); each post-crash wait names its
  backoff (1 s \<< n).
- `hook`, `inbox`, `teamsync`, `prepare`: the 300 ms hook deadline, the phase bound, the long
  poll and the version wait. `inbox.expireUntil` keeps its loop (every phase bound is 5 s, so
  the stopped connect bound and the auth bound share a due) and now waits on the bound, not a
  count.
- `clock`: the fake's own tests use `AwaitDue`; the zero-count wait after a cancelled sleep is
  an assertion (the waiter is disarmed before `Sleep` returns); `TestAwaitDue...` prove another
  timer, a stopped timer and a due counted from arming do not answer it.

## Toolchain

As remediation 1 (`go/analysis` in `src-go/qa/rules`, `analysistest`, the driver under go-qa).
Single-rule run: `go vet -vettool=<driver> -project_goroutine_end [-tags=X] ./...` from

## Defect and class

Originating instance: `internal/teamchat/member/link/link.go:167`, `go l.read()`. Its stop,
`close(l.quit)`, was only in `teardown`, deferred after the launch wait and the engine's build;
every link that ended before the launch left `read` blocked on its unbuffered send to `l.msgs`.

Class: a `go` statement whose goroutine signals no end, so no owner can wait for it. Hazard:
nothing proves it stopped; a stop missed on one path leaks it for the life of the process with
what it holds.

## Rule

`project_goroutine_end` (`src-go/qa/rules/goroutineend.go`), documented in its `Doc` and in
[GoProjectRules.md](../../../GoProjectRules.md#project_goroutine_end). Message: `goroutine
signals no end, so no owner can wait for it: defer close(done) or wg.Done in it, or start it
with a WaitGroup's Go, and wait for it`. Width and exclusions are in the catalogue section.

Narrowing, made in this part: a body also signals its end when every return of its own
directly follows a close, `Done` or send and it cannot fall off its end without one (its last
statement is one, or a `for` with no condition and no `break` or `goto`). Such a body ends only
through a signalled return, which an owner can wait on as surely as a deferred close; it was
flagged only because the rule read the last statement. The one real case is
`teams/flow/kit.go:264`, the line reader (each return follows a send on `got`, and `readLine`
receives `got` on both of its paths: the searcher marked it DOES NOT). A `break` or `goto`
anywhere in the loop, an inner switch's included, keeps a body flagged: the rule cannot judge
where it lands. Fixture lines: every return sends (clean); one return with no send, a loop
left by `break`, a loop with a condition (flagged). Red: `TestGoroutineEnd` reported the clean
case as an unexpected diagnostic before the change; green after.

Next wider rule considered: every goroutine's end must be awaited on every path of its owner.
Not built: which function is the owner, and whether each path reaches the wait, is a
whole-program question of the call graph, not a shape the analyzer sees in one package; the
run-time half, `leakcheck`, answers it for the code the tests run.

# Remediation 3: project_rawconn_probe (the pidfd watch that never fired)

Commits: `7ee7309ec` (the defence, red) and `db70c7c45` (the instance, the original, green).

## Specification followed

As remediation 1.

## Toolchain

As remediation 1. Single-rule run: `go vet -vettool=<driver> -project_rawconn_probe ./...`.

## Defect and class

Originating instance: `internal/teamchat/member/link/parent.go:62` (as it was), `watch`'s
`rc.Read(func(uintptr) bool { was := armed; armed = true; return was })`: the first call
answered "not ready" without testing the pidfd, to arm the wait. `RawConn.Read` calls
`prepareRead`, which resets readiness the poller has already seen, before the first callback.
A keeper that died, and whose pidfd the poller saw readable, before the watch goroutine first
ran was never seen: `TestTheWatchFiresWhenTheProcessEnds` hung under load, and in production
the link would outlive its keeper.

Class: a RawConn `Read` or `Write` callback that answers without testing its descriptor.
Hazard: readiness already seen and reset is never seen again, so the wait parks until an edge
that has passed, and never ends (or, answering true, ends on no event at all).

## Rule

`project_rawconn_probe` (`src-go/qa/rules/rawconnprobe.go`), in `rules.All()`, documented in
its `Doc` and in [GoProjectRules.md](../../../GoProjectRules.md#project_rawconn_probe). Message:
`RawConn callback answers without testing its descriptor, so a readiness Read has reset is
missed: poll the descriptor on every call`.

Width: any method named `Read` or `Write` of RawConn's shape (`func(func(uintptr) bool) error`),
on any type (an interface over a file's conn is judged too), in production and test files. The
callback must be a function literal or same-package function whose descriptor parameter is named
and read; an unnamed, blank or unread descriptor is flagged, and so is a function value or
another package's function (its body cannot be seen). Excluded as hazard-free: `Control`, which
runs once and decides no readiness, and methods of another shape.

Next wider rule considered: the callback must pass its descriptor to a readiness test
(`unix.Poll`, a read answering false only on `EAGAIN`). Not built: what counts as a test is
open-ended (a helper, a syscall wrapper, a struct the descriptor is put in, as the keeper's
`PollFd`), and the search found no callback that reads its descriptor without testing it.

## Proof

Fixture `src-go/qa/rules/testdata/src/fix/internal/badraw`, run by `TestRawConnProbe` (every
`want` met, nothing else). On the real tree at `7ee7309ec`: 1 finding,
`internal/teamchat/member/link/parent.go:62:21`, the same untagged, with `busfailpoints` and with
`tuwunel`; none in `qa`.

## Independent search

Dispatched before the rule, kept out of the rules and driver; its record is
[261023-n3e-10d-readiness-search.md](261023-n3e-10d-readiness-search.md). Text search found

## Sweep and count

Scope: first-party Go in both modules, production and test files, `vendor/` and `testdata/`
excluded, untagged and with `busfailpoints` and `tuwunel`. 1 instance.

## Fixes

`parent.go`: the callback is `pidfdReadable`, a zero-timeout `unix.Poll` of the pidfd on every
call (as the keeper's wait), answering true when the pidfd is readable or the poll fails, so a
failure ends the wait rather than parking it. `watch` is split into `openPidfd` and `watchFile`
so a test can hold an open, registered pidfd before the watch reads. The keeper's copy is
left in its own package: the two packages share no internal helper package, and a third for one
eight-line function is more weight than the duplication. The sweep reports 0 after.
