## Defect and class

Originating instance: `src-go/internal/teamchat/member/link/hooks_test.go:229-235` (as it was):
`armed := w.clk.Waiters()`, a goroutine that dials the link socket and then writes a hook
request whose deadline is `w.clk.Boot() + 300ms`, `w.clk.BlockUntil(ctx, armed+1)`,
`w.clk.Advance(hookDeadline)`, then an unbounded `<-got`.

What happened: the link server arms its read limit (`server.go`, `readLimit`, 5 s) on accept,
before it reads the request, and stops it once the line is read. Under load, the dial was
accepted and the read limit armed before the hook goroutine had built its request, so the
count reached `armed+1` on the read limit; the test advanced 300 ms; the goroutine then read
the advanced boot clock for its deadline, so the server armed the op's deadline 300 ms past the
advance, and nobody advanced again. `serveHook` sat in `AwaitPID` and the test in `<-got` until
the binary's timeout; `announceTeams` and the engine's loops in the dump were idle, not stuck.

Class: a test that synchronises with a fake clock by the number of armed waiters and then
advances it. Hazard: a count says how many timers are armed, not which; the code under test
arms, stops and re-arms its own timers on its own goroutines, so the count can be made by a
timer the test did not mean, the test advances too early, and the timer it meant is armed
afterwards at the new time and never fires (a hang), or the test passes on a different timer
than the one it describes.

## Rule

`project_fakeclock_count` (`src-go/qa/rules/fakeclockcount.go`, registered in `rules.All()`),
documented in its `Doc` and in [GoProjectRules.md](../../../GoProjectRules.md#project_fakeclock_count).
Message: `waits on a count of the fake clock's waiters (<method>): wait for the timer with AwaitDue`.

Width: a fake clock is any type whose method set has `Advance(time.Duration)`, so a second fake,
a value receiver or an interface holding one is judged too. Flagged: any use (call or method
value) of its method that takes a `context.Context` and an integer (a count wait, whatever it is
called), and a call of its no-argument `int` method inside a `for` statement or in a `return` of
a function literal (a poll). Excluded as hazard-free: a count asserted once (`if clk.Waiters() != 0`, in a range loop or a `t.Run` body), an integer method with no context (`StepWall(ms)`),
a reading that is not an `int` (the first sweep flagged `WallMS() int64` in fakehs's `Now`
closure in `teamsync/world_test.go:75`, a wall reading and no wait; the rule was narrowed to an
`int` result, and that case is a clean line of the fixture).

Next wider rule considered: flag every read of a fake clock's waiter count, assertions
included. Not built: an assertion after the code has finished (`Waiters() != 0` once a sleep
returned) carries no advance and no race, and the fake's own tests need it.

The fix the rule points at is new API: `clock.(*Fake).AwaitDue(ctx, d)` returns once a waiter
due `d` from the fake's present reading is armed, so a test names its timer by when it is due.
`BlockUntil` is deleted.

## Fixes

Every instance examined individually (the helper callers by reading each call's timer):

- `link`: the hook op (the original, below); the adds wait (`addsWait`) twice; the link lock's
  50 ms retry; the server's deadline (moved from 5 s to 3 s so it is not readLimit's 5 s), its
  read limit and its ack wait.
- `client`: the reconnect backoff steps (1, 2, 4 s, the 5 s cap) and the grace timer.
  `TestWaitAcrossARestart` listened before the fourth backoff, so the count was met by either
  the 5 s sleep or the post-dial grace timer; it now waits for the 5 s sleep, then listens.
- `engine`: `armed(n)` became `awaitDue(d)`; `dworld.advance(d)` waits for the timer due `d`, and
  `short(due, d)` for an advance that falls short of it (the 1 ms-before cases).
  `TestTrailingFactsAloneOnceAMinute` advanced 2 s on the count of the loop's minute hold (no
  2 s pace is armed there); it now waits for the minute and advances 2 s short of it.
- `keeper`: `advance(d, also...)` waits for the timer due `d` and each one in `also` (the stop's
  TERM and KILL; the restart backoff and the owed notice's 30 s); each post-crash wait names its
  backoff (1 s \<< n).
- `hook`, `inbox`, `teamsync`, `prepare`: the 300 ms hook deadline, the phase bound, the long
  poll and the version wait. `inbox.expireUntil` keeps its loop (every phase bound is 5 s, so
  the stopped connect bound and the auth bound share a due) and now waits on the bound, not a
  count.
- `clock`: the fake's own tests use `AwaitDue`; the zero-count wait after a cancelled sleep is
  an assertion (the waiter is disarmed before `Sleep` returns); `TestAwaitDue...` prove another
  timer, a stopped timer and a due counted from arming do not answer it.

No instance was suppressed or left: there is no excuse table for this rule and no inline
suppression exists.

## The original defect

`TestAnOpBeforeThePIDIsNotAnswered` now waits for `AwaitDue(hookDeadline)`: the op's deadline,
which the read limit (5 s) cannot answer, so the advance comes after the deadline is armed.
Reproduction: the test binary run alone, `-test.count 300 -test.cpu 1,2,4`, hung within a
minute before the fix (`panic: test timed out after 1m0s`, the same goroutines as the lead's
dump), and passed all 900 runs after it. The package's shuffled runs are in the next section.
