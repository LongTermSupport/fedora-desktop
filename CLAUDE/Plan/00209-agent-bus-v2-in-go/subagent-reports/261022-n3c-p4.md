`reexec`:

```go
func StartFiles(tb testing.TB, files []*os.File, name string, args ...string) *Process
```

`StartFiles` gives the files from descriptor 3 on. It copies them (`F_DUPFD_CLOEXEC`), and
closes the copies when the child ends. So the caller may close its own as soon as StartFiles
returns, and the race detector sees no close racing the exec.

## What Main does

1. Ignores SIGTERM, SIGINT and SIGHUP.
2. Works out the layout from `--run DIR`: the CCY layout when DIR is its run directory for
   DIR's base name, else `HomeLayout($HOME, $XDG_RUNTIME_DIR)`. Any other directory is 64
   `usage`.
3. Reads the kit from `Env.Digest`. With no digest it exits 78.
4. Takes fd 3 through `wire.NewConn`, which accepts only SOCK_SEQPACKET. Its `PeerPID` must be
   `os.Getppid()`, else 78.
5. Opens the state root and the run root with `homefs.Open(..., Private)`.
6. Calls `Run` with `clock.System()`, `OSProc{"/proc"}` and `OpenParent`, logging to stderr
   (the keeper points stderr at link.log).

`OpenParent` opens a pidfd on getppid with `PIDFD_NONBLOCK`, then reads getppid again. A changed
parent, or a parent that is already pid 1, is refused. The pidfd is wrapped in an `os.File`, so
the runtime's poller waits on it through `SyscallConn().Read`. There is no `poll(2)` and no
descriptor narrowing. `Close` closes the file, which ends that wait.

## Decisions

- **n3c-D24.** `Launch.Seats` is the number of adds; ready goes once that many have been
  handled. A failed add still counts. The wait is bounded by `addsWait` = 10 s on `Clock.Hold`,
  and the same hold also covers waiting for the launch. After the bound, ready goes with what
  was added and the shortfall is logged. Any later add is a hot add.
- **An owed leave before the adds is handled where it arrives, and the wait goes on.** P3's
  keeper sends launch, then each `owed`, then the adds. The brief counted "another kind before
  the adds" as a mismatch, which would have sent ready with no teams whenever a leave was owed.
  Every other kind still ends the wait early, as D24 says, and is handled after ready. Test:
  `TestOwedBeforeTheAddsKeepsTheWait`.
- **The server runs on the engine's context.** `Serve`, `Ack` and `Return` take the link's
  context, not `context.Background()`. Teardown runs in this order: close the server (every
  open hand-out is returned), shut the engine down, then cancel. So that context is still live
  for every Return.
- **Bounds:** the request line has 5 s to arrive (`readLimit`, my own bound); the ack wait is
  10 s; a removal's presence and leave get 30 s; the end and presence offline get 5 s.
- **AcceptFacts is built and tested, but no op calls it yet.** The hook ops come in n3e, and
  they reach it through the link's `session`. A first op that is not session-start records
  source `startup`. A corrupt session.json is logged, and the link starts a new one.

## Real-process tests (through reexec, the link as `Main` in a child)

- `TestProcIgnoresStopSignals`: SIGTERM, SIGINT and SIGHUP are sent. Status is still answered,
  and `end` gives exit 0.
- `TestProcEndsWithKeeper`: the keeper's end closes (EOF). The link ends the session and exits
  0, and link.lock is released.
- `TestKilledWhileHanded` (P11, `-tags busfailpoints`, `LinkWhileHanded`): the link is killed
  by SIGKILL after the done line reaches the client. The store still owes both items, and a
  restarted link hands both out again.
- The 5 s bound on keeper-died is proven on the fake clock (`TestEOFIsTheKeeperDying` and the
  finish bound), not against real time.

## How an offline member never blocks anything (the owner rule)

- **Adds don't wait on the network.** An add completes once its store is loaded and its handed
  items are put back. `NewTeam` must not dial, and each team's `Run` starts on its own
  goroutine. The state goroutine makes no network call.
- **Ready can't hang.** It goes once launch's seats adds are handled, or after 10 s.
- **recv's re-fetch is bounded.** Each team gets 2 s, and the teams run in parallel. A team
  that stops at its first error keeps its items pending. It never holds back another team's
  items.
- **Removal is bounded.** The engine's cancel and floor flush take at most 2 s + 2 s, then it
  answers `removed`. Presence and leave come after that, bounded at 30 s, then `left`.
- **The session's end is bounded.** `Ends.End` and presence offline get 5 s together. The
  keeper kills the link 5 s after `end` in any case.
