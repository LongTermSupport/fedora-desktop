# Task 0.6: does any v2 choice prevent a remote homeserver and members on other machines?

Read-only review against direction 6 (PLAN.md section 1, item 6). End state: one homeserver per team,
on this desktop, another server or a cloud host, reached only over a private network (VPN or mesh,
such as WireGuard or Tailscale); agents and humans on several machines, possibly on different networks.

## Verdict

**No IRREVERSIBLE choice BLOCKS direction 6.** Every identity v2 fixes for ever (team id, `server_name`,
handle, roster, counters) is independent of which machine runs the homeserver or the member. What
assumes one host is the *delivery machinery* around those identities: how a bundle is issued and
placed, how the board reads, how liveness is announced, the firewall model, and the no-TLS rule.
All of that is LIMITS-FIRST-BUILD: it can be widened later without changing anything a running team
depends on. One cheap rule should be written before a second homeserver host exists (item 1 below).
That rule is not a block, because with one host today every id is already unique.

## Recommended changes (none needed to unblock; cheap now)

1. **Team ids unique across the owner's estate (TID).** State in C 3.8 and A 2.2 that a team id is
   unique across every homeserver host the owner runs, not only within one `host_vars` file. Enforce
   it when a second homeserver host is introduced, for example with one estate-wide `teamchat_teams`
   list in group_vars carrying a `homeserver: <inventory host>` field. Today one host means every
   existing id is already unique, so adding the rule later breaks nothing. Without it, two
   independently created `x` teams can never be told apart on a shared member machine.
2. **`site` for every member kind (OD-A7).** C should name the source of the site for ccy and host
   members, for example `teamchat_site` per inventory host with a default the owner sets once. It
   should also say that the site differs per member machine, so that handles stay legible and
   per-prefix counting does not interleave across machines.
3. **TLS (R3).** Keep "no TLS" for loopback, the bus interface and the bridge. For off-machine
   members:
   - Plain HTTP over a WireGuard or Tailscale address is acceptable only when the listener binds the
     mesh interface and traffic never leaves the tunnel. The mesh then authenticates and encrypts
     node to node. It must not cross a subnet router or exit node, where traffic leaves the tunnel in
     plaintext on the far network.
   - For a cloud host, or any path not end-to-end inside the mesh, the bundle needs `https://`
     `base_url` support. Two ways: system roots (for example `tailscale cert` for a `*.ts.net`
     name), or a pinned CA or SPKI field in `seat.json`.
   - B's bundle decoder takes "exactly" the listed keys (B C1), so a new field is bundle `v: 2`: ship
     the member binary first, then hot-reissue the bundles. That works but costs a rollout. Reserving
     an optional `tls` field in bundle `v: 1` now, and saying that `https://` is verified with system
     roots, avoids the second rollout.
4. **Remote issuance.** Name the SSH forced-command transport for `member add|return|reissue` and the
   remote caller class as the intended future in C 3.3 or DC3, so nothing built now assumes the
   caller's uid is local.
