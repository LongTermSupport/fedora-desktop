## Trust boundary (host side deciding from a file a lower-privileged party can write)

- **Session directory, seat.json, desired.json, membership:** no code in apply, admin or host
  reads them. A grep for session, seat file, desired and membership paths finds only handle and
  seat-number logic. This slice has no surface here.
- **What root reads in host/:** every `state.ReadFile` names a path under
  `/var/lib/teamchat-admin/<team>/` (root's own, 0700), `/etc/systemd/system`, or the status
  tree, which root makes 0755 and owns. `state.ReadFile` (`state/state.go:66-96`) opens with
  `O_NOFOLLOW|O_NONBLOCK`, refuses anything that is not a regular file (so a FIFO cannot block
  it), and caps the size.
- **ctl/<team>/ (writable by teamchat-ctl):**
  - Root only makes this directory: `mkdirMode` works through a descriptor opened with
    `O_NOFOLLOW|O_DIRECTORY`, which round 2 verified.
  - Root removes it on a purge with `os.RemoveAll`. If the name has been swapped for a link,
    the first unlink removes only the link, and a walk inside the directory goes through
    `openat` and `unlinkat` without following links.
  - `exists` uses `Lstat`.
  - Root never reads a file inside the directory.
- **The child's answer:** this is the one thing root parses that teamchat-ctl wrote, and it is
  decoded strictly (`admin/child.go:399-501`):
  - exact keys and `v`
  - one-line CHANGED lines and notes (C0, C1, DEL and Cf are refused, so no forged `CHANGED`
    line reaches the play's stdout)
  - a handle that parses as one, and a credential that is printable ASCII
  - then `asked` (`verbs.go:276-301`) holds the handle and the credential kind to the request
    before a bundle is made.
- **Lock:** `/run/teamchat-admin` is root's, and the lock file is opened with `O_NOFOLLOW`.
- **Homeserver database (`/var/lib/private/teamchat/<team>/db`):** `isDir` uses `Lstat`, so a
  homeserver that swapped `db` for a link would skip its own backup and nothing more. That is
  the homeserver deciding about its own data, which is not a privilege gain.

No real gap here.

## Crash safety

Member operations: every step either saves before it acts on the result or is idempotent on a
rerun:

- the retirement in `account`
- the `--seat next` retirement in `admit`
- the token copy written before the save that records the issue
- `park` and `deactivate`

Host remove: `root/<team>/` is removed last, so a failed purge leaves the team installed, and
the next run finishes it.

Host apply has one gap, which is new finding 1.

## New findings

1. **major: a drop-in whose `daemon-reload` failed, or crashed before it ran, is never reloaded,
   and the next apply stamps the team as applied.** `host/apply.go:644-654` and `:672-677`.

   - Mechanism: `writeDropIn` writes the file and then calls `DaemonReload`. On a rerun,
     `readInstalled` reads the new drop-in, so `string(a.dropIn) == string(a.r.dropIn)` and
     `writeDropIn` is skipped, and nothing else reloads. `units.json` still holds the old
     digests, so `decide` answers reload or restart, but the reload answer has no action of its
     own in `converge7`: its only effect was the `daemon-reload` that never happened.

   - Scenario (proven): an applied team narrows `allow_from`. Apply 1 rewrites the firewall and
     the drop-in, the `daemon-reload` fails (for example a D-Bus timeout) and the verb exits 1
     at `unit`. Apply 2, unchanged input and no fault, answers
     `err=<nil>, ["team.json written" "units.json written" "stamp written"]`, and its call log
     holds no `daemon-reload` and no `restart` (probe
     `TestProbeReloadLostAfterFailedDaemonReload`).

   - Consequences:

     - systemd keeps the old `IPAddressAllow` and `MemoryHigh` for good.
     - `units.json` and the stamp say they are applied.
     - Every later apply answers "nothing".

   - For a restart-set change (a new Tuwunel version or port), apply 2 calls `Restart` on a unit
     systemd has not reloaded, so the old `ExecStart` runs, while `units.json` records the new
     version. If the port changed, the readiness wait fails on every rerun, and nothing breaks
     the loop.

   - A crash between the write and the reload has the same effect. That is item 4's case: an
     operation the roll-forward cannot finish.

   - Fix (any one):

     - (a) Reload whenever the answer is reload, restart or first, or whenever `units.json` is
       missing or different, not only when the drop-in bytes differ.
     - (b) Write the drop-in through a temporary name and reload in the same step.
     - (c) Ask systemd for `NeedDaemonReload` of the unit and reload when it is yes.

     Add the probe as a test, with the reload failing once.
