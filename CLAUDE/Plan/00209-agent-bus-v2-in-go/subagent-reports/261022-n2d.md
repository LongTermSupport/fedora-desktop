## The narrow check's finding: a lost daemon-reload

Finding (`261022-n2d-check.md` new finding 1, major): `writeDropIn` wrote the drop-in and then
called `DaemonReload`. If the reload failed, or the host crashed before it ran, the next apply
found the drop-in bytes matching the render and skipped both the write and the reload. It then
stamped the team applied while systemd kept the old `IPAddressAllow` and `MemoryHigh`, and a
version change restarted the old `ExecStart`. `team remove` had the same gap: once the drop-in
was deleted, a rerun found it gone and skipped the reload.

Mechanism (HS15): a reload is owed whenever `units.json` does not record this render's digests,
however the bytes on disk compare. `applying.loaded` starts true only for the answers "nothing"
and "write". A drop-in write sets it false, and `reload` (called before the backup start and
before step 7's start or restart) runs `daemon-reload` and sets it true. `units.json` is written
in step 11, after that reload has succeeded, so it is the record that a reload took. This option
was chosen over the other two:

- a pending-reload record would be a second file saying what `units.json` already says;
- asking systemd for `NeedDaemonReload` would widen the `Systemd` seam, and its answer covers
  only files systemd has seen change.

The cost is one extra `daemon-reload` on a config-only or base-unit-only restart. That reload is
idempotent and also correct: a restart on a changed base unit must not run the unit systemd
loaded earlier. `TestRestartBacksUpFirst` no longer asserts that a base unit change does not
reload. `team remove` now reloads on every remove of an installed team, and "drop-in removed" is
noted at the delete, before the reload.

The sweep of `host/` for other "skip if unchanged" steps that follow a write:

- the config's restart is already driven by `units.json`, not by its bytes;
- the firewall queries each rule in both configurations on every run;
- the stamp and `team.json` need no second action, and `Status.Refresh` runs every time.

None of these has the gap. A related case that is not this class: `startForBackup` skips its
readiness wait for a unit that is already active, and a backup against an unready server fails
on its own.

Tests, each seen red first, in `host/reload_test.go`:

- `TestAFailedReloadIsRetried`: two applies with the reload failing, each failing at `unit` with
  the stamp unchanged; the third applies.
- `TestADropInLeftByACrashIsReloaded`
- `TestAnUpgradeIsReloadedBeforeItsRestart`, for a failed reload and for a crash: the new
  version is what runs.
- `TestABaseUnitChangeIsReloadedBeforeItsRestart`
- `TestABackupDropInWhoseReloadFailedIsReloaded`: the backup runs on the old version.
- `TestRemoveRetriesAFailedReload`

The fake systemd now keeps the drop-in it loaded apart from the one on disk, and runs the loaded
one on a start or a restart. With `go test -race -cover`, host coverage is 92.9%. golangci-lint
reports 0 issues with and without `-tags tuwunel`.
