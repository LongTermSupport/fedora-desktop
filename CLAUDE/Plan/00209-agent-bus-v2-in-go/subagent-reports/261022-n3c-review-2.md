## 2. Declined items and gaps

- **B1, the abandoned-client EOF cancel: acceptable only once N1 is fixed.** fixb argues that
  "a hand-out to a closed connection is returned". It is returned, but `Return` wakes no
  waiter (see N1), so an abandoned waiter can still take a live waiter's items and leave that
  waiter asleep. With N1 fixed, the remaining cost of an abandoned waiter is a wrong `repeat`
  mark and a registration that lasts to its deadline. That cost is acceptable without an EOF
  reader.
- **B4, the e2e is not red without the fix: acceptable.** The unit test is red-proven, so the
  e2e is a guard of the relaunch. Its comment says it "waits for that link", which it does not
  prove (N6).
- **B3, go-qa stages because there was no tuwunel wiring to copy: acceptable.** That claim is
  true: go-qa.toml, qa-gates.tsv and CI set no build tag anywhere. A `[[stage]]` is go-qa's
  documented extension point for this. It runs from the go-qa root (`src-go`, not per module),
  and the pipeline runs its steps in order. See section 4 for the costs.

## 3. New defects

### N1 (minor): `Return` wakes no waiter, so a wait can sleep past items that are pending again

- **Where:** `engine/recv.go:474-505`. `settle` with `deliver` false puts an item back with
  `Handed` nil. Only `Persist` calls `e.wake()` (`engine/seam.go:217`). `hasPending`
  (recv.go:421-431) counts only unhanded items, and a wait whose check found nothing pending
  sleeps with no retry (recv.go:388-401).
- **Scenario:**
  1. An agent's `teamchat wait` is killed, by the user's interrupt or a tool timeout. Its waiter
     A stays registered (the EOF cancel was declined).
  2. The agent runs `wait` again, as waiter B.
  3. An item arrives. Persist wakes A and B.
  4. A's hand-out runs on the state goroutine before B checks. A takes the item, and B's
     `hasPending` sees only a handed item, so B sleeps on `woken` with no retry.
  5. A's write to the dead socket fails, and `Return` puts the item back, marked `repeat`.
     Nothing wakes B.
- **Effect:** B exits 4 at its deadline (by default a 110 s bound) with an item pending, and
  the agent's next recv shows the item as `repeat` though the agent never saw it. The same lost
  wake follows any return: an ack that never came, or a failed write.
- **Fix:** in `settle`, when any item went back to pending, call `e.wake()`.
- **Test:** two waiters. The first's hand-out is returned, and the second is handed the item
  with no new Persist.

### N2 (minor): a remove whose store delete fails now leaves the store on disk

- **Where:** `link/link.go:369-377` and `keeper/seats.go:338-352`.
- **What changed:**
  - `engine.Remove` can return a user id together with an error from `drop`: a `Remove` of
    the store writer other than ENOENT, or a close error.
  - The link now answers with that user id.
  - `onRemoved` deletes the store itself only when the user id is empty.
  - Before the fix, such a remove went unanswered, and the keeper's 10 s path deleted the store
    under the lock.
- **Scenario:**
  1. The store unlink fails (EIO, a read-only remount, a permissions slip).
  2. The keeper records the removal and lets the seat go.
  3. A later add of the team loads the old store, with its pending items and its user id.
- **Fix:** have `onRemoved` call `deleteStore` on every `removed`, not only on one with no user
  id. It is idempotent (ENOENT is ignored), and the keeper holds the lock.
- **Test:** a `removed` with a user id while the store file still exists. The store must be
  gone.

### N3 (minor): a request in flight at `close()` can be answered with the cancel's result

- **Where:** `link/server.go:122-130` (`close` closes `stopping` before it closes the
  connections) and `server.go:206-218` (handle answers whatever `Serve` returned).
- **Scenario:**
  1. The session ends while an agent's `wait` (or a recv) is in flight.
  2. `close(s.stopping)` cancels the request.
  3. Serve returns at once: `waitTimedOut`, through `done(ctx, …)`, or `internal` for a recv
     whose `e.do` saw the cancel.
  4. The handle writes that answer before `close()` reaches its connection.
- **Effect:** the client exits 4 "nothing arrived before wait's deadline" before its deadline,
  or exits 1 "tell a human". The owner rule's 4 is for the deadline only. If the connection is
  closed first, the client sees the link gone instead, and a wait retries across the restart,
  which is the intended path.
- **Fix:** close the connections first and then close `stopping`. Or, in handle, skip the
  answer when `stopping` is closed. Either way the client always sees a closed link.
- **Test:** a blocked wait at `close()`. The client must see EOF and no done.

### N4 (nit): Shutdown repeats Remove's stop and flush, and they should be one function

`engine/teams.go:204-213` and `teams.go:280-289` both stop the team goroutine, then put the floor
under a `flushWait` bound and log a failure. They differ only in the log text, and in that
Shutdown uses `context.WithoutCancel`. The link's ctx descends from Background, so that
difference changes nothing today. fixa kept them apart only to stay clear of B2, which in the end
did not touch `engine/teams.go`. I found no conflict between fixa and fixb:

- Remove marks `removed`.
- Shutdown skips removed teams.
- Removes are dispatched on the link's main loop, which has ended before teardown runs Shutdown.

Extract `stopAndFlush(ctx, id, tm, cancel, stopped, when string)` and call it from both.

### N5 (nit): Shutdown's bound does not compose with the keeper's end bound

- **The bounds:** the keeper SIGKILLs the link 5 s after End (`keeper/loop.go:629`). The link
  spends up to `endWait`, 5 s, in `finish` before teardown, and then Shutdown adds up to 4 s.
- **Effect:** when the homeserver is slow, the clean-end put is killed, and the comment's "about
  4 s at most" is the link's own time, not the session's. A2 part (2) puts the floor at the next
  start, so nothing is lost. Only a seat taken with no store in between still replays.
- **Fix:** say this in the comment and in SY10's text, or run the flush beside finish.

### N6 (nit): the e2e relaunch test's comment overstates what it proves

- **Where:** `wiring/e2e_failpoints_test.go:284-298`.
- **Problem:** the comment says the relaunch "waits for that link". Against fakehs the seat is
  already free when the relaunch reaches it, so the test never takes the wait path.
- **Fix:** say "a guard of the relaunch; the wait is proven by
  `TestHeldSeatOfAnEndingSessionIsWaitedFor`". Or arm a failpoint that holds the dying link in
  finish, which would make the test red.

`holderEnding` also reads a run root it cannot see as "keeper gone". If the holder's run is not
visible from this run root, the relaunch waits out its 7 s bound and then exits 75, and the log
line says the keeper is gone. This is a bounded delay, never a false seat, so it is a wording nit
only.

## 4. The busfailpoints gate against CLAUDE/QA.md

**The design holds:**

- The row in `CLAUDE/QA.md` names the stages.
- The stages are go-qa's own extension point, in `src-go/qa/go-qa.toml`, so qa-all,
  qa-changed and CI all reach them through `qa-go-qa.bash` with no new gate row. That is
  the right place, and no `qa-gates.tsv` row was owed.
- `golangci-lint` comes from PATH, and its version equals go-qa's `tools.lock` (2.14.0),
  since `qa-toolchain` pins `.qa-versions` to that version.
- Red is proven: a planted printf defect failed both the vet and the lint stage.

**Two points on the design:**

- **Diff mode.** None of the stages takes `{files}`, so in qa-changed's scoped run each one runs
  whole, for any `src-go` change. That is acceptable only because the test stage omits
  `-count=1`: go's test cache makes an unchanged teamchat a cache hit, and a teamchat change
  costs a 90 s bound of wall time.
- **Cache and shuffle.** The built-in runner uses `-race -shuffle=on -count=1`
  (go-qa `internal/runners/testrun.go:9`). The stage has neither `-shuffle=on` nor `-count=1`.
  - Add `-shuffle=on`: it costs nothing with the cache, and it brings the stage's order
    checking to the built-in's.
  - Leave `-count=1` out deliberately, and say so in the stage comment. The cache is what keeps
    qa-changed within bounds. qa-all then re-runs only what changed, which is a weaker guard
    against flaky crash scenarios than the built-in's.
  - Neither point blocks.

**Flakiness:** none seen. Three shuffled passes of the tagged packages were green, the crash
scenarios included. One pass of wiring under `-race` stays well inside go test's 10 min bound
for each package.

**Bounds:** nothing here has a stage timeout. go test's default 10 min for each package binary is
the bound, inside `QA_ALL_TIMEOUT`'s 30 min for each gate. That is acceptable.
