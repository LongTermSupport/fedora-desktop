## Findings

**B-M3 (forge health from any request).** `forge.go` `lost` and `get`. The forge is marked
down only on evidence that it cannot be reached:

- no connection was made (httptrace `GetConn` / `GotConn`, reset on each attempt the transport
  makes, so a dead kept-alive connection followed by a failed dial still counts as down);
- no answer, or a 5xx, to the repository's own request.

A cut or a 5xx on a compare or contents request leaves that check `unresolved` and does not
mark the forge down.

  qa-changed run it caught a reused-connection flake, which the per-attempt reset fixed.

**B-M1 (a rate wait slept past the caller's bound).** Rate health now sits beside down health.
A rate answer sets `ratedUntil` to now plus the wait, capped at one hour. Any check before then
answers `forge-rate` at once and makes no request.

The caller's bound is `clock.WithBound`:

- the link server sets it from `deadline_ms`;
- teamsync sets it to now + 30 s for each batch.

A wait that would end at or after the bound answers `forge-rate` and is not slept, so a
rate-limited send exits 14 `forge-rate` and never 20.

**B-M2 (forge calls not bounded per sender).** Three bounds, and no negative cache:

- **Per-sender budget.** At most 6 uncached checks per sender per 60 s receive window
  (`proto.ForgeChecksPerSender`), per team, held in memory. The check asks `spend` through
  `team.WithReceive` once, before its first request. Past the budget the ping drops `unresolved`
  and no request is made.
- **Deduplication.** Identical checks in a batch (same reference with its text ignored, same
  class, same branches) are asked once, and every copy gets that one answer.
- **Reserve.** When the last answer's `X-RateLimit-Remaining` is below a fifth of
  `X-RateLimit-Limit` (5000 is assumed if the limit is absent), receive checks answer
  `forge-rate` and make no request until the reset. Sends still ask.

The numbers and their reasons are in the SPEC-n3 row n3d-D31.
