## Defects the fix3 diff could have brought in

**`-shuffle=on` (G1).** It is not gate-wide. It is added to the `teamchat-failpoints-test`
stage only, whose command covers `./internal/teamchat/...` under `-tags busfailpoints`. go-qa's
built-in runner already ran every package with `-race -shuffle=on`. Runs, from `src-go/`:

- `go test -race -shuffle=on -count=1 ./...`: exit 0, every package green.
- `go test -race -shuffle=on -count=2 -tags busfailpoints ./internal/teamchat/...`: one
  failure, `member/guest` `TestRegister`, which panicked with "guest register-test registered
  twice". This is a `-count=2` artefact, not order dependence. The test registers into a
  package-level registry, so the second iteration in the same process finds the verb already
  registered.
  - The guest package was re-run three times with `-race -shuffle=on -count=1 -tags busfailpoints`.
    All three were green.
  - The stage never passes `-count>1`, so the gate is not flaky.
  - The failing code is outside the fix3 diff. I note it below and do not block on it.

**N1's wake of every waiter.** `wake` closes every registered channel and clears the list
(seam.go:309). Each woken wait goes round its loop again: it registers a new channel and
re-checks `hasPending(only)`.

- **A wait for another team** finds nothing eligible pending and sleeps again on its new
  channel. The cost is one pass of the state goroutine.
- **An item that is pending but not handed out** (recv hands nothing) makes the wait fall back
  to the `waitRetry` hold, as before.
- No wait ends early. A wait ends only on a hand-out, a non-zero exit, or its own ctx, and
  `waitTimedOut` (exit 4) still comes only at the deadline.
- No wake loop forms. A return happens only after a failed write or an ack that never came,
  and that request ends instead of waiting again.
- `returned` is set only when the store write succeeded (`err == nil && back`), so a failed
  persist wakes nobody for state that did not change.

**N3's reorder.** `track` refuses a connection once `closed` is set under `mu`, so no
connection opened after the loop can miss its close.

**N2's every-time delete.** It runs on the keeper's loop before `reconcile`, so a re-add of the
team cannot create a store first and then lose it to the delete. `NewStoreWriter` requires the
seat lock to be held.

The owner rule is unaffected. An offline member or a down server blocks nothing, 69 and 20
keep their meanings, and `wait` still gives 4 only at its deadline.
