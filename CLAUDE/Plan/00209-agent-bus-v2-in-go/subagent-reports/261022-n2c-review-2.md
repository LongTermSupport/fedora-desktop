## New findings

1. **Medium: `heldRecord` closes `held/`'s fd twice when the allocation lock cannot be taken.**
   `release.go:135-151`. Line 135 closes `h` but does not set it to nil. If `locked(...)` then
   fails before `f` runs (`Lock` returns ErrBusy after its 30 s, or a cancelled context), `err`
   is non-nil, `h` is still the closed `*dir`, and line 150 calls `h.close()` again. The
   reproduction, `TestReviewIncompleteHeldLockFailureClosesTwice`, runs `Announce` over a bare
   `held/` while the test holds the allocation lock. It returns `seat: busy … is held` joined
   with `bad file descriptor`. Here the second close met an fd number that was already closed.
   In the long-lived ccy-teams or launcher process, `Lock` itself opens and closes two fds
   between the two closes, and any other goroutine may open one too. The second `close` can
   therefore end an unrelated fd that reused the number: a homeserver socket, another store's
   root, or a seat lock. The path is ordinary: an `Announce` (the seat sweep) or a `Release`
   that meets a dead take's `held/` while another take holds the lock for longer than 30 s.
   **Fix:** `err, h = h.close(), nil` at line 135, as line 143 already does. The test is the
   reproduction: assert `errors.Is(err, ErrBusy)` and `!errors.Is(err, unix.EBADF)`.

2. **Low: a resumed release is stuck while its session holds another seat of the same team.**
   `release.go:86-90` and `106-112` (steps 1 and 2) treat `sessions/<session>/<team>` as this
   holding's directory without checking its claim. Here is the sequence. A leave of seat A
   stops after step 2, at a transient logout failure. The session then takes seat B of the same
   team, whose copy lands at the same `sessions/<session>/<team>`. Every retry of A's release
   now behaves wrongly. It waits up to 60 s on seat B's lock (ErrBusy while B's keeper runs).
   When B's lock is free, step 2 tries to move B's directory onto A's quarantine name, which is
   taken, and fails with a bare `file exists` (reproduction
   `TestReviewResumedReleaseMovesAnotherSeatsSessionDir`). A's `held/` and its live token stay
   for as long as the session lives, and a take of A by anyone is ErrHeld. `sessionHolds` makes
   the same conflation, probing B's lock for A's holding. Nothing is moved wrongly, because
   `RENAME_NOREPLACE` stops it, and the state heals once the session ends. The design's "step 2
   finds the session seat already gone" assumes the path cannot be reused, and the SPEC does not
   say so. **Fix:** at steps 1 and 2, read the session copy's `seat.json` claim through an fd
   (SW3). When it is a complete held bundle with another claim, treat the directory as not this
   holding's: step 1 skips its wait, and step 2 counts as done. Record this as n2c-D12, and add
   the reproduction as a test.

3. **Low: a broken `released.json` has no mend.** `place.go:182-185` (`Fill` refuses, n2c-D8)
   and `take.go:226-229` (`mint` refuses) both stop on an undecodable `released.json`. A take
   fails after step 2, leaving a `held/` with no token. The next take releases that `held/` and
   fails again in the same way, so the seat churns quarantine entries. `member reissue` is the
   documented mend for a broken pool record, and it is refused too. Only a hand edit of the
   store clears it. **Fix:** let a placement (reissue) move a broken `released.json` aside, or
   carry none, and record that the next take's `released_ms` is `null`. Alternatively, keep the
   refusal, but name the file and say that reissue cannot mend it.

4. **Low: two concurrent releases of one holding can both ask the announcer, and can fail each
   other's notice write.** `release.go:232-251` and `fs.go:145-158`. Both releases read
   `notice.json` as missing outside the lock, so both call `Disconnected`, which posts two
   notices and breaks SD2's "not asked again". Both then `replace` through the same fixed
   `notice.json.new`. One can unlink the other's fresh copy before its `renameat`, which then
   fails with ENOENT, or the `O_EXCL` create meets EEXIST. The failing release stops, and a
   retry completes, so no state is lost. `TestTwoReleasesOfOneHolding` nests the second release
   inside the first one's announcer, so it never runs this interleaving. **Fix:** either accept
   and record that a launcher release racing a sweep release may post twice (the design says the
   sweep re-runs releases), or give `replace` a per-call fresh name (`<name>.new-<claim or random>`).
