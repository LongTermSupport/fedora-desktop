## Why this is a separate plan, and what it is NOT

Spun out of Plan 00079's F17. Kept separate because the subject is the CCY
launcher's network policy, not podfreeze's build — and because the two possible
outcomes have very different blast radii: one changes nothing, the other changes
the daily driver every session on this machine goes through.

The ask arrived framed as *"podfreeze should probably skip the podman network
for grouping?"*. Pushed back on that and recorded it as D1. There are two
problems tangled together:

1. **isolation** — seven sessions on one L2 domain, each holding tokens, keys
   and a writable project tree;
2. **the menu row** — `network: podman` groups by an accident of the default
   rather than by intent.

They are coupled, and the coupling runs one way: fixing (1) with per-session
networks dissolves (2) for CCY automatically. Fixing (2) first would hide the
symptom of (1) in a file that is not the cause, and would remove a row that is
still a legitimate group for non-CCY containers. So (2) waits.

## The risk that actually decides this

Not "can we create a network per session" — trivially yes. It is **cleanup**.
CCY runs `--rm`, which disposes of the container and says nothing about a
network created alongside it. A `SIGKILL`, an OOM kill, or a power cut leaves
one behind, and a leak that happens once per crash on a machine running seven
concurrent sessions is a resource problem, not a cosmetic one. H4 is therefore
gating: if cleanup cannot be made reliable, the option is not viable however
attractive the isolation is.

Deliberately did NOT pre-judge the threat model. The honest answer may well be
that cross-session reachability gains an attacker very little in practice —
whether it does turns on what CCY's processes actually bind to (H3), which is a
fact nobody here has checked. "Change nothing, and write down why" is a listed,
acceptable outcome rather than a failure of the plan.

## The research came back and inverted the plan's premise — and corrected me

Two things I had written into PLAN.md were **wrong**, and the agent caught both.

**I claimed CCY passes no `--network` flag** and lands on the shared bridge as a
fallthrough. It does not. `claude-yolo:2677-2680` *explicitly* sets
`NETWORK_FLAG="--network podman"`. Verified directly rather than taken on trust:
the assignment is there, and `grep -n 'NETWORK_FLAG='` without a `head` returns
**eleven** assignments, the decisive one last.

That last clause is the whole story. I had run
`grep -n 'NETWORK_FLAG...' | head -n 30` and the output was cut at exactly 30
lines. I read a truncated list as exhaustive and concluded "every other route
leaves it empty". This is the repo's own defect class — a command's incomplete
output silently becoming data that is then trusted — committed in a plan whose
subject is grounding claims properly. Worth writing down precisely because it
was not carelessness about *facts*; it was carelessness about the *boundary of
what I had looked at*.

**I claimed `--no-network` does not isolate.** The opposite: it leaves
`NETWORK_FLAG` empty, the `elif` is skipped, and the session gets **pasta** —
rootless Podman's real default, which has no virtual network and isolates
containers from each other. So `--no-network` is currently the one way to run a
session nothing else can reach, and the docs undersell it as "skip
auto-detection". Task 4.0 flipped from "fix a misleading message" to "document
the isolating mode we already have".

## The premise inversion

The plan opened with "it is Podman's default, not a choice CCY makes". It is
exactly a choice CCY makes. Commit `ea7ba129` (CCY 2.5.2 → 2.6.0) added the
override because `ccy --connect` failed with
`"pasta" is not supported: invalid network mode` — pasta cannot join additional
networks after container start, so the launcher moved everything onto the
default bridge to keep `podman network connect` possible later.

So the shared L2 domain is a **side-effect of preserving `--connect`**. The
question is not "can we add isolation" — the isolated default already existed
and was traded away. It is "can that trade be undone without losing what it
bought", which is a much better question and points straight at Option 2: a
per-session network is still a bridge, so `--connect` keeps working, but it has
one member.

## What the research found that I would not have

- **A per-session network may not isolate at all.** netavark 2.0 (Podman 6.0)
  made bridge networks strictly isolated *from each other* by default; below
  that, containers on different rootless bridges could reach each other, with a
  filed issue showing exactly that. On a pre-6.0 host, Option 2 would produce
  **the appearance of isolation without the substance** unless `--opt isolate=`
  is passed. An appearance of a fix is worse than no fix, and I would have
  shipped it.
- **`isolate` does not do what its name suggests.** It is a *cross-network*
  control; intra-network traffic is untouched. So setting it on the shared
  network would have been a plausible-looking no-op.
- **A per-session network would silently change DNS.** User-created networks are
  DNS-enabled by default, and `ensure_network_dns()` then adds public resolvers
  to any network that is — so Option 2 as written would ship a resolver change
  nobody asked for.
- **Subnet exhaustion is not a real risk.** Podman's default pools allow ~42,700
  allocatable `/24`s. That risk row was mine, written on instinct; it is
  retracted in the table rather than quietly deleted.

## The threat model is appropriately deflationary

The agent was told not to inflate it, and did not. The honest position: the
shared bridge turns one compromised session into a foothold against **whatever
its neighbours are listening on**, and that surface is plausibly empty most of
the time. It does **not** expose the Anthropic token, the `gh` token, the SSH
keys or the project tree — those are environment variables, bind mounts and
filesystem namespaces, none of them network-reachable. Reaching a port is not
reading `/proc/*/environ`.

What pushes it up rather than down: seven concurrent sessions each holding live
push credentials is not a normal container fleet, and they run unattended by
design.

## triage.bash

Written from the probe list, with one improvement the agent could not make: it
recommended `ss -lntp || cat /proc/net/tcp`, and **`ss` is not in the CCY
image** — I checked inside this container. So the `/proc` path is the one that
always runs, and raw little-endian hex is unreadable. The script captures raw
inside the session and decodes it host-side into `LISTEN 0.0.0.0:8080` form,
which is the difference between a probe someone reads and one they skip.

Passive by default; the active probes create and remove `ccy80-probe-*` objects
behind `--reachability` and never touch a live session. Three deliberate
choices:

- **P4 fails loudly when no session carries `ccy=true`** rather than printing an
  empty listener set. An empty section there reads as "nothing is exposed",
  which is the opposite of what it would mean.
- **It refuses to pull the probe image.** A script advertised as read-only that
  quietly fetches from a registry is not read-only in the way it promised.
- **Cleanup asserts its own end state** instead of assuming its `rm` calls
  worked — on a plan about objects outliving what should have removed them,
  assuming would be the joke writing itself.

## D1's per-session row was wrong — the row fragments, it does not dissolve

Re-read D1 against the research's F23 before touching `podfreeze`, and found my
own decision text contradicted by the findings it was supposed to summarise.

D1 said: *"if per-session networks land, the `podman` row dissolves for CCY on
its own and no `podfreeze` change is needed."*

F23 says the opposite for that branch. Under per-session networks each session
brings its **own** single-member network, so the menu does not lose the network
axis — it grows one row per live session, each naming exactly one container. A
group of one is not a group. That branch therefore needs **more** `podfreeze`
work than the status quo (suppress single-member network rows), not none.

**The error shape**, which is worth naming because it is subtle: I collapsed two
different events into one. "CCY leaves the shared `podman` network" and "CCY
leaves the network *axis* entirely" are not the same thing, and only Option 4
(revert to pasta) does both. Option 2 does the first and not the second. Having
established that the shared bridge was CCY's own choice, I carried the mental
image of "CCY stops being on a network" into an option where it very much still
is — just on N of them.

This is the same family as the truncated-`grep` error earlier today: a
conclusion that was true of one branch quietly applied to a neighbouring one.
Different mechanism, same failure to check the claim against the branch it was
being asserted about.

D1 now carries an explicit three-row outcome table rather than a sentence, so
each branch states its own consequence and none can borrow another's. Task 4.1
was also made concrete against that table, with the constraint that matters
recorded in the task itself: whichever way it resolves, `--network <name>` stays
accepted on the command line. Curating a menu is not the same as removing a
capability, and the distinction is exactly the kind that gets lost between the
decision and the implementation.

No `podfreeze` code changed — D1's "do not change it until this plan resolves"
still holds, and the correction reinforces it rather than unblocking it: the
right edit genuinely depends on which option lands.

## Triage run 1: the host answered, and the probe was wrong

The user relaunched `ccy` and ran the passive report. It produced real facts and
two defects, one of them mine and instructive.

**What the host said.** Five live CCY sessions, all five on the `podman` bridge
(`podman  5 members`); every other network on the box has zero. F17 confirmed at
fleet scale. The app networks exist but nothing is running on them right now, so
the F15 shape — a session sitting inside a project's compose network — is not
currently occurring.

**Defect 1 — P4 covered 1 of 5 and read as if it covered 5.** The identity table
gave it away: only `fedora-desktop_yolo` carried `project=`/`github=` values.
The other four showed empty labels, because they predate 3.40.0 and the
changelog says plainly that containers keep their labels only from a restart
onward. P4 filtered on `label=ccy=true`, so it found one session, probed one
session, and printed `(no listening sockets)` beneath a header that says *"If
every session shows '(no listening sockets)', the exposure is THEORETICAL."*

I had guarded this probe. The guard fires when **zero** sessions carry the
label, with a comment explaining that an empty listener set would read as
"nothing is exposed". What I did not guard is the case that actually happened:
**some** labelled, most not. Zero-vs-nonzero, when the real axis was
covered-vs-complete.

That is this repo's documented defect class, committed inside the probe written
to avoid it, on the same day I corrected a fact derived from a truncated `grep`.
Same shape both times: a partial result presented with the authority of a total
one. The asymmetry is why it keeps happening — an over-match *names itself* in
the output, so you see it; an under-match is silent, and silence reads as
agreement.

Fixed by selecting the **union** of the `ccy=true` label and `podfreeze`'s own
`^.+_(yolo|browser)(_[0-9]+)?$` name pattern — the fallback `podfreeze` already
carries for pre-3.40.0 sessions, which P4 should have used from the start since
the two tools face the same fleet. Every session is now probed, each row is
marked `[labelled]` or `[UNLABELLED — pre-3.40.0, matched by name]`, and a
COVERAGE line states the numbers. The P4 header now says to read that line
first, because the "theoretical" conclusion needs *every* session probed, not
every session the label happened to select.

**Defect 2 — P5's inventory was absent, not empty.** `podman network ls --format
'{{.NetworkID}}'` returned `rc=125`: *"can't evaluate field NetworkID in type
network.ListPrintReports"*. It printed one row and died. The `probe()` helper
did its job — the non-zero rc is right there in the report — but a reader
skimming for network names would see a one-line list and take it for the answer.
The field is `.ID`.

Worth noting the two defects fail differently. P5 announced itself (`rc=125`, an
error string in the output). P4 did not: it produced well-formed, plausible,
*incomplete* output. The one that looked healthy was the dangerous one.

**Consequence for the plan.** F19 (zero listeners) is real but scoped to one
session, so H3 is **not** settled and "the exposure is theoretical" is not yet
earned. The passive report needs re-running now that it covers all five —
ideally while something is actually being built, since an idle session is the
best case and the snapshot caveat was always the point.
