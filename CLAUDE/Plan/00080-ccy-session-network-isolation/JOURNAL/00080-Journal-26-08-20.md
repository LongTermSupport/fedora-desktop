## Why this is a separate plan, and what it is NOT

Spun out of Plan 00079's F17. Kept separate because the subject is the CCY
launcher's network policy, not podfreeze's build — and because the two possible
outcomes have very different blast radii: one changes nothing, the other changes
the daily driver every session on this machine goes through.

The ask arrived framed as *"podfreeze should probably skip the podman network
for grouping?"*. Pushed back on that and recorded it as D1. There are two
problems tangled together:

1. **isolation** — seven sessions on one L2 domain, each holding tokens, keys
   and a writable project tree;
2. **the menu row** — `network: podman` groups by an accident of the default
   rather than by intent.

They are coupled, and the coupling runs one way: fixing (1) with per-session
networks dissolves (2) for CCY automatically. Fixing (2) first would hide the
symptom of (1) in a file that is not the cause, and would remove a row that is
still a legitimate group for non-CCY containers. So (2) waits.

## The risk that actually decides this

Not "can we create a network per session" — trivially yes. It is **cleanup**.
CCY runs `--rm`, which disposes of the container and says nothing about a
network created alongside it. A `SIGKILL`, an OOM kill, or a power cut leaves
one behind, and a leak that happens once per crash on a machine running seven
concurrent sessions is a resource problem, not a cosmetic one. H4 is therefore
gating: if cleanup cannot be made reliable, the option is not viable however
attractive the isolation is.

Deliberately did NOT pre-judge the threat model. The honest answer may well be
that cross-session reachability gains an attacker very little in practice —
whether it does turns on what CCY's processes actually bind to (H3), which is a
fact nobody here has checked. "Change nothing, and write down why" is a listed,
acceptable outcome rather than a failure of the plan.

## Research dispatched

One sub-agent, research-and-propose only. Constrained explicitly:

- it is inside a CCY container where **podman is not installed**, so it can
  verify nothing at runtime and must not fabricate output;
- every claim carries `[SOURCE: ...]` / `[VENDOR CLAIM]` / `[INFERRED]` /
  `[UNVERIFIED — needs host probe]`, an untagged claim being a defect;
- it must list the premises it could NOT confirm, and turn them into
  copy-pasteable read-only host probes;
- it may not render a verdict — options and trade-offs only, human decides;
- it may write only under `research/`, and that directory **is tracked**, so no
  real project names, accounts, token labels or home paths.

The no-verdict rule is there because a research agent that concludes tends to
have its conclusion adopted by default, and the evidence then gets read as
support for it rather than tested against it.
