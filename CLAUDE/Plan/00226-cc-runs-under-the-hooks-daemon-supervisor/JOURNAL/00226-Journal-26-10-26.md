Planning findings for issue #113 (plan written, no code).

- Dedupe: `find-plan supervisor` and `find-plan cc` matched no plan that owns host cc
  supervision. Plan 00194 names host cc sessions as out of scope; 00146 is ccy's token
  switch; 00167, 00191, 00133 and 00048 never mention the supervisor.
- The installed daemon is 3.70.0 (`expected_version` in `.claude/hooks-daemon.yaml`;
  `.claude/ccy/claude-supervise.py` has `__version__ = "3.70.0"`). Upstream v3.71.0 is
  released; its notes say the supervisor "counts a session as its own only when the session
  id is in the environment of the Claude process it started, or of one of that process's
  descendants" (upstream Plan 00551, their issue #138). The same release rewrites a
  `python3 .claude/ccy/claude-supervise` wrapper to `sh .claude/ccy/claude-supervise`
  (upstream Plan 00540).
- Bash headroom: none. `scripts/bash-limits.allowlist` holds cc at 182 code lines and
  cc-teams.bash at 87 code lines with 7 functions, both over the limits, so neither may
  grow. Neither needs to: `cc_teams_split_args` and `ccy_registry_launch_args` pass unknown
  arguments through, so `--supervise`/`--no-supervise` already reach cc-claude on both paths.
- ccy's order is pingbus seat exec > wrapper > claude (`entrypoint.sh`, the final
  `exec "${_ccy_seat_exec[@]}" "${_ccy_wrapper[@]}" "$@"`), so cc-claude exec'ing the
  supervisor gives the host the same chain.
- The project's `ccy.env` arms the supervisor with a `/workspace/...` path, which does not
  exist on the host, hence SPEC S8's path rewriting.
- No Go code reads ccy.env today (`internal/ccyenv` answers only whether CCY is installed).

## 12:11 · decision · —   — four defaults for the owner

Four defaults recorded in PLAN.md Technical Decisions, each open to the owner before Phase 2:

1. An older supervisor than 3.71.0 is refused on every path, naming `cc --no-supervise`
   (warning and wrapping harms other sessions; unwrapping on the default path is skip and
   continue). Cost: cc stops in other host projects until their daemon is upgraded.
2. ccy.env / ccy.env.local are read in Go, never sourced, and may only name the project's
   own supervisor; any other wrapper must come from the operator's environment.
3. `--supervise` outranks the project files (in ccy a plain assignment in ccy.env beats it).
4. The logic is in cc-claude; the default runs the daemon's `sh` launcher; no ast.parse
   probe, since the release check already reads the file.
