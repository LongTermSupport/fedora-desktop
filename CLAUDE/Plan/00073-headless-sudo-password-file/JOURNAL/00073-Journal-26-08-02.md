## 07:50 · finding · — — password sudo is already supported; only HEADLESS refuses it

The trigger is external: lts-infra Plan 00031 needs this runbook to provision a CI runner host
whose provisioning user must NOT keep `NOPASSWD:ALL`. The owner asked whether passwordless sudo is
*necessarily* required rather than letting it be assumed. Measured at `e67abde`:

- **Interactive** (`run.bash:1203`, `:2213`): probes `sudo -k -n true` and falls back to
  `--ask-become-pass`. Password sudo works today.
- **Headless** (`run.bash:193-195`): `headless_fail "Passwordless (NOPASSWD:ALL) sudo is
  required"`. A hard stop — because `--ask-become-pass` prompts and there is no TTY.

So the constraint belongs to the headless PATH, not to fedora-desktop. That reframes the work from
"remove a requirement" to "add the missing non-interactive equivalent of a branch that already
exists".

## 07:50 · finding · — — the askpass idiom is already in this script

`hl_ssh_agent_start` (`:222-248`) writes a `0600` secret file plus a `0700` helper from a **quoted**

## 08:00 · action · T1.1 — acceptance.bash written first, RED by design

Five legs: one regression (Plan 00063's gate 10 must still fire) and four new gates. Currently
1 pass / 4 fail, because the feature does not exist — which is the RED phase working.

Built on `_planlib.inc.bash` (`plan_mode gather`, one `plan_gather_leg` per case, `plan_finish`

## 08:00 · finding · T1.2 — the harness could not tell its own cases apart

The RED run failed the four new gates, which is what I wanted to see — and I nearly stopped there.
Reading the actual output rather than the tally:

```
[FAIL] exit 1 but missing message: RUN_BASH_SUDO_PASSWORD_FILE
       got: … Passwordless (NOPASSWD:ALL) sudo is required
            (sudo: run.bash: line 193: sudo: command not found)
```

**`sudo` is not installed in a CCY container at all.** Every case — all five — produced
byte-identical output, because run.bash's probe dies on the missing binary long before any
credential logic. Which means the regression leg's PASS was a **false pass**: it asserts the
message contains `NOPASSWD`, and it did, in a message emitted for entirely the wrong reason.

The consequence if I had not looked: after implementing the feature, this harness would have kept
reporting the same 1-pass/4-fail — or worse, been "fixed" until green — while proving nothing
whatsoever about the gates. `bash-standards §9`: *a control that FIRES is not necessarily a
control that DISCRIMINATES*, here inside the very thing whose job is discrimination.

Fixed by refusing outright when `sudo` is absent, rather than reporting results it cannot stand
behind. That is the same decision Plan 00072 reached for the rootless-engine guard — an
environment whose answer cannot be obtained has not given a safe answer — and it is satisfying
that the precedent already existed in this repo.

## 08:00 · correction · T1.2 — the refusal probe was broken in the same class, one line below

Having written a paragraph about controls that fire without discriminating, I wrote a probe that
did exactly that:

```bash
drop_run env -i PATH=… command -v sudo        # WRONG
# → env: 'command': No such file or directory
```

`command` is a shell **builtin**, so `env` cannot exec it — the probe fails identically whether or
not sudo exists, and would have refused on every host including the ones this feature is for.

What caught it was reading the refusal's **stated reason** in the run log rather than its exit
code. The exit code was 1 and the banner said "sudo is not available", both of which were
consistent with the belief I already held. The parenthesised reason was not.

Now `bash -c 'command -v sudo'`, and proven by two controls rather than assumed:

```
positive: runuser -u nobody -- env -i PATH=… bash -c 'command -v bash'  → rc=0, /usr/bin/bash
negative: runuser -u nobody -- env -i PATH=… bash -c 'command -v sudo'  → rc=1, (empty)
```

The mechanism works AND the absence is real. Refusal message now reads `(not found)` instead of
the bogus `env: 'command'` error.

## 08:15 · decision · T2.2 — the sudo askpass helper deliberately does NOT copy the ssh one

`hl_ssh_agent_start` exports `HL_SSH_PP_FILE` and its helper reads that variable at askpass
runtime. The obvious move was to mirror it exactly — reuse of a proven local idiom is the whole
argument for this design.

I did not, and the reason is worth recording because "consistency" would have been the easier
call. The ssh variant depends on ssh-add propagating the caller's environment to the askpass
child. That is **proven on this path** — the code has run. Whether *sudo* does the same is not,
and cannot be measured in a container. If it does not, the failure is silent in the worst way: an
unset variable means `cat ""`, an empty password, and a wrong-password error that sends the
operator to check a file that was correct all along.

So the sudo helper interpolates the path with `printf %q` instead. The path is not secret either
way — the property the quoted heredoc buys (the password never enters the helper's text) is
preserved exactly. What changes is that the mechanism has no unverifiable dependency.

## 08:15 · finding · T2.4 — removing `2>/dev/null` from the ansible probes improved the message

Both ansible sites ran `if sudo -k -n true 2>/dev/null`. The redirect is banned by this repo's own
rules and I was editing the lines anyway, so the probe now captures into `_sudo_probe`. That
forced a small question — an unused capture would be SC2034 — and the answer improved the code:
the captured reason goes into the "sudo needs a password" message the user already sees. The
constraint produced a better result than the version that satisfied it trivially would have.

The new branch is checked **first** at both sites, so `sudo -k` never runs on the password path.
Not cosmetic: `-k` would discard the timestamp `hl_sudo_probe_password` just established, making
Ansible re-authenticate for no reason.

## 08:15 · finding · T3.2 — Success Criterion 2 was assertable but not measurable, until it was

*"A headless run on a NOPASSWD box behaves byte-identically — proven, not assumed"* reads like
something only a host can show. In a container it reduces to one checkable claim: the argv `_sudo`
constructs. That needs no sudo binary at all, so it belongs in the container half — and the
harness had been built as though every leg needed a real sudo, which is why it was structured to
refuse wholesale.

Restructured into two groups: A (inertness, runs anywhere) and B (the credential gates, needs a
real sudo). Group B now records a REFUSED leg via `plan_finish` instead of `exit 1`-ing before any
leg runs, so the refusal is reported *alongside* group A's results and still drives a non-zero
exit. A check that did not run has not passed.

Two details in group A that are the point rather than decoration:

- The `_sudo` definition is **extracted from run.bash**, not copied into the test. A copy proves
  only that the copy works. An `awk` matching nothing emits nothing and exits 0, so the extraction
  asserts content and the presence of `HL_SUDO_OPTS` before running it.
- argv renders as `[a][b][c]`. The defect being excluded is an **empty argument**; in any
  unbracketed rendering it vanishes into whitespace and `sudo "" dnf …` looks identical to a
  correct call. The rendering is doing real work.

## 08:15 · finding · T3.2 — discrimination proven by perturbation this time, before being claimed

Twice this plan I have written a control that fired without discriminating. So rather than assert
group A works, I perturbed the one thing under test in fixtures and measured which legs fail:

```
shipped     EMPTY opts rc=0  [OK]  sudo [dnf][-y][install][git]
shipped     -A    opts rc=0  [OK]  sudo [-A][dnf][-y][install][git]
colondash   EMPTY opts rc=1  [FAIL] want [dnf]…  got [][dnf][-y][install][git]
colondash   -A    opts rc=0  [OK]  sudo [-A][dnf][-y][install][git]
absent      EMPTY opts rc=1  [FAIL] could not extract _sudo() … got: <empty>
absent      -A    opts rc=1  [FAIL] could not extract _sudo() … got: <empty>
```

`colondash` fails **only** the empty-opts leg, with exactly the predicted output, and the `-A` leg
still passes — because `[@]:-` is harmless on a non-empty array. That surgical signature is the
one §9 asks for; the failure mode it rules out is the uniform wrong exit code across unrelated
assertions, which proves nothing about any of them. `absent` trips the extraction guard with its
own distinct message rather than passing.

A third leg asserts the `[@]:-` claim directly against bash. Without it, the only reason `_sudo`
looks different from its `rm -f` neighbour is an assertion in a comment — and a comment is not a
test. If bash ever changed that behaviour, the leg says so instead of the comment quietly becoming
false.

## 08:15 · finding · — — a pre-existing false negative found in passing; raised, NOT bundled

`_sudo grubby --info=ALL 2>/dev/null | grep -q …` decides whether legacy cgroup args are present.
When grubby *fails*, stderr is discarded, stdout is empty, the grep finds nothing, and the script
prints `No legacy cgroup configuration found` — a check that could not look, reporting what a
check that looked and found nothing reports. Exactly this plan's family of defect.

I changed the `sudo` token and left the redirect. Fixing it properly means aborting where the
interactive path currently continues, and a box without a bootloader would then fail an install
that works today. That is a real decision with its own regression risk, and bundling it under a
sudo-credential plan would hide it in a diff nobody is reviewing for that. Recorded as open
question 2 instead. Noting it and moving on is the failure mode here, so it is written into
PLAN.md where it survives this session rather than only into this entry.
