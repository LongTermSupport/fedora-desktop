## 21:15 · finding · — — a challenge to one word found a check that was never a check

The owner queried a Plan 00068 line citing `/root/.claude`, then said plainly: *"we're not
running ccy as root!"* They were right, and chasing why produced this plan.

Established from source, not from my summary:

- `claude-yolo:1177-1183` **already refuses to run as uid 0**. ccy is not run as root.
- The image sets no `USER`, so the process is uid 0 *inside* the container — but podman here is
  rootless (Plan 00068 triage: `rootless: true`), so that maps to the invoking unprivileged host
  user through a user namespace. `/root/.claude` is the in-container HOME of a mapped-
  unprivileged identity, **not** host root.

I was one sentence from writing "the container runs as root" — the same narrow-scope-stated-as-
world error for the fourth time today. "uid 0 in the container" is true; "running as root" is
false, and the userns is the entire difference.

**The real finding is `claude-yolo:1208`:**

```
# Podman running as non-root is inherently rootless - no check needed
```

An inference standing in for a check: it reasons about the **client** and concludes about the
**engine**. A non-root user can still drive a rootful engine — `CONTAINER_HOST` / `DOCKER_HOST`
pointed at a system socket, or a docker context. Then container uid 0 is real host root, while
ccy bind-mounts the project and runs `--dangerously-skip-permissions` inside it.

The docker branch at `:1188-1206` fails the same way from the other side: it compares a **context
name** to the literal string `rootless`. A context can be named anything regardless of where it
points, and `DOCKER_HOST` overrides context entirely.

The fix is not a better inference. **Ask the engine.**

## 21:25 · decision · T1.1 — unknown REFUSES, and the pure function moves house

Verdict is three-valued — `rootless` / `rootful` / `unknown` — and only `rootless` proceeds.

Not defensive padding. Plan 00068's group-F probe **measured** this exact failure mode hours ago:
asking podman for an absent label returns **exit 0 and zero bytes**, so comparing two unknowns
returns *equal* and reports the safe-sounding answer having measured nothing. A rootlessness
check has the same shape — `info` can fail, print nothing, or print a field that moved. If empty
read as "fine", the guard would pass hardest exactly when it can see least.

**Task 1.1 as first written was wrong.** I specified `common.bash`, then found `common.bash:36-40`
calls `exit 1` at file scope when the engine is not on `PATH`. A test sourcing it would need a
container engine installed in order to test a function whose entire purpose is needing none.
`common-pure.bash` states the contract in its own header — *"ONLY pure helpers … safe to source
from any host shell without triggering a podman-check exit"* — so the decision lives there and
the querying wrapper `engine_assert_rootless()` stays in `common.bash` with `container_cmd`.
`PLAN.md` corrected in place.

**No override flag**, deliberately. An escape hatch here is precisely the `_armed` shape the
project bans: a precondition is asserted, not offered.

## 21:40 · action · T2.1/T2.3 — RED first, then a perturbation because green proves nothing

`scripts/test-ccy-rootless-guard.bash` written before the implementation. RED was specific:
*"engine_rootless_verdict is not defined after sourcing … (the guard is absent, not merely
broken)"* — absent and broken want different fixes, so the message distinguishes them.

Implemented; 15/15 green. **Green is the dangerous part**, so I perturbed the one thing under
test — flipped podman's `false) → rootless`, the most damaging possible regression (a rootful
engine reported as safe). Prediction stated before running: exactly 2 failures, the rootful case
and the discrimination check.

```
  FAIL  rootful daemon reports false        -> got rootless want rootful
  FAIL  verdicts for true/false are identical — the function does not discriminate
  passed: 13   failed: 2
```

Exactly the 2 predicted, `bash -n` still clean so the failures are semantic rather than the file
being broken, and **13 unrelated cases still passing**. That last part is what makes it evidence:
a suite where everything fails proves nothing about any single assertion, the tell being uniform
failure across unrelated cases. Reverted after.

The in-suite discrimination check earns its place for the same reason — if the function returned
`unknown` unconditionally, all 8 negative cases would pass and the guard would be worthless.

## 21:55 · finding · T3.1 — a Dockerfile comment documenting a control that is not there

`Dockerfile:211`: *"USER directive is NOT set here - we use --user flag at runtime"*.

**No `--user` flag is ever passed.** `DOCKER_FLAGS` is only ever `-i`/`-it`

to state what actually provides it, and to name what the comment used to claim, so the correction
is legible rather than silent.
