## Two independent sweeps, and a credential printed into a report

Ran two sub-agents over the repo for the partial-result class. They overlapped
on four findings and diverged on the rest, which is itself the argument for
running two: neither list is a superset of the other.

**The one that matters most is F8**, and only one agent found it. `pre-commit`
runs static patterns *and* the dynamic denylist built from the gitignored
`localhost.yml`. `commit-msg` runs only the static patterns and then prints
`✓ Commit message looks clean`. So an identifier with no static pattern — an
account alias, a hostname, a service username — is rejected in a staged file and
accepted in a commit message.

That asymmetry is backwards from the one you would choose. A file leak is fixed
by editing the file before pushing. **A commit message is permanent**: there is
no follow-up commit that removes it. The weaker check guards the less
recoverable surface.

**F7 is the other structural one.** The CCY version-bump gate keys on
`files/var/local/claude-yolo/claude-yolo`, and the runtime hash is `md5sum` of
`"$0"`. But the launcher sources six libraries totalling 212 KB against its own
149 KB — most of the program by weight. Measured across history: 71 commits have
touched `lib/`, and **22 touched the launcher not at all**, so they required no
bump and got none. `ContainerRules.md` says "ANY code change requires a version
bump"; the enforcement covers one file of seven. The gate was written when the
launcher *was* the whole program and never followed the code as it moved out.

### The sweep leaked while reporting on leaks

One agent's report quoted the real values it found in `localhost.yml` — account
aliases, machine hostnames, and a **NordVPN service username**, which is a
credential, not merely an identifier. Nothing of that reached a tracked file:
the values exist only in this session's transcript, and every plan entry here
names the *field* rather than the value.

Worth recording as a working practice, because it is not obvious in advance: an
agent asked to audit a secret scanner will read the secrets to test it, and its
report is prose that lands wherever the transcript lands. The brief should say
"name the field, never the value" — mine said to verify findings empirically and
did not say that, and a correct, careful, well-evidenced report is exactly the
thing that then carries the value out.

Flagged to the user for a rotation decision on the VPN credential. That is
theirs, not mine, and it is not something to quietly note in a plan file.

## Phase 1 complete — one scanner, sourced twice (Tasks 1.4, 1.5, 1.6)

`commit-msg` now runs the same private-identifier denylist as `pre-commit`, and
both filter whitelists per TOKEN. The shared code lives in
`scripts/git-hooks/lib/secret-scan.bash`; `play-git-hooks-security.yml` verifies
it exists, because neither hook can run without it.

Extraction rather than duplication was the point. The two hooks did not drift by
accident — they were written apart, and the per-token fix landed in one of them
earlier this same plan while the other kept eating whole lines. A second copy
would have drifted again on the next fix.

### The hole was already exploited, and history proves it

Building the denylist and scanning history turned up a private account alias
published on `origin/F44` in three places: two tracked plan files, and the
commit message of `fc20c5c9`. That message is F8 in the wild — the identical
string in a staged *file* would have been rejected, because the alias has been
in the denylist under `github_accounts` the whole time. `commit-msg` just never
consulted it.

One of the two files is `00049-full-repo-audit/research/security.md`, the audit
that catalogues this repo's leaks and scrubs every other identifier in its own
prose to `<alias-a>` / `<gh-username-a>`. It left this one in plaintext while
quoting a `github_accounts` mapping. Both files are now un-editable without
scrubbing, which is the gate doing its job rather than a new problem.

### Widening the harvest was measured, not assumed

`_account` → `_accounts` (and the other plural spellings) is a one-word change
that could have blocked every future commit: a short, common-word token in the
denylist would match everything. So it was measured against the real
`localhost.yml` before being believed — 8 tokens to 10, the two new ones present
in zero tracked files and zero of the last 300 commit messages. The one field
the widening added is `lastpass_accounts`, previously harvested by nothing.

Numbers only. Every entry in this plan names the FIELD, never the value.

### The gate caught me committing the sibling defect inside the fix for it

`_hook_grep_v` was written as `if out=$(grep "$@"); then …; fi` followed by
`rc=$?`. That reads the status of the **if statement**, which is zero whenever
no branch ran — so the `rc > 1` arm was unreachable and every grep error would
have been reported as "nothing matched". A broken whitelist regex would have
silently emptied the match list and passed the commit.

It was caught by this repo's own `bash-status-after-block` semgrep rule, in a
file I had already unit-tested — the tests passed because the error path was
dead, which is what dead error paths do. Check 10 now drives a deliberately
broken regex through the filter so it cannot go dead again.

### Acceptance: 10 checks, and the claim is now re-runnable

`acceptance.bash` gained `--hooks-dir DIR`, so "these checks fail against the
unfixed code" stops being an assertion and becomes a command:

    acceptance.bash                          # 10/10 PASS
    acceptance.bash --hooks-dir <pre-plan>   # 7 of 10 FAIL

Measured against `0369468b~1`: checks 1, 2, 5, 6, 7, 9 and 10 fail there.
Checks 3 and 8 pass in both — they exist to stop the fixes over-correcting into
false positives, and a check that passes everywhere is worth saying so about.

### The scanner rejected the commit that fixed it

Check 10's first draft hardcoded a plausible-looking address into
`acceptance.bash`, and `pre-commit` refused the commit. The file's own header
already states the rule — build leak tokens at RUNTIME from fragments, so this
tracked file never contains a plausible address — and I broke it two hundred
lines below writing it. Reusing `$LEAK` was the fix. Worth recording as a pass
of the gate rather than a nuisance: the block was correct, immediate, and about
the file whose whole subject is not doing that.

## Task 1.7 — "the CCY script" is seven files (F7)

`CCY_HASH` was `md5sum` of the launcher. The launcher sources six libraries, and
those six are the larger half of the program — 212 KB against 149 KB. So the
runtime integrity check and the `pre-commit` version-bump gate both watched the
smaller half, and the history says exactly what that cost: **71 commits touched
`lib/`, 22 of them without touching the launcher at all.** Those 22 required no
bump, got none, and `validate_ccy_integrity` reported a match throughout.

This is the plan's defect class in its purest form. Nothing failed. The hash was
computed correctly, compared correctly, and reported correctly — over a subset,
with a result shaped exactly like a complete one. The launcher *used to be* the
whole program, and the check never learned otherwise.

### The fix names the program once

`CCY_LIBS` is declared next to `SCRIPT_DIR` and now drives three things that had
been three separate lists: the presence check, the load order, and the hash. The
five-name loop and the hash formula could previously disagree about the library
set without anything noticing — which is how this kind of gap opens in the first
place.

Proven rather than assumed, with the same lib-only edit applied twice:

    new formula:  3d01ae52e4c3a433 -> 8d5ca1d54fc8e2b5   (moves)
    old formula:  unchanged                              (blind)

### The version lives in the launcher, and that falls out of the gate

A `lib/`-only commit cannot bump `CCY_VERSION`, because the variable is not in
any file it stages. Rather than special-casing that, the gate leaves
`STAGED_VERSION` empty when the launcher is not staged and fills it from HEAD —
so the versions compare equal and the commit is rejected with a message saying
to stage the launcher too. One less branch, and the rule states itself.

### Accumulated drift needs no separate decision

The plan asked whether to bump once for the 22 lib-only commits. It answers
itself: 3.41.0 *is* a version change, so every saved launch configuration
reconfigures once on the normal upgrade path. There is nothing extra to do.

### Acceptance is now 13 checks

Checks 11-13 drive the real hook over a throwaway repo carrying the CCY paths:
lib-only-without-bump rejected, lib-with-bump accepted, launcher-only-without-bump
still rejected. The middle one matters as much as the first — a gate that
blocked every `lib/` commit regardless would "pass" check 11 while being
unusable.

Against the pre-plan hooks: **8 of 13 fail** (1, 2, 5, 6, 7, 9, 10, 11). Checks
3, 8, 12 and 13 pass in both, and the coverage line says so rather than leaving
a reader to assume every check is a regression guard.

Sharper still: QA.md's own "For Python files that use external libraries" section

### One library, two exclusion lists — and why not one

The discovery library is now shared by all three source gates and renamed
`scripts/qa-discovery.bash`. The obvious move was to share the exclusion list
too. That would have been wrong: the shell list excludes the whole `.claude/ccy`
tree, and `.claude/ccy/claude-supervise.py` is tracked, repo-owned, and currently
gated. Unifying would have silently **removed** a file from coverage — this
plan's own defect, committed inside the fix for it, for the second time today.

So: one mechanism (`_qa_path_in_dirs`, `_qa_first_line`), two lists as data. The
mechanism is what drifts; the data is what differs.

Verification is the file count itself: bash stayed at exactly 165 across the
rename, python went 35 → 41, and the repo total went 528 → 534.

## Tasks 2.4 & 2.5 — and the day's best lesson, which came from getting it wrong

### A coverage loss hid inside a rising count (F14)

`qa-ansible-syntax.bash` hardcoded its population to `playbooks/imports/` plus
the entrypoint, so `playbooks/dev/play-collect-diagnostics.yml` — the play you
run *during an incident* — had never once been parsed. Neither had a plan-local
repair playbook. The 2.19 hazards in AgentNotes are caught by this gate and by
nothing else: PyYAML accepts what ansible-core rejects.

So I replaced the hardcoded path with a derived population: every YAML in the
repo with a top-level `- hosts:`. The count went **78 → 79**, which reads as
exactly what you want to see.

It was a loss. `playbooks/playbook-main.yml` contains no play of its own — it is
all `import_playbook:` — so the new predicate did not match it, and the single
most important playbook in the repo silently left the gate. The +1 was two files
gained and one lost, and the most important one was the one lost.

Every other instance this week has been a number that looked *complete*. This one
looked *improved*. I caught it only by listing the population instead of reading
the total — which is now what the gate's own pass line does:

    ✓ ansible-syntax: 80 playbooks OK (77 under playbooks/imports/, 3 elsewhere)

A count you can only compare against your memory of last time's count is not
evidence. A breakdown that names the buckets is.

### The over-match announced itself in sixty seconds (F10)

`failed_when: no` earned a green tick on the repo's #1 rule, because the regex
accepted `yes` for `ignore_errors` and only `false` — never `no` — for
`failed_when`. Both spellings are valid YAML booleans; the asymmetry lived
inside a single line.

One spelling list now drives every directive. The first version of it reported
**10 violations** against legitimate `failed_when: not foo.stat.exists` probes,
because `no` matches inside `not` — fixed with a trailing `\b`.

That mistake is worth keeping, because it is the asymmetry this plan keeps
running into, demonstrated live: the over-match printed all ten offending lines
on the first run and was fixed in a minute. The under-match it replaced printed
nothing and sat there indefinitely. The direction that feels dangerous while
you are writing is the one that shows you what it did.

### Making the instruction true rather than softening it (F11)

QA.md said "ALWAYS and ONLY use `./scripts/qa-all.bash`" and "NEVER use
individual scripts directly", then documented `qa-helper-tests.bash` and
`check_extension_compat` as gates `qa-all.bash` did not run. Anyone following
the rule as written got `✓ QA passed` over a `helpers/` change with its 161-test
suite unexecuted.

Two ways to close that: run them, or stop claiming qa-all is sufficient. Running
them is the one that makes the instruction people actually follow the correct
one — and both are fast (0.06s and a static check). They print a pass line for
the same reason the drift gate does: a gate whose only visible output is a
failure is indistinguishable from a gate that is not running, which is precisely
how these two spent months documented but unrun.

## Task 2.3 — Plan 00094's failure mode, inside the gate built to catch it

`qa-deployed-drift.bash` compared `files/home/.local/bin/<name>` against
`~/.local/bin/<name>`. The deployed name is not always the repo name:
`git-account-helper.j2` deploys as `git-account-helper`. So the gate looked for a
`.j2` in `~/.local/bin`, never found one, skipped the file, never incremented
`CHECKED` — and the pass line still read "N deployed script(s) match the repo".

That is exactly Plan 00094 — repo says fixed, host runs something else, nothing
sees it — reproduced inside the gate written to catch Plan 00094, on the one file
in its scope it could not see.

### Disclosure, not a fake comparison

A rendered template cannot be byte-compared against its source; the entire point
of `{{ user_login }}` is that the two differ. There is no honest byte comparison
to make, so the fix is not to invent one:

- the template is **counted separately and named in the summary**, so a reader
  can see what was not compared;
- what IS checked is that a playbook actually deploys it under the stripped name.
  A template that maps to no `dest:` **exits 2** — that would be a file the gate
  passes over having compared nothing, which is the whole defect;
- the summary now also states how many scripts are not installed on this host,
  because "2 match" and "2 match, 35 not installed" are very different sentences
  and the gate was only ever printing the first.

Exercised against a fake host tree rather than argued:

    pass:              2 compared; 35 not installed on this host; 1 template not byte-comparable
    drifted file:      exit 1
    unmapped template: exit 2

This is the AgentNotes rule "disclose rather than block when the gap is
unknowable" applied literally: the gap here is genuinely unfixable by comparison,
so being *quiet* about it was the defect, not the gap itself.
