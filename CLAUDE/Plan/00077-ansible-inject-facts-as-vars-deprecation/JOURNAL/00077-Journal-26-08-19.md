## Found in deploy output, which is the wrong place to find things

Deploying Plan 00074's ccy library, the play printed:

    [DEPRECATION WARNING]: INJECT_FACTS_AS_VARS default to `True` is deprecated,
    top-level facts will not be auto injected after the change. This feature will
    be removed from ansible-core version 2.24.
    Origin: playbooks/imports/play-claude-yolo.yml:291:15

Nobody was looking for it. It was on screen only because a deploy happened to be
running with output visible, on a play that happened to contain one of the
eleven references. That is the whole argument for Task 2.1: the finding was
luck, and luck is not a gate.

### What it actually costs when it lands

Not a warning that goes away — the name stops resolving. `ansible_env.HOME`
becomes an **undefined variable**, which errors the task at runtime, on the
machine, after earlier tasks in the same play have already changed system state.
A play that half-ran is worse than one that never started.

Host is on 2.19.12 and `ansible.cfg` does not set the option, so there is time.
There is no reason to spend it.

### Small surface, checked before assuming

Eleven live references, three fact names, seven playbooks. Two further hits were
in comments and are not references — worth confirming rather than counting,
because a grep total that includes prose overstates the job and then the "fix"
edits documentation into nonsense.

Two of the sites are bare expressions in `assert: that:`, not `{{ }}` templates:

    - ansible_distribution == 'Fedora'

Same substitution, different syntax context, and easy to miss if you grep only
for `{{`.

### The fix that would have been wrong

`inject_facts_as_vars = False` in `ansible.cfg` looks like the one-line fix and
is the opposite. It is the **test**, not the remedy — set it before converting
the references and every affected play breaks at once; set it after and it adds
nothing 2.24 will not do anyway. Recorded as Decision 1 and used instead as a
one-shot proof via `ANSIBLE_INJECT_FACTS_AS_VARS=False` on a converted play,
leaving `ansible.cfg` untouched.

### The style guide was teaching the deprecated form

`CLAUDE/AnsibleStyle.md`'s own "Preflight Assertions" example used
`ansible_distribution == 'Fedora'`. Fixing only the playbooks would have left the
documentation and the new gate contradicting each other, with the documentation
winning every time someone copied the example. Updated, with the rule and the
three concrete substitutions written out.

### The gate, and why it is keyed the way it is

`qa-ansible.bash` Check 5 matches a **known fact-name list**, never the
`ansible_` prefix. Prefix-matching would flag `ansible_facts` itself — the thing
we are migrating *to* — plus `ansible_version`, which is not a fact and is not
going anywhere, plus any repo-local variable someone names `ansible_something`
later. A gate that fires on the correct form is worse than no gate; it teaches
people to work around it.

Word boundaries at both ends, so `ansible_distribution` cannot match inside
`ansible_distribution_major_version`. The alternation happens to be longest-first
already, but relying on that would make correctness depend on list ordering
nobody would think to preserve.

Comment-only mentions are skipped, using the same position-relative-to-`#` test
Check 1 already uses for fail-fast prose — so this journal-style discussion of
`ansible_env` in a YAML comment does not fail the build.

Both controls run, because a gate nobody has seen fail is a gate nobody has
seen work:

## Task 2.2 first host run: FAIL, and the failure was the harness

The negative control caught a broken test before it could certify anything.

`ANSIBLE_INJECT_FACTS_AS_VARS=False` **is not a real variable**. Three similar
names are in play and only one of them is the environment variable:

| what                    | string                       |
| ----------------------- | ---------------------------- |
| the setting, as reported | `INJECT_FACTS_AS_VARS`      |
| the ini key             | `inject_facts_as_vars`       |
| the environment variable | **`ANSIBLE_INJECT_FACT_VARS`** |

No "AS", and "FACT" singular. From `ansible-config list`:

```
INJECT_FACTS_AS_VARS:
  default: true
  env:
  - name: ANSIBLE_INJECT_FACT_VARS
  ini:
  - key: inject_facts_as_vars
    section: defaults
```

Ansible ignores an unrecognised `ANSIBLE_*` variable in silence. The control play
ran with injection still on, printed `distribution is Fedora`, and passed. Its
own output carried the give-away — *"INJECT_FACTS_AS_VARS default to `True` is
deprecated"* — the word **default**, meaning nothing had overridden it.

Had the script gone straight to the positive case, `play-rpm-fusion.yml` would
have gone green and Task 2.2 would have been marked proven on a run where the
post-2.24 condition was never applied. The control is the only reason that did
not happen.

Verified both directions in the container (config introspection only — no
playbook runs in CCY):

```
ANSIBLE_INJECT_FACTS_AS_VARS=False ansible-config dump --only-changed
    -> INJECT not listed: the variable was ignored

ANSIBLE_INJECT_FACT_VARS=False ansible-config dump --only-changed
    -> INJECT_FACTS_AS_VARS(env: ANSIBLE_INJECT_FACT_VARS) = False
```

F2 re-confirmed at the same time: `grep -in inject ansible.cfg` returns nothing,
so the setting is on its default and the environment variable is the only lever.

## What changed in the script

- Every occurrence corrected to `ANSIBLE_INJECT_FACT_VARS`.
- New **check 0**, ahead of both plays: `ansible-config dump --only-changed`
  must report the setting as `False`. One command, no play executed, and a wrong
  variable name is caught immediately with the `ansible-config list` incantation
  printed in the failure message.
- Check 1 (the control play) stays. Check 0 proves the setting *resolved*;
  only the play proves it changed *task-time behaviour*, and those are different
  claims.
- If either check fails, the positive case is SKIPPED rather than run — a pass
  from an unproven harness is worth less than no result.

The header comment now states the naming trap explicitly, because the next
person to touch this will reach for the obvious name too.
