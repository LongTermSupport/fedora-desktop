# Task 1.9: a plain memory cap on every Lightning instance

## 1. What was built

- `playbooks/imports/optional/common/play-agent-bus-element.yml`, tag `agent-bus-lightning`:
  - play vars: `agent_bus_lightning_memory_cap` (from host_vars `agent_bus_lightning_memory_max`,
    default `2G`), `agent_bus_lightning_memory_cap_on`, `agent_bus_lightning_app_id` (read from
    `helpers/pingbus/matrix_clients.json`, so the play never spells the app id: rule
    `matrix-client-named-by-hand`), `agent_bus_lightning_cap_file`;

  - a read-only check, before anything is installed: the value is `false` or a whole number with
    K, M or G (rendered with real ansible over `2G`, `512M`, `false` (pass) and `2GB`, `2048`
    (refused));

  - places `~/.config/systemd/user/agent-bus-lightning-capped@.service` always;

  - while on: `~/.config/systemd/user/app-flatpak-<app id>-.scope.d/agent-bus-memory-cap.conf`:

    ```ini
    [Scope]
    MemoryMax=2G
    MemorySwapMax=0

    [Unit]
    OnFailure=agent-bus-lightning-capped@%n.service
    ```

    while off (`false`): that file removed;

  - the existing user-manager daemon-reload now also runs when the notifier unit or the drop-in
    is placed or removed.
- `files/home/.config/systemd/user/agent-bus-lightning-capped@.service`: oneshot,
  `notify-send --urgency=critical` naming the failed scope (`%i`) and the `journalctl` line to
  read why. Precedent: `stt-watch-failed.service`.
- `localhost.yml.dist` and `docs/agent-bus.md` name the key; `meta-deploy.list`'s existing
  entry for this play (`--tags agent-bus-lightning`) gains a Task 1.9 description.

## 2. Decisions and why

- **On for every host that runs the play, not gated like `lightning_diagnostics`.** The play
  installs Lightning on every such host, and the cap is protection, not tracing: the 25 and 26
  Nov runaways reached tens of GB whichever team's instance it was. It is one host-level key
  because a prefix drop-in covers the app's every scope; it cannot differ per team. `false` is
  the off switch.
- **`MemorySwapMax=0`.** `MemoryMax` limits RAM only; with Fedora's zram swap a runaway would
  go on growing into swap (which itself takes RAM) before the kernel kills it. Normal use is
  about 410-650 MB, so no swap at 2G costs nothing.
- **The notice is the scope's own `OnFailure=`, not the Go watch.** The watch runs only while a
  team has `lightning_diagnostics` true, and looks only at instances with a diagnostic log
  (W4), while the cap covers every instance. A pid seen gone with the slice's `oom_kill` risen
  is a guess between two ticks (any app's kill raises the slice's count); systemd's own failed
  state is the event itself. The notice sits in the same drop-in as the cap, so they are on and
  off together. No Go code changed, so there is no Go test; the guard test
  `internal/matrixclients` passes over the new files.
- **No automatic restart**, as the plan says.

## 3. Open

- **The teamchat notice is not built.** The watch posts nothing to teamchat today, and the
  desktop user holds no bus identity by design (agent-bus-lightning L4 refuses one), so it has
  no way to post. How a desktop-user event reaches the team (a seat or the host agent relaying,
  or something else) is a decision for the coordinator; asked by message.
- **The notice cannot name the team.** When `OnFailure=` runs, the scope's processes are gone;
  the scope name carries only a pid. The human sees which window closed.

## 4. Unchecked: the host seat must run these on the laptop after the play

1. `systemctl --version | head -1` (prefix drop-ins for `foo-.scope.d` need systemd 246 or
   later).
2. Close and reopen one Lightning instance, then
   `systemctl --user list-units --no-pager 'app-flatpak-*Lightning*'` to name its scope, and
   `systemctl --user show <scope> -p DropInPaths -p MemoryMax -p MemorySwapMax -p OnFailure --no-pager`:
   want the drop-in listed, `MemoryMax=2147483648`, `MemorySwapMax=0`, and the OnFailure unit.
   Also `cat /sys/fs/cgroup/user.slice/user-$(id -u).slice/user@$(id -u).service/app.slice/<scope>/memory.max`.
3. Whether an instance already running when the play reloaded gained the cap (step 2 on it,
   before reopening).
4. A stand-in kill, nothing of Lightning's touched:
   `systemd-run --user --scope --unit=app-flatpak-<app id>-999999 -- python3 -c 'b = b"x" * (3 * 2**30)'` (every page written, unlike a zeroed `bytearray`)
   then `systemctl --user show app-flatpak-<app id>-999999.scope -p Result --no-pager`
   (want `oom-kill`, if the unit is still loaded), `journalctl --user -u app-flatpak-<app id>-999999.scope --no-pager`
   and `journalctl --user -u 'agent-bus-lightning-capped@*' --no-pager`; the desktop must show
   the critical notification. Then `systemctl --user reset-failed app-flatpak-<app id>-999999.scope`.
5. That a Lightning that quits on its own (close it from its menu) raises no notification (its
   scope ends inactive, not failed).
