## Shape (PlanScriptStandards R1–R14)

R1 filesystem-only bootstrap → `plan_init` → `PLAN_USAGE` → `plan_mode gather` →
`plan_parse_common_flags` (unknown args → exit 64) → `plan_require_host` →
`plan_start_log auto`. No `git rev-parse` anywhere.

The COVERAGE mechanism is the one from Plan 00099's `acceptance.bash`: an `EXPECTED_CHECKS`
array, a `RAN_CHECKS` array, a `check()` registrar that every numbered section calls, and a
verdict printing `COVERAGE: n of m checks executed` that **rejects an incomplete run even
with zero failures**.

Exit status: 0 ACCEPTED, 1 REJECTED, 2 COULD NOT ESTABLISH, 64 usage error.

**Deviation, deliberate and commented in `render_verdict`**: `plan_finish` distinguishes two
outcomes (all legs OK / some failed) and this gate has three, because "could not be
established" must read as neither a pass nor a failure. So the ACCEPTED path ends at
`plan_finish`; the other two call `plan_list_reports` (R10's report listing) and then exit
with the status the printed text says.

No legs are used — the checks are top-level sections so the registrar sees each one directly
(a leg-invoked local function would be SC2317-unreachable, and suppressions are banned).

### Why [8] exists separately from [7]

`helpers/gnome/extension_state.py::classify` returns OK for any state that is not `ERROR` and
not a genuine version mismatch. **`INITIALIZED` and `INACTIVE` therefore pass the play's own
verifier** — and "installed, loaded, not enabled" is precisely the defect this plan exists to
remove. [8] reads the state out of the verifier's own message (rather than issuing a second
query, so the two cannot disagree about which session they looked at) and demands ACTIVE.
Smoke run D confirms the split: [7] PASS, [8] FAIL.

[8]'s buckets: `State ACTIVE` → pass; live session + shell knows it + not ACTIVE → **FAIL**;
`pending_scan` / `pending_reload` (needs a logout) or `skip_no_session` → COULD NOT ESTABLISH,
never a pass.

## Verification performed

In the container, via a throwaway scratch harness that sourced the library, blanked
`PLAN_CONTAINER_MARKERS` and sourced a copy of the gate, with stub `gsettings` /
`gnome-extensions` / `gnome-shell` on PATH and a fixture extensions tree. All fixtures and the
fake run directories were deleted afterwards; `git status` shows only the new script.

- all 9 declared present and ACTIVE, triage pair with no removal, matching checker →
  **ACCEPTED, exit 0, COVERAGE 10 of 10**
- short enabled list, `disable-user-extensions=true`, a removal between the two triage
  reports, drifted deployed checker → **REJECTED, exit 1**, five failures, each naming its
  remedy; the removal was identified by UUID
- shell knows every extension but State is INACTIVE → [7] PASS, **[8] FAIL**, exit 1
- one UUID unknown to the shell (`pending_scan`) → [8] COULD NOT ESTABLISH, **exit 2**
- `gsettings` and `gnome-extensions` genuinely absent → check [0] FAIL,
  `NOT RUN: 1 2 3 4 5 6 7 8 9`, **exit 1**

**A real defect was found by that last scenario and fixed.** Behind the
`dbus-run-session --` prefix the helpers use when there is no live bus, a missing binary comes
back as the wrapper exiting 127 — indistinguishable from "there is no session", which is a
legitimate result. The gate was downgrading a missing tool to an unproven check, which is the
same conflation this plan fixed one layer down (`pending_scan` vs `skip_no_session`). The
probe now checks `shutil.which` for both tools first and fails loudly as an IaC gap, naming
the play that installs them.

A second, smaller fix from the same pass: [7] originally PASSED when the verifier had reached
no session at all (`skip_no_session` exits 0 by design, so "nothing failed" was a pass over
extensions nobody looked at). It now reports COULD NOT ESTABLISH in that case.
