## 08:55 · action · P1 — Phase 1 landed: the enabled list is declared state

The fix is two helpers and three task edits in `play-gnome-shell-extensions.yml`.

`helpers/gnome/enabled_extensions.py` is the pure half. It parses the GVariant `as`
literal `gsettings get` prints (`@as []`, `[]`, `['a', 'b']`, escapes and all), merges the
deployed UUIDs into it **additively** — nothing the user enabled is ever removed — formats
the result back, and discovers which UUIDs are deployed by reading each `metadata.json`
rather than trusting the directory name. A disagreement between the two is an error, not a
skip: GNOME Shell refuses to load such an extension, and skipping it would hand the play a
short list that then passes as "everything deployed is enabled". Same reasoning for a
missing `uuid` key, unparseable JSON, and a UUID containing a comma (the executor reports
the list comma-separated; one would silently become two).

`helpers/gnome/apply_enabled_extensions.py` is the side-effecting half, and the part that
had to be got right:

- **Session bus resolution.** `DBUS_SESSION_BUS_ADDRESS` if set, else the user's
  `$XDG_RUNTIME_DIR/bus` socket, else `dbus-run-session --`. The live socket means the
  running shell sees the change immediately; the fallback means a `run.bash` from a TTY
  still lands the value in the user's dconf database. That fallback is what lets the
  `failed_when: false` go — the no-session case is no longer a failure to tolerate.
- The socket is tested with `os.access`, not `os.path.exists`. `sudo -u` can leave a stale
  `XDG_RUNTIME_DIR` pointing at another user's `0700` runtime directory; the socket is
  visible there and unusable, and falling back succeeds where using it would fail.
- **It re-reads what it wrote.** dconf can accept a `set` and keep the old value (locked or
  read-only database). Without the read-back this task would report ok while the session
  came up with nothing enabled — Plan 00110's finding reintroduced one layer down, which is
  precisely the "check that cannot fail" class the 00110 review found three of.

In the play:

- The `Enable Workspace Names in Overview Extension` task is gone, and its
  `failed_when: false  # FAIL-FAST-OK: GNOME session may not be active` with it.
- `Declare Deployed Extensions Enabled` calls the applier once, after the schemas are
  compiled and the custom extension is copied. `--require workspace-names-overview@fedora-desktop`
  pins the copied extension, so a failed copy fails here instead of reading as "seven
  deployed, all enabled". `changed_when` keys on `GNOME-EXT-ENABLED-CHANGED`.
- `Verify Deployed Extensions Are Healthy` loops over **every** deployed UUID instead of
  the one custom extension it covered before. The list comes from the applier's
  `GNOME-EXT-DEPLOYED` marker, not from re-deriving the play's own literals, which would
  drift the moment an id is added to the installer loop. `extension_state.classify` is
  untouched, so the pending-Wayland-reload rule still holds and `INITIALIZED` still passes
  the play — demanding `ACTIVE` here would fail provisioning for a shell that has not
  rescanned yet. `ACTIVE` is what the desktop scenario demands, after the reboot, which is
  the honest place for it.

Task 1.4 needed no change: `run.bash`'s closing "System Reboot" step recommends a reboot on
every path — the interactive prompt, and both headless messages — so it already covers a
run where this play changed the list.

## 09:00 · thought · P2 — dash-to-dock is deliberately out of scope, and the run will say whether that is right

The play installs `gnome-shell-extension-dash-to-dock` from DNF, which lands in
`/usr/share/gnome-shell/extensions`, not the user directory — so the applier does not see
it and the desktop scenario's `deployed-extensions-active` check does not count it. Two
tasks later the play writes dash-to-dock's `intellihide-mode` dconf key, which does nothing
unless the extension is actually enabled.

That is plausibly the same defect in a second place, but it is not established: nobody has
read that session's `enabled_extensions_live`. Plan 00110's desktop scenario prints it as
evidence on every run, so the acceptance run below will answer it as data rather than
inference. Widening the applier to system extensions before that would be a guess.

## 09:10 · finding · P1 — the check-mode preview my own change would have crashed

`deploy.bash --check` advertises a preview that changes nothing. It would have died instead.
`ansible.builtin.command` has no check mode, so under `--check` the applier is skipped and
never prints its `GNOME-EXT-DEPLOYED` marker — and `Collect Deployed Extension UUIDs` then
dereferences `gse_enabled.stdout_lines` on a skipped task's result, which is an undefined
attribute, not an empty list. The play aborts before it previews anything.

Nothing in the repo would have caught this: `--syntax-check` passes, `qa-all.bash` passes,
and the desktop scenario never runs `--check`. It was found by reading the deploy script's
own promise back against the play.

The `set_fact` is now `when: not ansible_check_mode`, and the verify loop iterates
`gse_deployed_uuids | default([])` — under `--check` there is nothing this run deployed to
verify, and saying so is honest where inventing a list would not be. Both carry the reason
inline; the comment explains why the guard exists, not what it does.
